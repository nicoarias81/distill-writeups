Sshamble: exposiciones inesperadas en Secure Shell

Fuente: «DEF CON 32 - Sshamble: Unexpected Exposures in the Secure Shell - HD Moore, Rob King» · ver el video original

Resumen

El ecosistema SSH vivió su año más agitado en 2024: la puerta trasera de xz Utils dirigida contra las compilaciones Debian/Red Hat de OpenSSH con parches de systemd, la vulnerabilidad Terrapin (ataque de truncado que afectó a casi todas las implementaciones) y la regresión de OpenSSH —un solo bug de reentrada de señal que da root remoto con la configuración por defecto, explotable en horas en 32 bits y en semanas o meses en 64—. Siguiendo esa estela, el proyecto Sshamble nació como escáner de media autenticación para cazar la clave pública de "Jia Tan" por toda internet y terminó como una herramienta open source de investigación que destapó decenas de miles de shells gratuitas.

La clave pública dejó de ser secreta hace años: Ubuntu permite provisionar servidores desde GitHub o Launchpad por nombre de usuario, herramientas como age usan claves SSH para cifrado, y GitHub preserva el campo comentario (suele ser el usuario por defecto). La autenticación SSH es de dos fases —primero el servidor confirma que aceptaría esa clave pública, luego hay que firmar—, y la primera fase no exige private key. Eso permite dos ataques simétricos: una clave contra toda internet (en ~1 hora por máquina individual) o 117 millones de claves de GitHub/Launchpad contra un solo servidor.

Implementaciones como SonicWall, Juniper o Ruckus aceptan auth none y luego piden usuario y contraseña dentro de la sesión SSH ya establecida. Nadie prueba esa capa interior, y ahí se escondían bugs que deberían haberse encontrado hace veinte años:

  • Ruckus: ~36.000 puntos de acceso expuestos; en el prompt de contraseña interna, escribir $(comando) la ejecuta como root pre-autenticación. El fabricante lo había parcheado en silencio, sin CVE ni aviso de seguridad, así que ~900 dispositivos siguen sin actualizar.
  • Digi Transport (gateways ICS): dan shell pre-auth por transición de estados del protocolo; el fabricante recompiló firmware legacy para parchearlo. La reproducción fue un caso Heisenberg: la variable sin inicializar se fijaba al hacer login para monitorizar antes de explotar.
  • Netterbit/Netis y clones: firmware 2018-2023 con shell libre, populares en Irán; más unos 70 dispositivos adicionales sin identificar, incluyendo switches Panasonic de documentación inaccesible.

Envenenamiento de entorno y máquina de estados

Las bibliotecas SSH embebidas en Git forges (Gitea, Gogs, Forgejo, soft serve) aceptan variables de entorno arbitrarias porque delegan el filtrado en la aplicación:

  • Gogs ejecutaba el comando env al recibir una variable: ejecución de comandos directa pre-autenticación. Sin parche (descubrimiento paralelo con Sonar Source, que los adelantó por dos días).
  • Soft Serve (biblioteca charmbracelet sobre gossh) permitía fijar LD_PRELOAD apuntando a shellcode subido vía Git LFS: shell con acceso de solo lectura al repositorio. Parcheado y con CVE.
  • libssh (2018): enviar USERAUTH_SUCCESS desde el cliente seguía soltando shell en servidores sin parchear.

El ataque sistemático —pedir shell entre cada transición de estado, con y sin autenticación, con claves falsas y contraseñas vacías— rinde shells en dispositivos que entregan sesión sin siquiera empezar a autenticar.

El problema de las distribuciones: todos modifican OpenSSH

OpenSSH puro (87% del despliegue mundial) no es lo que corre en los servidores: Debian/Ubuntu acumulan ~36 parches (los que enlazaban con systemd y abrieron la puerta a xz Utils) y Red Hat más de 60, todos con menos escrutinio que el código base. PKIX-SSH, el fork de 2002 para X.509/FIPS que usan los fabricantes que venden al gobierno federal, diverge del upstream en condicionales que ya no coinciden. Y el fork de Windows en el repo de PowerShell cambia 350 archivos: PrivSep reimplementada, telemetría que no se puede desactivar (envía versiones de cliente/servidor de cada conexión SSH a Microsoft, incluidos parámetros negociados dentro de la sesión cifrada) y una reescritura de TimingSafeBcmp que en dos líneas añadidas destruye tres propiedades: deja de ser timing-safe (mira un byte por delante), lee fuera de límites (puntero+1) y permite sustituir la comparación por bytes predecibles del final del buffer. Microsoft no lo consideró elegible para parche ni bounty.

La herramienta

Sshamble (sshamble.com, código abierto) escanea, documenta y da pruebas: detecta forwarding TCP, inyección de entorno, los bugs de Gogs/Ruckus/soft serve, prueba todas las host keys (no solo la primera) contra claves comprometidas, y expone la sesión larval (--interact-first, --interact-auto=none) para fijar LD_PRELOAD, inyectar señales o machacar teclas antes del shell. Efectos secundarios documentados: cambiar accidentalmente contraseñas de servidores (el segundo parámetro de ssh-userauth de SASL es "nueva contraseña"), doxear ~5.000 honeypots (aceptan contraseña byte nulo, algo que ninguna máquina real hace) y dejar ~60 GB de resultados por un escaneo completo de internet.

Conclusiones

  • La recomendación final es simple: usar OpenSSH estable y no tocar nada. Cada modificación "compatible" de la cadena —distros, forks, bibliotecas embebidas— introduce bugs nuevos.
  • La media autenticación es un oráculo de identidad. El protocolo confirma aceptación de claves públicas sin firmar nada; combinado con claves públicas en GitHub, cualquier servidor puede revelar qué usuarios tienen acceso.
  • Lo post-auth es tierra incógnita. Toda la capa de segunda autenticación, señales, forwarding y entorno dentro de sesiones SSH semiabiertas está prácticamente sin auditar, y ahí es donde vive el software más expuesto (firewalls, gateways ICS, APs).
