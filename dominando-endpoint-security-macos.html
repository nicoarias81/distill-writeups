Dominando Endpoint Security: el framework de Apple para herramientas de seguridad en macOS

Fuente: «DEF CON 33 - Mastering Apple's Endpoint Security - Patrick Wardle» · ver el video original

Resumen

Endpoint Security (ES) es la API en C que Apple publicó específicamente para que herramientas de seguridad de terceros monitoreen eventos del sistema y detecten actividad maliciosa. Antes de su existencia, escribir algo tan simple como un monitor de procesos en macOS era una batalla contra APIs no pensadas para eso y contra los cambios de cada versión del sistema. Hoy es el camino recomendado, documentado y en mejora continua por Apple — y tan potente que hasta el malware más sofisticado queda observable mientras actúa.

Este artículo recorre cómo construir un cliente de ES desde cero y luego se adentra en las esquinas oscuras: la caché global de respuestas de autorización (y cómo un cliente sin caché puede saturar el CPU de otro), el campo de scripts que queda vacío cuando el intérprete recibe el script como argumento, los deadlines de autorización cuyo incumplimiento mata al cliente sin reiniciarlo, el muting y la inversión de muting, los eventos nuevos (XProtect, persistencia BTM, modificaciones de TCC, categorías de firma de código en macOS 26) y las limitaciones que conviene conocer antes de diseñar una herramienta completa.

El modelo básico: cliente, eventos y mensajes

Escribir una herramienta de ES son dos pasos conceptuales:

  1. Crear un cliente de Endpoint Security (es_new_client) pasándole un handler block: la función que ES invocará automáticamente cada vez que ocurra un evento subscrito, en cualquier parte del sistema. Verificar el resultado de esta llamada es crítico: falla sin los entitlements, privilegios o permisos correctos.
  2. Subscribirse a los eventos de interés (es_subscribe) sobre una estructura con más de 150 eventos: procesos, archivos, actividad USB, y más, con Apple agregando nuevos en cada versión.

Los eventos vienen en dos sabores:

  • Notificación (notification): llegan después de que el hecho ocurrió. Ideales para monitores pasivos de procesos o archivos.
  • Autorización (auth): llegan antes; el sistema operativo pausa la operación hasta que el cliente responde permitir o denegar. Con auth::exec, por ejemplo, un proceso puede impedirse antes de arrancar.

Cada mensaje entrega, entre otros: el proceso responsable (quién disparó el evento — esencial para distinguir si quien tocó la base de datos del llavero fue el usuario, la app legítima o un stealer), el tipo de evento (los datos son específicos por tipo: PID y ruta para procesos; rutas origen/destino para archivos) y, para los eventos de autorización, el deadline.

La documentación en línea es decente y Apple hasta incluye eslogger, una utilidad para explorar ES desde la terminal — pero el consejo que da cualquiera que desarrolle herramientas en serio es: ignorá la web e id a los header files (es_client.h, es_message.h, es_types.h en el SDK). Prerrequisitos: entitlement, root y Full Disk Access

Apple protege un framework con observabilidad casi total del sistema. El costo de entrada:

  • Un entitlement que hay que solicitar a Apple.
  • Binario notarizado y con entitlement, desplegado a los usuarios.
  • Los usuarios deben ejecutarlo como root y otorgar Full Disk Access a la utilidad (o a la terminal).

Caché de autorizaciones: necesaria, global y con trampas

Para eventos de autorización, la respuesta se envía con es_respond_auth_result, que lleva la decisión y un flag de caché. Con caché activada, ejecuciones posteriores del mismo binario no generan nuevos mensajes.

Un caso real de por qué importa: una herramienta anti-persistencia con modo "bloquear todo lo no notarizado" subscribía auth::exec y verificaba la notarización en cada lanzamiento, sin cachear. Con compilaciones grandes, donde el compilador se invoca una vez por archivo, el CPU se disparaba: ES preguntaba una y otra vez por el mismo compilador confiado. Cachear una vez resolvía todo.

Pero la historia siguió: usuarios con esa herramienta y Jamf Protect instalados vieron el CPU de Jamf irse a las nubes. Razón: la caché de ES es global, y si algún cliente en el sistema no cachea, eso deshace el caching de los demás. Jamf hacía hashing y escaneo YARA (caro) una sola vez gracias a su caché... que el otro cliente invalidaba al no cachear. Culpa compartida: quien no cachea, Apple por hacer la caché global, y cualquier cliente serio debería además implementar su propia caché interna (Apple incluso documenta que la caché se invalida cuando entra un cliente nuevo).

Y la nuance final: la caché se basa en el binario/inode y ignora los argumentos. Si se cachea bash o curl aprobados al instalar Homebrew, un malware que después ejecute curl con argumentos maliciosos no generará evento: mismo binario, misma caché. Regla: no cachear binarios cuyo comportamiento depende de argumentos — curl, python, intérpretes de scripts.

Scripts e intérpretes: el campo nulo

Mucho malware macOS se distribuye como scripts sueltos (Joker Spy en Python, SIGINT en bash). Los eventos de ES están atados al proceso responsable, que para un script es el intérprete — y del intérprete no nos importa nada: queremos escanear el script.

Apple lo resolvió en ES 2.0 agregando el campo script a las estructuras de exec. Con dos verificaciones previas (versión de ES compatible para no crashear en macOS viejos, y campo no nulo), el flujo funciona: ejecutar el script directamente genera el evento con la ruta del script, que se escanea, se detecta como malware y se bloquea.

El problema: ejecutar python script.py (el script como argumento del intérprete) genera el evento con script nulo. El comentario en el header lo dice en una línea: el campo solo es válido si el script se ejecutó directamente, no como argumento. Solución parcial: ante un intérprete, enumerar los argumentos manualmente y tratar como scripts los que sean rutas de archivo.

Deadlines de autorización: responder o morir

Mientras el cliente decide en un evento auth, la operación queda pausada — y Apple no tolera que la experiencia de usuario sufra. Si el cliente no responde a tiempo, macOS lo mata (genera crash report y no lo reinicia: el sistema queda desprotegido).

Datos duros de los headers: el deadline es un mach_absolute_time, "failure to respond: you will get nuked", y varía por mensaje — unos 3-4 segundos para procesos del sistema, ~15 para aplicaciones. No conviene pedirle a Apple que lo alargue.

Dos trampas al implementarlo:

  1. Conversión de unidades: casi todas las APIs de tiempo quieren nanosegundos, y en Apple Silicon no se puede convertir mach_absolute_time a nanosegundos directamente — hay que usar la función auxiliar que Apple provee (documentado en "Addressing Architectural Differences").
  2. Esperar al usuario: si la herramienta consulta al usuario (¿permitir este proceso no notarizado?) y el usuario está distraído, hay que responder programáticamente antes del deadline. Patrón: calcular el delta restante, restar un margen de seguridad, y usar un dispatch_semaphore con timeout justo antes del deadline.

Muting: dominar el ruido

Subscribirse a todos los eventos de archivo satura al cliente por dos razones: el I/O legítimo del sistema es masivo, y la propia salida de la herramienta genera eventos de archivo que generan más salida — un loop recursivo.

  • es_mute_process (audit token) o es_mute_path (ruta): silencian a un proceso. El audit token es la forma moderna de identificar procesos (los PIDs se reutilizan); para obtenerlo desde un PID, task_name_for_pid — siempre con mach_port_deallocate o habrá leak de memoria.
  • Muting de eventos: el mismo es_mute_path con un parámetro de target distingue mutear un proceso o un evento/ruta, cada uno en variantes literal (ruta completa) y prefix (prefijo, útil para silenciar todo lo que va al directorio temporal). Nuance: ES no resuelve symlinks — mutear /tmp en macOS (que es symlink) silencia la ruta pero no los eventos reales; hay que resolver el path antes.
flowchart LR
    M[es_mute_path / es_mute_process] --> T{Target}
    T -->|process literal/prefix| P[Silencia eventos de un proceso]
    T -->|path literal/prefix| V[Silencia eventos hacia una ruta]

Inversión de muting

Para el caso inverso — un monitor de archivos que analiza malware y quiere ver solo los eventos de ese proceso, o proteger el directorio de cookies de Chrome autorizando únicamente al navegador — Apple no agregó APIs nuevas: agregó es_invert_muting, que invierte la semántica de las APIs de mute existentes (lo muteado pasa a ser lo único visible).

Antes de invertir hay que conocer el default mute set: ES silencia por defecto un conjunto de binarios críticos del sistema (para evitar panics y timeouts del cliente). Invertir el muting desmutea todo, incluido ese conjunto. La secuencia correcta documentada por Apple: llamar primero es_unmute_all (desmutea temporalmente el default set) y luego invertir — al mutear todo, el default set vuelve a quedar muteado. Después, cada llamada a es_mute_path sobre el directorio protegido lo "desmutea", convirtiéndolo en lo único observable.

Eventos nuevos que valen la pena

Apple sigue invirtiendo y agregando eventos (declarados al final de la estructura de eventos en es_types.h, con comentarios que indican desde qué versión de macOS — no se backportean; envolver su uso en checks de runtime, p. ej. @available en Objective-C):

  • XProtect::malware_detected (macOS 13): cuando el antivirus integrado de Apple detecta malware, la herramienta también se entera.
  • BTM::launch_item_add: notifica cualquier persistencia como login item, launch daemon o launch agent — el mecanismo de persistencia de la gran mayoría del malware, observable genéricamente.
  • TCC::modify (macOS 15.4): eventos de modificación de permisos TCC. Antes, cuando un troyano como GravityRAT pedía al usuario "otorgame Full Disk Access" para esquivar TCC, ninguna herramienta de seguridad podía verlo. Ahora sí: el evento expresa el acceso concedido, el sujeto (proceso que recibe el permiso) y el instigador. Consejo práctico: como la estructura es compleja y la documentación escasa, usar eslogger con el evento, disparar la acción en System Settings y leer los valores reales.
  • ESCS validation category (macOS 26): ES reporta directamente la categoría de validación de firma del proceso — platform, development, app_store, locally (ad hoc), etc. Antes cada cliente lo deducía por su cuenta con código complicado y costoso en CPU. Diferencia práctica: el malware firmado ad hoc es abundante; el que sale de la Mac App Store (firmado, validado y sandboxeado) es rarísimo.

Limitaciones a tener en cuenta

  • Los eventos no cubren todo lo deseable: TCC::modify solo se emite cuando TCC se modifica. Un malware que verifica si tiene permisos TCC (Joker Spy) o intenta una acción bloqueada por TCC (WindTail intentando capturar pantalla) no genera ningún evento — y justamente el software legítimo rara vez consulta permisos, así que detectar esas consultas sería oro.
  • Solo actividad nueva: ES notifica lo que ocurre después de instalarse. Enumerar persistencia preexistente o permisos TCC ya otorgados no es su trabajo; la herramienta debe hacer ese barrido inicial por otros medios.
  • No cubre redes: para monitoreo de red hace falta complementar con los frameworks de Network Extension. Una herramienta de seguridad completa en macOS suele necesitar más de una tecnología.

Técnicas y herramientas mencionadas

  • Endpoint Security (ES) — framework en C de Apple para herramientas de seguridad de terceros en macOS.
  • es_new_client / es_subscribe — creación del cliente con handler block y suscripción a eventos.
  • eslogger — utilidad de Apple para explorar eventos ES desde la terminal.
  • Header files del SDK (es_client.h, es_message.h, es_types.h) — fuente de verdad documental.
  • es_respond_auth_result — respuesta a eventos de autorización, con flag de caché global.
  • es_mute_path / es_mute_process / es_invert_muting / es_unmute_all — control de ruido e inversión de muting.
  • Audit token — identificador moderno de procesos (los PIDs se reutilizan); task_name_for_pid + mach_port_deallocate.
  • mach_absolute_time — base del deadline de autorización; conversión a nanosegundos distinta en Apple Silicon.
  • dispatch_semaphore — mecanismo para responder antes del deadline cuando se espera al usuario.
  • XProtect, BTM, TCC, ESCS — eventos nuevos: malware detectado, persistencia como launch item, cambios de permisos TCC y categoría de validación de firma de código.
  • Network Extension — complemento necesario para monitoreo de red, fuera del alcance de ES.

Conclusiones

  • Endpoint Security es, por fin, un framework de Apple diseñado para herramientas de seguridad de terceros: con ~15 líneas se arma un monitor de procesos y con eventos de autorización se bloquea malware antes de que corra.
  • La potencia viene con matices que muerden: la caché global de autorizaciones (cacheá siempre, y además implementá caché propia; no cachees intérpretes), el campo script nulo para scripts pasados como argumento, los deadlines que matan al cliente que no responde, el default mute set antes de invertir el muting, y los symlinks sin resolver.
  • Las fuentes de verdad son los header files del SDK, no la documentación web; y eslogger es el atajo para inspeccionar estructuras de eventos nuevos.
  • Conociendo estas piezas, hasta el malware más sofisticado resulta observable en macOS: el trabajo restante del defensor es decidir qué es malicioso.
