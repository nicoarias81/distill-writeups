AI-300 Module 1 — Introduction to Red Teaming AI Systems

Distilled from OffSec AI-300 (OSAI) course material (module 1) — internal training reference, not for redistribution.

Objective

Frame AI systems as an extension of the traditional attack surface and establish the red team methodology used throughout the course: enumerate AI-powered functionality, fingerprint the underlying models and pipelines, and probe them for weaknesses that traditional application testing does not cover. The module is conceptual — no labs — and sets the vocabulary (LLM, inference server, RAG, agent, guardrails) used in later modules.

Target surface

AI functionality shows up in ordinary infrastructure in recognizable shapes:

  • Direct LLM integrations — chat assistants, text generation endpoints exposed via APIs (frequently OpenAI-compatible /v1/chat/completions).
  • Inference servers — Ollama, vLLM, llama.cpp, TGI, LM Studio; often self-hosted and reachable on internal ports (Ollama default 11434).
  • RAG pipelines — LLM + document retrieval (vector store + embeddings + chunking). Attack surface includes the retrieval layer, the indexed corporate documents, and the source metadata returned by APIs.
  • AI agents — LLMs with tool/function calling (web search, code execution, file access, database queries). Each tool is a new injection point.
  • API gateways — Kong, NGINX, AWS API Gateway fronting AI endpoints; expose headers, rate-limit state, and routing artifacts.

Typical lab topology used in the course: web application on .31 exposing an AI chat widget, an API gateway on :8000, chat/model endpoints on .23/.24/.26, RAG knowledge bases on .28/.34, and a SIEM (Kibana on :5601) collecting AI interaction logs.

Techniques

1. AI asset discovery

  • Inventory everything that "thinks": any endpoint accepting natural-language input (chat widgets, support forms, email triage, code assistants) and any backend serving inference.
  • Banner and port fingerprints of common inference servers:
  • Ollama: POST /api/generate, GET /api/tags on port 11434.
  • OpenAI-compatible servers: /v1/models, /v1/chat/completions.
  • LM Studio / vLLM / llama.cpp expose similar OpenAI-shaped routes.
  • Web app JS bundles often name the assistant endpoint in config objects (e.g. assistantEndpoint in chat-widget.js) — always read the shipped JavaScript.

2. Model fingerprinting (conceptual preview, exercised in module 2)

Determine which model family powers an endpoint: direct identity questions, contradiction testing (assert a false creator and let the model's honesty training correct you), knowledge-cutoff probing with era-specific events, behavioral/style analysis, and context-window measurement. Model family matters because jailbreak and injection patterns do not transfer uniformly across families.

3. Threat modeling AI-specific attacks

Map findings onto an AI attack taxonomy:

  • Prompt injection (direct and indirect via retrieved documents) — the AI analogue of injection flaws.
  • Jailbreaks — bypassing safety guardrails; success varies by model family and guardrail implementation.
  • Data leakage — training-data extraction, RAG source enumeration, system-prompt extraction.
  • Excessive agency — agents with tool access performing destructive or out-of-scope actions when steered by injected instructions.
  • Denial of wallet / resource exhaustion — token-heavy prompts driving inference cost, context-window flooding.

4. Where AI differs from traditional appsec

  • Input is natural language: no schema to fuzz against; boundaries are behavioral, not syntactic.
  • Non-determinism: the same payload can yield different results across runs (temperature, sampling); test repeatedly.
  • The "database" is often the model's weights plus an attached retrieval corpus — data extraction replaces data dumping.
  • Guardrails live in multiple layers (system prompt, application middleware, model-level safety training); each layer fails independently.

Detection & defense

  • Log every AI interaction (query, response, sources, session) into a SIEM — module 2 shows attackers reading these same logs to find detection gaps.
  • Keyword-based detection rules (KQL patterns like *what documents*) catch naive enumeration but not semantically equivalent phrasing; combine with rate/anomaly detection and semantic classifiers.
  • Treat AI endpoints like privileged components: auth, rate limiting, egress control for agents, and least-privilege tool permissions.
  • Strip retrieval metadata (chunk IDs, scores, raw snippets) from user-facing API responses — it is an enumeration gift.
  • Deploy canary/honeypot content deliberately (fake credentials in RAG corpora) and alert on their use.

Ares integration notes

  • This module is the framing document: every AI-facing surface found during recon should be inventoried the same way web endpoints are — AIG Infra/Skill/MCP/Agent asset records for LLM endpoints, inference servers, gateways, and RAG systems.
  • Fingerprinting playbooks (module 2) should land in Pikit as an AI-target profile and feed the pentest-ai-recon-fingerprinting workflow.
  • Prompt-injection and jailbreak payload sets from later modules belong in Fickling-adjacent tooling for pickle/agent artifact checks and in ModelAudit for model-file and deployment audits (unsafe serialization, permissive configs, exposed inference servers).
  • Defense findings (logging gaps, keyword-only detection rules) map to detection-engineering backlogs: semantic detection of prompt injection, canary tokens inside RAG corpora, and metadata minimization on AI APIs.
