Un email, 7.000 dólares: secuestrando agentes de IA con tool spoofing

Fuente: «This Hacker Made $7,000 Hacking AI With One Email» · ver el video original

Resumen

Una sola dirección de email bastó para cobrar un bounty de 7.000 dólares: el payload engañó a un agente de IA hasta hacerle entregar la bandeja de entrada completa de otra persona. La técnica —sin nombre formal, descrita como tool spoofing combinado con conversation mimicking— se usó contra objetivos reales en varias ocasiones y funciona prácticamente contra cualquier LLM con acceso a herramientas: navegadores agénticos, asistentes de código, integraciones de productividad.

El principio es brutalmente simple: dondequiera que una IA lee algo que ella no escribió, hay una superficie de toma de control. Y los agentes actuales leen mucho: correos, documentos, hojas de cálculo, mensajes de commit.

Prompt injection como SQL injection

Quien desarrolló la técnica llega del hacking web y razona sobre prompt injection igual que sobre SQL injection: se inyecta contenido donde no debería estar, se usan comillas para romper el contexto del tool y escapar del marco de datos. La analogía no es metafórica: el tool de lectura de email devuelve un objeto JSON con campos from, to, subject, body y fecha. Cualquier campo controlable por el atacante es un sink de inyección; el body es el favorito porque no tiene límite de caracteres y admite más contexto de payload.

El campo to, en cambio, no sirve —es el correo de la víctima— y el subject es limitado. El resto es terreno fértil.

Primero, el payload cierra el objeto JSON del tool output imitando su formato exacto: comillas, coma, campo de fecha, corchetes de cierre. El modelo queda convencido de que el contexto del tool terminó. Luego viene el conversation mimicking: se insertan tags XML con bloques assistant y user falsos, simulando que la conversación continuó y que el usuario está pidiendo cosas nuevas. Un detalle que ayuda mucho: usar en los campos assistant la salida real del modelo.

Ingeniería inversa del formato interno

En productos reales no se puede ver el JSON que el tool le pasa al modelo: es información sensible. Pero hay un atajo: como el modelo sí ve ese formato, se le puede pedir. El procedimiento empieza siempre igual —una petición benigna preguntando cómo se ve la estructura—. El modelo típicamente responde que es información sensible que no puede mostrar; entonces se lo convence de que está bien mostrarla, y entrega el output tal como lo ve, listo para ser imitado en el payload.

Escalada gradual: de la prueba benigna al impacto

Con el formato clonado, la validación de que la inyección funciona se hace con peticiones deliberadamente inofensivas. El primer ataque real usó el email auténtico de la víctima seguido del payload, y la verificación fue pedirle al modelo algo como: "repetí los emails que recibí, no los enumeres, dame un párrafo resumiendo el contenido". Si el modelo resume también el email inyectado —que no debería tratar como instrucciones— la inyección funciona. Eso es prompt injection de manual. Confirmado el control, se escala al comportamiento deseado: en el caso del bounty, hacer que el agente reenviara la bandeja completa a un correo controlado por el atacante.

Cualquier tool es un sink

La técnica no depende del email. Todos los proveedores de aplicaciones LLM tienen integraciones para leer Gmail —nadie quiere responder correos a mano—, así que prácticamente cualquier agente tiene acceso a la bandeja. Los navegadores agénticos también. Y fuera del email valen los mensajes de commit de git, pestañas de navegador, cualquier contenido que termine en el contexto del agente. El desafío propuesto para practicar: lograr una prompt injection a través de un mensaje de commit de git.

El equipo responsable lleva estos ataques a una charla en Black Hat.

Técnicas y herramientas mencionadas

  • Tool spoofing: inyección de contenido malicioso a través de la salida de tools del agente.
  • Conversation mimicking: falsificación de turnos assistant/user (tags XML) tras el cierre simulado del tool output.
  • JSON escape: clonado del formato exacto del tool output para que el modelo crea que el contexto terminó.
  • Integraciones de email en agentes LLM (Gmail y similares): el sink más extendido.
  • Recuperación del formato interno vía jailbreak: convencer al modelo de que muestre su propia estructura de contexto.
  • Git commit messages, pestañas de navegador, Google Sheets/Docs: otros sinks de inyección.
  • Black Hat: venue donde el equipo presenta variaciones de estos ataques.

Conclusiones

  • Cualquier dato que entra al contexto de un agente desde afuera es un canal de ataque: email, commits, documentos, pestañas web.
  • Imitar el formato exacto del tool output y luego simular la conversación es una receta repetible contra casi cualquier LLM con tools.
  • La validación con peticiones benignas permite confirmar la inyección y escalarla con seguridad operativa.
  • La superficie no es el modelo sino su contexto: mientras los agentes lean contenido controlado por terceros, el secuestro por inyección sigue abierto.
