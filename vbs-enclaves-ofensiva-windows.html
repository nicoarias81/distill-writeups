Virtualization Based Insecurity: cuando la fortaleza de Windows se vuelve arma

Fuente: «DEF CON 33 - Virtualization Based Insecurity: Weaponizing VBS Enclaves - Ori David» · ver el video original

Resumen

Virtualization-Based Security (VBS) es uno de los avances de seguridad más significativos de Microsoft en años: usa el hipervisor Hyper-V para crear límites de confianza que ni siquiera un kernel comprometido puede cruzar. Sobre esa base se construyen los VBS enclaves, regiones de memoria aisladas dentro de un proceso donde un atacante con control total del sistema operativo no puede leer ni escribir. La promesa es atractiva: guardar secretos —API keys, contraseñas, claves criptográficas— fuera del alcance de un proceso o kernel comprometido.

Pero toda frontera de seguridad que protege código puede, invertida, proteger malware. La misma memoria inaccesible para los EDR, el mismo flujo de syscalls invisible para los hooks, sirve tanto al defensor como al atacante que consiga ejecutar código dentro del enclave. Este artículo recorre cómo funciona VBS y sus enclaves, y desarrolla varias vías para weaponizarlos: abuso de enclaves debuggeables firmados, explotación de enclaves vulnerables (bring your own vulnerable enclave), la técnica de sleep obfuscation "Mirage", y los usos ofensivos de un enclave ya comprometido: manipulación del proceso anfitrión, ejecución remota en VTL0 y anti-debugging irrompible.

Anatomía de VBS: rings, hipervisor y Virtual Trust Levels

La protección tradicional de los sistemas operativos se apoya en los anillos del procesador: kernel en ring 0, aplicaciones en ring 3. Con el tiempo ese modelo demostró ser insuficiente. El kernel expone una superficie de ataque enorme, y la técnica de "bring your own vulnerable driver" permite a los atacantes cargar drivers firmados con vulnerabilidades conocidas y explotarlos para lograr ejecución en ring 0. Hacía falta un límite de seguridad adicional.

VBS llega a través de Hyper-V. La capacidad esencial de un hipervisor es el aislamiento: impedir que una VM acceda a la memoria de otra. La idea de Microsoft fue aplicar esa misma primitiva al sistema operativo consigo mismo: tomar una región de memoria del SO y aislarla del propio sistema operativo. Así nacen los Virtual Trust Levels (VTLs):

  • VTL0 (normal world): el sistema operativo de siempre, con su user mode (ring 3) y kernel (ring 0). Es el nivel menos privilegiado.
  • VTL1 (secure world): más privilegiado en términos de aislamiento de memoria. El código en VTL0 no puede acceder a la memoria de VTL1; VTL1 sí puede acceder a la de VTL0.

Dentro de VTL1 existen dos modos de ejecución nuevos: el secure kernel (VTL1 ring 0), capaz de imponer políticas al kernel normal, y el isolated user mode (IUM) (VTL1 ring 3), que corre en ring 3 —sin operaciones sensibles de kernel— pero protegido por la frontera de VTL1. Aunque un atacante comprometa el kernel normal, no puede tocar lo que vive en IUM.

VBS enclaves: la mitad aislada de un proceso

Un enclave es una región de memoria aislada dentro de un proceso. El proceso no puede leerla ni escribirle; lo único que puede hacer es invocar los métodos exportados por el enclave. El caso de uso canónico: un proceso maneja un secreto. Si el proceso —o el sistema operativo entero— es comprometido, el atacante roba el secreto de memoria. Si el secreto vive en un enclave, el atacante no puede extraerlo; solo puede pedirle al enclave que opere con él (por ejemplo, pasarle un valor y recibirlo cifrado).

VBS enclaves es la implementación de Microsoft usando VBS, y es deliberadamente simple: se divide el proceso en dos mitades. El proceso normal vive en user mode de VTL0; el enclave vive en isolated user mode de VTL1. Nada en VTL0 puede acceder a los datos del enclave.

Detalles prácticos:

  • Cualquier proceso puede crear un enclave y cargar en él un enclave module: una DLL compilada específicamente para ejecutarse dentro del enclave.
  • La interacción se hace mediante la API CallEnclave, que invoca funciones exportadas por el módulo.
  • No cualquier DLL sirve: para cargarse en un enclave, el módulo debe estar firmado con un certificado de Microsoft designado específicamente para firmar enclaves. Esa firma es la barrera principal —y el blanco de todo lo que sigue.

Cómo meter código hostil dentro de un enclave

Ejecutar malware en un enclave ofrece ventajas inmediatas: memoria que ningún EDR ni analista puede escanear, y un flujo de llamadas API invisible. Cuando un proceso normal llama a una API de Windows, atraviesa las DLL de sistema hasta ntdll y ejecuta una syscall al kernel normal; en ese camino los EDR tienen múltiples puntos de observación. Cuando un enclave llama a una API, el flujo pasa por DLL residentes en VTL1 (ntdll de VTL1, VBS Enclave Runtime DLL) y la syscall la gestiona el secure kernel. Todo ocurre exclusivamente en VTL1: visibilidad cero para productos de seguridad.

El problema es la firma. Vías posibles, de la más simple a la más creativa:

  1. Firma legítima. Microsoft expone el desarrollo de enclaves a terceros; un atacante podría firmar enclaves legítimamente como ya se ha visto con drivers y ejecutables: comprometiendo a un firmante autorizado u obteniendo privilegios de firma mediante una empresa pantalla. Vía realista para actores avanzados o estatales.
  2. Vulnerabilidad en el loader. Explotar la validación de la firma del enclave en el loader de Windows para cargar DLLs sin firmar; algo que Alex Ionescu demostró el año pasado con una vulnerabilidad ya parcheada. Actores avanzados pueden encontrar vías nuevas.
  3. Abuso de enclaves debuggeables. Ver abajo.
  4. Bring your own vulnerable enclave. Ver abajo.

Enclaves debuggeables: una excepción peligrosa

Debuggear un enclave es difícil por diseño: el enclave corre en VTL1 y el debugger en VTL0, así que sin ayuda no hay breakpoints ni lectura de memoria. Microsoft resolvió esto con un flag de compilación que marca el módulo como debuggable. La sorpresa es que el enclave debuggeable no se emula: sigue residiendo en IUM de verdad. Lo que cambia es que el secure kernel implementa excepciones deliberadas: la función de debug read/write memory permite acceder a la memoria si el enclave es debuggeable, y debug protect virtual memory permite cambiar permisos de memoria sobre él.

El abuso se apoya en dos hechos: los módulos de enclave no están emparejados a un proceso específico (cualquier proceso puede cargar cualquier módulo), y los enclaves debuggeables firmados existen o existirán. El ataque: obtener un enclave firmado marcado como debuggable, cargarlo en el proceso propio, usar las excepciones del secure kernel para escribir en su memoria y lograr ejecución en VTL1. Concretamente: obtener la dirección de una rutina exportada del enclave, cambiar los permisos de la página a execute/read/write, sobrescribir la rutina con shellcode, y dispararla con CallEnclave — que solo invoca funciones exportadas, y esa lo sigue siendo.

Hay contrapesos. El acceso a memoria es bidireccional: un EDR puede leer un enclave debuggeable igual que el atacante. Aun así quedan dos ventajas: es una forma de ejecución tan inusual que hoy nadie la detecta, y aunque el enclave sea debuggeable sus llamadas API siguen usando la cadena de VTL1, imposibles de hookear. La limitación práctica es que no se ha encontrado aún ningún enclave debuggeable firmado en la naturaleza —pese a búsquedas extensas en VirusTotal—, pero la adopción de enclaves está creciendo (Microsoft los usa cada vez más internamente) y los desarrolladores cometen errores: es cuestión de tiempo que un módulo debuggeable firmado aparezca público.

Bring your own vulnerable enclave: CVE-2023-36880

La analogía directa con bring your own vulnerable driver: si los enclaves exigen firma, ¿por qué no cargar un enclave firmado con una vulnerabilidad conocida y explotarla? Existe un candidato perfecto: CVE-2023-36880, una vulnerabilidad de information disclosure en un enclave module usado por Microsoft Edge, descubierta por Alex Go del equipo de seguridad de Chrome. Aunque catalogada como fuga de información, las notas del parche admiten que podía llevar a ejecución limitada de código. Es una vulnerabilidad simple que otorga arbitrary read/write sobre el espacio de direcciones del enclave: cargando la versión vulnerable firmada, se puede escribir y leer cualquier dirección del enclave aunque sea un enclave normal, no debuggeable.

Mirage: sleep obfuscation con el enclave como bóveda

La explotación directa choca con una mitigación: los enclaves tienen ACG (Arbitrary Code Guard) por defecto. ACG impide ejecutar código dinámico: no se pueden asignar nuevas páginas ejecutables ni convertir páginas ejecutables existentes en escribibles. Sin ejecución arbitraria dentro del enclave, la cadena clásica —filtrar una dirección del call stack, sobrescribirla con una ROP chain— se complica. (No imposible: el equipo de Outflank —Cedric van Bockhaven y Matteo Malvica— logró paralelamente, sobre la misma vulnerabilidad, un exploit ROP completo que implementa una técnica de sleep obfuscation basada en ROP chain.)

Lo que sí ofrece la vulnerabilidad son dos capacidades inusuales:

  • Escribir datos arbitrarios dentro del enclave. No ejecutables, pero almacenados. Eso convierte al enclave en una bóveda segura para shellcode, configuración de malware o claves de cifrado: nada en VTL0 puede tocarlos.
  • Escribir datos en VTL0 desde VTL1. Disparando la vulnerabilidad al revés, el enclave escribe en el espacio de direcciones normal del proceso. Como la escritura la realiza el enclave, un EDR que monitoree operaciones de escritura sobre regiones de memoria no ve nada: no tiene visibilidad sobre esa interacción.

Combinadas, producen Mirage, una técnica de sleep obfuscation donde el payload pasa la mayor parte de su vida dormido, despierta por un disparador, ejecuta y vuelve a dormirse. El ciclo:

flowchart LR
    A["Cargar enclave vulnerable\nCVE-2023-36880"] --> B["Explotar: escribir\nshellcode dentro del enclave"]
    B --> C["VTL0 limpio:\nmemoria inocente"]
    C --> D["Re-disparar la vulnerabilidad:\nel enclave escribe el shellcode en VTL0"]
    D --> E["Ejecutar shellcode"]
    E --> F["Sobrescribir con datos benignos\ny volver a dormir"]
    F -->|trigger periódico| D

Si un EDR inspecciona el proceso en cualquier momento fuera de la ventana de ejecución, el buffer en VTL0 contiene solo datos benignos y todo el código hostil vive en VTL1, donde no puede entrar. Es casi imposible de detectar por inspección de memoria. El proof of concept está publicado en el GitHub de Akamai.

Vivir dentro del enclave: qué puede hacer el malware una vez dentro

Microsoft restringe muchísimo la superficie de ataque de un enclave: sin operaciones de archivos, sin red, sin interacción con procesos, sin registro. La mayoría de las técnicas tradicionales de malware quedan fuera. Aun así, quedan varias jugadas:

Leer y escribir la memoria VTL0 del proceso anfitrión. El enclave, pese a correr en VTL1, puede leer y escribir el user mode normal de su proceso. Eso permite inyectar un enclave en un proceso remoto y residir en VTL1 monitorizando y manipulando la actividad del proceso de forma —como mínimo— difícil de detectar. Demostración: un programa que hace echo de un string de entrada, con un enclave que vigila el buffer de entrada; cuando detecta el string prohibido lo reemplaza por otro. Lo revelador es el mecanismo: al poner breakpoints sobre todas las instancias de memcpy del proceso, la copia que hace el enclave atraviesa el proceso sin tocar ningún breakpoint, por la evasión de API descrita antes. Interactuar con el proceso así es indetectable por los medios habituales.

Ejecutar código en VTL0 desde VTL1. Ejecutar directamente una dirección ejecutable de VTL0 desde VTL1 está prohibido. Pero CallEnclave es una función de doble uso: además de invocar métodos del enclave desde el proceso, permite invocar métodos de VTL0 desde el enclave, pasando cualquier dirección ejecutable. El flujo: el malware reserva un buffer RWX en VTL0 —última vez que lo toca desde VTL0—, pasa la ejecución al enclave, y desde el enclave invoca el shellcode en el buffer. Desde la óptica de un EDR solo se ve CallEnclave disparándose y luego un thread nuevo lanzando la calculadora: no hay conexión directa entre ambos, lo que ayuda a la evasión (con el matiz de que el código sí corre en VTL0).

Anti-debugging invencible. En cualquier análisis de malware, el analista usa un debugger de VTL0 —kernel mode o user mode—. Un chequeo anti-debug dentro del enclave no puede ser parcheado por ese debugger: no tiene acceso a la memoria del enclave. Sin acceso a APIs clásicas (IsDebuggerPresent, contadores), las opciones desde el enclave son: inspeccionar manualmente el PEB —el enclave tiene acceso a la memoria VTL0— y, si detecta debugging, terminar el proceso; y usar ensamblado inline, concretamente RDTSC, para medir ciclos de CPU y detectar breakpoints y actividad de debugging.

La jugada devastadora es combinarlo con la lógica crítica del malware: mover al enclave una rutina difícil de analizar estáticamente —una rutina de descifrado, o una VM custom— junto con el chequeo anti-debug en la misma invocación de CallEnclave. El resultado es un dilema para el defensor: para ver el comportamiento real y que el código corra, hay que dejar que la ejecución llegue al enclave; en cuanto lo hace, el enclave detecta el debugger y mata el proceso. Bien implementado, la única salida sería un hypervisor debugger o un secure kernel debugger.

Técnicas y herramientas mencionadas

  • VBS (Virtualization-Based Security): aislamiento de regiones de memoria del SO mediante Hyper-V; base de los nuevos límites de confianza de Windows.
  • VTLs (Virtual Trust Levels): niveles de confianza de VBS; VTL0 (normal world) y VTL1 (secure world), con frontera de memoria unidireccional.
  • IUM (Isolated User Mode): user mode de VTL1, ring 3 protegido incluso frente a kernel de VTL0 comprometido.
  • Secure kernel: kernel de VTL1; aplica políticas al kernel normal y gestiona las syscalls de VTL1.
  • VBS enclaves: regiones de memoria aisladas dentro de un proceso, implementadas sobre IUM; solo accesibles vía sus funciones exportadas.
  • CallEnclave: API de doble uso: invoca métodos del enclave desde el proceso y métodos de VTL0 desde el enclave.
  • Enclave modules: DLLs compiladas para enclaves; requieren firma con certificado de Microsoft específico para enclaves.
  • Enclaves debuggeables: flag de compilación que habilita excepciones en el secure kernel (debug read/write memory, debug protect virtual memory) para acceder a su memoria.
  • Bring your own vulnerable driver / enclave: cargar binarios legítimamente firmados con vulnerabilidades conocidas y explotarlos.
  • CVE-2023-36880: information disclosure con arbitrary read/write en un enclave module de Microsoft Edge; permite la técnica Mirage.
  • ACG (Arbitrary Code Guard): mitigación que bloquea código dinámico: prohíbe páginas ejecutables nuevas y páginas ejecutables escribibles.
  • Mirage: sleep obfuscation que esconde shellcode en IUM durante el dormido y lo escribe en VTL0 desde el enclave para ejecutarlo (PoC en GitHub de Akamai).
  • RDTSC: instrucción de ensamblado para medir ciclos de CPU; base del anti-debugging dentro del enclave.
  • Hipervisor debugger / secure kernel debugger: únicas vías de análisis para el esquema anti-debug propuesto.
  • VirusTotal: canal donde eventualmente aparecerá un enclave debuggeable firmado filtrado.

Conclusiones

  • VBS y sus enclaves son una frontera de seguridad real y crecientemente adoptada; el aislamiento funciona y complica la vida del red teamer.
  • Pero la frontera es neutral: la misma memoria inescaneable y la misma cadena de syscalls invisible que protege secretos protege también código malicioso que logre entrar.
  • Las vías de entrada no requieren ser un actor estatal: enclaves debuggeables firmados filtrados y enclaves vulnerables firmados (BYO vulnerable enclave, CVE-2023-36880) son caminos accesibles.
  • Defensivamente, hay que vigilar: CallEnclave inesperado, módulos debuggeables en producción (equivale a no usar enclave), y enclaves cargados por procesos donde no corresponden.
