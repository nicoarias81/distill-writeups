HTTP/1.1 debe morir: el endgame del request smuggling

Fuente: «DEF CON 33 - HTTP 1 1 Must Die! The Desync Endgame - James 'albinowax' Kettle» · ver el video original

Resumen

HTTP/1.1 tiene un defecto fatal: el aislamiento entre requests está fundamentalmente roto. No existe una forma única y confiable de saber dónde termina una petición y empieza la siguiente, así que la mínima discrepancia de parsing entre el front-end y el back-end habilita un desync —request smuggling— que puede derivar en el secuestro total de un sitio. Esto se conocía desde 2019, cuando la clase de ataque ya permitió tomar control persistente de la página de login de PayPal en dos ocasiones.

En seis años la industria no arregló el protocolo: parchó las herramientas de detección con regular expressions, adoptó HTTP/2 solo del lado del cliente y sigue degradando a H1 en el tramo hacia el origen, lo que empeora la amenaza. El resultado es el "desync endgame": los sitios parecen seguros, pero con el más mínimo cambio en la técnica vuelven a ser explotables. Un caso emblemático: durante un período, si se testeba cualquier sitio detrás de Cloudflare con la técnica correcta, no se encontraba nada —pero si se olvidaba un cache-buster, se causaba un desync dentro de la propia infraestructura de Cloudflare y se podía comprometer persistentemente prácticamente todos los sitios que la usan: unos 24 millones.

Este artículo recorre el toolkit actualizado de detección, dos clases de ataque nuevas (el zero-CL desync con double desync y el header Expect) y la única salida real: eliminar HTTP/1.1 del tramo entre front-end y back-end.

Por qué la solución de 2019 nunca llegó

El remedio era conocido: usar HTTP/2 en el upstream entre front-end y back-end y la clase de ataque casi desaparece. Lo que ocurrió en su lugar fue lo contrario. HTTP/2 se adoptó solo en la conexión cliente-front-end, y la mayoría de los servidores convierten la petición a H1 para hablar con el back-end. Esa conversión añade traducciones sucesivas —H2 a H1, y a veces de vuelta a H2 contra el upstream— que multiplican la complejidad y el margen de error.

Mientras tanto, los WAF y los proveedores de CDN apilaban regular expressions para bloquear las sondas de detección clásicas. La paradoja: se parcheó la metodología de detección y las herramientas de escaneo, no la vulnerabilidad. Varias de las infraestructuras más caras de explotar en esta investigación resultaron vulnerables precisamente porque tenían un WAF delante; sin él, habrían estado a salvo.

Detección de discrepancias: HTTP Request Smuggler v3

La base del endgame es detectar discrepancias de parsing de forma confiable sin disparar las regex. La extensión de Burp Suite HTTP Request Smuggler v3 (open source, compatible con la versión gratuita) clasifica cómo interpreta cada servidor la petición combinando múltiples headers, permutaciones y estrategias.

El patrón básico: enmascarar un header (por ejemplo, un Host precedido por un espacio) y observar que el front-end lo ve pero el back-end no —una discrepancia "visible-hidden", que suele explotarse como CL.0 desync ocultando el header Content-Length. Si algo bloquea ese camino, conocer la falla subyacente permite adaptarse: en un objetivo que bloqueaba GET con body, bastó cambiar el método a OPTIONS.

El enfoque incluso predice vulnerabilidades. Si un servidor no acepta un \n solitario como terminador de línea (permitido por el RFC), basta ponerlo detrás de un proxy que sí cumpla el RFC para que probablemente haya desync —un hallazgo que se rastreó hasta una librería subyacente con parche en camino. La variante inversa (hidden-visible, el front-end no ve el header enmascarado) destapó un patrón masivo de servidores IIS detrás del Application Load Balancer de AWS, protegidos por AWS Desync Guardian. Un bypass independiente permitió el exploit completo; aun tras arreglar el bypass, la discrepancia de parsing seguía ahí, y mitigarla era cuestión de cambiar dos settings del front-end. AWS se negó a hacerlo por defecto porque algunos clientes usan clientes HTTP antiguos que envían requests malformados. Moraleja: al usar un cloud proxy, se importa la deuda técnica de otras gente a la propia infraestructura.

El zero-CL desync y el double desync

flowchart LR
    A["Request 1 del atacante
(zero-CL desync)"] --> B["Request 2 del atacante
(weaponizada, CL.0 desync)"]
    B --> C["Request de la víctima
explotada por el payload"]

Los desyncs de Content-Length cero se consideraban imposibles: si el front-end no ve el Content-Length, solo reenvía el bloque de headers, y el back-end se queda esperando un body que nunca llega. El resultado es un deadlock del lado del servidor —excelente para tumbar un servicio, inútil para un desync.

La salida es un early response gadget: hacer que el back-end responda antes de recibir el request completo. Nginx ya responde a requests incompletos (hecho que destapó un problema con timestamps negativos al medir tiempos de carga). Para IIS, la documentación de Windows da la clave: las rutas que coinciden con nombres de dispositivo reservados (/con, y similares) activan un código especial que responde temprano. Ese momento explica además un misterio de años: los "mystery 400" que la herramienta reportaba como hallazgos raros eran casi seguramente desyncs explotables.

Con el desync confirmado, el salto a un ataque real exige inyectar el payload en el request de la víctima, no solo recortarlo. Ahí entra el double desync: el primer request del atacante causa el zero-CL desync que "weaponiza" el segundo request del propio atacante, y ese segundo desync termina explotando la petición de la víctima. El problema práctico son los headers extra que los front-end inyectan antes de reenviar (a menudo con valores variables como la IP del cliente); la solución robusta es colocar el payload antes del punto donde la mayoría de los servidores inyectan headers —al final del bloque—. Encadenando ese desync con input reflection y con la técnica HEAD para fusionar dos respuestas en una, se sirvió JavaScript malicioso a usuarios reales del sitio. La race condition implicada hacía que el ataque fuera estable enviando unos cientos de requests por segundo.

El header Expect: la segunda clase de ataque

El header Expect divide el envío de una petición en dos fases para que el cliente pueda abortar temprano. Ningún browser lo usa, pero como está en el RFC desde siempre, casi todos los servidores intentan soportarlo. Y porque introduce estado en una zona de la lógica que antes no lo necesitaba, todo sale mal al combinarlo con otros casos especiales: un HEAD más un Expect válidos hacen que el servidor olvide el primer caso especial, lea más bytes de los debidos y se deadlockee.

Efectos observados, de menor a mayor:

  • Fugas de memoria: en varios servidores web, enviar Expect filtra memoria, incluyendo claves secretas.
  • Bypass de stripping de headers internos: Expect genera dos bloques de headers y rompe los intentos del front-end de ocultar headers sensibles. Funciona contra todo el CDN de Netlify (que lo consideró "feature" pero pagó el reporte).
  • Zero-CL desync masivo: un Expect válido produce CL.0 desync en una gran cantidad de objetivos. Sobre el dominio que almacena los adjuntos de los reportes del bug bounty de GitLab, se ejecutó response queue poisoning —smugglear dos requests completos para que el servidor mezcle respuestas entre usuarios— y tras 27.000 requests se obtuvo el reporte de vulnerabilidad privado de otra persona ($7.000). Con T-Mobile, bastó ofuscar el valor del header con un carácter extra para conseguir un payout de $12.000 y un servidor de pre-producción.
  • A escala de CDN: sobre Netlify, el mismo desync permitía secuestrar un flujo continuo de respuestas de más de un millón de sitios a la vez. Netlify respondió que "los sitios que usan Netlify no están en scope" y no pagó.

Akamai, LastPass y la economía del bounty

El último ataque fue el más rentable: control total sobre auth.lastpass.com, sirviendo contenido de sitios completamente distintos en el dominio —el bounty máximo del programa—, más una lista larga de objetivos vulnerables compartiendo la misma raíz (en su mayoría detrás del CDN de Akamai). Entre los objetivos estaba example.com: había evidencia significativa de que la técnica funcionaba, pero sin programa de vulnerabilidades, demostrarlo habría sido ilegal y nunca se sabrá.

Reportar a cada empresa afectada o reportar solo a Akamai era una decisión incómoda. La resolución final: los bounty hunters que colaboraron reportaron el hallazgo sin incluir al investigador original en el reporte, y se llevaron más de $200.000. Akamai, bombardeada por tickets de soporte de sus propios clientes, pagó $9.000 por la coordinación directa, sacó un hotfix para algunos clientes con rapidez... y tardó más de 65 días en resolver el problema por completo. El total acumulado de la investigación supera los $350.000 en bounties —dinero contante como evidencia del peligro de HTTP/1.1.

Cómo matar HTTP/1.1

Todos los ataques explotan implementaciones, pero comparten una única falla de protocolo: la falta de aislamiento robusto de requests. Se agrava porque H1 es inmanejable para un proxy y porque nadie quiere arreglarlo "de verdad" si eso rompe clientes legacy. Conclusión inevitable: siempre habrá más ataques de desync.

La salida:

  1. Asegurarse de que el origin server soporte HTTP/2.
  2. Activar upstream H2 en el front-end. No hace falta desactivar H1 para los clientes: esas conexiones no se comparten entre usuarios y son mucho menos peligrosas.
  3. Jamás depender de H2-downgrading (convertir H2 entrante a H1 hacia el origen): empeora todo.

Quedan rezagados Nginx, Akamai, CloudFront y Fastly, que todavía no soportan upstream H2; para quienes estén atascados ahí, las mitigaciones alternativas son paliativos hasta poder migrar. La única forma de usar H1 de forma segura es no tener un servidor front-end.

Para la investigación futura, la gran pregunta es "cuál es el próximo Expect": otros features de H1 tienen potencial de desync, y H1 es tan mal entendido que hay oro incluso fuera de ese reino. Ejemplo: TRACE deshabilitado en el back-end no significa nada si el header Max-Forwards permite apuntar el request a un servidor intermedio arbitrario de la cadena. Y mientras tanto, escanear periódicamente con HTTP Request Smuggler es la forma más rápida de saber si se está expuesto.

Técnicas y herramientas mencionadas

  • Request smuggling / desync: explotación de discrepancias de parsing entre front-end y back-end para interferir con requests de otros usuarios.
  • CL.0 desync: desync basado en ocultar el header Content-Length al front-end.
  • Zero-CL desync: desync sin Content-Length, considerado imposible hasta el uso de early response gadgets.
  • Double desync: encadenamiento de dos desyncs para inyectar payloads en requests de terceros.
  • Early response gadget: técnica para que el back-end responda antes de recibir el request completo (rutas de dispositivo Windows como /con en IIS, respuestas tempranas de Nginx).
  • Response queue poisoning: smugglear dos requests completos para que el servidor entregue respuestas de un usuario a otro.
  • Header Expect: header del RFC que divide la petición en dos fases; origen de deadlocks, fugas de memoria, bypass de stripping y desyncs masivos.
  • Headers enmascarados: ocultar headers con espacios u obfuscación para detectar discrepancias visible-hidden / hidden-visible.
  • Max-Forwards + TRACE: combinación para apuntar a servidores intermedios arbitrarios de la cadena.
  • HTTP Request Smuggler v3: extensión open source de Burp Suite para detectar y clasificar discrepancias de parsing.
  • Turbo Intruder: cliente HTTP del autor, roto por el header Expect.
  • AWS Desync Guardian / AWS ALB + IIS: combinación de infraestructura con discrepancia de parsing conocida.
  • Upstream HTTP/2: la mitigación estructural real; incompatible aún con Nginx, Akamai, CloudFront y Fastly.

Conclusiones

  • La industria parcheó la detección, no el protocolo: seis años de regexes dejaron un ecosistema que parece seguro hasta que se varía mínimamente la técnica.
  • Los ataques nuevos —zero-CL con early response gadgets, double desync y la familia completa del header Expect— demuestran que "más ataques de desync siempre están en camino".
  • La única mitigación estructural es eliminar HTTP/1.1 del tramo front-end a back-end mediante upstream H2; las mitigaciones parciales (WAF incluidos) a menudo empeoran la situación.
  • H1 sigue siendo una mina de oro de investigación más allá del desync: header TRACE, Max-Forwards y features poco comprendidos ofrecen terreno fértil mientras el protocolo siga vivo.
