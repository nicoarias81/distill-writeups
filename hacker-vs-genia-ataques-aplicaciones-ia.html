¿Hacker 1, IA 0? Ataques reales a aplicaciones con modelos de lenguaje y cómo defenderse

Fuente: «Hacker vs GENI: Who Wins? From Open Source To AI Malware: The Rise of LLM-driven Threats | Efraín Reyes» · ver el video original

Resumen

Efraín Reyes (Roquiset), CTO de una financiera ecuatoriana y dedicado en su tiempo libre a pentesting, research y bug bounty, recorrió el panorama de ataques a aplicaciones que integran inteligencia artificial. El punto de partida es el contexto de mercado: el hype de la IA lleva a que en Europa, si un producto no incorpora un módulo de IA, "no está en la onda", lo que empuja a las empresas a sumar agentes y automatizaciones a toda velocidad, muchas veces sin seguridad.

Como marco de referencia sirve el OWASP Top 10 para LLM y aplicaciones de IA generativa: prompt injection, manejo inseguro del output, envenenamiento de datos de entrenamiento, denegación de servicio (incluida la monetaria, que consume el crédito de tokens), vulnerabilidades de cadena de suministro, divulgación de información sensible, diseño inseguro de plugins, alucinaciones y robo del modelo. Sobre esa base, el recorrido presentó tres escenarios de arquitectura —del agente simple al que ejecuta plugins con acceso al backend— y ejemplos reales de explotación, cerrando con las recomendaciones de desarrollo seguro.

Tres escenarios de arquitectura, tres niveles de riesgo

El escenario básico es un front con un agente que dialoga con el usuario y detrás un backend con uno o varios modelos. Aun sin base de datos, ya concentra vulnerabilidades: el prompt injection (la puerta de entrada para concatenar todo lo demás), el manejo inseguro del output (que encadenado con fallos del Top 10 web o API dispara cross-site scripting o HTML injection) y la denegación de servicio si la API no está cubierta.

El segundo escenario agrega una base de datos en el medio, usada como historial de chat o como base de conocimiento del modelo. Aparecen tres riesgos nuevos: envenenamiento de datos de entrenamiento, vulnerabilidades de cadena de suministro y exposición de información sensible según lo que contenga la base y las funciones adicionales del modelo. Si el modelo se comunica con componentes internos sin segurizar, el impacto puede ser catastrófico.

El tercer escenario incorpora plugins: microservicios internos con los que el modelo ejecuta acciones avanzadas hacia adentro de la organización. Aquí surgen las vulnerabilidades más graves, desde RCE hasta SSRF.

Prompt injection en acción: del self-XSS al robo de sesión

El primer ejemplo combinó prompt injection con manejo inseguro del output: pedirle al agente que imprima ciertos tags HTML, lo que dispara un cross-site scripting si no hay sanitización. Por sí solo es un self-XSS de poco impacto, pero encadenado con un IDOR permite inyectar el payload en el chat de un tercero y robarle las cookies.

Un segundo prompt, más avanzado, pide al modelo que olvide el prompt del sistema y solo atienda lo que esté dentro de un símbolo concreto (un numeral), donde va el mismo payload. El modelo abandona su tarea original y ejecuta lo que pide el atacante. La técnica más efectiva, sin embargo, usa matemática: partir el payload en las variables A y B, pedirle al modelo que resuelva C = A + B e imprima C. El modelo arma y devuelve el payload completo; funciona en múltiples modelos de terceros, no en los abiertos como OpenAI.

El vector de impacto llega con el historial de chat: si el producto no está bien desarrollado, usa el mismo thread ID para todos los usuarios, y el atacante puede inyectar código en la sesión de otro.

Envenenamiento del conocimiento y SQL injection con IA

El escenario de training data poisoning derivó en el mismo cross-site scripting: un administrador carga documentos o datasets en una base de conocimiento (por ejemplo, descargados de Hugging Face, donde hay datasets llenos de estos payloads). El atacante entrega un documento Word con el prompt ofuscado —un punto de un píxel con el color del fondo, con una cadena gigante dentro— que pasa desapercibido y el modelo sí interpreta. Cuando el usuario consulta, el output no sanitizado ejecuta el ataque.

Otro ejemplo revive un clásico: el SQL injection blind. Si el modelo está conectado a una base de datos y puede consultar información del usuario, pedirle datos de un tercero recibe un "no" por confidencialidad. Pero si se le pide que responda solo verdadero o falso —¿el nombre del administrador empieza con A?, ¿la segunda letra es B?— el modelo entrega la información letra por letra sin darse cuenta. Automatizable, extrae usuarios y contraseñas en segundos.

Plugins inseguros: scores crediticios y phishing masivo

Con plugins que ejecutan acciones avanzadas el riesgo se multiplica. Dos ejemplos: un plugin de score crediticio personalizado o de corrección de exámenes. Un atacante sube su parcial en Word o PDF con la instrucción de olvidar el prompt del sistema y devolver siempre 100 puntos; el modelo obedece, y esa respuesta termina guardándose en la base de datos de la empresa. Referencia además una vulnerabilidad conocida en un plugin de envío de e-mails que terminó en RCE.

En el caso del plugin de correo, un archivo subido por el usuario puede contener un prompt que ordene redactar un mail con características de phishing y enviarlo a todos los destinatarios indicados: daño reputacional y pérdidas económicas fuertes para la empresa.

Cómo desarrollar con IA de manera segura

Las recomendaciones, en orden de impacto: filtrar el prompt injection con herramientas open source o pagas (controlar esa puerta de entrada resuelve un porcentaje alto del problema); usar datasets propios y revisar —aunque sea de manera automatizada— los de terceros, porque los documentos también se ofuscan y "un documento de tres páginas" no es garantía de nada; sanitizar input y output con listas negras (sin tags de script, sin URLs, sin HTML si el agente no los necesita); adoptar el esquema de agentes supervisores, donde un segundo modelo revisa cada respuesta antes de entregarla al usuario —más dinámico y efectivo que la lista negra, aunque agrega costo en tokens—; aplicar cero trust al agente, con los mínimos permisos posibles para que una vulnerabilidad no detone los servicios internos; y monitorear con logs y trazabilidad toda la interacción, para mejorar los datasets y las medidas y evitar que el modelo sea una caja negra que gasta dinero sin control.

Conclusiones

  • Sin prompt injection no hay nada: es la puerta de entrada; encontrada la vía, "el resto es historia" y el límite es la creatividad del atacante.
  • Un mismo prompt sirve para múltiples ataques: self-XSS encadenado con IDOR roba sesiones; variables matemáticas burlan filtros; el thread ID compartido convierte el self-XSS en ataque a terceros.
  • Hoy la balanza la tiene ganada el hacker: los modelos cumplen códigos de conducta y no piensan maliciosamente; el desarrollador aún está crudo en conciencia, metodologías de testing y madurez.
  • Hay oportunidad profesional: el rubro ofensivo sobre IA tiene muy pocas personas dedicadas, y se espera una ola de productos con IA que necesitarán revisión.

Técnicas y herramientas mencionadas

  • Prompt injection: técnica base para desviar al modelo de su función; incluye el patrón "olvidá el prompt del sistema" y la partición del payload en variables matemáticas (C = A + B).
  • Insecure Output Handling: renderizado de tags HTML/JS en el chat para cross-site scripting e HTML injection.
  • Training data poisoning: inyección de payloads en bases de conocimiento vía documentos ofuscados o datasets de terceros (Hugging Face).
  • SQL injection blind asistido por IA: extracción de datos letra por letra con respuestas verdadero/falso.
  • Thread ID compartido: vector para inyectar contenido en la sesión de otros usuarios.
  • Agentes supervisores: segundo modelo que revisa cada respuesta antes de entregarla.
  • OWASP Top 10 para LLM y GenAI: marco de referencia de riesgos, incluida la denegación de servicio monetaria.
