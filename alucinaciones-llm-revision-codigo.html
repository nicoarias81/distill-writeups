Las alucinaciones de los LLM en revisión de código: el problema de los nombres

Fuente: «DEF CON 32 - Defeating Secure Code Review GPT Hallucinations - Wang Zhilong, Xinzhi Luo» · ver el video original

Resumen

Los LLM se volvieron herramientas centrales del ciclo de desarrollo de software: generan código, crean casos de test, redactan documentación y ayudan a detectar vulnerabilidades. Pero también alucinan — aseguran información falsa con total confianza, como el célebre caso del chatbot de Google que se equivocó en su primera demo pública, o cuando ChatGPT afirmó que 9.11 es mayor que 9.9. La raíz es estructural: son sistemas de autocompletado probabilístico, no bases de conocimiento.

Una serie de experimentos puso a prueba cuánto entienden estos modelos la lógica real de un programa, y el resultado es incómodo: dependen casi por completo de los nombres y comentarios del código, no de su semántica ejecutable. Eso convierte una convención de nombres pobre —o deliberadamente engañosa— en un vector de manipulación de las herramientas de revisión segura de código.

Anonimización como experimento mental

El código fuente es una secuencia de tokens de tres tipos: keywords y operadores (definidos por la especificación del lenguaje, controlan el flujo de ejecución) y nombres definidos por el usuario. El experimento clasificó el primer grupo como características lógicas y el segundo —nombres, anotaciones, comentarios— como características literales.

La pregunta: si se eliminan las características literales, ¿puede el modelo seguir razonando sobre la lógica? Para averiguarlo se tomaron funciones como un bubble sort en Java y se aplicaron tres tipos de anonimización: nombres de funciones, nombres de variables y nombres de invocaciones a métodos. Además, dos estrategias de reemplazo: strings aleatorios, o mezclar los nombres con otros nombres reales del código (más engañoso para quien lee).

Sobre el código anonimizado se corrieron dos tareas clásicas de análisis:

  • Clone detection: identificar fragmentos de código equivalentes que producen el mismo resultado con la misma entrada.
  • Code search: recuperar de un corpus grande el fragmento que mejor coincide con una intención expresada en lenguaje natural.

Los resultados: los LLM leen los nombres, no la lógica

La anonimización degradó fuertemente el rendimiento, y el efecto se multiplicó cuando se reemplazaron los tres tipos de nombres a la vez. En code search, anonimizar el nombre de la definición daña más que anonimizar el de la invocación: hay una correlación fuerte entre el nombre de una función y su propósito. Java sufrió más que Python cuando se anonimizó todo — la verbosidad y estructura del lenguaje amortiguan la anonimización parcial, pero esa estructura se pierde al reemplazar todos los nombres. Y code search cayó más que clone detection: sin nombres, el código pierde el puente hacia su descripción en lenguaje natural.

La conclusión central: aunque las características lógicas son lo único que importa para que un programa se ejecute, los LLM procesan casi exclusivamente las características literales.

Tres raíces del problema y dos limitaciones adicionales

El sesgo hacia los nombres tiene tres fuentes reales:

  1. Committers maliciosos: quien quiere infiltrar código malicioso en un proyecto open source puede elegir nombres engañosos para pasar desapercibido ante las herramientas de revisión basadas en LLM.
  2. Comentarios desactualizados: el código cambia con cada commit pero los comentarios no siempre se actualizan; esa inconsistencia confunde al modelo durante el análisis.
  3. Malas prácticas de nomenclatura: incluso un desarrollador benigno puede usar nombres de variables confusos que desorientan al revisor automático.

Además, hay dos limitaciones estructurales. La primera es la falta de contexto: GPT-3 maneja 2.048 tokens y GPT-4 unos 32.000, pero incluso un proyecto pequeño tiene miles de líneas con más de 10 tokens por línea. El modelo analiza cada función de forma aislada, sin visión global del proyecto. La segunda es el rendimiento desigual por lenguaje: en pruebas de inferencia de lógica, GPT-3.5 rinde mejor en PHP y Go, mientras que Gemini destaca en PHP y Python — cada modelo tiene fortalezas distintas según el lenguaje.

Mitigaciones: de las defensas ad hoc al cambio de preentrenamiento

Las soluciones inmediatas pasan por separar código de confianza del resto: si el commit viene de un desarrollador confiable, basta exigir buenas convenciones de nombres; si viene de un desarrollador no confiable, hay que presuponer que un committer malicioso puede engañar al LLM — algo trivialmente alcanzable según los experimentos. Una defensa concreta es desplegar detección de inconsistencias de nomenclatura y lógica antes de ejecutar la revisión automática de código.

La solución de fondo es reentrenar. El preentrenamiento dominante de los LLM es la predicción de tokens enmascarados, que al aplicarse a código aprende sobre todo características literales. Para NLP eso es aceptable — el lenguaje natural no tiene tantas características lógicas— pero el código sí. La propuesta: añadir tareas de preentrenamiento de predicción de características lógicas, para que el modelo capture la semántica ejecutable y no dependa de los nombres.

Técnicas y herramientas mencionadas

  • GPT-3.5 / GPT-4 / Gemini — modelos evaluados en tareas de análisis de código.
  • Clone detection — detección de fragmentos de código funcionalmente equivalentes.
  • Code search — recuperación de código a partir de una consulta en lenguaje natural.
  • Anonimización de nombres — técnica experimental: reemplazo de identificadores por strings aleatorios o mezclados.
  • Mask token prediction — tarea de preentrenamiento dominante de los LLM actuales, sesgada hacia características literales.
  • Preprint en arXiv — los detalles del estudio y las soluciones propuestas están documentados en un paper de referencia.

Conclusiones

  • Los LLM de revisión de código procesan principalmente nombres y comentarios, no la lógica del programa; anonimizar identificadores degrada su rendimiento de forma severa.
  • Un committer malicioso puede explotar esa dependencia con nombres engañosos para evadir la revisión automática de código.
  • La falta de contexto (ventana limitada de tokens) y el rendimiento desigual por lenguaje son limitaciones adicionales a considerar al desplegar estas herramientas en el SDLC.
  • El arreglo real está en el preentrenamiento: incorporar tareas de predicción de características lógicas para construir modelos que razonen sobre la semántica, no sobre los nombres.
