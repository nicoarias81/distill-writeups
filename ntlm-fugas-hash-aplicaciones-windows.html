El último viaje de NTLM: cómo las aplicaciones de Windows filtran tus hashes

Fuente: «DEF CON 32 - NTLM The Last Ride - Jim Rush, Tomais Williamson» · ver el video original

Resumen

NTLM tiene más de 30 años y Microsoft lleva tiempo queriendo jubilarlo, pero sigue vivo en todas partes: cualquier proceso de Windows puede responder a un desafío de autenticación y regalar el hash de la cuenta con la que corre. La investigación que se recoge aquí parte de una pregunta simple: ¿cuántas aplicaciones legítimas del ecosistema Microsoft pueden ser convencidas, con un solo clic, de autenticarse contra un servidor atacante?

La respuesta resultó ser "bastantes". Recorriendo NuGet, Visual Studio, Outlook, los manejadores de URI de Windows y las redirecciones HTTP, se documentaron cuatro bugs reportados a MSRC —dos con bounty— que permiten capturar hashes NTLM sin advertencias visibles para la víctima. El hilo conductor es un cambio de mentalidad: en lugar de ver estas interacciones HTTP como funciones inofensivas, tratarlas como variantes de SSRF donde el "exfiltrado" es el hash del usuario.

NTLM: el protocolo que no se va

NTLM sobrevive por inercia. Es el mecanismo de autenticación por defecto de recursos compartidos, servicios internos y componentes heredados de Windows, y cualquier aplicación que intente hablar con un recurso SMB o con un endpoint que pida autenticación puede terminar enviando un desafío NTLM con el hash del usuario que la ejecuta. La herramienta clásica para explotarlo es Responder, que escucha en la red, responde a esos desafíos y captura los hashes para crackearlos o retransmitirlos.

La superficie de ataque no es exótica: análisis previos ya mostraban que abrir ciertos archivos con VLC disparaba autenticaciones salientes hacia puertos como el 80, y los foros de desarrolladores están llenos de casos similares. El problema recurrente en Windows es que la única protección genérica es un diálogo de confirmación —el clásico "¿seguro que querés continuar?"— que en la práctica nadie lee y todos aceptan. Para que un bug sea explotable a escala, la cadena tiene que funcionar sin ningún aviso.

.NET e ICredentials: el fallback traicionero

Gran parte de la autenticación web en el ecosistema .NET pasa por la interfaz ICredentials, que provee credenciales a los clientes HTTP. Sus implementaciones tienen antipatrones peligrosos: cuando no hay credenciales configuradas, algunas caen en fallbacks que acaban usando la identidad del usuario actual vía NTLM.

El caso más ilustrativo es NuGet. Su documentación recomienda almacenar credenciales cifradas en el archivo NuGet.Config, pero cuando la autenticación falla o no hay credenciales, NuGet cae de vuelta a NTLM durante un restore. Como Visual Studio ejecuta restores automáticamente al clonar una solución, un desarrollador que clona un proyecto desde una URL controlada por el atacante dispara la fuga sin ver un solo diálogo. Microsoft aceptó el bug y pagó bounty —el importe, contaron los investigadores, alcanzó justo para la cirugía de ligamento cruzado de una perra.

Reencuadrar el problema como SSRF

La observación que desbloqueó el resto de los hallazgos: en vez de preguntarse "¿dónde se filtran hashes NTLM?", conviene preguntarse "¿qué aplicaciones hacen peticiones HTTP arbitrarias y las siguen a cualquier lado?". Vista así, una fuga de hash es un SSRF donde el recurso sensible es la identidad del usuario.

La prueba de concepto más directa: apuntar una de esas peticiones HTTP a un servidor atacante que responde con una redirección hacia una ruta UNC (\\atacante\recurso). Los navegadores bloquean ese salto de protocolo HTTP→SMB porque es una redirección peligrosa; las aplicaciones de Microsoft no. Ante la redirección, la aplicación cambia felizmente de protocolo, intenta autenticarse contra el share SMB, y Responder captura el hash. Eso fue el bug número dos reportado a Microsoft.

Manejadores de URI: un clic, cero avisos

Cada programa instalado en Windows registra esquemas de URI (ms-word:, ms-excel:, etc.) que una página web o un mail pueden invocar para abrir la aplicación automáticamente. Volcando todos los esquemas de una máquina y probando cuáles disparan advertencias, el resultado fue revelador: casi todos avisaban, salvo los esquemas de la propia Microsoft.

Un enlace como ms-word:ofe|u|<URL> abre Word y le hace descargar el recurso remoto, con posibilidad de forzar además la extensión del archivo resultante. Las mitigaciones existentes —vista protegida, Mark of the Web, prohibición de UNC directos en el esquema— se desmoronan con la técnica anterior: la URL es HTTP legítima, pero la redirección del servidor la convierte en UNC, y Word autentica contra el atacante. Un clic en un mail, sin advertencia alguna, y el hash está capturado.

Esta técnica compone además con investigación previa: Monocle Link, documentado por Check Point Research en 2024, usa monikers de archivo y monikers compuestos de COM —con el componente tras el signo !— para cargar extensiones de archivo normalmente bloqueadas. Controlar la URL mediante redirección amplía esa clase de bugs. También permite revivir el CVE de Varonis de 2023, que afectaba a las cabeceras de sharing de Outlook (content-class y X-Sharing-Content-URL): el parche de Microsoft fue añadir una advertencia, y una redirección a UNC la sortea por completo, convirtiendo el aviso en una instrucción de Microsoft pidiendo al usuario que haga clic.

Outlook, RSS y el periplo con MSRC

Outlook aporta más variantes. La importación de feeds mediante archivos OPML dispara peticiones HTTP que siguen redirecciones a UNC; el manejador outlookfeed: abre un feed RSS directamente y, embebido en las cabeceras de sharing, lo hace sin el aviso habitual. Microsoft triageó estos casos como "moderados" —el primero llegó a estar a punto de publicarse sin bounty, y la experiencia con MSRC incluyó idas y vueltas donde un bug aceptado "para servicing inmediato" resultaba luego "fuera de alcance" para recompensa. Al final se reportaron cuatro bugs: dos bounties, un swag, uno reclasificado, y uno parcheado en un Patch Tuesday como único moderate del lote.

Git, Visual Studio y un límite de responsabilidad difuso

Visual Studio usa Git Credential Manager, y git compilado con soporte NTLM envía el hash del usuario actual cuando un servidor pide autenticación y no hay credenciales —comportamiento pensado para servidores internos, pero que se convierte en fuga cuando alguien clona ciegamente una URL externa. La cadena empeora con los submódulos: un repositorio inofensivo puede referenciar submódulos profundos hacia el atacante, y Visual Studio los clona todos por defecto sin preguntar. VCPKG y otros flujos que consumen URLs de git heredan el problema. JetBrains o GitHub Desktop, en cambio, no lo hacen.

La respuesta de Microsoft —"clonar de una fuente no confiable es como navegar un share SMB no confiable"— dejó a los investigadores buscando en vano dónde está el límite de seguridad: ¿Visual Studio, Git Credential Manager, git, libcurl compilado con NTLM? La conclusión es que el problema está "en todas partes y en ninguna", y nadie asume el parche; Microsoft arregla lo demostrable dentro de sus productos y el resto queda como "problema de Windows".

Metodología y horizonte

La metodología cabe en una línea: donde haya una petición HTTP, apuntarla a Responder y ver qué pasa. Etiquetas de imagen, cabeceras de sharing, feeds RSS, restores de NuGet, clones de git — cada superficie HTTP de una aplicación de escritorio es candidata. Las líneas abiertas apuntan a build servers y pipelines CI (que consumen URLs externas), procesamiento de documentos y generadores de PDF, clientes de mensajería y videojuegos con chat.

Técnicas y herramientas mencionadas

  • NTLM / Responder — protocolo de autenticación heredado de Windows y la herramienta clásica para capturar y crackear sus hashes.
  • SSRF reencuadrado — tratar las peticiones HTTP de apps de escritorio como SSRF cuyo recurso sensible es el hash del usuario.
  • Redirección HTTP → UNC — un servidor atacante redirige a \\host\share; apps de Microsoft saltan de protocolo y autentican, los navegadores lo bloquean.
  • Manejadores de URI de Windows — esquemas como ms-word:ofe|u|<url> que abren apps Office con descarga remota y sin advertencia para los esquemas Microsoft.
  • Monocle Link (Check Point, 2024) — abuso de file/composite monikers de COM para cargar extensiones bloqueadas; componible con redirecciones.
  • CVE Varonis 2023 / cabeceras sharing de Outlook — content-class y X-Sharing-Content-URL; el parche por advertencia se sortea con una redirección.
  • NuGet / ICredentials — fallback a NTLM en NuGet restore dentro de Visual Studio, sin diálogos.
  • Git Credential Manager + libcurl (NTLM) — envío del hash del usuario actual al clonar; submódulos clonados en cadena por defecto.
  • OPML / RSS en Outlook — importación de feeds y handler outlookfeed: como vías de fuga.

Conclusiones

  • NTLM se filtra por rutas completamente convencionales: un clic en un enlace de mail puede bastar si la aplicación sigue redirecciones a UNC sin avisar.
  • Los mensajes de confirmación de Windows no son un control de seguridad efectivo; los bugs serios son los que ni siquiera los disparan.
  • La cadena de responsabilidad entre Visual Studio, Git Credential Manager, git y libcurl deja el bug de fuga por clone sin dueño y sin parche.
  • Para defenderse: desactivar NTLM donde sea posible y usar Kerberos; y como regla de caza, cualquier campo que acepte una URL es superficie de fuga de hashes potencial.
