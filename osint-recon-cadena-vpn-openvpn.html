OSINT y recon moderno: de una apuesta a una cadena RCE sobre OpenVPN

Fuente: material del curso correspondiente (sin video público)

Resumen

Un investigador senior de Microsoft (Vladimir) cuenta cómo una apuesta entre amigos por las bondades de una VPN de consumo terminó en una cadena de ataque completa contra OpenVPN — el motor que usan ExpressVPN, NordVPN, CyberGhost, ProtonVPN y miles de routers — combinando OSINT/recon (YARA, VirusTotal, búsqueda de repos), un desbordamiento de entero en drivers Windows, escalada de privilegios local vía named pipes, robo y crackeo de hashes NTLMv2 en GPU alquiladas en la nube, y ejecución remota de código vía plugin malicioso cargado desde un share SMB del atacante.

La apuesta y el primer bug: overflow en el driver de la VPN

  • Todo empezó jugando a Deep Rock Galactic: un amigo instaló ExpressVPN, el autor le dijo que no valía para nada, y le retaron a demostrarlo. Primera parada: el driver TAP de Windows (la "tarjeta de red virtual" que envuelve el tráfico).
  • En la función de transmisión del miniport NDIS, el buffer se asigna con data_length + 18 para el offset y otros 18 bytes de overhead — con un paquete lo bastante grande, integer overflow en asignación de kernel seguido de un copy mucho mayor que el buffer. Kernel heap overflow clásico, pero muy difícil de explotar hoy: HVCI, Device Guard y demás mitigaciones lo hacen casi impracticable, así que lo dejó reposar.
  • El punto de inflexión: en el driver de ProtonVPN encontró el mismo bug. ¿Caso aislado o patrón sistémico? Escribió reglas YARA para buscar el patrón de asignación (identificable por el pool tag) en binarios de 32 y 64 bits, las corrió sobre VirusTotal y encontró 50 matches: muchos drivers de VPN compartían el código defectuoso.

OpenVPN: recon sobre el motor común

  • Preguntarle a ChatGPT "¿cuál es la VPN más popular?" apuntó a OpenVPN, base de la mayoría de VPNs comerciales y presente en routers de todo el mundo (Windows, Linux, macOS, iOS, Android). Recon sobre el org de GitHub: repos openvpn3, easy-rsa, la GUI de Windows y tap-windows6, donde el mismo patrón de asignación defectuosa aparecía en código fuente.
  • Arquitectura relevante: cliente/servidor con TLS/mTLS, protocolo propio sobre TCP/UDP (longitud de 16 bits, key ID + opcode, payload), y en Windows el OpenVPN Interactive Service: un servicio SYSTEM con named pipe openvpn\service que recibe "startup data" (directorio, config y log), suplanta al cliente conectado, valida que pertenece al grupo OpenVPN y lanza el proceso daemon, que se comunica de vuelta por otra named pipe por la que los clientes poco privilegiados pueden pedir al servicio que cambie rutas o configuración DNS en su nombre.

Escalada local: named pipes y potatoes

  • Sobre la lógica que maneja los mensajes del pipe interior: se lee una cantidad fija de bytes sobre una estructura en el stack dimensionada para el mensaje más largo de la unión — enviar un tipo con más datos de los esperados es un stack overflow. El stack cookie lo frena (crash en lugar de control), y la cookie se deriva de entropy del sistema, así que sin un read primitive no hay bypass.
  • Combinación con problemas clásicos de named pipes (race de creación de instancias y superfluous pipe connectivity — el cliente no sabe con quién habla): la cadena de LPE es (1) cargar una DLL maliciosa como plugin de OpenVPN en el daemon, (2) usar el pipe interior para desbordar y matar el servicio, (3) el exploit recréa la named pipe con el mismo nombre y suplanta al próximo cliente que conecte — si ese cliente es un proceso potente (la GUI corre elevada), se ejecuta en su nombre. De local a remoto: hashes, nube y el plugin malicioso

  • Named pipes se pueden alcanzar remotamente por SMB/IPC (net use \\host\IPC$), pero por defecto Windows bloquea el acceso anónimo. Solución del atacante: recon de red — esperar hashes NTLMv2 con Responder, capturarlos y crackearlos.
  • El crackeo no necesita granja de GPUs propia: con la RTX 3070 del portátil (~6.000 CUDA cores, ~2.800 M hash/s) una contraseña corta cae al instante pero una larga tarda años; alquilando en Vast.ai una máquina con 18 RTX 4090 por ~8,50 USD/hora, una contraseña de 9 caracteres cayó en menos de 3 minutos.
  • Cadena RCE completa: recoger hashes → crackear → net use con las credenciales → conectar a la named pipe del servicio OpenVPN remoto → pasarle startup data con configuración y log en un share SMB controlado por el atacante (con acceso anónimo habilitado para Everyone) → la config carga el plugin malicioso desde ese share → código ejecutado en la víctima. Demo: volcado masivo de archivos en el escritorio remoto.

La cadena completa y el final del juego

  • RCE + LPE se montan juntas: el plugin remoto ejecuta a su vez la lógica de escalada local. Con SYSTEM, el vector clásico de APT: bring your own vulnerable driver (crear un servicio con un driver con primitivas read/write de kernel) o living off the land (MSI firmados); el autor explotó un bug en AppID.sys para conseguir arbitrary kernel read/write.
  • Cereza: con primitivas de kernel se sobrescribe el campo PS_PROTECTION para quitar la protección PPL de WinInit (proceso firmado de nivel WinSystem que ni SYSTEM puede matar) y tumbarlo — vía para desactivar antivirus/EDR, ocultar rootkits y moverse en silencio. Cadena final: RCE por plugin → LPE → kernel R/W → de-PPL de WinInit.
  • Lecciones: un solo vector de extensión mal diseñado (el mecanismo de plugins) vale por toda una cadena; ya no hace falta hardware propio para crackear a escala (la nube lo pone barato y disponible para cualquiera); y las herramientas de recon/OSINT (VirusTotal + YARA, búsqueda de repos, Meddle/Hunt — "showdown in Zoom" en el transcript) son parte del arsenal habitual del investigador de seguridad, no solo del analista de inteligencia.
