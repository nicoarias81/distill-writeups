Sin símbolos no hay reversión: recuperación automatizada de nombres de funciones con Ghidra

Fuente: «DEF CON 32 - No Symbols When Reversing? No Problem - Bring Your Own Signatures - Max Kersten (Trellix)» · ver el video original

Resumen

Analizar un binario stripped —sin símbolos— significa enfrentarse a miles de funciones llamadas fun_00012345 sin indicación de qué hacen. Para un investigador de malware, distinguir qué código es runtime del lenguaje, qué es una librería de terceros y qué es código propio del autor es la diferencia entre horas de trabajo manual y un análisis enfocado. La recuperación de símbolos automatizada convierte ese problema en un pipeline: generar firmas de funciones conocidas, aplicarlas contra el binario objetivo, y dejar para el análisis humano solo lo que de verdad es nuevo.

El enfoque aquí descrito se apoya en dos mecanismos de Ghidra: Function ID, su equivalente a las firmas FLIRT de IDA, que mapea hashes de funciones a nombres, y BSim, la base de datos de similitud comportamental de la NSA basada en el p-code del descompilador, que identifica funciones con código superpuesto aunque no coincidan exactamente. Ambos se automatizan con scripts headless para procesar binarios sin intervención, y se acompañan de un corpus de firmas generado a partir de cientos de gigabytes de binarios benignos —runtimes y librerías— que el autor ha publicado en GitHub junto con las herramientas.

Qué es (y qué no es) un símbolo

Un símbolo, desde la perspectiva de reversión, es esencialmente el nombre de la función: debería ser reconocible, autoexplicativo e inequívoco. Los binarios mezclan tres tipos de código que conviene distinguir. El runtime del lenguaje —Golang es el ejemplo canónico— se compila estáticamente dentro del binario, de modo que diez binarios Go de la misma versión comparten gran cantidad de código: no están relacionados entre sí, pero sin nombres de función cuesta determinar qué hace cada una. Las librerías aportan pistas adicionales: rastrear una versión concreta de una librería o clasificar malware por las librerías que usa es una técnica habitual, pero requiere saber qué librería está incluida y dónde. Y el user code, todo lo que escribió el desarrollador, es la parte más interesante para el analista de malware: es relativamente único, de modo que encontrarlo en varios binarios indica código compartido entre muestras.

Las dos vías de Ghidra: Function ID y BSim

Function ID es el mecanismo diseñado específicamente para esto: calcula un hash de la función y lo mapea a un nombre; si el hash aparece en otro binario, se recupera el nombre de la base. Se ejecuta como analizador dentro del análisis por defecto de Ghidra y es la vía más rápida. Una limitación obvia: si el binario es C++ stripped sin metadatos, no queda otra que firmas externas.

BSim (behavioral similarity), publicado por la NSA la víspera de Navidad de su lanzamiento, opera en otro nivel: el descompilador de Ghidra produce un lenguaje intermedio llamado p-code, y sobre los vectores de alto nivel de ese p-code se calculan similitudes entre funciones. Su ventaja natural es comparar descompilaciones lado a lado —ideal para patch diffing—, pero eso exige conservar acceso al proyecto Ghidra y a los archivos originales de la base. El truco aquí es usarlo de forma forzada: los scripts prescinden de esa dependencia, de modo que una base BSim generada por un analista puede usarse sin tener el proyecto original. BSim admite además bases sin tamaño (no size), que ignoran diferencias de tamaño de tipos entre arquitecturas —un int de 4 bytes en 32 bits frente a 8 en 64—, permitiendo cruzar firmas de binarios de 64 bits contra objetivos de 32 bits y viceversa.

El pipeline automatizado empieza antes: si el binario contiene metadatos —como la tabla PCLNTAB de Golang, que permite recuperar los nombres de función directamente— hay que explotarlos primero. Después, generar bases Function ID por arquitectura y compilador (un language ID de Ghidra es, a grandes rasgos, un binario PE de 32 bits para Windows con un compilador concreto), aplicar Function ID —más rápido y diseñado para esto— y luego BSim con un umbral de similitud configurable entre 0 y 1.

Coincidencias exactas, genéricas y el problema del umbral

Con BSim los resultados se dividen en dos clases. Las coincidencias idénticas —todas las funciones de la base que coinciden llevan el mismo nombre— se renombran directamente, y el script añade como metadatos el archivo original, la similitud, la significance (que depende del tamaño de la función) y la arquitectura del match. Ese archivo original es información valiosa: si las firmas se generaron desde binarios llamados go1.13, go1.14, etc., el match revela de paso qué versiones del runtime contienen esa función.

Las coincidencias genéricas —más de un nombre distinto en la base para la misma función— no se renombran automáticamente con un nombre, sino con un prefijo configurable (por ejemplo golang_). El motivo: ocurre que el paquete Go cambió de nombre entre versiones mientras la función seguía siendo la misma, y automatizar esa discriminación con lógica adicional es trabajo futuro. El prefijo cumple además una función práctica: en ejecuciones posteriores contra otras bases, cualquier función que ya no tenga el nombre por defecto (fun_ o thunk_fun_) se excluye de la búsqueda, acelerando el proceso y mejorando la precisión según el orden y la estructura de las bases.

El umbral es una decisión de analista. Con 0,75 de similitud, por ejemplo, puede interesar ver todos los candidatos y no solo el primero; si todas las coincidencias llevan el mismo nombre, la decisión es clara, pero si hay varios nombres distintos hay que investigar más. Y bajar demasiado el umbral produce demasiados resultados como para ser útil.

El corpus: 117 GB de firmas

Como prueba de concepto y para ahorrar ciclos de CPU ajenos, el autor descargó cientos de gigabytes de binarios benignos —mayoritariamente runtimes y librerías, compilándolos cuando hizo falta— y generó 117 GB de firmas BSim. Para Function ID, donde se obtienen estadísticas detalladas, la distribución es reveladora: el 60% corresponde al runtime de Golang (todas las versiones disponibles en su momento), el 35% a Boost, la librería C++ más ubicua, y el 5% restante a otras como LibXML, OpenSSL y libgcrypt. En conjunto: una masa de funciones que nadie vuelve a tener que revertir ni firmar a mano.

Caso práctico: Qubit Stealer

La muestra de prueba es un stealer de credenciales escrito en Golang. Con el análisis por defecto de Ghidra: 2.016 funciones, de las cuales una tiene nombre —la función de entrada. Tras aplicar Function ID se recupera aproximadamente el 40% de los nombres (y una función se fusiona). Añadiendo BSim con umbral 0,75 se recupera otro 16%, hasta un 58% del total.

La cifra parece modesta y tiene explicación: el autor tuvo acceso al código fuente del Qubit Stealer y el malware importa una librería de Golang para la que no existen firmas en el corpus. Generando firmas para esa librería, el porcentaje subiría. La lección es tan importante como los números: la calidad del resultado depende directamente de la cobertura de la base.

Metodología recomendada

El flujo propuesto, aceptando que es una propuesta abierta a feedback:

  1. Extraer todo el metadato disponible del binario (PCLNTAB en Go, etc.) y usarlo primero.
  2. Identificar runtimes y librerías presentes; si no hay firmas, generarlas.
  3. Aplicar Function ID (rápido, diseñado para el propósito) y después BSim.
  4. Solo entonces, lógica adicional —incluida la renombración asistida por LLM que mucha gente ya aplica, con o sin revisión—, todo dentro de una ejecución headless que puede dejarse corriendo de noche y encontrar el binario anotado por la mañana.

Sobre las limitaciones reconocidas: el rendimiento de BSim ante compiladores distintos no se ha probado a fondo, aunque el uso del descompilador abstrae parte de las diferencias —siempre que Ghidra conozca las convenciones de llamada—. Las opciones de compilación (optimización, -ffunction-sections, reubicación de símbolos) alteran el código y por tanto las firmas: si el cambio es grande, hay que bajar el umbral y ahogarse en falsos positivos. La opción más precisa, aunque costosa, es compilar las librerías objetivo con todas las combinaciones de opciones y firmarlas todas.

Técnicas y herramientas mencionadas

  • Ghidra: framework de ingeniería inversa de la NSA sobre el que se construye todo el pipeline; soporta ejecución headless para automatización.
  • Function ID: analizador de Ghidra que mapea hashes de funciones a nombres conocidos; equivalente a FLIRT en IDA.
  • BSim (behavioral similarity): sistema de similitud de funciones de la NSA basado en p-code del descompilador; calcula similitudes entre 0 (sin solape) y 1 (match exacto).
  • p-code: lenguaje intermedio que produce el descompilador de Ghidra; base de los vectores de similitud de BSim.
  • PCLNTAB: metadato de Golang del que se recuperan los nombres de función directamente.
  • Language ID de Ghidra: combinación de arquitectura/bitness/compilador (p. ej. PE 32 bits Windows); las bases Function ID se generan por cada uno.
  • Bases no size de BSim: ignoran tamaños de tipos para cruzar matches entre binarios de 32 y 64 bits.
  • Prefijos de renombrado genérico: estrategia para marcar funciones con múltiples candidatos y excluirlas de pasadas posteriores.
  • Corpus de firmas: 117 GB de firmas BSim y ~66 GB de binarios Go (main vacío con runtime completo) publicados en GitHub junto a los scripts.
  • Qubit Stealer: muestra Golang de prueba; 58% de funciones renombradas combinando Function ID + BSim 0,75.

Conclusiones

  • Antes de firmar nada, hay que explotar los metadatos del binario: en Golang la tabla PCLNTAB recupera los nombres sin esfuerzo alguno.
  • Function ID es la primera herramienta (rápida y hecha para esto) y BSim la segunda (más flexible, funciona incluso con similitud parcial gracias al p-code); ambas se automatizan headless y se complementan.
  • Las coincidencias genéricas no se descartan: se renombran con prefijos que aceleran y afinan las pasadas siguientes contra otras bases.
  • El 58% de recuperación en el Qubit Stealer sube si se firman las librerías que el malware importa: la cobertura de la base es el factor limitante, no la técnica.
  • Ante diferencias de compilación agresivas, la única vía precisa sigue siendo compilar las librerías con todas las opciones relevantes y firmar cada variante.
