Emular dispositivos Linux embebidos a escala con LightTouch

Fuente: «DEF CON 33 - Emulating Embedded Linux Devices at Scale w LightTouch Firmware Rehosting - S Polke» · ver el video original

Resumen

El equipo de investigación avanzada de CrowdStrike venía rehosteando firmware de Linux embebido con una inversión baja y un retorno alto. La idea central: no tocar para nada el user space. Nada de LD preload, nada de hacks durante el boot; se le ofrece al entorno de rehosting la imagen de firmware exacta —la misma que viene en la actualización oficial— y simplemente corre. Como el user space solo puede interactuar con lo que el kernel le da, todos los trucos se hacen en el kernel, construyendo el entorno alrededor del firmware en lugar de parchar el firmware.

Por qué el enfoque de user space se queda corto

La mayoría de la emulación embebida funciona en user space: una máquina QEMU ARM o MIPS genérica bootea un distro normal, se descomprime el firmware en el guest, se hace chroot y se ejecutan los binarios con LD preload para tapar las incompatibilidades. Funciona bien cuando el objetivo es un binario específico de un dispositivo específico. Pero compensar periféricos faltantes y una configuración de sistema distinta con LD preload tiene límites: cuando el sistema está diseñado para funcionar holísticamente, con muchas piezas moviéndose juntas, el parche a nivel de binario no alcanza.

El objetivo del equipo era distinto: investigación de vulnerabilidades y honeypots, o sea emulación de sistema completo, todo el sistema corriendo como correría en el dispositivo real. Emular un dispositivo puntual de forma completa exige demasiado tiempo y esfuerzo para el retorno; de ahí la idea de rehosting a escala.

Receta de rehosting

  1. Tomar el firmware stock de la actualización, descomprimirlo y extraerlo.
  2. Obtener del firmware la línea de comandos del kernel, el baud rate de la consola, si tiene UART y qué módulos necesita.
  3. Compilar un kernel para una máquina QEMU adecuada y bootear el sistema con los mismos bits, en el mismo orden en que los espera.

Los problemas concretos que aparecen son uno por dispositivo, pero generalizan bien.

NVRAM, el clásico

El ejemplo canónico de incompatibilidad es la NVRAM, el almacenamiento de configuración que en el hardware real vive fuera del sistema de archivos. El enfoque tradicional de user space la resuelve con LD preload de libnvram o derivados; acá no. En cambio, se interceptan esas llamadas dentro del kernel: un módulo de kernel implementa el manejo de NVRAM, y los valores por defecto se extraen del propio firmware para que el sistema vea la configuración que espera ver. Mismo resultado, pero sin tocar un solo binario del firmware.

UART y red

La salida de consola se redirige por UART emulado, lo que da visibilidad directa del boot y de los servicios al arrancar. Para la red, las interfaces del dispositivo se mapean a las de la máquina virtual y se puentean, de modo que los servicios del firmware quedan alcanzables como si fueran el dispositivo real.

    E --> G[Servicios accesibles: web UI, binarios]
    F --> G

La demo: un router desde la actualización oficial

La prueba de concepto corre sobre un router ASUS con SoC Broadcom (BCM4709, dual core ARM Cortex-A9, 128 MB de flash, 256 de RAM) y el firmware de la actualización oficial, sin modificaciones. Al arrancar, el kernel del rehosting toma el control, monta el rootfs del firmware y lanza los init scripts del fabricante. Con la red puenteada, la interfaz web de administración aparece en el puerto 80 del guest y es accesible desde afuera; las credenciales por defecto del fabricante entran sin problema.

Ese entorno completo habilita lo que el enfoque de user space no da: correr el daemon vulnerable con su configuración real, fuzzear los endpoints web en contexto, disparar honeypots que responden como el dispositivo real, y verificar vulnerabilidades de forma dinámica antes de confirmarlas sobre el hardware físico.

Limitaciones honestas

  • Blobs cerrados y drivers propietarios: los drivers wireless y otros módulos que dependen del hardware no funcionan en QEMU; los servicios que los exigen no arrancan.
  • Arquitecturas y periféricos exóticos: cada familia nueva de SoC trae sorpresas; el método es un patchwork, más proof of concept que framework pulido.
  • Fidelidad no es 100%: alcanza para research de vulnerabilidades y honeypots, pero hay interacciones de hardware que solo se reproducen en el dispositivo real.

Técnicas y herramientas mencionadas

  • QEMU full-system emulation con kernel compilado a medida por familia de dispositivo.
  • Rehosting de firmware stock sin modificar la imagen de actualización oficial.
  • Módulo de kernel para NVRAM con valores por defecto extraídos del firmware.
  • UART emulado para consola y observabilidad del boot.
  • Red puenteada para exponer los servicios del guest.
  • Honeypots y fuzzing de servicios web sobre el sistema rehosteado.

Conclusiones

  • El cambio de nivel es la clave: en lugar de parchar el user space binario por binario, se construye un kernel y un entorno que le dan al firmware todo lo que espera; el firmware ni se entera.
  • Es un enfoque de baja inversión y alto retorno: los problemas resueltos para un dispositivo generalizan al siguiente, lo que habilita emular muchas imágenes de firmware en lugar de una sola.
  • Para investigación de vulnerabilidades, tener el sistema completo corriendo en QEMU permite fuzzear, debuggear y verificar en un entorno reproducible, y recién después confirmar sobre el hardware.
  • Para defensores, el mismo pipeline produce honeypots fieles sin exponer hardware real.
