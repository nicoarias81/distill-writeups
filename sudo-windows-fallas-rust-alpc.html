Sudo para Windows: qué hay (y qué falla) bajo el capó

Fuente: «DEF CON 32 - Sudos and Sudon'ts: Peering inside Sudo for Windows - Michael Torres» · ver el video original

Resumen

Michael Torres (seguridad de tecnología operacional en Google, reservista del Cuerpo de Marines y voluntario de VetSec) destripó Sudo for Windows, la utilidad que Microsoft anunció para Windows 11 en la actualización H2 de septiembre. Todo el trabajo se hizo contra versiones de Insider Preview antes de que el código fuera publicado en GitHub: Torres llegó a analizar binarios de Rust en Ghidra — experiencia que no recomienda — y tuvo que distinguir dos binarios que Microsoft llamó "versión 1" sin incrementar el número de versión, usando la fecha de firma de código como única pista.

El funcionamiento, a alto nivel: Sudo apalanca UAC para ofrecer la experiencia de línea de comandos de Linux, devolviendo entrada y salida de la consola al prompt original mediante tuberías y redirección de los handles de consola (que en Windows son distintos de stdin/stdout/stderr). Ofrece tres modos — new window, input closed e inline — presentados de más seguro a menos seguro; Torres hizo la mayor parte de su investigación sobre inline por ser el objetivo más fácil. La coordinación entre el proceso sin privilegios y el privilegiado ocurre por ALPC, el framework de comunicación inter-proceso no documentado de Microsoft, vía un servidor que se levanta en un proceso elevado y recibe la petición con el comando, argumentos, directorio de trabajo y entorno a ejecutar.

Sobre esa base encontró cuatro problemas. Dos "sin impacto de seguridad" según MSRC pero curiosos: una corrupción de memoria en Rust — sorprendente por definición — causada por asumir que un path apuntaba a un buffer terminado en null cuando en realidad era un vector de bytes; un path con backslash inicial provocaba una lectura en exceso del heap hasta el primer byte nulo, permitiendo leer memoria de allocaciones previas aunque sin control fino sobre qué se lee. Y una confusión de orden de búsqueda: el path se resolvía en el contexto del proceso privilegiado, con otro directorio de trabajo, así que sudo cmd.exe ejecutaba el cmd.exe de system32 en lugar del binario local del usuario. Microsoft respondió que no era vulnerabilidad — pero lo arregló igual.

Los dos hallazgos con impacto real son más serios. El primero: ejecución de código cruzando usuarios. Tras el blog post de un compañero de Google que documentó que el servidor RPC carecía por completo de autenticación, Microsoft añadió una comprobación que solo comparaba el nombre de imagen del proceso cliente con el del servidor (ambos sudo.exe). Torres lo burló inyectando una DLL en un proceso sudo propio — con el nombre de imagen legítimo — y usando que el nombre del puerto ALPC se deriva del PID del proceso sin privilegios, que cualquier usuario puede consultar. El ataque es una carrera: el implant espera a que la víctima ejecute sudo, corre para conectarse al servidor objetivo antes de que el proceso legítimo lo haga, y ejecuta el comando que quiera en el contexto de esa víctima, que solo ve que "no pasó nada" tras aceptar el prompt de UAC. La ventana era cortísima porque la API bloquea llamadas futuras apenas se atiende la primera petición de elevación; ganó la carrera en un depurador primero y tras muchas iteraciones en vídeo. Fue parcheado en la segunda iteración de la "versión 1", firmada el 4 de marzo.

El segundo, reportado el 13 de junio, sigue bajo embargo: permite a un usuario sin privilegios manipular los datos de entrada y salida del sudo de un usuario privilegiado, con divulgación de información incluida. Torres lo descubrió — según cuenta — durante una carrera huyendo de las diapositivas, dándose cuenta de que había más problemas en el diseño cliente-servidor.

La lección grande va más allá de Sudo: en Rust no se puede llamar a las APIs nativas de Windows (CreateProcess, ShellExecute, etc.) sin entrar en código unsafe — vía los crates windows o windows-sys de Microsoft. Eso significa que un programa en Rust que toque APIs de Windows puede tener corrupción de memoria como cualquier otro: si estás cazando bugs y ves un binario de Rust llamando APIs nativas, pica en esa frontera.

Conclusiones

  • Sudo for Windows eleva procesos vía UAC y coordina la ejecución por ALPC (framework no documentado de Microsoft), devolviendo stdin/stdout/stderr y consola al prompt original mediante tuberías y redirección de handles.
  • Los tres modos (new window, input closed, inline) van de más a menos aislados; inline — el más expuesto — fue el banco de pruebas principal de la investigación.
  • "Escrito en Rust" no implica seguro: llamar APIs nativas de Windows exige unsafe (crates windows/windows-sys), y ahí aparecen lecturas en exceso del heap; el bug de Sudo se originó en la suposición C de un buffer terminado en null sobre un vector de bytes.
  • La autenticación original del servidor RPC (comparar nombre de imagen del cliente) era trivialmente burlable: una DLL inyectada en un proceso sudo propio hereda el nombre legítimo, y el nombre del puerto ALPC es predecible porque se deriva del PID, visible para cualquier usuario.
  • El resultado fue ejecución de código cruzando usuarios mediante una carrera contra la víctima: el atacante corre para atender la petición de elevación primero y ejecuta su comando en el contexto del usuario privilegiado, que solo percibe que el comando no hizo nada.
  • MSRC clasificó dos de los hallazgos como "sin impacto de seguridad" y aun así los arregló; un cuarto hallazgo (manipulación de E/S del sudo de otro usuario, con divulgación de información) quedó bajo embargo al momento de la divulgación.
  • El prompt de UAC de sudo no muestra qué comando va a ejecutar realmente — solo que es una invocación de sudo — algo que Microsoft se comprometió a mejorar; y sí, la comunidad ya pidió el modo "insults" de sudo para Windows.
