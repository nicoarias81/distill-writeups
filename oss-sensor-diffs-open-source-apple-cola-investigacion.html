OSS Sensor: convertir los diffs open source de Apple en una cola de investigación priorizada

Fuente: «DCSG1 - Augmenting Apple's Source Code and OS Logs with AI Agents -Olivia Gallucci» · ver el video original

Resumen

Un flujo de trabajo con IA para investigación de vulnerabilidades en macOS que trata el código open source de Apple como un sensor, y a los agentes de IA como el motor que convierte ese sensor en una cola de triage priorizada: qué cambió, qué parece relevante para seguridad, qué hacer reversing y qué fuzzear. La herramienta resultante, OSS Sensor, genera esa cola a partir de diffs del OSS de Apple, características básicas de binarios y plantillas de logs, con scoring por reglas — sin LLM integrado ni verificación de vulnerabilidades: es una ayuda de triage y generación de hipótesis, no un descubridor automático de vulnerabilidades. La narrativa es diff → hipótesis → harness, y la filosofía explícita: el modelo no es un dios, es un analista junior con herramientas — lo que además mantiene los costos a raya.

El código abierto de Apple como sensor

Un sensor es cualquier fuente de datos que produce señales sobre el estado de un sistema sin interpretarlas. Apple publica más de lo que se espera: el kernel XNU, librerías core como LibSystem, LibC y LibDispatch, y daemons históricos como launchd. Pero no todo: faltan componentes o están parcialmente disponibles (CoreFoundation, CFNetwork, drivers de iOS, partes de libダイアlogue y core crypto, con restricciones de redistribución), y los drops suelen ser incompletos o desactualizados — headers que referencian archivos inexistentes, instrucciones de build ausentes.

La clave es tratarlo como un mapa: puede que no esté el cuadro completo, pero los puntos de referencia son reales. Investigadores y agentes usan el open source como referencia mientras trabajan con los binarios propietarios: tomar launchd, syslogd o un driver, casar patrones de funciones conocidas con el source que exista, anotar patrones de llamadas y hacer reversing de la lógica desconocida. Incluso con símbolos stripped, estructura + constantes de string + uso de syscalls permite mapear de vuelta al código abierto.

Las herramientas básicas que aparecen una y otra vez: strings (mensajes de debug, format strings, paths), what (versión e info de proyecto), nm (nombres de símbolos, sobre todo en binarios unstripped) y class-dump (interfaces de frameworks privados y métodos Objective-C), más el manifest de distribución de Apple para cruzar componentes por release. Son pasos repetitivos y dependientes de contexto — exactamente lo que se le entrega a un agente como herramientas: que llame a strings, parseé la salida, recupere los chunks de source correspondientes y produzca conclusiones acotadas con citas a lo observado. No se quiere un modelo inventando hechos.

Diffs quirúrgicos: el caso syslogd

El ejemplo favorito del flujo: en 2016, un reverser usó Diaphora para diffear syslogd entre 10.11.2 y 10.11.3 y encontró que una sola función cambió — un fix de aritmética de aloca­ción: value + 4 pasó a value * 4 + 4. Con mentalidad de explotación eso es sospechoso: parece la mitigación de un heap overflow, y un string cercano ("add lockdown session, realloc failed") daba la pista de vuelta al source. Ese diffing quirúrgico es cómo se reversan vulnerabilidades después del parche, y por qué importa: los fixes a menudo deben aplicarse en múltiples ubicaciones, y si código idéntico se parchea en unos archivos y no en otros, los no parcheados siguen vulnerables. Cuanto más grande y burocrática la organización, más errores repetidos en archivos vecinos.

Imaginar ese flujo corriendo continuamente en cada release de Apple: ingestar tags, tarballs y manifests nuevos, computar diffs a nivel de función y semántico, scorear los cambios por relevancia de seguridad (aritmética de aloca­ción, bounds checks, entitlement gating, parsing de XPC, cambios en tablas de métodos externos de IOKit), correlacionar con binarios y string anchors, y emitir una cola rankeada con pointers para validación humana. Para investigación ofensiva individual fue un multiplicador de throughput — probado solo en componentes pequeños, nunca el OS completo — y para una organización comprimiría el ciclo desde "Apple acaba de shippear algo" a "identificamos estos comportamientos y superficies cambiadas" en tiempo de ajustar monitoreo y triage.

Arquitectura del pipeline agéntico

flowchart TD
    A[Diffs OSS + binarios + logs unificados] --> B[Retriever: índice de código OSS,
símbolos, notas, plantillas de logs]
    B --> C[Toolbox: strings, otool, class-dump,
queries de logs - analizadores deterministas]
    C --> D[Agentes especializados:
diff triage · re-context · hipótesis · planning]
    D --> E[Cola de triage rankeada + hipótesis
+ planes de tracing/fuzzing]
    E --> F[Humano: exploitability,
privilege boundaries, validación]

Los agentes son un conjunto coordinado de tool-users que convierte inputs crudos en outputs con evidencia. El retriever es la capa de indexación que busca sobre el código OSS embebido, símbolos, notas y plantillas de logs. El toolbox reúne analizadores deterministas y comandos de sistema — los agentes llaman para juntar hechos en vez de adivinar. Varios agentes manejan el output: triage de diffs, re-context, hipótesis, planning y análisis (cuáles funcionan mejor, no se puede decir; cómo se contabiliza, sí).

El modelo se trata como un ingeniero junior que lee rápido, sigue procedimientos y genera hipótesis estructuradas para validar con reversing, tracing y fuzzing. Advertencia práctica: cada paso puede fallar y todos dependen entre sí; conviene que el setup lo contemple, porque un plan pago con límites se puede quemar en 3.000 dólares de golpe.

Logs unificados: la señal nueva

La gran adición sobre el flujo clásico de "usar OSS de Apple para reversar" son los logs. Unified logging da etiquetas de subsystem y category que mapean a componentes, message strings estables que se pueden cazar en binarios y source, y hints de ejecución para reconstruir diagramas de flujo de datos sin tener el source completo. Se tratan como un pivote hacia la superficie de ataque y los code paths, no como doctrina: dicen qué componentes manejaron realmente un input (vía subsystem/category, más sender image info) y qué error paths se dispararon — lo que revela supuestos de parsing, expectativas de tipos y contratos IPC. ROI alto para selección de targets, diseño de harnesses y la pregunta de qué fuzzear después.

Tres tareas acotadas que un agente hace bien con logs: tomar una línea de log y encontrar dónde vive ese string en un binario (vía strings) hasta su basic block y caller; recuperar el código OSS adyacente a esos callers si existe y producir un resumen estructurado (inputs, trust boundaries, parsing); y alimentar el fuzz planning y el detection engineering — qué fuzzear, qué parámetros controla el atacante, cómo se ven los modos de falla. Cuando el pipeline aprende un nuevo límite de input no confiable o un nuevo entry point XPC privilegiado, eso se traduce en requerimientos de telemetría y reglas de correlación: convertir investigación de vulnerabilidades en cobertura de detección. El precedente son los kernel extensions: diffeando kexts entre versiones, investigadores hallaron cambios en tablas de métodos externos que exponen entry points nuevos o parcheados en drivers IOKit.

El fuzz planner: planes, no exploits

Lo que produce el agente planner no es un exploit: es un plan general. Enumera superficies candidatas (handlers de syscalls, user clients de IOKit, servicios XPC, parsers) para enfocarse en entry points controlados por el atacante que crucen un trust boundary. Propone un driver o harness mínimo con el path de invocación, los entitlements requeridos y las formas de input esperadas, de modo que el target sea alcanzable y reproducible. Recomienda una estrategia de seeds — diccionarios extraídos de strings, parámetros minados de logs, bootstrap desde tráfico observado — para que la cobertura crezca rápido en vez de mutar desde nada. Y define métricas de éxito: bucketing de crashes, señales de sanitizers, stack traces únicos.

Dónde se rompe hoy el flujo: pedirle cadenas de exploit completas. Los modelos inventan pasos de vez en cuando — sobre todo si se les conecta un chatbot — así que se mantiene acotado a predicción de bug class y diseño de harnesses, los outputs de más valor, dejando la exploitability en manos humanas. Para chequear hipótesis contra trabajo establecido sirven las publicaciones de Patrick Wardle (contra las que se contrastan las hipótesis propias con IA), y OSS Sensor se licenció GPLv3 precisamente para devolver el favor a esa tradición de código compartible.

Técnicas y herramientas mencionadas

  • OSS Sensor: herramienta de triage que genera una cola priorizada a partir de diffs del código OSS de Apple, características básicas de binarios y plantillas de logs; scoring por reglas, sin LLM integrado.
  • Diffing binario: Diaphora (el caso syslogd entre 10.11.2 y 10.11.3) y diffs de kernel extensions; los fixes aplicados a unos archivos y no a otros como fuente de vulnerabilidades.
  • strings: localizar una línea de log en el binario hasta su basic block y caller.
  • Unified logging: las plantillas de logs como señal complementaria a los diffs de código.
  • XPC: los entry points privilegiados nuevos detectados en el código se traducen en requerimientos de telemetría.
  • Agentes de IA con herramientas: el modelo como analista junior con grep y lectura de código, no un oráculo; mantiene costos bajos.
  • Fuzz planning y detection engineering: qué fuzzear, qué parámetros controla el atacante y cómo convertir los hallazgos en reglas de correlación.

Conclusiones

El source parcial de Apple es poderoso: combinado con análisis de binarios se reversan sus sistemas con precisión sorprendente, con las restricciones de releases incompletos, ofuscación y licencias. El pipeline es compliant by design: indexación local, manejo cuidadoso de los drops y trazabilidad de provenance para poder explicar cada conclusión. La narrativa final — diff a hipótesis a harness — convierte el churn de plataforma de Apple en cobertura: investigación más escalable, enseñable y útil operativamente. Para quien quiera seguir el trabajo, existe un newsletter enfocado en seguridad de Apple con publicaciones mensuales (o cada dos meses).
