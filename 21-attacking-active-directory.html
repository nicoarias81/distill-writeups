Overview

Module 21 focuses on three hardening/abuse areas of a typical Windows enterprise:

  • Kerberos delegation — unconstrained, constrained, and resource-based constrained delegation, and how each can be abused to compromise privileged accounts.
  • Just Enough Administration (JEA) — constrained administration endpoints and how to break out of them.
  • Just-In-Time (JIT) access — time-boxed administrative access via a JIT manager application and GPO-driven group membership.

Enumeration techniques shown are tailored to each specific scenario; in a real engagement, adapt the same methodology to find misconfigurations in the target environment.

Learning Objectives

  • Unconstrained Delegation
  • Constrained Delegation
  • Resource-Based Constrained Delegation
  • Just Enough Administration (JEA) and its restrictions
  • Just-In-Time access

Kerberos Delegation

Kerberos delegation solves the double-hop issue: a frontend service (e.g. a web app using Windows Authentication) receives only the user's service ticket, which cannot be used to authenticate to a backend (e.g. a database) on the user's behalf. Microsoft's delegation mechanisms let the frontend authenticate to backend services on behalf of the user.

Unconstrained Delegation

Concept. When a service is configured with unconstrained delegation, a user requesting a service ticket also embeds their forwardable TGT into the request. The service receives and stores the user's TGT, allowing it to authenticate as that user to any service — not just the intended backend. Any account (machine or service account) can be configured for it.

Notes:

  • Modern browsers block automatic delegation to services with unconstrained delegation unless the service is in the browser's trusted delegation list, but organizations may still allow it for backwards compatibility.
  • The DC stores delegation configuration in userAccountControl (TRUSTED_FOR_DELEGATION, value 524288).

I am a Domain Controller

Concept. Instead of waiting for users, we can force a high-privileged authentication: coerce the domain controller's machine account (a de-facto Domain Admin) to authenticate to our unconstrained-delegation machine using the printer bug (MS-RPRN RpcRemoteFindFirstPrinterChangeNotification), then capture its TGT and DCSync.

Constrained Delegation

Concept. Constrained delegation uses two Kerberos extensions — S4U2Self and S4U2Proxy. It is configured on the computer or user object via the msds-allowedtodelegateto property, which lists the SPNs the object may delegate to.

  • S4U2Self: a frontend service that doesn't use Kerberos itself can request a TGS to itself on behalf of any user from the KDC. If we compromise such an account, we can request tickets as any domain user — including a domain administrator.
  • S4U2Proxy: using the TGS obtained via S4U2Self (or a forwardable TGS supplied by the user), the frontend requests a service ticket to a backend service listed in msds-allowedtodelegateto on behalf of that user. Two separate TGSs are involved, both requested on behalf of the user.
  • The TRUSTED_TO_AUTH_FOR_DELEGATION value in useraccountcontrol indicates whether the account can use protocol transition (S4U2Self without a user-supplied ticket).

Listing 15 — Enumerating constrained delegation (PowerView from CLIENT01 as adam):

PS C:\Tools> Get-DomainUser -TrustedToAuth
...
distinguishedname        : CN=IISSvc,OU=Service,OU=CorpUsers,DC=corp,DC=com
samaccountname           : iissvc
msds-allowedtodelegateto : {MSSQLSvc/sql01.corp.com:SQLEXPRESS, MSSQLSvc/sql01.corp.com:1433}
serviceprincipalname     : HTTP/web.corp.com
useraccountcontrol       : NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD, TRUSTED_TO_AUTH_FOR_DELEGATION
...

Key observations: the IISSvc service account has constrained delegation; it may only delegate to the MS SQL server on SQL01; and protocol transition is enabled — the scenario we exploit.

Attack from Kali (works from a non domain-joined machine; point DNS at the DC via /etc/resolv.conf since the DC also runs DNS; cleartext password or NTLM hash both work — no need to run as IISSvc):

[*] Saving ticket in iissvc.ccache

kali@kali:~$ export KRB5CCNAME=iissvc.ccache

Windows injects tickets into memory; on Linux we point the KRB5CCNAME variable at a ccache file instead.

We are logged into the MSSQL instance as the domain administrator. Compromising any account with constrained delegation grants access to every service in its msDS-AllowedToDelegateTo list — from there, chase the service for code execution.

Resource-Based Constrained Delegation (RBCD)

Concept. Classic constrained delegation requires SeEnableDelegationPrivilege (domain admin–level) to configure SPNs on the frontend. RBCD (Windows Server 2012+) flips it: the backend resource sets msDS-AllowedToActOnBehalfOfOtherIdentity on its own object, listing which principals may delegate to it. No SeEnableDelegationPrivilege needed — the backend service administrator can typically configure it.

Requirements and implications:

  • The frontend service must have an SPN. User accounts normally don't; computer accounts always do.
  • If we can compromise a frontend listed in msDS-AllowedToActOnBehalfOfOtherIdentity, the same S4U2Self/S4U2Proxy attack as constrained delegation applies.
  • RBCD is not pre-configured in the lab — we must find write access to a computer object and configure it ourselves.

Listing 20 — Enumerating GenericWrite on computer objects (PowerView from CLIENT01 as adam):

PS C:\Tools> Get-DomainComputer | Get-ObjectAcl -ResolveGUIDs | Foreach-Object {$_ | Add-Member -NotePropertyName Identity -NotePropertyValue (ConvertFrom-SID $_.SecurityIdentifier) -Force; $_}
...
ObjectDN              : CN=BACKUP01,OU=CorpComputers,DC=corp,DC=com
ActiveDirectoryRights : ListChildren, ReadProperty, GenericWrite
Identity              : CORP\mary
...

The mary user has GenericWrite on BACKUP01 — she can set any non-protected property, including msDS-AllowedToActOnBehalfOfOtherIdentity.

Takeaways:

  • Constrained delegation compromise = access to all services in msDS-AllowedToDelegateTo; RBCD compromise = impersonate any user on the resource we control delegation rights for.
  • Enumerate both directions: accounts with TRUSTED_TO_AUTH_FOR_DELEGATION and users holding write rights on computer objects (MachineAccountQuota makes any domain user a potential computer-account owner).

Just Enough Administration (JEA)

Concept. JEA (introduced in Windows Server 2016) provides delegated administration via PowerShell: instead of giving a user full admin rights on a server, they connect to a restricted session endpoint and may only run explicitly allowed commands — executed with administrative privileges. Setup requires three things from the admin side:

  1. A Session Configuration File (.pssc) — created with New-PSSessionConfigurationFile.
  2. A Role Capabilities File (.psrc) — created with New-PSRoleCapabilityFile.
  3. Registration with Register-PSSessionConfiguration.

Theory notes

Listing 26 — Default PSSession Configuration file:

@{
    # Session type defaults to apply for this session configuration.
    # Can be 'RestrictedRemoteServer' (recommended), 'Empty', or 'Default'
    SessionType = 'Default'

    # Directory to place session transcripts for this session configuration
    # TranscriptDirectory = 'C:\Transcripts\'

    # Whether to run this session configuration as the machine's (virtual) administrator account
    # RunAsVirtualAccount = $true

    # User roles (security groups), and the role capabilities that should be applied to them
    # RoleDefinitions = @{ 'CONTOSO\SqlAdmins' = @{ RoleCapabilities = 'SqlAdministration' } }
}

Key fields: SessionType (RestrictedRemoteServer is the recommended hardening value), TranscriptDirectory (logs who ran what), RunAsVirtualAccount (temporary local-admin context), and RoleDefinitions (which AD groups map to which role capability files).

Listing 27 — Partial view of the Role Capability file for JEA:

...
# Cmdlets to make visible when applied to a session
# VisibleCmdlets = 'Invoke-Cmdlet1', @{ Name = 'Invoke-Cmdlet2'; Parameters = @{ Name = 'Parameter1'; ValidateSet = 'Item1', 'Item2' } }
...
# Providers to make visible when applied to a session
# VisibleProviders = 'Item1', 'Item2'
...

VisibleCmdlets controls what the connecting user may run — e.g. Start-Process without parameter validation effectively grants arbitrary code execution. VisibleProviders exposes PowerShell providers (none are available in a JEA session by default):

Listing 28 — Available PowerShell providers:

PS C:\Tools> Get-PSProvider
Name                 Capabilities                                      Drives
----                 ------------                                      ------
Registry             ShouldProcess, Transactions                       {HKLM, HKCU}

A user given the FileSystem provider effectively has access to the entire file system (what they can do with it still depends on their permissions).

Enumerating and Breaking out of JEA

JEA is enforced by PowerShell, not Active Directory, so no AD attributes reveal it — enumeration relies on network reconnaissance (WinRM/PS-Remoting ports) and information gathered during lateral movement. Always check PowerShell history on any machine and account we obtain.

Listing 35 — Copying the hosts file as a write test:

Listing 36 — Verifying the copy from the local prompt:

# Copyright (c) 1993-2009 Microsoft Corp.
...

Copy-Item reads and writes anywhere with admin privileges — effectively administrative CIFS-like access on FILES02, which can usually be turned into SYSTEM code execution. A cheap option is dropping a payload into C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Startup\ (waits for a reboot/login). The cleaner option is DLL hijacking via the Windows DLL search order:

  • The directory from which the application is loaded (e.g. C:\Program Files\application)
  • The system directory (C:\Windows\System32)
  • The 16-bit system directory
  • The Windows directory
  • The current directory
  • Directories listed in PATH

If a service's application directory contains a load attempt for a non-existent DLL, we can plant our own DLL (payload) there — the JEA admin privileges do the writing, and the service loading our DLL does the executing.

Enumeration on FILES02: FileZilla-Server 1.7.0 is installed and running; on service start it attempts to load DLLs from its own application directory. Replicate the attack on CLIENT01 first (FileZilla-Server is installed there too): run Process Monitor as adam (log in on CLIENT01; Procmon is in C:\Tools), set filters, start the FileZilla-Server service, and inspect which DLLs filezilla-server.exe tries to load from its own directory.

Choosing the right DLL matters: services load DLLs early, and a DLL that fails to load can crash the service before our code runs. DLL proxying solves this — the malicious DLL forwards calls to the legitimate one. Trial and error shows three of the six candidate DLLs yield a shell on CLIENT01; the other two crash the service. Listing 37 — Generating the hijack DLL with msfvenom (we chose msasn1.dll):

No encoder specified, outputting raw payload
Payload size: 510 bytes
Final size of dll file: 9216 bytes

After testing on CLIENT01 and getting a shell, move back to CLIENT02 (as mary) and use the JEA configuration to stage the payload.

Just-In-Time (JIT) Access

Concept. JIT Administration grants users privileges for a limited time via time-based group membership instead of permanent admin rights. When used with AD it relies on the Privileged Access Management (PAM) feature (a one-way forest trust + memberTimeToLive-style time-bound group membership). Microsoft's own solution is MIM (Microsoft Identity Management), but the lab uses a custom JIT manager web application — such systems must be secure at all costs, since compromising them devastates the domain.

JIT exploitation typically happens in the later stages of an assessment. Enumeration: JIT requires PAM to be enabled, but PAM being enabled doesn't guarantee JIT is in use (it also supports time-based group membership for other solutions).

Mary is not a member of any JIT group. Request access to Web01 via the JIT manager ("Create New Request") — status is pending until approved. We simulate approval by logging in to CLIENT02 as james, opening http://mgmt01, clicking Review Requests, approving, and waiting for Processed? to change from Waiting... to Processed (up to one minute in the labs).

Access denied — mary's current Kerberos ticket doesn't contain the new group membership. A new ticket is obtained by logging off/on, rebooting, or purging the ticket cache:

We are now in BUILTIN\Administrators on WEB01 via the la_web membership — local admin on the web server. The JIT manager also offers the SQL instance path for further escalation.

Takeaways: JIT limits permanent high-privileged accounts, but the JIT manager itself, the approval chain (j_approve), and the GPO/SYSVOL configuration mapping groups to local admin rights are all attack surface. After approval, remember the ticket refresh step (klist purge or re-logon) before the access actually works.

Wrapping Up

This module explored techniques for exploiting Active Directory and its hardening features: the forms of Kerberos delegation (unconstrained, constrained, resource-based) and the vulnerabilities they introduce when mismanaged, then JEA and JIT access — two mitigation strategies that limit the number of high-privileged accounts, and how each can be broken out of or abused. The overarching lesson: penetration testers must understand the vulnerabilities hiding in an organization's security policies and configurations.
