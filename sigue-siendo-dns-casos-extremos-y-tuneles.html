Sigue siendo DNS: casos extremos, túneles y explotación

Fuente: «DCSG1- Its Still DNS - David Leadbeater» · ver el video original

Resumen

El nombre del problema es un chiste clásico de las comunidades de operaciones, pero David Leadbeater lo toma en serio: DNS sigue siendo un protocolo con casos extremos sorprendentes y útiles tanto para depurar como para atacar. El recorrido va de qué caracteres son válidos en una consulta, a cómo eso derrota el mecanismo de confianza de SSH, inyecta texto en la terminal, se cuela por los comodines en navegadores y termina en un chat cifrado que funciona dentro de un navegador sobre DNS sobre HTTPS.

Qué es realmente válido en DNS

Casi cualquier cosa. Con dig (mejor que nslookup o host para ver todos los campos de la consulta), se puede preguntar por un nombre con espacios — codificados como escape decimal 32, no octal, detalle que confunde a todos — con comillas UTF-8, con asteriscos, con caracteres de control e incluso con un punto escapado dentro de una etiqueta. El error más común al leer la salida de dig: buscar el error donde no está. Hay que mirar la línea de estado — status: NOERROR — porque "no error" es la respuesta de error implícita cuando algo falla silenciosamente.

La vulnerabilidad de SSH: CVE del carácter coma

La cadena: en una máquina con musl libc (Alpine) o macOS, el filtrado de caracteres de nombre de host es más laxo que en otros sistemas. ssh github.com, con una coma final es un nombre válido para DNS; el server responde, el usuario acepta la clave en el prompt usual de trust on first use, y known_hosts registra github.com, con la clave del atacante. Como la coma es el separador de hostnames en known_hosts, después ssh github.com — el legítimo — encuentra una coincidencia en el archivo y el MITM queda tapado por el mecanismo de confianza de SSH, no por DNS.

La explotación práctica es vía git clone de un repositorio malicioso: el .gitmodules de un submódulo puede contener la cadena con escape que hace que el usuario vea github.com cuando en realidad se conecta a otra cosa. El usuario escribe "yes" sin ver qué tipea (el prompt no muestra el input) y clona el repositorio del atacante con su MITM activo. De ahí se puede escalar: varios submódulos, distintos comportamientos según cuándo se escribieron las claves.

El fix llegó en OpenSSH 10.0, que simplemente rechaza conexiones a hostnames con comas. La lección de fondo: los RFC de DNS definen qué es válido, pero cada libc y cada OS filtran (o no) de forma distinta — el mismo ping foo,bar falla en Windows y funciona en macOS, y de paso Windows imprime el CNAME devuelto sin escaparlo, lo que permite inyectar códigos ANSI a la terminal (rojo, newline, borrado de línea) desde una respuesta DNS. ping de Windows, traceroute de Windows y nslookup de BusyBox quedan afectados; Microsoft y BusyBox, reportados hace años, no mostraron interés en arreglarlo. Combinado con las vulnerabilidades de emuladores de terminal (el eje de una charla anterior del autor en DEF CON 31, más un bug reciente en iTerm2 hallado con IA), la inyección puede llegar a ejecución de código.

Comodines, IDN y comportamiento de clientes

Los comodines DNS no los maneja el cliente: los expande el servidor, y esa expansión tiene comportamiento variable según el proveedor — Cloudflare no resuelve nombres con caracteres de control, Amazon Route 53 u otros sí. Un mismo test da resultados distintos según el servidor autoritativo, lo que complica tanto el debugging como los ataques.

En el navegador, la divergencia es entre Safari y Chrome: Safari muestra emojis y otros caracteres Unicode en la barra de direcciones tal cual, Chrome muestra la forma punycode. Safari además tiene protecciones — un emoji de candado en el hostname fuerza la representación punycode — pero la ventana para confundir usuarios existe, y alcanza con un registro comodín en un subdominio propio.

Límites y túneles sobre DNS

  • Nombre consultado: máximo 255 caracteres.
  • TXT records: el límite de 255 bytes es por cada string; se pueden concatenar, así que en la práctica no hay límite útil más allá del tamaño del mensaje.
  • UDP: respuestas de ~1 KB; el fallback a TCP permite paquetes casi de 65 KB.

El túnel sobre DNS tiene más de veinte años: Iodine con su negociación adaptativa de qué caracteres permite cada servidor, DNScat2 (relevante para respuesta a incidentes: es lo que un atacante puede tunelar por tu servidor DNS interno), el "Wikipedia over DNS" del propio autor en 2008, y las ideas de Dan Kaminsky con voice over DNS y las señales estándar de E/S encapsuladas en consultas.

El cierre: DNS sobre HTTPS desde el navegador, con certificados de IP

La novedad es combinar tres piezas:

  1. DoH con CORS: Google (y otros) sirven DNS sobre HTTPS con cabeceras CORS, así que JavaScript en cualquier página puede consultar dns.google y parsear la respuesta JSON.
  2. TXT records largos vía TCP fallback: caben casi 65 KB por consulta — suficiente para entregar un payload real (malware ya hizo esto con un .exe chico en un TXT, pero sin DoH).
  3. Certificados para direcciones IP: Let's Encrypt ya emite certificados de validez corta para IPs (Google lleva años con el 8.8.8.8). El resultado: el tráfico va por HTTPS a una IP literal, sin query DNS en el cable — invisible para quien monitorea DNS salvo que inspeccione SNI.

La demo que junta todo es DNS Chat, abierto: un cliente de chat donde cada mensaje es una consulta DNS con la clave del canal cifrada en el nombre consultado. Funciona desde el navegador (consola abierta, mensajes numerados que filtran metadatos mínimos), desde IRC vía un proxy que el autor escribió, y — detalle clave — desde una URL file://, porque CORS no aplica. Un archivo HTML guardado en cualquier lado chatea por DoH contra una IP con certificado sin que en la red haya ninguna consulta DNS. El cliente aún no es adaptativo (probar varios endpoints DoH, recurrir a DNS directo), pero la arquitectura permite que un atacante haga exactamente eso.

Técnicas y herramientas mencionadas

  • dig — lectura de status/NOERROR, escapes decimales, debug de respuestas truncadas.
  • known_hosts + trust on first use — vector de envenenamiento con hostname coma (OpenSSH < 10.0).
  • musl libc / macOS — sistemas con filtrado laxo de caracteres en hostnames; Windows y BusyBox con output sin escapar.
  • Códigos ANSI en respuestas DNS — inyección de color/newline/clear en ping, traceroute y nslookup.
  • Wildcard DNS — expansión del lado del servidor, divergencia Cloudflare vs. Route 53.
  • IDN / punycode — diferencia de rendering Safari vs. Chrome, emoji en la barra de direcciones.
  • TXT concatenados + TCP fallback — payloads de ~65 KB por consulta.
  • DoH + CORS + certificados IP (Let's Encrypt) — túnel completo desde el navegador sin visibilidad DNS.
  • Iodine, DNScat2 — herramientas clásicas de tunneling sobre DNS, relevantes para detección y respuesta.
  • DNS Chat — demo open source del autor: chat cifrado sobre DoH desde file://, IRC y web.

Conclusiones

  • Los casos extremos de DNS no son curiosidades: un carácter válido pero inesperado (la coma) bastó para derrotar el trust on first use de SSH en sistemas con filtrado laxo.
  • Los clientes que imprimen respuestas DNS sin escapar convierten cualquier respuesta en un vector de inyección de terminal, y los mantenedores no siempre van a arreglarlo.
  • DoH + certificados de IP + TXT largos cierran el círculo: DNS se convierte en un canal de datos completo, cifrado y usable desde un archivo HTML local, invisible para el monitoreo tradicional de DNS.
  • Para defensores: vale la pena bloquear o alertar sobre protocolos de tunneling conocidos (DNScat2, Iodine), considerar interceptar por SNI cuando no hay query DNS en el cable, y tratar las respuestas DNS como datos no confiables que un cliente puede terminar imprimiendo.
