Del servidor a la cámara: cómo se toma el control completo de una flota de videovigilancia Axis

Fuente: «DEF CON 33 - Turning Camera Surveillance on its Axis - Noam Moshe» · ver el video original

Resumen

El ecosistema de videovigilancia de Axis — cámara IP empresariales con su propio Linux modificado, un servidor de gestión centralizado y aplicaciones cliente .NET — depende de un protocolo propietario, Axis Remoting, para que las empresas vean y administren sus flotas a distancia. El protocolo viaja cifrado con mTLS y autenticado con NTLM, y esa combinación se presentaba como garantía suficiente para exponerlo a internet.

El análisis del protocolo demuestra lo contrario. Una deserialización JSON con TypeNameHandling.Auto abre la puerta a ejecución remota de código en el servidor; la ausencia de firma en los mensajes NTLM permite secuestrar sesiones de clientes legítimos en escenarios de intermediario; y un protocolo de respaldo sobre HTTP con un endpoint de autenticación anónima elimina por completo el requisito de credenciales. El resultado: código ejecutándose en el cliente, en el servidor y en las cámaras, sin autenticación previa. Casi 6.500 servidores con Axis Remoting estaban expuestos a internet al momento del estudio.

El flujo de ataque paso a paso

La ruta hacia el control total de la flota encadena varias etapas, cada una aprovechando un diseño distinto del protocolo:

  1. Reconocer el servicio en internet mediante motores de búsqueda de dispositivos expuestos.
  2. Interceptar o emular la comunicación para entender un protocolo sin documentación alguna.
  3. Descubrir la deserialización insegura que convierte mensajes JSON en ejecución de código.
  4. Evitar la autenticación, ya sea reenviando el desafío NTLM de un cliente real o entrando por el canal de respaldo anónimo.
  5. Pivotar del servidor a las cámaras usando funciones de administración legítimas.

Qué es Axis Remoting y por qué existe

Axis fabrica cámaras IP orientadas al mercado empresarial: oficinas, universidades, hospitales, agencias gubernamentales. Todas corren Axis OS, un fork de Linux fuertemente modificado. Cuando una compañía tiene docenas de pisos y sedes físicas distintas, controlar cada cámara a mano es inviable, así que Axis provee:

  • Axis Device Manager: la consola central para configurar, respaldar y actualizar el firmware de toda la flota.
  • Axis Camera Station: la matriz de video en vivo desde la que los guardas supervisan las cámaras.

Como las sedes no comparten red, ambos productos necesitan acceso remoto. La solución de nube de Axis, Secure Access, se factura por tráfico y resulta demasiado cara para la mayoría de organizaciones, que optan por servidores on-premise con el puerto de Axis Remoting abierto hacia afuera. El protocolo promete estar "completamente cifrado y autenticado"; el riesgo real es otro.

Ingeniería inversa de un protocolo cerrado

Sin documentación, sin clientes de terceros y sin estudios previos, la única forma de entender Axis Remoting fue observarlo en texto claro. Un proxy man-in-the-middle con soporte mTLS — expone el TLS hacia el cliente y crea su propia conexión mTLS hacia el servidor — permite inspeccionar cada mensaje.

La secuencia de conexión que aparece tiene tres fases: un user agent con el que el servidor valida que el cliente es genuino, la autenticación NTLM SSP con su desafío y respuesta, y finalmente el intercambio de RPC sobre JSON con el que el cliente invoca métodos del backend. Un efecto colateral de usar NTLM: el handshake revela de inmediato el hostname y el dominio del servidor, información que después sirve para identificar organizaciones afectadas una por una.

El fallo central: el cliente elige la clase

La implementación del RPC usa service contracts de .NET, el patrón habitual para exponer métodos invocables remotamente. Con argumentos primitivos funciona bien, pero métodos como LogonAsync reciben DTOs complejos que el servidor debe reconstruir deserializando JSON.

La configuración elegida por Axis fue TypeNameHandling.Auto, el modo en que el campo $type del JSON le dice al servidor qué clase instanciar. Un atacante que controla ese campo controla qué objetos nacen en el backend, y en .NET existen gadgets públicos que transforman eso directamente en ejecución de código; el payload se construye con ysoserial.net. La explotación solo requiere seguir el protocolo completo: mTLS, user agent, NTLM SSP y el JSON malicioso.

El primer obstáculo es que el RCE queda tras la autenticación. Pero los mensajes NTLM no llevan firma, así que un intermediario puede dejar que el cliente legítimo pase el desafío contra el servidor y reemplazar en pleno vuelo su payload por el malicioso — pass the challenge. Además, cliente y servidor hablan el mismo protocolo, de modo que el mismo objeto serializado malicioso dispara la ejecución de código también en la aplicación cliente. Con el servidor bajo control, la escalada a las cámaras usa una función legítima: Axis acepta paquetes ACAP desarrollados por terceros con su SDK, y un paquete compilado en C++, firmado y cargado desde el servidor comprometido otorga ejecución de código en las cámaras mismas.

El canal de respaldo y el bypass total

La meta seguía siendo RCE pre-autenticación sin interacción del usuario. El protocolo principal exigía NTLM apenas se abría el socket, y ahí el camino se cerraba. La salida apareció en la documentación: existe un protocolo de respaldo en otro puerto para cuando el principal no está accesible, descrito como "HTTP con cifrado AES".

Al probarlo en un navegador, el servidor pide credenciales y luego se queda en blanco: no es HTTP convencional. La ingeniería inversa muestra un diseño peculiar: un GET inicial devuelve un channel ID; el cliente abre un segundo socket con GET /<channel_id>; y con eso obtiene dos canales, uno de transmisión y otro de recepción, que emulan sockets sobre HTTP. Sobre esos canales cada extremo envía su clave pública, genera una clave AES aleatoria, la cifra con la pública del par y todo lo sucesivo viaja cifrado simétricamente.

Toda esa criptografía no protege de nada: dentro del túnel corre el mismo Axis Remoting con RPC JSON y la misma deserialización vulnerable. El servidor web exige Negotiate (Kerberos o NTLM), pero existe una ruta secreta, /__/, que acepta autenticación anónima. Conectando por esa ruta, implementando el protocolo de canales y enviando el payload de deserialización, se obtiene RCE pre-autenticación completa en el servidor y en las cámaras que gestiona.

Cuántos quedan expuestos

Censys reveló casi 6.500 servidores Axis Remoting accesibles desde internet, concentrados en Estados Unidos, y cada servidor puede gestionar hasta 10.000 cámaras. Como NTLM filtra hostname y dominio en el handshake, un cliente mínimo basta para etiquetar cada servidor con su organización: la lista final incluye universidades, agencias gubernamentales, instituciones médicas y grandes empresas.

La exposición masiva tiene causas estructurales: las prohibiciones occidentales sobre marcas chinas de cámaras redujeron las alternativas, el acceso remoto a la videovigilancia es una necesidad operativa, y el cifrado del protocolo genera la percepción de que abrir el puerto es seguro. Las vulnerabilidades se reportaron a Axis de forma responsable; el fabricante respondió rápido con parches.

Técnicas y herramientas mencionadas

  • Axis Remoting: protocolo propietario RPC-sobre-JSON para gestión remota de flotas de cámaras, envuelto en mTLS y NTLM.
  • Proxy MITM con mTLS: técnica para desencriptar y observar protocolos cerrados terminando el TLS en ambos lados.
  • TypeNameHandling.Auto / $type: configuración de deserialización JSON de .NET que permite al cliente instanciar clases arbitrarias en el servidor.
  • ysoserial.net: herramienta para generar payloads de deserialización que ejecutan código vía gadgets .NET.
  • Pass the challenge NTLM: reutilización del desafío-respuesta de un cliente legítimo, posible porque Axis no firma los mensajes.
  • Protocolo de canales HTTP (fallback): mecanismo de respaldo que multiplexa TX/RX sobre dos sockets HTTP con intercambio de claves AES.
  • Endpoint /__/: ruta anónima del servidor web que habilita el bypass de autenticación completo.
  • ACAP SDK: kit de desarrollo de Axis para paquetes de cámara; usado para desplegar código en las cámaras desde el servidor.
  • Shodan / Censys: motores de búsqueda de superficies expuestas, usados tanto para descubrir el servicio como para estimar el alcance (~6.500 servidores).

Conclusiones

  • Toda la cadena es atacable: cliente, servidor y cámaras comparten el mismo protocolo vulnerable, así que un solo fallo de deserialización compromete el ecosistema completo de videovigilancia.
  • La autenticación no cubre lo que los mensajes no firman: sin firma NTLM, cualquier intermediario puede sustituir cargas en una sesión ya autenticada.
  • Los canales "alternativos" son la peor superficie: el protocolo de respaldo y el endpoint anónimo convirtieron un RCE post-autenticación en RCE pre-autenticación.
  • La cifra no reemplaza la auditoría: miles de organizaciones confiaron el perímetro de su videovigilancia a un protocolo propietario sin revisión pública, y la única defensa real fue el reporte responsable y el parche del fabricante.
