Cámaras Dahua: claves de firmware escondidas bajo la alfombra

Fuente: «DEF CON 33 - Never enough about cameras: Firmware keys hidden under the rug - Alexandru Lazar» · ver el video original

Resumen

En 2025 la gente sigue exponiendo sus cámaras web a Internet: la mayoría de esos dispositivos tiene exploits simples y fiables a través de múltiples versiones de firmware, lo que los convierte en objetivos perfectos para botnets. Hay reportes militares de cámaras de seguridad hackeadas para seguir movimientos logísticos, y un caso de banda de ransomware que usó una cámara para pivotar dentro de la red víctima. Este trabajo disecciona dispositivos de Dahua —tres cámaras y un XVR— desde dos flancos: cómo extraer y descifrar un firmware que el fabricante cifra con un esquema casero lleno de agujeros, y dos vulnerabilidades (una en el servicio HTTP, otra en ONVIF) que terminan en shell de root.

Obtener el firmware

Hay caminos fáciles —descargarlo del sitio web del fabricante, shell por UART, interceptar una actualización— y el camino de hardware: leer el chip de memoria. Para dos cámaras y el XVR bastó el sitio web; para la tercera cámara hubo que desoldar el chip flash, consultar el datasheet para el pinout, conectar un lector (un Bus Pirate sirve) y escribir un script de Python con los comandos del datasheet, porque FlashROM no soportaba esa marca de chips.

Descifrar el sistema de archivos

Con dos cámaras, extraer el archivo y pasar binwalk fue suficiente. En los otros dos dispositivos, los ficheros con nombres sugerentes (web.squashfs) solo contenían cabeceras UImage y datos de alta entropía. Pistas de que no estaba cifrado del todo: firmas zlib falsas que, al extraerlas, revelaban strings, nombres de archivo e incluso código JavaScript; la firma ZIP PK reemplazada por DH (de Dahua); y cabeceras UImage en los ficheros del sistema de archivos, algo inusual. Con el kernel ilegible, el punto de entrada fue el bootloader —sin cifrar, una variante de U-Boot incluida en el mismo archivo—.

En Ghidra (arch64 little-endian, base 0), el punto de partida fue la constante más reconocible: la S-box de AES, y de ahí subir por el árbol de llamadas hasta strings como u-boot encrypt file y firmware get key. El descifrado ocurre en cuatro pasos:

flowchart LR
    A[firmware get key: hash SHA-256 truncado a 16 bytes] --> B[key factors: AES-256 key expansion]
    B --> C[set flags: opcional segun modelo]
    C --> D[u-boot encrypt file: AES-256-CBC in-place por bloques de 0x200]
  1. Firmware key: bytes hardcodeados copiados a un buffer, idénticos en varios dispositivos salvo los primeros 6, que se sustituyen por el nombre del procesador (la clave cambia por tipo de dispositivo). Tres funciones de hash se dedujeron por sus constantes —con una parada cómica: ChatGPT dio la respuesta equivocada y, descartada una opción, quedó SHA-256—. El hash de 32 bytes se entrelaza (primer byte con el último, etc.) para producir la clave de 16 bytes.
  2. Key factors: una función con operaciones a nivel de bits y buffers hardcodeados que, desglosada paso a paso, revela memset/memmove deducibles por contexto, las tablas T de AES y un bucle de 10, 12 o 14 iteraciones (la expansión de clave). El modo de operación se infiere de un quinto parámetro con forma de IV: probando el modo más común, CBC, el patrón de alto nivel encajaba (cifrar el IV junto al plaintext, el ciphertext resultante pasa a ser el nuevo IV) → AES-256-CBC. El IV se genera con 6 caracteres únicos; la key, con bytes incrementados de 0x20 a 0x30 y de 0x23 a 0x33. Dos buffers hardcodeados de 32 bytes —distintos para kernel y sistema de archivos— se combinan entre sí para producir el plaintext de 32 bytes que, cifrado, aporta los últimos 16 bytes del ciphertext: esos 16 bytes concatenados con la firmware key forman la clave AES final.
  3. Set flags: presente solo en algunos modelos.
  4. U-boot encrypt file: descifrado in-place con 5 o 7 parámetros (la ruta XVR usa 7), bloques de 0x200 (32 bloques AES por llamada) y un IV que arranca en 0 y se incrementa. El detalle que explica el misterio inicial: el offset a veces se incrementa en más de 0x200, así que algunos bloques se saltan y quedan sin cifrar en la salida —por eso aparecían strings y código dentro de ficheros "cifrados"—.

Con la clave, el IV y el algoritmo, solo faltaba la entrada: la cabecera UImage de 64 bytes tiene un campo de tamaño que coincide exactamente con los bytes que la siguen. Se recortan con dd, se descifran y binwalk vuelve a funcionar: sistema de archivos completo.

Superficie de ataque

El binario que lo hace todo se llama Sonia o Challenge según el dispositivo, y allí viven los listeners. Nmap solo revela tres puertos abiertos (HTTP, RTSP y DHAP, el protocolo propio de Dahua), pero el binario apila de 10 a 16 protocolos sobre el mismo puerto: un regex parsea el paquete entrante y despacha al handler correspondiente (UPnP, WebSocket, RTSP sobre HTTP...). No todos están habilitados en todos los modelos y la mayoría exige autenticación —bien implementada, en general—. Como siempre, sobran los handlers sin autenticación.

Vulnerabilidad 1: HTTP (RPC2 upload file with name)

Un handler sin autenticación permite subir archivos —solo MP3 con ruta fija, el nombre engaña—, pero construye mal la cabecera csec: en lugar del tamaño del buffer usa el tamaño del string, y el overflow alcanza la sección BSS tras solo 0x34 bytes. El binario crashea, sí, pero el puntero sobrescrito apunta a la estructura de sesiones HTTP, y la función del crash borra los tokens expirados mediante un puntero a función que vive en esa misma estructura: el plan es reescribir la estructura en memoria y sustituir ese cleanup por una llamada a system.

Sin debugger y sin otra cámara con servicio HTTP para reconstruir en paralelo, el análisis estático (listas enlazadas, diccionarios, punteros a punteros a punteros, cookies de integridad en las estructuras) no bastaba para acertar a la primera. La salida: el pin TX de la cámara imprime los registros en cada crash, y con eso se reescribió la estructura un crash por vez —en cada fallo, mirar el program counter y el registro culpable y hacer que ese registro apunte dentro de la estructura—. Tras unas 15 iteraciones, el crash cambia a "PC fuera de la sección de código": se llegó al puntero a función.

Para ejecutar código faltaba sortear otra sorpresa: el kernel no ejecuta binarios sin firmar (protección notable para una webcam). La vía fue LD_PRELOAD: una shared library compilada para esa arquitectura exacta con un toolchain de buildroot (con hard float y musl), un bind shell, y descarga por TFTP —la cámara no tiene netcat, pero sí TFTP—. Root número uno.

Vulnerabilidad 2: ONVIF (stack overflow con un solo gadget)

ONVIF es HTTP con parsers propios y lo interesante vive tras autenticación. Los getters get capabilities y get service capabilities usan el header Host para mostrar los endpoints al cliente: el único dato que parsean, y lo hacen mal. Sin corchetes en el header, el tamaño se limita a 64 bytes; si se imita un IPv6 e incluye un corchete, la comprobación se salta y todo se copia al stack: overflow de buffer clásico.

Las restricciones moldean el exploit: se controlan los registros R4–R11, pero strcpy deja pasar un único byte nulo y debe ser el último. El binario no es position independent (se carga siempre en la misma dirección), pero esa dirección es baja y contiene un byte nulo, así que la cadena ROP solo admite un gadget —y para un solo gadget, system es la elección natural—. Faltaba el payload: ninguna shell embebida en la cámara, así que había que escribirlo en memoria. BSS es escribible y su dirección no contiene bytes nulos, pero sin memory leak no había forma de apuntar a gadgets de librerías. La solución fue un gadget del propio binario con el mismo epílogo que la función vulnerable: ejecuta su store (escribe 4 bytes de R7 a la dirección en R5, ambos controlados) y deja el stack pointer en su sitio, de modo que el flujo regresa limpio y el payload acumulado en BSS sobrevive. Con 20 MB de binario, la búsqueda de instrucciones de Ghidra dio unos 15-60 candidatos; se eligió el de store más cercano al return. Diez o quince requests escriben el payload (el mismo truco TFTP + LD_PRELOAD), y una petición final salta al gadget de system con su dirección en R6: root número dos.

Divulgación

El equipo de Dahua respondió como debería: clave PGP, respuestas rápidas, corrección real del problema y, algo poco visto entre vendedores de IoT, una lista de los dispositivos afectados.

Técnicas y herramientas mencionadas

  • Hardware: desoldado del chip flash, Bus Pirate como lector, script Python con comandos del datasheet (FlashROM incompatible).
  • Extracción: binwalk, carving con dd, cabeceras UImage de 64 bytes, LZMA (módulos Python cuando las utilidades se quejan de datos corruptos).
  • Ingeniería inversa en Ghidra: arch64 little-endian; reconocimiento por constantes (S-box y tablas T de AES, bucles de 10/12/14 iteraciones = expansión de clave), deducción de memset/memcpy por contexto.
  • Cripto casera: firmware key con SHA-256 entrelazado + nombre del procesador; AES-256-CBC con IV incremental y bloques parcialmente sin cifrar por offsets incorrectos.
  • Exploit HTTP: overflow de csec hacia BSS (0x34 bytes), reescritura de la estructura de sesión HTTP y de un puntero a función de cleanup → system; reconstrucción guiada por los registros que el pin TX imprime en cada crash.
  • Exploit ONVIF: stack overflow vía header Host con corchete (salta el límite de 64 bytes); ROP de un gadget con epílogo idéntico al de la función vulnerable para escribir el payload en BSS sin destruir el stack.
  • Post-explotación: kernel con ejecución restringida a binarios firmados → LD_PRELOAD con shared library compilada en buildroot (hard float, musl), descarga por TFTP.

Conclusiones

  • Cifrar el firmware con claves derivadas de datos presentes en el propio dispositivo y con un esquema AES-CBC mal aplicado solo añade oscuridad: la ingeniería inversa del bootloader sin cifrar basta para reconstruir el descifrado completo.
  • Un solo handler sin autenticación en un binario que aglomera 10-16 protocolos por puerto basta para comprometer el dispositivo entero; y dos bugs de corrupción de memoria distintos (uno en BSS con puntero a función, otro de stack con un único gadget ROP) terminaron en root.
  • Los fabricantes de IoT pueden hacerlo bien: la respuesta de Dahua (PGP, rapidez, fix real, lista de dispositivos afectados) es el estándar a exigir.
