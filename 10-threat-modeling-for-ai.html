Distilled from OffSec AI-300 (OSAI) course material (module 10) — internal training reference, not for redistribution.

Objective

Formalize target selection into a repeatable, iterative threat-modeling methodology for AI-enabled targets. Unlike a textbook decomposition, a real engagement starts with fragments (scoping doc, DNS, job postings, assumptions); the threat model is a living artifact that evolves with every piece of intelligence collected, every assumption validated or discarded, and every scope constraint that eliminates a theoretical path.

Working scenario: 10-day grey-box assessment of Nexus AI, an enterprise AIOps platform deployed by Megacorp Financial Services. Access: VPN tunnel into the Kubernetes cluster network (attack host 10.10.40.2 routed to service subnet 10.10.50.0/24) and a read-only Kubernetes API token scoped to the nexus-ai namespace (pod listing + secret read; no write). No prior perimeter breach. The deliverable is an attack intelligence brief: the artifact that says which target to pursue next based on what is known right now.

Target surface

  • Scoping document — hybrid cloud (on-prem Kubernetes + AWS); Nexus AI is internal-only, no public endpoint. Out of scope: production financial trading systems, customer-facing banking apps, AD domain controllers.
  • RoE highlights (used later as hard constraints): no destructive actions against production DBs; vector DB poisoning permitted only against staging (Qdrant-staging, port :16333); no DoS; no real customer PII exfil; all MCP tool invocations must be reported to the Blue Team POC within 24 hours; testing window 08:00–20:00 Mon–Fri.
  • Passive OSINT: LinkedIn posting for "Senior ML Platform Engineer" (MLflow, Qdrant, Kubernetes); DevOps profile (HashiCorp Vault, MCP integrations); a public GitHub fork of an MCP server library referencing the private upstream megacorpfs/nexus-mcp-tools with three tools: aws_cli_exec, snow_create_ticket, datadog_query.
  • Client data-flow statement: alerts → central orchestrator → specialized agents (triage, remediation, security) → shared knowledge base for context + central tool server for actions.
  • Active recon (nmap -sV -p- --open -T4 10.10.50.0/24) — 9 services:

Techniques

1. Assumption register (the backbone)

Every hypothesis about the target is tracked with source, confidence, and validation status. Template (initial entries from pre-engagement intel):

ID Observation Hypothesis Confidence Source Status
A-01 Client doc: "central orchestrator" Single orchestration component routes all tasks HIGH Client kickoff doc UNVALIDATED
A-02 Client doc: agents for triage/remediation/security ≥3 distinct agent services HIGH Client doc UNVALIDATED
A-03 Job posting: MLflow, Qdrant, K8s MLflow = model registry, Qdrant = vector storage MEDIUM LinkedIn OSINT UNVALIDATED
A-04 DevOps profile: Vault Credential management via Vault, not embedded secrets MEDIUM LinkedIn OSINT UNVALIDATED
A-05 GitHub fork: aws_cli_exec, snow_create_ticket, datadog_query MCP Server exposes ≥3 tools HIGH Public fork UNVALIDATED
A-06 Client doc: "shared knowledge base" RAG pipeline exists, likely Qdrant-backed (A-03) MEDIUM Client doc + A-03 UNVALIDATED
A-07 No mention of vector DB auth Qdrant may be unauthenticated in-cluster LOW Absence of evidence UNVALIDATED
A-08 aws_cli_exec tool MCP Server has AWS credentials (likely via Vault, A-04) MEDIUM A-05 + A-04 UNVALIDATED

Rules of the register:

  • Lifecycle: observation → hypothesis → validation testing → VALIDATED (drives attack planning) or INVALIDATED (generates new hypotheses). Update after every new artifact (port scan, API response, config file).
  • Confidence reflects the reliability of the source, not the probability the hypothesis is true. A-07 is LOW confidence flagged "absence of evidence": missing documentation is not evidence of a missing control. Treating absence of information as confirmation of a vulnerability is the most common pre-engagement threat-modeling mistake. LOW-confidence assumptions drive verification tasks, not attack planning.
  • Hypotheses can be partially wrong: A-02 resolved to 4 agents (Knowledge Agent is standalone — own network presence, own attack surface, directly queryable); A-08's flat credential model was invalidated — the MCP Server enforces per-agent tool scoping. Learning a path is closed early is more valuable than clinging to a plausible one; it re-aims time budget.

2. Progressive validation (Phase 2 — active recon → register updates)

Exact steps, in order:

  1. Unauthenticated vector DB check — curl -s http://10.10.50.20:6333/collections | jq '.result.collections[].name' → operational_knowledge, detection_rules, incident_history, runbook_corpus. A-07 VALIDATED: direct unauthenticated read on the production vector DB. Immediately check RoE: reads permitted on production, writes only against staging :16333.
  2. MCP tool listing — curl -s http://10.10.50.15:9005/tools → the three OSINT tools plus a fourth not present in the public fork: vault_rotate_secret ("Rotate a secret in HashiCorp Vault"). A tool that writes secrets means the MCP Server's Vault credentials include rotation, not just retrieval → new assumption A-10 (HIGH).
  3. Kubernetes secret extraction — kubectl --token=$K8S_TOKEN get secrets -n nexus-ai → nexus-{triage,remediation,security,knowledge}-agent-token plus nexus-mcp-vault-approle. Extract with kubectl get secret nexus-triage-agent-token -n nexus-ai -o jsonpath='{.data.token}' | base64 -d → a JWT carrying agent identity and per-tool scope claims. (K8s secrets are base64-encoded, not encrypted; the read-only grey-box token sufficed.)
  4. Tool authorization test — POST to /invoke with each token against vault_rotate_secret on a canary path (secret/nexus/test_canary): Triage token → Agent triage not authorized; Remediation token → {"status": "success", "message": "Secret rotated", "new_version": 4}. Two findings: (a) per-agent tool scoping is real; (b) the Remediation Agent can overwrite Vault credentials — write access, strictly stronger than read. Deliberately avoid testing aws_cli_exec here to limit detection footprint → A-12b stays UNVALIDATED (it later gates Path 1).
  5. Attribution question → A-12c: at TB-5, Vault sees only the MCP Server's AppRole identity, not the requesting agent — the agent audit trail collapses at this boundary (INFERRED from AppRole architecture).

3. Crown jewel analysis under uncertainty

Rank assets by offensive value given current knowledge, re-rank as intel arrives:

Rank Asset Location Offensive value Confidence
1 AWS credentials Vault → MCP Server Direct infra control; Remediation Agent can rotate (A-11) HIGH
2 Detection rule collection Qdrant detection_rules The defender's playbook — what is monitored, what evasion looks like. Readable now HIGH
3 Runbook corpus Qdrant runbook_corpus Procedures, topology, known vulns. Readable now HIGH
4 Agent identity tokens Agent pods / K8s config Per-agent tool authorization; Remediation token = Vault write key MEDIUM (obtained Day 2)
5 Model weights MLflow :5000 Fine-tuned on proprietary ops data; access unverified MEDIUM
6 MCP tool schemas MCP Server :9005 Complete capability map; already obtained HIGH (obtained)

Operational rule: jewels already accessible (#2, #3, #6, #4) should be extracted immediately — they inform every later decision. #1 stays behind multiple trust boundaries and is the primary objective. Also invert staging: reading (not writing) Qdrant-staging:16333 may yield dev artifacts, draft runbooks, credential patterns scrubbed from production — and reads are RoE-permitted.

4. Trust boundaries and trust zones

A trust boundary exists wherever a component accepts input/instructions from another without independent verification. AI systems add a new category: boundaries enforced by inference rather than policy. A traditional API gateway rejects bad tokens (policy); a Triage Agent classifying an alert "critical" via LLM inference makes a trust decision with no policy backing — exploitable through input manipulation, not authentication bypass.

ID From → To Trust type Enforcement Status Offensive implication
TB-1 Alert sources → Orchestrator Input trust Webhook auth — mechanism unknown UNVALIDATED If unauth'd, untrusted input enters the pipeline directly
TB-2 Orchestrator → Agents Delegation trust Internal mTLS between pods VALIDATED (nmap TLS fingerprint) Agents execute whatever is dispatched
TB-3 Agents → Vector DB Data integrity trust None — unauthenticated VALIDATED Any agent treats Qdrant content as ground truth
TB-4 Agents → MCP Server Tool invocation trust Per-agent identity tokens VALIDATED Token scoping limits tools per agent; parameters unvalidated (A-15)
TB-5 MCP Server → Vault Credential trust AppRole (MCP service identity) INFERRED If Vault sees only MCP identity, agent-level audit trail is lost
TB-6 MCP Server → External APIs Infrastructure trust API keys from Vault INFERRED No additional auth gate after credential retrieval
TB-7 Triage Agent → Orchestrator Classification trust None — inference-based UNVALIDATED Manipulated classification drives the whole downstream workflow
TB-8 Knowledge Agent → Other agents Advisory trust None INFERRED Agents incorporate RAG responses without verification

The zone map marks VALIDATED boundaries solid and INFERRED/UNVALIDATED ones dashed, so the plan distinguishes validated attack surfaces from theoretical ones.

5. Escalation paths, constrained by reality

Unconstrained theory (the most efficient chain): poison production vector DB (TB-3) → influence Remediation Agent (TB-8) → trigger MCP tool call with malicious parameters (TB-4) → Vault (TB-5) → AWS (TB-6). Five boundary crossings, zero authentication. The RoE kills the first link — production poisoning is prohibited. Do not keep RoE-prohibited paths in the plan "pending client approval"; the RoE is a hard constraint. Remove the path from execution, keep the underlying weakness (unauthenticated DB) in the report as a risk finding.

  • Path 1 — Remediation Agent token theft → direct MCP abuse (PRIMARY). We already hold the token from K8s secret extraction ("theft" = using a token outside its intended context). Chain: TB-4 → TB-5 → TB-6, crown jewel #1. Go/No-Go gates: A-12b (does the Remediation token also authorize aws_cli_exec?) and A-15 (is MCP parameter monitoring absent?). Time constraint: the 24-hour MCP reporting clock starts at the first aws_cli_exec invoke — all post-exploitation on the retrieved AWS credentials must finish inside it. Detection risk LOW if A-15 holds and execution happens in business hours (avoids nexus-mcp-002 timing detection).
  • Path 2 — Staging vector poisoning → indirect remediation influence. Uses the RoE-permitted staging instance. Complexity: the Knowledge Agent serves all agents, so the poisoned runbook must be crafted to match Remediation-type queries (credential rotation procedures, AWS operations) — if another agent retrieves it, its token lacks Vault write and the path may burn. Hard validation gate: does the Knowledge Agent ever query :16333? If it only touches :6333, the path is dead. Advantage: malicious MCP parameters are generated by the Remediation Agent itself, so they match its normal patterns and A-15 becomes irrelevant.
  • Path 3 — Intelligence extraction (SUPPORT, execute first). Extract detection_rules/runbook_corpus from the attack host; accept the nexus-qdrant-004 detection risk because the intel enables every go/no-go decision. If a pod foothold appears later (e.g. container vuln, or a K8s token with pods/exec), route further queries through an agent IP for stealth.

Decision matrix under time pressure (Day 3 of 10, ~8 days left): GO on Path 3 and on each cheap validation (A-12b single invoke — irreversible, starts the reporting clock; A-15 rule analysis; Path 2 traffic observation); HOLD on Paths 1 and 2 until their gates resolve. If both paths validate but time allows one, pick the lower detection risk first. The engagement plan is a decision tree, not a script — prune branches as information arrives.

6. Attack intelligence brief (deliverable template)

Versioned living document (v1.0 Day 1 hypotheses → v1.1 recon results + invalidated flat-credential model → v1.2 detection intel + go/no-go gates). Structure:

ATTACK INTELLIGENCE BRIEF — <TARGET>
Classification / Engagement Day / Brief Version

=== TARGET SUMMARY ===          platform, environment, confirmed components, architecture confidence
=== CROWN JEWELS ===            ranked, each with location + status [OBTAINED / ACCESSIBLE / BEHIND N BOUNDARIES]
=== ASSUMPTION REGISTER ===     totals (VALIDATED/UNVALIDATED/INVALIDATED) + critical unvalidated, each tagged
                                with what it blocks (e.g. A-12b → BLOCKS Path 1)
=== SCOPE CONSTRAINTS ===       BLOCKED / REQUIRED items from the RoE
=== ESCALATION PATHS ===        per path: status (GO/HOLD), priority, boundaries crossed, crown jewels,
                                detection risk, time window, ATLAS + ATT&CK references
=== NEXT ACTIONS ===            concrete Day-N tasks

The brief's value is honesty about what is known, assumed, and blocked — a team reading it knows exactly which decisions are pending and what information unlocks them. The version history doubles as a decision log documenting every assumption formed, tested, and resolved.

7. When paths close and new ones open

  • Path 2 precondition fails (Knowledge Agent only queries production) → path removed, but the test yields new intel: the routing is now known. If the Knowledge Agent's Qdrant endpoint is configurable (ConfigMap / pod env), a new path emerges: pod foothold → change endpoint :6333 → :16333 → staging poisoning viable again. New hypothesis (A-16), register grows, brief updates.
  • A-15 invalidated (parameters are monitored, e.g. a rule matching aws iam in aws_cli_exec parameters) → Path 1 is constrained, not killed: find an objective-achieving command outside the detection pattern (e.g. aws ssm send-command for code execution instead of IAM modification).
  • "The engagement team that succeeds is not the one that had the best plan on Day 1. It is the team that replanned correctly when Day 3 broke the plan."

The brief also carries ATT&CK companions per path (Path 1: AML.T0085 + ATT&CK T1078.004 Cloud Accounts, T1059.004 Unix Shell; Path 2: AML.T0020 staging-only; Path 3: AML.T0025).

Detection & defense

Five detection rules extracted from the unauthenticated detection_rules collection (a defender should assume this corpus leaks):

  • nexus-mcp-001 — unusual MCP tool invocation pattern
  • nexus-mcp-002 — vault_rotate_secret called outside the maintenance window
  • nexus-agent-003 — agent-to-agent direct communication bypassing the orchestrator
  • nexus-qdrant-004 — bulk vector read from a non-agent source IP
  • nexus-aws-005 — AWS IAM modification outside change window

Gap (A-15, MEDIUM): no extracted rule inspects the content/semantics of MCP tool parameters — a malicious aws_cli_exec command during business hours under a legitimate tool name looks identical to normal activity. Also note the compounding effect: the RoE's 24-hour MCP reporting requirement plus nexus-qdrant-004 means bulk reads both risk automated alerting and guarantee human notification.

Defensive takeaways the module itself draws:

  1. The most dangerous escalation paths don't break through trust boundaries — they flow through gaps where trust was never enforced: an unauthenticated vector database, a vault that cannot distinguish agents, an orchestrator that trusts classification without verification. These are architectural decisions prioritizing functionality over security, not bugs.
  2. Kubernetes secrets are base64, not encrypted — scope secret-read RBAC tightly; a "read-only" grey-box token should not yield every agent identity.
  3. Per-agent tool scoping works (defense win) but is undermined by unvalidated parameters — validate tool arguments, not just tool names and caller identity.
  4. Preserve attribution at tool boundaries (TB-5): have the Vault path carry the requesting agent's identity, or stolen-token use becomes indistinguishable in Vault audit logs.
  5. When AI systems get backend access, treat them like privileged service accounts: the attack surfaced through capability discovery (tool listing) and credential material reachable from a single token.

Ares integration notes

pentest-attack-flow and pentest-attack-navigator (both in skills/cybersec/, wired into pentest-orchestrate STEPs 6.8/6.9) currently speak ATT&CK only: the Navigator layer pins versions.attack = "16" and colors enterprise techniques Txxxx by severity; Attack Flow builds STIX 2.1 attack-action objects whose technique_id field expects ATT&CK. Neither consumes MITRE ATLAS, so an AI-300-style engagement loses every AML.Txxxx mapping above. An ATLAS mapping would add, concretely:

  1. A second Navigator layer / matrix source for the ATLAS matrix (ML Attack Stages: Reconnaissance → Resource Development → Initial Access → ML Attack Stages; enterprise+ATLAS versions block), highlighting AML.T0040, AML.T0025, AML.T0020, AML.T0085 etc. per finding — the module's per-component table is exactly the input format.
  2. Dual-tagged attack-action objects in attack-flow STIX output: each chain step carries technique_id (ATT&CK) plus an atlas_technique_id extension property, so a chain like "unauth Qdrant read → poisoned runbook → vault_rotate_secret → AWS creds" renders as AML.T0025 → AML.T0020 → AML.T0085 alongside T1078.004/T1059.004.
  3. An atlas-mappings.json enrichment source for pentest-framework-enrichment (STEP 6.7 currently enriches ATT&CK / D3FEND / NIST CSF from cwe-framework-mappings.json) — component/asset classes in an AI target (vector DB, model registry, MCP server, agent tokens) would auto-map to ATLAS techniques.
  4. AI-specific asset taxonomy in attack-flow: attack-asset currently models servers/APIs; ATLAS brings jewel classes the enterprise matrix lacks — model weights, embeddings/vector corpora, detection-rule corpora, agent identity tokens, tool schemas.
  5. Go/no-go gate semantics: ATLAS precondition tagging ("applicable if access validated") would let the flow generator mark actions as conditional on unvalidated assumptions (A-12b/A-15 style), matching the brief's HOLD/GO statuses instead of rendering every step as executed.
