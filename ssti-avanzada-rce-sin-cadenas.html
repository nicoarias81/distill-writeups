SSTI avanzada: RCE sin cadenas, sin recursos externos y en cualquier escenario

Fuente: «Advanced server-side template exploitation with RCE everywhere» · ver el video original

Resumen

Una inyección en plantillas del lado del servidor (SSTI) suele quedar trabada en un impacto bajo: el atacante confirma que puede ejecutar operaciones aritméticas —el clásico "7*7=49"— pero cualquier intento de ejecutar comandos falla porque los payloads convencionales exigen recursos que el entorno no da: cadenas literales entre comillas, parámetros HTTP, encabezados. Esta investigación parte de un hallazgo real de bug bounty que rindió solo un impacto de 49 y plantea un desafío más ambicioso: lograr ejecución remota de código en los motores de plantillas más populares usando exclusivamente funciones y métodos incorporados en cada librería.

Las reglas autoimpuestas definen el valor del trabajo: nada de cadenas escritas directamente, nada de parámetros ni encabezados HTTP (para que el payload funcione incluso dentro de un PDF renderizado o con ejecución diferida una semana después), y cobertura de los motores de PHP, Java y Python: Jinja, Twig, FreeMarker y Groovy. El resultado son técnicas de construcción de cadenas puramente computacional —generando el texto de los comandos carácter por carácter con los métodos internos de cada motor— que además burlan escapes de HTML, porque nunca usan comillas ni caracteres que los sanitizadores convencionales toque.

Jinja (Python): encadenar atributos y fabricar letras

El payload básico de RCE en Jinja encadena atributos desde self hasta llegar al módulo os y popen, pero exige pasar id como cadena literal. La solución llega por Python mismo: la cadena de métodos globales contiene todas las letras del alfabeto, así que basta con indexarla —el carácter en la posición 51 es la i, sumado al de la posición 34 que es la d— para fabricar id sin escribirlo. Con esa construcción, popen ejecuta el comando y el motor entregado como playground (Dojo de YesWeHack) confirma la ejecución remota.

Twig (PHP): el más difícil, resuelto con bloques y encoding

Twig es reconocido como uno de los motores más limitados. El payload teórico es trivial —['id']|map('passthru')— pero usa dos cadenas prohibidas. La construcción sin cadenas toma varios días de trabajo y es la pieza más elegante del recorrido:

  1. Un bloque {% block %} declara el texto id passthru como valor de una variable.
  2. El filtro charset devuelve la codificación por defecto, UTF-8, y la primera letra de ese texto es la u que permite llamar al bloque sin escribir su nombre.
  3. Ese bloque se divide con split usando ceros como separador —los ceros no son letras, así que no violan la regla— y se arma la lista con los dos "comandos" fabricados.
  4. La ejecución final replica el payload original: el primer elemento (id) entra a map, el último (passthru) se une con join, y se obtiene RCE completo.

FreeMarker (Java): letras por índice y hasta los puntos

FreeMarker ofrece un truco hecho a medida: los métodos lower_abc y upper_abc convierten enteros en letras —1 es a, 2 es b—, pensados para generar listados alfabéticos pero perfectos para construir cadenas. Como en Java casi todo es tratable como string, el método freemarker.template.utility.execute invocado con ?new crea un objeto de ejecución de comandos al que se le pasa el comando armado letra por letra.

El problema fino son los caracteres fuera del abecedario, como los puntos. La salida: pasar el flotante 1.1 a una variable convertida en lista y tomar su segundo elemento, que es justamente el punto. Con eso se completa cualquier comando. Para no escribir estos payloads a mano, un script en Python arma automáticamente el equivalente de cualquier comando de terminal.

Groovy (Java): ASCII y conversiones

Groovy no tiene lower_abc, pero permite bucles y aritmética. La construcción crea un string vacío a partir de un objeto String sin comillas, itera sobre los valores ASCII de las letras (105 y 100 para id), los convierte con chr() y los acumula con += hasta formar el comando, que finalmente pasa a execute(). El patrón, similar al de FreeMarker, cierra la cobertura de los cuatro motores objetivo.

Detección, mitigación y preguntas del público

  • Doble render y second order: la SSTI casi nunca nace de un desarrollador que llama dos veces a render a sabiendas; suele provenir de un framework que mete un render oculto en una función por defecto, o de una función propia que renderiza sin querer. La variante second order aparece cuando el payload se guarda en base de datos —un comentario en un blog, por ejemplo— y se renderiza más tarde en un panel de administración: no ejecuta donde se inyecta, sino donde se re-renderiza. Para detectarla conviene probar payloads out-of-band (una consulta DNS propia, al estilo del blind XSS) y luego rastrear dónde se ejecutó.
  • Escapes y sanitización: los sanitizadores tipo html_escape solo escapan según HTML, y estos payloads ni siquiera los necesitan porque no usan comillas. La excepción real es ERB de Ruby, cuya sintaxis de tags coincide con HTML y rompe casi cualquier payload. El límite duro: si el motor escapa los caracteres de apertura de plantilla ({{), no hay SSTI; si no los escapa, estos métodos funcionan casi siempre, salvo regex estrictas personalizadas.
  • Mitigación concreta: nunca incluir render dentro de funciones propias, y sanitizar la entrada de usuario como salvavidas adicional.
  • Caracteres especiales: en FreeMarker no se construyeron :, - o /, pero la propia shell los suple: con backslash en bash se puede escapar casi todo, o usar herramientas como curl para traer contenido externo mediante peticiones POST.

Técnicas y herramientas mencionadas

  • SSTI (Server-Side Template Injection): inyección en plantillas del lado servidor; con doble render se convierte en vector second order.
  • Construcción de cadenas sin literales: fabricar texto con índices de strings globales (Jinja), filtros charset/split sobre bloques (Twig), lower_abc sobre enteros (FreeMarker) y valores ASCII con chr() (Groovy).
  • Playground de Template Injection de Hackmanit y Dojo de YesWeHack: plataformas de prueba usadas para validar cada payload.
  • map/passthru (Twig), freemarker.template.utility.execute + ?new (FreeMarker), execute().text (Groovy), popen con encadenamiento de atributos (Jinja): primitivas de ejecución de cada motor.
  • Payloads out-of-band con dig/curl: detección de SSTI ciegas y exfiltración cuando el resultado no es visible.

Conclusiones

  • La limitación de una SSTI es casi siempre una ilusión: con creatividad sobre los métodos internos del motor, el RCE está disponible incluso sin escribir una sola cadena literal.
  • Cada motor exige su propia construcción, pero el principio es común: derivar los comandos de primitivas aritméticas y de manipulación de datos que nadie sanciona.
  • Diseñar payloads independientes de recursos externos los hace universales: funcionan en PDFs, en ejecuciones diferidas y a través de sanitizadores HTML.
  • Para mitigar: no renderizar dentro de funciones custom, sanitizar entrada, y sospechar de todo punto donde la entrada del usuario vuelva a atravesar un motor de plantillas, aunque sea días después y desde una base de datos.
