Smuggling binario: SQL injection a nivel de protocolo de base de datos

Fuente: «DEF CON 33 - SQL Injection Isn't Dead: Smuggling Queries at the Protocol Level - Paul Gerste» · ver el video original

Resumen

Si la aplicación usa prepared statements, query builders y ORMs, la inyección SQL clásica está resuelta en papel. Este trabajo baja de la cubierta al motor: ataca el protocolo binario que conecta la aplicación con la base de datos y provoca un desincronizado de mensajes — request smuggling, pero para protocolos binarios — mediante truncamiento de enteros de 64 a 32 bits en las bibliotecas cliente. Resultado: inyección de sentencias SQL completas en Postgres y MongoDB a través de aplicaciones vulnerables como Harbor, sin tocar una sola consulta del código fuente.

De HTTP desync a wire protocols

El punto de partida es el request smuggling clásico de James Kettle en HTTP: dos sistemas que no acuerdan dónde termina un mensaje. La pregunta aquí es qué pasa con los protocolos binarios. Dos mecanismos de delimitación existen: delimitadores (bytes nulos en strings) y campos de longitud (familia TLV: type-length-value). El objetivo elegido fue el enlace aplicación→base de datos: casi toda aplicación web tiene una, las bases son objetivos de alto valor y — punto clave — la aplicación siempre deja al usuario introducir datos que acaban en una consulta, así que hay entrada garantizada.

Un vistazo a los formatos: Postgres usa un byte de tipo + entero de 4 bytes de longitud + valor; MySQL agrega un byte de secuencia para reensamblar paquetes; Redis combina byte de tipo, longitud decimal parseable y delimitadores; MongoDB usa longitud little-endian de 4 bytes, opcode y un valor BSON (TLV anidado).

El bug: truncamiento de int64 a int32

El patrón repetido en las bibliotecas cliente: calcular la longitud total del mensaje en un entero de 64 bits y luego truncarlo explícitamente a int32 para escribirlo en el campo del protocolo. Si el mensaje supera los 4 GB — algo posible en Go, Python o Rust — el número "da la vuelta" y se escribe una longitud diminuta. La aplicación envía los 4 GB igual; la base de datos lee un mensaje pequeño y luego intenta parsear el resto del búfer como mensajes nuevos. Si el atacante controla el contenido del búfer (por ejemplo, un ID de usuario de 4 GB concatenado en la consulta), puede colocar en el offset exacto un mensaje completo con su propia sentencia SQL.

El impacto es mayor que el de la inyección clásica: no hay límite de tipo de sentencia (un INSERT después de un SELECT, si las stacked queries están habilitadas), el atacante lee, escribe y borra con los permisos de la aplicación, y en configuraciones inseguras de la base eso puede llegar a ejecución de código. La exfiltración es menos directa — la aplicación solo procesa la respuesta del primer mensaje — pero se resuelve con subconsultas que insertan los datos robados en otra tabla que la lógica de negocio luego muestra.

Encontrar el offset: knob sleds y trampolines

El offset exacto del payload depende de la consulta y del punto de inyección; en caja negra no se conoce. La fuerza bruta es inviable: cada intento cuesta 4 GB. Dos técnicas de explotación binaria clásica adaptadas:

  • Knob sled: repetir miles de veces el mensaje más pequeño posible del protocolo y colocar el payload real al final. Si el offset cae al inicio de uno de esos mensajes, todo se parsea y el payload se ejecuta; si cae en cualquier otro byte, error fatal y cierre de conexión (el pool la reabre). Con mensajes de 5 bytes: máximo 5 intentos (20 % de acierto por intento).
  • Trampolines: hacer que los propios bytes de longitud sean bytes de tipo válidos (patrón 0x51…) para que cada alineación posible "salte" con un salto de longitud hasta un mensaje pre-construido que aterriza justo en el payload. El límite: Postgres impone un máximo lógico de mensaje por debajo de 1 GB, así que el primer byte de longitud nunca puede superar 0x3F — y 0x3F no es un tipo válido. La solución es un patrón alternado donde cada segundo byte es un inicio de mensaje válido: éxito garantizado en 2 intentos.

Bibliotecas y aplicaciones afectadas

  • Go: las 4 bibliotecas Postgres probadas resultaron vulnerables y explotables; solo una (pgx) corrigió tras el aviso de febrero. pgsql, aPG y PGDriver seguían sin corregir al momento de la divulgación.
  • C#: la biblioteca probada era explotable; corrigieron y backportearon a ramas viejas.
  • Java/JavaScript: varias bibliotecas con el overflow teórico pero no explotables — las cadenas/buffers del lenguaje no alcanzan los 4 GB.
  • MongoDB/Rust: la biblioteca oficial de Rust era vulnerable y explotable; corregida en 2.8.2. Payload más complejo: todo debe ser UTF-8 válido, y el opcode necesario (0xDD07) jamás lo es — la solución es fabricar esos bytes usando los campos de longitud de strings del propio BSON.
  • Aplicaciones: Grafana, Gitea y Syncthing usaban bibliotecas vulnerables (ruta explotable sin confirmar); Mattermost y Gogs vulnerables en configuración no por defecto; Harbor vulnerable y explotable pre-autenticación en configuración por defecto — corregido en 2.11 actualizando la dependencia. La demo en vivo mostró la creación de un usuario administrador inyectando un INSERT.

El elefante de 4 GB: cómo pasar los límites

Los frameworks limitan el tamaño del body, ¿cómo enviar 4 GB? Vías demostradas:

  • Endpoints sin límite o con límites deshabilitados: Harbor desactivó el límite de 1 MB de Nginx para recibir imágenes Docker grandes, dejando toda la API sin límite.
  • Compresión: comprimir el payload para no mandar 4 GB reales; Nginx mira el tamaño crudo sin descomprimir, y si el backend descomprime después del chequeo, el límite es inútil. Fastify hace ambos chequeos pero en el orden equivocado.
  • WebSockets: soportan compresión y mensajes enormes (campo de tamaño de 64 bits); los middlewares del framework a menudo no aplican a mensajes individuales.
  • Tipos de body alternativos: multipart en vez de JSON, con límites distintos u olvidados.
  • Creación server-side: llevar la cadena grande al servidor por otra vía — SSRF hacia un servidor del atacante cuya respuesta enorme se guarda y acaba en la consulta (funcionó contra Gogs vía webhooks), o inflar strings con templating/traducción.

Radiografía por lenguajes

Go, Python y Rust manejan strings/buffers de más de 4 GB; Java no (arrays indexados con enteros de 31 bits); C# no en strings pero sí en buffers combinables; JavaScript depende del runtime (Node: strings chicas, buffers grandes). En overflows silenciosos de suma: Go, Java, C/C++ envuelven; JavaScript pierde precisión (floats); Python no puede desbordar; Rust solo en release (debug emite chequeo). En serialización a campos fijos: struct.pack de Python valida; el resto deja la responsabilidad al desarrollador antes del cast — ahí nacieron los bugs de Go y Rust.

Qué queda por hacer

El propio orador pide no lanzar payloads de 4 GB contra APIs de bug bounty — tumba sistemas y alertas de monitoreo — y señala la falta de detección no invasiva (fingerprinting de la biblioteca cliente para saber si vale la pena el test). Líneas futuras: más bases de datos y sistemas (caches, colas de mensajes, logging estructurado), protocolos con delimitadores, más bypasses de límites, y — la más prometedora — campos de longitud de 2 bytes: explotar enviando 65 KB en vez de 4 GB elimina casi todas las trabas.

Técnicas y herramientas mencionadas

  • Request smuggling en protocolos binarios: desincronizado de límites de mensaje entre cliente y servidor.
  • Truncamiento int64→int32: bug raíz en pgx, pgsql, aPG, PGDriver (Go), biblioteca C#, cliente oficial Rust de MongoDB.
  • Knob sled: repetición del mensaje mínimo del protocolo para "deslizar" hasta el payload.
  • Trampolines: bytes de longitud reutilizados como bytes de tipo para saltos encadenados; patrón alternado ante el límite lógico de mensaje de Postgres.
  • Bypasses de límites de tamaño: límites deshabilitados (Harbor/Nginx), compresión descomprimida después del chequeo (Fastify), WebSockets, multipart, SSRF server-side (Gogs).
  • BSON crafting: fabricar bytes no-UTF-8 (0xDD07) mediante longitudes de strings del documento.
  • Exfiltración indirecta: subconsulta + INSERT a tabla visible por la lógica de negocio.

Conclusiones

  • Los overflows de enteros siguen vivos y explotables en lenguajes memory-safe: sin corrupción de memoria, el desincronizado de protocolo es el nuevo vector.
  • Las protecciones de tamaño de request son bypassables por múltiples rutas; no cuentan como defensa.
  • La inyección SQL no murió: cuando la capa de consultas está bien escrita, el ataque baja al protocolo de red — hay que ir un nivel más profundo.
  • Harbor 2.11, pgx y el cliente Rust de MongoDB corregidos; varias bibliotecas Go de Postgres seguían vulnerables sin fix al momento de la divulgación.
