Android root explotando la GPU Adreno: CVE-2024-23380

Fuente: «DEF CON 32 - The Way To Android Root: Exploiting Smartphone GPU - Xiling Gong, Eugene Rodionov» · ver el video original

Resumen

Los drivers de GPU son el blanco favorito de quien busca privilegios en Android por tres razones: no requieren ningún permiso (las librerías de OpenGL y Vulkan del proceso de la aplicación hablan directamente con el device node, sin mediación de IPC ni binder), su exigencia de rendimiento les da acceso a la RAM física del sistema (mapean memoria de usuario a kernel y a hardware sin copiar — la primitiva que todo atacante quiere), y su complejidad los hace propensos a bugs y a arreglos incompletos. El Android Red Team de Google — cuyo trabajo consiste en simular adversarios contra las features clave de Android para que cada dolor que sufren en la investigación se traduzca en seguridad para el usuario final — elegó Qualcomm Adreno como objetivo: es la GPU más usada en los SoC del mercado, acaba de estrenar una arquitectura nueva (generación 7 en adelante), y sus security bulletins muestran un goteo constante de issues cada trimestre.

El resultado de la investigación: más de nueve issues reportadas a Qualcomm durante el engagement, y una explotación completa a root desde un usuario sin privilegios en un smartphone de gama alta con el último security patch — vía CVE-2024-23380, parcheada en el boletín de julio de 2024 (con aviso a los vendors desde abril).

La arquitectura nueva agranda la superficie

El driver KGSL es la capa de pegamento entre user space y hardware: expone interfaces de contexto, memoria (básica, de user space, DMA — la sparse ya no se usa), comandos y sincronización. El flujo clásico: cola de comandos → software dispatcher → ring buffer → firmware del GPU.

La generación 7+ cambió las piezas: el software dispatcher fue reemplazado por un hardware scheduler — el driver ya no toca el ring buffer, sino que envía los comandos a una cola HFI y un firmware (sin código fuente disponible) se encarga del trabajo que antes hacía el driver. Se sumaron hardware fences (con su cola y eventos propios), un nuevo objeto de memoria virtual (VBO) y un IOMMU propio de Qualcomm que reemplaza al ARM IOMMU. Cada feature nueva es capacidad nueva — y superficie de ataque nueva.

Los objetos de memoria y el VBO

Tres tipos de memoria, con roles distintos:

  • Basic memory object: el caso general. Un ioctl pide N páginas físicas; el driver las asigna, reserva un rango en el espacio virtual del GPU y arma el mapeo físico→virtual vía IOMMU; el user space además hace mmap y obtiene el mapeo vía MMU. La misma página física accesible desde el GPU y desde la app.
  • User space memory object: importa memoria existente del proceso al GPU.
  • Virtual buffer object (VBO): no tiene memoria física propia — es solo un rango de direcciones virtuales del GPU mapeado inicialmente a una página cero dummy. Su función es ser un lienzo: vía bind_range, se ligan basic memory objects al VBO en offsets específicos. Al bindear, el driver elimina los mapeos previos, registra la conexión (que impide liberar el objeto ligado) y arma los mapeos físico→virtual de todas las páginas.

Poderoso, flexible — y vulnerable.

CVE-2024-23380: la carrera del mapeo

Al bindear, dos pasos deben protegerse con el mismo mutex: la inserción en el interval tree (la conexión objeto↔VBO) y el mapeo físico→virtual. El fix muestra cuál faltaba: el mapeo estaba fuera del lock. La secuencia de carrera:

flowchart TD
    A[Thread A: lock + bind
conexion objeto-VBO en interval tree] --> B[Thread A: UNLOCK
mapeo fisico-virtual todavia pendiente]
    B --> C[Thread B: lock + unbind
conexion eliminada, objeto y paginas liberadas]
    C --> D[Thread A: mapea la pagina victima
al VBO sobre el espacio ya liberado]
    D --> E[Mapping colgante: pagina fisica libre
accesible lectura/escritura via GPU VA]

El resultado es un use-after-free de página física: lectura y escritura sobre una página ya devuelta al kernel, a través de la dirección virtual del GPU. Es una race condition, pero con propiedades de lujo: se dispara sin ajustar prioridades de threads ni trucos, es estable (se repite decenas de veces sin colgar el kernel) y tiene oráculo de feedback — el exploit sabe en cada momento si el disparo funcionó y cuántas páginas controla.

De páginas controladas a root

Controlar páginas físicas arbitrarias es el punto de partida; el método de elevación es lo novedoso. La cadena completa:

  1. Acumular: disparar la race unas 200 veces → 200 páginas físicas controladas.
  2. Forzar low memory: alocar memoria masivamente desde user space; el cache del kernel se devuelve al sistema y las 200 páginas controladas vuelven al heap del kernel.
  3. Heap spray dirigido: sembrar estructuras KGSL memory entry — que contienen una memory description con dirección física, tamaño y puntero a ops — más metadata mágica para identificarlas.
  4. Escanear y hallar: recorrer las páginas controladas buscando las estructuras sembradas por su metadata.
  5. Parchear la descripción: cambiar dirección física y tamaño por los del kernel completo → un mmap de ese objeto mapea toda la memoria física del kernel en user space → lectura/escritura arbitraria del kernel.
  6. Root: parchear versión y código del kernel.

El paso 4 depende de la suerte (que alguna entrada caiga en una página controlada), pero el método es repetible hasta acertar. Y la técnica es genérica: cualquier kernel heap overflow o race condition puede usarla — sembrar memory descriptions, desbordar sobre dirección física y ops, y mapear el kernel entero, reintentando hasta lograrlo.

Bypass de KASLR "gratis"

El puntero a ops parece exigir derrotar KASLR primero. No hace falta: KASLR opera a nivel de página, y el valor original y el objetivo suelen vivir en la misma página — los bytes altos coinciden, así que basta sobrescribir los bytes bajos. El byte más bajo es conocido del binario del kernel. En el caso residual de páginas contiguas distintas, la diferencia se reduce a ~4 bits: 16 intentos de fuerza bruta. Otros punteros de la estructura (page table, host ptr, SGT) no se usan en el flujo normal y pueden sobrescribirse con basura.

Metodología de caza y camino a mitigar

  • Patch analysis + revisión manual: leer los fixes de los boletines de Qualcomm y las publicaciones de otros investigadores; el estado del GPU es demasiado grande y con demasiadas piezas móviles para entenderlo sin el contexto de otros. La variante analysis rinde: un fix interno de Qualcomm → un blog de un investigador sobre un issue relacionado → otro issue más en la misma zona (detalles retenidos porque seguía en remediación).
  • Fuzzing con obstáculos propios del GPU: esta clase de bug (mapeo colgante en el IOMMU) exige fuzzing on-device, menos escalable; no crashea, ningún sanitizer reporta entradas MMU colgantes, y el estado (secuencias precisas de syscalls, syzkaller custom, código concurrente) resiste la automatización. Algunos vendors permiten compilar el kernel-mode component independiente de la arquitectura para fuzzear sin hardware; la emulación es alternativa pero exige trabajo manual.
  • Mitigaciones estructurales: mover el acceso al GPU de in-process a out-of-process vía IPC/binder (como hace Android para aislar componentes) — con costo de rendimiento y compatibilidad hacia atrás — y lenguajes memory-safe en los drivers, que eliminan la mayoría de las causas raíz.

Conclusiones

  • El acceso sin permisos al device node del GPU, combinado con la gestión directa de páginas físicas por rendimiento, convierte a los drivers de GPU en el camino más corto de app sin privilegios a kernel.
  • Una ventana de carrera entre la conexión en el interval tree y el mapeo IOMMU produce un use-after-free de página física accesible por el GPU: una primitiva estable, repetible y con oráculo, ideal para explotación determinista.
  • El spray de estructuras con memory description del kernel (dirección física + tamaño + ops) es una receta genérica que convierte cualquier overflow o race de heap en lectura/escritura total del kernel — con KASLR esquivado por aritmética de páginas y a lo sumo 16 intentos.
  • Las mitigaciones realistas son arquitectónicas (aislar el GPU detrás de IPC) y de lenguaje (memory safety), no parches puntuales: el patrón "páginas liberadas con mapeo IOMMU vivo" es recurrente en los bugs del GPU reportados.
