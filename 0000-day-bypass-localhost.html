0.0.0.0 Day: cómo una IP especial derribó el muro del localhost

Fuente: «DEF CON 33 - 0.0.0.0 Day: Exploiting Localhost APIs From The Browser - Gal Nagli, Avi Lumelsky» · ver el video original

Resumen

El navegador no debería poder hablar con servicios locales desde un dominio .com — y durante 18 años pudo. La investigación detrás de 0.0.0.0 Day parte de una anomalía histórica: un foro de seguridad de Mozilla que lleva casi dos décadas abierto bajo el título "websites are trying to attack my router". De ahí nacieron drive-by farming y ataques masivos contra cientos de miles de routers domésticos que, sin HTTPS ni certificados, aceptaban reconfigurar su servidor DNS con una simple petición HTTP disparada al cargar una página.

El modelo de seguridad que debía contener esto divide el mundo en tres zonas —red pública (.com), red privada (oficina/hogar) y dispositivo local (localhost/loopback)— y es la base de Private Network Access (PNA), el borrador que Google lidera desde hace unos ocho años y que sigue sin estandarizarse: retrasado varias veces, revertido tras romper webs durante la noche, y relanzado de forma gradual.

El hueco: 0.0.0.0

0.0.0.0 significa "este host en esta red" y según el RFC nunca debe usarse como IP destino; su único uso legítimo es identificarse durante un handshake DHCP antes de tener dirección asignada. En la práctica, sin embargo, los servicios que escuchan en 0.0.0.0 son iguales de accesibles que los de 127.0.0.1 — y Windows bloquea ese destino a nivel de sistema operativo, por lo que el problema queda confinado a macOS y Linux.

El efecto: todo lo que corre en la máquina —herramientas de desarrollo, servicios del sistema, port-forwarding hacia pods de Kubernetes, cualquier interfaz conectada incluida la VPN— queda alcanzable desde una web pública. Los contadores que Chromium añadió muestran que el uso de 0.0.0.0 en páginas web se multiplicó por diez en poco más de dos años, justo el vector que PNA no contemplaba.

Las demos lo demuestran todo:

  • Port scanning desde el navegador: un escáner en WebAssembly distingue puertos abiertos leyendo el código de error que el browser devuelve al JavaScript (connection refused = nada; otro error = algo escucha). Wireshark confirma que 0.0.0.0 se redirige a loopback.
  • DNS rebinding, vivo otra vez: un subdominio mapeado a 0.0.0.0 reactiva una técnica que se daba por muerta, sin tocar 127.0.0.1.
  • ShadowRay en el navegador: el punto de partida real de la investigación. Ray —el "Kubernetes de la IA" que OpenAI usa para entrenar sus mayores modelos— carece de autenticación y ejecuta código arbitrario por diseño (el CVE que lo documentaba fue disputado por ser "capacidad deseada"). En clusters expuestos a internet esto produjo una campaña real cubierta por Forbes. La variante aquí es peor: con Ray en su configuración por defecto (ray.init() sin flags, escuchando en localhost), una petición POST desde una web basta para ejecutar código — hasta una reverse shell desde un VPS hacia el equipo de quien clicó un enlace de phishing. CORS se preocupa de la respuesta; aquí ni hace falta leerla: basta con despachar la petición.

Disclosure coordinado entre navegadores

Los cuatro navegadores acordaron corregir a la vez para no zero-day-earse mutuamente:

Navegador Mitigación
Safari/WebKit Bloqueo a nivel de browser (23 archivos modificados) antes de tener PNA; cubre todos los WebViews de watchOS/iPadOS
Chromium Deprecación de 0.0.0.0 antes de que PNA termine de desplegarse; reconoce que la IP permite DNS rebinding y bypass de PNA en macOS/Linux y que malware lo aprovecha contra toolkits de desarrollo
Firefox Cambio del estándar fetch: descartar la petición HTTP cuando la IP destino sea 0.0.0.0; PNA llegará cuando el estándar se estabilice
Todos Cambios breaking, desplegados de forma gradual

Conclusiones

  • "Local" ya no es confiable. El navegador tiene capacidades de enrutamiento hacia las interfaces locales; HTTPS, CORS, tokens CSRF y autorización son obligatorios también en proyectos y servicios que solo escuchan en localhost.
  • El perímetro privado es una falsa sensación de seguridad. WAF o firewall no protegen frente a una sola petición HTTP capaz de comprometer una aplicación interna; los atacantes explotan precisamente la ausencia de un estándar.
  • Escáneres web también son víctimas: los port scanners online pueden hacerse escanear a sí mismos usando 0.0.0.0 como objetivo.
  • La aplicación debe contener sus propias mitigaciones; confiar en las viejas fronteras de red es, con los datos de esta investigación, una apuesta perdida.
