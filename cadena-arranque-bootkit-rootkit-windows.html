Infectar la cadena de arranque para tomar el kernel: anatomía de un bootkit UEFI

Fuente: «DEF CON 33 - Infecting the Boot to Own the Kernel - Alejandro Vazquez, Maria San Jose» · ver el video original

Resumen

El trabajo de simulación adversaria choca con un problema de acceso: el malware que despliegan los grupos de amenaza persistentes avanzada —bootkits, rootkits de kernel— es territorio que casi nadie documenta a fondo, y quien quiera emularlo necesita años de búsqueda fragmentada. Como respuesta, dos investigadoras e investigadores de perfiles complementarios —una analista de malware del departamento de cibercrimen de la Defensa y una operadora de red team especializada en Windows internals— publicaron un bootkit UEFI y un rootkit de kernel de Windows completos, documentados y listos para estudio, junto con un repositorio de más de 400 recursos y scripts que automatizan el montaje del entorno de desarrollo.

La premisa desmitificadora atraviesa todo el material: un bootkit no es magia oscura, es una aplicación UEFI maliciosa; un rootkit, un driver de modo kernel malicioso. Ambos tienen documentación oficial de Microsoft y del foro UEFI que permite construirlos desde cero. Lo que se comparte aquí es el mapa conceptual de la cadena completa: del encendido al control del kernel, las protecciones que hay que sortear y las seis capacidades que convierten a un driver malicioso en un rootkit con fundamento sólido.

Las definiciones sin misterio

Un bootkit es un programa que se implanta lo antes posible en el proceso de arranque: gana control sobre cada etapa del inicio y modifica el flujo de booteo, instalando componentes que permanecen vivos incluso después de que el sistema operativo toma el control. Un rootkit es un programa que funciona dentro del kernel; como el kernel gestiona memoria, procesos e interrupciones, un componente a ese nivel puede ocultar archivos, conexiones de red, desactivar protecciones y alterar estructuras internas del sistema.

Para quien arranca en el tema, la traducción útil es esta: en cualquier sistema hay drivers de modo kernel legítimos; el mismo concepto llevado a cabo con fines maliciosos es un rootkit. Si el equipo arranca con firmware UEFI, el punto inicial es una aplicación UEFI; una aplicación UEFI maliciosa es, por definición, un bootkit. En su forma básica, el malware requiere dos componentes: un binario .efi para la etapa temprana del arranque y un archivo .sys de driver de modo kernel para modificar el sistema operativo una vez cargado.

Las dos murallas: Secure Boot y Driver Signature Enforcement

Secure Boot es una cadena de confianza forzada por firmas digitales y claves criptográficas: cada componente del proceso de arranque debe estar firmado por un vendedor confiable y verificado contra una lista de claves de carga. Un bootkit no corre a menos que el firmware confíe en su firma. La muralla cae si existe una forma de insertar una clave propia en la cadena —varias vulnerabilidades públicas lo han logrado— o una falla de firmware que la omita. Y una vez que se controla el arranque, las protecciones posteriores, incluidas las que el sistema operativo refuerza, dejan de importar: quien controla el boot, controla todo.

Driver Signature Enforcement (DSE) es la segunda barrera: Windows se niega a cargar drivers de modo kernel sin firma válida de Microsoft o de un vendedor de confianza. Si la cadena de arranque ya fue comprometida, DSE pierde relevancia —el rootkit puede soltarse en memoria antes de que el sistema arranque—, pero si no, queda la técnica de Bring Your Own Vulnerable Driver: cargar primero un driver legítimo y firmado con una vulnerabilidad conocida, explotarlo para ejecutar código arbitrario en espacio de kernel y desde ahí instalar el rootkit. Microsoft mantiene una lista de drivers bloqueados, y el resultado es un permanente juego del gato y el ratón: se descubren drivers vulnerables, se abusa de ellos, se bloquean, y el ciclo continúa.

La cadena de arranque y el enganche escalonado

Al pulsar el botón de encendido, el sistema ejecuta el Power-On Self Test (POST) para verificar el hardware; después el framework UEFI busca los archivos y particiones necesarios y carga el Windows Boot Manager desde la partición del sistema EFI (ESP). Ese gestor carga el Windows OS Loader, que a su vez carga el kernel de Windows NT. Tres piezas clave que el malware quiere interceptar.

La idea central explota una propiedad del proceso: cada componente carga al siguiente en memoria, de modo que hay instantáneas en que el siguiente archivo ya está en memoria pero aún no tomó control. En esos momentos se pueden enganchar funciones dentro del siguiente componente:

flowchart TD
    A[POST + firmware UEFI] --> B[Windows Boot Manager]
    B --> C[Windows OS Loader]
    C --> D[Kernel NT]
    E[App UEFI maliciosa en la ESP] -->|reemplaza y engancha al Boot Manager| B
    B -->|hook cuando el loader ya está en memoria| C
    C -->|hook cuando el kernel ya está en memoria| D
    D --> F[Rootkit en kernel: activo antes del arranque del SO]

El bootkit reemplaza el Windows Boot Manager con una versión maliciosa que engancha la función del firmware responsable de cargar el gestor original; en lugar de ceder el control de inmediato, asegura que el gestor legítimo quede cargado en memoria, lo escanea con un patrón conocido para localizar la función que se invoca cuando el siguiente componente ya está en memoria, y la engancha parcheando su punto de entrada con un pequeño trampolín en ensamblador que redirige la ejecución a un manejador propio y devuelve el control a la función original. El mismo procedimiento se repite en cada etapa: hook tras hook, el control se mantiene durante todo el arranque. Además, estas funciones se usan para soltar el rootkit —el driver malicioso— en memoria en el momento justo, de modo que ya esté listo y corriendo cuando el sistema operativo inicie.

La especificación UEFI, con miles de páginas que cubren protocolos de memoria, sistemas de archivos e incluso redes, multiplica el alcance: una aplicación UEFI puede abrir ficheros de un servidor remoto, modificar particiones y dejar marcadores para cargas posteriores, antes incluso de que el sistema operativo exista. La especificación distingue dos categorías de servicios: los boot services, disponibles solo durante el arranque temprano, y los runtime services, que siguen disponibles después de que el sistema toma control. Al llamar a ExitBootServices, toda la memoria configurada por la aplicación se descarta —irrelevante si el rootkit ya está cargado—, pero un diseño cuidadoso aprovecha los runtime services para establecer persistencia: un driver DXE de runtime, una clase especial de driver UEFI que permanece en memoria después del arranque y permite enganchar los runtime services, funciona como puerta trasera casi invisible para ejecutar cargas y leer o escribir memoria mientras el sistema corre.

Las seis capacidades que hacen bueno a un rootkit

El corazón del malware es el rootkit: vive en espacio de kernel, opera con los máximos privilegios y entrega el control real. Todo lo anterior —UEFI, hooks, secuestro del arranque, drivers de runtime— es la cadena de infección que asegura que el rootkit corra de forma confiable. Seis técnicas forman la base recomendada para empezar:

  1. Comunicación: con una aplicación en modo usuario, con un servidor de comando y control, o ambas, manteniendo capacidad de actuar de forma autónoma.
  2. Manipulación directa de objetos del kernel (DKOM): lo que permite, por ejemplo, ocultar procesos; en 2025 hay que hacerlo bien para no disparar una protección y provocar una pantalla azul.
  3. Captura de pulsaciones de teclado a nivel kernel, interceptando los paquetes correspondientes.
  4. Filtrado de red con la plataforma de filtrado de Windows (WFP): alterar, bloquear o capturar tráfico en tiempo real.
  5. Comando y control a nivel kernel con Winsock Kernel (WSK): el driver puede hacer conexiones HTTP por sí mismo, sin proceso en modo usuario, cerrando el ciclo de control completo en espacio de kernel.
  6. Filtrado del sistema de archivos con la tecnología de minifiltros —la misma que usan las soluciones de seguridad— para ocultar archivos y carpetas y denegar su acceso.

Las demostraciones en vivo lo mostraron sobre una máquina física con Secure Boot habilitado: un proceso desaparece del Administrador de tareas y de Process Hacker, una carpeta se oculta del explorador, direcciones IP quedan bloqueadas, conexiones TCP al puerto 443 desaparecen de netstat y el canal de comando y control corre íntegramente dentro del driver. También se mostró que el DSE seguía habilitado —el error de firma apareció en pantalla— y aun así el rootkit ya estaba en memoria, porque la aplicación UEFI lo soltó antes del arranque. Para quien quiera profundizar, el fundamento recomendado es dominar cómo una aplicación de modo usuario se comunica con un driver de kernel mediante IOCTLs e IRPs: esa base prepara de forma natural para seguir explorando vulnerabilidades en drivers de kernel.

Qué se publicó y para qué sirve

La publicación incluye el proyecto de bootkit UEFI (aplicación, drivers de kernel básicos que puede soltar en memoria, driver DXE de runtime con su herramienta de comunicación, scripts de montaje y la herramienta que genera la configuración cifrada que consume la aplicación), el repositorio del rootkit con pruebas de concepto independientes para cada técnica, y más de 400 recursos de investigación, notas para instalar el rootkit en una máquina física real y guías para analizar el propio firmware UEFI en busca de vulnerabilidades. La motivación declarada: que cualquier equipo que entregue servicios de simulación adversaria pueda emular el tipo de malware que hoy solo despliegan los grupos APT, sin pasar un año juntando migajas dispersas.

Desde la óptica defensiva, el material funciona como catálogo de lo que hay que asumir posible: un atacante con acceso físico o firmware comprometido puede mantener persistencia por debajo del sistema operativo, con canales de comando y control que no dejan proceso visible en modo usuario. Los minifiltros maliciosos usan la misma tecnología que los productos de EDR; la detección de hooks en la cadena de arranque y la verificación de la integridad del firmware son, por tanto, superficies de defensa que merecen la misma atención que el modo usuario.

Conclusiones

  • Un bootkit es una aplicación UEFI maliciosa y un rootkit un driver de kernel malicioso: no son conocimiento secreto, son desarrollo de software ofensivo con documentación oficial disponible.
  • El enganche escalonado de la cadena de arranque explota un patrón simple —cada componente carga al siguiente en memoria— y se repite etapa por etapa desde el Boot Manager hasta el kernel.
  • Secure Boot es la protección crítica: si la cadena de firmas se rompe o el firmware tiene una falla, todas las protecciones posteriores pierden sentido; verificar y actualizar firmware es defensa de primer orden.
  • Las seis capacidades esenciales de un rootkit moderno —comunicación, DKOM, keylogger, filtrado de red, C2 a nivel kernel y filtrado del sistema de archivos— definen también la lista de comportamientos que un detector debería vigilar en espacio de kernel.
  • Compartir código documentado con la comunidad defensiva reduce la asimetría entre quienes emulan amenazas y quienes las persiguen: dominar IOCTLs e IRPs es el punto de partida natural para el análisis y la explotación de drivers.

Técnicas y herramientas mencionadas

  • Bootkit UEFI: aplicación UEFI maliciosa que secuestra el flujo de arranque enganchando funciones del Boot Manager, el OS Loader y el kernel.
  • Trampolín en ensamblador: parche del punto de entrada de una función que redirige la ejecución a un manejador propio y vuelve a la original.
  • Secure Boot: cadena de confianza de firmas digitales y claves criptográficas que valida cada componente del arranque.
  • Driver Signature Enforcement (DSE): política de Windows que impide cargar drivers de kernel sin firma válida.
  • Bring Your Own Vulnerable Driver (BYOVD): carga de un driver firmado vulnerable para explotarlo y ejecutar código en kernel.
  • DXE runtime driver: driver UEFI que persiste en memoria tras el arranque y permite enganchar los runtime services como puerta trasera.
  • DKOM: manipulación directa de objetos del kernel para ocultar procesos.
  • Windows Filtering Platform (WFP): tecnología para filtrar, bloquear o capturar tráfico de red a nivel kernel.
  • Winsock Kernel (WSK): API que permite al driver mantener conexiones HTTP y comando y control sin proceso en modo usuario.
  • Minifiltros: clase de drivers de filtrado del sistema de archivos, usados tanto por soluciones de seguridad como por rootkits para ocultar archivos.
  • IOCTL / IRP: mecanismos de comunicación entre aplicaciones de modo usuario y drivers de kernel; fundamento para el análisis de drivers.
  • ExitBootServices: llamada que marca el traspaso del control del firmware al sistema operativo y descarta la memoria de boot services.
