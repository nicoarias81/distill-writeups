Kafka: la primera RCE del broker, cacería de bugs en todo el ecosistema y el bypass de la lista negra de login modules

Fuente: «DEF CON 32 - Apache Kafka: Founder or Servant, the Shield and Sword of Democracy in Kafka - Ziyang Lin, Ymir (Alibaba Cloud)» · ver el video original

Resumen

Apache Kafka es la plataforma de streaming distribuido que sostiene pipelines de datos, análisis en tiempo real y arquitecturas críticas en empresas de todo el mundo. Su broker —el corazón del sistema— nunca había tenido una vulnerabilidad de ejecución remota de código. Este trabajo parte de una vulnerabilidad conocida del cliente (CVE-2023-25194, inyección JNDI a través del login config), generaliza la técnica en tres direcciones y termina donde nadie había llegado: una RCE autenticada en el propio broker, confirmada por el equipo de Kafka y premiada por Confluent con el bug bounty más alto de su historia.

El hilo conductor es una idea simple y potente: si el parche de 2023 pone en lista negra el JNDI login module, basta encontrar otro login module que se comporte igual. Esa búsqueda —ProxyLoginModule de JBoss, módulos de WebSphere, el LdapLoginModule del propio JDK— produce bypasses del parche, RCE en componentes del ecosistema (Kafka Connect, ksqlDB, Confluent CP Server) y, finalmente, la ruta hacia el broker. El trabajo fue presentado por ingenieros de seguridad de Alibaba Cloud.

De CVE-2023-25194 al patrón general

Kafka se organiza en productores (fuentes de datos), consumidores (lectores y procesadores) y el clúster, dividido en plano de control (metadatos: topics, brokers, replicación; con las implementaciones ZooKeeper y KRaft) y plano de datos (los brokers que atienden produce y fetch requests por topic).

La vulnerabilidad original, CVE-2023-25194, vive en el cliente: si un atacante controla la cadena de conexión (connection string) con la que un cliente Kafka se conecta al servidor, puede inyectar un login config malicioso que dispare una búsqueda JNDI hacia un servidor LDAP controlado, y de ahí ejecución remota de código. El flujo de ataque: servidor LDAP malicioso → cadena de conexión maliciosa al cliente → construcción del JAAS login config → LoginContext.login → JNDI lookup → takeover.

El parche de la versión 3.4.1 introduce una lista negra de login modules, y el JNDI login module está deshabilitado de fábrica: cualquier config que lo mencione lanza una excepción. La pregunta que estructura todo lo demás: ¿hay más login modules explotables?

Los criterios de búsqueda: que implemente la interfaz LoginModule, que exista en librerías Java populares y que pueda terminar en RCE. Con esos filtros aparecen tres candidatos que valen por toda una familia de técnicas:

  • ProxyLoginModule (JBoss): delega la autenticación en otro módulo cuyo nombre se configura libremente. Configurarlo para delegar en el JNDI login module —que sigue en la lista negra— hace que el módulo vetado termine ejecutándose igual. El bypass es directo: la lista negra revisa el config del usuario, pero no sigue la delegación.
  • Módulos de WebSphere: la cadena de dos payloads permite escribir un web shell. Primero un payload instruye al servidor para usar un login config controlado; el segundo provoca un error cuyo mensaje —con contenido malicioso— el servidor escribe en el archivo indicado. Web shell y RCE.
  • LdapLoginModule (integrado en el JDK): obtiene usuario y contraseña vía callback handler y, si la contraseña no está vacía, dispara la misma inyección JNDI. Necesita un callback handler que cumpla tres condiciones a la vez: manejar NameCallback y PasswordCallback, devolver una contraseña no vacía, e implementar la interfaz AuthenticatedCallbackHandler de Kafka —el filtro que más reduce el universo de candidatos—.

Ese tercer camino desemboca en Confluent: los custodios de Kafka publican una versión community (cp-kafka) y una comercial (CP Server). En CP Server existe un FileBasedDynamicCredentialsCallbackHandler que lee usuario y contraseña de un archivo local cuyo nombre se controla: no hace falta subir un archivo propio, basta apuntarlo a /etc/passwd y usar un usuario existente (por ejemplo root) como credencial no vacía. Con eso, LdapLoginModule + callback handler de Confluent = RCE en CP Server. Probado en la versión 7.7.1 (noviembre de 2024); corregido en versiones posteriores.

Del cliente al ecosistema: Kafka Connect y ksqlDB

El patrón general queda formulado así: con configuración de cliente Kafka controlada por el atacante y las técnicas de bypass, hay RCE. La pregunta siguiente es dónde aparece esa configuración controlable en sistemas reales.

Kafka Connect: siguiendo la documentación oficial de Confluent, la PoC de CVE-2023-25194 funciona sin cambios; convirtiéndola a formato YAML y sustituyendo el payload por el bypass del ProxyLoginModule, la RCE se reproduce.

ksqlDB: el hallazgo fue accidental. Leyendo un issue de GitHub ("the producer is closed falsely") surgió la duda de por qué hay un productor dentro de un motor de consultas. La respuesta: las operaciones INSERT producen datos, y la configuración de ese productor se obtiene de la "session config". Probando, la configuración es modificable —y con ella, inyectar el bypass y lograr RCE en el servidor ksqlDB. Con esta técnica se tomaron el control de despliegues Confluent de varios cloud proveedores.

El broker: RCE autenticada vía listeners dinámicos

El broker era el territorio sin explotar: sin RCE conocidas hasta entonces. El punto de entrada fue la documentación, buscando configuraciones sospechosas: existe una funcionalidad de listeners dinámicos —se pueden agregar (y quitar) listeners en caliente— y, lo más interesante, la configuración JAAS del listener también se puede fijar dinámicamente.

El escenario de ataque: un atacante autenticado (con credenciales de cliente válidas) envía una petición AddListener al broker pidiendo un nuevo listener con protocolo SASL_PLAINTEXT. El broker intenta levantar el listener, descubre que no hay configuración JAAS asociada y falla —pero el mensaje de error revela el camino: Kafka autentica mediante JAAS, así que si se provee la configuración JAAS correcta, el proceso JAAS se dispara y con él la inyección JNDI hacia un servidor LDAP malicioso.

La configuración se fija por clave dinámica: listener.name.<nombre>.<mecanismo>.sasl.jaas.config. Con el mecanismo por defecto GSSAPI falla en un primer intento (falta el server name); se resuelve añadiendo sasl.kerberos.service.name, o directamente cambiando el mecanismo a PLAIN. Con ambos ajustes, el broker emite la petición LDAP hacia el servidor del atacante: shell.

La sorpresa llegó al probar contra la versión 3.4.0 —la que parcheó CVE-2023-25194—: la misma excepción del cliente. La explicación está en el código: cliente y servidor cargan el contexto JAAS por caminos distintos (loadClientContext / loadServerContext) pero ambos terminan en la misma función load, donde Kafka puso la restricción. El parche del cliente había arreglado por accidente una vulnerabilidad desconocida del servidor. De no ser por ese parche, el broker habría llevado una RCE sin descubrir.

¿Y en Confluent? El bypass del ProxyLoginModule (presente en la versión comercial) reaparece aquí: en el broker hay que declarar antes el listener en listener.security.protocol.map y luego fijar el callback handler —que también se puede configurar dinámicamente— con la clave listener.name.sasl_plaintext.sasl.login.callback.handler.class apuntando al módulo que delega en el vetado. Con el servidor LDAP malicioso levantado y un puerto a la escucha, el exploit entrega shell dentro del contenedor del broker Confluent.

Ambos hallazgos se reportaron: Kafka confirmó la vulnerabilidad —la primera RCE que afecta a su broker— y Confluent emitió el mayor bug bounty de su historia. El parche es directo: deshabilitar por defecto los módulos JNDI y LDAP.

Técnicas y herramientas mencionadas

  • CVE-2023-25194: RCE en cliente Kafka vía connection string controlado → inyección JNDI; aplica a Kafka Connect y otros componentes.
  • Lista negra de login modules (3.4.1): mecanismo de mitigación que bloquea el JNDI login module por nombre.
  • ProxyLoginModule (JBoss): delegación de autenticación a un módulo configurable; evita la lista negra al invocar el módulo vetado indirectamente.
  • Módulos de WebSphere: doble payload que provoca escritura de un mensaje de error controlado en un archivo → web shell.
  • LdapLoginModule (JDK): dispara JNDI lookup si el callback handler entrega contraseña no vacía; requiere AuthenticatedCallbackHandler de Kafka.
  • FileBasedDynamicCredentialsCallbackHandler (Confluent CP Server): lee credenciales de un archivo controlable; /etc/passwd con usuario existente (root) como fuente de credenciales.
  • ksqlDB session config: configuración del productor interno modificable vía INSERT → RCE en el servidor.
  • Listeners dinámicos del broker: AddListener en caliente con listener.name.<listener>.<mechanism>.sasl.jaas.config para fijar JAAS malicioso.
  • SASL_PLAINTEXT + JAAS: combinación que dispara el proceso de autenticación del broker hacia el LDAP del atacante.
  • listener.security.protocol.map: mapa obligatorio de protocolos por listener en Confluent, requisito previo al exploit del broker comercial.
  • Kafka config tool: lectura de la configuración del broker (broker id, listeners, puertos 9092/9093) como reconocimiento previo.

Conclusiones

  • La lista negra de login modules es una mitigación de superficie: bloquea nombres, no comportamientos. Cualquier módulo que delegue (ProxyLoginModule) o que alcance el mismo lookup (LdapLoginModule con un callback handler usable) la sortea.
  • La RCE del broker nació de leer documentación en busca de configuraciones dinámicas: listeners y JAAS configurables en caliente convierten una función administrativa en superficie de ataque autenticada.
  • Los parches tienen efectos laterales que nadie auditó: el fix del cliente en load() protegió también al servidor por accidente — la revisión de código de un parche es en sí misma una actividad de caza de vulnerabilidades.
  • La defensa práctica se resume en tres capas: actualizar Kafka a versiones con el fix (módulos JNDI y LDAP deshabilitados por defecto), exigir autenticación habilitada y nunca exponer componentes del ecosistema de Kafka a internet: son piezas internas de infraestructura, y el catálogo de componentes explotables —CP Server, Connect, ksqlDB, broker— no deja de crecer.
