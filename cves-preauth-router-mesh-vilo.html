De CTF al mundo real: nueve CVEs pre-auth en un router mesh Vilo

Fuente: «DEF CON 33 - From CTF Skills to Real World Hacking - Springboarding from CTF to Firmware and CVE Discovery - Justin Applegate, Ava Peterson, Justin Mott, Wyatt Pangirl» · ver el video original

Resumen

Un equipo de estudiantes de BYU aplicó técnicas de CTF a un objetivo real: el router mesh doméstico Vilo. Sin investigación previa publicada, sin firmware descargable y sin vía directa al bug bounty del fabricante, el proyecto de un semestre culminó en nueve vulnerabilidades (seis críticas, tres medias), de las cuales cuatro son buffer overflows pre-autenticación con CVSS 9.6, además de una command injection autenticada que permite obtener shell como root. Los números CVE quedaron reservados ante MITRE.

La ruta fue la clásica de investigación en hardware y firmware: extraer la flash por SPI, emular con QEMU, invertir el protocolo custom del servicio local y buscar bugs a mano en Ghidra — sin fuzzing. El resultado es también una demostración de que el salto de CTF a vulnerabilidades reales en IoT es corto: los dispositivos baratos comparten los mismos patrones de código inseguro, y la superficie sin auditar es enorme.

El objetivo y por qué fue elegido

Vilo Living es una startup de 2021 con solo dos productos, ambos routers mesh Wi-Fi (5 y 6). No había CVEs, ni análisis técnicos, ni siquiera reviews que documentaran las funciones internas. Sumado a un precio bajo (de los más baratos en Amazon), parecía el blanco ideal para aprender: terreno virgen y asequible.

Tres particularidades definieron el enfoque. Primera: no hay interfaz web de administración (nada de 192.168.1.1); todo se configura desde una app móvil. Segunda: el bug bounty requería firmar un NDA e ingresar al grupo de beta testers — el fabricante nunca respondió con el NDA, así que se investigó sin él. Tercera: el firmware no era descargable, había que extraerlo del dispositivo.

Los objetivos del proyecto: obtener el firmware (para convertir el black box en white box y facilitar el exploit development), lograr shell en el dispositivo, y encontrar la máxima cantidad de RCE pre-autenticación.

Reconocimiento de hardware: dos routers muertos

La desmonta reveló pines UART. El primer intento de soldadura destruyó el primer router. El segundo router sobrevivió y mostró un login de Linux, pero la contraseña era desconocida y la interfaz UART moría 30 segundos después del boot, imprimiendo la cuenta regresiva cada segundo — imposible entrar por ahí.

El resultado clave del reconocimiento vino de la app Android: junto con información de Firebase y servicios cloud, se identificó un servicio custom en TCP 5432, usado para la configuración inicial cuando el router no tiene acceso a internet.

Extracción del firmware por SPI

Un chip de memoria flash almacenaba el firmware. Las utilidades de software devolvían datos corruptos; la solución fue un analizador lógico Salae conectado al bus SPI: al encender el router, todo el tráfico SPI se capturó y decodificó directamente en el software del analizador, y scripts de Python lo convirtieron en el binario del firmware. Un mes de intentos fallidos, dos horas con la herramienta correcta.

Emulación con QEMU y toolchain MIPS

El SoC es MIPS 32-bit little-endian, imposible de ejecutar nativo en máquinas x86/ARM. La emulación combinó QEMU compilado estáticamente con chroot (para que los binarios encontraran sus librerías en las rutas hardcodeadas) y breakpoints de GDB calculados con ingeniería inversa en Ghidra. QEMU con -g 1234 abre una sesión de debugging remoto en el puerto 1234, conectable con gdb-multiarch desde otra terminal.

Para compilar binarios propios (el firmware carece incluso de whoami o netcat) se armó un toolchain con Buildroot y uClibc-ng — fork de uClibc, sin mantenimiento desde 2012. El bind shell compiló sin problemas; gdbserver conectaba pero hacía segfault. Esta emulación fue la base para fuzzing, testing y exploit development.

El protocolo custom del puerto 5432

El servicio usa un header de 15 bytes más payload, con mensajes diferenciados por opcodes. La "encriptación" es XXTEA más una capa de obfuscación custom: la app envía una key hardcodeada, el router responde con una nueva key cifrada — todo reversible. Con las claves derivadas desde la hardcodeada fue posible hablar el protocolo.

El problema de diseño: el servicio no tiene autenticación real y permanece activo todo el tiempo que el router está encendido, aunque ya tenga internet. Cualquier cliente de la LAN que hable el protocolo puede controlar el router como si fuera el dueño: ver y cambiar SSID, contraseña Wi-Fi, credenciales PPPoE, reiniciar el dispositivo y explotar las demás vulnerabilidades. Esto convirtió varios buffer overflows autenticados en RCE no autenticados.

Las vulnerabilidades

De las nueve, destacan tres. Cuatro buffer overflows pre-auth en el servicio (CVSS 9.6), una fuga de información y una ausencia de autenticación completan la lista; los números están reservados ante MITRE en el orden de publicación del repositorio.

Falta de autenticación (CVE de información). Descrita arriba: sin autenticación en el servicio local, la frontera de seguridad es solo saber hablar el protocolo. Invitar un amigo a la red Wi-Fi equivale a darle control total del router.

Buffer overflow en appSetRouterToken (opcode 0x3e). El opcode actualiza un token y zona horaria recibidos como JSON cifrado. Un sscanf copia el token a un buffer fijo sin validar longitud: un token de 20 bytes en un buffer de 16 produce el overflow. Con canaries deshabilitados (versión antigua del firmware), se controla el registro ra (return address) y s8. La explotación en MIPS es incómoda: no hay instrucción return, lo que dificulta encadenar gadgets ROP. La estrategia fue un gadget "one-shot": con ASLR activo pero PIE deshabilitado, las variables globales tienen direcciones conocidas; apuntar s8 a un comando controlado y el instruction pointer al gadget debía ejecutarlo. La prueba con ; reboot ; no funcionó — y accidentalmente reinició el router de forma tal que quedó en un boot loop permanente, nunca más online (error propio, no del exploit). En la versión más reciente del firmware los canaries están habilitados y este overflow no es explotable tal cual.

Command injection autenticada en sysconf (el hallazgo accidental). Buscando el código responsable del boot loop, apareció el verdadero camino al shell: sysconf, que corre en el boot, arma un comando udhcpc con variables interpoladas — incluido el hostname del router — y lo pipea directo a system(). Como el hostname se configura desde la app, setearlo a un comando bash da RCE. Limitaciones: el comando corre una sola vez en el boot, y el hostname se limita a 30 caracteres.

La cadena encadena las restricciones: /folly es uno de los pocos directorios a la vez escribible y persistente; el router aún no tiene internet cuando corre el comando inyectado (por eso la espera de 20 segundos); y el shell final es un binario C compilado con el toolchain MIPS. Resultado: netcat al router y prompt de root.

Divulgación: un mes para encontrar al fabricante

Contactar a Vilo fue difícil: el email de security de los términos de servicio rebotaba, las direcciones web y redes sociales no respondieron, y los tickets de soporte tardaron un mes en derivar al equipo de desarrollo. Timeline: proyecto de enero a principios de abril, contacto a fin de abril con los detalles de las nueve vulnerabilidades y deadline de 90 días, seguimientos sin respuesta, registro de CVEs ante MITRE conforme a lo avisado, respuesta del fabricante recién cerca del vencimiento — con firmware nuevo publicado justo antes de DEF CON, pendiente de verificación. El canal de actualizaciones OTA corre por MQTT cifrado dentro del ecosistema AWS IoT; el endpoint HTTP que reportaba "último firmware" en realidad no lo servía (detalle que hizo que se analizara una versión más vieja que la instalada).

Técnicas y herramientas mencionadas

  • UART — interfaz serial de depuración; en este router moría 30 segundos tras el boot.
  • SPI + Saleae logic analyzer — captura del bus de la memoria flash para extraer el firmware binario.
  • QEMU (estático) + chroot — emulación del firmware MIPS en x86 con rutas de librerías respetadas.
  • QEMU -g + gdb-multiarch — debugging remoto del binario emulado en el puerto 1234.
  • Ghidra — ingeniería inversa del firmware MIPS (búsqueda de vulnerabilidades manual, sin fuzzing).
  • XXTEA + obfuscación custom — "cifrado" del protocolo del puerto 5432, reversible desde la key hardcodeada.
  • Buildroot + uClibc-ng — toolchain para compilar binarios MIPS (bind shell propio).
  • ROP en MIPS — sin instrucción return; gadget one-shot controlando ra y s8.
  • PIE deshabilitado + ASLR — variables globales en direcciones fijas para posicionar el comando.
  • sscanf sin validación de longitud — origen del buffer overflow en appSetRouterToken (opcode 0x3e).
  • Command injection vía hostname → system() — sysconf interpola el hostname en el comando udhcpc del boot.
  • Payload en stages — script en /folly → wget → bind shell C compilado para MIPS.
  • MQTT cifrado (AWS IoT) — canal real de distribución de actualizaciones OTA.
  • MITRE CVE — números reservados para las nueve vulnerabilidades.

Conclusiones

  • El salto de CTF a vulnerabilidades reales es directo: el mismo kit (reversing en Ghidra, explotación de memory corruption, protocolos custom) funciona en IoT, solo cambia la fase de acceso al firmware.
  • Los patrones inseguros se repiten en dispositivos baratos: claves hardcodeadas, servicios sin autenticación activos permanentemente, sscanf sin límites y comandos armados por interpolación de strings.
  • La extracción de firmware por SPI con analizador lógico es rápida cuando las utilidades de software fallan; dos horas frente a un mes de intentos alternativos.
  • La superficie de ataque quedó mayormente intacta: solo se examinó una fracción pequeña, y los autores dejaron el repositorio abierto para quien quiera continuar la búsqueda.
