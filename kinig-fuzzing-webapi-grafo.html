CONiQ: fuzzing de Web APIs guiado por grafos, sin escribir gramáticas a mano

Fuente: «DEF CON SG1 - CSIT Village - Poh Cai Min & Shawn Pang - Kînig Bridging Webapi Fuzzing With A Graph» · ver el video original

Resumen

Chai Min y Shawn presentan CONiQ, una herramienta que aplica formación de grafos al fuzzing de Web APIs: automatiza la generación de gramáticas a partir de los archivos WebIDL públicos y convierte el conocimiento del investigador en una base de datos de grafo compartible, para hacer fuzzing más inteligente, más rápido y mucho más accesible.

El punto de partida: fuzzing estructurado y su cuello de botella

El fuzzing es una técnica de prueba de software que alimenta a un programa con entradas aleatorias e inesperadas para provocar errores y, sobre todo, errores de seguridad. Su gran ventaja es que no exige conocer los internos del programa antes de empezar: se puede entrar a ciegas pensando solo en qué entrada espera y avanzar desde ahí. Herramientas clásicas como la suite de AFL, el fuzzer de "lip" o el "hong fuzz" encarnan esa idea: como un equipo que amasa masa al azar, se estira y se ve qué pasa.

El fuzzing lleva más de una década evolucionando para reducir el espacio de entrada y volverlo dirigido: hay fuzzing guiado por cobertura de código, por diccionario y por estructura. El foco de esta presentación es el fuzzing basado en gramática: cuando el objetivo no acepta bits sueltos sino sintaxis y estructura —por ejemplo un lenguaje de programación o una API—, un fuzzer clásico se queda en la capa de parsing inicial y no llega a ejercitar la lógica más profunda. Herramientas como Dharma o Domato generan entradas a partir de una gramática, pero el problema vuelve a aparecer: escribir la gramática consume mucho tiempo. Y si se pasa de una Web API a otra —de Web Audio a WebRTC, por citar el ejemplo— la gramática cambia por completo y no hay forma de combinar el conocimiento acumulado entre investigaciones.

Cómo funciona CONiQ

flowchart LR
    A[Archivos WebIDL\nopen source de la Web API] --> B[CONiQ]
    B --> C[Grafo de relaciones\nde interfaces y tipos]
    B --> D[Gramática\ncompatible con Domato]
    D --> E[Muestras HTML\ncomo casos de prueba]
    E --> F[Navegador\nChrome + WebGPU]
    F --> G[Hallazgos y conocimiento\ndel investigador]
    G --> H[Base de datos de grafo\nNeo4j]
    H --> B

El pipeline arranca de algo que ya existe y es público: los archivos WebIDL, el lenguaje de definición de interfaces que usan los navegadores como Chrome para generar el glue code entre JavaScript y el C++ del navegador. Cada Web API —Web Audio, WebRTC, Chrome AI, la API de redes neuronales web, y en el demo WebGPU— tiene sus IDL publicados en open source, con tipos, métodos, argumentos y enums.

CONiQ toma esos archivos y genera dos artefactos:

  • Un grafo de relaciones donde cada interfaz de la API queda encapsulada como nodo: los métodos, sus argumentos con tipos y los enums cuelgan de esos nodos con las dependencias necesarias para invocarlos.
  • Una gramática compatible con Domato, el motor de Project Zero que consume gramáticas y produce muestras HTML de fuzzing listas para soltar en un navegador como Chrome.

Sobre ambos se agrega la pieza diferencial: el grafo se carga en Neo4j como base de conocimiento central, donde el investigador entra a modificar el grafo y, a partir de él, se mejora la gramática. Todo el flujo es un ciclo: generar muestras → campañas de fuzzing → aprender de los resultados → ajustar el grafo → regenerar gramática.

El caso real: código de shader que salía como basura

El demo recorre el ciclo completo sobre WebGPU. Primer paso: generar grafo, gramática y muestras HTML desde los IDL de WebGPU, sin bootstrapping engorroso. Después, el trabajo del investigador en Neo4j: navegar los nodos, consultar el camino más corto entre la interfaz de un módulo de shader GPU y su uso como entrada del render pipeline, expandir nodos para ver cómo se construye cada método.

Ahí aparece el problema que justifica todo el sistema: en WebGPU se puede cargar código en el lenguaje de shaders WGSL mediante la función de creación de módulo de shader de la interfaz de dispositivo GPU. Pero en el IDL ese código está tipado como un string, y el string termina expandiéndose a contenido plano de bytes o arrays de enteros: puro ruido aleatorio. El navegador espera código de shader válido; con ruido, todos los casos de prueba que invoquen la compilación del shader fallan, y con ellos toda la rama de código que se quería ejercitar.

La solución es declarativa y vive en el grafo, no en la gramática:

  1. Se crea un nodo de valor auxiliar en Neo4j con código WGSL válido —que puede incluir a su vez sentencias Domato que se expanden recursivamente—.
  2. Se conecta al nodo del diccionario de código, en lugar del generador aleatorio de strings.
  3. Se le pone probabilidad de selección: por ejemplo, 80% de las veces usar el shader válido y 20% el ruido aleatorio. La probabilidad queda como atributo del borde en el grafo.
  4. Se vuelve a pasar el grafo por CONiQ y la gramática regenerada ya incluye el nodo auxiliar; las muestras HTML salen con código de shader real incrustado.

Todo ese ajuste queda capturado en un único archivo patch versionado, que otro investigador puede aplicar para partir exactamente de donde quedó el anterior. Y no es el único tipo de conocimiento bakeable: si una API solo acepta múltiplos de 4 en un entero de 64 bits, se agrega un modificador que fuerce esos valores; si un array solo puede tener longitud 1 a 3, se limita la generación en el grafo.

IA en el ciclo

Los autores también muestran el atajo moderno: en lugar de escribir las consultas a mano, se le pide a Claude Code —con el MCP de Neo4j— que inspeccione el grafo, cree el nodo con las restricciones descubiertas durante el fuzzing y ajuste las probabilidades. El investigador describe en texto lo que la API rechazó ("solo arrays de longitud 4") y el agente modifica el grafo.

Como extensión futura plantean cerrar el círculo completo: agentes de IA que lean los crashes y bugs, extraigan el conocimiento de los hallazgos y modifiquen el grafo automáticamente para mejorar la estabilidad y generar casos de prueba que lleguen a rutas de código aún no cubiertas, montado sobre la base que ya existe: gramáticas generadas con esfuerzo mínimo, conocimiento acumulado y transferible entre investigadores.

Técnicas y herramientas mencionadas

  • Fuzzing basado en gramática vs. fuzzing clásico: llegar más allá de la capa de parsing.
  • WebIDL: fuente pública de interfaces, tipos, métodos y enums de cada Web API.
  • Domato (Google Project Zero): motor que consume la gramática generada y produce muestras HTML.
  • Neo4j como base de conocimiento: consultas de caminos más cortos, nodos auxiliares de valor, probabilidades en los bordes.
  • WebGPU como objetivo del demo, incluyendo generación de código WGSL válido en lugar de ruido.
  • Patches versionados del grafo para transferir conocimiento entre investigadores.
  • Claude Code + MCP de Neo4j: edición del grafo por lenguaje natural.

Conclusiones

  • El costo real del fuzzing de Web APIs no está en ejecutar el fuzzer sino en escribir y mantener gramáticas específicas por API; ese costo se elimina derivando la gramática de los IDL públicos.
  • Convertir la API en un grafo consultaible permite que el conocimiento operativo —"este argumento acepta solo múltiplos de 4", "este string debe ser WGSL válido"— se codifique una vez y se reutilice, en lugar de perderse en notas de cada investigación.
  • Las probabilidades en el grafo permiten calibrar el balance entre exploración aleatoria y caminos válidos conocidos, ajustando cuánto ruido tolera el objetivo sin romper la cobertura.
