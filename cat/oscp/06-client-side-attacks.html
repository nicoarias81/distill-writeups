PEN-200 — Client-Side Attacks

Fuente: material del curso correspondiente (sin video público)

Objective

Establish a foothold on a target network through the client instead of the perimeter: profile the target's software remotely, fingerprint the victim's OS/browser without touching a routable host, then deliver a payload via two vectors — Microsoft Word macros and Windows Library files — to obtain a reverse shell from a non-interactable internal machine. All four transcripts follow the same arc: gather → fingerprint → weaponize → deliver → shell.

Target surface

Client-side attacks here target people and their workstations, not listening services. The transcripts use a simulated victim workflow (documents delivered by email / an SMB share) against an "offsec" Windows user desktop; no fixed lab IPs are given in the source material — attacker-side listeners run on Kali (reverse shells land on a Netcat listener on port 4444 in the examples).

Surface Vector Prerequisite
Public documents on the org website Metadata extraction (offline) Org publishes PDFs/Office docs
Victim's browser Canary Token fingerprinting link (requires internet egress from victim) Victim clicks a link
Victim's Office install VBA macro in a .doc file Victim clicks Enable Content
Victim's Explorer Windows Library file (.library-ms) → WebDAV share → shortcut (.lnk) Victim double-clicks the library file, then the shortcut

The victim's machine is assumed non-routable from the attacker — every payload must call out (download cradle + reverse shell), which is why the same PowerShell/Powercat cradle recurs across both weaponization sections.

Techniques

Note: source transcripts are noisy ASR. Commands below are normalized from the spoken walkthroughs; tool names were corrected where the ASR mangled them (e.g. "ExifTool with dash A" → exiftool -a). Anything not stated verbatim in the transcripts is marked as inferred.

1. Remote software profiling via document metadata (module 41)

Works with zero target interaction — no packets to the victim, no alerts, no forensic traces. Trade-off: the profile may be stale or inaccurate.

Browse the target organization's site ("Mountain Vegetables" in the lab) for downloadable documents, then dump metadata:

# -a = show duplicated tags, -u = show unknown tags
exiftool -a -u brochure.pdf

What the output buys you:

  • Create Date / Modify Date — relative age of the document.
  • Author — a real internal employee's name; drop it casually into a targeted email or phone call to bootstrap trust (especially effective if the person keeps a small public profile).
  • Creator/Producer software (e.g. Microsoft PowerPoint for Microsoft 365) — confirms the target uses Microsoft Office.
  • Absence of macOS/4Mac tags — probabilistic evidence the fleet is Windows.

That last two points select the attack vector: Windows client-side vectors and malicious Office documents are viable; the metadata told you so before you ever sent a payload.

2. Client fingerprinting with Canary Tokens (module 42)

Goal: confirm the victim runs Windows with Internet Explorer/Edge available (the precondition for an HTA attack) from a victim inside a non-routable network. The token link is the outbound channel that bypasses the network isolation.

Workflow on canarytokens.org:

  1. Pick the token type (web/URL token) from the drop-down, enter an email or webhook URL for alerts, click Create My Canary Token.
  2. Copy the generated tracking link; Manage This Token → History shows every visitor (empty until triggered; default settings are fine for pure fingerprinting).
  3. Send the link under the pretext. The victim sees a blank page.

What the History entry reveals:

  • User agent → OS + browser (e.g. Chrome on 64-bit Windows 10). ⚠️ User agents are client-controlled and not always reliable.
  • JavaScript fingerprinting section → browser details collected by embedded JS on the token page — more precise and reliable than the UA, and it also agreed on Chrome/Windows.
  • Geolocation map and attempted organization-name resolution.

Decision rule from the module: the lab's fingerprint showed Chrome on Windows, which neither confirms nor denies IE/Edge availability. Either switch to a different client-side vector or change the pretext so the victim must open the content in IE/Edge (e.g. "the screenshot is only viewable in Internet Explorer").

3. Microsoft Word macros → reverse shell (module 43)

Macros remain effective if the fingerprinting/pretext work convinced the victim to click Enable Content.

Build steps (in Word):

  1. Save as .doc — a .docx can run macros from an attached template but cannot embed/save the macro in the document, so the macro would not persist. This is the classic gotcha.
  2. View tab → Macros → name the macro, set "Macros In" to the document itself, Create.
  3. In the VBA skeleton (Sub ... End Sub; ' starts a comment), instantiate a Windows Script Host Shell object via ActiveX and call its Run method to launch a process.
  4. Office macros don't auto-run: wire the code into the predefined AutoOpen macro / DocumentOpen event so it fires when the document opens.

Minimal concept (normalized from the walkthrough):

Sub AutoOpen()
    MyMacro
End Sub

Sub Document_Open()
    MyMacro
End Sub

Sub MyMacro()
    Dim str As String
    str = "<chunked base64 PowerShell cradle>"
    ' CreateObject("WScript.Shell").Run "powershell ..."
End Sub

Escalating to a reverse shell with Powercat:

  • Build a Base64-encoded PowerShell download cradle that fetches Powercat from the attacker web server and starts the reverse shell; Base64-encoding sidesteps special-character quoting issues.
  • VBA literal strings are capped at 255 characters — the limit does not apply to strings built in a variable, so split the Base64 blob into ~50-character chunks and concatenate them. (The course does this with a short Python helper that chunks the encoded string and prints each line in VBA assignment format.)
  • On Kali: serve Powercat (python3 -m http.server in its directory) and start a Netcat listener on 4444.

Operational details worth remembering:

  • First open of a modified document → "macros have been disabled" banner; the victim must click Enable Content or the attack dies. Macros are disabled outright in some enterprises but are common enough in real environments that this usually works.
  • The security warning does not reappear on reopen — it only triggers again if the document is renamed. The lab's second open ran the macro silently.
  • Confirmation trail: GET request for the Powercat script on the Python web server + incoming shell on the Netcat listener.

4. Windows Library files → WebDAV → shortcut, two-stage attack (module 44)

Stage 1 gains a foothold in Explorer without exposing the payload to spam filters; stage 2 delivers the executable that starts the reverse shell.

Stage 0 — attacker WebDAV share. A WebDAV server is started on Kali (listen host on all interfaces, port 80, authentication disabled, share root set to a directory holding a placeholder test.txt). ⚠️ Ambiguity: the transcript describes the parameters but never names the tool; the parameter set (--host/--port/--auth/--root, "running on port 80") matches wsgidav, which is the tool used in the PEN-200 labs — treat as inferred. Verify by browsing to the share.

Stage 1 — the library file. Create an empty file on the victim's (test) desktop as config.library-ms (ASR rendered it "config.libraryms" — the real extension is .library-ms). Library files are XML with three major parts; the walkthrough builds:

  • XML declaration + library-format namespace (the Windows-7-era format version).
  • <name> — ⚠️ not arbitrary: it must reference a DLL name and index. <version> is free-form (e.g. 6).
  • <isLibraryPinned>true</isLibraryPinned> — pins it to the Explorer navigation pane; small authenticity boost.
  • <iconReference> — same DLL-name-and-index format; the lab uses the Pictures folder icon, replacing the uncommon (suspicious-looking) default .library-ms icon.
  • <templateInfo>/<folderType> — set to the Documents GUID so Explorer shows the expected columns/details.
  • <searchConnectorDescriptionList> → <searchConnectorDescription> describing the remote location:
  • <isDefaultSaveLocation>true</isDefaultSaveLocation> — default save target behavior.
  • <isSupported>false</isSupported> — ⚠️ undocumented tag, used for compatibility.
  • <simpleLocation> → <url> pointing at the attacker WebDAV share over HTTP — the critical tag.

Opening the file shows the WebDAV contents, and the Explorer address bar displays only config — no hint it's a remote location. One caveat Windows introduces for you: after first open, VS Code shows an auto-added <serialized> tag (Base64 metadata describing the URL location) and Windows rewrites the <url> content to optimize it for the Windows WebDAV client. The file still works on the machine that opened it, but the serialized form may break on other machines or after a restart (Explorer shows an empty share). Usually irrelevant — you only need the victim to double-click once.

Stage 2 — the shortcut. On the victim desktop: right-click → New → Shortcut → point it at PowerShell with the same Base64 download-cradle command (fetch Powercat from Kali, start reverse shell) → name it something innocuous like "Automatic Configuration". Test locally (double-click → shell on the Netcat listener), then copy the .lnk onto the WebDAV share — conveniently draggable through the library file itself.

Delivery. Email the library file in a real engagement; the lab simulates delivery over SMB:

smbclient //<target>/share -c 'put config.library-ms'

⚠️ Ambiguity: the transcript shows the put via smbclient's -c flag but does not state the share name or credentials (redacted) — use whatever the lab/engagement provides.

Pretext (the module calls it out explicitly as the important part): "new IT team member configuring all client systems for the new management platform, included a user-friendly configuration program." Simulated victim opens the library file, double-clicks the shortcut, shell received. The module notes this chains naturally with the macro attack or any other client-side vector.

Detection & defense

  • Document metadata hygiene: strip metadata before publishing (Exiftool is exactly what an attacker uses — assume whatever it shows is readable). Train staff that author/software fields leak; authors of public documents are social-engineering lures by name.
  • Fingerprinting / phishing links: egress-proxy and DNS reputation for canarytokens.org-style domains; block or banner unknown external links in email. Blue teams can run their own canary tokens — a trigger you didn't send is recon.
  • Office macros: the single highest-leverage control. Block macros from the internet (Mark-of-the-Web), block .doc/.docm macro execution via policy, and treat every Enable Content click as user-assisted compromise. Macro-enabled formats in email attachments should be stripped at the gateway. Note the course's observation in reverse: the warning banner re-appears on rename, so users get one silent bypass per file.
  • Library files / WebDAV: alert on outbound WebDAV (HTTP PROPFIND) to untrusted hosts and on Explorer opening .library-ms/.ms connector files from email; the attack's OpSec strength (address bar shows only "config", payload never touches spam filters) is also its detection gap — hence egress monitoring over endpoint-only inspection.
  • Download cradles: PowerShell fetching and executing scripts from the internet (Base64-encoded, chunked to dodge length limits and string signatures) is the common thread of both weaponization modules — constrain PowerShell (Constrained Language Mode, script block logging, AMSI), and alert on IEX/DownloadString + encoded-command patterns.
  • Kill chain view: every stage here is detectable at the egress boundary (token beacon, Powercat GET, reverse shell) even when the entry vector looks benign — layered egress filtering beats trying to classify the lure document.
