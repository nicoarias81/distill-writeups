PEN-200 Module Block — Linux Privilege Escalation (LPE_01–LPE_04)

Fuente: material del curso correspondiente (sin video público)

Objective

Take an unprivileged foothold on a Linux target (the course's Debian lab machine, plus an Ubuntu target for the kernel-exploit unit) and climb to root. The block is a four-stage ladder:

  1. Enumeration — manual baseline first (LPE_01_02), automated sweeps second (LPE_01_03).
  2. Credential hunting — user trails in dotfiles (LPE_02_01), service footprints leaking passwords at runtime (LPE_02_02).
  3. Misconfiguration abuse — writable cron scripts (LPE_03_01), a writable /etc/passwd (LPE_03_02).
  4. Binary/OS abuse — SUID binaries and capabilities (LPE_04_01), permissive sudo with AppArmor in the way (LPE_04_02), and kernel exploits (LPE_04_03).

A recurring theme: automation finds the common misconfigs, but unique one-off changes are only caught by manual inspection — the course runs both, always manual first to build the model the tools will corroborate.

Target surface

  • Primary lab host: Debian 10 ("buster", x86_64), reached via SSH as user joe (UID/GID 1000). Services visible on it: Apache 2 web server, SSH daemon. Hostnames encode OS type + role.
  • Secondary user: eve, a standard user with a home directory who turns out to be an administrative (sudo-all) account.
  • Kernel-exploit unit target: Ubuntu 16-series machine, kernel 4.x, x86-64.
  • Supporting hosts: Kali attack machine (gcc, searchsploit, pre-installed unix-privesc-check).
  • Lab IPs and passwords are not stated in the audio / are redacted here as [REDACTED].

Techniques

1. Manual enumeration — LPE_01_02

The ordered baseline for any Linux foothold:

User context. id for the current user; read /etc/passwd for all users (ASR: "Etsy password"). Field-by-field walkthrough: username, x (hash lives in /etc/shadow), UID (root = 0; regular users count from 1000 — the "Real User ID"), GID, GECOS, home, shell. Service accounts (www-data, sshd) carry /usr/sbin/nologin shells — that also fingerprints what's installed (web server, SSH). Knowing all users identifies high-privilege targets worth attacking.

Hostname & OS. hostname (don't trust the prompt — use the command). Role abbreviations (web, db, dc) focus the hunt; enterprise naming conventions encode location/OS/service level. For kernel-exploit targeting precision (a mismatched kernel exploit can crash the box): /etc/issue and /etc/os-release (Debian 10, codename buster), then uname -a for kernel version + architecture.

Processes. ps aux — processes running as root that are research-worthy for vulns; filter by user when needed.

Network. Interfaces: ifconfig -a / ip a (multiple networks = pivot potential; virtual interfaces hint at virtualization/AV). Routes: route / ip route. Connections and listening ports: netstat -anp / ss -anp — services bound only to loopback are invisible to remote scanning but reachable locally; a privileged program listening on 127.0.0.1 is a prime LPE target.

Firewall. iptables -L needs root, but the iptables-persistent package stores rules in files under /etc/iptables (readable at boot), and any iptables-save dump the admin ever made may be world-readable — grep the filesystem for it. Lab finding: a non-default rule explicitly allowing destination port 1999 — noted for later.

Scheduled tasks. /etc/cron.* directories (cron.daily, …), admin-added jobs in /etc/crontab (most run as root — inspect file permissions carefully), crontab -l for your own jobs. sudo crontab -l (when sudo rules allow it) reveals root's jobs: the lab has a backup script running every minute.

Installed software. dpkg -l (Debian) / RPM equivalents (Red Hat) — corroborates port enumeration: the machine is indeed running Apache 2. Version notes feed exploit search later.

Weak permissions. Can't check every file by hand — use find:

find / -writable -type d 2>/dev/null        # dirs writable by current user
find / -perm -4000 2>/dev/null              # SUID binaries

Lab hit: /home/joe/.scripts is world-writable — and it's where the root cron script lives (→ technique 5).

Storage & modules. mount, /etc/fstab, lsblk — unmounted partitions can be mountable and may hide credentials/documents. lsmod lists loaded kernel modules; modinfo <module> (full path required) gives version info for exploit matching.

SUID/SID concept. Executables with s in permissions run with the owner's rights: if root owns the binary, any user executes as root (effective UID/GID). If you subvert a SUID-root program into calling a command of your choice, you effectively are root — hence find-ing them is standard first move. (/bin/cp as SUID would let you overwrite /etc/passwd.) The course points to g0tmi1k's Linux privesc compendium for a technique catalog.

2. Automated enumeration — LPE_01_03

unix-privesc-check (bash, pre-installed on Kali): run with no args for modes; standard mode is speed-optimized with fewer false positives, detailed mode is exhaustive. Transfer to target, run standard mode, redirect to output.txt. Lab finding: /etc/passwd writable by non-root users — attacker can edit it or add accounts (→ technique 6).

Also mentioned: LinEnum and LinPEAS (ASR garbles the second name), actively developed privesc checkers. Caveat the course insists on: every system is different; unique one-off changes are missed by all automated tools — manual inspection (technique 1) is not optional.

3. Inspecting user trails (dotfiles) — LPE_02_01

Low-hanging fruit first. Dotfiles (hidden, .-prefixed) in home directories hold user activity and configuration; history files can contain cleartext passwords. .bashrc runs on every new shell and commonly exports environment variables — admins sometimes stash credentials there for custom scripts.

Lab walkthrough: the live environment shows a credential-looking variable; confirming it is persistent means reading .bashrc where the export lives. Two escalation routes from one finding:

  • Direct: su to root with the discovered password [REDACTED] — done.
  • Derived: pivot to user eve. Build a custom wordlist from the known password pattern with crunch (min=max=6, pattern lab%%-style: fixed prefix + 3 digits — ASR loses the exact mask), then remote brute force SSH with Hydra:
hydra -l eve -P wordlist.txt <target-ip> -t 4 -v ssh

Hydra cracks it → SSH as eve → sudo -l shows she can run any command as an elevated user → sudo -i with her credentials = root (sudo credential cache valid ~15 minutes). Two routes to root from one dotfile.

4. Inspecting service footprints — LPE_02_02

Unlike Windows, Linux lets unprivileged users inspect root-owned process activity. Two credential-leak angles:

  • Process command lines: ps is a snapshot — refresh it with watch -n 1 and grep for pass. A root daemon is seen invoking its connection with eve's cleartext credentials on the command line. Running as root doesn't shield a process from inspection.
  • Traffic capture: tcpdump needs raw sockets (root), but admins routinely grant specific users sudo rights to it for troubleshooting — the lab grants exactly that to joe. Capture on the loopback interface with ASCII output and filter for pass; within seconds the root user's cleartext credentials scroll past.

5. Abusing cron jobs (writable script) — LPE_03_01

Find an executable we can write to and that runs elevated. Cron is the prime target: system-level jobs run as root, and admins write their scripts with insecure permissions. Confirm from the cron log: a user_backups script under /home/joe executes as root once a minute. The script is trivial (copies the home dir to a backups subdir) and its permissions allow any local user to write it.

Exploitation: append a reverse-shell one-liner to the script, set up a listener on Kali, and wait ≤ one cron interval → root-level reverse shell. The course notes this is not an artificial example — production boxes routinely have exactly this because admins prioritize shipping over securing script permissions.

6. Abusing password authentication (writable /etc/passwd) — LPE_03_02

Background: without central auth (AD/LDAP), password hashes live in /etc/shadow (root-only). Historically they were in the world-readable /etc/passwd; for backwards compatibility, if a hash is present in the second column of a /etc/passwd record it is valid for authentication and takes precedence over /etc/shadow. Writable /etc/passwd therefore = arbitrary password for any account.

Exploitation:

openssl passwd <new-password>          # default: crypt(3) hash, valid for Linux auth
# append:  root2:<hash>:0:0:root2:/root:/bin/bash
su root2                               # then: id  → uid=0

The 0:0 UID/GID makes the new account a superuser. The course admits world-writable /etc/passwd seems unlikely in the wild, but third-party vendor integrations that trade security for usability keep it alive in practice.

7. Abusing SUID binaries and capabilities — LPE_04_01

SUID mechanics, demonstrated properly: why can a normal user change their own password when /etc/shadow is root-only? Because of the effective UID/GID — the value the kernel checks for sensitive operations. Run passwd, leave it waiting, and from a second shell inspect /proc/<pid>/status: four UID fields (Real, Effective, Saved Set, Filesystem). For passwd (PID e.g. 5489): Real UID = 1000 (joe), the other three = 0 (root) — set by the SUID bit (s in permissions, settable via chmod), which forces the effective UID to the file owner. A legitimate, constrained escalation — which means the binary must be bug-free or it's a root door.

Exploitation — SUID find: enumeration flags find as SUID-root. Any -exec action it runs inherits root:

find <known-file> -exec /bin/bash -p \;     # -p keeps the effective user from being reset

Root shell: UID still reads joe, effective UID is 0.

Capabilities: extra attributes on processes/binaries/services granting fine-grained privileges (packet capture, kernel-module loading). Misconfigured = same risk as SUID. Enumerate recursively:

getcap -r / 2>/dev/null

Lab finding: Perl binaries carry cap_setuid=ep (effective+permitted). GTFOBins provides the ready payload (set the UID and spawn a shell with the appropriate POSIX directives) → root shell via a third misconfiguration vector.

8. Abusing sudo (with AppArmor in the way) — LPE_04_02

sudo = superuser-do; on Debian the user must be in the sudo group. Per-user rules live in /etc/sudoers (and drop-ins); sudo -l lists what the current user may run. The lab user may run three things: crontab, tcpdump, apt-get. Overly permissive sudo rules let a user convert short-lived admin rights into permanent root.

  • crontab variant doesn't allow editing an actual crontab — dead end.
  • tcpdump GTFOBins payload fails with permission denied. Investigate via syslog: the audit daemon logged the attempt — AppArmor blocked it. AppArmor is a kernel module providing mandatory access control through per-application profiles, enabled by default on Debian 10; aa-status (as root) confirms tcpdump has a dedicated active profile. Lesson: a GTFOBins entry is necessary but not sufficient — MAC profiles can neuter a nominally-abusable binary.
  • apt-get GTFOBins route works: the changelog option pipes into less, from which you drop into a bash shell — root shell via the third allowed command.

9. Exploiting kernel vulnerabilities — LPE_04_03

Kernel exploits are powerful but unforgiving: must match kernel version and distro flavor (Debian, RHEL, Gentoo…). A mismatched exploit can crash the box.

Workflow:

  1. Fingerprint: /etc/issue (Ubuntu), uname -a (Ubuntu-16-specific kernel, x86-64).
  2. SearchSploit on Kali, keywords like linux kernel ubuntu 16 local privilege escalation; filter output (exclude < 4.4.0 and the 4.8 branch); pick the newest match (here: any kernel < 4.13.9).
  3. Read compile instructions — first ~20 lines of the exploit usually state them; rename the source to the expected filename if the procedure assumes it.
  4. Compile with matching architecture. Preferred when the target has gcc (this one does): transfer the source via scp, compile on the target (gcc <source>.c -o <out>) so the target's own libraries/headers are used — removes cross-compilation compatibility risk. Verify the produced ELF with file.
  5. Run the binary → root shell.

Detection & defense

  • Privilege boundaries: the whole block exists because ordinary users can read root's metadata (/etc/passwd, /proc/<pid>/status for root processes, ps aux, ss/netstat, cron logs). Hardening means shrinking that readable surface: restrict cron log access, avoid plaintext credentials in process arguments (pass config via root-only files), and audit dotfiles/env-var secrets — .bashrc exported passwords were the single easiest root in the block.
  • File permissions: world-writable anything under a root-executed path is a finding — the cron script (LPE_03_01) and /etc/passwd (LPE_03_02) were both trivially exploitable. Watch for /etc/passwd containing hash columns (legacy compat is an attack primitive); keep hashes only in /etc/shadow. Baseline with the same tools attackers use (unix-privesc-check, LinPEAS) as scheduled integrity checks.
  • SUID/capabilities: inventory SUID binaries and getcap -r / output; remove SUID from anything not requiring it (find should never be SUID); replace broad capabilities with scoped ones. A SUID bug in a root-owned binary is a guaranteed local root.
  • Sudo: least-privilege the sudoers entries — apt-get→less, tcpdump postrotate tricks, and similar GTFOBins routes convert any allowed command with a shell escape into root. Keep AppArmor/SELinux profiles active (they demonstrably blocked the tcpdump route) and audit log the sudo group; sudo -l output is the attacker's roadmap, so keep it short.
  • Credential hygiene: password patterns derived from one leak (crunch wordlist from the discovered password) defeated eve's account — reject password-mangling patterns and enforce lockouts against small custom wordlists over SSH; disable/restrict cleartext credential channels (the pass greps found passwords over loopback and on a command line).
  • Kernel patching: kernel exploits end the game with no configuration left to save you — patch and reboot on a cadence; keep compilers (gcc) off production targets to force the riskier cross-compilation path, and monitor for new SUID/ELF binaries appearing in user-writable locations.
  • Monitoring optics: watch-looped ps, greps for pass, find / -perm -4000, getcap -r /, and rapid Hydra SSH attempts all generate distinctive noise; auditd already caught the tcpdump GTFOBins attempt in this block — that's the detection that worked.
