Objective

With an authenticated position inside the corp.com lab domain, this module attacks the two pillars of AD authentication — NTLM (cached/LSASS-held secrets) and Kerberos (tickets) — as a progression of privilege:

  1. Dump what's cached — Mimikatz against LSASS: password hashes (and sometimes cleartext, via WDigest) of every user logged onto a compromised host, plus steal TGT/TGS tickets from memory.
  2. Password spraying done surgically — read the domain account policy first (net accounts), compute the lockout-safe attempt budget, then spray via three protocols with different noise/stealth profiles: LDAP/ADSI, SMB (CrackMapExec), and Kerberos (Kerbrute).
  3. Abuse Kerberos design gaps — AS-REP roasting (accounts without pre-authentication) and Kerberoasting (SPNs mapped to user accounts): request a crackable hash with an ordinary domain user, crack it offline.
  4. Forge tickets — with the SPN account's NTLM hash, mint silver tickets granting any user/group against one SPN, without ever touching the DC.
  5. Become a DC — DCSync with Domain Admin rights (Mimikatz lsadump::dcsync / impacket secretsdump): impersonate a replication partner and request any user's hash directly, including Administrator.

Structure follows the course order: video AADA_01_03 covers cached credentials; AADA_02_01–02_05 form the attack ladder.

Target surface

  • Domain: corp.com, domain controller referred to only as "the domain controller" — its IP is never spoken; commands that need it are written with <dc-ip>.
  • Client75 — Windows 11 lab client where all hands-on examples run over RDP. Accounts used, in escalating order:
  • jeff — domain user, local administrator on Client75 (enough for Mimikatz, needs privilege::debug for SeDebugPrivilege).
  • jeffadmin — member of Domain Admins (used for DCSync).
  • dave, pete, jen — domain users (Dave: no-pre-auth victim + sprayed credential; Pete: authenticating user from Kali; Jen: second spray hit).
  • iis_service — service account mapped to an HTTP SPN (Kerberoast victim, silver-ticket forging key).
  • WEB04 — domain server running IIS (http/web04.corp.com SPN target; also the SMB share accessed to cache a demo service ticket).

Techniques

1. Cached AD credentials with Mimikatz — AADA_01_03

Since jeff is a local administrator on Client75, run PowerShell as administrator, launch Mimikatz, enable the debug privilege (lets Mimikatz interact with processes owned by other accounts, i.e. LSASS), then dump LSASS-held logon material:

privilege::debug                    # enable SeDebugPrivilege
sekurlsa::logonpasswords            # dump credentials of all logged-on users

Output gives the credential material for every user logged onto the host, including remote logons (RDP sessions) — the video shows two hash types each for dave and jeff:

  • Functional level Windows 2003: NTLM is the only available hash algorithm.
  • Windows Server 2008 or later: NTLM plus SHA-1, a common companion for AES encryption (Kerberos keys), may be available.
  • On WDigest-enabled systems — Windows 7 by default, or wherever it was manually re-enabled — Mimikatz also returns cleartext passwords alongside the hashes.

Armed with hashes, the next step is offline cracking as in the password attacks module.

Tickets live in the same place. TGTs and TGSs for logged-on users are cached in LSASS; to generate one, open a second PowerShell window and list an SMB share on WEB04 (dir \\web04\...) — this caches a service ticket. Then:

sekurlsa::tickets                   # list TGTs/TGSs in memory

Output shows both a TGS and a TGT. Stealing a TGS grants only that ticket's specific resource; a TGT lets you request TGSs for any resources you want in the domain. Mimikatz can also export tickets to disk and import tickets into LSASS (sekurlsa::tickets /export and kerberos::ptt), covered later. Overall verdict from the course: Mimikatz extracts authentication material from most protocols and mechanisms — a Swiss Army knife for cached credentials.

2. Password attacks: policy-aware spraying — AADA_02_01

The gating consideration for brute force/wordlist attacks in AD is account lockout. First read the domain's account policy as jeff on Client75:

net accounts

Key fields from the lab output: Lockout threshold: 5 bad attempts → 4 attempts are safe before a lockout; Lockout observation window: 30 minutes → after that window past the last failure, more attempts are possible. Budget math: (24h / 30min) × 4 = 192 login attempts per user per 24 hours without triggering a lockout (assuming real users never fail a login themselves). That motivates the spray shape: a short list of very common passwords against a massive number of users — cheap success rate, huge network traffic if done naively.

Three spraying approaches with different protocol/noise profiles:

a) LDAP/ADSI — low and slow. .NET DirectoryEntry can be constructed with three arguments: the LDAP path to the DC, a username, and a password. Object creation succeeding = correct password; an exception ("The user name or password is incorrect") = wrong. A script can enumerate all domain users and authenticate at a rate respecting threshold/window. This is already implemented in SprayPasswords.ps1 on Client75:

SprayPasswords.ps1 -Pass <password>     # single password
SprayPasswords.ps1 -File <list.txt>     # wordlist file
SprayPasswords.ps1 -Pass <password> -Admin   # include admin accounts

The script auto-enumerates domain users and sprays; the lab run returned two valid credential sets.

b) SMB — traditional but noisy and slow. Every attempt builds and tears down a full SMB connection → high traffic, slower. From Kali, CrackMapExec:

crackmapexec smb <client75-ip> -u users.txt -p passwords.txt -d corp.com --continue-on-success

-u/-p take lists or single values; --continue-on-success avoids stopping at the first hit. Output marks validity per line with +/-. Two caveats from the course: CrackMapExec does not read the domain password policy first — lockout risk is on you — but as a bonus it reports local administrative privileges of valid credentials: a run with dave's sprayed password against Client75 shows (Pwn3d!) → Dave is local admin on that box. Excellent for triaging access level without extra enumeration.

c) Kerberos TGT — quietest. kinit (Linux) with a username/password sends an AS-REQ and inspects the response — two UDP frames per attempt. Bash/scripting can automate it; the off-the-shelf, cross-platform (Windows/Linux) tool is Kerbrute:

kerbrute passwordspray -d corp.com --usernames usernames.txt <password>

Lab usernames.txt held Pete, Dave, Jen; Kerbrute confirmed the password valid for Pete and Jen. User lists come from the AD enumeration module or the built-in user enumeration of CrackMapExec/Kerbrute. Spraying is especially effective when the account policy has no lockout threshold set.

3. AS-REP roasting — AADA_02_02

Targets accounts with "Do not require Kerberos pre-authentication" enabled: anyone can request their TGT, and the returned AS-REP contains a hash encrypted with the account's key → crack offline. From Kali as a pre-authenticated user (Pete, [REDACTED]):

impacket-GetNPUsers -dc-ip <dc-ip> -request -outputfile hashes.asreproast corp.com/pete:[REDACTED]

-request asks for the TGT; the output AS-REP hash is hashcat-format by default. The run identifies Dave as vulnerable. Find the hashcat mode:

hashcat --help | grep -i kerberos    # AS-REP roast → mode 18200
hashcat -m 18200 hashes.asreproast rockyou.txt -r best64.rule --force

Result: Dave's plaintext password ([REDACTED] in this writeup; --force because cracking runs in a VM).

On Windows, Rubeus (raw Kerberos interaction/abuse toolkit), run as authenticated domain user jeff on Client75 — no options needed beyond the attack mode, it finds vulnerable accounts itself:

Rubeus.exe asreproast

It lists Dave and prints the AS-REP hash. To feed hashcat, the paste into hashes.asreproast2 in kali's home needs manual fix-up: remove all line breaks/spaces so the hash is one line, and add the $23 (encryption-type) separator to make it hashcat-18200-compatible; then crack as above.

4. Kerberoasting — AADA_02_03

Targets SPNs mapped to domain user accounts: any authenticated user can request a TGS for the SPN, and the TGS is encrypted with the service account's key → offline crack. Windows first, as jeff on Client75:

Rubeus.exe kerberoast /outfile:hashes.kerberoast

Rubeus identifies all SPNs linked to domain users, finds one vulnerable account (iis_service), and writes the TGS-REP hash to the file. On Kali, check the mode (hashcat --help | grep -i kerberos → 13100 for TGS-REP) and crack:

hashcat -m 13100 hashes.kerberoast rockyou.txt -r best64.rule --force

Recovered the plaintext password of user iis_service. From Linux, since the Kali host is not domain-joined, authenticate as Pete:

impacket-GetUserSPNs -dc-ip <dc-ip> -request corp.com/pete:[REDACTED]

Cracking the saved hashes.kerberoast2 yields the same plaintext password. The course's power caveat: this is immensely potent when high-privileged service accounts have weak passwords (common in practice) — but if managed/group-managed service accounts (gMSA) are used for the SPN, the password is random, complex, and 120 characters long, making cracking unfeasible.

5. Silver tickets — AADA_02_04

Forge your own TGS instead of requesting/cracking one. Scenario: iis_service has an established session on Client75 (we're local admin there) and its password is known from Kerberoasting. Three inputs required:

  1. SPN password hash (NTLM of iis_service — Mimikatz privilege::debug + sekurlsa::logonpasswords as before),
  2. Domain SID — whoami /user, strip the final RID (or read it from the Mimikatz output, same domain),
  3. Target SPN — here http/web04.corp.com (the IIS web page).

Baseline check first: iwr (Invoke-WebRequest) with -UseDefaultCredentials sends the request as the current user — Jeff cannot access the web page. Then forge with Mimikatz's kerberos::golden module (used for golden and silver tickets; golden tickets are the next module's topic):

kerberos::golden /domain:corp.com /sid:<domain-sid> /target:web04.corp.com /service:http /rc4:<ntlm-of-iis_service> /user:jeffadmin /ptt

/domain, /sid, /target (host where the SPN runs), /service (SPN protocol), /rc4 (SPN account NTLM hash), /ptt (pass-the-ticket: inject the forged ticket into memory now). /user must be an existing domain user — the video uses jeffadmin — but the permission/groups in the ticket are whatever we set: the forged ticket claims the user is the built-in local administrator (RID 500) and a member of highly privileged groups including Domain Admins (RID 512). Confirm with klist (silver ticket for jeffadmin → http/web04.corp.com in the current session), then re-run the iwr -UseDefaultCredentials — access granted as jeffadmin.

Key points: the attack works without the plaintext password of the impersonated user, and forging works the same for SPNs run in the context of a machine account — one SPN's hash = arbitrary identity/permission against that SPN, with the DC never consulted. Most situations need privileged access to harvest the SPN hash, which is why silver tickets shine in later phases of an engagement.

6. Domain Controller Synchronization (DCSync) — AADA_02_05

Exploit the redundancy of synchronized DCs: ask one to replicate. Requires replication rights — the course uses jeffadmin (Domain Admins member) via RDP on Client75. Windows, Mimikatz:

lsadump::dcsync /domain:corp.com /user:dave

Mimikatz impersonates a domain controller and obtains Dave's credentials through the replication mechanism — output includes the NTLM hash. Crack it offline (hashcat mode 1000, NTLM, as learned in the password attacks module):

hashcat -m 1000 hashes.dcsync rockyou.txt -r best64.rule --force

→ Dave's plaintext password. With these rights you can pull the NTLM hash of any domain user — including administrator — and later use hashes directly for lateral movement (covered in the Lateral Movement in AD module). From non-domain-joined Kali, impacket:

impacket-secretsdump -just-dc-user dave 'corp.com/jeffadmin:[REDACTED]@<dc-ip>'

-just-dc-user names the target user; credentials of a user with the required rights + DC IP go in domain/user:password@ip format. The tool's own output states it uses the Microsoft API implementing the Directory Replication Service Remote Protocol (MS-DRSR) — the same replication channel Mimikatz abuses.

Detection & defense

  • LSASS dumping (sekurlsa::*): the root enabler is a local admin touching LSASS. Enable Credential Guard (no LSASS plaintext/WDigest since Win10; never re-enable WDigest), run users without local admin, and monitor for SeDebugPrivilege use and protected-process access attempts. EDR signatures for Mimikatz are table stakes; restricted admin mode for RDP limits credential exposure on jump hosts.
  • Password spraying: enforce lockout policies (the course's 192-attempts/day budget disappears with a threshold + observation window), but tune so lockouts don't become a DoS for the attacker's benefit. The LDAP/ADSI and Kerberos variants are near-silent — detect via failed 4625/4771/4776 rates per source and per password, DC logs (Kerbrute = bursts of pre-auth failures from one host), and 30-per-window pacing. CrackMapExec's SMB mode is the loudest: full connection per attempt — network sensors can flag sequential SMB auth storms.
  • (Pwn3d!)-style privilege triage is the attacker's early warning of which accounts are DA/local-admin — inventory those accounts (tiering model), since sprayed-credential-to-local-admin is the whole escalation path.
  • AS-REP roasting: the account flag "Do not require Kerberos pre-authentication" should be enabled nowhere unless a legacy app truly demands it — audit for it (DC-side event 4768 without pre-auth type). Strong passwords make the cracked hash worthless but fix the flag regardless.
  • Kerberoasting: minimize user-mapped SPNs; use gMSAs (the course's own counter: 120-char random passwords make cracking unfeasible) and long passwords on any remaining service accounts. Detection: 4769 requests with RC4 encryption type en masse from a host, especially for many SPNs in sequence — service tickets are requested in bulk by Kerberoast tooling.
  • Silver tickets: the DC is bypassed entirely, so DC logs won't show the forged TGS — the service (here IIS) sees only a ticket it can't fully validate. Mitigations: protect service-account credentials (they are the signing key), prefer gMSA, and where possible configure services with PAC validation / Kerberos armoring so the DC is re-consulted. Blue teams can hunt on 4769-absence plus suspicious 500/512 group claims at the application.
  • DCSync: replication should come only from DCs. Audit accounts holding Replicating Directory Changes / Replicating Directory Changes All (Domain Admins, DCs) — any other principal holding them is an immediate alert (event 4662 with the replication GUIDs). Mimikatz/secretsdump impersonate DCs over MS-DRSR; the control is rights hygiene, not traffic signatures.
  • Hash use: every cracked/DCSync'd NTLM hash enables pass-the-hash later — treat NTLM hash exposure as password-equivalent compromise; enable SMB signing, restrict NTLM, plan for the hash-free world (Kerberos-only).
  • Cross-cutting, in the course's own terms: the ladder in this module starts from one local-admin session on a client and ends at every password in the domain. Defenders should price each rung — credential guard, lockout policy, no-pre-auth audit, gMSA, replication-rights audit — because each is the single checkpoint between a phished workstation user and domain takeover.
