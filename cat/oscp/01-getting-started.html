PEN-200 Module 1 — Getting Started: Information Gathering (passive & active enumeration)

Fuente: material del curso correspondiente (sin video público)

Objective

Establish the enumeration mindset that the rest of PEN-200 builds on: information gathering is cyclic, not linear — every finding (a hostname, a mail server, a NetBIOS name) seeds the next round of queries against the new subset of hosts, and each round is recorded in notes. The module walks the full ladder against the Megacorp One (megacorp1.com) lab target:

  1. Passive reconnaissance — whois, Google hacking, Netcraft, open-source code (GitHub), Shodan, Security Headers / Qualys SSL Labs. Third parties do the scanning; we never touch the target.
  2. Active enumeration — DNS (host/dnsrecon/dnsenum, nslookup from Windows), port scanning with Nmap (traffic budgeting, SYN/connect/UDP scans, sweeps, OS/service detection, NSE), and service-specific enumeration: SMB (139/445), SMTP (25, VRFY/EXPN), SNMP (161/UDP, MIB trees).

Structure follows the course order: videos IG_02_01–IG_02_06 are passive, IG_03_01–IG_03_06 are active (DNS → Nmap → SMB → SMTP → SNMP).

Target surface

  • Primary domain: megacorp1.com (Megacorp One). Passive sources surface their registrar data, name servers, technologies, public repos, and internet-facing devices.
  • Secondary domain used in the Windows-side DNS examples: megacorp2.com (e.g. mail.megacorp2.com, info.megacorp2.com).
  • Lab Windows hosts referenced: a Windows 11 client (client01-style VM) used as the "no-tools, no-internet" vantage point, and domain controller DC01 for SMB/SNMP enumeration.
  • Transcript note: the ASR output contains no lab IP addresses (192.168.x) and no credentials — the videos narrate over screen captures. Everything below is command-shape and methodology; lab-specific values were not recoverable from audio.

Techniques

1. Whois (passive) — IG_02_01

Whois is a TCP service, tool, and database type exposing domain registration data (name servers, registrar). Registrars charge for private registration, so much of it is public. Forward search, forcing a specific whois server:

whois -h <whois-server-ip> megacorp1.com

Value in the output: the registrant — the lab's domain was registered by Alan Grofield, who per the Megacorp One contact page is the IT and Security Director (useful for social engineering later) — plus the name servers, which feed the DNS enumeration phase. With an IP in hand, a reverse whois lookup reveals who hosts that IP.

2. Google hacking (passive) — IG_02_02

Popularized by Johnny Long (2001): clever search-operator combinations to uncover exposed files, vulnerabilities, and misconfigurations. The process is iterative — broad search, then narrow with operators. Operators demonstrated:

site:megacorp1.com                      # rough map of the org's web presence
site:megacorp1.com filetype:txt         # txt files on the domain → exposed robots.txt
site:megacorp1.com -filetype:html       # exclude HTML → directory indices, non-HTML pages
intitle:"index of" "parent directory"   # directory listings without index pages

The robots.txt hit is the canonical example: it instructs crawlers what to allow/disallow, and here it disclosed a PHP page otherwise hidden from search. Most operators work across multiple engines; the Google Hacking Database (GHDB) is the operator playbook.

3. Netcraft (passive) — IG_02_03

Netcraft's web portal performs information-gathering functions: which technologies run on a given site, and which other hosts share the same IP netblock. Using its DNS search for megacorp1.com, each server has a site report (registration info, then site technology entries and history). The subdomain + technology list produced here is the direct input for the active enumeration and exploitation phases. Passive because we never interact with the target directly.

4. Open-source code (passive) — IG_02_04

Public repos reveal languages, frameworks — and occasionally committed credentials. GitHub search supports many of the Google operators from technique 2; an account is needed to search across all public repos (per-user/org search works without). Example query: filename:users against Megacorp One's repos → one hit, xampp.users. XAMPP is a web application development environment, and the file contained a username plus a password hash — directly useful in the active attack phase.

5. Shodan (passive) — IG_02_05

Google indexes web content; Shodan indexes internet-connected devices (servers, routers, IoT) by interacting with them and recording banners. Searching hostname:megacorp1.com lists IPs, services, and banner data passively. Workflow shown:

  • Filter by port (e.g. click 22/SSH under Top Ports) → exact OpenSSH version per server.
  • Click an IP → host summary: ports, services, technologies, and published CVEs for what's running.

This snapshot decides where active testing starts.

6. Security headers & SSL/TLS posture (passive-adjacent) — IG_02_06

Specialty scanning sites blur the passive/active line, but a third party initiates the scan, which is what matters for our footprint:

  • securityheaders.com — grades HTTP response headers. Missing defensive headers are not vulnerabilities per se, but they fingerprint developers/admins unfamiliar with hardening.
  • Qualys SSL Labs SSL Server Test — grades TLS configuration against current best practice and identifies known vulns (POODLE, Heartbleed). The lab target scored better here, but still negotiated TLS 1.0/1.1 with insecure cipher suites → the org is not applying current TLS hardening.

Either way the payoff is the same: an inference about the organization's security culture before touching it.

7. DNS enumeration (active) — IG_03_01

DNS is the first active stop — a distributed, hierarchical database that is lucrative because of how much it holds. Linux host:

host megacorp1.com                       # default A record
host -t mx megacorp1.com                 # 4 mail servers, lowest priority number tried first
host -t txt megacorp1.com                # 2 TXT entries
host www.megacorp1.com                   # valid hostname → resolves
host idontexist.megacorp1.com            # invalid hostname → different output

The valid/invalid output difference is the primitive for brute-forcing. Bash one-liner forward brute force with a wordlist of common hostnames:

for name in $(cat names.txt); do host "${name}.megacorp1.com"; done | grep -v "not found"

Simplified list → found www, mail, router; missed ftp, owa, proxy. With the exception of www, hits were scattered IPs in a nearby range — so switch to reverse lookups across that range (works when the admin configured PTR records):

for ip in $(seq 200 254); do host <base-ip-prefix>.$ip; done | grep -v "not found"

(Audio does not state the subnet verbatim; the shape is: loop a numeric range, filter out the NXDOMAIN string.) Scans like this are cyclical — extend from every new result (mail2, router, …).

Automation on Kali:

dnsrecon -d megacorp1.com -t std                  # standard scan of main record types
dnsrecon -d megacorp1.com -D names.txt -t brt     # brute force with a subdomain wordlist
dnsenum megacorp1.com                             # second tool, domain-only invocation

dnsenum discovered several previously unknown hosts → everything learned must be re-run (passive + active) against the new subset.

Windows equivalent — nslookup:

nslookup mail.megacorp2.com                        # A record via the default DNS server
nslookup -type=TXT info.megacorp2.com <dns-server> # TXT records for a specific host

Equally versatile to host, and scriptable via PowerShell/batch.

8. Port scanning with Nmap (active) — IG_03_03

Traffic budgeting first — measure what a scan costs before running it blind. Insert counting rules on the scanner, zero counters, scan, then read:

sudo iptables -I INPUT 1 -s <kali-ip> -d <target-ip> -j ACCEPT
sudo iptables -I OUTPUT 1 -s <kali-ip> -d <target-ip> -j ACCEPT
sudo iptables -Z                              # zero packet/byte counters
nmap <target-ip>                              # default: 1000 most popular TCP ports
sudo iptables -vnL                            # read counters

Results from the lab: default 1000-port scan ≈ 63 KB of traffic; explicit all-ports scan (-p-) ≈ 4 MB and found ports the default scan missed. Extrapolation: a full scan of a class C network ≈ 1 GB+ to the wire. Ideal is a full TCP+UDP scan of every host; reality is balancing traffic constraints (slow uplink, restrictions) against coverage — especially on larger networks.

Scan types:

  • SYN scan (default, "stealth"): send SYNs, never finish the handshake — target returns SYN/ACK for open ports and Nmap doesn't send the final ACK. Because no connection is ever established, nothing reaches the application layer → no app logs; also faster (fewer packets).
  • TCP connect scan (-sT): full three-way handshake via the Berkeley sockets API; default when raw sockets are unavailable (no root), needed for some proxy setups, and much slower. It is what surfaced the Windows-only services on the lab DC — already enough to infer the host's OS and role (domain controller).
  • UDP scan (-sU, sudo): for most ports, empty packet + ICMP port-unreachable method; for well-known ports (e.g. SNMP on 161) sends a protocol-specific payload to get an app-layer answer. Combining -sU with a TCP SYN scan disclosed additional UDP services.

Network sweeping — broad first, specific later:

nmap -sn <cidr>                       # host discovery: ICMP echo + SYN to 443 + ACK to 80 + ICMP timestamp
nmap -sn <cidr> -oG sweep.gnmap       # greppable output for live-host extraction
nmap -sT --top-ports 20 -A <targets>  # short-list sweep; -A = OS/version detection, scripts, traceroute

--top-ports ranks come from the nmap-services file (service, port/protocol, open-frequency from internet-wide research scans). Follow up with exhaustive scans only on service-rich hosts.

Fingerprinting:

  • OS detection (-O): matches TCP/IP-stack implementation quirks against a fingerprint list; only printed when highly confident, so add --osscan-guess to force best-effort output (lab result: Windows).
  • Version/banner detection (-sV) and enumeration scripts (-sC/-A) — mindful that banners inflate traffic and slow the scan.

NSE: user-created scripts automating DNS enumeration, brute force, vuln identification, etc. Example http-headers (connects to the HTTP service and dumps supported headers). Inspect any script with --script-help <name> (description + URL with args/usage; also readable in the script file itself when offline).

Windows, no tools, no internet — living off the land with PowerShell:

Test-NetConnection <dc-ip> -Port 445        # TcpTestSucceeded : True → SMB open

# first 1024 ports in one line
1..1024 | % { if (Test-NetConnection <dc-ip> -Port $_ -WarningAction SilentlyContinue).TcpTestSucceeded { Write-Host "open: $_" } }

(ASR garbles the exact one-liner; the shape is a foreach over ports 1–1024 running Test-NetConnection -Port and logging successes.) This is a starting point — extendable toward full Nmap parity.

9. SMB enumeration (active) — IG_03_04

SMB's long vulnerability history (null sessions on Win2000/XP onward) makes it a standing target. Distinction the course draws: NetBIOS (TCP 139 + UDP ports) ≠ SMB (TCP 445) — NetBIOS is an independent session-layer protocol; modern SMB works without it, but NetBIOS-over-TCP persists for backward compatibility and the two are usually enabled together, so they are enumerated together.

nmap -p 139,445 <targets> -oN smb-scan.txt     # hosts with both ports open
nbtscan -r <target-ip>                          # NetBIOS names via UDP/137
nmap --script smb-os-discovery -p445 <dc-ip>    # OS, domain, AD details

nbtscan (-r forces originating UDP port 137) returned two NetBIOS names for two hosts — names are typically descriptive of host role, feeding the next enumeration cycle. The smb-os-discovery NSE script reported the lab client as Windows 10 when it actually runs Windows 11 (accuracy caveat vs -O), but NSE-based SMB enumeration adds what plain fingerprinting can't: domain and Active Directory details, with low traffic that blends into normal enterprise noise.

Windows side — net view:

net view \\DC01        # shares on the host
net view \\DC01 /all   # include administrative (trailing-$) shares

Lists domains, resources, and computers; /all exposes the hidden admin shares.

10. SMTP enumeration (active) — IG_03_05

Vulnerable/open mail servers leak user existence. Two abuse-prone commands: VRFY (verify an email address exists) and EXPN (expand a mailing list membership). Success and error responses differ, so the server confirms valid usernames — automate with a Python socket script:

#!/usr/bin/env python3
# smtp_vrfy.py — usage: python3 smtp_vrfy.py <username> <target-ip>
import socket, sys
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect((sys.argv[2], 25))
print(s.recv(1024).decode())
s.sendall(f"VRFY {sys.argv[1]}\r\n".encode())
print(s.recv(1024).decode())
s.close()

(ASR describes the script's behavior — open TCP socket, connect, issue VRFY, take username as arg 1 and IP as arg 2 — rather than dictating it line by line; the listing above is the standard reconstruction.) Feed it a username wordlist to enumerate valid mail users.

Windows fallback: Test-NetConnection proves the port is open but can't speak SMTP; install the Microsoft Telnet client (requires administrative privileges — an obstacle when running as low-priv) and interact with the server directly, same as from Kali. Another instance of enumerating from a compromised Windows host when Kali isn't available.

11. SNMP enumeration (active) — IG_03_06

Why SNMP is a favorite: UDP-based (stateless → IP spoofing/replay), versions 1/2/2c have no encryption (credentials interceptable on the local network), weak authentication, and default public/private community strings — on the protocol whose job is managing the network.

The MIB is a tree: branches = organizations/functions, leaves = variable values queryable by an external user. Microsoft Windows exposes SNMP parameters well beyond network management (users, processes, software, listening ports — see below).

Discovery and brute force:

nmap -sU -p161 --open <targets>                  # find open SNMP
# onesixtyone: build community-strings.txt + hosts.txt, then:
onesixtyone -c community-strings.txt -i hosts.txt

(ASR renders the tool name only as "a tool such as 161" — this is onesixtyone, which brute-forces community strings against an IP list.) Querying with snmpwalk once a read-only community string is known:

snmpwalk -c public -v2c <target-ip>              # walk the entire MIB tree
snmpwalk -c public -v2c <target-ip> <OID>        # walk a specific branch

The full-tree walk uses -c (community), -v (version), and an option raising the timeout to 10 s. One immediate use of the output: email addresses → social-engineering targets. Note the video says the community string on the lab machine is the default public — that is a configuration fact, not a credential value, so it is quoted as-is.

Against the Windows target DC01, the course walks four specific subtrees (the video names their function, not the OIDs; the OIDs below are the standard Windows MIB values for those functions — treat the mapping, not the audio, as the source):

Data Standard Windows MIB OID
Local user account names 1.3.6.1.4.1.77.1.2.25
Running processes 1.3.6.1.2.1.25.4.2.1.2
Installed software 1.3.6.1.2.1.25.6.3.1.2
TCP listening ports 1.3.6.1.2.1.6.13.1.3

Payoff of each: usernames feed password guessing; the process list reveals vulnerable applications and which antivirus is running; installed software cross-checked against processes pins exact versions; listening-port output discloses locally-bound-only services never visible to network scans.

Detection & defense

This block is offensive methodology, but each technique carries its own defensive optics:

  • Whois/GHDB/Netcraft/GitHub/Shodan are passive — nothing to alert on at the target. Defense is shrinkage, not detection: private registration, minimal robots.txt disclosures, no secrets in public repos (secret scanning, pre-commit hooks), and knowing Shodan already indexed your banner inventory (banners leak versions).
  • Third-party scanners (securityheaders.com, SSL Labs) prove headers/TLS posture is public knowledge. Fix what they grade: send the standard defensive headers; disable TLS 1.0/1.1 and legacy cipher suites.
  • DNS brute force and PTR sweeps generate a burst of NXDOMAIN queries from one source — visible to DNS server logging / passive DNS monitoring; per-zone zone transfers (AXFR) should be restricted (the course's tools would have used one if offered).
  • Nmap: SYN scans never complete a handshake, so application logs stay clean — detection belongs on the wire (IDS signatures for SYN-scan patterns) and in firewall counters, exactly the iptables -vnL instrumentation the course uses to self-measure. Hosts that answered the -sn sweep (ICMP echo, SYN→443, ACK→80, ICMP timestamp) each independently reveal the probing. sweeping with --top-ports+-A is loud: version probes and script execution hit every open port.
  • SMB: NetBIOS name lookups (UDP 137) and smb-os-discovery are low-traffic and blend into enterprise noise — the course explicitly notes they "will likely go unnoticed." Restrict NetBIOS where possible; SMB enumeration via null sessions should be blocked by not permitting anonymous SMB access; admin shares (/all) should not be listable by ordinary users.
  • SMTP: VRFY/EXPN user enumeration is defeated by disabling VRFY/EXPN on internet-facing mail servers — the entire technique only works when the server voluntarily answers.
  • SNMP is the block's worst offender: use SNMPv3 (authentication + encryption), replace public/private community strings, and ACL SNMP to management hosts. Everything enumerated here — users, processes, installed software, local-only listening ports — was served to an unauthenticated reader.
  • Windows LOOLB enumeration (Test-NetConnection loops) appears as legitimate native PowerShell; blocking it means watching connection patterns (fast sequential connects across ports), not executables.
  • Cross-cutting, in the course's own terms: enumeration is cyclic, so defenders should assume every previously-enumerated artifact (hostname, username, software version, email address) will be re-attacked against new hosts — inventory hygiene (what does DNS, Shodan, and the MIB say about us?) is the defensive counterpart of the loop.
