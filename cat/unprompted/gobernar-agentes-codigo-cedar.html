Gobernar el bucle del agente: hooks y políticas Cedar para agentes de código

Fuente: «Matt Maisel - Hooking Coding Agents with the Cedar Policy Language | [un]prompted 2026» · ver el video original

Resumen

Los agentes de código ya no sugieren: ejecutan. Escriben archivos, corren comandos de shell, ejecutan código y orquestan sub-agentes en bucles continuos de planificación y acción. Ese poder necesita una frontera dura. La propuesta presentada es un harness de políticas que intercepta cada evento del bucle del agente mediante hooks y lo autoriza con Cedar, el lenguaje de políticas de AWS, convirtiendo decisiones que hoy dependen del criterio del modelo en decisiones formales, analizables y verificables.

El bucle del agente como modelo de eventos

Todo scaffold de agente de código repite el mismo patrón: planificar, generar código, ejecutar herramientas. Ese espacio de acciones se puede mapear a un modelo de trayectoria con cuatro tipos de eventos:

  • Actions: lo que el agente inicia — escribir o modificar archivos, ejecutar comandos de shell, ejecutar código. Mutan el entorno.
  • Observations: lo que el entorno devuelve al agente como feedback para la siguiente inferencia del modelo.
  • Control events: prompts de usuario, peticiones de permisos, orquestación de sub-agentes.
  • State events: mecánica interna — compactación de memoria, pruning, snapshots del entorno.

Sobre este modelo encaja el threat model canónico del "lethal trifecta": input no confiable (skills descargadas por web fetch o provenientes de un marketplace, que llegan como observaciones con posibles inyecciones), datos sensibles ya presentes en el contexto del agente (código fuente, documentación interna, contenido recuperado de la memoria) y cambios de estado que permiten la exfiltración (comandos de shell o ejecución de código). Pero el modelo de trayectoria cubre más que exfiltración: ataques multi-paso que combinan observaciones, acciones y eventos de control a lo largo de varios turnos, y otros marcos de riesgo como el top 10 de OWASP para aplicaciones agénticas.

Reference monitor y puntos de aplicación

La pieza central es un reference monitor situado fuera del agente y del modelo, que medie cada evento. Las propiedades que debe cumplir son las clásicas: invocación garantizada en cada evento, resistencia a manipulación y verificabilidad. Es la frontera dura entre el agente y el entorno.

Un reference monitor solo vale por sus puntos de aplicación, y ahí entran los hooks de los agentes de código: puntos del ciclo de vida del bucle donde se puede interceptar el evento, procesarlo y decidir permitir, modificar o detener la ejecución. Cada implementación tiene sus particularidades:

  • Gemini CLI: hooks before/after del modelo, que permiten procesar tokens individuales en streaming.
  • Claude Code: no tiene hooks de modelo; solo el evento de notificación con la respuesta final del agente.
  • Cursor: hooks granulares para MCP, comandos de shell y llamadas genéricas a herramientas.

Cedar: políticas formales, no listas de permisos

Cedar es un lenguaje de políticas expresivo, rápido y analizable gracias a sus propiedades formales y a su compilador simbólico verificado en LEAN. A diferencia de otros lenguajes como Rego, Cedar permite análisis formal para detectar políticas contradictorias, vacuas o sombreadas — conjuntos de reglas que nunca aplican y dan falsa seguridad. Su soporte nativo de control de acceso basado en atributos (ABAC) encaja con el dominio: el esquema define entidades como agente, usuario y trayectoria, y las políticas se escriben sobre sus atributos.

Esos atributos no tienen por qué ser estáticos: etiquetas de firma, clasificación de sensibilidad de datos y valores computados por modelos de seguridad (un clasificador tipo GPT Safeguards de 20B parámetros, o un sistema DLP corporativo) alimentan las políticas en tiempo de ejecución. La clasificación se aplica a los eventos mismos, con el dato que contengan o recuperen.

Las políticas no son solo de seguridad. Un ejemplo real: Claude Code permite escribir archivos estando en modo plan, algo que viola la expectativa del usuario. Una política puede detectar permission_mode = plan combinado con una acción de escritura y bloquearla.

Privilegios mínimos dinámicos y flujo de información

El trabajo implementa etiquetado de flujo de información (information flow control): los eventos se taintan con etiquetas de sensibilidad, y una política puede permitir un comando solo si la trayectoria no está contaminada. Esto complementa los sistemas de permisos existentes — por ejemplo, los wildcards de bash de Claude Code siguen funcionando, pero Cedar añade contexto que ellos no tienen.

Un almacén de trayectorias hace bookkeeping de las entidades observadas a lo largo de la conversación, exponiéndolas como atributos dinámicos. Lenguajes con más soporte temporal (linear logic y similares) son la línea futura para razonar sobre trayectorias completas.

Preguntas frecuentes del dominio: la identidad no está cubierta en esta implementación pero cualquier IdP se integra vía Cedar (su uso tradicional); las políticas pueden vivir en los archivos de configuración del equipo (CLAUDE.md, cursor rules) o en los documentos de prácticas de ingeniería, decidiendo cada equipo su balance entre utilidad y acceso — el eterno mínimo privilegio aplicado a agentes. El motor de políticas Cedar está liberado como open source con bindings para LangChain, Strands y ADK, así que funciona también dentro de agentes de primer partido. Para arquitecturas multi-agente, los control events son la frontera natural donde aplicar políticas de integridad contextual (un agente que conoce un secreto no debería poder filtrarlo a otros agentes del entorno), aunque ese trabajo está pendiente.

Técnicas y herramientas mencionadas

  • Modelo de trayectoria: cuatro tipos de eventos (actions, observations, control, state) que abstraen cualquier scaffold de agente.
  • Lethal trifecta: input no confiable + datos sensibles en contexto + capacidad de exfiltración.
  • Reference monitor: mediación completa, a prueba de manipulación y verificable, fuera del agente y del modelo.
  • Hooks de agentes de código: puntos de aplicación por ciclo de vida (Gemini CLI, Claude Code, Cursor).
  • Cedar: lenguaje de políticas con compilador simbólico en LEAN; detección de políticas contradictorias, vacuas o sombreadas; ABAC.
  • Rego: lenguaje de referencia para contrastar las propiedades formales de Cedar.
  • Information flow control / taint tracking: etiquetas de sensibilidad sobre eventos y trayectorias.
  • GPT Safeguards / DLP: clasificadores que computan atributos de sensibilidad para las políticas.
  • Cedar policy engine open source: bindings para LangChain, Strands y ADK.

Conclusiones

  • El bucle del agente se puede formalizar como un modelo de cuatro tipos de eventos, y esa abstracción hace posible aplicar política sobre él de forma uniforme.
  • Los hooks son los puntos de aplicación naturales de un reference monitor, pero su granularidad varía mucho entre agentes: sin hooks de modelo, como en Claude Code, la cobertura es parcial.
  • Cedar aporta lo que las listas de permisos no tienen: análisis formal, atributos dinámicos y decisiones contextuales (permitir solo si la trayectoria no está taintada).
  • La seguridad del agente no es solo bloquear: también corregir comportamientos legítimos pero inesperados, como escribir archivos en modo plan.
