Resumen

Brooks, ingeniero de seguridad de infraestructura y nube en Dropbox, no presenta el trabajo de su empresa sino su laboratorio personal: un enjambre de 19 agentes —13 interactivos y varios agentes-servicio tipo cron que llaman a Claude Code o a otros agentes— corriendo a diario sobre un servidor MCP local stdio con 73 tools (email, creación de archivos, lectura del file system, herramientas del SO). Todo el código está en GitHub como referencia —open source para mirar, no para descargar y ejecutar; él sí lo corre todos los días—. Los números están actualizados a la noche anterior y ya volvieron a quedar viejos.

Cada agente arranca por CLI, por web UI con wrapper de voz, por app standalone o por Slack personal con un filtro que enruta cada mensaje al agente correcto. Sobre ese bus conviven MCPs remotos (los personales y GitHub), y los controles de seguridad atraviesan todo: capabilities acotadas, scopes por tool (read/write/admin), memoria aislada, observabilidad y un tope de iteraciones por turno —optimizado a unas 3 o 4, también para no fundir la tarjeta de crédito—.

El ecosistema que se mantiene solo

El flujo estrella es una task management propio: un cron job con claude -p que revisa tareas, las corrige u optimiza y emite reportes. Cuando se queda sin tareas, despierta a sub-agentes de code review —auditoría de seguridad, cobertura de tests, calidad de código, documentación— que generan tareas nuevas: un ecosistema auto-sostenido de optimización que corre hasta que se agota el crédito y Anthropic corta. El humano en el loop cada vez participa menos —lo cual, reconoce, da miedo—. Los contrapesos: revisión semanal de PRs y dos agentes revisores de Claude que deben aprobar cada PR antes de cerrar los tasks automatizados, como check de que el LLM no está entregando basura.

Security by default, demostrada en vivo

El sistema de capabilities tiene dos capas por agente: qué tools puede usar y con qué permisos. Ejemplos: el task manager (el daily driver) puede buscar, escribir por Slack, enviar email y usar memoria; el security researcher es read-only sobre un RAG de blogs; y existe un chatbot con todo habilitado —que es a la vez el conejillo de indias—. Al agregar tools al MCP server en expansión perpetua, la regla es denegar por defecto: sin configuración explícita, todo queda locked down a admin. En la demo, un agente sin permiso de escritura intenta guardar una memoria, recibe un error verboso, y entiende solo qué le falta y qué pedir. Con permisos, la memoria funciona y muestra el key-value crudo que después se limpia.

El MCP relay: depurar LLMs conversando entre sí (o un implant, según se mire)

Para dejar de copiar y pegar entre Claude Code del servidor y del cliente, Brooks construyó un MCP relay: una sala de chat para sus LLMs, donde el agente del servidor comparte el código fuente y los dos conversan hasta depurar el cliente aunque el código del servidor no sea accesible para él. También sirve para equipos sin Claude Code instalado: un agente remoto corre en contenedores LXC de Proxmox con medio giga de RAM, se autentica por OAuth —el mecanismo estándar de todos sus agentes— y espera comandos en la sala. Herramienta de debugging para él; implant para cualquier otro lector. Él mismo lo advierte: inyección de contexto de un LLM a otro sin scoping de capabilities, todo en memoria —no está listo para producción, no lo usen—; en la hoja de ruta, Redis de backend y transferencia de capabilities del agente a permisos reales de Linux sobre usuarios restringidos.

Memoria: el bug de los mil dólares al mes

La v1 de memoria era una tabla Postgres compartida: funcionaba, hasta que cruzaron las identidades. Brooks le pidió a un business agent —lanzándole la meta "optimizá para llegar a mil dólares al mes"— y desde entonces cada desglose de tareas del task manager mencionaba la meta de los mil dólares. La solución: identidad por agente (cada agente es una subclase de su framework; el nombre de la clase se traduce, al levantar el MCP server local, en un namespace de memoria que el LLM no puede elegir ni suplantar) más inyección selectiva: solo las memorias con importancia alta se inyectan solas, el resto se busca por función. Menos contexto quemado, agentes menos distraídos.

Firewall de LLM: cuando la seguridad bloquea tus propias tareas

Un firewall de prompts con detección de prompt injections cierra el circuito —y demostró su filo doble en vivo: bloqueó la consulta del security agent buscando memorias ajenas, que era justamente la demo. Pero el hallazgo más incómodo llegó dos semanas después revisando logs: una tarea que Brooks mismo había creado ("agregar el campo de hora del servidor a cada respuesta de la API") llevaba semanas bloqueada junto a otras dos docenas por la configuración de fábrica del firewall, demasiado agresiva. Lección: la seguridad de fábrica sin tuning mata funcionalidad silenciosamente; hay que definir tolerancia al riesgo por setting, y las queries de research de seguridad requieren baja sensibilidad o ninguna.

Recortar contexto sin perder las señales de ataque

Para análisis de logs a largo plazo planteó otro problema sutil: si el contexto se llena y se recorta, un atacante puede lanzar un evento malicioso cada 200.000 tokens y solo se ve uno por ventana. Su solución: tagging consciente del trimmer —los eventos de seguridad (SSRF bloqueado, permission denied) se marcan como importantes y sobreviven al recorte, quedando disponibles para el análisis posterior. No es perfecto: con más logs y sesiones más largas el contexto igual se llena, y calibrarlo es trabajo continuo.

Observabilidad: la que paga las facturas

Activar cost tracking reveló despilfarro inmediato: memorias completas inyectadas en cada llamada (que además empeoraban la función) y coding agents que despertaban los cinco review agents constantemente —cada ronda vale unos 250k tokens—. Hoy corre LangFuse para trazas por agente, detectó usos accidentales de Opus donde iba Sonnet, y mantiene dashboards de costo con desglose diario y audit trail de seguridad: si a la mañana hay un cargo extra de cien dólares, se puede trazar de qué agente y qué llamada vino.

Lecciones

  • Seguridad bien hecha también mejora la funcionalidad: scoping de 73 tools por agente ahorra contexto y mantiene a cada agente enfocado en su misión, igual que con un humano.
  • Cost tracking desde el día uno, no después del primer susto.
  • Arquitectura en madurez: hoy agentes en el desktop personal y MCPs externos en un web server; la migración en curso es a un clúster K3s con contenedores, service mesh y controles de red por delante.
  • Deuda declarada: delegation chains e identidad transversal —con la promesa de robar ideas a la sesión de SANS de más tarde—.

Técnicas y herramientas mencionadas

  • MCP server local stdio con 73 tools y restricciones por llamada (directorios y tipos de archivo permitidos), tipo sidecar por agente.
  • Capabilities bounding: allowlists por agente, scopes read/write/admin, denegación por defecto a admin.
  • Memoria con namespaces derivados de identidad (nombre de clase → namespace), inyección selectiva por importancia y búsqueda on-demand.
  • MCP relay: sala de chat LLM-a-LLM para debugging cliente-servidor; agente remoto con OAuth en LXC de 512 MB de RAM.
  • Firewall de LLM con detección de prompt injection (requiere tuning agresivo) y tagging de eventos de seguridad que sobreviven al context trimming.
  • LangFuse para trazas, cost tracking con dashboards y audit trail; cron jobs con claude -p; migración a K3s con service mesh.
  • Alternativa mencionada por la audiencia para boundaries fuera de la ventana de contexto: Envoy + OPA.

Conclusiones

  • Un enjambre personal es el banco de pruebas perfecto: los errores —memorias que se contagian, firewalls que bloquean tus propias tareas— enseñan más rápido que cualquier postura teórica.
  • Identidad y namespace no negociables: si el LLM puede elegir su identidad, el aislamiento es decorativo.
  • Todo control de seguridad tiene un costo funcional oculto; los logs del firewall son el único lugar donde se descubre a tiempo.
  • La observabilidad no es lujo: es lo que explica por qué la factura se multiplicó y qué agente lo hizo.
