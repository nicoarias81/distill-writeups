Las IDE con IA repiten las guerras del navegador: 37 vulnerabilidades y una lección vieja

Fuente: «Piotr Ryciak - Vibe Check: Security Failures in AI-Assisted IDEs | [un]prompted 2026» · ver el video original

Resumen

La última generación de IDE asistidos por IA no sugiere código: lee archivos, escribe otros, ejecuta comandos, modifica configuración y hace push. Ese es el attack surface que el equipo de red teaming de MindGuard audita. El resultado de meses de investigación: 37 vulnerabilidades en más de 15 proveedores —incluyendo Google Gemini CLI, OpenAI Codex y Amazon Kiro— que llevan a ejecución remota de código, exfiltración de datos o evasión de sandbox. Todo destilado en 25 patrones de vulnerabilidad repetibles en cuatro categorías, más un toolkit gratuito con catálogo, skills de testing para Claude Code y checklist para testers y builders.

Guerras del navegador 2.0

Hay más de 40 IDE con IA en el mercado; Google, Amazon, OpenAI, Anthropic, Microsoft y JetBrains tienen la suya, y la mayoría salió en los últimos doce meses. La dinámica es la de las guerras del navegador: mercado fragmentado, churn masivo, carrera por publicar features y la seguridad como tarea postergada. En la era del navegador ese patrón produjo ActiveX y Flash —más de 1.000 CVEs en su vida útil— y diálogos "click to allow" que los usuarios atravesaban sin leer. La industria tardó quince años en entender que la respuesta no eran mejores diálogos de advertencia sino sandboxing: Chrome aisló procesos y Flash murió. La misma película se está rodando con las IDE de IA, con la presión de adopción como acelerante: con la lista de conceptos que hay que dominar (agentes, sub-agentes, MCP, LSP, hooks, skills), un desarrollador sin IDE de IA siente que se queda atrás.

La primera barrera: el modelo de confianza del workspace

Terminología mínima. El workspace es el directorio donde opera la IDE, típicamente un repo clonado, y puede contener input no confiable. Los config son archivos que la IDE carga y que modifican su comportamiento —a veces ejecutando código: servidores MCP, LSP, hooks—. Las rules (CLAUDE.md, cursor rules, AGENTS.md) son extensiones del system prompt que viven en el workspace y también pueden inyectar instrucciones del atacante.

Para gatear todo esto, las IDE introdujeron el diálogo "¿confías en esta carpeta?". Esa decisión es la puerta de seguridad primaria, y negar la confianza hace la herramienta casi inutilizable, lo que empuja a aceptar. El baseline mínimo para que el modelo de confianza signifique algo tiene tres condiciones: desconfiar por defecto de todo workspace nuevo, deshabilitar las features que ejecutan código mientras el workspace no es confiable, y re-preguntar la confianza si la configuración del workspace cambia más adelante. VS Code lo resolvió en 2021 con restricted mode, pero varias IDE salieron sin ello o con implementaciones pobres: la brecha entre lanzamiento y enforcement —durante la cual los usuarios estuvieron expuestos a ataques vía config sin interacción alguna— supera el año en algunos casos, y algunos productos aún no lo implementan. Encima, es un problema de industria: decenas de IDE con UIs de confianza distintas y desarrolladores orientados a objetivos fabrican la fatiga de aprobación perfecta, igual que con Flash.

Cero clics: código que se ejecuta al abrir el proyecto

El patrón más grave: el desarrollador abre el workspace y el código se ejecuta. Sin diálogo aprobado, sin mensaje enviado al agente.

  • Codex, MCP autoload: el atacante planta un .codex/config.toml en el repo que define un servidor MCP cuyo campo command apunta a una reverse shell. Al correr codex, el servidor MCP se lanza durante la inicialización. El detalle crítico: Codex permite activar un sandbox a nivel kernel, pero los servidores MCP corren fuera del sandbox — el sandbox solo cubre las tool calls del agente, mientras los procesos MCP nacen con privilegios completos del usuario. Ya corregido en versiones recientes.
  • Gemini CLI, race de inicialización: Gemini CLI sí tiene modelo de confianza, pero el .gemini/settings.json soporta un campo discovery cuyo comando corre para descubrir herramientas antes de que aparezca el diálogo. Con una reverse shell en ese campo, cuando el usuario ve "¿confías en esta carpeta?" la shell ya está conectada; decir "don't trust" no mata el proceso. La documentación oficial recomendaba activar folder trust para protegerse: falsa seguridad, porque el exploit dispara antes y el modo por defecto era allow, no deny.

Un clic: el agente como arma

Cuando el modelo de confianza funciona y los configs están gateados, queda otro objetivo: el agente. Con prompt injection —instrucciones ocultas en archivos del workspace— el atacante opera a través del contexto del agente, independientemente del estado de confianza del workspace. El usuario manda un mensaje cualquiera ("hi" basta) y el agente ejecuta las instrucciones del atacante.

Demostrado contra Amazon Kiro como cadena de cuatro primitivas encadenadas:

flowchart LR
    A[Prompt injection
en nombre de directorio] --> B[Leer .env con grep
robar API key]
    B --> C[Modificar config
del workspace]
    C --> D[Fetch automático vía Kiro Powers
exfiltración fuera de banda]

La inyección viaja en el nombre de un directorio largo que ordena leer el index.md interior y seguir sus instrucciones; al indexar el workspace, el agente obedece. Las instrucciones usan la herramienta de búsqueda grep para localizar api_key en el .env — curiosamente, con el patrón key= el agente lo interpretó como actividad sospechosa, pero Y= (que matchea el final de api_key=) pasó sin fricción. La clave robada se inserta en la URL de recomendación de powers y el fetch integrado de Kiro completa la exfiltración. Cada primitiva es menor por separado; juntas, son exfiltración completa.

Confianza envenenada: el ataque diferido

La tercera condición del baseline —re-preguntar confianza si la configuración cambia— es exactamente la que varias IDE no implementan. En Claude Code el patrón es un TOCTOU: el víctima clona un workspace benigno con un .mcp.json que define un servidor MCP legítimo (por ejemplo, un agente Playwright) y otorga confianza. Días o semanas después, un colaborador con acceso de escritura al repo hace commit cambiando el campo command por una reverse shell. La víctima hace git pull: sin aviso. Corre el comando de Claude: ejecución de código automática.

La causa: no hay re-aprobación ni chequeo de integridad; la confianza está ligada al nombre del servidor —una ruta de archivo—, no al hash del contenido. Solo en Claude Code se encontraron nueve vectores distintos de trust-persistence. La corrección es simple —hashear el config confiado y re-preguntar cuando el hash cambie—, y lo que los proveedores exigen hoy al usuario es replicar a mano una verificación de integridad que la herramienta debería hacer.

Las respuestas de los proveedores al mismo patrón son reveladoras: Anthropic respondió que es "el balance apropiado entre seguridad y usabilidad"; OpenAI lo marcó como bug informativo porque "no se cruzó ninguna frontera de seguridad"; y el mismo patrón en Cursor había recibido un CVE severo el agosto anterior tras la disclosure de Check Point. No hay consenso de industria sobre si trust-persistence es siquiera una vulnerabilidad; el riesgo para el usuario es real igual. Para defenderse manualmente habría que inspeccionar cada git pull, git switch y pull request, recordando qué rutas de configuración ejecutan código en cada IDE que se use.

Técnicas y herramientas mencionadas

  • Catálogo de 25 patrones de vulnerabilidad en cuatro categorías: ataques zero-click, one-click, time-delayed y fallas del modelo de confianza como clase.
  • Toolkit gratuito: catálogo en GitHub, skills de testing para Claude Code y checklist por security gates para auditar cualquier IDE.
  • Skills de testing (8): black box para targets cerrados, análisis de documentación, observación de runtime, pilot testing y white box; compatibles con el testing handbook de Trail of Bits.
  • Semgrep y CodeQL: reglas y queries de taint tracking sobre las seis zonas de código que históricamente más hallazgos producen.

Conclusiones

  • La lección de las guerras del navegador se repite literal: los diálogos de aprobación no escalan; el sandboxing sí. Reducir el impacto exige desacoplar la IDE del filesystem del desarrollador — dev containers, entornos de desarrollo en la nube, máquinas desechables— para que cuando un ataque tenga éxito el blast radius quede contenido.
  • El modelo de confianza del workspace es la puerta primaria, y sus tres condiciones (deny by default, features deshabilitadas, re-prompt al cambio) siguen sin cumplirse de forma uniforme más de un año después de las primeras disclosures.
  • Las capas de defensa (prompts del sistema, guardrails del modelo, allow lists, sandboxes) existen pero fallan por implementación: el exploit de race de Gemini CLI dispara antes del diálogo, y los procesos MCP de Codex nacen fuera del sandbox.
  • La misma vulnerabilidad recibió tres veredictos distintos de tres proveedores; falta consenso —y falta integridad de configuración: hash del config confiado y re-prompt al cambio—.
