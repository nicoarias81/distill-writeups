Hacia dos account takeover, eslabón por eslabón

Resumen

Casi desde que existe el bug bounty, hay una categoría de hallazgos que despierta una fascinación especial: el account takeover. Es la vulnerabilidad que permite tomar el control de la cuenta de otro usuario, y suele ser el premio mayor de cualquier programa de recompensas. Pero llegar a un ATO completo rara vez es un camino directo: casi nunca hay un botón mágico que diga "tomar esta cuenta". En cambio, hay cadenas: pequeñas fallas que, por sí solas, parecen inocuas o insignificantes, pero que encadenadas entre sí forman un ataque con impacto real.

En este trabajo, Benjamín "bronxi" Muñoz (Response Analyst en Rappi, pentester y bug bounty hunter en su tiempo libre) cuenta dos campañas reales, cada una con su premio: dos account takeover logrados eslabón por eslabón, construyendo el ataque pieza por pieza cuando cada intento individual parecía quedarse corto. Las dos historias comparten una moraleja: el hallazgo inicial es solo el primer hilito; el valor está en ser persistente y creativo para encontrar los eslabones que faltan.

Historia 1: OAuth ID y 16 números que no fueron por fuerza bruta

Todo empieza con el single sign-on (SSO): el mecanismo por el que uno se registra o inicia sesión en una plataforma usando un proveedor de identidad externo (Google, Facebook, X/Twitter) que comparte la información que ya tiene del usuario. En una plataforma —que llamaremos vulnerable.com— había varios proveedores configurados, y bronxi se puso a revisar el flujo completo, request por request, de cada uno.

El hallazgo inicial: la última request del flujo con Facebook era un POST a un endpoint de OAuth que devolvía las cookies de sesión. El body tenía cinco parámetros:

  • El nombre del proveedor (siempre "Facebook"; cambiarlo rompía el flujo).
  • Un redirect_url que no hacía nada.
  • Un OAuth ID de 16 dígitos: lo único que se necesitaba para machea­r con la cuenta y recibir las cookies de sesión.

Lo correcto habría sido que ahí viajara el token que Facebook entrega al usuario, no un número fijo. Ese número no es el ID global de Facebook: es un ID único del usuario para esa app en particular, y se puede ver en la configuración de seguridad de Facebook (donde incluso se puede revocar la conexión).

El intento directo: fuerza bruta (y por qué no)

Bronxi consideró la fuerza bruta: iterar los 16 dígitos hasta machea­r con una cuenta que tenga inicio de sesión vía Facebook, copiar las cookies y entrar sin interacción del usuario. Pero antes de mandar el reporte, revisó la policy del programa. Detalle importante: en este programa la fuerza bruta no estaba explícitamente fuera de scope (otros ítems como los cross-site scripting sí lo estaban), pero igual decidió no presentarlo así, porque:

  • Muchos programas prohíben expresamente la fuerza bruta.
  • Los triagers suelen responder NA (not applicable) cuando el ataque no es "razonable".
  • El backend no respondía rápido: encontrar una cuenta válida entre 16 dígitos era cuestión de días.

Envió igual el reporte con la fuerza bruta como vector y una alternativa "tirada ahí" (robar el token con un XSS). Respuesta: NA. El triager le dijo que un ataque por fuerza bruta de 16 dígitos no es un ataque razonable. Y tenía razón.

El eslabón perdido: de token a user ID

Ahí vino la parte "graciosa y triste a la vez": si la plataforma hubiera estado bien configurada y usara el token para iniciar sesión, el token robado bastaría. Pero como necesitaba el user ID y el token no lo contiene, hacía falta un puente. Lo encontró en la API GraphQL de Facebook, documentada oficialmente: un GET donde se pide el campo id del usuario junto con el token, y la API responde "este token pertenece a este user ID".

Con eso, la cadena quedó completa:

sequenceDiagram
    participant A as Atacante
    participant V as Víctima
    participant F as Facebook
    A->>V: Link malicioso con payload XSS
    V->>A: Ejecuta el XSS; exfiltra el token de Facebook (localStorage)
    A->>F: GET a la API GraphQL con el token, pidiendo el campo id
    F->>A: Devuelve el user ID (16 dígitos)
    A->>A: POST OAuth con ese ID y obtiene las cookies de sesión
  • El atacante manda un link malicioso con el payload XSS.
  • La víctima lo abre; el atacante recibe el token de Facebook (robado del localStorage, clave fblst_<número>).
  • Con el token, el atacante consulta la API de Facebook y obtiene el user ID.
  • Con el user ID, hace el POST de OAuth y recibe las cookies de sesión.

El reporte y la pelea con el triage

El XSS estaba fuera de scope, así que bronxi lo presentó como un eslabón del ataque, no como la vulnerabilidad en sí: el reporte era un account takeover vía login de Facebook, y el XSS era solo el medio para robar el token. Primera respuesta: NA otra vez, con el argumento de que "es el mismo reporte de hace una semana" y una amenaza de sanción si volvía a mandar reportes duplicados. Bronxi pidió revisión, argumentando que no era el mismo ataque: la cadena era distinta. Otro triager lo reabrió, lo validó como High (porque requería interacción del usuario: abrir el link malicioso) y lo pagó.

Moraleja doble: aunque un vector (como un XSS o un open redirect) esté fuera de scope, si se le da una vuelta y se demuestra un impacto mayor (como un ATO), el reporte es válido. Y también: los triagers a veces no leen los reportes completos; conviene anticiparse y aclarar al principio qué es distinto respecto de reportes previos.

Historia 2: Borrando tokens y vinculando UIDs

La segunda plataforma (otra vulnerable.com) procesa datos y los analiza con IA, y permite invitar gente a un espacio de trabajo por correo. El objetivo: el clásico flujo de "olvidé mi contraseña".

El flujo normal es: (1) el usuario entra a "forgot password" y pone su correo, (2) recibe un link con un token para cambiar la contraseña, (3) completa el formulario y la cambia. La request final del cambio tenía tres parámetros:

  • user: un UUID versión 4 (el identificador del usuario).
  • password: la nueva contraseña.
  • token: otro UUID v4, el que venía en el link del mail.

Detalle técnico: la versión de un UUID se lee en el tercer grupo, después del segundo guion. La versión 1 es predecible (deriva del timestamp y la MAC); la versión 4 es aleatoria y no se puede adivinar.

El hallazgo: el token no se valida

Bronxi aplicó su técnica habitual de borrar o alterar parámetros uno por uno. Al borrar el token y enviar la request, la plataforma devolvió un 409 (su código habitual de "contraseña cambiada") y la contraseña se cambió igual. Es decir: el backend no estaba validando el token; bastaba el UUID del usuario.

Pero un UUID v4 no es adivinable, y sin una forma de obtenerlo, el reporte habría recibido el clásico "¿cómo obtenés vos el UUID de ese usuario?". Hacía falta el eslabón que permitiera conseguirlo.

El eslabón: invitar a la víctima al espacio de trabajo del atacante

La idea: si el atacante invita a la víctima a su espacio de trabajo, ¿la respuesta de la invitación incluye el UUID de la víctima? Probó: sí, la response devolvía el mail, el rol asignado y también el UUID. Con eso, más el POST sin token, tenía un account takeover sin interacción del usuario — o eso creía.

Al enviar la request con el UUID obtenido por invitación, la plataforma respondió "el usuario no existe". Raro: la víctima existía. La explicación: la plataforma genera un UUID cuando el usuario se registra, y otro UUID distinto cuando se lo invita a un espacio de trabajo ajeno. El POST de cambio de contraseña solo machea­ba con el UUID original, no con el de la invitación.

La pista para unir ambos mundos: si la víctima ya existe y la invitan, no puede elegir a qué espacio entrar (primera anomalía). Pero si la víctima hace un "forgot password" después de ser invitada, al iniciar sesión la plataforma le pregunta a qué espacio quiere ingresar (registrado o invitado). Algo en ese flujo de recuperación homologaba el UUID de la invitación con el original: a partir de ese momento, el UUID de la invitación pasaba a ser válido para el cambio de contraseña.

El último eslabón: forzar el forgot password

Quedaba un problema: la víctima tenía que hacer un "forgot password" por su cuenta. Sin eso, el ataque era teórico. La solución vino de una prueba previa de fuerza bruta sobre el login que había bloqueado una cuenta propia: la plataforma bloquea la cuenta tras 6 intentos fallidos de inicio de sesión, y la única forma de desbloquearla es hacer un "forgot password".

Con eso, el ataque completo quedó así:

sequenceDiagram
    participant A as Atacante
    participant V as Víctima
    participant P as Plataforma
    A->>P: Invita a la víctima a su workspace
    P->>A: Response con el UUID v4 de la víctima (versión de invitación)
    A->>P: 6 intentos de login fallidos con el mail de la víctima
    P->>V: Cuenta bloqueada
    V->>P: Forgot password (obligado por el bloqueo)
    Note over P: El forgot password homologa el UUID de invitación con el original
    A->>P: POST de cambio de contraseña con el UUID (sin token)
    P->>A: 409 - contraseña cambiada; control total de la cuenta
  1. El atacante invita a la víctima a su espacio de trabajo y obtiene su UUID de invitación.
  2. El atacante fuerza 6 intentos fallidos de login con el mail de la víctima.
  3. La cuenta queda bloqueada; la víctima, para recuperarla, debe sí o sí hacer "forgot password".
  4. Después del "forgot password", el UUID de la invitación queda homologado y el atacante usa el POST sin token para cambiar la contraseña.

Fue aceptado como High (de nuevo, por la interacción requerida de la víctima) y pagado a los 10 días del triage.

Detalle de la ventana de tiempo

En la ronda de preguntas confirmaron un punto importante: una vez que la víctima hace el "forgot password", el UUID queda homologado permanentemente; el atacante puede cambiar la contraseña todas las veces que quiera, sin límite de ventana. La única forma de revocarlo sería que la víctima sea invitada desde otro espacio de trabajo y vuelva a hacer un "forgot password" — y aun así, el atacante podría repetir la invitación.

Lecciones para cazar account takeover

  • El flujo de login es el campo de batalla: conocer cada request y response es el punto de partida. Si hay SSO con varios proveedores, hay varios flujos para probar, cada uno con sus propias aristas.
  • Conocer los errores comunes de OAuth/SSO ayuda: los laboratorios de PortSwigger sobre OAuth son un buen punto de partida, y leer write-ups de otros abre la mente para pensar variantes.
  • La interacción del usuario define la severidad: un ATO sin interacción suele ser Critical; con interacción, High. Diseñar el ataque para minimizar esa interacción es parte del trabajo.
  • Los detalles "inocuos" suman: un ID que parece inofensivo, un parámetro que se puede borrar, un mensaje de error que revela estado — cada uno es un eslabón potencial.
  • Leer la policy del programa evita NA y sanciones, pero también: un vector fuera de scope (XSS, open redirect) puede ser válido si se demuestra un impacto mayor encadenándolo.
  • La persistencia vale más que el primer hallazgo: el primer error encontrado es solo el primer hilito; el trabajo real es construir la cadena completa. Entre una y dos semanas de caza por cada uno de estos reportes,Working los fines de semana.
  • Disfrutar el tiempo de hunting: como repite bronxi, el tiempo de hunting no es tiempo perdido — es aprendizaje, práctica y, tarde o temprano, recompensa.

Técnicas y herramientas mencionadas

  • Single Sign-On / OAuth: flujos de login con proveedores externos (Google, Facebook, X); análisis request por request de cada proveedor.
  • Facebook App-scoped User ID: ID de 16 dígitos único por app, visible en la configuración de seguridad de Facebook.
  • Facebook Graph API (GraphQL): endpoint documentado que resuelve token → user ID.
  • Cross-site scripting (XSS): usado como eslabón para exfiltrar el token del localStorage (clave fblst_*) mediante un payload document.write con imagen que envía el valor a un servidor del atacante.
  • UUID v4 vs UUID v1: lectura de la versión (tercer grupo tras el segundo guion) y predictibilidad de cada una.
  • Parameter tampering: borrado sistemático de parámetros (user, password, token) para detectar validaciones ausentes.
  • Account lockout como oráculo de ataque: bloqueo tras 6 intentos fallidos usado para forzar a la víctima al flujo de recuperación.

Conclusiones

  • Un account takeover casi nunca es una sola vulnerabilidad: es una cadena de hallazgos aparentemente menores que, bien encadenados, producen un impacto crítico.
  • La fuerza bruta rara vez es el camino: los triagers la descartan como "no razonable" y muchos programas la prohíben; buscar eslabones alternativos (robos de token, fugas de IDs) rinde más.
  • Un vector fuera de scope no descarta el reporte: si el XSS o el open redirect son solo un eslabón hacia un impacto mayor, el reporte es válido — hay que saber presentarlo así.
  • Los errores de diseño (usar un user ID en lugar de un token; no validar el token del reset; homologar UUIDs tras un forgot password) son la materia prima de estas cadenas.
  • La interacción del usuario marca la frontera entre High y Critical: cada eslabón que se elimina del ataque (menos clics de la víctima) sube la severidad y el valor del reporte.
