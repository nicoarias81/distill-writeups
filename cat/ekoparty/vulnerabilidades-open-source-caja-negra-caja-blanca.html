Vulnerabilidades en proyectos open source: caja negra y caja blanca combinadas

Resumen

El código abierto es una mina para la investigación de vulnerabilidades: miles de proyectos públicos en GitHub y GitLab, algunos con programas de bug bounty que pagan por cada hallazgo, y sin firewall de por medio. La tesis del trabajo es simple y poderosa: combinar análisis de caja negra (la aplicación funcionando) con análisis de caja blanca (el código fuente), porque ninguna de las dos técnicas por sí sola alcanza. Con la app corriendo se descubre dónde duele; con el código se logra mayor cobertura, se encuentra la línea exacta del problema y se detecta si el mismo patrón vulnerable se replica en otros lugares.

El caso de estudio es un chatbot colaborativo de inteligencia artificial publicado en una plataforma de bug bounty —un software "súper verde", tan plagado de fallas que terminaron retirándolo del programa—. A través de él se recorren las herramientas del ecosistema: proxy web para interceptar tráfico, escáneres dinámicos como Nuclei, analizadores estáticos como CodeQL, Orusec, Semgrep y Gitlet, y los asistentes de IA como apoyo inicial, siempre con la misma regla: ningún resultado se reporta sin validar que sea explotable.

El punto de partida: qué buscar y por dónde

Una vulnerabilidad es una debilidad en un sistema —una app móvil, un software embebido en un auto o un smartwatch, un servicio web— que compromete la confidencialidad, la integridad o la disponibilidad de la información. Ese pilar comprometido da la pauta de la gravedad. Los ejemplos cercanos abundan: una aplicación de estacionamiento de Córdoba exponía por API los datos de todos los clientes, incluidas tarjetas de crédito (confidencialidad comprometida); Instagram y Zoom acumulan vulnerabilidades y por eso empresas como Meta mantienen programas de bounty.

El flujo de trabajo recomendado para un proyecto público:

  1. Clonar el repositorio y seguir al pie de la letra las instrucciones del maintainer para el despliegue (la sección de contribuciones suele detallar servicios previos y pasos).
  2. Levantar el proyecto localmente, típicamente en localhost con algún puerto, preferentemente bajo Linux o el subsistema de Linux en Windows.
  3. Usar el software primero como usuario normal: entender para qué fue pensado, qué se puede y qué no, dónde están los datos más críticos.
  4. Recién después, atacar: todo input de usuario es manipulable.

Caja negra: proxy, navegador y sockets

El navegador con sus herramientas de inspección es el primer instrumento: la pestaña de red y la consola muestran todo lo que viaja hacia el backend y vuelve. Un proxy web (Burp Suite, Zap Proxy, o Postman para interactuar con el backend) se interpone entre navegador y servidor: captura cada request —crear proyectos, borrarlos, obtener el estado de los usuarios— y permite modificarla antes de que llegue al destino. Validaciones que existen en el frontend se saltan interceptando el request.

Sobre el chatbot de ejemplo, el proxy reveló de inmediito que el backend no validaba nada: los mensajes con contenido malicioso se guardaban tal cual, sin sanitización en ningún punto. Donde hay un input, hay que probar cross-site scripting; donde se renderiza contenido, hay que mirar también los logs, porque los mensajes maliciosos terminaban escritos en ellos. Un cross-site scripting en los logs es mucho más que un pop-up molesto: el mensaje malicioso queda guardado, y cuando otro usuario accede a los logs, el payload se ejecuta contra él.

Un hallazgo recurrente en este tipo de aplicaciones: la falta de cabeceras básicas de protección. "Un header faltante" parece poco crítico, pero si permite robar información sensible —claves de servicios, contenido privado— la criticidad cambia de escala: el atacante levanta su propio servidor, la víctima abre la URL y el atacante se lleva todo, codificado, sin ninguna validación de origen que lo frene. El fix, cuando llegó, fue agregar el origen permitido en la configuración de CORS: solo localhost en el puerto 3000 podía consumir ese contenido.

Los websockets merecen inspección aparte: los chats funcionan sobre ellos y no aparecen en el tráfico HTTP habitual. En este proyecto los mensajes viajaban por websocket sin ningún tipo de validación ni autenticación al crear los sockets: entraban, se procesaban, se guardaban y se enviaban. Hasta se puede hacer caer a la víctima para robarse el mensaje privado que está mandando.

Escáneres dinámicos: Nuclei contra la app funcionando

Con la aplicación levantada, un escáner como Nuclei masifica las pruebas: apuntado a localhost, lanza miles de requests reducidas según los templates activos y encuentra en minutos fallas básicas de cross-site scripting, inyección SQL y demás. Nuclei, hoy muy popular, tiene además carpetas de templates para analizar código: APKs de Android, JavaScript, Node.js, PHP, Python. La contra: le falta cobertura —la comunidad necesita desarrollar más templates, tanto de tipos de vulnerabilidad como de lenguajes—.

Caja blanca: leer el código con ayuda de las máquinas

Abrir el proyecto en el IDE y navegar la estructura es el paso que muchos se saltean. La carpeta APIs es la clave en cualquier sistema web: ahí llega todo lo que el navegador envía, y ahí se ve qué se valida y qué no —tipos de datos, rangos, expresiones regulares para el email—. También se detecta de un vistazo si el código guarda el objeto completo confiando en el input del usuario, o si escribe a la base de datos sin distinguir campos editables. Un buscador global de texto (control + shift + F) rastrea el camino del mensaje malicioso hasta el socket y confirma que no hay validación en ningún tramo.

Las extensiones de análisis en el IDE dan el panorama inicial. Una de ellas marcó path traversal relacionado con archivos —e incluso sugería cómo corregirlo—, librerías mal utilizadas y problemas de calidad de código que sirven también a quien hace code review. Sobre los resultados automáticos rige la regla central: no basta correr la herramienta y entregarle al desarrollador la lista. Hay que mirar cuáles fallas son explotables, cuáles están más cerca del usuario final y cuáles puede explotar de forma simple. La criticidad marcada por la herramienta (high, medium, low) es discutible; la explotabilidad se demuestra.

El entregable cambia de calidad cuando se conoce el código: en lugar del consejo genérico "agreguen validación de input", el reporte puede indicar la expresión regular o la librería concreta para ese lenguaje y ese punto del código. El desarrollador deja de adivinar.

CodeQL, Orusec, Semgrep y Gitlet

  • CodeQL, de GitHub, es la referencia: construye un grafo del código, identifica sources (el input) y sinks (dónde se procesa de forma vulnerable) y encuentra muchas vulnerabilidades con pocos falsos positivos. Flujo: crear la base de datos por lenguaje del proyecto clonado, correr las suites de queries de seguridad o de calidad, exportar el reporte en CSV y revisar línea y columna. Las queries las alimenta la comunidad: cuando aparece una nueva clase de vulnerabilidad, cualquiera desarrolla el template y lo sube. Con su reporte, cada cross-site scripting hallado por caja negra se convierte en una lista de puntos candidatos: hay que ir y probar cuál explota.
  • Orusec tenía pocos falsos positivos, una extensión de IDE, una consola web local y imagen de Docker, aunque su mantenimiento está casi abandonado. Genera un archivo de configuración, corre contra la ruta del proyecto y vuelca resultados a una plataforma web local mediante token. Comparar sus hallazgos con los de CodeQL —event listeners, validaciones de origen, llamadas directas al sistema operativo concatenando input del usuario— cruza señales.
  • Semgrep creció hasta ser un monstruo del análisis estático y, además, escanea dependencias: vulnerables, obsoletas, que no se deberían usar. La contra es la licencia de algunas funciones. El escaneo por defecto (config auto) es de una línea y exporta en JSON, CSV y HTML.
  • Gitlet está quedando obsoleta pero sigue siendo útil para secretos y depende poco de falsos positivos.
  • Nuclei en modo código: apuntado a la carpeta src (excluyendo node_modules) con los templates de Python, reporta code injection y command injection candidatas —con llamadas como subprocess en el punto señalado— que luego hay que validar: puede ser explotable solo en capas internas del backend, o puede ser un falso positivo.

IA como asistente, no como oráculo

Los asistentes de IA agregan un capítulo nuevo: se les entrega el proyecto en zip —con el límite de tamaño que impone el proveedor— y devuelven un panorama razonable: CORS sin validación de orígenes, logs problemáticos, manejo de input sin controles, posible ejecución remota de comandos, sockets creados sin autenticación. Incluso pueden generar la prueba de concepto cuando no se sabe cómo explotar el hallazgo. Pero también se equivocan: marcó como dato sensible una variable de entorno cuyo valor hardcodeado era inofensivo. La regla es la misma que con cualquier escáner: nadie reporta sin mirar la línea de código señalada.

Conclusiones

  • Caja negra y caja blanca se complementan: la app funcionando muestra dónde duele; el código da mayor cobertura, revela la línea exacta y permite recomendar el fix específico en lugar de un consejo genérico.
  • Un proyecto público clonado y desplegado localmente elimina el firewall: se pueden hacer todas las pruebas que en un servicio remoto bloquearían, incluida la fuzzing masiva con escáneres dinámicos.
  • Los websockets, los logs y las validaciones de origen (CORS) son tres zonas calgadas que casi siempre esconden fallas serias en proyectos jóvenes.
  • Ningún resultado automático —escáner, extensiones de IDE o IA— se reporta sin validación manual: el falso positivo es la norma, y la explotabilidad se demuestra, no se declara.
  • El ciclo es virtuoso: reportar, ver el fix, intentar bypassear el fix y volver a reportar; o sumarse como fixer y cobrar por corregir vulnerabilidades ajenas. Colaborar como maintainer y hacer más seguro el código que ya está dando vueltas es parte del mismo trabajo.
