Orquestar DevSecOps con Secure Code Box

Fuente: «Orquestando un ambiente DevSecOps con Secure Code Box - Sergio Correa - Ekoparty 2024» · ver el video original

Gestionar un ecosistema de SecOps es, en la práctica, gestionar el caos: herramientas SAST, DAST, pentest, threat modeling; alternativas open source y pagas; cada una con su propio gestor de vulnerabilidades y su propio formato de findings. El resultado es un entorno no estandarizado donde representar lo mismo de diez maneras distintas complica cualquier intento de gestión.

Secure Code Box, un proyecto open source de OWASP, propone resolver exactamente eso: integrar más de 20 herramientas de seguridad conocidas —Nmap, ZAP, Nuclei, Semgrep, Trivy, Gitleaks, entre muchas otras— en un mismo ecosistema basado en Kubernetes, con salida unificada hacia gestores de vulnerabilidades como DefectDojo o Elasticsearch y notificaciones por Slack o mail.

Por qué Kubernetes

Estar construido sobre Kubernetes no es un detalle: es la decisión que define la herramienta. Cada scan es un manifiesto YAML con el mismo formato que cualquier recurso de Kubernetes; la ejecución se hace con comandos de kubectl; y la plataforma hereda todo lo bueno del ecosistema: modularidad, escalabilidad, jobs en paralelo y optimización de recursos. Para pedir un scan se describe la actividad en YAML —por ejemplo, Nmap contra scanme.nmap.org con ciertos parámetros—, se aplica el archivo y el cluster se encarga del resto.

Los resultados se almacenan en un bucket: S3, Google Cloud o, por defecto, MinIO, el bucket open source que viene integrado. Desde ahí, los findings se consultan por línea de comando o se visualizan directamente.

Scans agendados y en cascada

Dos características destacan:

  • Scans agendados: un tipo de recurso que ejecuta el scan con la frecuencia definida (cada minuto, cada hora) y cuyo estado y findings se consultan después con comandos de Kubernetes.
  • Scans en cascada: cuando la salida de una herramienta matchea un patrón JSON definido, se dispara automáticamente un segundo scan sobre los campos indicados. Kubernetes levanta los jobs en paralelo y la cadena continúa sola.

Los escenarios demostrados muestran el potencial:

  1. Repositorios → SAST: GitRepo Scanner enumera los repos de una organización de GitHub o GitLab; cada hallazgo dispara un análisis estático con Semgrep en paralelo, y los findings terminan en el bucket.
  2. Dominios → ZAP: AMASS enumera dominios y subdominios de un sitio, y sobre esa salida se lanza ZAP contra cada uno.
  3. Subred → fuerza bruta: Nmap barre una subnet buscando puertos SSH; los servicios detectados disparan Ncrack, cuyas listas de usuarios y contraseñas se cargan como secretos de Kubernetes.

Autodiscovery: seguridad continua sin pedir permiso

La funcionalidad de autodiscovery escucha los recursos de un namespace o de todo el cluster: cuando aparece un servicio nuevo con endpoint HTTP, dispara automáticamente el scan definido (ZAP, por ejemplo). El complemento de container autodiscovery analiza con Trivy cada imagen desplegada y devuelve la lista de librerías vulnerables, que puede alimentar herramientas como Dependency-Track.

La demo lo muestra en vivo: se instala OWASP Juice Shop en el namespace default con un comando de Helm, y el autodiscovery, al detectar el nuevo servicio HTTP, lanza el scan sin intervención adicional.

Integración y adopción

Como todo pasa por la API de Kubernetes, los flujos se automatizan fácilmente: un GitHub Action puede disparar scans cuando se pushea código, y los resultados pueden alimentar DefectDojo o integrarse con Jira mediante un hook. La instalación también es mínima: un cluster local (Minikube o kind), un comando para instalar Secure Code Box vía Helm y un comando por cada escáner que se quiera agregar.

Sobre extenderla: las integraciones existentes las aportaron los desarrolladores, pero al ser open source cualquiera puede agregar un escáner —incluso herramientas pagas, entendiendo la lógica del programa—, y la documentación explica cómo. Tampoco hay restricción sobre los objetivos: se escanea desde dentro del cluster o hacia afuera, como el scan a scanme.nmap.org.

Limitaciones honestas

  • Dependencia de Kubernetes: conocer al menos lo básico del ecosistema es requisito previo.
  • Curva de aprendizaje: aunque la documentación es muy buena —algo poco frecuente en open source—, hay que entender cómo se estructura un YAML para armar los manifiestos.
  • Sin interfaz gráfica: no hay UI para visualizar la información; está pensado para desarrolladores y gente de seguridad.
  • Configuración manual mínima en los flujos en cascada.

Cierre

El proyecto nació como trabajo de investigación universitario sobre cómo mejorar la gestión de herramientas de seguridad en un ambiente de SecOps, y el recorrido muestra la idea central: cuando la orquestación es el problema, la respuesta no es otra herramienta aislada sino una capa que unifique formatos, automatice cadenas de análisis y aproveche una plataforma que ya existe. Secure Code Box convierte cada scanner en un recurso de Kubernetes y deja que la plataforma haga el trabajo pesado.
