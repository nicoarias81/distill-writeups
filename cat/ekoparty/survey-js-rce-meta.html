De survey.js a RCE en Meta: la cadena completa de un bug bounty

Fuente: «From survey.js to RCE in Meta - Adrian Pedrazzoli - Ekoparty 2024» · ver el video original

  • Video: DiFHt-Wp-wE · URL: https://youtu.be/DiFHt-Wp-wE · Conferencia: 02_ekoparty · Título original: From survey.js to RCE in Meta - Adrian Pedrazzoli - Ekoparty 2024

Resumen

Un subdominio de la academia de Meta, un endpoint de subida de archivos olvidado en el historial de Burp y una falta de validación en el content-type bastaron para convertir un simple comentario de curso en ejecución remota de código (RCE) con lectura y escritura totales sobre los discos del servidor. Es la historia del primer bug en Meta de Adrián Pedrazzoli (Lemon of Troy), pentester en Salesforce y bug hunter en su tiempo libre, contada con cada decisión y cada truco intermedio.

El hallazgo nació de una circunstancia adversa: en mayo la comunidad fue a un light hacking event de Meta en Sudáfrica, pero una paternidad de dos meses lo dejó afuera. Para no quedarse fuera, un amigo le pasó un link interno "por algo será", y ahí empezó todo. La moraleja de fondo: buscar el mayor impacto posible en cada hallazgo, no quedarse con el primer XSS.

El punto de partida: un code de registro como muro

El sitio era la academia de Meta: cursos, videos y contenidos sobre inteligencia artificial. El primer obstáculo era autenticarse, y el formulario exigía un registration code obligatorio que nadie tenía. En lugar de rendirse, la respuesta fue recon clásico: inteligencia de subdominios valiosos dentro del ecosistema de Meta, buscando la misma aplicación publicada en otro lugar.

El razonamiento es un tip de oro: las grandes empresas tienen muchísimas aplicaciones que pasan por estados de QA y staging, y a veces esos entornos quedan vivos con la misma aplicación. Puede tratarse incluso de un virtual host en el mismo servidor con la misma IP: si el acceso no está disponible por un subdominio, quizá esté públicamente accesible por otro.

La alternativa encontrada pedía el mismo registro, pero sin el registration code: un usuario gratis y acceso completo a la plataforma.

Tip previo: validar el ownership antes de tocar nada

Antes de seguir, la advertencia para quienes arrancan en bug bounty: siempre validar el ownership o el certificado de lo que se está por vulnerar. Un vistazo al certificado —Meta Platforms, California— confirmó que el sitio era de Meta y estaba en scope. Laburar horas y descubrir que el certificado pertenece a otra empresa es una sorpresa evitable de dos segundos.

Recon del interior: el endpoint escondido

Dentro de la plataforma, la superficie era plana: cursos, videos y casi nada dinámico. La única funcionalidad interactiva evidente era rankear cursos con comentarios, y jugar con eso no dio nada. La pista apareció revisando el historial de Burp: un archivo service.js con un endpoint que no había aparecido en ninguna interacción previa:

  • upload answer attachment — un request multipart para subir archivos adjuntos.

Cuando una plataforma de comentarios "solo espera texto", un endpoint de upload es automáticamente interesante.

La checklist del Unrestricted File Upload

El corazón práctico del análisis: al encontrar un multipart —un request donde se puede subir un archivo, un comentario, lo que sea— hay que validar mínimamente cuatro cosas del request:

  1. File name: jugar con caracteres especiales, null characters (%00, %0A, %23, %40), encodings URL de arroba, hashtag, etc., y observar qué responde el servidor.
  2. Extensiones: si la plataforma espera imágenes o texto, probar si acepta HTML, JavaScript, PDF o cualquier otra cosa que no corresponda.
  3. Content-type: el tipo de contenido que viaja en el request informando qué se envía (text/html, application/json, image/svg+xml...).
  4. Content: el contenido mismo del archivo.

Y del lado de la respuesta, cuatro escenarios a buscar:

  • Un 200 OK con un file link que devuelve el path completo donde quedó alojado el archivo. Es el jackpot: permite validar post-upload qué subió realmente y si se ejecuta.
  • Un 200 sin más: se subió, pero hay que encontrar dónde.
  • Permisos: saber dónde está no sirve si no se puede abrir, o si el contenido no se renderiza/ejecuta.
  • Errores: si no hay nada de lo anterior, forzar errores para lograr information disclosure. Un reporte de error puede no ser reportable en bounty, pero es oro para chainear: hay bypasses que nacen de poner una comilla simple que rompe el request y obtiene, del otro lado, un stack trace con la ruta exacta donde se sube el archivo.

Consejo práctico sobre la automatización: en estos casos conviene jugar a mano y de a poquito. Tirar un flujo entero de requests automatizados puede activar un WAF, banear la IP y terminar el juego; con una VPN se mitiga, pero la regla es probar poco y observar.

De XSS almacenado a error revelador

Para armar el multipart en limpio, el request se pasó directo a GPT con la consigna de estructurarlo: content-disposition, content-type, nombre de archivo y contenido, todo delimitado por el boundary de WebKit que separa las partes del multipart. La primera prueba combinó incoherencias a propósito —un lemon.html.jpg como filename con text/html como content-type— y la respuesta fue la mejor posible: 200 OK con el file link y la ruta completa del archivo subido. Al abrirlo, el HTML se renderizaba.

El siguiente paso fue el clásico SVG con un alert(1) dentro: cross-site scripting almacenado, autenticado, dentro de un subdominio de Meta, y con cross-user validado — es decir, con potencial de account takeover. Interesante, pero "¿y si hay algo más que un XSS?".

El pequeño detalle que cambió todo estaba al pie de un error: Microsoft .NET Framework / aspx.net. Si el backend corre ASPX, se puede intentar meter un shell. La deducción fue inmediata.

El WAF, las extensiones y el content-type

Hubo un WAF de por medio: no dejaba subir HTML directamente. Pero las validaciones estaban flojas de papeles:

  • La extensión del filename sí era validada: HTML no pasaba, pero SVG, JPG y otras sí.
  • El content-type no se validaba: se podía poner el que se quisiera, text/html incluido, y el contenido viajaba tal cual.

Es decir: el tipo de archivo filtraba la extensión, pero el contenido pasaba de largo. Esta asimetría es la que permitió subir lo que fuera, con la extensión que fuera, siempre que el contenido llegara intacto.

RCE: el shell ASPX

Con el backend identificado como ASP.NET, el paso final fue copiar un shell ASPX público de un repositorio conocido de GitHub — "está recontraquemado, popular en todos lados" — pegarlo como contenido del multipart y enviarlo. Respuesta: 200 con file link. Al abrirlo, el shell web se renderizaba completo: listado de discos, aplicaciones, y múltiples terceros y grandes empresas hosteadas en el mismo servidor. Acceso total, full read and write sobre todos los discos.

¿Se podía escalar más? Sí, pero con un RCE ya ganado no tenía sentido. Un recordatorio de método: ante una ejecución de código, lo protocolar es parar en un whoami/id; aquí se exploró más porque nadie esperaba que un shell quemado de GitHub pasara los filtros. Pasó de largo, ejecutó, y el impacto era una barbaridad.

Triage, bounty y remediación

La respuesta de Meta fue veloz y ordenada, y sirve como radiografía de un triage serio:

Fecha Evento
25 de abril, 23:00 Se inicia el reporte
26 de abril Triage; piden remover el shell
26 de abril, tarde El sitio baja a mantenimiento
15 de mayo Bounty pagado
1 de agosto Hall of Fame (para el descubridor y el compañero que colaboró)

El equipo de triage de Meta recibe miles de reportes diarios que son spam o ruido, por lo que prioriza de lo más crítico a lo menos crítico; un RCE se valida y atiende enseguida. Un detalle operativo: cuando pidieron remover el shell, la solución fue reutilizar el mismo request de subida y pisar el archivo con contenido inofensivo — con el shell todavía abierto se listaba todo con un ls y se confirmó el reemplazo. Borrarlo directamente habría destruido el propio acceso; sobrescribirlo fue la vía limpia.

Sobre las cifras: en el programa de Meta un RCE se paga en el orden de las decenas a cientos de miles de dólares según la aplicación y el impacto, de ahí la importancia de buscar el máximo alcance antes de reportar.

Técnicas y herramientas mencionadas

  • Recon de subdominios — buscar la misma aplicación publicada en otros subdominios, entornos QA/staging vivos o virtual hosts con la misma IP.
  • Validación de ownership/certificado — confirmar el scope antes de testear (certificado SSL del sitio).
  • Burp Suite — proxy e historial de requests para descubrir service.js y el endpoint de upload.
  • Multipart/form-data — estructura del request de subida: boundary, content-disposition, content-type y contenido por parte.
  • Unrestricted File Upload — checklist completa: file name, extensiones, content-type y content.
  • WAF bypass por asimetría — extensión filtrada pero content-type libre: cambiar extensión manteniendo text/html.
  • SVG con JavaScript — vector clásico de XSS almacenado cuando el HTML directo está bloqueado.
  • Information disclosure por errores — forzar errores (comilla simple, parámetros raros) para obtener stack traces y rutas de subida; clave para chainear.
  • Shell ASPX — web shell público de GitHub aprovechando el backend .NET identificado en el error.
  • GPT para armar el multipart — automatizar la construcción del request en lugar de memorizar la sintaxis.
  • Sobrescritura de archivos — técnica para "remover" el shell reutilizando el mismo request de subida.

Conclusiones

  • Un bug de bajo impacto aparente (un upload en una funcionalidad de comentarios) puede terminar en RCE si se sigue tirando del hilo: la asimetría entre validación de extensión y de content-type fue la puerta.
  • El file link con el path completo en la respuesta es el objetivo número uno al testear uploads: permite validar la explotación post-subida y orienta todo lo demás.
  • Los errores del servidor son material de chain: un stack trace con una ruta convierte un fallo menor en el mapa para el siguiente paso.
  • En bug bounty, el mayor impacto define el pago: un XSS autenticado era interesante, pero seguir buscando —hasta detectar el framework del backend en un error— multiplicó el resultado.
  • La celeridad del triage de Meta (menos de 24 horas entre reporte y mantenimiento del sitio) muestra cómo se trata un RCE correctamente, y la remediación del shell se resolvió sobrescribiendo el archivo con el mismo request.
