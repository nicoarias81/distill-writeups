Resumen

Un ataque a infraestructura en la nube es mucho más que una colección de comandos sueltos: es una historia completa que va desde la obtención de las primeras credenciales hasta el impacto real sobre los datos. El recorrido aquí se planta como un ejercicio de red teaming contra AWS con un objetivo doble: mostrar las técnicas de ataque en vivo —una docena de demos— y enseñar a traducirlas al lenguaje de los equipos defensivos. Porque un reporte de red team vale lo que pueda hacerse con él: si el blue team, el incident response y el equipo de inteligencia no entienden qué se explotó y cómo, la información muere en un PDF.

La columna vertebral del recorrido es la matriz ATT&CK de MITRE. Aunque genere cansancio verla una vez más, funciona como idioma común: decir "initial access por valid accounts" le permite a un incident responder que no domina AWS ubicar la técnica en su contexto y empezar a razonar sobre ella. La otra brújula conceptual es la pirámide del dolor: cambiar hashes e IPs es barato para cualquier atacante, cambiar dominios ya cuesta más, y las TTPs —las tácticas, técnicas y procedimientos— son lo más caro de cambiar. De ahí la conclusión central para los defensores: las detecciones que se apoyan en indicadores frágiles (hashes, IPs) son fáciles de esquivar; las detecciones que se anclan en TTPs resisten.

El modelo de responsabilidad compartida también recibe su dosis de realismo: aunque AWS administre partes del stack, la responsabilidad sobre la data de los clientes nunca se delega. Y en la zona gris del modelo —aquello que ni el proveedor ni el cliente monitorean— es donde los atacantes encuentran espacio para moverse sin visibilidad.

Primer objetivo: credenciales estáticas y dinámicas en la workstation

El punto de partida es una workstation comprometida. En AWS hay tres tipos de identidad que importan para el atacante:

  • Usuarios IAM con access keys y secret access keys: credenciales programáticas que, por defecto, no rotan. Son el primer objetivo al aterrizar en una máquina: a menos que alguien las deshabilite manualmente, suelen seguir válidas.
  • Roles con session tokens: la forma más segura de operar, porque el token expira tras un tiempo. Si el token está vencido, la credencial sirve poco —salvo que se vuelva a aparecer cuando esté activa.
  • Credenciales de SSO: una variación de los roles, guardadas en el archivo cache dentro del directorio .aws, donde se pueden encontrar tokens, región y refresh tokens.

La búsqueda es trivial pero efectiva: listar el contenido de ~/.aws revela qué perfiles existen. Un detalle forense útil: si el perfil incluye un session token, es un rol; si no, es un usuario programático. Al intentar una llamada a la API de S3 con el perfil del rol, el error expired token confirma que la credencial es legítima pero su sesión venció —un indicador de que conviene volver más tarde o buscar otra vía.

De credenciales a consola: tomar el management plane

Con la credencial de usuario en mano, el siguiente paso es averiguar qué se puede hacer con ella:

  1. sts get-caller-identity — el "whoami" de AWS: devuelve el ARN, que incluye el número de cuenta. Un dato defensivo: esta llamada es un indicador clásico de enumeración, así que un atacante cuidadoso puede obtener la cuenta directamente del ARN sin ejecutarla.
  2. get-login-profile — si devuelve "not such entity", el usuario no tiene acceso a consola: es puramente programático.
  3. create-login-profile — se le crea un perfil de consola con la contraseña que el atacante elija. Si el usuario ya tenía un perfil con contraseña fuerte, no importa: delete-login-profile y se vuelve a crear uno nuevo. El flujo puede repetirse infinitas veces.

Con usuario, contraseña y número de cuenta en mano, el acceso al management console de AWS está servido. ¿Por qué molestarse? Porque hay muchas cosas que son mucho más fáciles de ver desde la consola que por API, y esta técnica aparece en ataques reales. Dos límites a recordar: los permisos en AWS están acotados al tenant —a diferencia de GCP y Azure, un usuario no salta entre cuentas de la organización— y borrar el login profile revierte todo el acceso.

Persistencia en servidores: SSM, el 22 y las llaves

Dentro de la consola, un servidor EC2 con el puerto 22 expuesto a internet se vuelve territorio de juego. AWS Systems Manager (SSM) permite conectarse por "SSH" a través de la propia consola sin poseer ninguna llave SSH. Y una vez dentro de la sesión, agregar una llave propia al archivo authorized_keys configura persistencia directa sobre el servidor: sin credenciales SSH robadas, sin herramientas ruidosas, solo con permisos de IAM y un puerto abierto.

Instance Metadata v1: convertir un servidor en fuente de credenciales

El Instance Metadata Service es el mecanismo que permite a un servidor consultar información sobre sí mismo: IP pública, tipo de instancia, nombre. Pero también devuelve las credenciales del rol asociado a la instancia. Basta ejecutar, desde dentro del servidor, un curl a la IP fija 169.254.169.254 —la misma en todos los proveedores de nube— y pedir el path de IAM security-credentials: el servicio responde con un access key, un secret y un session token válidos como el rol del servidor.

Aquí está la magia de la técnica: el token expirado que falló al principio se reemplaza por este nuevo, y a partir de ese momento todas las llamadas a la API se ejecutan como el rol ec2-admin. Para el defensor, los logs ya no muestran a un usuario sospechoso sino a una instancia EC2 legítima haciendo llamadas —actividad que parece un script de la propia aplicación. El atacante literalmente cambia de identidad: deja de ser un usuario y pasa a ser el servidor.

Una versión aún más persistente aprovecha las trust relationships: si un rol está limitado a ser asumido por el rol de la instancia EC2, asumir ambos encadenadamente renueva el session token en cada salto. Con un loop entre las trust relationships, el rol se mantiene activo indefinidamente.

Qué ve el defensor mientras tanto

Todo lo anterior dejó rastro en dos servicios que conviene conocer a fondo:

  • CloudTrail registra todas las API calls: source IP, user agent, cada get-caller-identity y cada listado de buckets. Se habilita manualmente y envía los logs a un bucket de S3, pero AWS conserva igualmente el Event History por defecto —útil saberlo tanto para defensores que creen no tener logs como para atacantes que creen operar a oscuras. El talón de Aquiles: CloudTrail tiene hasta 15 minutos de delay; para un atacante, esa es una ventana de ataque contra sistemas de detección alimentados por él.
  • GuardDuty combina logs de VPC, DNS y API calls en detecciones listas para usar, con la ventaja de activarse con un clic. Detecta bien comportamiento anómalo, minado de criptomonedas y permite escanear malware en servidores, pero no es especialmente afinado para las técnicas de movimiento descritas aquí.

La parte incómoda para el defensor: con los mismos permisos comprometidos, un atacante puede listar los detectores de GuardDuty y las trails de CloudTrail, y ejecutar stop-logging sobre la trail activa. El registro simplemente se apaga.

Lecciones de hardening

  • Deshabilitar todo lo que no se use, especialmente regiones. Muchas detecciones son regionales: un detector en Estados Unidos no ve nada de lo que ocurre desde Brasil si esa región está habilitada y desmonitoreada.
  • Rotar y restringir credenciales estáticas. Las access keys que no rotan por defecto son el regalo favorito del infostealer. Los roles con session tokens cortos son la alternativa correcta.
  • Cerrar el Instance Metadata v1. La versión 2 exige un token por consulta y mitiga el robo directo de credenciales; pese a los esfuerzos de AWS, la v1 sigue en producción en muchas empresas por comodidad.
  • Revisar trust relationships. Un rol débil asumible por el rol de una instancia comprometida convierte la cadena en una escalada silenciosa.
  • Cuidado con las tools automatizadas. Herramientas como AWS Nuke dejan rastros masivos que todas las detecciones atrapan de inmediato; la actividad manual, metódica y con llamadas mínimas es la que realmente se cuela. Para el defensor, esto significa que el volumen anómalo de API calls es una señal valiosa, pero no la única: el patrón "usuario programático que de repente tiene login profile" es una TTP mucho más estable de detectar.
