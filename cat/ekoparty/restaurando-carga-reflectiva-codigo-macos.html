Restaurar la carga reflectiva de código en macOS: el viejo DYLD vuelve a la carga

Fuente: «Restoring Reflective Code Loading on macOS - Patrick Wardle» · ver el video original

  • Video: LLwLQxuR-kQ · URL: https://youtu.be/LLwLQxuR-kQ · Conferencia: 02_ekoparty · Título original: Restoring Reflective Code Loading on macOS - Patrick Wardle

Resumen

La carga reflectiva de código (reflective code loading) consiste en ejecutar binarios compilados —por ejemplo, una librería dinámica— directamente desde memoria, sin que el payload toque jamás el sistema de archivos. Para un atacante que ya consiguió ejecución inicial de código en una Mac, es la técnica ideal para desplegar implantes de segunda etapa: en macOS, las herramientas de seguridad y el propio sistema operativo son casi ciegos ante lo que ocurre en memoria de otro proceso.

El problema es que Apple introdujo un cambio en DYLD, su loader nativo, que neutralizó el enfoque clásico: las APIs históricas ahora escriben el payload en memoria a un archivo temporal antes de cargarlo, dejándolo expuesto a cualquier monitor de sistema de archivos. La investigación de Patrick Wardle, cofundador de la Objective-See Foundation, demuestra que esta mitigación es traspasable de forma elegante: compilando una versión antigua del propio DYLD de Apple dentro de un loader custom, se restaura la ejecución 100 % en memoria incluso en macOS Tahoe 26, con soporte para payloads en Objective-C y Swift y compatible con la notarización de Apple.

El artículo recorre la historia de la técnica, el cambio de Apple que la "mató", el método de restauración y —para los defensores— las pocas opciones de detección reactiva que quedan.

Por qué la ejecución en memoria es un superpoder ofensivo

En un flujo normal, al abrir un binario el loader de macOS (DYLD) lo lee del disco, lo mapea en memoria, resuelve dependencias, aplica relocaciones, configura permisos de memoria, ejecuta inicializadores y transfiere el control. Un binario en disco tiene un layout optimizado para almacenamiento, distinto de su representación en memoria: no se puede simplemente copiar los bytes y saltar al código.

La carga reflectiva se salta el disco: un binario compilado (típicamente un dylib, el equivalente a un DLL de Windows) se descarga directamente a memoria y se prepara para ejecución allí mismo. La consecuencia es crítica para ambas partes del tablero: las capacidades de escaneo de memoria en macOS son muy limitadas. Apple no permite que un proceso lea la memoria de otro proceso —la API Task for PID, que antes daba un task port para escanear memoria remota, fue cerrada—. Esa política protege la privacidad (un malware con root no puede volcar cookies del navegador ni el keychain de esa forma), pero también cega a las herramientas de seguridad. XProtect, XProtect Remediator y MRT funcionan escaneando archivos en disco; un payload que nunca aterriza en el disco es invisible incluso para un producto de seguridad con acceso root.

Un antecedente ilustrativo llega de Windows: el malware Gauss (2010-2012) usaba un loader en memoria con payloads cifrados. Fue detectado y algunos payloads capturados, pero más de una década después nadie ha podido descifrar qué hacían esos módulos: la combinación de cifrado y ejecución en memoria preservó el secreto para siempre.

Breve historia: de proyecto de Apple a arma de Lazarus

La técnica tiene pedigree oficial. En 2005 Apple publicó un proyecto de ejemplo, "Memory Based Bundle", que mostraba cómo ejecutar código Mach-O directamente desde memoria. En 2009, el Mac Hacker's Handbook portó ese loader a shellcode, y el propio Wardle construyó herramientas ofensivas sobre las mismas APIs. Recién hacia 2017 el malware de macOS adoptó la técnica en serio: muestras como Snake, ThiefQuest, SugarLoader y otras —varias atribuidas a actores norcoreanos, el colectivo DPRK/Lazarus— ejecutaban componentes de segunda etapa en memoria.

El patrón de ingeniería inversa es idéntico en todas: descargar el payload del C2, copiarlo a memoria sin tocar el sistema de archivos, y llamar a dos APIs de Apple: NSCreateObjectFileImageFromMemory y NSLinkModule. En el caso de AppleJeus (2019), el código resultó ser una copia exacta —mismos mensajes de error, mismos offsets— de un proof-of-concept open source publicado por la empresa Silasence (Silance) basado en el código de Apple. En EvilQuest (2020) pasaba lo mismo: las APIs de Apple más una sección de estrellas cifrada que, al descifrarla, coincidía con el proyecto Memory Based Bundle. Los autores de malware simplemente reciclaron código oficial. Por qué reinventar la rueda.

El cambio de DYLD3 que "mató" la técnica

Todo funcionaba sin fricción hasta DYLD3. Al examinar su código fuente (ABIerto por Apple), aparece el cambio clave: si NSLinkModule detecta que se le pasa un payload en memoria, lo escribe en un archivo temporal —con nombre NSCreateObjectFileImageFromMemory-XXXX, donde XXXX son bytes aleatorios— dentro del directorio temporal, y luego lo carga como un binario normal desde disco. La ejecución 100 % en memoria desaparece: hay eventos de archivo, y cualquier herramienta puede observar y capturar el payload escrito a disco.

Peor aún para el atacante, investigadores señalaron que ese nombre de archivo prefijado era una señal de detección poderosa: si aparece un archivo con ese patrón, alguien está intentando ejecutar un payload en memoria, y conviene agarrarlo.

Se probaron varias evasiones, cada una con costos:

  1. RAM disk: la API obtiene el directorio temporal vía getenv("TMPDIR"), variable de entorno del propio proceso, así que se puede apuntar a un RAM disk. El payload se escribe "en memoria", pero el RAM disk sigue siendo un filesystem: genera eventos de archivo y cualquier herramienta puede leer el payload ahí.
  2. Truncamiento del nombre: strlcat concatena con tope máximo; creando una estructura de directorios muy larga, la extensión NSCreateObjectFileImageFromMemory-XXX ya no entra en la ruta y el archivo deja de coincidir con el patrón de detección. Útil, pero el archivo sigue escribiéndose.
  3. Parchear el loader (Adam Chester): escanear la memoria del proceso y "desparchear" las APIs que escriben a disco. Funciona, pero sigue habiendo escritura a archivo (aunque sea de un señuelo) y en Apple Silicon (M1-M5) tocar memoria así choca de inmediato con pointer authentication y otros mecanismos de seguridad.

Ninguna era la solución limpia. Escribir un loader propio desde cero —manejar relocaciones, permisos, dependencias— es un proyecto enorme.

La epifanía: compilar el DYLD viejo dentro del loader

La idea central es casi obvia en retrospectiva: la ejecución en memoria sigue técnicamente soportada; lo único que cambió es que las APIs nuevas escriben a disco. ¿Y si se toma una versión antigua de DYLD —la que no escribe nada a disco— y se compila directamente dentro del propio programa?

Funciona, y en unas 15 líneas de código:

flowchart LR
    A[Descarga dylib del C2 a memoria] --> B[instantiate from memory - DYLD viejo]
    B --> C[image.link - linking completo]
    C --> D[Registro de clases/selector - runtime ObjC]
    D --> E[Resuelve símbolo y ejecuta - dlopen from memory]

El loader custom descarga la librería precompilada a su propio espacio de direcciones y llama a las funciones del DYLD antiguo embebido —instantiate from memory seguido de image.link— que hacen todo el trabajo de loader sin tocar el sistema de archivos. Un monitor de archivos confirma que no se escribe absolutamente nada.

Soporte para Objective-C y Swift

Quedaba un detalle: si el payload estaba escrito en Objective-C o Swift, se cargaba pero crasheaba al invocar código Objective-C, porque el loader no registra clases ni métodos con el Objective-C runtime. Basándose en investigación previa sobre JIT de LLVM, la solución es registrar el código Objective-C on demand:

  • Selectores: iterar la sección __objc_selrefs del Mach-O; para cada selector, obtener su nombre y registrarlo con sel_getName/sel_registerName, actualizando la referencia al selector registrado.
  • Clases: iterar la sección __objc_classlist y llamar objc_readClassPair por cada clase, que bajo el capó la registra con el runtime.

Con ambos pasos, payloads con código Objective-C y Swift corren sin problemas desde memoria.

Compatibilidad con la notarización

Para distribuir el loader en máquinas objetivo modernas hace falta notarización, que exige optar por el Hardened Runtime. El problema: el Hardened Runtime mata el proceso ante cualquier fallo de verificación de firma de código, y un payload en memoria no tiene imagen en disco que verificar. La salida son los entitlements de excepción (como com.apple.security.cs.allow-unsigned-executable-memory), que declaran que el proceso está autorizado a ejecutar código directamente desde memoria. El resultado: un binario con el flag del Hardened Runtime activo (bit 0x100 en codesign), entitlements de excepción, y pasable por notarización — Apple escanea contra malware conocido, y un programa cuyo único trabajo es cargar y ejecutar cosas desde memoria no es per se malicioso. Además, si alguien captura el loader, solo obtiene el código del loader, nunca los payloads.

El proof-of-concept es open source y soporta payloads Objective-C y Swift incluso en macOS 26.

¿Qué puede hacer un defensor?

Las opciones son escasas y todas reactivas:

  • Enumerar dylibs cargadas en un proceso remoto: en teoría detectaría librerías sin archivo asociado, pero los payloads en memoria no aparecen en la lista de librerías cargadas, y las APIs para hacerlo exigen un entitlement privado que solo Apple posee. Descartado.
  • Logs y Endpoint Security: en pruebas con el loader modificado para pausar antes de ejecutar el payload, no aparece nada: ni mensajes de log, ni eventos de Endpoint Security (ni siquiera el evento de mapeo de páginas). El framework que Apple recomienda para detectar actividad maliciosa no emite nada ante la ejecución en memoria.
  • vmmap: esta utilidad sí tiene los entitlements para ver el mapa de memoria de un proceso remoto, y un payload en memoria aparece como un dylib sin path (dylib). Es una señal, pero snapshot-based y sin forma de extraer la memoria.
  • sample: otra utilidad con permisos especiales que muestra backtraces de threads; los frames dentro del payload aparecen etiquetados como "binary unknown". Misma limitación: detecta, no recupera.
  • Flaggear entitlements de excepción: trivial de escanear, pero más de 60 aplicaciones legítimas de un solo directorio usan los mismos entitlements. Heurística inútil.

La conclusión incómoda para el defensor: la única vía realista es ignorar la carga en memoria y monitorear lo que el payload hace después —robar cookies del navegador, tocar el keychain— porque esas acciones sí generan eventos. Y aun detectando la actividad, el payload en sí es irrecuperable.

Conclusiones

  • La carga reflectiva de código en macOS sigue viva y bien: el cambio de DYLD3 que escribe payloads a disco se traspasa compilando versiones antiguas del propio DYLD de Apple dentro de un loader custom, con soporte completo para Objective-C/Swift y compatibilidad con la notarización vía entitlements de excepción del Hardened Runtime.
  • Para los atacantes es una capacidad poderosa y de bajo costo: el código de Apple hace el trabajo pesado del loader, el payload jamás toca el filesystem, y capturar el loader no revela nada.
  • Para los defensores, el panorama es sombrío: sin escaneo de memoria remota posible, sin eventos de Endpoint Security, y con detecciones solo snapshot-based (vmmap, sample) que exigen sondeo constante.
  • El caso es un ejemplo del desbalance entre privacidad y visibilidad defensiva: Apple prohibió la lectura de memoria entre procesos pero dejó abierta la ejecución en memoria. El paralelo con iOS es directo — el ataque de triangulación infectó dispositivos de investigadores de Kaspersky sin ser detectado durante cuatro años, precisamente porque el cerramiento de la plataforma deja a los defensores sin instrumentos. La petición implícita: si Apple bloquea extensiones de kernel de terceros (y lo hace, con el modo de recuperación como único camino), debería proveer frameworks de user mode con capacidades equivalentes para las herramientas de seguridad. Hasta entonces: atacantes contentos, defensores a ciegas.

Técnicas y herramientas mencionadas

  • Reflective code loading: ejecución de binarios compilados directamente desde memoria, sin pasar por el sistema de archivos.
  • DYLD / DYLD3: el loader nativo de macOS; DYLD3 introdujo el cambio que escribe payloads en memoria a archivos temporales.
  • NSCreateObjectFileImageFromMemory / NSLinkModule: APIs históricas de Apple para preparar y enlazar un binario desde memoria.
  • Memory Based Bundle: proyecto de ejemplo de Apple (2005) que documentó la técnica originalmente.
  • Mach-O: formato ejecutable nativo de macOS (equivalente a PE en Windows, ELF en Linux).
  • Objective-C runtime: registro dinámico de selectores (sel_registerName) y clases (objc_readClassPair) desde las secciones __objc_selrefs y __objc_classlist.
  • Hardened Runtime + entitlements de excepción: mecanismo de firma de Apple; los entitlements permiten ejecutar código sin verificación desde memoria.
  • Notarización: escaneo previo de Apple que habilita la distribución de software; no detecta un loader genérico de memoria.
  • Task for PID: API histórica de task ports, cerrada por Apple, que permitía escanear memoria de otros procesos.
  • Endpoint Security: framework oficial de Apple para telemetría; no emite eventos ante ejecución en memoria.
  • vmmap / sample: utilidades de macOS con entitlements privilegiados, útiles solo para detección reactiva (dylib sin path, "binary unknown" en backtraces).
  • Malware de referencia: AppleJeus, EvilQuest, Snake, ThiefQuest, SugarLoader (varios atribuidos a DPRK/Lazarus); Gauss como antecedente en Windows.
  • Herramientas del autor: Objective-See Foundation, libros The Art of Mac Malware y Mac Malware Bug Hunting (gratuitos en línea), y el proof-of-concept open source del loader.
