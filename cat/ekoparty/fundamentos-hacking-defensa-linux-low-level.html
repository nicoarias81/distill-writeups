Fundamentos de hacking y defensa en Linux: lo que pasa abajo del hello world

Resumen

En la época de Kubernetes, contenedores y capas de abstracción, se está perdiendo de vista la base: el kernel. Este recorrido baja hasta el fondo del sistema operativo para desarmar qué ocurre realmente cuando se ejecuta un hello world en Linux: la libc, las llamadas al sistema, los anillos de privilegio, los file descriptors, el formato ELF y las secciones de memoria de un proceso. Y muestra por qué ese conocimiento decide quién encuentra lo que otros esconden: desde una shell reversa camuflada en una "calculadora" hasta un hook con LD_PRELOAD capaz de ejecutar cualquier cosa — incluso controlar las luces inteligentes de una casa.

Por qué bajar tan abajo

  • Linux está en todas partes: supercomputadoras, equipos que viajaron a Marte, servidores, teléfonos. Es el descendiente más trascendente de Unix, nacido inspirado en ese modelo.
  • La abstracción actual oculta lo que pasa en el fondo, y el pentesting serio exige entenderlo: cuando se ataca un binario hay que trabajar contra sus protecciones y segmentos de memoria.
  • El formato a.out — el de los viejos binarios compilados — inspiró el recorrido: son horas y días de investigación, y lo que queda afuera siempre es más que lo que entra.

Los anillos de seguridad y las llamadas al sistema

El modelo de anillos separa lo privilegiado de lo que no lo es:

  • Ring 3 (user space): cualquier aplicación — una consola, un navegador.
  • Rings 1 y 2: drivers, entre el kernel y el user space.
  • Kernel: el único con acceso directo al hardware; agarra interrupciones y le ordena al hardware qué hacer.

La syscall es la interfaz entre el user space y el kernel: read, write, stat, fork, clone, mmap, ioctl, brk, entre muchas. Cada una tiene un número; en ARM, la número 64 es write y la 93 es exit.

Fork es cómo nacen los procesos: duplica el espacio de memoria del padre, clona sus estructuras y reemplaza el comando antiguo por el nuevo, con copy-on-write — solo copia un segmento cuando hay que modificarlo — para no arrastrar gigabytes. Todo proceso tiene un PID y un PPID: existe una jerarquía que antes descendía de init y hoy de systemd.

Clásico obligado del bajo nivel: la fork bomb — :(){ :|:& };: — una recursión que llena todo el espacio de procesos hasta colgar el equipo. Se previene limitando la cantidad de llamadas recursivas por proceso.

El /proc y la regla de oro: todo es un archivo

En Linux existe un sistema de archivos virtual que expone la metadata de cada proceso como mecanismo de IPC:

  • /proc/<PID>/cmdline muestra el comando ejecutado; la entrada existe solo mientras vive el proceso — al cerrar la terminal, desaparece.
  • /proc/<PID>/fd lista los file descriptors: 0 entrada estándar (el teclado), 1 salida estándar (la pantalla), 2 salida de errores.
  • Porque para el kernel los nombres de archivos no existen: los mapea a file descriptors, números que identifican lo que el proceso tiene abierto.

Y la regla que organiza todo: en Linux todo es un archivo. Un disco, la memoria, una placa de red, un módem y una conexión TCP son archivos. La demostración más elocuente: abrir el file descriptor 3 hacia google.com:80 con la sintaxis de socket, mandarle un GET / y leer la respuesta HTTP desde el /proc de otro proceso. Si las conexiones son archivos, todo se puede redirigir y encadenar — esa es la forma de trabajar de Unix.

La syscall por dentro: de la libc al ensamblador

El mismo "hola hackademy" escrito tres veces, cada vez más abajo:

  1. Por la libc: printf es la puntita del iceberg. Bajo strace se ve el desfile completo: fstat para verificar archivos, apertura de ld.so.cache y librerías compartidas, mmap de memoria con permisos de lectura/escritura, brk para ubicar el heap, y al final un write al file descriptor 1 con la cantidad exacta de caracteres.
  2. Por el wrapper: llamando directamente a write en C — que aún es un wrapper de la libc sobre la syscall del kernel. Detalle instructivo incluido: contar mal el largo del string recorta el salto de línea, y lo corrige en vivo compilando de nuevo.
  3. En ensamblador: secciones .text (instrucciones, solo lectura) y .data (variables y constantes); se carga 64 (write) en el registro de syscall, los argumentos en los siguientes registros, y una interrupción de supervisor hace el switch del ring 3 al kernel space. Después, la syscall 93 (exit) con código 0. Compilado con as y enlazado, el binario hace exactamente lo mismo.
flowchart TD
    A["printf (libc)"] --> B["write (wrapper libc)"]
    B --> C["syscall 64: write"]
    C -- "interrupcion de supervisor" --> D["KERNEL: mapea memoria de video"]
    E["Assembler: mov syscall + args + svc"] --> C

Comparando el código objeto de ambas versiones queda a la vista por qué el assembler es más eficiente: el binario de C arrastra la inicialización de la libc, la PLT (tabla de enlace dinámico) y las secciones init/fini; el de assembler es un puñado de instrucciones. Y en la metadata del ELF aparecen las defensas: el magic number \x7fELF que identifica el formato, y el ASLR (Address Space Layout Randomization), que carga el programa cada vez en una dirección distinta para frustrar los buffer overflow.

Anatomía aplicada: la calculadora que llama a casa

Todo esto sirve para una cosa: entender qué hace realmente un proceso. Caso demostrativo:

  • La víctima descarga un binario que se supone una calculadora. El atacante deja una shell a la escucha con netcat en el puerto 4444 — un socket, que también es un archivo, visible como file descriptor extra en /proc/<PID>/fd.
  • La víctima ejecuta la calculadora: se establece una reverse shell y el atacante tiene acceso completo (uname -a incluido).
  • ¿Cómo la detecta la víctima? Con strace -f — siguiendo también los procesos hijos — se ve el intento cíclico de conexión al puerto 4444: connection refused mientras nadie escucha, y al abrir el puerto, el fork de la bash y cada byte escrito y leído en la shell.

El mensaje es directo: cuando se esté en un pentest o auditando código, hay que entender qué hace el binario en el fondo — y con las herramientas de bajo nivel nada se puede esconder. Complemento ofensivo/defensivo del propio kernel: BPFtrace, que permite colocar sondas dentro del kernel y auditar cuántas syscalls ejecuta cada proceso y cuánto demoran.

LD_PRELOAD: si podés hacer aparecer un trenecito, podés hacer cualquier cosa

La demo final encadena todo:

  1. objdump sobre el binario ls para inspeccionar sus funciones, y captura de la función opendir.
  2. Una librería compartida (sl.so) que redefine opendir y, vía la variable de entorno LD_PRELOAD, reemplaza la función original: al ejecutar ls, en vez de archivos aparece el trencito del clásico sl.
  3. El principio: si se puede hacer que aparezca un trencito, se puede ejecutar cualquier cosa — una shell, capturar todo lo que se teclea y mandarlo a una ubicación remota, reiniciar servidores, persistir en la inicialización del sistema. Solo una auditoría completa del sistema de archivos y de las librerías linkeadas por cada comando lo delata.
  4. La demostración lúdica: la misma técnica inyectando llamadas a los comandos de las luces inteligentes del cuarto — y todo el flujo de la casa manejado desde el ls de la terminal.

Técnicas y herramientas mencionadas

  • GCC, as y enlace de binarios — el mismo hello world compilado en C y en ensamblador ARM.
  • strace / strace -f — trazado de syscalls de un proceso y de sus hijos; base de la detección de la reverse shell.
  • /proc — filesystem virtual de procesos: PID, cmdline, file descriptors, redirección entre procesos.
  • File descriptors y sockets — entrada/salida/errores (0/1/2) y conexiones de red como archivos.
  • Formato ELF, readelf y magic number — estructura del binario ejecutable y metadatos de carga.
  • mmap, brk y copy-on-write — mapeo de memoria, heap y duplicación eficiente de procesos.
  • ASLR — aleatorización de direcciones contra buffer overflow.
  • Netcat — shell a la escucha y sockets como archivos.
  • BPFtrace — sondas dentro del kernel para auditar syscalls por proceso.
  • LD_PRELOAD + objdump — hooking de funciones de un binario (opendir) con librería compartida.

Conclusiones

  • Un hello world que parece trivial es, debajo, una cadena completa: libc, wrapper, syscall, interrupción y kernel mapeando memoria de video. Conocer esa cadena es la diferencia entre usar Linux y entenderlo.
  • "Todo es un archivo" no es un eslogan: es la llave que permite redirigir memoria, conexiones y dispositivos entre procesos, y la que hace de /proc el mapa de todo lo que corre.
  • Los binarios se auditan en el fondo: strace convierte una "calculadora" sospechosa en una reverse shell visible, syscall por syscall. Fuera del ensamblador no se puede esconder nada.
  • LD_PRELOAD muestra el poder del hooking: capturar una función de un comando cotidiano y ejecutar cualquier cosa con ella — del trencito al keylogger, y del keylogger a las luces de la casa.
  • El conocimiento es poder: entender lo que sucede en el fondo del sistema operativo permite entender — y hacer — todo lo demás. No se aprende en un día, pero es la base que el hacking y la defensa serios exigen.
