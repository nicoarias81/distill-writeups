Explorar APIs vulnerables con Yrprey: del reto a la vida real

Fuente: «Yrprey Frameworks to Exploitation OWASP TOP 10 API - Fernando Mengali» · ver el video original

  • Video: 92R6M1hCbrI · URL: https://youtu.be/92R6M1hCbrI · Conferencia: 02_ekoparty · Título original: Yrprey Frameworks to Exploitation OWASP TOP 10 API - Fernando Mengali

Resumen

La mayoría de los frameworks vulnerables clásicos (WebGoat, Juice Shop, VAmPI, crAPI) llegan acompañados de documentación, videos y walk-throughs que transforman cada reto en un ejercicio guiado de cinco minutos. Yrprey nació como la respuesta opuesta: un framework vulnerable exclusivamente dedicado a APIs, con alrededor de 22 vulnerabilidades y sin documentación, para que quien lo enfrente deba razonar por su cuenta. Esa ausencia deliberada lo convirtió en una herramienta de evaluación usada por universidades —principalmente en Luxemburgo— y por centros militares.

El proyecto forma parte de una familia de más de nueve frameworks vulnerables (PHP, C, Node.js, ASP, Python) y su tabla comparativa contra VAmPI y crAPI marca el contraste: ambos llegan con documentación al 100% y nueve vulnerabilidades mapeadas (VAmPI, con un 41% del OWASP API Top 10 cubierto; crAPI, con ocho vulnerabilidades y un 81%), mientras que Yrprey se queda en 22 vulnerabilidades y cero documentación. Todos los retos reproducen fallos encontrados en pentests reales: bancos, aseguradoras y plataformas de seguridad. Esta publicación recorre esa demostración en vivo, vulnerabilidad por vulnerabilidad, con sus correcciones y las historias reales detrás de cada una.

Inyección SQL donde nadie mira: dentro del JSON

El primer reto es una página de login común. Muchos pentesters prueban inyección SQL en la ruta de la petición, pero rara vez dentro de cada valor del JSON. Al enviar un payload en el campo del formulario aparece el error característico de la base de datos: no existe ningún tratamiento de lo que se envía. Desde ahí el camino es el clásico —descubrir columnas, ajustar la unión— hasta listar todos los usuarios y sus contraseñas en una sola respuesta.

La lección: la inyección SQL sigue viva justo en los lugares donde la costumbre deja de mirar, y el volumen del JSON no es excusa para omitir el test.

Ejecución de comandos disfrazada de registro

Al crear una cuenta, la aplicación también crea una carpeta con el nombre del usuario. Esa correlación entre registro y sistema de archivos abre la puerta a la ejecución remota de comandos inyectando contenido que el sistema termina interpretando. La recomendación práctica es directa: si crear una cuenta dispara la creación de archivos o carpetas en el servidor, hay un problema de diseño, y ese patrón apareció en múltiples organizaciones reales.

Otras dos fallas completan el primer bloque: un endpoint de carga de archivos que permite subir un shell con acceso pleno al sistema, y una comparación trivial (1=1) que otorga acceso directo a la plataforma.

SSRF en un botón de "Backend On"

Un panel mostraba un indicador verde "Backend On": un motor que valida internamente si las APIs están funcionales. La pregunta incómoda es por qué esa validación acepta valores arbitrarios del usuario. Al manipularla, es posible lanzar peticiones hacia la red interna y descubrir máquinas, servidores, puertos y recursos compartidos. Cuando la interacción apunta a servicios externos se habla de Remote File Inclusion; aquí el objetivo es interno, y por eso es SSRF.

Lo llamativo: esta misma falla se encontró en una plataforma de desarrollo seguro muy conocida, y patrones similares son habituales en entornos cloud como Amazon, donde las peticiones internas también permiten leer archivos, por ejemplo PDFs.

Envenenamiento de logs: el log que ejecuta

Otro clásico poco difundido: una funcionalidad que envía cada petición a un archivo de log, sin correlación ni saneamiento, y con el log en una ubicación ejecutable. Inyectar comandos en el log hace que el servidor los interprete: ifconfig para reconocimiento, wget para descargar herramientas, y a partir de ahí el servidor es del atacante. El equipo ha logrado incluso buffer overflows en servidores alcanzados por esta vía.

Denegación de servicio por parámetros desbordados

Un endpoint de sliders devuelve la cantidad de imágenes que se le pide: tres pedidos, tres respuestas; mil pedidos, mil respuestas. Con mil peticiones concurrentes de mil imágenes, el servidor se ahoga y la base de datos colapsa. El patrón es general: cualquier endpoint que acepte un número sin validar se convierte en una palanca de DoS.

BOLA: el token que abre todas las puertas

La tercera vulnerabilidad del OWASP API Top 10, Broken Object Level Authorization, aparece en todo su esplendor: cambiar el identificador del token en la petición devuelve los datos de otros usuarios. El agravante es el vector de obtención: cada error en la página de login genera automáticamente un token válido. Con dos peticiones —provo un error, capturo el token, lo uso— se obtienen los datos de todos los usuarios.

flowchart LR
    A[Error deliberado en el login] --> B[El sistema devuelve un token válido]
    B --> C[Petición con ese token a la API]
    C --> D[Datos de otros usuarios expuestos]

Es exactamente el caso de Uber: errores de login devolvían tokens, y la base NoSQL respondía con todos los registros —corridas, pagos, cuentas, ubicaciones— en lugar de uno solo.

Otra variante: una API expuesta en dos versiones, la 2 actual y la 1 "deprecada" pero viva. Cambiar un solo carácter en la versión revivió el caso de JustDial en India: mismo endpoint, todos los datos de todos.

Datos reales, no de laboratorio

Estas fallas no son teóricas. Una anécdota de trabajo lo demuestra: al registrar la entrada al trabajo, la pantalla de un director de la empresa apareció en pantalla; dentro había vacaciones, recibos de sueldo, legajos. Al interceptar el tráfico se descubrió que los ambientes de desarrollo y producción compartían la misma base: más de 6.000 empleados de una multinacional expuestos.

Otro caso reciente de Brasil: el boleto —el mecanismo de pago tipo QR— permitía comprar 50 dólares y pagar 1. Cinco millones de reales perdidos, alrededor de un millón de dólares, por una manipulación de valor en la petición. Algo parecido le pasó a Mercado Pago hace años: se enviaba el detalle de una compra manipulada y la respuesta era "gracias, vamos a verificar", sin verificación alguna.

Exposure: el comentario que se fue a producción

La vulnerabilidad de exposición de datos sensibles tiene aquí su versión más didáctica. Con un problema sin resolver en la aplicación, un desarrollador agrega un dato de prueba a la tabla, prueba el flujo, no encuentra el bug y decide comentar una línea para "arreglar después"... y esa versión se despliega a producción. Resultado: la aplicación devuelve tokens a cualquiera que cometa un error de login, sin necesidad de contraseña alguna. Uber sufrió exactamente esto y perdió millones de registros.

Corregir bien, no maquillar

La demostración de remediación incluyó: consultas preparadas para eliminar la inyección SQL, la eliminación de la generación automática de tokens en errores de login, la revisión de CORS y de credenciales embebidas. Sobre esto último, una historia ilustrativa de un pentest: un archivo .env.old accesible con la contraseña de la base de datos; el servidor solo aceptaba conexiones por VPN, pero el cuarto eslabón —credenciales válidas— estaba resuelto.

El factor humano: los errores no son de ignorancia

Una idea que atraviesa todo el relato: los grandes incidentes casi nunca nacen de vulnerabilidades exóticas. Nacen de días difíciles, backlogs imposibles, lo que debía hacerse ayer, y de decisiones de negocio donde "primero ganamos plata, después vemos la vulnerabilidad". El programador suele saber; el sistema lo obliga a priorizar otra cosa. Esa es, quizás, la vulnerabilidad más difícil de parchear.

Técnicas y herramientas mencionadas

  • Yrprey: framework vulnerable dedicado exclusivamente a APIs, con ~22 vulnerabilidades y sin documentación.
  • VAmPI y crAPI: frameworks vulnerables de APIs usados como comparación en la tabla de cobertura.
  • OWASP API Top 10: catálogo de fallas en APIs; Yrprey cubre un 41% del mismo.
  • SQL injection vía JSON: inyección en los valores del cuerpo JSON de una petición de login.
  • SSRF (Server-Side Request Forgery): abuso de una validación interna para escanear la red del servidor.
  • BOLA (Broken Object Level Authorization): falla de autorización por objeto que permite leer datos ajenos cambiando el token.
  • Log poisoning: inyección de comandos en archivos de log ubicados en rutas ejecutables.
  • NoSQL: base de datos documental cuyas respuestas sin filtrar expusieron todos los registros en el caso Uber.

Conclusiones

  • Las APIs concentran fallas de autorización (BOLA), exposición de datos y SSRF que suelen explotarse cambiando un solo carácter o parámetro.
  • Los patrones de laboratorio —tokens en errores de login, carpetas creadas por registro, logs ejecutables, versiones de API viejas activas— se repiten con nombres propios en incidentes de empresas globales.
  • Corregir exige tratar datos en origen (consultas preparadas, validación de entrada, revisión de despliegues) y no simplemente ocultar el síntoma.
  • La ausencia de documentación puede ser una virtud formativa: obliga a descubrir la falla en lugar de leer la solución.
