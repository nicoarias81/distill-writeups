Bounty Hunter: automatizar el bug bounty desde un script hasta una plataforma web

Fuente: «Bounty_Hunter - El poder de la automatización en la era de AI - Ignacio Pérez» · ver el video original

  • Video: GEG_w5AhcgY · URL: https://youtu.be/GEG_w5AhcgY · Conferencia: 02_ekoparty · Título original: Bounty_Hunter - El poder de la automatización en la era de AI - Ignacio Pérez

Resumen

Bounty Hunter nació como un script personal para familiarizarse con el bug bounty automatizado y terminó siendo una plataforma web completa, presentada públicamente por primera vez en este evento. El recorrido resume dos ideas que se refuerzan: que la etapa inicial de cualquier caza de recompensas —reconocimiento, descubrimiento de URLs, fuzzing de parámetros, escaneo de vulnerabilidades conocidas— es altamente automatizable, y que hoy construir una herramienta propia ya no exige un equipo de desarrollo.

Todo el desarrollo se hizo con ChatGPT y, en la última parte, Copilot en Visual Studio. El autor no es desarrollador; el vibe coding con IA transformó un hobby en una plataforma con dashboard, integración con plataformas de bug bounty y escaneos que se autoexpanden.

De script a plataforma

La primera versión era un script al que se le pasaba -d (dominio) o -u (URL) y poco más. La idea de lanzar directamente contra programas de bug bounty —propuesta de un compañero de trabajo— cambió el rumbo: módulos de herramientas concentrados en una interfaz, dashboard visual y alertas fáciles de identificar. La versión 2.0 trajo rediseño, nueva pantalla de login, dashboard global y una vista por dominio o URL escaneado de forma manual, además de la vista de proyecto creado desde un programa de bug bounty.

La plataforma corre sobre una instancia de Docker y se despliega creando una cuenta con usuario y credenciales. Una recomendación práctica: recursos de máquina generosos, porque los escaneos corren en segundo plano y se multiplican en simultáneo.

Integración con plataformas de bug bounty

Se integraron HackerOne, Intigriti, Bugcrowd y YesWeHack. Sin API, al menos en esta versión: el intento con la API de HackerOne terminó en frustración, así que se optó por un camino alternativo —un repositorio de GitHub con JSONs que se actualizan cada 8 o 9 horas y que la plataforma consume directamente—. La API queda pendiente para una segunda iteración.

El flujo con un programa público:

  1. La plataforma lista los targets del programa y los segmenta por dominio y por URL.
  2. Se tildan los dominios y URLs que interesan y se manda a escanear.
  3. Se crea un proyecto con los targets seleccionados y arranca el reconocimiento en la instancia de Docker.
  4. A medida que el reconocimiento encuentra URLs, la plataforma amplía el scope automáticamente: cada URL descubierta se convierte en un nuevo target y lanza su propio escaneo en formato URL, sin repetir el reconocimiento de dominio.

El resultado visible en el dashboard: vulnerabilidades clasificadas por criticidad (críticas, high), resultados por herramienta en un formato parecido al output original, y cada hallazgo con sus archivos descargables para revisión posterior o para continuar el trabajo manual con Burp Suite.

La metodología de escaneo

  • Si el escaneo parte de un dominio: descubrimiento de subdominios guardados en una lista; verificación de cuáles tienen servicio HTTP o HTTPS en los puertos por defecto; recolección de todas las URLs de cada sitio; y en cada URL, enumeración de todos los parámetros.
  • Si parte de una URL: arranca desde la mitad del flujo, dado que no requiere reconocimiento de dominio previo.
  • Sobre esa lista de URLs y parámetros se lanza el fuzzing.

La criticidad de riesgo se asigna de forma estática según la herramienta que encuentra el hallazgo:

Criticidad Herramientas
Critical SQLMap, módulo LFI
High/Medium XSS Strike, Dalfox, FAF
Medium TPL Map (template injection)
Low Doble de fase

El arsenal concentrado

Un módulo de Recon gestiona Subfinder, HTTPX, Katana y Asset Finder. Otro módulo de SQLi configura el escaneo con SQLMap, junto a TPL Map para inyección de plantillas. Completan el set: Arjun (parámetros ocultos), Dalfox y XSS Strike (XSS), FAF, GF, QS Replace, Nuclei para escaneos generales, un script propio de preparación de URLs, y un módulo de LFI. Todo el código por detrás es Python.

Limitaciones actuales y road map

  • Recursos y concurrencia: los escaneos se lanzan en simultáneo de forma multihilo; un descubrimiento de 700 URLs en una sola máquina llegó a planchar todo. Las alternativas en discusión —colas de tareas en lugar de multihilo, o infraestructura en la nube— son welcome feedback.
  • Escalamiento horizontal: la pregunta de escanear de forma masiva a través de múltiples VPS no estaba contemplada, pero es una dirección natural.
  • Alertas: están en la lista de refinamientos pendientes.
  • APIs oficiales de las plataformas de bounty, en la segunda iteración.

Una advertencia honesta: esto no es mágico. Contra programas de empresas mega conocidas, donde hay gente de todo el mundo pegándoles constantemente, hacen falta paciencia y esfuerzo manual. El valor de la herramienta está en cubrir la etapa inicial de recolección de información y dejar el terreno preparado.

Conclusiones

  • La etapa de reconocimiento y fuzzeo inicial del bug bounty es lo bastante mecánica para automatizarse casi por completo, incluida la ampliación automática del scope conforme aparecen URLs nuevas.
  • La integración con cuatro plataformas de bug bounty se logró sin APIs oficiales, consumiendo datasets públicos actualizados periódicamente; el código es revisable y las URLs de origen, visibles.
  • Construir una plataforma de este alcance ya está al alcance de un profesional de seguridad sin perfil de desarrollador, usando IA para el vibe coding; el costo se paga en decisiones técnicas de arquitectura (concurrencia, recursos) que conviene abrir al feedback de la comunidad.
  • El proyecto se publica como open source para que crezca con módulos, configuraciones y contribuciones.
