Atacando AWS: de una credencial robada al ransomware sobre S3

Resumen

Comprometer un entorno de AWS no exige zero-days ni herramientas sofisticadas: casi siempre empieza con una credencial filtrada y termina en lo que la imaginación del atacante alcance a hacer. Una vez que alguien tiene acceso a un tenant, el impacto puede ir desde la persistencia silenciosa hasta un ransomware sobre buckets de S3 o la destrucción completa de la cuenta con herramientas como AWS Nuke — un caso real que ocurrió sobre una cuenta de un cliente, ejecutado incluso desde el usuario root.

El camino más interesante no es el impacto final, sino las TTPs intermedias: cómo un atacante se mueve, qué registros deja y qué ventanas de tiempo aprovecha. Recorrer esas técnicas desde ambos lados — la ejecución del ataque y la experiencia del blue team que lo intenta detectar — revela que muchos controles de detección tienen costuras: demoras de CloudTrail, regiones sin cobertura, arquitecturas de notificación frágiles y API calls que casi ningún SIEM monitorea.

Este artículo recorre una cadena de ataque completa sobre AWS: robo de credenciales, acceso a la consola, movimiento lateral entre roles, salto entre cuentas, escalada de privilegios, robo de secretos, evasión de GuardDuty y sabotaje del logging, cerrando con un ransomware real sobre S3 y las defensas que suelen fallar.

El modelo de responsabilidad compartida define el campo de batalla

Antes de atacar conviene entender quién puede ver qué. En infraestructura como servicio (una instancia EC2), todo desde el sistema operativo hacia arriba es responsabilidad del cliente: parches, networking, hardening de la aplicación. En Lambda (software como servicio) el cliente solo ve su código, y en RDS o DynamoDB el control se reparte en niveles intermedios.

Para el defensor esto implica un trade-off: cuanto más SaaS es el componente, menos visibilidad tiene. Cuesta instalar un EDR en una Lambda; el monitoreo queda librado a controles como Cloud Security Posture Management, menos efectivos. Para el atacante, comprometer un componente SaaS reduce drásticamente las probabilidades de ser detectado por controles de endpoint.

El plano de identidad, IAM, administra cómo se interactúa con la cuenta: usuarios de consola, o acceso programático con access keys. La consola web es intuitiva pero ruidosa — genera una nube de API calls de relleno para dibujar la interfaz. El CLI permite movimientos quirúrgicos: una sola llamada, mínima superficie. Un buen indicador de detección surge ahí: un usuario pensado para automatización (Terraform, GitHub Actions) cuyo user agent es Mozilla y que ejecuta ConsoleLogin es comportamiento anómalo que merece alerta.

Los logs siempre llegan tarde

Todo lo que se hace contra AWS es una API call, y esas llamadas quedan en CloudTrail. El Event History de la consola es cómodo y casi en tiempo real, pero solo retiene tres meses: útil para lo táctico, inútil para lo estratégico. El CloudTrail "de verdad" deposita logs comprimidos en un bucket de S3, organizados por región, año, mes y día — un formato que pocos equipos pueden consumir sin un SIEM.

Hay tres ventanas que el atacante explota:

  1. CloudTrail tarda hasta 15 minutos en depositar los logs en el bucket.
  2. El SIEM los levanta por polling, sumando otros minutos.
  3. El equipo responde después de generar y triagear la alerta.

Entre la acción y la primera impresión del defensor pueden pasar treinta minutos. GuardDuty acorta ese camino: se habilita con un clic, usa machine learning, y se integra con EventBridge para notificar casi en tiempo real si el caso de uso está bien configurado. Pero tiene costos: no cubre todo, carece del contexto del negocio, y — como se verá — su pipeline de notificación es tan explotable como cualquier otro componente.

La regionalidad es el multiplicador silencioso. GuardDuty, las reglas y los logs son regionales; los endpoints de S3 son globales. Un atacante que sabe que GuardDuty está habilitado en us-east-1 pero no en us-east-2 puede ejecutar s3 ls --region us-east-2 --no-verify-ssl y que la enumeración complete su logueo en la región oscura. Las regiones que la empresa no usa rara vez tienen casos de uso de detección: son zonas grises donde trabajar tranquilo.

De una credencial a un servidor

Las credenciales de AWS se filtran de las formas más mundanas: el archivo ~/.aws/credentials mal protegido, repos de GitHub, templates de HTML con keys harcodeadas. Un escaneo del corpus de entrenamiento de DeepSeek encontró 12.000 credenciales de este estilo. El malware de TeamTNT, un bash script bien documentado, recoge credenciales del sistema, de Docker, de los archivos de configuración y de las variables de entorno, y las empaqueta como un infosteiller.

Con una access key programática, el primer movimiento es verificar con sts get-caller-identity quién soy, y luego convertir un usuario programático en usuario de consola:

  • iam get-login-profile revela si el usuario puede loguearse por web (los usuarios de automatización no tienen contraseña).
  • iam delete-login-profile + iam create-login-profile le crea una contraseña nueva al atacante.

El resultado: acceso completo a la Management Console con un usuario que nunca debió usarla — y que GuardDuty todavía no marcó. Desde la consola, si una instancia EC2 tiene un role asignado y el puerto 22 expuesto, EC2 Instance Connect permite conectarse por SSH sin tener ninguna llave. La creencia de que "exponer el 22 no importa porque sin la llave no entrás" se derrumba con un botón.

Dentro del servidor aparecen dos botines clásicos:

  • Las SSH authorized keys, donde el atacante agrega su propia llave para persistir desde su workstation.
  • El instance metadata: un curl a una IP interna (169.254.169.254) que expone el AMI ID, los security groups y, sobre todo, las security credentials del role de la instancia.

Esas credenciales incluyen un session token: a diferencia de una access key de usuario — que no rota hasta que alguien la revoca — las de un role tienen expiración. Aun así, son plenamente usables fuera de la instancia, y el role robado puede estar bien jardinizado: existen porque una instancia debe asumirlos. Robar el mecanismo de confianza es distinto de romperlo.

La Instance Metadata versión 2 exige un token previo y cierra el vector más grosero, aunque el token sigue viviendo en el servidor. La defensa de fondo es la misma pregunta de siempre: ¿el servidor necesita tener credenciales? ¿necesita estar expuesto a internet?

Movimiento lateral: roles, trust relationships y salto de cuentas

La escalada natural en AWS es asumir roles. La trust relationship de un role define qué entidades pueden asumirlo; cuando está mal configurada — abierto a toda la cuenta, por ejemplo — un atacante con sts assume-role se convierte en ese role. El beneficio táctico es doble:

  • Rompe la investigación: hasta ahora el defensor filtraba por username: backdoor y veía todo. Después de un assume-role, hay que entender que ocurrió un cambio de identidad y seguir al nuevo principal.
  • Se camufla: todas las API calls de IAM y STS se loguean en us-east-1, donde un AssumeRole es una llamada ruidosísima entre miles. Es fácil de perder y difícil de convertir en detección.

El esquema multicuenta — separar producción, desarrollo, seguridad y datos en cuentas distintas — es la arquitectura recomendada precisamente para contener estos movimientos. Pero si un role tiene permiso para asumir un role en otra cuenta, la barrera cae: de usuario a role, de role a role cross-account, y el get-caller-identity muestra un ARN con número de cuenta distinto. El reconocimiento previo para encontrar estos caminos puede venir del historial de comandos de un servidor comprometido (buscar assume-roles previos), de la enumeración de roles IAM con nombres reveladores, o del pentesting tradicional de numeración.

Permisos, secretos y las 800 variantes de la escalada

Los permisos en AWS son policies. La escalada clásica — agregarle una policy al usuario, o crear una policy nueva — es fácil de detectar porque son API calls conocidas y monitoreadas. Pero hay variantes que casi nadie cubre: modificar una policy existente agregándole statements, o crear una policy version y setearla al usuario. Mismos efectos, API calls completamente distintas, y los casos de uso de detección están pensados para llamadas puntuales.

Con permisos suficientes, los secretos están a un comando de distancia:

  • Secrets Manager: valores como tokens de GitHub o secret access keys, por región.
  • Variables de entorno de Lambdas: webhooks de Discord, API keys de integraciones.
  • User Data de instancias EC2: scripts de arranque con inputs que rara vez se limpian.
  • Buckets de S3 y archivos locales de servidores.

Levantar secretos manualmente dispara a GuardDuty casi seguro — en la demo, el uso del role de la instancia desde una IP externa generó un finding. La respuesta defensiva de fondo es una sola: las identidades de IAM no deberían poder modificar sus propios permisos, ni tocar el entorno de IAM en general. Suena a trivialidad y no lo es; es exactamente lo que buscan las herramientas de posture management cuando preguntan "¿quién tiene la policy de administrador?".

Evasión: no apagar el detector, sabotear el pipeline

Deshabilitar el detector de GuardDuty es la opción grosera: DisableDetector es una API call que todo SIEM con capacidades monitorea. Y tiene un efecto secundario perverso para el atacante — al re-habilitarlo, los findings previos desaparecen, como una consola reseteada — pero también para el defensor: si no hay un explicit deny que impida esa operación, la historia forense se pierde.

La opción elegante ataca la arquitectura de notificación, que casi siempre es la misma:

    G[GuardDuty
findings] --> R[CloudWatch rule
event pattern]
    R --> L[Lambda
notificadora]
    L --> D[Discord / Slack / email]

Cada eslabón de esa cadena es explotable con API calls del ciclo de vida normal del desarrollo:

  • Modificar la Lambda: un UpdateFunctionConfiguration que arruine el webhook. GuardDuty detecta, la regla dispara, el finding nunca llega. La llamada es rutinaria y no exige ningún permiso sobre GuardDuty.
  • Modificar el event pattern de la regla: agregar una condición que excluya los findings provenientes de la IP del atacante. Otro PutRule rutinario.
  • Suppression rules de GuardDuty: crear un filtro que archive silenciosamente todos los findings que matcheen un criterio (la IP pública del atacante, el username). La belleza macabra: desde la Management Console no hay forma de ver las suppression rules — solo aparecen con ListFilters programático. Un equipo que no las monitorea proactivamente nunca se entera de que existe.

El mismo razonamiento aplica al CloudTrail crudo. El bucket donde deposita los logs es un bucket común; su bucket policy — no una policy de IAM — define quién puede hacer PutObject. Quitarle ese permiso a CloudTrail corta el flujo de logs sin generar ninguna alarma: el SIEM deja de recibir datos, el equipo de ingeniería entra en un proceso de debugging largo (¿la integración? ¿la conectividad?), y mientras tanto el atacante trabaja sabiendo que nada se graba. CloudTrail lo nota — el dashboard marca la policy rota y hasta ofrece un botón de fix — pero no alerta: si nadie monitorea activamente el estado de los trails, el silencio puede durar meses. Y el Event History solo retiene tres meses, así que la ventana ciega se vuelve irrecuperable.

Variantes del mismo principio: denegarle al usuario del SIEM el acceso al bucket, ocultar los logs de un día puntual, o bloquear el acceso al Event History de los investigadores durante el ataque.

Ransomware sobre S3: tres API calls y nadie lo vio

El cierre es un ransomware real contra un bucket de S3, escrito con boto3. La mecánica:

  1. Crea una KMS key y una key policy cuyo único owner es un usuario de "ransomware" — ni administradores ni root pueden usar la llave.
  2. Lista los objetos del bucket, los baja, los re-encripta con la llave y los vuelve a subir.
  3. Elimina los rastros y deja un ransom note.

El resultado en la consola: los objetos muestran "Server side encryption with KMS key" y un checksum inaccesible incluso para AdministratorAccess. La única forma de recuperar la data es encontrar al usuario dueño de la llave.

Lo escalofriante es la detección — o su ausencia. CloudTrail registró exactamente tres API calls del usuario del ransomware: CreateKey, PutKeyPolicy y GenerateDataKey. ¿Por qué no se ven los GetObject y PutObject sobre los objetos? Porque los data events de S3 — el logueo de operaciones sobre objetos individuales — no vienen habilitados por defecto. Sin esa configuración, un proceso que encripta todo un bucket es invisible para CloudTrail y Event History. Encima, la bucket policy del propio bucket de CloudTrail pudo haber sido saboteada antes, y una suppression rule sobre el username del ransomware habría silenciado a GuardDuty para siempre.

El versioning de S3, mencionado durante la demo, habría salvado los objetos: es una de las pocas líneas de defensa que operan fuera del plano de permisos.

Conclusiones

  • El hardening debe pensar en el edge case, no en el atacante tradicional. Cada componente de la cadena defensiva tiene que ser tan duro como la cadena: si GuardDuty importa, importan los permisos IAM sobre GuardDuty, las reglas de CloudWatch, las Lambdas notificadoras y la bucket policy del bucket de CloudTrail. "Todo está bien" es la mejor metáfora del problema: la alerta grosera es la única que todos tienen, y el atacante sofisticado no opera ahí.
  • Las identidades de IAM no deben poder auto-modificarse, ni tocar el plano de IAM, el detector de GuardDuty ni la infraestructura de notificación. Las SCPs (aunque su cuota es limitada), Control Tower — bloqueando servicios fuera del stack tecnológico — y AWS Config para trazar y revertir cambios son los mecanismos concretos.
  • Los data events de S3 deben habilitarse explícitamente para los buckets críticos, y el estado de los trails debe monitorearse activamente: CloudTrail avisa las policies rotas pero no alerta.
  • La regionalidad es un blind spot estructural: cubrir todas las regiones con detección, o al menos las que tienen endpoints globales como S3, y vigilar la actividad en las regiones "sin uso".
  • GuardDuty vale la pena, pero no basta solo: se habilita con un clic, carece de contexto del negocio, y su valor depende de que el pipeline de notificación — reglas, Lambdas, suppression rules — esté monitoreado como un activo de primer orden.
