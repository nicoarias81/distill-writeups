Análisis de seguridad en apps móviles: herramientas y técnicas (Android)

Resumen

Workshop de arranque para analizar aplicaciones Android: qué es un APK y cómo está armado, cómo montar el entorno (emulador, ADB, proxy), cómo descompilar y reconstruir la aplicación, y qué vulnerabilidades buscar primero — desde credenciales hardcodeadas hasta deep links mal validados. La meta: poder hacer un análisis cabal con un set básico de herramientas bien elegidas, sin marearse con las cientos que existen.

Anatomía de un APK

Un APK es esencialmente un zip: un empaquetado de archivos que se puede descomprimir. Los puntos clave:

  • Nombre de paquete: cada app se identifica con su package (por lo general com.<nombre>), que además define su ruta de instalación /data/data/<paquete>/, donde pueden quedar archivos con información sensible.
  • Sandbox: cada aplicación corre aislada del resto.
  • Android Manifest (XML): el primer archivo que se mira. Declara activities (clases que manejan las pantallas), servicios (tareas en background sin UI), broadcast receivers (reaccionan a eventos del dispositivo, como un cambio de red o un mensaje entrante), content providers (comparten datos entre apps o exponen una base de datos propia) y web views (un navegador dentro de la aplicación). Los escáneres empiezan por acá buscando malas configuraciones.
  • Cadena de compilación: .java → .class (JVM) → .dex (Dalvik) → binario; desde Android 5, ART reemplaza a Dalvik. El reversing es el camino inverso: desde el paquete compilado, intentar recuperar los .java lo mejor posible.
  • Carpeta de recursos (res): strings.xml suele esconder credenciales, API keys y URLs hardcodeadas — a veces de ambientes de testing que no deberían estar en producción. Los assets pueden contener JavaScript analizable, y las librerías son otro mundo para quienes gustan del reversing profundo.

Armando el entorno

  • Emulador: Android Studio trae el suyo, pero Genymotion permite levantar solo el emulador sin el IDE completo. Recomendación: empezar con versiones viejas (Android 5, 7, 8 — menos protecciones, intercepción de tráfico más fácil) y modelos Pixel o Nexus (menos customizaciones). OpenGaps como plugin para bajar apps de la Play Store.
  • Dispositivo físico: no hace falta que esté rooteado. Siempre uno de pruebas, nunca el personal.
  • ADB: viene con Android Studio (Platform Tools) o se baja aparte. Si adb devices no funciona, revisar USB debugging y la ruta del comando en la PATH. Con adb shell pm list packages + grep se encuentra el nombre del paquete; con adb shell pm path <paquete> la ruta del APK, que se trae con adb pull. adb push lleva archivos al dispositivo (ideal para manipular cosas en memoria sin exploradores ni cables raros).
  • Obtener la APK: pedirle la versión final al cliente, descargar de sitios de APKs (verificando siempre en VirusTotal antes de instalar nada, en un ambiente de pruebas), o extraer la instalada. Los archivos .aab de Play Store se convierten con Bundletool en un .apks (un zip de APKs optimizadas), del que se extrae e instala la base APK.

Intercepción de tráfico

El proxy (Burp Suite como estrella, aunque hay varios) se interpone entre el dispositivo y el backend, rompe la confianza y permite ver y manipular requests y responses: tanto modificar lo que sale hacia el servidor como alterar la respuesta antes de que llegue a la app, para ver si habilita pantallas o funcionalidades ocultas.

Pasos y trampas:

  1. Desde Android 7, las apps ya no confían en certificados de usuario por defecto. Hay que editar el Network Security Config (XML en res/xml) para que confíe en certificados de usuario — y verificar que el manifest lo invoque en la tag <application>. En Android 5 y anteriores no hace falta.
  2. Exportar el certificado del proxy en .der; si el dispositivo no lo toma, renombrarlo a .cer, instalarlo desde la tarjeta SD (tipo VPN/app) y nombrarlo distinto si ya existe otro para que no lo pise.
  3. En dispositivo físico: Burp escuchando en todas las interfaces (el asterisco junto al puerto), y el celular en la misma red Wi-Fi que la computadora — el fallo clásico es configurar todo perfecto y descubrir que el celular estaba en otra red o usando datos.
  4. En emulador Genymotion (versiones recientes): el comando adb settings que apunta al proxy — sin eso no intercepta nada por más que la configuración sea idéntica a la del celular.

Si aun así no se intercepta, la app probablemente usa SSL pinning: fija el certificado del servidor dentro de la aplicación para rechazar cualquier intermediario. Se rompe de forma manual (reversing + recompilar) o automatizada con scripts de Objection o Frida (con Magisk en dispositivos rooteados). Filtrando en el código por CertificatePinner y similares se descubre si hay pinning y con qué librería está implementado — a veces encadenadas, lo que complica el bypass.

Reversing: decompilar y recompilar

  • Jadx (GUI): abre la APK, descompila, intenta desofuscar, y muestra smali y Java lado a lado. Un Ctrl+Shift+F global permite buscar strings, credenciales, métodos y ver quién invoca a quién. Posicionarse en com.<paquete> y analizar desde ahí; después el resto. Con la APK decompilada localmente, también puro Linux: grep -iR filtrando hasta en binarios.
  • APKTool: apktool d descompila (y sirve para el Network Security Config); apktool b recompila (usar la versión del framework indicada o falla; el resultado queda en dist/). Después de rebuild: zipalign primero y recién entonces firmar (zipalign después de firmar rompe la instalación), generando el keystore con keytool y firmando con apksigner.
  • Al recompilar con código descomentado o modificado y reinstalar, se pueden habilitar funcionalidades ocultas que no estaban productivas.

Qué buscar: el catálogo de hallazgos

En el manifest, tag <application>: debuggable en true (los logs aparecen por defecto), allowBackup en true (backup manual de una app productiva), usesCleartextTraffic (tráfico sin cifrar), y activities exportadas — otra aplicación o un proceso externo puede invocar pantallas internas que deberían estar protegidas por capas previas.

  • Logs: adb logcat filtrado por el PID de la app (primero ps para obtenerlo, después logcat del proceso). Desarrolladores dejan credenciales, tokens de sesión, peticiones y responses impresas como console.log — en CTFs siempre hay algo en logcat, y en producción es mala práctica grave.
  • Credenciales hardcodeadas: filtrar por password, username, token, cookies; también URLs de servicios internos o de testing.
  • SharedPreferences con username o password sin cifrar: mala configuración directa.
  • Deep links mal validados: las rutas internas de la app pueden llevar parámetros (se detectan buscando getExtras). El caso tipo: una web view que recibe un parámetro de URL y solo valida que no sea nulo — se puede invocar la activity desde la computadora con adb shell am start pasando el parámetro (--es url <sitio>) y la app navega donde uno quiera. Si en esa URL viaja información sensible (tokens de sesión que quedan pegados en sucesivas navegaciones), es una vulnerabilidad válida — en pentest, siempre reportable; en bug bounty, depende del programa.
  • Validaciones de host incompletas: la app valida que la URL termine en su dominio (el famoso endsWith) sin revisar protocolo, subdominio ni ruta completa. Un deep link hacia un dominio que solo comparte el sufijo la bypasea. Estas validaciones son muy comunes.
  • Web views: XSS e inyecciones, y configuraciones que permiten acceso a archivos locales. Filtrar por URI, URL, https para mapear hacia dónde navega la app.

MobSF y Objection: automatización con criterio

MobSF levanta una interfaz web local: se sube la APK y produce un diagnóstico completo — activities exportadas, servicios insecuros, strings de URL, comunicación insegura, permisos mal usados o excesivos, análisis del manifest con los problemas señalados, verificación de firma, código smali, hasta descargar la APK de nuevo. El aviso importante: un diagnóstico no es un pentest. Que el escáner marque una activity exportada no significa que sea explotable — puede tener protecciones que impiden el ataque desde afuera. Siempre hay que ir y explotar cada hallazgo para comprobarlo; entregar el PDF de MobSF como "reporte de pentest" no es un pentest.

Objection funciona incluso en dispositivos no rooteados: parcha la APK inyectando un gadget de Frida (detecta solo la arquitectura y la versión a descargar), se instala la app parcheada y se maneja desde la computadora. Trae scripts incorporados — incluida la ruptura de SSL pinning — y permite inspeccionar archivos, variables de entorno, hacer dump de memoria, y revisar las bases de datos locales por información sensible. En dispositivos rooteados, el esquema clásico: Frida Server en el dispositivo, cliente en la computadora. Se pueden además importar scripts de Frida dentro de Objection.

Conclusiones

  • El análisis de una app Android empieza por entender su estructura (manifest, recursos, componentes) y montar un entorno reproducible: emulador con versiones viejas, ADB funcionando, proxy configurado con el certificado instalado.
  • La intercepción de tráfico tiene una secuencia fija: Network Security Config → certificado → misma red → (si hay) romper el pinning. Casi todos los "no me intercepta nada" tienen causa en uno de esos cuatro puntos.
  • Los hallazgos de mayor rendimiento inicial son previsibles: logs con datos sensibles, credenciales hardcodeadas en strings.xml o el código, SharedPreferences sin cifrar, activities exportadas y deep links con validaciones de URL incompletas.
  • Los escáneres como MobSF son un punto de partida, nunca el entregable: sin explotación comprobada, no hay pentest.
