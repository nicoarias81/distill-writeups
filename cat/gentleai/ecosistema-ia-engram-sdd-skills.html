Resumen

La mayoría de los desarrolladores usa los agentes de IA muy por debajo de su potencial. Cada sesión arranca de cero: no hay memoria de decisiones anteriores, no hay skills, no hay workflow —preguntarle cosas a un chat con herramientas de archivos— y no hay coordinación entre sesiones ni entre agentes. El ecosistema descrito aquí (el stack de Gentle AI) ataca esos cuatro huecos sin instalar agentes nuevos: potencia los que ya se usan.

La premisa es "un comando, cualquier agente, cualquier sistema operativo": soporte nativo para Windows (sin WSL), varias distribuciones de Linux y macOS, y compatibilidad con Gemini CLI, Claude Code, OpenCode, Codex, Cursor y VS Code. Todo el stack es open source y está pensado tanto para individuos como para equipos que quieren algo que funcione sin tunear configuraciones.

El stack combina cuatro piezas: Engram (memoria persistente), SDD (desarrollo dirigido por especificaciones), skills (contexto particionado) e integraciones MCP (Context7 para documentación, Notion, Jira). Además instala una persona configurable en el agente, con un objetivo explícito: que no solo responda sino que enseñe, pregunte el porqué de cada decisión y no escriba código sin contexto. Para alguien junior es, literalmente, una forma de aprender: con human in the loop, sin dejar que la IA lo haga todo.

El problema de la compactación y la economía de tokens

La ventana de contexto es finita. A medida que el chat crece y el agente lee y edita archivos, se llena, y entra en juego la compactación: se resume todo lo conversado, se abre una sesión nueva y se continúa con ese resumen. El problema es que en esa compactación se pierden cosas.

La respuesta del stack es un orquestador principal que delega todo el trabajo sucio en subagentes. Cada subagente arranca con una página en blanco y una tarea concreta; el hilo de la conversación se queda en el orquestador, sin ruido. Las mediciones publicadas en el repositorio reportan un ahorro de entre 50% y 70% de tokens con este esquema.

La delegación tiene un beneficio adicional: empezar en blanco es excelente para un agente. No hay historial contaminando el trabajo, hay menos errores y menos tokens gastados en re-leer contexto irrelevante.

Las skills siguen siendo la unidad de partición de contexto: si algo es repetitivo o muy particular del proyecto, es candidata a skill. Pero acá van un paso más allá: cada fase de SDD es en sí misma una skill, y cada subagente puede cargar skills dentro de sí. No es "andá y creá este archivo": es delegar un proceso de trabajo entero.

Engram: el cerebro con acceso por capas

Engram es un servidor escrito en Go con una base SQLite local y un servidor MCP al que se conecta cualquier agente. Su función: aprender de las conversaciones. Cada decisión tomada, cada bug encontrado (dónde estaba, cómo se arregló, qué se aprendió), cada observación de arquitectura queda registrada para que una sesión futura —o un compañero— la encuentre.

El acceso a la información es por capas, lo que lo hace eficiente en tokens: primero busca si hay información del proyecto; si la hay, busca tipos de acciones y observaciones relacionadas; solo si encuentra algo relevante va por el detalle completo. Es una búsqueda en embudo, no un volcado de contexto.

Dos propiedades importantes:

  • Privacidad: si en el contenido se detecta una clave secreta, se marca como privado y se filtra en Go antes de llegar a la base de datos.
  • Sincronización: engram sync empaqueta la memoria por proyecto (comprimida, con manifiesto para versionado); un compañero hace pull e importa, y hereda las observaciones de las sesiones ajenas. Las especificaciones de OpenSpec también pueden guardarse en Engram, útil cuando el proyecto es público y no se quiere versionar las specs en el repositorio.

El roadmap incluye Engram Cloud: la misma memoria en un servidor, con varios desarrolladores sincronizando automáticamente sus observaciones a la nube. Cada dev guarda en local un caché que sube al servidor, y un dev nuevo llega con todo el contexto disponible. Como es MCP sobre un binario Go, funciona con cualquier IDE o agente.

Qué cambia con y sin el ecosistema

Sin el ecosistema: se pierde contexto entre sesiones, se repiten bugs ya resueltos, se re-dicen decisiones ya tomadas, el onboarding de una persona nueva lleva días, se desperdician tokens en preguntas y vueltas atrás, y cada developer configura la IA de manera distinta (resultados inconsistentes).

Con el ecosistema: la sesión se mantiene en memoria persistente, el agente retoma con contexto previo, el onboarding baja a menos de un día, el ahorro de tokens es significativo, y todo se instala con un comando idéntico para todo el equipo.

Instalación y modelos por fase

El instalador (distribuido vía Homebrew tap, con variantes para PowerShell en Windows y scripts para Linux/Mac) detecta el sistema operativo, las herramientas y las dependencias, hace backups de instalaciones previas, y solo exige dos prerrequisitos: Go y npm. Ofrece elegir la persona del agente (estilo propio, neutro o custom) y el alcance: full (todo), solo ecosistema (memoria, SDD, skills, documentación) o mínimo (solo Engram).

Para OpenCode existe un modo multi notable: elegir un modelo distinto para cada fase de SDD, entre todos los proveedores conectados. Las recomendaciones para cada fase:

  • Inicializar y explorar: Sonnet; no exige mucho.
  • Propuesta: modelo de alto razonamiento — Opus o Gemini (Gemini razona muy bien y cuesta alrededor de $2 por millón de tokens de salida frente a $5.25 de Opus).
  • Especificaciones: Google, porque la escritura tiene que ser buena.
  • Diseño: Opus, razonamiento técnico puro.
  • Tareas: modelo liviano alcanza.
  • Implementar: Sonnet.
  • Verificar: Codex; los modelos de OpenAI son excelentes descubriendo bugs.
  • Documentar y archivar: cualquiera, algo liviano.

Una advertencia transversal: Gemini es malo para implementar a nivel de herramientas —llega a inventar herramientas que no existen en la máquina y tira errores—; es excelente para razonamiento y documentación, no para ejecutar.

El flujo diario: lenguaje natural, no comandos

Una objeción habitual es "¿tengo que aprender comandos de SDD?". No: la mejor interfaz es lenguaje natural. Se puede decir "implementá un componente con SDD" y el agente inicia el proceso, o simplemente pedir una implementación y que el agente proponga hacerlo con SDD si la tarea lo amerita. Lo mismo con Engram: no se borra ni se administra a mano; la IA decide qué guardar y cuándo.

En Claude Code, tras instalar el stack, el orquestador de SDD pasa a ser el agente por defecto. Puede lanzar varios subagentes simultáneos y asíncronos: mientras uno explora el codebase (con su propia ventana de contexto, sin mover la del orquestador), el usuario sigue trabajando. En OpenCode el orquestador se elige con un tab, y el modelo del orquestador tiene que ser potente: es quien sostiene la orquestación de subagentes, y un modelo liviano no da abasto.

Un ejemplo del comportamiento esperado: pedirle "hacé un componente nuevo en React" sin más detalle devuelve preguntas, no código —¿reutilizable o de feature?, ¿qué hace?, ¿en qué pantalla vive?—. El agente está diseñado para obligar a definir la arquitectura antes de escribir una línea.

Filosofía: descubrir los límites y mantener al humano en el loop

Dos ideas cierran el enfoque. La primera: la IA no tiene límites conocidos; los límites hay que descubrirlos usándola hasta el punto donde sea contraproducente. La anécdota que lo ilustra: el creador de Claude Code pasaba horas debugueando con herramientas de profiling un problema de memoria, como siempre lo había hecho; alguien menos experimentado le preguntó por qué no lo hacía con la IA, y en 15 minutos el problema estaba identificado y resuelto.

La segunda: revisar el código siempre. Validar cada fase de SDD antes de pasar a la siguiente, meter al humano en el loop del proceso. El usuario es el orquestador del orquestador: lleva la rienda, y un agente bien configurado no deja avanzar con instrucciones sin pies ni cabeza.

Técnicas y herramientas mencionadas

  • Gentle AI stack: instalador único multi-OS/multi-agente del ecosistema completo, vía Homebrew tap o scripts.
  • Engram: servidor Go + SQLite + MCP de memoria persistente, con búsqueda por capas, filtrado de secretos y sincronización entre devs.
  • Engram Sync / Engram Cloud: exportación de memoria por proyecto vía Git y sincronización centralizada en servidor (roadmap).
  • SDD (spec-driven development): desarrollo por fases basado en especificaciones, inspirado en openspec.dev; cada fase es una skill.
  • Modo multi de OpenCode: modelo distinto por fase de SDD (Sonnet para implementar, Opus/Gemini para proponer, Codex para verificar).
  • Skills: contexto cargado por necesidad; los subagentes de SDD son skills que a su vez cargan skills.
  • Orquestador + subagentes: delegación con página en blanco; 50-70% de ahorro de tokens medido.
  • Compactación: resumen de sesión al llenarse la ventana de contexto; el mecanismo que el stack busca evitar.
  • Context7: MCP recomendado para consultas de documentación.
  • Integraciones MCP: Notion y Jira accesibles desde el agente.
  • Gemini CLI, Claude Code, OpenCode, Codex, Cursor, VS Code: agentes/IDEs soportados.

Conclusiones

  • El 90% de los desarrolladores desperdicia el potencial de los agentes: sin memoria, sin skills, sin workflow y sin coordinación. El stack cierra esos cuatro huecos sin reemplazar las herramientas existentes.
  • La delegación a subagentes con página en blanco es la palanca principal de ahorro de tokens: el orquestador conserva el hilo, los subagentes queman contexto que no vuelve.
  • Engram convierte las conversaciones en memoria institucional del proyecto: decisiones, bugs y observaciones de arquitectura sobreviven a la sesión y viajan entre compañeros vía sync.
  • Elegir el modelo por fase (razonar caro, ejecutar barato, verificar con modelos fuertes en detección de bugs) rinde más que usar un único modelo para todo.
  • El humano sigue en el centro: lenguaje natural para disparar procesos, revisión de código obligatoria, y un agente configurado para enseñar y cuestionar en lugar de obedecer a ciegas.
