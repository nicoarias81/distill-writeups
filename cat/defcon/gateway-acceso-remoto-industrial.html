Cerrajería industrial: cómo un gateway de acceso remoto "seguro" cayó en cadena

Fuente: «DEF CON 32 - Unlocking the Gates Hacking a secure Industrial Remote Access Solution - Moritz Abrell» · ver el video original

  • Video: fc6c2hP86Wk · URL: https://youtu.be/fc6c2hP86Wk · Conferencia: 01_defcon · Título original: DEF CON 32 - Unlocking the Gates Hacking a secure Industrial Remote Access Solution - Moritz Abrell

Resumen

Las soluciones de acceso remoto industrial son el cordón umbilical entre los técnicos de mantenimiento y las plantas: un dispositivo de la red industrial abre un túnel VPN hacia un servidor del fabricante, y el técnico se conecta desde fuera a través de ese túnel. Comprometer ese puente significa tocar energía, plantas industriales, plataformas petroleras y demás infraestructura crítica.

El objetivo del análisis fue el Ewon Cosy+ de HMS, un gateway usado a gran escala —el fabricante declara más de medio millón de dispositivos conectados— y vendido como seguro por diseño: hardware security module con root of trust, certificados individuales, secure boot y un certificado de auditoría independiente publicado en la web del fabricante. Con ficheros de firmware cifrados, el enfoque fue puramente black box sobre el software expuesto.

El resultado fue una cadena completa: de un XSS persistente a root en el dispositivo, de root a la descifrado de contraseñas y firmware, y de ahí a la suplantación de certificados que permitía secuestrar sesiones VPN de dispositivos ajenos —con más de 500.000 equipos potencialmente afectables—. El fabricante parcheó el backend de inmediato y publicó firmware corregido.

De fichero OpenVPN a shell root

El primer vector fue sorprendentemente directo: el dispositivo acepta subir configuraciones OpenVPN personalizadas, y OpenVPN admite ejecutar comandos con el parámetro up. El parámetro estaba en una lista negra, pero el filtro se burló duplicando los guiones —--up— sin romper la semántica del parámetro. Con una configuración que incluía una reverse shell, el comando se ejecutó con privilegios root.

La condición es tener acceso administrativo al gateway, así que hacía falta un vector previo de escalada hacia el panel. Se encontró en un XSS persistente originado en los intentos de login FTP: las credenciales fallidas quedan registradas y, cuando un administrador visita la página de logs, el JavaScript inyectado se ejecuta en su navegador. Para colmo, la cookie de sesión contenía la contraseña administrativa en texto plano, simplemente codificada en base64. El problema del plaintext en cookies ya se había reportado en 2015 para un dispositivo similar del mismo fabricante.

Criptografía a medias: contraseñas y firmware descifrados

Con root en el dispositivo llegó la pregunta clave: ¿se podían descifrar los datos sensibles? Las contraseñas de los ficheros de configuración se cifraban con funciones OpenSSL bien conocidas, y la clave y el IV estaban incrustados en la sección de datos de solo lectura de un binario ARM. Reimplementando el algoritmo, cualquier contraseña cifrada se vuelve legible.

El firmware de actualización usaba una protección mayor: el hardware security module, un EdgeLock de NXP. Analizar el bus I2C pasivamente mostró que los comandos APDU viajaban en claro pero el payload iba cifrado, así que espiar la conexión física no servía. Intentar extraer claves directamente con el middleware Plug & Trust tampoco funcionó: las políticas del HSM estaban bien configuradas.

La vía fue reconstruir el proceso de descifrado desde el firmware mismo: se leen 4 bytes de una memoria flash sin cifrar que indican la longitud del bloque siguiente, ese bloque se descifra con el módulo criptográfico del i.MX6, y de ahí se derivan claves de sesión AES-CBC para la comunicación. Para las actualizaciones: el fichero contiene un tipo de clave, una clave e IV cifrados que el HSM descifra, y un script bash cifrado que se desencripta con esa clave en claro; el script extrae y descifra cada parte del firmware. Consecuencia: cada versión de firmware tiene su propia clave, pero un dispositivo rooteado puede descifrarla y, con ella, todo el paquete de actualización —incluido el sistema de ficheros raíz—.

El golpe final: certificados firmados para dispositivos ajenos

La comunicación con el backend del fabricante usa TLS con autenticación mutua. Instalar un proxy TLS exige que el gateway confíe en el certificado del analista —trivial, el trust store está incrustado— y que el backend confíe en el certificado cliente. Este último resultó inalcanzable: la ruta a la clave privada estaba incrustada, pero el fichero contenía una "reference key", un puntero a la clave real guardada dentro del HSM.

La solución fue usar la configuración de OpenSSL que referencia un engine que implementa el HSM: con ella, herramientas conscientes de OpenSSL como curl podían hablar con el backend desde el propio dispositivo. Sin la clave privada exportable no hay proxy posible, así que el análisis se hizo por reconstrucción: interceptar una petición del dispositivo, repetirla con curl, capturar la respuesta, reimplementarla en un servidor propio y avanzar a la siguiente petición.

Así se mapearon los endpoints y apareció el flanco letal: durante la asignación de cuenta, el dispositivo genera una certificate signing request, el servidor del fabricante la firma, y el certificado firmado —que contiene el número de serie del dispositivo— se usa para autenticarse ante el servidor VPN. El número de serie dentro del certificado es lo que asigna la sesión VPN a una cuenta.

La pregunta era obvia: ¿se puede obtener un certificado firmado con el número de serie de otro dispositivo? Con un serial proporcionado por el propio fabricante para la prueba, la CSR se generó con ese serial ajeno y se envió desde el dispositivo rooteado. La petición fue aceptada y el certificado se usó para abrir una sesión VPN en nombre del dispositivo del laboratorio del fabricante.

Impacto: medio millón de puertas que se pueden cerrar de golpe

El secuestro de sesión VPN tiene un efecto en cascada demoledor:

  • La sesión VPN del dispositivo original se sobrescribe y queda inaccesible.
  • Cualquier usuario que intente conectar a ese número de serie es redirigido —sin darse cuenta— al atacante.
  • Por la ausencia de restricciones de red dentro del túnel, el atacante accede a todos los servicios del cliente conectado: escritorio remoto, PLCs, autenticación, carga de programas secretos.
  • El atacante puede imitar la infraestructura original y espiar datos sensibles.

Y como los números de serie son enumerables en la práctica, el ataque es escalable: la capacidad de desconectar y suplantar dispositivos alcanza a más de medio millón de instalaciones de todo el mundo. El fabricante parcheó el backend de inmediato —ya no es posible obtener certificados para seriales ajenos— y publicó una versión de firmware corregida.

Técnicas y herramientas mencionadas

  • Ewon Cosy+ (HMS): gateway de acceso remoto industrial, objetivo del análisis por su base instalada y sus declaraciones de seguridad.
  • OpenVPN up / --up: parámetro de ejecución de comandos; el doble guion burló la lista negra del dispositivo.
  • XSS persistente vía logs FTP: inyección de JavaScript que se ejecuta cuando el administrador revisa la página de logs.
  • Cookie con contraseña en base64: credencial administrativa expuesta en texto plano codificado.
  • EdgeLock (NXP) y Plug & Trust: HSM y middleware; el HSM protege claves pero su flujo de derivación fue reconstruible.
  • i.MX6 CAAM: módulo criptográfico del SoC usado en la derivación de claves de sesión.
  • AES-CBC y OpenSSL: primitivas de cifrado con clave y IV incrustados en el binario ARM.
  • Reference key / OpenSSL engine: mecanismo por el que la clave privada vive solo en el HSM y solo es usable vía engine.
  • CSR con serial ajeno: certificado firmado por el backend con el número de serie de otro dispositivo; pivote del secuestro VPN.

Conclusiones

  • Las declaraciones de "seguro por diseño" —HSM, secure boot, auditoría externa— no eliminan la superficie de ataque del software expuesto: una lista negra eludible y un XSS bastaron para root.
  • Obtener root en el gateway abre la puerta a descifrar contraseñas, claves de firmware y a manipular la identidad criptográfica del dispositivo; proteger solo las claves, no el flujo que las usa, es insuficiente.
  • Un esquema de confianza basado en el número de serie firmado dentro del certificado, sin validar la procedencia de la CSR, permite suplantar dispositivos a escala industrial.
  • Las soluciones de acceso remoto concentran un riesgo desproporcionado, especialmente cuando el backend corre en la nube o en manos de terceros: comprometerlas puede dejar inaccesibles plantas enteras y exponer a quienes conectan.
  • Para investigadores: hallar el "initial foothold" correcto —aquí, un fichero de configuración subible— desbloquea vulnerabilidades que probablemente existan también en otras soluciones del sector.
