Relative Path File Injection: cuando la confusión de rutas sirve cualquier archivo

Fuente: «Relative Path File Injection: The Next Evolution in RPO - Ian Hickey» · ver el video original

  • Video: 3y_6oSZwLr0 · URL: https://youtu.be/3y_6oSZwLr0 · Conferencia: DEF CON 32 (AppSec Village) · Título original: Relative Path File Injection: The Next Evolution in RPO - Ian Hickey

Resumen

Ian Hickey, desarrollador de edtech (no de seguridad), presenta una evolución del clásico Relative Path Overwrite (RPO, Gareth Hayes, PortSwigger Research, 2014). Donde RPO confundía al navegador para interpretar una página HTML como hoja de estilos CSS, su técnica — Relative Path File Injection (RPFI) — explota la misma confusión de rutas para que un enlace de descarga con ruta relativa sirva, en lugar del archivo pedido, la página HTML actual contaminada con contenido inyectado persistente. La clave está en los parsers tolerantes: formatos que no les importa lo que hay antes o después de su contenido útil — PDF, scripts de shell, lenguajes de plantillas del lado del servidor — pueden ejecutar el HTML envenenado como si fuera el archivo esperado.

De RPO a RPFI: el razonamiento

  • RPO (2014): con inyección de CSS en una página vulnerable a confusión de rutas, el <link> por defecto interpreta la página HTML actual como CSS; en IE viejo, expression() permitía ejecutar JavaScript desde CSS.
  • Punto de partida: los labs imposibles de PortSwigger — contextos HTML donde el navegador no ejecuta JavaScript, como <noscript> o <noframes> dentro de <frameset>, que tratan todo lo inyectado como texto plano.
  • Primera observación: ahí AngularJS sí ejecuta (aunque esté EOL) si se instancia dentro de esos tags. Lección: usar parsers ajenos al navegador que no respetan sus reglas y además son lenientes — encuentran su contenido útil aunque esté rodeado de HTML.
  • Segunda epifanía (PDF): los PDF se pueden escribir a mano como texto plano (comienzan y terminan con caracteres mágicos, y les da igual lo que haya alrededor). Un HTML con PDF inyectado persistente, guardado como .pdf, se abre como PDF y ejecuta su JavaScript.
  • El problema de la entrega: nadie descarga un HTML renombrado a PDF voluntariamente. La solución viene de reutilizar la confusión de rutas de RPO.

El vector: confusión de rutas + descarga relativa

  • Escenario: una página vulnerable a inyección de contenido persistente (p. ej. el blurb público de un perfil) en un servidor que, al añadir una barra final a la URL, devuelve la página actual (comportamiento típico, p. ej. del servidor PHP por defecto). Señal rápida de vulnerabilidad: añade / al final de la URL y si la página pierde el estilo, el servidor tiene confusión de rutas.
  • Requisitos del ataque:
  • Un <a> (ancla) con ruta relativa al archivo a descargar (el análogo del <link> relativo de RPO).
  • El atributo download con nombre explícito (p. ej. sample.pdf) — si no, el Content-Disposition no cuadra y el navegador no descargará el HTML como PDF.
  • Inyección de contenido persistente del formato objetivo en la página.
  • Mecánica: la víctima pulsa un enlace de descarga legítimo de un sitio de confianza; con la barra final, el servidor devuelve la página contaminada en vez del archivo; el navegador la descarga como PDF. Al abrirla, se ejecuta el contenido malicioso, no el documento esperado.
  • Impacto amplificado: si es un sitio de biblioteca de PDFs, cada enlace de descarga relativa de la página sirve el mismo PDF malicioso. Y la víctima no nota nada raro: es un servidor de confianza que visita desde hace años — equivalente funcional a haber reemplazado un archivo dentro del servidor.

Más allá del PDF: parsers lenientes por todas partes

Con Gareth Hayes (RPO) y Orange Tsai (maven de polyglots; su tarjeta de visita es un PDF que además arranca en un emulador de Super Nintendo) como caja de resonancia, Hickey exploró qué otros formatos toleran HTML alrededor:

  • Scripts de shell: los shells también son lenientes — ejecutan línea a línea, fallando en lo que no entienden. Si la víctima descarga "un script" para ejecutarlo como superusuario (el consejo habitual de todo tutorial) y el enlace es relativo, puede recibir el HTML envenenado: WSL2 y PowerShell ejecutan el HTML línea a línea fallando hasta llegar al comando inyectado (echo hello world y lo que venga después), y luego lo ejecutan. En shells Linux puros lo más cercano exige inyectar contenido justo tras <html>; en macOS/Linux es factible vía launch commands de Foxit PDF Reader (que lee y ejecuta su propio archivo).
  • Lenguajes de plantillas del lado del servidor (PHP, Ruby, ColdFusion...): esperan HTML alrededor de su código, así que el archivo contaminado ejecuta sin queja. Demo en vivo: la descarga "segura" de un PHP imprime welcome user; la versión con / final ejecuta el código inyectado (welcome bad guy — que podría ser leer un archivo de contraseñas y enviarlo a cualquier parte).
  • HTML sobre todo: el parser más leniente de todos — si inyectas tags que no le gustan, los despoja y sigue. Esto da el salto sin descarga: con los frameworks HTML-over-the-wire (Livewire, Hotwire, HTMX), que traen fragments de HTML del servidor para inyectarlos en el DOM, un fetch a la URL confundida trae la página envenenada, el navegador despoja el <frameset> y el framework inyecta el resto automáticamente. Contextos que antes parecían inocuos (contenido tratado como texto) se vuelven explotables.

Mitigaciones

  • Rutas no relativas: usar <base> o rutas root-relative (barra inicial) para que los enlaces no dependan del path actual.
  • Revisar el servidor: comprobar si añadir / al final de la URL rompe el estilo de la página — indicador directo de confusión de rutas (el servidor PHP por defecto la tiene).
  • Content Security Policy y el resto del estándar de mitigaciones.
  • Educación de usuarios: no se puede confiar en una descarga de archivo servida por ruta relativa.

Cierre

  • Repositorio con los PoCs: ian-hickey en GitHub; muchas variantes sin descubrir ("nadie ha buscado nunca estas vulnerabilidades") — terreno fértil para bug bounty: decenas de formatos lenientes candidatos, y el caso de shell scripts en Linux queda abierto.
