Robar la PRT cookie en macOS y persistir en Entra ID: tres técnicas, registro de dispositivo falso y el bypass de NGC MFA

Resumen

La Primary Refresh Token (PRT) es la llave maestra del single sign-on de Microsoft: representa la identidad del usuario y la identidad del dispositivo, y con ella se pueden canjear tokens para cualquiera de los cientos de servicios de Microsoft — incluidos los claims de MFA y de dispositivo confiable que hacen pasar las políticas de conditional access —. En Windows, robarla está investigado desde hace años; en macOS, el terreno estaba casi inexplorado, con una ironía central del trabajo: la implementación de Microsoft en macOS resultó estar más protegida que la de Windows, y aun así se logró robar la cookie por tres caminos distintos.

El trabajo, de investigadores de Sitecraft (más un estudiante universitario taiwanés y capitán de CTF), cubre la cadena completa: extraer la PRT cookie de macOS comprometido — con navegador headless y la extensión SSO de Chrome, con un binario suplantador vía path interception contra la verificación de codesign del browser core, o invocando directamente la API SSO de Apple saltándose la verificación de team ID —, y luego persistir en Entra ID: resetear la contraseña de la víctima sin conocerla (inconsistencia entre el frontend y el backend del servicio My Sign-ins), agregar un MFA propio con la PRT robada (lo que anula la protección NGC MFA), registrar un dispositivo falso, hacerlo compliant y registrar una propia clave de Windows Hello for Business. El demo final: login en Office 365 con MFA "robustísimo" — un TOTP en el teléfono del atacante y una clave Hello for Business en una máquina que no existe físicamente —.

Microsoft parcheó el robo de PRT cookie en macOS (no en Windows, donde sigue funcionando), y tras recibir el material del trabajo aceptó revisar la protección del registro de dispositivos. Las mitigaciones y artefactos liberados (herramientas de robo y el proyecto PRTcookie-safe) cierran el trabajo.

La PRT en Windows: el mapa que ya existía

El single sign-on de Microsoft existe para no pedir la contraseña en cada uno de sus cientos de servicios, con cuentas Entra ID o Microsoft account. En Windows, el flujo es: navegador (Edge, Chrome, Firefox) pasa el nonce al browser code (binario integrado en el sistema), que delega en la Microsoft Account Token Provider DLL, que habla con LSASS — el proceso que maneja la autenticación —. Dentro de LSASS, el plugin CloudAP interactúa con el TPM, el chip diseñado para que las claves privadas y secretas nunca salgan del dispositivo. En el TPM viven la PRT (identidad del usuario) y la session key (identidad del dispositivo).

Por diseño la PRT no sale del TPM: se calcula la PRT cookie, con vida de ~5 minutos (a veces se cita hasta 15), que se canjea por refresh y access tokens (hasta 24 horas) y de ahí se entra a cada servicio cloud. La cookie codifica identidad de usuario e información del dispositivo vinculado: quien la obtiene hereda claims de MFA y de dispositivo, suficientes para pasar políticas de conditional access. En Windows hay tres vías conocidas para producirla (el rol/tool roadmap, request AAD refresh token y el AAD token broker) que funcionan hasta hoy — de ahí la paradoja: la versión Windows es la menos protegida.

macOS: la anatomía del Company Portal

Para tener PRT en macOS, el dispositivo se inscribe en Intune vía la app Company Portal, que contiene dos piezas relevantes: el SSO extension (antes Platform SSO, renombrado) — por donde pasan apps macOS y Safari para hacer SSO a Entra ID — y el plugin de autofill. Dentro, el framework AD Authentication Broker macOS (el equivalente funcional de una DLL de Windows, pero como framework con más recursos de bundle) hace las verificaciones de caller, y en Resources vive un browser core — el mismo componente que juega el rol central en el flujo Windows —, sospecha inmediata de que cumple la misma función en macOS.

La comparación arquitectónica: Apple aporta el App SSO agent (backend) y la app el authentication frontend; como macOS no tiene LSASS, el SSO extension del Company Portal es quien computa la PRT cookie final, y toda petición pasa por el AD Authentication Broker para validar al caller.

Tres métodos de robo en macOS

  1. Navegador headless + extensión SSO de Chrome. Microsoft distribuye la extensión "Microsoft SSO" para Chrome; con un navegador headless (que sigue dependiendo de sesión de escritorio con login activo) y la extensión instalada, se inicia una petición SSO y la PRT cookie cae directo. Los logs confirman al browser core manejando la petición, como en Windows. Limitaciones: requiere sesión de escritorio del usuario y solo funciona con Chrome y Edge oficiales — el motivo se entiende con el método 3.

  2. Suplantación de proceso con path interception. El reverse del browser core reveló la verificación de caller: RunningApplication(withProcessIdentifier) obtiene la info del proceso padre, concatena el PID con codesign -dv para extraer bundle ID y team ID, los hashea y compara contra una whitelist interna. Los términos importan: el team ID viene del certificado que Apple emite a cada developer — no falsificable —; el bundle ID es un string de identificación, modificable a voluntad (el análogo Windows, el SID, es igual de presuntivo: Microsoft nunca implementó nada como el team ID). El ataque: binario paralelo + binary fake con codesign falso en /tmp declarando el bundle ID de Chrome y el team ID de Microsoft, todo empaquetado en un .app (necesario: se descubrió tarde que RunningApplication solo funciona sobre procesos de app). El fallo explotado: el browser core ejecuta codesign -dv sin path absoluto, así que un path interception redirige al binario falso. El descubrimiento fue accidente de debugging: al parchear el browser core la corrida fallaba con "caller is not allowed" (-6000), pero al adjuntar lldb la cookie apareció — porque el App SSO agent, responsable de leer bundle/team ID del caller, lo hace solo si el proceso tiene el flag CS_VALID o CS_DEBUG; lldb activa el segundo. (Usar lldb como método requiere deshabilitar SIP y autenticar el prompt de developer tools: escalación extra, descartada.) Este método corre sin dependencias y con privilegios de usuario.

  3. Invocación SSO directa por la API de Apple. El análisis del authentication framework reveló cuatro rutas SSO: browser native message (la ruta del browser core) y passkey credential operation — ambas verifican bundle y team ID — frente a general SSO extension request (usada por apps Microsoft: PowerPoint, Outlook, Teams, Excel) y cookie SSO acquisition (para terceros: Firefox, Opera), que no verifican el team ID en absoluto. Su whitelist de bundle IDs contiene 39 entradas (Edge + navegadores de terceros): basta elegir cualquiera de la lista y pedir la cookie directo. Sin dependencias, en userland.

Persistencia en Entra ID: el plan de cuatro movimientos

La PRT y la session key viven en hardware (TPM/Secure Enclave) — inaccesibles incluso como admin — y la cookie caduca en minutos, así que la persistencia pasa por registrar un dispositivo propio: el atacante obtiene PRT y session key propias y genera cookies a demanda. Pero el registro exige un access token sin device ID (no sirve la PRT robada) y una identidad con claim NGC MFA (Next Generation Credentials + MFA, el estado "MFA fresco" de los últimos 10 minutos) para registrar una clave de Windows Hello for Business — la protección pensada para impedir usar tokens con MFA cacheado.

La cadena de pasos: (1) token con device ID propio; (2) re-autenticar por MFA; (3) registrar el dispositivo falso; (4) hacerlo compliant (con PyToon, el proyecto presentado en Black Hat Europe — que aún no soporta macOS —); (5) registrar la clave Hello for Business propia. Los pasos 3 y 5 se resuelven con tools directos; la verdadera dificultad son 1 y 2.

Token sin device ID (sin conocer la contraseña). Las opciones: phishing (reliable pero ruidoso y sin requerir el dispositivo); el Seamless SSO de Kerberos (bajo ruido — solo hace falta un service ticket a cambio de un token —, pero <25% de tenants lo tienen y solo Windows hybrid joined); resetear la contraseña de la víctima (funciona en todos los OS y join types, pero puede alertar). La joya está en la tercera: en el servicio My Sign-ins, autenticado con token que contenga claims de password y MFA, la API password reset permite cambiar la contraseña sin conocer la original; con autenticación passwordless (solo claim MFA) el frontend exige la contraseña actual y llama a password change. El hallazgo: inconsistencia entre frontend y backend — el backend solo exige el claim de MFA para el reset, el de password sobra —, así que se resetea la contraseña de usuarios passwordless sin saberla. Y funciona independientemente de que SSPR (self-service password reset) esté habilitado o no.

MFA fresco. Registrar un nuevo método MFA (passkey o llave FIDO) no exige MFA fresco: con la PRT robada basta. Eso convierte la protección NGC MFA en papel mojado: el atacante registra su propio MFA con el token "viejo" y luego obtiene el NGC MFA pasando su propio segundo factor. Microsoft, consultada como "MFA Bypass", respondió que no es vulnerabilidad y que MFA bypass es una hipérbole — aceptable solo si se renombra: es un NGC MFA bypass, que suena peor. Después de recibir el material con la demo, Microsoft cambió de postura (30 de julio) y anunció que exigirá autenticación más fuerte (MFA fresco) para proteger My Sign-ins.

El demo completo: PRT cookie pedida por la API de Apple → canje por token de My Sign-ins → password reset (nueva contraseña) → registro del dispositivo falso → login en Office 365 bloqueado por MFA → nuevo MFA agregado con la PRT (TOTP en el teléfono del atacante) → token con claim NGC MFA (pasando su propio MFA) → registro de Windows Hello for Business key → login exitoso con MFA "premium" desde un dispositivo inexistente. Bonus: con PRT propia, se puede mover lateralmente a dispositivos Entra-joined — el tema de la investigación presentada en Troopers de este año —: global admin, Intune admin y owner del dispositivo son admin locales por defecto en equipos joined, y la PRT canjea por un P2P certificate para entrar en ellos.

Mitigaciones

  • Parchear: Microsoft ya arregló el robo de PRT cookie en macOS (Windows sigue vulnerable; el fix del registro de dispositivos llegó tras la disclosure).
  • Detección mientras tanto: monitorear el binario codesign — debe correr siempre desde /usr/bin — y alertar ante binarios que declaren los bundle IDs whitelisted sin firma válida. Verificar la política de Intune: si se agregan bundle IDs a la allowlist propia, la exposición persiste.
  • Contra la persistencia: endurecer el conditional access con criterios débiles para el atacante (ubicación IP, user agent) que dificulten agregar dispositivos o métodos MFA; y monitorear nuevos dispositivos registrados y nuevos métodos MFA — ruidoso, pero detecta el patrón completo de este ataque.
  • Para developers de macOS: verificar binarios por team ID, nunca por bundle ID — es la diferencia entre una verificación criptográfica y una etiqueta editable.

Técnicas y herramientas mencionadas

  • PRT / PRT cookie: Primary Refresh Token en TPM/Secure Enclave; cookie de 5-15 min canjeable por refresh/access tokens (24 h) con claims de MFA y dispositivo; base de todo el single sign-on de Microsoft.
  • Company Portal / Intune / SSO extension (ex Platform SSO): cadena de inscripción y SSO en macOS; AD Authentication Broker macOS valida callers; browser core computa el flujo.
  • Extensión "Microsoft SSO" de Chrome + navegador headless: método 1 de robo; requiere sesión de escritorio y Chrome/Edge oficiales.
  • Verificación de caller con bundle ID + team ID: hash contra whitelist interna; team ID no falsificable (certificado de Apple), bundle ID trivialmente editable; análogo débil del SID de Windows.
  • Path interception de codesign -dv sin path absoluto + fake .app en /tmp: método 2; App SSO agent lee identidad del caller solo con flags CS_VALID/CS_DEBUG.
  • Rutas SSO sin verificación de team ID (general SSO request / cookie SSO acquisition): método 3; whitelist de 39 bundle IDs para elegir.
  • My Sign-ins password reset: backend solo exige claim MFA — reset de contraseñas de usuarios passwordless sin conocer la actual, con SSPR habilitado o no.
  • Protección NGC MFA y su bypass: registro de métodos MFA (passkey/FIDO) sin MFA fresco → NGC MFA claim obtenible con la PRT robada → Windows Hello for Business key propia.
  • Registro de dispositivo falso + compliance (PyToon) + Hello for Business: persistencia total con PRT, session key y MFA propias; máquina inexistente con biometría del atacante.
  • Movimiento lateral a dispositivos Entra-joined vía P2P certificate (referencia Troopers): global admin/Intune admin/device owner como admin local por defecto.
  • PRTcookie-safe y herramientas de robo liberadas: artefactos de detección y PoC publicados junto a la investigación.

Conclusiones

  • La paradoja del título es real: la implementación macOS de la PRT cookie, más protegida que la de Windows, cayó igual por tres vías — y la de Windows sigue sin parche. La seguridad del SSO de Microsoft descansa más en la confianza en el caller que en la criptografía del token.
  • Verificar por bundle ID es verificar una etiqueta: sin el team ID (certificado de Apple) en todas las rutas — dos de cuatro no lo chequeaban —, cualquier proceso puede pedir la cookie del usuario. Es la lección transferible a cualquier developer de macOS.
  • La persistencia en Entra ID es un problema de consistencia, no de criptografía: el backend que no exige el claim de password en el reset, y el registro de MFA que no exige MFA fresco, convierten una PRT robada de minutos en un control permanente de la identidad, con MFA "premium" controlado por el atacante.
  • La respuesta de Microsoft — negar, renombrar el problema y luego parchear tras ver la demo — muestra el valor de la disclosure con evidencia: el fix del registro de dispositivos llegó una semana antes de DEF CON.
  • Para defensores: monitorear codesign fuera de /usr/bin, firmas inválidas con bundle IDs whitelisted, y sobre todo altas de dispositivos y métodos MFA — el ataque de persistencia deja huella en cada paso del registro.
