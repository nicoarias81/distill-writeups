BOLABuster: automatizar la detección de BOLA con LLMs

Fuente: «DEF CON 32 - BOLABuster-Harnessing LLMs for Automating BOLA Detection - Ravid Mazon, Jay Chen» · ver el video original

  • Video: 9bNv3XkhjQA · URL: https://youtu.be/9bNv3XkhjQA · Conferencia: 01_defcon · Título original: DEF CON 32 - BOLABuster-Harnessing LLMs for Automating BOLA Detection - Ravid Mazon, Jay Chen Palo Alto Networks · API security research

  • TL;DR

  • Broken Object Level Authorization (BOLA) encabeza el OWASP API Security Top 10 y es la cuarta vulnerabilidad más reportada en HackerOne, pero no existía una herramienta que la detecte de forma fiable y a escala.
  • La propuesta toma como única entrada una especificación OpenAPI/Swagger y encadena cinco etapas: selección de endpoints potencialmente vulnerables, descubrimiento de dependencias productor→consumidor, cálculo de rutas de ejecución, generación de scripts de prueba con LLMs y ejecución contra un servidor de pruebas.
  • Contra tres aplicaciones deliberadamente vulnerables, el enfoque encontró todos los casos de BOLA con menos del 1 % de las peticiones que generó RESTler (el fuzzer de APIs de Microsoft), que no detectó ninguno.
  • En proyectos reales se documentaron 17 BOLA nuevas: una en Harbor, una en Grafana y 15 en Easy!Appointments (siete críticas, CVSS 9.9, que permiten a un usuario sin privilegios escalar a admin).

Por qué BOLA es difícil de automatizar

BOLA es un fallo de autorización a nivel de objeto: un usuario accede, modifica o elimina un recurso que no le pertenece (por ejemplo, borrar el comentario de otro usuario). No es un patrón de payload malicioso como XSS o SQL injection: es un error lógico, y eso complica el análisis. Los principales obstáculos son cuatro:

  1. Mecanismos de autorización complejos: aplicaciones con múltiples usuarios, roles y recursos, donde decidir "quién puede hacer qué" no es trivial.
  2. Estado compartido y dependencias: las APIs son stateful; para probar el borrado de un comentario hay que crear primero el artículo y el comentario. El orden de ejecución importa y no se puede aislar un endpoint.
  3. Falta de indicador de vulnerabilidad: la respuesta "éxito" del servidor no distingue entre un ataque y un uso legítimo.
  4. Contexto: entender qué endpoint y qué parámetro transporta datos sensibles, y cuál es el impacto real de cada acción, exige razonamiento semántico.

Ese último punto es el que hace viable el uso de LLMs: extraer lógica e intención de texto (la descripción de la spec) es justo su punto fuerte.

  • Identificación de endpoints objetivo (PVE): se buscan endpoints con parámetros que referencian información privada o confidencial (username, email…), porque un BOLA ahí permitiría, por ejemplo, resetear la contraseña de otro usuario. Un prompt con reglas y ejemplos hace el trabajo que antes hacía un pentester a mano sobre cientos de endpoints.
  • Relación productor/consumidor: un endpoint consumidor necesita como entrada valores que otros endpoints (productores) generan. Probar delete user con un nombre de usuario inexistente solo produce errores sin valor; hay que alimentarlo con un usuario real creado antes. El emparejamiento heurístico de nombres de parámetros no basta (los desarrolladores reutilizan nombres para objetos distintos y viceversa), así que se combinan heurísticas con análisis semántico del LLM.
  • Árbol de dependencias y rutas de ejecución: para cada PVE se construye un árbol donde el nodo raíz es el objetivo y cada arista padre→hijo es una relación consumidor→productor. Cada camino de hoja a raíz es un escenario de prueba ejecutable; se busca cubrir todos los caminos posibles.
  • Generación y ejecución: cada ruta se convierte en un script bash autónomo (generación asíncrona, ~1,5 segundos por test). Antes de ejecutar, se aísla del spec solo el subconjunto relevante para el test —reducción del 90-95 % del documento—, lo que baja el costo en tokens y mejora la precisión. Registro de usuarios, login y refresco de tokens están automatizados, y cada actor (Alice, Bob) recibe un token único.
  • Orquestación del orden: los tests que crean datos se ejecutan primero; las operaciones update y delete se empujan al final, para que un fallo se deba a la lógica de autorización y no a razones técnicas.

El test canónico: Alice crea un artículo y un comentario (guardando slug e id), y Bob intenta borrar el comentario de Alice con su propio token. Si la operación tiene éxito, hay un BOLA potencial.

Resultados: laboratorio y proyectos reales

Como referencia se usó RESTler, el fuzzer de APIs open source de Microsoft, sobre tres aplicaciones deliberadamente vulnerables al OWASP API Top 10. RESTler no identificó ningún BOLA pese a lanzar miles o cientos de miles de peticiones; la metodología aquí descrita encontró todos los BOLA de las tres aplicaciones con menos del 1 % de las llamadas, con el objetivo puesto en una tasa de verdaderos positivos del 100 % (se asumen falsos positivos controlables).

En proyectos reales, el balance fue de 17 BOLA nuevas:

Proyecto Qué es Hallazgo
Harbor Registro de contenedores cloud-native (CNCF graduado) 1 BOLA: la API permite a un maintainer modificar la configuración del proyecto (visibilidad pública/privada, escaneo de imágenes) aunque la UI lo bloquee; violación de la integridad del proyecto. Con CVE publicado.
Grafana Visualización y monitoreo (~20 M de usuarios) 1 BOLA nueva.
Easy!Appointments Gestión de citas (~200 k descargas) 15 BOLA nuevas, 7 críticas (CVSS 9.9): un usuario con privilegios bajos obtiene acceso de administrador.

El caso de Harbor ilustra un patrón frecuente: la UI aplica correctamente las políticas y la API no. Cualquier auditoría de autorización que solo pruebe la interfaz gráfica deja expuesta exactamente esta clase de fallos.

Implicaciones prácticas

  • Las pruebas de BOLA se pueden automatizar a partir de la especificación OpenAPI que casi toda organización ya produce, sin tocar el código fuente.
  • La combinación heurísticas + LLM supera a cualquiera de los dos por separado: las heurísticas son baratas y deterministas, el LLM resuelve la ambigüedad semántica de nombres de parámetros.
  • Reducir el spec al subconjunto relevante por test (90-95 % menos de texto) es la palanca principal de costo y calidad.
  • Todo test de BOLA es malicioso por definición: solo debe ejecutarse contra servidores de prueba controlados.
  • Revisar la paridad UI/API: discrepancias entre ambas son un indicador directo de autorización inconsistente.

Lecciones sobre el uso de LLMs

  • La IA no siempre es la respuesta: si un problema (ordenar, resolver ecuaciones) tiene solución heurística óptima, úsela.
  • No confiar, validar: la salida del modelo debe verificarse antes de pasarla a la etapa siguiente; confiar ciegamente es peligroso.
  • Divide y vencerás: tratar al modelo como un junior muy capaz —excelente en tareas simples, propenso a errores en tareas complejas— y partir el trabajo en pasos pequeños.

Límites y suposiciones

  • La metodología asume una especificación OpenAPI/Swagger disponible y de calidad; sin ella no hay punto de partida.
  • La detección marca BOLA potenciales: la confirmación final (impacto real, contexto de negocio) sigue requiriendo análisis humano.
  • El objetivo declarado es maximizar verdaderos positivos, no eliminar falsos positivos.
  • Las mediciones de eficiencia (menos del 1 % de las llamadas de RESTler, 1,5 s por test) corresponden a las aplicaciones evaluadas, no a una garantía general.
