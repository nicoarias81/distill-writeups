Offensive security testing en el segmento terrestre espacial

Fuente: «DEF CON 32 - Offensive Security Testing Safeguarding the Final Frontier - Andrzej Olchawa» · ver el video original

  • Video: YtMutNk8RpY · URL: https://youtu.be/YtMutNk8RpY · Conferencia: 01_defcon · Título original: DEF CON 32 - Offensive Security Testing Safeguarding the Final Frontier - Andrzej Olchawa

Resumen

El software que controla misiones espaciales lleva décadas desarrollándose sin contrapartida ofensiva: cada organización construye su propio sistema de control de misión —"el espacio es difícil", dicen— y casi nadie lo prueba como lo haría un adversario. Este walkthrough presenta el segmento terrestre (ground segment) de una misión espacial, se concentra en el mission control system como eslabón más expuesto, y demuestra cadenas de explotación reales contra software open source de control de misiones: NASA OpenMCT, NASA AIT Core y SCOS 2000 de la Agencia Espacial Europea. Todas las vulnerabilidades fueron reportadas a los vendors, corregidas y tienen CVE asignado.

Por qué el mission control system es el blanco

El segmento terrestre son muchos componentes interconectados —estación terrena, sistemas de procesamiento, planificación— que se pasan entradas y salidas entre sí, pero la mayoría no requiere interacción humana. La excepción es el mission control system: la interfaz principal entre la estación terrena y los demás componentes, y la interfaz primaria entre los controladores de la nave y la nave misma. Y como el eslabón débil de cualquier sistema informático es el humano, esa condición lo vuelve el sistema más vulnerable de todo el segmento.

El cambio reciente agrava el cuadro: durante décadas las misiones se operaban desde salas de control dedicadas, accesibles solo a los controladores. Con la pandemia, las organizaciones abrieron las puertas y permitieron operar remotamente. Eso creó una superficie de ataque nueva sobre software típicamente desactualizado, vulnerable a los mismos fallos cotidianos de cualquier software de escritorio. La respuesta de la comunidad espacial —estrategias que incluyen seguridad, políticas, requisitos de seguridad— sigue dejando afuera un elemento específico: el offensive security testing.

Vulnerabilidades encontradas

  • NASA OpenMCT: prototype pollution, XSS y CSRF.
  • NCS/IMCS (mission control system establecido): directory traversal, borrado arbitrario de archivos, session hijacking y varias vulnerabilidades XSS.
  • NASA AIT Core (framework para construir software de segmento terrestre): SQL injection, varias ejecuciones locales de código y ausencia total de cifrado en las comunicaciones.
  • SCOS 2000 (ESA): sin análisis extenso, solo static code analysis con Flawfinder: casi 2500 vulnerabilidades de buffer overflow, de las que es razonable suponer que al menos una es explotable.

Cada vulnerabilidad aislada tiene impacto modesto; el riesgo real aparece al encadenarlas.

Cadena 1: XSS + session hijacking + directory traversal

Escenario sobre el mission control system: Bob envía telecomandos y recibe telemetría de la nave; Alice trabaja con él; la organización tiene un sitio web público; el atacante opera un servidor C2.

flowchart TD
    R[Recon: la web pública delata a Alice] --> P1[Phishing a Alice: beacon C2 en su workstation]
    P1 --> P2[Los atacantes descubren a Bob en sus mails]
    P2 --> P3[Phishing interno suplantando a Alice: payload XSS a Bob]
    P3 --> X[Bob confía y ejecuta: se dispara el XSS]
    X --> H[Session hijacking + directory traversal]
    H --> F[Lectura de archivos arbitrarios del servidor del mission control system]
    F -->|Bob con Internet| D1[Exfiltración directa al servidor C2]
    F -->|Bob tras firewall/VPN| D2[La workstation de Alice actúa como proxy]

El exploit desarrollado genera el payload —bautizado xVJS— y levanta un servidor HTTP del atacante. Bob recibe el archivo creyendo que es una pantalla de telemetría que Alice compartió con él, lo carga en el sistema y lo abre. Bajo el capó, el XSS disparado combina el session hijacking con el directory traversal para recuperar el archivo y mandar su contenido al servidor HTTP del atacante. En la demo, el proof of concept muestra la lectura del archivo de contraseñas del sistema. Encadenar las tres vulnerabilidades es, en sí, sencillo.

Cadena 2: man-in-the-middle contra AIT Core

Con una ejecución remota de código y la comunicación sin cifrado, el ataque es un man-in-the-middle que inyecta un payload en el stream de telemetría. La demo: a la izquierda, el telemetry client (lo que correría la estación de control) y el telemetry simulator, ambos provistos por AIT Core; a la derecha, el exploit y un listener de netcat esperando la shell. Se arranca el cliente, luego el simulador que genera paquetes de telemetría como si vinieran de la nave, y se corre el exploit. El primer frame que viaja del simulador a la estación es capturado por el MITM, se inyecta el payload, este se ejecuta en el telemetry client y entrega una reverse shell al netcat del atacante. Es decir: telemetría falsificada que ejecuta código en la consola de la misión.

Lecciones

  • El análisis estático encuentra la fruta baja, pero no alcanza: el análisis dinámico y la fase de explotación son indispensables para medir el riesgo real de lo encontrado.
  • Las cadenas son el peligro: vulnerabilidades de impacto individual moderado se combinan en divulgación de información sensible o ejecución remota de código en el sistema de control.
  • El testing ofensivo falta en los marcos espaciales: hay que contratar el servicio —o hacerlo internamente— e incorporarlo a los frameworks de seguridad antes de que los adversarios lo hagan primero.
  • Todo el material está publicado: los papers y las vulnerabilidades con CVE asignado están disponibles, y las slides se comparten tras la exposición.

Conclusiones

  • El segmento terrestre heredó supuestos de aislamiento físico que la operación remota rompió: el mission control system quedó expuesto a phishing, XSS y robo de sesión como cualquier web app.
  • El software de control de misión desarrollado a medida no es más seguro por ser propio: OpenMCT, AIT Core y SCOS 2000 acumulan fallos clásicos que un adversario paciente encadena sin necesidad de acceso a la nave.
  • La defensa empieza por suponer ataque: testing ofensivo sistemático —estático y dinámico, con explotación incluida— antes del lanzamiento, no después del incidente.
