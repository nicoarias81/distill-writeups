Impersonate Me: auth bypasses en Entra ID y las librerías de identidad

Fuente: «DEF CON 33 - Impersonate Me: Unveiling Auth Bypasses in Entra ID & Identity Libraries - Nikhil Sahu» · ver el video original

  • Video: ui_5uG31Am4 · URL: https://youtu.be/ui_5uG31Am4 · Conferencia: 01_defcon · Título original: DEF CON 33 - Impersonate Me: Unveiling Auth Bypasses in Entra ID & Identity Libraries - Nikhil Sahu

Resumen

Nikhil Sahu, ingeniero de seguridad de software en el equipo Microsoft Serpent (dentro de Microsoft Specialized Cloud), recorre los patrones vulnerables y errores comunes que los desarrolladores cometen al implementar autenticación y autorización con proveedores de identidad como Entra ID: desde decisiones de autorización basadas en claims mutables hasta cuatro variantes de bypass de firma en el ecosistema .NET. El resultado puede ir de account takeover a escalada de privilegios, con tokens perfectamente válidos o directamente sin firma. Todo el material usa C# y .NET con Entra, pero los patrones reaparecen en otros lenguajes y proveedores.

Base: OAuth, OpenID Connect y tokens

El flujo moderno: la aplicación manda al usuario a la página del proveedor de identidad (Microsoft, Google, GitHub…), el usuario se autentica, el proveedor emite tokens —ID token y access token— y la aplicación los usa para identificar al usuario y decidir qué puede hacer. Toda la seguridad del sistema descansa en cómo consume la aplicación esos tokens: si no los valida bien, nada de lo que aporta el proveedor sirve.

  • OAuth es autorización delegada: da access tokens para llamar a otros recursos.
  • OpenID Connect es una capa de identidad estandarizada sobre OAuth: emite ID tokens para probar que el usuario se autenticó.
  • La confusión entre ambos es fuente clásica de bugs: usar ID tokens para decisiones de autorización, que no es para lo que existen.

Un JWT tiene header, payload y firma; las dos primeras partes van en Base64 y son legibles por cualquiera. La seguridad no viene de ocultar los claims, sino de la firma: es lo que garantiza que nadie los manipuló. Los claims se agrupan en cuatro familias:

  1. Identificadores de sujeto: sub, oid (object ID).
  2. Para mostrar / consumo de aplicación: email, name, preferred_username.
  3. Para autorización: roles, groups, scopes.
  4. Contexto del token: iss (issuer), aud (audience), exp (expiry), y el crucial tid (tenant ID).

Tenants: el límite que hay que validar

Un tenant es una instancia aislada de Azure AD, con su GUID único (tid), su dominio, y usuarios con object IDs estables. Un detalle que rompe supuestos: el mismo email puede existir en varios tenants —admin@example.com en el tenant A y en el tenant B son identidades distintas, con permisos distintos—.

  • App single-tenant: solo usuarios del tenant donde vive el app registration pueden obtener tokens; el endpoint es login.microsoftonline.com/<tenant-id>. Un atacante de otro tenant recibe rechazo.
  • App multi-tenant: cualquiera de cualquier tenant obtiene token (endpoint /common o /organizations).

El multi-tenant no es malo: es la base de las apps SaaS (que quieren que cualquier usuario de cualquier tenant entre). El problema aparece cuando un desarrollador no entiende el flujo y configura como multi-tenant una app interna u organizacional: de pronto cualquiera en internet puede autenticarse en ella. Para apps multi-tenant que no deben ser abiertas, hay que validar explícitamente el tenant y el sujeto en cada request.

Ataque 1: claims mutables como base de autorización

Existen los optional claims: no vienen por defecto, hay que habilitarlos en el manifiesto o la configuración de tokens, varían según flujo y tenant, y —clave— son mutables: cambian a lo largo de la vida. Dentro de ellos, los display claims son los peligrosos:

  • preferred_username (tokens v2.0): el nombre legible con el que el usuario inicia sesión —email, teléfono o username genérico, sin formato impuesto—.
  • unique_name (tokens v1.0 legacy): el UPN o email, para mostrar.
  • email: la dirección asociada a la cuenta; puede no coincidir con el identificador de login.

La guía de Microsoft es explícita: nunca usar email, preferred_username ni unique_name para decidir si el usuario de un token debe tener acceso a datos. No son únicos, los controla el administrador del tenant (o el propio usuario), y su valor no está garantizado ni es estable. En la página de propiedades del usuario en Entra ID se editan a mano en "Contact information" (email y "other emails"), y eso es exactamente lo que viaja en el token.

El patrón vulnerable es inocente por fuera:

var userId = User.FindFirst("preferred_username")?.Value
             ?? User.FindFirst("oid")?.Value;
var profile = await _profileService.GetByIdentifierAsync(userId);

Si el token trae preferred_username = admin@example.com, la app busca ese registro y lo devuelve. Cualquiera que consiga un token legítimo con ese claim alterado suplanta a cualquier usuario.

El flujo del ataque:

  1. El atacante va a las propiedades de su propio usuario en su tenant y cambia su email al de la víctima.
  2. Se autentica normalmente; Entra ID le emite un token perfectamente válido y firmado criptográficamente, que ahora contiene el email de la víctima en el claim mutable.
  3. La API valida el token (firma OK: lo emitió Entra), extrae el claim mutable y, basándose en él, devuelve el registro de la víctima.

El detalle práctico de la explotación: al iniciar sesión hay que usar "sign-in options" y declarar primero el tenant (tenant ID o dominio) antes de escribir el email suplantado; si no, el flujo matchea con el admin@example.com real que existe en Entra, no con el del tenant propio. También se puede habilitar "email as alternate login ID" en Entra Connect para loguearse directamente con el identificador alternativo.

En la demo, un portal de RRHH con una política HRAdmin que extrae user_email del contexto HTTP y la compara contra una lista de administradores en appsettings.json (admin@example.com), y un EmailResolutionService que resuelve el email mirando claims mutables (email, preferred_username, e incluso un token de Graph generado en nombre del usuario para leer unique_name): con el email cambiado, el usuario normal entró al endpoint de administración.

Cómo se hace bien

  • Nunca usar display claims para autorización.
  • Aplicar acceso por roles y políticas explícitas, no por atributos de identidad inferidos.
  • En multi-tenant, validar tenant y sujeto en cada request.
  • Para atar acceso a sujetos concretos, usar identificadores estables: tid + oid, estables durante toda la vida del tenant. Una política RequireAdmin correcta exige dos cosas: que el tid del token matchee el tenant esperado y que el claim role sea admin.

Cómo valida tokens .NET (y dónde se rompe)

La validación tiene tres niveles: validación del token (firma, issuer, audience, lifetime), validación del caller (contexto de tenant, identidad por oid/sub, o appid/azp en tokens de app) y checks de autorización (scopes, roles, políticas). Si la firma falla, todo lo demás es papel mojado: el atacante forja cualquier claim y la app los confía.

En .NET todo pasa por TokenValidationParameters, con propiedades como ValidIssuer, ValidateAudience, ValidateLifetime, RequireSignedTokens (segura por defecto: true si no se toca) y ValidateIssuerSigningKey. Cuatro patrones de bypass:

  1. RequireSignedTokens = false: desactiva la exigencia de firma. El atacante arma un JWT con header y payload —sin tercer segmento—, pone el issuer, audience y lifetime que la app espera, y pasa todas las demás validaciones porque ya no hay nada criptográfico detrás. Matiz importante del comportamiento real: si el token sí trae firma, la validación de firma se ejecuta igual; el bypass exige mandar el token sin el segmento de firma.
  2. SignatureValidator reemplazado: el delegate existe para agregar lógica de validación, pero suele usarse para reemplazarla: TokenValidationParameters.SignatureValidator = (token, _) => new JwtSecurityToken(token) —convierte el string en objeto y lo devuelve: ninguna verificación criptográfica. Es equivalente al anterior, pero menos obvio, porque el código parece estar validando.
  3. ReadJwtToken sin validar: el método de IdentityModel solo convierte el JWT en objeto. Es legítimo usarlo si se valida antes o después; el bug es extraer los claims con él y decidir autorización —por ejemplo, una política "admin-only" que lee el token del header Authorization, hace ReadJwtToken y comprueba role == admin—. El atacante forja role: admin y entra.
  4. Override de ValidateToken sin base: sobrescribir el método del handler es legítimo para extender, pero si en el override no se llama a base.ValidateToken, se pierden todos los checks integrados. En la demo, un handler SkipSignatureHandler que hereda de JwtSecurityTokenHandler, "lee" el token y devuelve el ClaimsPrincipal tal cual.

El flujo de ataque completo, sobre un flujo client credentials (app → API → base de datos): el atacante observa la estructura del token (o se autentica una vez legítimamente), arma el payload con la aud esperada, el tid del tenant objetivo y el appid de la aplicación autorizada (azp), Base64, sin firma. En la demo de una API de notificaciones —consultar y enviar notificaciones a emails arbitrarios— la política por defecto exigía que el tid matchee el tenant hardcodeado y que el appid/azp esté en la lista de callers autorizados; con el payload forjado a medida, ambas pasaron y la API respondió 200 con envío de notificación incluido.

Cazar los patrones

Análisis estático sobre los repositorios:

  • Semgrep para reglas rápidas y sucias por patrón: una regla con regex que flaguea cualquier propiedad de TokenValidationParameters puesta en false (RequireSignedTokens, ValidateIssuer, ValidateAudience, …), y otra que marca todo uso de ReadJwtToken.
  • CodeQL cuando hace falta taint tracking y análisis de flujo de datos más profundo.

Mitigaciones

  • No deshabilitar la validación de firma; y si se implementa lógica propia, llamar siempre a base.ValidateToken en los overrides.
  • La firma sola no alcanza: enforzar los cuatro checks adicionales en todos los tokens.
  • Issuer: sin esto se aceptan tokens de tenants no deseados.
  • Audience: sin esto, un token emitido para otra aplicación se usa contra la propia.
  • Lifetime: que el token no esté vencido.
  • Caller con claims estables (tid, oid).
  • Si el app es multi-tenant sin necesidad real de serlo, validar el tenant en cada request.
  • Los claims mutables no son identidad: email, preferred_username y unique_name son solo para mostrar.
  • Autorizar con identificadores estables (tid + oid); usar las librerías estándar, que ya traen los checks integrados, en vez de lógica custom.

Lecciones

  • Cada check que se salta en la validación de un token es una vulnerabilidad nueva; la cadena firma → issuer → audience → lifetime → caller funciona como conjunto, no como menú.
  • El atacante no necesita romper la criptografía: con claims mutables obtiene tokens legítimamente firmados con el valor que quiere; con los bypass de firma, ni siquiera necesita firmar nada.
  • La misconfiguración más común no está en el proveedor de identidad sino en el consumo: el proveedor hace su parte bien; el bug vive en el código que decide qué hacer con el token.
