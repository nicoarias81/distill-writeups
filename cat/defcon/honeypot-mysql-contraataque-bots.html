Honeypot MySQL: contraatacar a los bots que vacían bases de datos

Fuente: «DEF CON 32 - Atomic Honeypot-A MySQL Honeypot That Drops Shells - Alexander Rubin, Martin Rakhmanov» · ver el video original

  • Video: 8oAxv7UBZJA · URL: https://youtu.be/8oAxv7UBZJA · Conferencia: 01_defcon · Título original: DEF CON 32 - Atomic Honeypot-A MySQL Honeypot That Drops Shells - Alexander Rubin, Martin Rakhmanov

Resumen

Los bots de ransomware llevan años escaneando Internet en busca de servidores MySQL expuestos en el puerto 3306: fuerzan la contraseña, descargan lo que pueden, borran las bases y dejan una nota pidiendo rescate. La investigación detrás de este proyecto invierte el juego: en lugar de solo defender, se levanta un honeypot MySQL (el "Atomic Honeypot") para capturar y fingerprintear los ataques, y luego usar las debilidades del propio malware y de sus herramientas para contraatacar a los atacantes desde el servidor "víctima".

El desenlace: tres técnicas ofensivas contra los bots —lectura arbitraria de archivos del atacante, ejecución remota de código vía plugin de MySQL, e inyección de comandos a través de mysqldump— y un consejo práctico para víctimas: no pagar, porque los bots que dicen haber descargado tu base de datos solo se llevan 10 registros.

El ecosistema: bots por todas partes

El punto de partida es la exposición masiva de MySQL en Internet (millones de instancias visibles en servicios tipo Shodan). Los atacantes automatizados bruteforcean credenciales débiles, se conectan, enumeran las bases con SHOW DATABASES y ejecutan su cadena de explotación. El método de investigación fue montar un honeypot con un MySQL deliberadamente vulnerable, dejar que los bots llegaran, y registrar todo: comandos, fingerprints del cliente, utilidades que ejecutan y malware que intentan desplegar.

Del análisis de las capturas emergió un patrón repetido con dos grandes familias de ataque, cada una con su fingerprint característico —y cada una, resultó, con una debilidad explotable de vuelta.

Técnica 1: lectura arbitraria de archivos hacia el atacante

El primer fingerprint corresponde a clientes MySQL viejos. Contra ellos funciona la técnica clásica del "rogue MySQL server": el atacante se conecta a un servidor falso que pide al cliente, mediante LOAD DATA LOCAL INFILE invertido, enviar un archivo cualquiera de su propia máquina. Es una lectura arbitraria de archivos en el cliente, con herramienta pública en GitHub: se levanta en el puerto 3306, se pide la contraseña, el cliente viejo se conecta al servidor falso y el archivo pedido viaja de vuelta.

Usándola contra los propios bots se identificó su entorno: descargando archivos característicos se determinó que las máquinas atacantes corren Windows Server 2003 —un sistema operativo sin soporte desde 2015, confirmando la baja calidad de la infraestructura atacante.

Técnica 2: ejecución remota de código vía plugin

Con el fingerprint de versiones viejas también es viable la RCE por plugin de MySQL (ataque presentado el año anterior, explotando la carga dinámica de plugins con directory traversal). El problema operativo era la entrega: el DLL malicioso tiene que estar en la máquina del atacante antes de poder dispararlo.

La solución salió de observar los comandos que los bots ejecutan contra el honeypot: el propio malware descarga su código desde un servidor FTP que corre en la máquina del atacante, con usuario, contraseña y puerto visibles en el fingerprint. El plan contraataque:

  1. Subir el DLL malicioso vía ese FTP (credenciales conocidas) a una ubicación pública del servidor comprometido del atacante.
  2. Arrancar el honeypot con el plugin_dir apuntando a esa ubicación pública.
  3. Esperar la conexión del bot y disparar la RCE vía directory traversal, que termina invocando LoadLibrary sobre el DLL controlado.

Demostración en laboratorio incluida: cliente MySQL real conectándose al honeypot, DLL que despliega un diálogo de "código ejecutado", RCE confirmada contra la máquina atacante.

Técnica 3: inyección de comandos vía mysqldump

La segunda familia de bots es más moderna: versiones nuevas de MySQL cliente donde el plugin y la lectura de archivos ya no funcionan. Pero su fingerprint delata una rutina: una aplicación con conector MySQL/ADO se conecta, ejecuta SHOW DATABASES, y luego lanza la utilidad mysqldump pasando base de datos y tabla —el objetivo es descargar la base de datos para poder afirmar que la tienen "backupeada".

Dato clave para las víctimas: solo descargan 10 registros. No tienen los datos; reclamar lo contrario es parte del extortion playbook. Y para el investigador, la superficie de ataque estaba en cómo construyen ese dump: ejecutan mysqldump interpolando nombres de bases de datos sin sanitizar. Creando en el honeypot una base con nombre inyectado entre backticks (la clásica inyección de comandos a nivel de shell), el comando del atacante ejecuta código adicional en su propia máquina.

Con esa inyección se descargó el código malicioso del atacante: un script Python que se conecta a la base de datos víctima, bruteforcea la contraseña y lanza el mysqldump —con múltiples puntos donde ejecutar el comando inyectado. La PoC final: script VBS que despliega "you have been pwned" al ejecutarse mysqldump en un Windows con MySQL 5.7.36 (una versión antes de la última de la rama).

Cómo replicarlo sin riesgo

El contraataque es reproducible por cualquiera con una instalación mínima: un servidor MySQL cualquiera (versión indiferente) con root sin contraseña —si los bots se llevan los datos falsos, no importa—, más la creación de una base de datos cuyo nombre lleva la inyección en backticks. El resto lo hace el bot al conectarse y lanzar su mysqldump.

Conclusiones

  • No pagar: el modus operandi capturado muestra que los bots solo extraen 10 registros antes de borrar; la nota de rescate miente sobre el volumen de datos comprometidos.
  • Las herramientas de los atacantes son attack surface: fingerprints, utilidades (mysqldump, FTP propio), credenciales embebidas y sistemas operativos abandonados convierten al atacante en objetivo.
  • Para exponer MySQL: no exponer 3306 a Internet, credenciales fuertes, y monitoreo de conexiones anómalas —el honeypot es a la vez técnica de investigación y formulario de detección temprana.
  • La investigación se completó con reporte responsable del problema de inyección de comandos detectado (detalles de CVE pendientes de número al momento de la exposición).
