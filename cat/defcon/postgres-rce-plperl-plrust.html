De variables de entorno a shell: RCE en PostgreSQL gestionado en la nube

Fuente: «DEF CON 33 - Rusty pearls: Postgres RCE on cloud databases - Tal 'TLP' Peleg, Coby Abrams» · ver el video original

  • Video: eroPf1N-pAk · URL: https://youtu.be/eroPf1N-pAk · Conferencia: 01_defcon · Título original: DEF CON 33 - Rusty pearls: Postgres RCE on cloud databases - Tal 'TLP' Peleg, Coby Abrams

Resumen

PostgreSQL es una de las bases de datos relacionales más extendidas del mundo, y casi todos los proveedores de nube ofrecen instancias gestionadas de Postgres. Esta ubiquidad la convierte en un objetivo de alto valor: romper el aislamiento entre el usuario y el proveedor de nube puede exponer credenciales o incluso abrir camino a movimientos laterales entre clientes.

Investigadores de Varonis descubrieron y demostraron una cadena de escalada que parte de un usuario de base de datos sin privilegios de superusuario y termina ejecutando código arbitrario en el sistema operativo que aloja la base de datos. La cadena combina dos extensiones oficiales de Postgres: PL/Perl, que permite modificar variables de entorno de la sesión pese a ser un lenguaje "trusted", y PL/Rust, cuyo proceso de compilación con Cargo puede ser secuestrado mediante esas mismas variables.

La investigación no quedó en el laboratorio: el equipo ejecutó código en una instancia real de AWS RDS. El entorno cloud resultó estar fuertemente restringido —sin acceso a la red interna ni tokens a la vista—, pero el hallazgo demuestra que las superficies de ataque de los servicios gestionados van mucho más allá de las cargas de trabajo tradicionales.

El punto de partida: el usuario admin de RDS no es superusuario

Tras divulgar una inyección SQL muy impactante en una base de datos alojada en AWS RDS, la pregunta natural era qué podría hacer un atacante real con ese acceso. En RDS, el usuario administrador que entrega Amazon puede gestionar esquemas y datos, pero no es superusuario de Postgres. La barrera de confianza entre cliente y proveedor permanece intacta.

El objetivo se fijó entonces en dos niveles: obtener acceso de superusuario o, mejor todavía, ejecutar código en el sistema subyacente. Lograrlo en la nube tendría implicaciones graves: romper esa frontera podría permitir exfiltrar credenciales de la nube o moverse lateralmente entre clientes de la misma plataforma.

PL/Perl: un lenguaje "trusted" que escribe variables de entorno

Las extensiones de lenguaje de Postgres permiten definir funciones en SQL, C, Python, Perl o, más recientemente, Rust. Postgres las divide en dos categorías: los lenguajes untrusted tienen acceso pleno al sistema —variables de entorno, ficheros, sockets, procesos— y solo un superusuario puede ejecutarlos; los lenguajes trusted operan en un entorno restringido y cualquier usuario puede usarlos.

Esa suposición de seguridad se rompió a través de Perl mismo. Perl expone el "hash mágico" %ENV, que permite leer y escribir las variables de entorno del proceso actual. La hipótesis fue que algo tan enterrado en el corazón del lenguaje no estaría neutralizado por el sandbox de PL/Perl —y lo era—. Con una función PL/Perl trivial, un usuario sin superusuario puede modificar variables de entorno del proceso de su sesión de Postgres.

Tener la capacidad de alterar variables de entorno suele ser casi sinónimo de ejecución de código. El resto del trabajo consistió en encontrar dónde consumirías.

Secuestrar a Cargo: la segunda mitad de la cadena

Postgres complica el camino clásico: las extensiones no lanzan procesos directamente, sino a través de una API de background workers, así que los procesos creados por Postgres no heredan las variables de entorno modificadas. La búsqueda se centró entonces —con GitHub Search y Copilot sobre extensiones open source— en código que ejecutara binarios de forma directa: funciones system, la familia execv o, en Rust, el constructor Command.

El blanco fue PL/Rust. Al crear una función PL/Rust, Postgres invoca Cargo, el gestor de paquetes de Rust, que a su vez llama al compilador rustc. Ese proceso es sensible a variables de entorno. PL/Rust sanitiza el entorno antes de lanzar Cargo y elimina, entre otras, RUSTC_WRAPPER —que permite sustituir el binario del compilador—. Pero olvidó su equivalente CARGO_BUILD_RUSTC_WRAPPER, con exactamente el mismo efecto.

Con ese vector solo se puede cambiar qué binario se ejecuta, no sus argumentos. La pieza final fue el script rust-gdb que instala la toolchain de Rust: ejecuta el contenido de la variable RUSTGDB. La cadena completa queda así:

flowchart LR
    A[Función PL/Perl] -->|escribe %ENV| B[CARGO_BUILD_RUSTC_WRAPPER = rust-gdb]
    B --> C[RUSTGDB = comandos bash]
    C --> D[Creación de función PL/Rust]
    D --> E[Cargo compila y llama al binario sustituido]
    E --> F[Script rust-gdb ejecuta los comandos inyectados]
    F --> G[RCE como usuario de Postgres]

El procedimiento: instalar las extensiones PL/Perl y PL/Rust, crear una función Perl que apunte CARGO_BUILD_RUSTC_WRAPPER a rust-gdb y cargue los comandos deseados en RUSTGDB, y luego crear una función PL/Rust —vacía, basta con que se compile—. Al compilar, la cadena dispara la ejecución y devuelve la salida estándar de los comandos: código ejecutado en Postgres sin ser superusuario.

La prueba de fuego en AWS RDS

RDS ofrece tanto PL/Perl como PL/Rust, así que el equipo replicó la explotación en su propia instancia gestionada. El entorno resultó mucho más limitado que el de un Postgres local: el script rust-gdb dependía de binarios que no existían allí, y hubo que recurrir al parámetro ENV de bash —que bash expande antes de arrancar— para ajustar la cadena al entorno restringido.

El código se ejecutó, pero el entorno estaba bien aislado: sin acceso a la red interna, sin tokens interesantes al alcance, sin indicios de acceso entre tenants. Y la respuesta de AWS fue rápida y contundente: en muy poco tiempo llegaron avisos desde la propia AWS, correos al CEO de la empresa de los investigadores y contactos vía LinkedIn —facilitados porque la base de datos se llamaba como uno de ellos—. La instancia fue apagada preventivamente.

Cómo se eligió el objetivo

La selección de PL/Perl fue deliberada: es parte del repositorio oficial de Postgres, así que viene incluida en muchas instalaciones y multiplica el impacto; Perl es un lenguaje de los años 80, con décadas de código escrito con una conciencia de seguridad muy inferior a la actual; tiene variables "mágicas" integradas que son terreno fértil; y al ser open source resulta fácil inspeccionarlas.

Esta clase de hallazgos no es rara. El caso de "Sekicle umbrella" de Emerico Rodi en GCP siguió una línea parecida, y el mismo equipo descubrió poco después una vulnerabilidad en Azure Cosmos DB for PostgreSQL que también permitía ejecutar código en el backend. El patrón se repite: los servicios gestionados son enjambres de microservicios donde algo puede salir mal, y conviene buscar RCE en todos ellos, no solo en las cargas de trabajo de moda.

Técnicas y herramientas mencionadas

  • PostgreSQL: base de datos relacional open source y extensible, base de las ofertas gestionadas de prácticamente todos los proveedores de nube.
  • AWS RDS: servicio gestionado cuyo usuario admin no es superusuario de Postgres; escenario donde se validó el RCE.
  • Extensiones de lenguaje (PL/Perl, PL/Rust): mecanismo de Postgres para definir funciones en otros lenguajes, divididas en trusted y untrusted.
  • %ENV de Perl: hash mágico que expone las variables de entorno del proceso; vía de escritura desde un lenguaje trusted.
  • Cargo y rustc: gestor de paquetes y compilador de Rust, invocados al compilar funciones PL/Rust.
  • CARGO_BUILD_RUSTC_WRAPPER: variable de entorno no sanitizada por PL/Rust que permite sustituir el binario del compilador.
  • rust-gdb y RUSTGDB: script de la toolchain de Rust que ejecuta el contenido de esa variable; pivote final hacia comandos arbitrarios.
  • bash ENV: parámetro que bash expande antes de arrancar, usado para adaptar el exploit al entorno restringido de RDS.
  • GitHub Search y Copilot: herramientas empleadas para rastrear extensiones que lanzan procesos sin la API de Postgres.

Conclusiones

  • La barrera "trusted vs. untrusted" de los lenguajes de Postgres es frágil: un lenguaje supuestamente confinado permitió alterar variables de entorno del proceso, y eso bastó como primera piedra de un RCE completo.
  • Las variables de entorno son una superficie de ataque sistemáticamente subestimada: sanitizar una variable (RUSTC_WRAPPER) sin su equivalente (CARGO_BUILD_RUSTC_WRAPPER) dejó la puerta abierta.
  • Los servicios gestionados en la nube merecen la misma atención de seguridad que las cargas de trabajo propias: un RCE en Postgres gestionado toca territorio del proveedor y puede escalar a amenazas entre tenants.
  • Para administradores: mantener Postgres al día al menos en versiones menores (el parche cubre desde la versión 12), aplicar el mínimo privilegio —sin crear funciones ni instalar extensiones a usuarios que no lo necesiten— y restringir las extensiones cargables con el parámetro allowed_extensions.
  • Para la comunidad: la investigación responsable sobre nube debería institucionalizarse, con marcos que permitan verificar que un exploit no alcanza recursos de red ni acceso entre tenants.
