Resumen

El Remote Procedure Call (RPC) es el mecanismo de comunicación entre procesos que Windows usa por todas partes: los servicios del sistema se hablan entre sí mediante servidores RPC que exponen interfaces. Toda la investigación ofensiva clásica sobre MSRPC apunta al código vulnerable de los servidores para conseguir RCE o escalada de privilegios. Este trabajo da la vuelta: ataca el código de los clientes.

La idea nace de una analogía con DNS. El endpoint mapper (EPM) de Windows funciona como un servidor DNS, pero resuelve UUIDs de interfaz RPC a endpoints de comunicación. Si existe el DNS poisoning, ¿existe el EPM poisoning? La respuesta es sí, y no hace falta ningún privilegio para montarlo: un proceso de integridad media puede registrarse en el EPM con la interfaz de un servicio del sistema —incluso de uno crítico como Windows Defender— y el mapper le reenviará clientes sin hacer ninguna verificación de identidad.

Encadenando esa usurpación con un servicio de arranque tardío, un método indocumentado que devuelve una ruta y una máquina unida a un dominio, se consigue que un servicio protegido autentique con NTLM usando las credenciales de la cuenta de máquina. El fallo del storage service fue reconocido por Microsoft y parcheado el 8 de julio.

Cómo funciona el RPC de Windows

Un servidor RPC expone funcionalidades que los clientes le piden ejecutar en su nombre. Ambos lados comparten un archivo IDL (interface definition language) con structs, enums, funciones y, sobre todo, el UUID de la interfaz: el identificador único con el que el servidor se registra y el cliente lo busca.

Antes de comunicarse, el cliente crea un binding handle con tres partes:

  1. Secuencia de protocolo: TCP, named pipes sobre SMB, o LPC/ALPC para comunicación local eficiente y segura. La mayoría de servidores RPC de Windows usan endpoints ALPC.
  2. Dirección de red: IP o nombre del equipo.
  3. Endpoint: el puerto (TCP), el nombre del pipe (SMB) o un string único (LPC).

Al registrarse, un servidor puede declarar su endpoint (well-known, hardcodeado en el cliente) o dejar que el sistema le genere un string dinámico (dynamic endpoint). Ahí aparece la pregunta clave: si el endpoint dinámico es aleatorio, ¿cómo lo encuentra el cliente? Por el endpoint mapper, que mapea cada UUID a los endpoints que lo exponen y conecta al cliente con el primer servidor que registró esa interfaz (el orden no puede modificarse; las entradas solo se quitan cuando el proceso original se desregistra o muere).

EPM poisoning: sin credenciales, sin privilegios

El primer hallazgo fue casi decepcionante de tan fácil: con la API RpcEpRegister, un proceso cualquiera registra una interfaz que pertenece a un servicio del sistema y funciona. Sin admin, sin elevation. El EPM no comprueba nada sobre quién registra qué.

El matiz: los clientes solo llegan si el servicio original todavía no se registró. Registrando la interfaz de un servicio apagado, el cliente conectó inmediatamente al impostor. La conclusión estructural: todo servidor RPC que no arranca en el boot es secuestrable.

Para cazar objetivos se desarrolló RPC Recon (público en GitHub): un tool que se lanza como tarea programada al iniciar sesión, consulta el EPM y escanea la memoria de los procesos (localizando el módulo RPCRT4 y parseando sus estructuras internas) para listar endpoints well-known y dinámicos. Escanea dos veces —temprano en el boot y varios minutos después, cuando arrancan los servicios diferidos— y la diferencia entre ambas pasadas son las interfaces que se pueden registrar antes que el servicio legítimo.

Primer intento: impersonar y chocar con la política

Armado con una lista de objetivos, un servidor RPC genérico se puso a registrar interfaces y a recibir conexiones de procesos que corren como Local System. La escalada más intuitiva falló: llamar RpcImpersonateClient y crear un proceso con el token obtenido devuelve "bad impersonation level". La razón es la política de impersonación: un thread de integridad media solo puede obtener el nivel identification (consultar quién es el cliente) sobre un token de integridad superior, no el nivel impersonate (actuar con su contexto de seguridad) ni delegation (acceder a recursos remotos con él).

El segundo intento —usar el token para autenticar NTLM contra un SMB propio y capturar el hash— choca con la misma política: el acceso a recursos remotos exige delegation.

Segundo intento: servicios de autenticación y el QoS de seguridad

Cambiando de enfoque, se buscó entre las interfaces vulnerables una cuyo secuestro entregara credenciales directamente: nombres con "credentials", "identity", "accounts" apuntaron al Vault service, Microsoft Account Signing Assistant y Sync Host. Ninguna conexión llegó. Motivo: el security quality of service del binding handle. Un cliente puede exigir que el servidor corra como un SID concreto (por ejemplo, NT AUTHORITY\SYSTEM); si el impostor corre como otro usuario, la conexión se rechaza. Microsoft Account Signing Assistant hace exactamente eso antes de aplicar el binding.

Tercer intento: el storage service y la ruta maliciosa

Recapitulando: conexiones de servicios privilegiados sin posibilidad de impersonar; servicios de autenticación que exigen un SID específico. La tercera vía fue pedirle al servicio víctima que hiciera una acción que el atacante no puede hacer nativamente, como escribir en system32. Mascarándose como servicio de sistema de archivos, algún cliente privilegiado pediría datos que luego copia donde sea.

El elegido fue el storage service (implementado en fileStoreSVC.dll, configurado con delayed start). Su lista de clientes deja sin aliento: Windows Update —un servicio que puede modificar drivers y DLLs del core— conecta a un proceso desconocido sin privilegios. Luego conectó el propio storage service (se usa a sí mismo como cliente, pero el impostor se registró primero) y el delivery optimization service, que corre como Protected Process Light, la clase de proceso más protegida de Windows. Hasta los procesos más blindados caen en la trampa.

De los 36 métodos de la interfaz, solo tres se invocaban. Dos devolvían enteros (poco útil); el tercero, getStorageDeviceInfo, devolvía una estructura indocumentada con mucho más potencial. Para entenderla se miró el lado cliente: el call stack atravesaba AppXDeploymentClient, cuyos símbolos públicos contenían enums, nombres de variables y toda la definición necesaria, incluida una ruta.

Comparando el desensamblado de todos los clientes se encontró la joya: el delivery optimization service hace unos sanity checks sobre la ruta recibida (superables devolviendo un share de red hacia C: de la máquina local) y luego crea un directorio basado en esa ruta. Un proceso sin privilegios dicta una ruta que un proceso privilegiado usa. Probado: se creó un directorio en el home del usuario del servicio.

La cuenta de máquina: cruzar la frontera

¿Por qué importa? El delivery optimization corre como Network Service: token de integridad altísima, pero fuera del grupo administradores. Su propósito es poder autenticarse contra máquinas remotas, y lo hace con la cuenta de máquina: la cuenta que Active Directory crea en NTDS para cada equipo unido al dominio, reconocible por el $ final. Las sesiones de usuarios logueados no pueden usar esas credenciales; solo Local System y Network Service.

La vulnerabilidad rompe justo esa frontera: devolviendo un share de un servidor externo, el delivery optimization autentica NTLM contra él con la cuenta de máquina, y el atacante retransmite (relay) la autenticación. El exploit completo vive en RPC Racer (también público): lanza una tarea programada al logueo, registra la interfaz del storage service, deja que delivery optimization pida la ruta y recibe la autenticación NTLM de la cuenta de máquina para retransmitirla.

Impacto en dominio: ESC8 y volcado de secretos

Relayar el NTLM de vuelta a la misma máquina está bloqueado por mitigación, así que hay que encontrar otro servidor en el dominio. El caso ideal: correr el attack desde un domain controller y apuntar al ESC8, la explotación del web enrollment de Active Directory Certificate Services (ADCS). La cadena:

  1. NTLMRelayX (Impacket) recibe la autenticación de la cuenta de máquina del DC y la retransmite al web server de ADCS, obteniendo un certificado que representa esa cuenta.
  2. Certify pide al DC un TGT (ticket granting ticket de Kerberos) a partir del certificado.
  3. Con el TGT de la cuenta de máquina del DC, SecretsDump (Impacket) vuelca los hashes de todos los usuarios del dominio.

La demostración completa: SMB relay, logueo sin privilegios, reinicio, autenticación capturada, certificado, TGT y volcado de secretos del controlador de dominio.

Detectar y corregir

El parche de Microsoft (8 de julio) tocó al cliente del storage service: en vez de un binding handle simple, ahora aplica un security QoS que exige que el servidor corra como Local System. Pero como solo se parcheó ese cliente, quedan muchos otros expuestos al EPM poisoning. Sugerencias de detección:

  • Hooking de RpcEpRegister: si un proceso no legítimo intenta registrar una interfaz built-in conocida, alertar.
  • ETW: el provider Microsoft-Windows-RPC registra eventos que correlacionan el PID del impostor, el PID de la víctima y la interfaz secuestrada, incluso el número de procedimiento invocado.

Otras vías con el mismo primitivo: ataques man-in-the-middle reenviando peticiones al servicio original y filtrando llamadas para ocultar el foothold; denegación de servicio silenciosa registrando interfaces ajenas; envenenar los archivos de configuración que el delivery optimization busca en la carpeta privada que el atacante ahora controla (lkg.dat con URLs de descarga, dosvcstate.dat con CDN URL y working directory). Y candidatos evidentes para seguir investigando: Windows Security Center (delayed start, interactúa con Windows Defender) — secuestrarlo podría quizá neutralizar al antivirus.

Lecciones

  • Verificar la identidad del servidor, siempre. Como SSL pinning valida que el certificado use una clave pública concreta, los clientes RPC deberían validar quién está del otro lado. El diseño actual del EPM no lo hace; la carga recae en el cliente.
  • Los delayed starts son deuda de seguridad. Se configuran para acelerar el boot, pero cualquier ventana donde código no confiado pueda ejecutarse antes es terreno de ataque. El rendimiento no puede pagarse con seguridad.

Herramientas publicadas: RPC Recon (mapear interfaces secuestrables) y RPC Racer (explotar y observar clientes), ambas en GitHub.
