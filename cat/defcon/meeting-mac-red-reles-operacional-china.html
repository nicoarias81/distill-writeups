Meeting Mac: anatomía interna de una red de relés operacionales basada en China

Fuente: «DEF CON 33 - Inside Look at a Chinese Operational Relay Network - Michael Torres, Zane Hoffman» · ver el video original

  • Video: e93V9TWnxJo · URL: https://youtu.be/e93V9TWnxJo · Conferencia: 01_defcon · Título original: DEF CON 33 - Inside Look at a Chinese Operational Relay Network - Michael Torres, Zane Hoffman

Resumen

Las redes de relés operacionales (ORB, operational relay networks) son la infraestructura invisible que usan actores maliciosos para ocultar el origen de sus operaciones: enjambres de nodos que reenvían tráfico para lavar la atribución. Entender cómo están construidas y de qué servicios gratuitos se alimentan es una de las preguntas más difíciles de la seguridad ofensiva-defensiva actual.

Este artículo documenta el hallazgo accidental de una de esas redes —bautizada "Meeting Mac"— a partir de una investigación completamente distinta: la búsqueda masiva de secretos filtrados en imágenes de Docker Hub. Desde esa puerta de entrada inicial, dos investigadores reconstruyeron durante meses la infraestructura completa: proveedores en la nube abusados, esquemas de contraseñas, dominios, direcciones de correo, cuentas de redes sociales, herramientas de gestión de identidades y hasta registros de chat con asistentes de IA usados para desarrollar la propia red.

El valor del análisis es doble: un mapa concreto de cómo opera este tipo de red (almacenamiento gratuito, cómputo serverless, túneles, API de credenciales con huellas de navegador) y una advertencia práctica para cualquiera que publique contenedores: lo que se "borra" de una imagen sigue ahí, y lo que se copia sin cuidado llega a públicos no previstos.

Origen: secretos en Docker Hub

Todo empezó en DEF CON 32, viendo una demo del Docker exploitation framework que mostraba cómo identificar archivos marcados con whiteout en imágenes de contenedores. Cuando borras un archivo de una imagen de Docker, este no desaparece del tarball completo: queda registrado como "eliminado" pero sigue presente en el overlay FS. La idea inicial era buscar a escala secretos publicados accidentalmente: archivos .env, contraseñas, claves SSH.

La primera versión fue, en palabras propias, "el peor Trufflehog del mundo": un regex sobre imágenes descargadas masivamente, empezando en una habitación de hotel. Los primeros cinco hallazgos motivaron ampliar el alcance a claves de API de proveedores cloud, claves SSH y contraseñas en general. En tres meses llegaron a 240.000 hallazgos indexados en Elasticsearch, con muchos falsos positivos (claves de ejemplo, bots de trading cripto repetidos decenas de veces), y al ritmo de 5.000 contenedores al día tuvieron que contratar la cuenta premium de Docker Hub justo antes de que el proveedor anunciará un límite de 50.000 descargas mensuales para ese tier.

El pivote: repositorios Git privados

Con demasiado ruido, el siguiente paso fue buscar dentro de los contenedores archivos .git/config, que indican si la imagen proviene de un repositorio privado. El patrón que lo hace posible es el flujo de containerización típico: hacer git clone del repositorio, crear un Dockerfile basado en una imagen base (FROM ubuntu) y copiar todo con COPY . .. Esa instrucción copia también archivos y directorios ocultos: el .env filtrado y, sobre todo, la carpeta .git completa del repositorio clonado. Cuando un pipeline de CI hace clone → build → push a Docker Hub, si el repositorio es privado pero la imagen es pública, el contenido del repositorio viaja con la imagen.

De más de 80.000 contenedores analizados en tres meses, unos 15.000 contenían metadatos Git y 1.500 correspondían a repositorios no públicos (identificados por respuestas 404 al consultar el remoto, o redirecciones a dominios corporativos tipo git@empresa.com). Entre los hallazgos: una rama enterprise de un proyecto open source de Apache, un fabricante ruso de cámaras de salpicadero y reglas de detección privadas de un proveedor de seguridad. Los intentos de reporte, incluyendo correos al autor del último commit del log, no obtuvieron respuesta.

Detalle extra del .git/config: contiene también el token usado por el job de CI para hacer push. Esos tokens de CI son de vida corta y sin permisos de escritura, pero algunos usuarios usan personal access tokens con permisos de lectura-escitura para sus pipelines. En ese caso, extraer el token da acceso de escritura al repositorio privado, y cualquier push posterior dispara otro job de CI que incluye el código inyectado en la imagen pública del contenedor —un vector de cadena de suministro con potencial serio, demostrado en directo escribiendo en el README del repo víctima.

Meeting Mac: la red que emergió

Entre el ruido, un usuario de Docker Hub destacaba: subía varios contenedores al día, con actualizaciones constantes, y sus imágenes activaban alertas por contener repositorios Git privados. Al mirar el contenido parecía usar Docker como almacenamiento cloud gratuito: gigas de datos etiquetados como "backups". Alrededor de las 22:40, una mirada más profunda reveló que esos backups apuntaban a infraestructura cloud que se levantaba y destruía dinámicamente para proxyar tráfico, con redirecciones al Great Firewall. El interés inmediato desembocó en meses de investigación.

La red resultó ser, con confianza alta, una red de relés operacionales basada en China (PRC): infraestructura que hace de proxy para actores maliciosos, de las mismas que Google ha documentado usando a actores chinos de amenazas. Con confianza media: sirve para proxyar tráfico web, gestionar cuentas de redes sociales y navegar de forma anónima. Con confianza baja: no hay pruebas directas de operaciones maliciosas dentro de los backups, aunque sí herramientas y evidencia de uso puntual — un paquete PyPI malicioso (visible todavía en VirusTotal) y un log de listener de Cobalt Strike, aparentemente de pruebas. La red está en desarrollo desde 2022, con múltiples personas implicadas (los backups contienen mensajes entre varias personas usando un formato .rec de aplicación de notas que no se pudo identificar) y múltiples personas operativas.

El almacenamiento se reparte entre Docker Hub, Mega y repositorios de GitHub; el cómputo combina VMs tradicionales con cómputo serverless (GitHub Actions, Hugging Face, con los nodos de Hugging Face numerados en la serie 42x); los datos se persisten en TerraBox (el de mayor volumen), Backblaze, Hugging Face Spaces, GitHub, OneDrive y las propias imágenes de Docker.

Dominios, correos y contraseñas

De los dumps salieron los dominios principales del hub, además de servicios internos curiosos: un dominio de acceso a repositorios privados (si conocés la estructura de directorios, podés navegar y descargar los archivos), un servidor propio de hosting de herramientas y scripts que se descargan al aprovisionar infraestructura, y dominios varios que apuntan a Cobalt Strike crackeado. Los correos superan los 50, con herramientas propias para crear cuentas en Outlook y Gmail.

La plantilla de contraseñas es sistemática: dos letras iniciales, unos caracteres que no se revelan, un @ y una letra derivada del nombre de usuario (para temp0230 la letra era t; para Coral86, CO). Esa misma contraseña se usa en correos, gestión de dominios, redes sociales y prácticamente todo. Hay además claves de API en texto plano por todo el código y las notas: Heroku (nodos de salida) y GitHub dominan, junto con una clave de Grok y otra de xAI que usaban para desarrollo asistido por IA —accediendo a esos servicios a través de su propia red, ya que desde China están bloqueados.

Un token de OneDrive, al ser un JWT decodificable, reveló un correo en un dominio compartido de universidades chinas (host.ac.cn) y una IP residencial de China Telecom en el ASN correspondiente.

La API de credenciales

La red opera una API que sirve credenciales a sus propios operadores o usuarios. Además de claves de API, persiste cookies de navegador y huellas de navegador (browser fingerprints): no basta con reutilizar un session ID, también se imita la huella del navegador original para evadir detección de cuentas automatizadas o para suplantar por completo la sesión robada a un usuario.

Grupos de trabajo y acceso a nodos

Los servicios se organizan en work groups:

  • Social: headless Chrome, presumiblemente para gestionar cuentas de redes sociales.
  • Op stations: Visual Studio Code Web y ttyd (terminal web) sobre la máquina objetivo.
  • Scraper: llamadas a APIs de terceros y salida propia para scrapear sitios web, devolviendo contenido crudo y capturas de pantalla bajo demanda.

Todos los nodos corren SSH y VNC para administración. El acceso se orquesta desde un servidor hub central mediante reverse port forward, con un esquema de puertos predecible: el ID del nodo de tres dígitos concatenado con el puerto del servicio (node 123 + SSH → puerto 12322). Un puerto 90 en cada nodo devolvía el bloqueo del Great Firewall, lo que sugiere un servicio interno no accesible desde fuera.

El paquete PyPI malicioso y btPanel

El paquete PyPI, llamado ptmpl, descargaba un script desde uno de sus dominios y lo ejecutaba, con un hook post-instalación que hacía exactamente eso: descargar de internet y ejecutar como script Python. Sin sofisticación, pero funcional.

La joya fue btPanel, un equivalente chino de cPanel implementado en Python/Flask que la red usaba para administrar servidores. La investigación de vulnerabilidades sobre él arrojó dos vías de RCE como root si sos man-in-the-middle:

  1. Módulo PAM en texto plano: el panel descarga un módulo PAM sin cifrar; un MITM puede sustituirlo por uno malicioso que se ejecuta como root en el próximo inicio de sesión. (Parcheado.)
  2. Script de instalación/actualización inseguro: descarga RPMs y tarballs por HTTP y se ejecuta como root; seguía sin parchear al momento de la publicación del trabajo, con detalles publicados en colaboración con SSD Disclosure.

A eso se suman fallos de diseño en autenticación: el TOTP de doble factor usa la misma clave para todos los usuarios (registrando tu propio autenticador obtenés los códigos de todos), y el "one-time password" de SSH es en realidad una credencial estática sin expiración.

Vibe coding: la IA también construye infraestructura maliciosa

En los backups aparecieron logs de bases de datos y chats con asistentes de IA usados para desarrollar la red. Los operadores, al tener ya partes del sistema funcionando, podían usar su propia infraestructura para acceder a modelos como OpenAI pese a los bloqueos geográficos desde China. Los chats —en chino simplificado, pasados por Google Translate, y en inglés— muestran pedidos de ayuda para implementar nuevas funciones, configurar la estructura de directorios para que Cursor trabaje mejor, y lluvias de ideas sobre nuevos servicios a ofrecer. Hay evidencia puntual del uso de Cursor como entorno de desarrollo.

Última actualización y lecciones

El último contenedor actualizado se vio el 20 de junio. Para entonces habían implementado cifrado en sus datos, pero como el esquema de generación de contraseñas ya era conocido, el cifrado resultó inútil: se descifró todo de nuevo, revelando nuevos repos Git y direcciones de correo.

Lecciones prácticas:

  • Docker Hub: los contenedores públicos arrastran secretos con ellos. Se recomendó a Docker un .dockerignore por defecto; confirmaron recepción y no hubo respuesta hasta que se anunció la publicación.
  • GitHub y GitLab: el .git/config incluye credenciales en texto plano por defecto; se sugirió cambiar ese comportamiento. La respuesta fue que es un problema de configuración del usuario —lo es, pero el valor por defecto importa—.
  • La nube no es solo de los buenos: plataformas cloud, incluidos los free tiers, sirven para construir infraestructura de ataque o de manipulación de redes sociales. La misma facilidad que permite a cualquiera levantar servicios distribuidos está disponible para quien quiera abusar de ella.

Técnicas y herramientas mencionadas

  • Whiteout en Docker overlay FS: los archivos borrados de una imagen siguen presentes en el tarball completo; base de la búsqueda de secretos.
  • Trufflehog / regex a medida: herramienta clásica de detección de secretos; aquí reimplementada de forma mínima para escanear imágenes a escala.
  • .git/config en imágenes de contenedor: identifica el repositorio remoto de origen y, a veces, tokens de CI o personal access tokens con permisos de escritura.
  • COPY . . en Dockerfile: instrucción que arrastra archivos ocultos, incluyendo .env y .git, al construir la imagen.
  • Cadena de suministro vía token de CI: si el token tiene permisos de escritura al repo, se puede inyectar código que termina en la imagen pública tras el siguiente push.
  • Elasticsearch: índice de los 240.000 hallazgos para exploración y filtrado.
  • ORB (Operational Relay Network): red de nodos proxy que oculta el origen del tráfico; el objeto de estudio bautizado Meeting Mac.
  • NPS y FRP: herramientas de túnel/C2 usadas por la red; el fingerprint de FRP fue modificado (renombrando claves) para evasión.
  • Headless Chrome, VS Code Web, ttyd: servicios de los work groups de la red (social, op stations, scraper).
  • Reverse port forward con esquema de puertos nodeID+servicio: patrón de acceso centralizado a los nodos relay.
  • Browser fingerprints y cookies en la API de credenciales: persistencia de identidad de navegador para evadir detección o suplantar sesiones.
  • JWT de OneDrive: decodificable para extraer información adicional (correos, IPs).
  • ptmpl: paquete PyPI malicioso con hook post-instalación que descarga y ejecuta un script remoto.
  • btPanel: panel de administración chino (Flask) con RCE como root vía módulo PAM descargado en texto plano y actualizaciones por HTTP; MFA con TOTP compartido y OTP de SSH estático.
  • SSD Disclosure: publicación de detalles de las vulnerabilidades de btPanel.
  • Cursor y asistentes de IA: usados por los operadores para desarrollar la red, accediendo a modelos bloqueados en China a través de su propia infraestructura.

Conclusiones

  • Las imágenes de Docker públicas son una mina de secretos a escala industrial: 80.000 contenedores en tres meses arrojaron 240.000 hallazgos, 15.000 con metadatos Git y 1.500 apuntando a repositorios privados.
  • El vector más peligroso no es el secreto suelto sino la combinación: un .git completo dentro de una imagen pública expone código fuente, historia de commits y, en algunos casos, tokens de CI con permisos de escritura capaces de comprometer la cadena de suministro del proyecto.
  • Las redes ORB se construyen con servicios cloud legítimos y gratuitos (Docker Hub, Mega, GitHub, Hugging Face, Backblaze, Heroku, OneDrive), y su higiene de seguridad interna puede ser pésima: plantillas de contraseñas predecibles, claves SSH compartidas, MFA con semilla común y OTP estáticos.
  • La infraestructura ofensiva también se desarrolla con IA: los logs de chat muestran operadores usando modelos bloqueados en su país a través de su propia red de relés, con Cursor como entorno de trabajo.
  • Para el defensor, el valor de estos análisis está en los indicadores concretos: patrones de puertos (nodeID+servicio), dominios de hub, herramientas de túnel con fingerprints modificados y APIs de credenciales con huellas de navegador persistidas.
