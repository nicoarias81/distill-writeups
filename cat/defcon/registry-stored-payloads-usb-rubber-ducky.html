Payloads almacenados en el registro para USB Rubber Ducky

  • TL;DR

  • El USB Rubber Ducky se hace pasar por teclado y tipea a ~750 pulsaciones por segundo: un script de Invoke-Mimikatz de ~2 millones de caracteres tarda ~48 minutos en inyectarse, tiempo de sobra para que el objetivo reaccione.
  • Las evasiones clásicas fallan en entornos aislados: download-and-run exige conectividad, el almacenamiento masivo suele estar restringido por listas de allowlist (VID/PID/serie) y otros clases USB (adaptador de red con servidor web propio, dispositivo de imagen) también se detectan con facilidad.
  • La vía alternativa: antes de que Windows identifique la clase del dispositivo, la enumeración USB ya escribe en el registro los valores de los descriptores — y los descriptores Microsoft OS permiten definir propiedades de registro personalizadas con hasta ~64 KB de contenido arbitrario (REG_BINARY, nombre de propiedad y valor = payload).
  • El límite de 2 bytes del header del descriptor set se evita forzando re-enumeraciones sucesivas con VendorRevision distinto: el SO suma las nuevas propiedades al registro y las viejas persisten; un script de 96 KB se parte en dos enumeraciones (64 KB + 30 KB).
  • La reconstrucción se inyecta con apenas ~153 pulsaciones (o menos, almacenando los comandos de reconstrucción en otra propiedad y ejecutándolos con Invoke-Expression); funciona con cualquier archivo, no solo PowerShell, y no depende de clases USB.

El problema: la velocidad de tipeo

El USB Rubber Ducky es un dispositivo que parece un pendrive común pero que, al conectarse, se enumera como teclado y comienza a inyectar pulsaciones a velocidad inusualmente alta. En un entorno de pruebas, el máximo alcanzable ronda las 750 pulsaciones por segundo — y esa tasa es exactamente el talón de Aquiles: cuanto más largo el payload, más tiempo en el aire. Un script de PowerShell Invoke-Mimikatz de alrededor de 2 millones de caracteres necesita ~48 minutos de tipeo continuo; medio planeta de ventana para que el cliente detecte y bloquee el ataque.

Las evasiones clásicas y por qué no alcanzan

La solución tradicional es download and run: descargar el script de internet y ejecutarlo con Invoke-Expression, reduciendo las pulsaciones a un par de líneas. Pero en un entorno aislado (air-gapped) no hay conectividad — y los entornos aislados son justamente los objetivos de mayor valor.

Alternativa siguiente: hacer que el ducky se comporte como teclado y almacenamiento masivo a la vez, guardar el script en la partición de almacenamiento e inyectar las pulsaciones que lo copian y ejecutan. El problema: los entornos aislados suelen restringir el almacenamiento USB — allowlist por ID de proveedor, ID de producto o número de serie, o bloqueo directo del almacenamiento en las estaciones de trabajo con kioscos dedicados para transferir archivos. El almacenamiento masivo deja de ser una opción viable.

Queda la vía de usar otra clase USB para esconder el almacenamiento: la clase de comunicaciones (presentarse como adaptador de red, levantar un servidor web dentro del dispositivo e inyectar la descarga del script desde ahí) o la clase de imagen (presentarse como escáner y recuperar el script del dispositivo). Pero ambas también se detectan con facilidad: son clases inusuales en el inventario de un entorno restringido.

La ventana de enumeración: almacenar antes de que Windows decida la clase

La pregunta correcta: ¿existe una oportunidad de almacenamiento antes de que Windows identifique la clase del dispositivo? Sí — la propia enumeración.

Cada vez que un dispositivo USB se conecta, corre el proceso de enumeración: el dispositivo se presenta mediante los descriptores USB estándar (dispositivo, configuración, interfaz, endpoint y, opcionalmente, descriptores de cadena). Tras la enumeración, parte de esa información se propaga al registro de Windows: ID de proveedor, ID de producto, número de serie y nombre de producto — y todos esos valores los controla el dispositivo. Limitación: los descriptores estándar son cortos (4 caracteres para VID/PID, 126 como máximo para número de serie y nombre de producto), insuficiente para un payload real.

La puerta grande son los descriptores Microsoft OS, un mecanismo de Microsoft para dispositivos que no se ajustan a los descriptores USB estándar (dispositivos VR, webcams con sensor de profundidad, sensores industriales). Su propiedad clave: permiten definir propiedades de registro personalizadas para el dispositivo — valores de suspensión selectiva para ajuste de energía, GUIDs de interfaz de dispositivo, o cualquier propiedad que se quiera definir.

La estructura de un descriptor Microsoft OS tiene un descriptor set header más una serie de feature descriptors. Para almacenar contenido basta con un feature descriptor de propiedad que declare el tipo de dato (por ejemplo REG_BINARY), el nombre de la propiedad (por ejemplo LongPayload) y el valor — que es el payload real. Un descriptor opcional adicional, VendorRevision, declara a qué versión del dispositivo corresponde esa propiedad (revision 1 → propiedades de la versión 1).

Con esto, un script de PowerShell de ~45 KB (un Invoke-P0dsScan) queda íntegro dentro del valor de registro long_payload del dispositivo — visible con cualquier editor de registro como un valor de 45.000 bytes — y se despliega con ~90 pulsaciones: una inyección simple que busca la propiedad del dispositivo USB y ejecuta su contenido.

Superando el límite de 64 KB con re-enumeraciones

El techo: el header del descriptor set usa solo 2 bytes para representar el tamaño total del conjunto, así que ninguna propiedad puede superar los ~65.000 bytes. Pero hay escape: forzar una re-enumeración del dispositivo y enviar un descriptor set nuevo con valores de propiedad nuevos. Al ver los valores nuevos, el SO los agrega al registro de Windows — y los valores anteriores no desaparecen.

El procedimiento para un script de ~96 KB (WinPCap), mayor que el límite:

  1. Primera enumeración: VendorRevision = 1, se envía la primera parte del script → queda en LongPayload1 (~64 KB).
  2. Segunda enumeración (forzada): VendorRevision = 2, se envía la segunda parte → queda en LongPayload2 (~30 KB).
  3. Reconstrucción: la inyección consulta el registro del dispositivo, recupera la parte 1 de LongPayload1 y la parte 2 de LongPayload2, y las concatena — ~153 pulsaciones en total.

La mejora final: como a más partes, más pulsaciones de reconstrucción, los propios comandos de reconstrucción se almacenan en otra propiedad de registro (reconstruct). La inyección se reduce a leer esa propiedad y ejecutarla con Invoke-Expression: la variable pasa de longitud 0 a 96.000 bytes y WinPCap arranca. La demo de ejecución se registró en video: se conecta el dispositivo, aparece la clave de registro nueva, arranca la inyección de pulsaciones, se lee reconstruct y el script corre.

Ventajas, defensas y límites

Ventajas del método: no depende de ninguna clase USB — evita por completo las restricciones basadas en clases (ni almacenamiento masivo, ni red, ni imagen) — y no está limitado a scripts de PowerShell: archivos ejecutables, scripts de Python, cualquier cosa que quepa en el registro.

Defensas posibles: la más directa es deshabilitar las aplicaciones que permiten consultar el registro (reg.exe, cmd.exe, powershell.exe) en los hosts sensibles. Es una mitigación parcial — rompe herramientas de administración legítimas — y es una pregunta abierta si existen defensas más finas (por ejemplo, monitoreo de claves de registro de dispositivos USB creadas por enumeración, o detección de re-enumeraciones repetidas del mismo dispositivo con VendorRevision cambiante).

Límites a tener en cuenta: el canal depende de que el host acepte procesar los descriptores Microsoft OS (comportamiento estándar de Windows, pero sujeto a hardening del USB stack); cada parte cuesta una re-enumeración física — retirar y reconectar el dispositivo o forzar el reset del puerto —; y el contenido almacenado en registro queda expuesto a cualquier herramienta de consulta del registro del host mientras el dispositivo esté conectado.
