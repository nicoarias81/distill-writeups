Prompt injection: el LLM es un límite de confianza, no un oráculo

Fuente: «DEF CON 33 - Breaking down the anatomy of a prompt injection attack - Sean Perd» · ver el video original

  • Video: 2-C7xSJ9rhI · URL: https://youtu.be/2-C7xSJ9rhI · Conferencia: 01_defcon · Título original: DEF CON 33 - Breaking down the anatomy of a prompt injection attack - Sean Perd

Resumen

Sean Perd (integrante del equipo de respaldo / red team de Netflix) desarma el prompt injection como se desarma un exploit: qué es, cómo se arma payload a payload, por qué las defensas por listas negras no funcionan y qué hacer en su lugar. La tesis de cierre: hay que tratar el LLM como un límite de confianza propio — un "zero trust boundary" para LLMs — y aplicar a sus capacidades (leer archivos, llamar APIs, enviar datos) las mismas salvaguardas que a cualquier endpoint público.

Qué es y por qué funciona

Un prompt injection es una técnica de explotación específica de los LLM, con payload — "olvida tus instrucciones anteriores y..." —, goal — hacer que el modelo revele el system prompt, ejecutar comandos que no debería, modificar datos — y un objetivo — "victory condition": cuando el modelo reemplaza sus instrucciones originales, revela información sensible o bypassea las reglas de seguridad—. A diferencia de un bug de memoria, no es un bug del modelo: es el abuso del mecanismo que hace útil al modelo. Las inyecciones pueden ser directas (el usuario escribe el payload) o indirectas (el payload viaja dentro de los datos que el LLM procesa — un PDF, una página web, un email — y el modelo lo obedece sin que nadie lo vea).

Anatomía del payload

El ataque se construye con un proceso de cuatro pasos, ilustrado con ejemplos en vivo contra un chatbot con system prompt, incluyendo:

  • Jailbreak de modelo: hacer que el modelo ignore sus instrucciones (el clásico "ignore previous instructions").
  • Revelación del system prompt: el objetivo más común; hay un repositorio público con los system prompts de GitHub Copilot, Gemini, ChatGPT, Microsoft y compañía — todos han sido filtrados, incluso el de GPT-4o se filtró recién publicado.
  • Escalada: del texto a la acción, cuando el chatbot tiene capacidades (function calling): leer archivos, consultar APIs, ejecutar comandos. Ahí la inyección deja de ser molesta y se vuelve explotación con impacto.

Vulnerabilidades en el código: la demo del chatbot de facturas

La demo central es un snippet corto que integra la API de OpenAI con un asistente de soporte que consulta facturas. En pocas líneas conviven tres vulnerabilidades:

  • Prompt injection directa: el input del usuario entra al prompt sin sanitización, validación ni filtrado.
  • Prompt injection indirecta: el contenido de la factura (texto de un PDF devuelto por la API de invoices) se concatena al system prompt; si ese texto contiene instrucciones maliciosas, el modelo las ejecuta.
  • Falta de control de acceso (IDOR): la llamada a la API de facturas no lleva token ni restricciones — el chatbot puede devolver la factura de cualquier cliente. Si se le da al LLM capacidades, hay que aplicarle los mismos controles que a un endpoint público.

Defensas: el casino de las listas negras

Se repasan las defensas habituales y sus límites: monitoreo de output con regex (buscar palabras clave, detectar pedidos de base64), limitación de temas, stop sequences que cortan la generación ante palabras peligrosas o secretos, "false leads" (secretos falsos plantados para detectar al atacante), denegación sistemática ("always deny knowing the secret"), tagging del input del usuario con delimitadores custom, una segunda llamada LLM de verificación, e instrucciones pre y post en el prompt ("sandwich defense", con repetición). Veredicto: ninguna funciona sola, es apuestas — "estamos en Vegas": no hay silver bullet contra el prompt injection.

La arquitectura segura propuesta sí es defendible:

  • Pre-procesamiento del input: regex y reglas hardcodeadas antes de que llegue al modelo.
  • Modelos de contenido dañino: modelos especializados (Moderation API de OpenAI —gratuita—, modelos pequeños de HuggingFace entrenados para detectar jailbreaks, prompt injection y contenido dañino) aplicados tanto al input como al output — hay bypasses que solo se ven en la salida.
  • Access control real en cada capacidad que el LLM ejecute: el LLM es su propio límite de confianza.
  • Testing continuo: pruebas de caso de uso (prompts que deben funcionar) y de mal uso (inyecciones conocidas), automatizadas y repetidas — el modelo nunca responde igual dos veces, y las blocklists envejecen porque los modelos son intercambiables. Hacen falta end-to-end tests reales, como en el software tradicional.

Conclusiones

  • El prompt injection no es un bug del modelo sino el abuso de su mecanismo: payload, goal y victory condition; directo e indirecto (via datos que el LLM procesa, como PDFs de facturas).
  • Cuando el LLM tiene capacidades (APIs, archivos, comandos), la inyección escala a explotación real; la demo mostró un IDOR en la API de facturas conviviendo con dos inyecciones en pocas líneas.
  • Todas las defensas por listas negras (regex, stop sequences, false leads, tagging, sandwich) son apuestas: incluso los system prompts de los grandes proveedores están filtrados en un repositorio público.
  • La arquitectura defendible combina pre-procesamiento, modelos de contenido dañino en input y output, controles de acceso por capacidad y testing automatizado continuo.
  • El takeaway central: threat model todo y tratar al LLM como su propio límite de confianza — zero trust para LLMs — considerando todos los tipos de inyección sobre cualquier dato que se le dé o al que tenga acceso.
