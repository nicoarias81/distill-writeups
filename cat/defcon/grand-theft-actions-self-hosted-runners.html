Grand Theft Actions: supply chain a escala sobre self-hosted GitHub runners

Fuente: «DEF CON 32 - Grand Theft Actions Abusing Self Hosted GitHub Runners - Adnan Khan, John Stawinski» · ver el video original

  • Video: 5P7KatZBr_I · URL: https://youtu.be/5P7KatZBr_I · Conferencia: 01_defcon · Título original: DEF CON 32 - Grand Theft Actions Abusing Self Hosted GitHub Runners - Adnan Khan, John Stawinski

Resumen

Adnan Khan y John Stawinski cuentan cómo convirtieron una investigación de CI/CD en una campaña de doce meses que produjo más de 20 reportes de bug bounty high/critical contra organizaciones de la talla de GitHub Actions, Microsoft, PyTorch, TensorFlow, ByteDance o ASTAR. El caso central es un ataque completo contra el repositorio público de PyTorch, reconstruido paso a paso como estudio de caso de los TTPs de GitHub Actions: infiltración en la lista de contribuidores, persistencia en runners self-hosted no efímeros, robo del GITHUB_TOKEN y exfiltración de secrets con una cadena que termina en un escenario SolarWinds-class.

La tesis: GitHub Actions expone una superficie de ataque enorme cuando los self-hosted runners (gestionados y asegurados íntegramente por el usuario, a diferencia de los GitHub-hosted, que son efímeros y rotados por job) se conectan a repositorios públicos. GitHub lo desaconseja en la documentación, pero la advertencia está enterrada: quien registra un runner nunca la encuentra. Y el default inseguro — aprobar workflows de PRs solo para contribuidores de primera vez — hace que un typo mergeado sea una llave maestra.

El vector: defaults inseguros + typo

La receta de entrada es la misma en todos los ataques ("grammar police"):

  1. Encontrar un repo público con un self-hosted runner no efímero (candidatos vía GitHub code search + Sourcegraph; confirmación automatizada analizando los logs de los workflow runs, que filtran runner name, grupo y nombre de máquina — GatoX lo hace automáticamente).
  2. Enviar un PR trivial de corrección ortográfica en un markdown. Al mergearse, el atacante entra en la lista de contribuidores, y el default de GitHub deja de exigir aprobación para sus PRs futuros.
  3. Desde un fork, lanzar un PR malicioso que ejecuta código en el runner self-hosted (poisoned pipeline execution).

"Ser contribuidor no es un security boundary" — y el default de aprobación existe por conveniencia para repos muy activos, exactamente los más valiosos.

Runner-on-runner: persistencia que vuela bajo el radar

La técnica firma del ataque es el runner-on-runner (RoR): instalar un segundo self-hosted runner encima del runner comprometido. El runner implantado se registra contra un repo privado de C2 del atacante y se le puede taskear comandos vía workflow_dispatch — esencialmente un web shell. Ventaja operacional: todo su tráfico sale por los mismos dominios e IPs que usa el runner legítimo, así que un EDR en la máquina rara vez lo marca. En PyTorch implantaron C2 en tres runners distintos.

La clave de por qué esto escala a supply chain: los runners no efímeros ejecutan workflows futuros del repo base. El workflow del fork-PR del atacante no tiene acceso a secrets y su GITHUB_TOKEN es de solo lectura — pero al persistir, el atacante captura el GITHUB_TOKEN (y cualquier secret) de los workflows legítimos que corren después sobre el mismo runner. Ese token es un OAuth bearer con scopes configurados a nivel repo/org/workflow, válido solo durante la duración de cada job.

Post-explotación en PyTorch

Con el GITHUB_TOKEN capturado (con permisos actions:write y contents:write) de un build futuro:

  • Tampering de releases: vía API modificaron el título del último release de PyTorch para firmarlo con el nombre del investigador, screenshot, y revert inmediato. El mismo token permite borrar un release asset y subir uno backdoor encima; el único IoC visible en la UI es el timestamp.
  • Borrado de workflow run logs para cubrir huellas mientras dure la demostración.
  • Pipeline privilege escalation: los secrets interesantes estaban en workflows que no corrían sobre los runners comprometidos. La solución: el GITHUB_TOKEN no puede escribir en .github/workflows/ (GitHub lo bloqueó precisamente para frenar estos ataques), pero sí puede escribir fuera. Encontraron weekly.yaml → llama a _update_commit_hash.yaml → que ejecuta update_commit_hashes.py desde .github/scripts/, fuera del directorio restringido. Con el token crearon un branch, inyectaron un payload en ese script (guardar los tokens de entorno en archivos, cifrarlos con la pública del atacante y printearlos al log), dispararon el workflow con workflow_dispatch, recuperaron los blobs del build log, cancelaron el run, borraron los logs y desencriptaron.
  • Dos PATs robados (PyTorch update bot y PyTorch bot): tokens de larga vida, miembros de la org, con scope repo y acceso a 93 repos — muchos privados y sin branch protection. Caminos triviales a compromiso de supply chain: un bot crea el PR y el otro lo aprueba y mergea; backdoor de una dependencia interna de la org; o inyectar código en un feature branch en progreso y dejar que se mergee solo.
  • AWS keys del PyTorch bot: mismo esquema de workflow hopping. El usuario tenía S3 amplio, y la sorpresa final: esos buckets contienen los releases que sirve download.pytorch.org. Con esas keys se podía subir un release backdoor de PyTorch que todo usuario que instale siguiendo las instrucciones de la web ejecutaría. SolarWinds-style, directo.

La respuesta de Meta

Reportado a Meta Bug Bounty en agosto de 2023. Un mes después: "no hay update". Dos meses más tarde: "consideramos el issue mitigado" — los investigadores volvieron a entrar y ejecutar código en los runners para probar que no. Recién el 15 de diciembre, tras un email "fuertemente redactado", Meta aplicó fixes y ofreció una llamada con dos maintainers de PyTorch, que estaban al tanto y preocupados. Cuatro meses de exposición de un framework usado por OpenAI, Google y Lockheed Martin.

Automatización: GatoX

Todo el ataque requirió muchísima mano en el teclado, así que open-sourcearon GatoX, que automatiza el self-hosted runner takeover: enumerar runners no efímeros, crear fork, desplegar el payload RoR en un gist vía draft PR, esperar el check-in del runner y dropear un shell interactivo (cada comando se ejecuta taskando al runner implantado vía workflow_dispatch contra el repo de C2). Incluye un "hall of fame" en la wiki para quien encuentre y logre fixear vulnerabilidades de pwn-request, injection o self-hosted runner en proyectos open source.

Otros TTPs del arsenal

  • Solo-run build compromise: con persistencia en el runner, modificar scripts de build o el source ya chequeado antes del build; el artefacto final sale envenenado sin vínculo con el source original. Muy stealth.
  • Post-checkout hook: si el workflow con los secrets corre muy infrecuentemente, plantar un script en .git/hooks/ del repo clonado en el runner que exfiltre el .git/config (con el token), lo cifre y duerma 15 minutos — extiende la ventana de explotación del token sin romper el build ni avisar a nadie.
  • Inyección 90s-style en workflow_dispatch: si el input del dispatch se usa en una expresión ${{ github.event.inputs.* }} dentro de un github-script o run, basta el GITHUB_TOKEN con actions:write para disparar con input malicioso, cerrar la sintaxis del script e inyectar JavaScript/Python que pipea código de un C2 a bash.
  • Permisos peligrosos del token: contents:write + actions:write (el combo PyTorch: branches, scripts fuera de workflows/, dispatches), pero también pages:write, pull-requests:write y packages:write son explotables. Solo contents:write permite: modificar branches no protegidos, releases, tags (¡donde referencian reusable actions!) y disparar repository_dispatch.
  • Emboscada al developer: con contents:write sobre un feature branch, modificar un unit test con un info-stealer: cuando corra el workflow de CI, se compromete la cuenta del dev — en muchas orgs, game over.
  • Compromiso del default branch protegido: precondiciones — permitir que GitHub Actions apruebe y mergee PRs, máximo un reviewer requerido, y sin code owners. Atacante crea fork-PR malicioso, lo aprueba con el token capturado y lo mergea.
  • Runtime token y cache poisoning: robar el actions runtime token de workflows futuros abre ataques de GitHub Actions cache poisoning (blog del autor). Runner groups a nivel de organización compartidos con repos privados abren salto a repos privados y a otros grupos de runners.
  • OIDC abuse: señalado como tema de una investigación posterior del mismo track.

Recomendaciones

  • GitHub (lo que pidieron): advertencias ruidosas al conectar self-hosted runners a repos públicos, defaults más seguros en la aprobación de workflows, y requisitos de aprobación granulares en vez de tres opciones de privilegios amplios.
  • Organizaciones:
  • Activar la aprobación para todos los outside collaborators (un radio button que mata el vector del typo).
  • GITHUB_TOKEN en read-only — casi todos sus ataques dependen de permisos de escritura.
  • Personal access tokens fine-grained, nunca classic (los classic con scope amplio son la festa; los fine-grained de un solo repo cortan el lateral movement).
  • Runners efímeros de verdad: Actions Runner Controller en Kubernetes, autoscaling groups de cloud, o terceros; y ojo — la efimeridad incluye el entorno: un runner efímero sobre un file share persistente permite saltar entre workflows guardando archivos.
  • Runner group pinning: fijar grupos de runners a workflows o SHAs específicos para proteger los runners más privilegiados.

Conclusiones

  • El pipeline CI/CD es el "nuevo ADCS" de las redes internas: en casi cada red team los autores comprometieron la plataforma de CI y escalaron hasta el objetivo. El CI/CD interno es peor que el público.
  • El problema de fondo es la falta de awareness: los mismos TTPs funcionaron contra organizaciones maduras y avanzadas. 20+ reportes high/critical en doce meses, sin búsquedas exóticas.
  • Demostrar impacto real (screenshot del release firmado, buckets S3 que sirven download.pytorch.org) fue lo que movió las agujas: "ejecutar código en un runner" no mueve a nadie porque es lo que el runner hace de todos modos; mostrar el SolarWinds-class sí.
  • Y el mensaje final: no es sobre PyTorch — es sobre todos los que montan self-hosted runners no efímeros en repos públicos porque la documentación que lo desaconseja no se cruza en el camino.

Técnicas y herramientas mencionadas

  • Runner-on-runner (RoR): implantación de un runner self-hosted sobre el runner comprometido, registrado contra un repo de C2; tráfico indistinguible del legítimo.
  • Poisoned pipeline execution / pwn requests: ejecución de código en workflows privilegiados vía PRs de fork.
  • Captura del GITHUB_TOKEN desde builds futuros; scopes actions:write, contents:write, pages:write, pull-requests:write, packages:write y su impacto.
  • Restricción .github/workflows/ del token y su bypass via scripts fuera del directorio (workflow hopping + workflow_dispatch).
  • Exfiltración de secrets cifradas a build logs; post-checkout git hooks; solo-run build compromise; release asset tampering; tag tampering.
  • Workflow injection vía ${{ }} expressions en inputs de workflow_dispatch (github-script / run).
  • Self-approval de PRs con tokens capturados para comprometer el default branch protegido.
  • Cache poisoning con el actions runtime token; OIDC abuse; salto por runner groups de organización.
  • Herramientas: GatoX (enumeración y takeover automatizado, open source), Gato (predecesor, del trabajo Phantom of the Pipeline en ShmooCon 2023), AWS CLI, Wireshark no — GitHub API/curl, Grammarly como "arma" de los grammar police.
  • Referencias de contexto: Microsoft DeepSpeed (brecha previa de los autores), ASTAR/Polkadot (bug bounty "en mala fe", blog del autor), Hardware: runners en máquinas domain-joined.
