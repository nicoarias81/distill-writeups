Optimización peligrosa: la eliminación de stores muertos como vector de ataque en V8

Resumen

Los compiladores optimizan código asumiendo que ciertas escrituras no importan. Cuando esa asunción falla, el resultado no es un bug de rendimiento: es una vulnerabilidad explotable. El caso de estudio es un bug real de V8, el motor JavaScript de Chrome (CVE-2025-5419), donde el optimizador Turboshaft elimina incorrectamente un "store muerto" y termina entregando un primitivo completo de escritura dentro del heap de V8.

La tesis central invierte la perspectiva habitual: normalmente se habla de vulnerabilidades como de algo que ocurre cuando no debía (leer o escribir memoria donde no corresponde). Acá ocurre lo contrario —algo que debía suceder no sucede— y ese silencio es el bug. El material recorre el pipeline de un compilador (LLVM como ejemplo), explica qué es la dead store elimination, por qué puede romper el borrado seguro de secretos, y desarma paso a paso cómo un criterio de "store muerto" mal implementado se transforma en type confusion, fake objects y primitivos de lectura/escritura arbitraria en el navegador más usado del mundo.

El compilador como superficie de ataque

Un compilador es famoso por su complejidad —los libros de texto le ponen un dragón en la portada por algo— y esa complejidad tiene consecuencias de seguridad en cada fase:

  • Frontend (lexing, parsing, AST): procesa input no confiable. En Chrome, el JavaScript es input del atacante: el compilador de WGSL para WebGPU, por ejemplo, guardaba nombres de variables en buffers de tamaño fijo —y un nombre demasiado largo era un buffer overflow real.
  • Backend (selección de instrucciones, asignación de registros, encoding): diferencias entre arquitecturas generan errores propios; Chrome tuvo un caso en el que el chequeo de overflow de enteros de 32 bits para ARM se implementó mal, y el overflow pasaba desapercibido.
  • Middle end (SSA, IR, optimizaciones): donde vive el protagonista de la historia, la eliminación de stores muertos.

La lógica del compilador es notoriamente difícil de corregir: si optimiza mal, el binario no hace lo que el código fuente dice, y el programador ni se entera.

Dead store elimination: el árbol que cae en el bosque

Un dead store es una escritura a una variable cuyo valor nunca se lee después. Si se asigna a = 1 y de inmediato a = 2, la primera escritura no tiene efecto observable y el compilador puede borrarla. La analogía filosófica: si un store escribe en una dirección y nadie lo lee, ¿sucedió? Para el compilador, podría no haber sucedido.

El problema aparece cuando esa escritura "invisible" sí importa:

char buf[64];
/* ... leer datos del usuario ... */
memset(buf, 0, sizeof(buf));   // scrubbing: borrar secretos de memoria

Desde el punto de vista del optimizador, ese memset escribe y nadie vuelve a leer: es un dead store perfecto candidato a eliminación. Desde el modelo de seguridad, es la barrera que impide que shellcode residente en el proceso lea secretos del heap. La literatura académica (2017) documenta el problema, y la dead-store analysis insegura sigue siendo tema de investigación activa.

La matriz de casos aclara dónde está el peligro: eliminar un store realmente muerto es correcto; no eliminar uno vivo es solo código menos eficiente; pero eliminar un store vivo —o eliminarlo cuando una lectura ocurre en un contexto que el análisis no ve, como dentro del propio runtime o del GC— rompe la semántica del programa.

Dos muertes de un store

Un store muere dos veces, y conviene distinguirlo porque el bug de V8 vive en la segunda:

  1. Muerte por sobrescritura: un store posterior al mismo lugar tapa el valor; el primero es inalcanzable.
  2. Muerte por olvido: nadie vuelve a leer la variable (sale de scope o el valor retornado es constante).

En ambos casos, lo que mata al store viene después de él. La consecuencia estructural: el análisis debe recorrer el grafo de flujo de control hacia atrás, desde los puntos de retorno hacia el inicio, marcando qué se lee. Todo store cuya ubicación pueda ser leída después se marca "visible" y queda protegido; el algoritmo marca todos los stores como muertos al inicio y los "resucita" al encontrar usos. Si el manejo de alguna operación durante ese retroceso está mal —si una lectura que debería resucitar stores no lo hace—, stores vivos se eliminan en silencio.

El bug en Turboshaft (CVE-2025-5419)

En V8, la optimización de stores muertos vive en Turboshaft, la fase final del pipeline de compilación que recibe el IR de Turbofan. El retroceso por el CFG procesa cada operación; ante un load, verifica si debe resucitar stores. El criterio se apoya en una variable booleana: si la carga es "load-op" y su índice de operación es válido, se hace el chequeo de aliasing; si el índice se considera inválido, el código corta por una rama que no marca nada como visible —y los stores vivos mueren sin razón.

La validez del índice se decide con un valor sentinel: UINT32_MAX representa "índice no asignado". Ese sentinel solo queda en el índice si el nodo load se construyó por un camino específico del constructor, y ese camino depende de cuántos inputs tiene el nodo y de qué tipo de load es en Turbofan:

  • array.x con x variable (ElementLoad) construye el nodo por un camino que deja el índice sentinel → stores eliminados → bug.
  • array[const] construye un Load con índice válido → comportamiento correcto.

Así, el requisito para disparar el bug es hacer que el nodo load llegue a Turboshaft con exactamente dos inputs, pasando por la ruta de ElementLoad. Después de seguir más de diez capas de código fuente de Chrome, el gatillo es una carga de elemento sobre un array —nada exótico.

De POC a primitivos: anatomía del exploit

El POC. Una función热 (hot function, optimizada tras muchas invocaciones) escribe dos veces en el mismo índice de un array de floats: a[0] = 2.2 y luego, tras aritmética intermedia, a[0] = x con x que en teoría iguala el resultado. El segundo store es eliminado como falso muerto: la primera llamada devuelve 2.2 y, tras optimización, la segunda devuelve 1.1 —mismos argumentos, mismo código, resultado distinto. La divergencia observable es la firma del bug.

Internals de V8 necesarios. Los valores usan pointer tagging: el bit menos significativo distingue punteros (bit en 1) de Smis, enteros empaquetados (bit en 0, 31 bits de valor). Chrome además comprime punteros: guarda los 32 bits bajos y descomprime contra una base común. Un objeto JS (new Array(0x10000) lleno de 1.1) se ve en WinDbg como: map (define el tipo), properties (vacío), elements (puntero al backing store con los doubles), y el length con el bit de tagging que hay que desplazar. El backing store es un mapa seguido de los floats crudos.

Fake objects. Si esos doubles se eligen para que su representación hexadecimal coincida con un objeto JS válido, el atacante puede fabricar un fake array dentro de un array de doubles. Hacen falta dos piezas: un info leak (saber qué valores escribir: map, properties, length) y una type confusion que haga que el motor trate esos doubles como objeto. El bug lo provee: escribiendo de forma especial un valor "sin materializar" y dejando que el store eliminado preserve un valor controlado, la función retorna datos no inicializados —direcciones de mapas de los objetos preparados previamente—.

Encadenamiento del exploit, tal como se muestra en vivo en d8:

  1. Función trigger calentada para forzar optimización.
  2. Preparación de objetos victimas y spray para estabilizar el heap; liberación con gc() para crear huecos controlados.
  3. infoLeak: dos stores al mismo lugar; el segundo, mal clasificado como muerto, se elimina y la función retorna un valor no inicializado con direcciones comprimidas de maps.
  4. Con esos valores se construyen fake objects dentro de un gran array de doubles; sus direcciones se reservan y liberan para el paso siguiente.
  5. Segunda primitiva hace que el motor devuelva el fake object como un JSArray real: type confusion demostrada (un array "de doubles" que contiene un objeto array).
  6. readPrimitive / writePrimitive sobre el fake array: lectura del map de un objeto real y reescritura del tipo de un array existente (de objetos a doubles), otorgando lectura/escritura arbitraria.

Técnicas y herramientas mencionadas

  • Dead store elimination (DSE): optimización del middle end; peligrosa cuando el store implementa scrubbing de secretos o cuando el análisis de liveness falla.
  • Pipeline de V8: Turbofan genera el IR, Turboshaft optimiza y baja a código máquina; el bug vive en StoreStoreEliminationReducer y la construcción del TurboshaftGraph.
  • Liveness backwards sobre el CFG: los stores mueren "hacia adelante"; detectarlos exige recorrer el grafo desde los retornos.
  • Pointer tagging y pointer compression: bit bajo para Smi vs. puntero; punteros comprimidos a 32 bits con base común.
  • Fake object exploitation: doubles que codifican un objeto JS válido; requiere info leak + type confusion.
  • Herramientas: d8 (shell de V8), WinDbg para inspección de memoria, %DebugPrint.
  • Lectura de fondo: la página de Wikipedia sobre compiler optimization; literatura académica sobre dead store elimination insegura (2017).

Conclusiones

  • Las optimizaciones del compilador son una superficie de ataque de primera clase: un criterio de liveness levemente mal implementado se convierte en un primitivo de escritura completa en V8.
  • El bug no requiere técnicas exóticas de disparo: un ElementLoad con la forma correcta basta; la dificultad está en leer el código del compilador, no en el trigger.
  • Un "simpático" bug lógico de stores eliminados encadena a info leak → fake objects → type confusion → lectura/escritura arbitraria; desde ahí, el compromiso total del navegador es ingeniería conocida.
  • La defensa no puede apoyarse solo en revisión manual: compiladores son demasiado complejos y los humanos erramos de forma predecible. Hacen falta verificaciones sistemáticas de que el código compilado haga lo que el fuente dice —chequeos estáticos, y cada vez más, asistencia de LLMs—.
  • Para defensores: bugs de esta clase son extremadamente valiosos como primer eslabón y se combinan con otras primitivas para compromiso total del sistema.
