Splitting the email atom: discrepancias de parsers y bypass de control de acceso

Fuente: «DEF CON 33 - Splitting the Email Atom: Exploiting Parsers to Bypass Access Controls - Ben Harris» · ver el video original

  • Video: JERBqoTllaE · URL: https://youtu.be/JERBqoTllaE · Conferencia: 01_defcon · Título original: DEF CON 33 - Splitting the Email Atom: Exploiting Parsers to Bypass Access Controls - Ben Harris

Resumen

Las direcciones de email parecen mundanas, pero las RFCs que las gobiernan son francamente descabelladas. La premisa del hallazgo: predecir a qué dominio llega un email es inesperadamente difícil incluso para direcciones válidas conforme a la RFC — y eso importa porque muchas websites usan la parte del dominio del email para inferir la organización del usuario y aplicar control de acceso. Slack da acceso automático al canal de la empresa según el email de trabajo; Cloudflare Zero Trust puede configurarse para proteger la red interna por dominio. Eso convierte la verificación de email en un límite de seguridad crítico — y las discrepancias de parser en un vector de bypass.

Las discrepancias de parsers de URL están establecidas como críticas (SSRF, path traversal); las de email lo son igual, aunque apenas exploradas. El recorrido cubre: los cimientos inestables del email (source routes, el percent hack, el bang path de UUCP), las técnicas de generación de caracteres bloqueados (Unicode overflows, encoded word, UTF-7 y Base64), los case studies reales (GitLab Enterprise, GitLab como IdP, Zendesk, GitHub, WordPress, Cloudflare Zero Trust), el escalado a RCE vía punycode contra Joomla, la metodología y herramientas, y la defensa.

Los cimientos: protocolos antiguos dentro de direcciones modernas

La validación de email se suele hacer con regexes copiadas de Stack Overflow intentando seguir la RFC. Antes de preguntar "¿cuál dirección es válida?", la pregunta correcta es ¿a qué dominio van a llegar?. Dos direcciones visualmente idénticas dirigidas a example.com pueden llegar ambas a psres.net — una funciona en Postfix, la otra en Sendmail.

  • Quoted local part. La RFC permite caracteres normalmente prohibidos en la parte local si se encierran entre comillas (por ejemplo un @ literal), y quoted pairs escapados con backslash. Los comentarios entre paréntesis se ignoran al entregar.
  • Source routes. Una secuencia de servidores por los que el email pasa antes de su destino final, separados por comas, con el destino final tras dos puntos. Variante: el percent hack, donde el carácter (determinado por el mailer) se convierte en @ tras una primera entrega y el proceso puede repetirse.
  • Bang path (UUCP). El protocolo Unix-to-Unix Copy, anterior al email y a internet, separaba usuario y hosts con signos de exclamación, listando los hosts de izquierda a derecha con el buzón destino a la derecha.
  • El mecanismo del bypass: los paréntesis (o la escape del @) eliminan la parte del dominio, y sin dominio Postfix interpreta la dirección como source route y Sendmail como dirección UUCP. El descubrimiento fue empírico, no un análisis de código: un objetivo permitía caracteres especiales, el syslog mostraba "host unknown" en la delivery status notification, y acotar el carácter responsable (el signo de exclamación) reveló el comportamiento UUCP; un fuzzer posterior encontró el source route de Postfix. Bonus de la investigación: los parámetros SMTP opcionales de la RFC permiten eliminar la parte del dominio escapando el backslash para salir del quoted local part, cerrando el RCPT TO con > y escondiendo el resto de la dirección en el parámetro — verificado contra un target real como conversación SMTP válida. También en Postfix: direcciones UUCP que se envían ignorando las comillas, y source routes via sintaxis de corchetes.

Generar caracteres bloqueados: Unicode overflows y encoded word

Muchas aplicaciones bloquean múltiples @. Para sortearlo:

  • Unicode overflows. Un sistema sin soporte de Unicode alto trunca puntos de código >255 al rango 0–255 (como el chr de PHP: módulo tras un loop sobre negativos). En JavaScript, fromCodePoint con dos números (el overflow, p. ej. 0x100, y el carácter objetivo, p. ej. 0x40 = @) produce un carácter Unicode que, al transformarse, deviene el ASCII deseado. Caso real: un target que alteraba caracteres dentro de la conversación SMTP del mailer bloqueaba el backslash del quoted local part; el overflow lo evadió y permitió smugglear caracteres en la conversación SMTP (una doble validación — aplicación y envío — impidió el exploit completo, pero el patrón queda demostrado).
  • Encoded word (RFC 2047). Formato =?charset?encoding?data?= que permite incluir caracteres codificados que se decodifican al enviar: =?utf-8?q?=40?= es un @. Para sondear soporte: dos requests con dos charsets distintos (mayoría de librerías soporta charsets distintos), en minúscula, y un tercer follow-up con charset x para reducir falsos positivos; payload de collaborator como destino.

Case studies: Ruby Mail (508M de descargas)

La librería mail de Ruby se usa en GitHub, Zendesk, GitLab y Bugcrowd (versión testeada 2.8.1).

  • GitLab Enterprise: charset x + @ codificado (=40) + underscore (encoded word soporta =20 como espacio y también underscore): el email se parte en dos, GitLab cree que el dominio es example.com pero llega a psres.net. Impacto: verificar emails de dominios no controlados → acceso a servidores GitLab Enterprise con restricciones de registro por dominio.
  • GitLab como IdP: variante con > codificado y espacio codificado: GitLab cree un dominio, llega otro. Se puede spoofear y verificar cualquier dominio — Microsoft.com, GitHub.com, Mozilla.com verificados en la demo. Bypass de controles por dominio en toda website que use GitLab como identity provider, incluidas instancias de Cloudflare Zero Trust con validación por dominio de email.
  • Zendesk: quoted local part con comillas codificadas (=22), @ codificado, > y carácter null (el null evita que se use el resto de la dirección), más < codificado y doble comilla por los quirks del mailer — la teoría es que Zendesk parsea el email varias veces. Impacto: verificar emails de dominios no controlados → acceso a support centers protegidos por dominio.
  • GitHub: @ codificado + > codificado que cierra el RCPT TO + null character que descarta el resto de la dirección. Mismo bypass de controles por dominio con GitHub como IdP.

La escalera de la suciedad: Base64 y UTF-7 dentro del email

Durante el testing de librerías Ruby apareció soporte para direcciones Base64 (B como encoding type): =?utf-8?B?<base64>?= se decodifica y envía a la dirección interna. Peor: UTF-7, el charset del vector clásico de XSS en IE — las librerías de parsing lo aceptan (& como delimitador UTF-7). Y combinaciones: Base64 con charset UTF-7 (decodificación doble), y UTF-7 con Q-encoding dentro (dos capas). Todo funciona también en la parte del dominio. GitHub en su momento soportaba UTF-7 (parcheado antes de que el exploit llegara).

Fuera de Ruby: PHPMailer soporta encoded word en el nombre del destinatario — difícil de explotar en WordPress por la exigencia de angle brackets, pero candidato realista para bug bounty en sistemas que decodifican el nombre del destinatario.

De bypass a RCE: punycode y Joomla

El punycode representa caracteres Unicode en el DNS actual (siempre xn-- + secuencia alfanumérica y guiones). El algoritmo es frágil para testing: cambiar un byte puede alterar todo el output. El objetivo: generar caracteres maliciosos al decodificar. Experimentando con un convertidor online (librería PHP IDN) se lograron generar una coma y un @ añadiendo ceros al inicio de la secuencia. En GitHub apareció el target: Joomla, donde XSS equivale a RCE. Análisis de código: Joomla escapa el email antes de decodificar punycode — HTML producido por la decodificación daría XSS.

El fuzzer de punycode malformado (placeholders sustituidos por números, caracteres o espacios aleatorios) encontró múltiples caracteres generables, con restricciones duras: solo dos ASCII por subdominio, y Joomla prohíbe underscores en el dominio — descartando el vector con atributo entre comillas. Conclusión tras mucho testing: el único vector explotable era un tag <style> de apertura generado con punycode malformado, donde el HTML preexistente de Joomla aporta el espacio y el > de cierre.

La demo en vivo mostró el flujo completo: dos cuentas registradas (la primera con el style inyectado, la segunda con el payload CSS que hace import — ordenadas alfabéticamente A y X para que la inyección preceda al payload, y con llaves para que todo el HTML previo se trate como selector CSS inválido), el admin visita la página, el token se exfiltra, el ataque CSRF modifica el template de Joomla y el atacante obtiene RCE con cat /etc/passwd.

Metodología y herramientas

Método: probe → observe → encode → exploit. Sondear si encoded word se soporta; observar que se decodifica; codificar varios caracteres y observar la decodificación; recién entonces explotar abusando de esos caracteres.

Herramientas (libres, de PortSwigger): Hackverter (extensión Burp con tags para generar Unicode overflows y encoded word attacks), script de Turbo Intruder para explotar mailers (el null de GitHub se encontró así), fuzzer de punycode para generar punycode malformado, y wordlist actualizada de Burp Intruder.

Defensa

  • Filtrar o deshabilitar encoded word.
  • Verificar siempre la dirección de email antes de usarla, incluso si llega de un proveedor SSO.
  • Tras validar, nunca usar el dominio como único medio de autorización.
  • Material práctico: CTF de Web Security Academy para practicar email splitting y Docker file con la instalación vulnerable de Joomla.

Conclusiones

  • Direcciones de email perfectamente válidas pueden disparar discrepancias de parser mayores: incluso una dirección que termina en @example.com puede llegar a otro lado.
  • El corolario de seguridad: nunca es seguro usar dominios de email para enforcement de control de acceso — Slack, Cloudflare Zero Trust, GitLab, GitHub y Zendesk lo aprendieron con reportes reales.
  • La superficie explota en capas: source routes y UUCP (protocolos de los 70-80), Unicode overflows, encoded word, Base64 y UTF-7 anidados, y punycode malformado que escala de bypass a XSS y de ahí a RCE.
  • La ruta de descubrimiento fue observación empírica (syslog, delivery status notifications) más fuzzing — no reversing de miles de líneas de código.
