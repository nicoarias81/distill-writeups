Controles de acceso en GraphQL: el caso de la app de citas Feeld

Fuente: «DEF CON 33 - Examining Access Control Vulnerabilities in GraphQL: A Feeld Case Study - Bogdan Tiron» · ver el video original

  • Video: mPo-an8BUXc · URL: https://youtu.be/mPo-an8BUXc · Conferencia: 01_defcon · Título original: DEF CON 33 - Examining Access Control Vulnerabilities in GraphQL: A Feeld Case Study - Bogdan Tiron

Resumen

Un penetration tester analizó los controles de acceso de la API de Feeld, una app de citas popular en la comunidad de relaciones éticas no monógamas, y encontró ocho vulnerabilidades encadenadas: leer conversaciones ajenas, filtrar fotos y videos que debían autodestruirse, recuperar y editar mensajes borrados de otros usuarios, modificar perfiles ajenos, fabricar likes de perfiles falsos y hasta escribir en chats de terceros haciéndose pasar por alguien más. Todas las fallas se reportaron de forma responsable y ya están corregidas. El caso es un manual práctico de cómo auditar una API moderna con un proxy y dos cuentas.

La app y el terreno de juego

  • Feeld organiza su interfaz en cuatro menús: descubrimiento de perfiles, lista de personas que dieron like, chat con los matches y perfil propio con fotos, biografía y membresía premium.
  • El backend combina una API GraphQL con endpoints REST, más un servicio de mensajería de terceros (Stream) y un CDN de medios (Cloudinary).
  • El método de trabajo: interceptar el tráfico de la app móvil con Burp Suite, anotar cada operación GraphQL y cada endpoint REST, y usar dos cuentas (una atacante y una víctima) para comparar qué debe ver cada una.

Ocho vulnerabilidades, una tras otra

  1. Datos de perfiles a usuarios sin premium: la app oculta quién dio like tras fotos borrosas, pero la respuesta de la operación likesQuery llega completa desde el servidor. Copiando la URL de la "foto borrosa" se obtiene la imagen nítida y el perfil entero.
  2. Leer los mensajes de otros usuarios: con el ID de usuario de Stream filtrado en el paso anterior, basta una petición al endpoint /channels dejando solo el parámetro members con el ID de la víctima para recibir todas sus conversaciones.
  3. Filtrar fotos y videos "de un solo uso": los archivos se suben a Cloudinary y se sirven por dos endpoints (emisor y receptor) según el ID del archivo. El backend no valida quién pide: cualquier letra vale en la posición del ID de perfil. El resultado: fotos repetibles y fotos con autodestrucción a los 10 segundos quedaron accesibles sin autenticación desde un dominio de terceros.
  4. Borrar, recuperar y editar mensajes ajenos: un DELETE repetido sobre el mismo ID de mensaje devolvía el texto original "borrado", y un PUT con contenido nuevo lo reemplazaba sin dejar rastro visible para el destinatario, que no puede distinguir si quien editó fue el remitente original.
  5. Actualizar el perfil de otra persona: la operación profileUpdate no verificaba la propiedad del perfil.
  6. Recibir un like de cualquier perfil: combinando profileLike y profileQuery, se fabricó un like desde un perfil inexistente ("Annie, mujer, 26") que apareció en la cuenta víctima.
  7. Escribir en chats ajenos: el endpoint /channel/messaging/{channelID}/message aceptaba mensajes del atacante dentro de una conversación entre dos personas, y como los nombres de usuario no son únicos, era posible hacerse pasar por uno de los participantes.
  8. Ver los mensajes de otros chats: la operación chatListQuery completaba la cadena exponiendo listados de conversaciones ajenas.

Por qué la cadena importa

  • Cada falla alimenta la siguiente: el ID de Stream filtrado en el primer bug habilita la lectura de mensajes, de ahí salen los IDs de adjuntos y de canales, y con ellos se accede a los medios y se falsifican interacciones.
  • El diseño confió en que el cliente ocultaría datos (el blur de las fotos, la expiración de los archivos), pero el servidor los servía igual: la regla de oro es que el backend debe aplicar el control de acceso, no confiar en la interfaz.
  • La mezcla GraphQL + REST + servicios de terceros multiplica la superficie: cada proveedor externo (Stream, Cloudinary) introdujo supuestos propios que nadie validó de punta a punta.

Técnicas y herramientas mencionadas

  • Burp Suite como proxy para interceptar y manipular las peticiones de la app móvil.
  • Pruebas con dos cuentas (atacante y víctima) para comparar respuestas y verificar cada abuso de acceso.
  • Recon de esquema GraphQL: observación de operation names (likesQuery, profileUpdate, profileLike, chatListQuery) para mapear la superficie.
  • Manipulación de métodos HTTP (DELETE, PUT) sobre IDs de mensajes ajenos.
  • Análisis del flujo de medios: subida a Cloudinary con credenciales efímeras y construcción manual de URLs de descarga.

Conclusiones

  • Los controles de acceso rotos son la clase de vulnerabilidad más rentable en APIs: no requieren exploits sofisticados, solo observar qué devuelve el servidor cuando el cliente no lo pide.
  • Convención de nombres no es autorización: IDs de canales, mensajes y archivos deben validarse contra la sesión que los solicita, siempre y en todos los endpoints.
  • Feeld respondió con un proceso de divulgación responsable serio: los ocho reportes se aceptaron y se corrigieron, y el caso queda como ejemplo de auditoría bien hecha por ambas partes.
