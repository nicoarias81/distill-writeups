Cazando secretos y DNS huérfanos a escala con big data

Resumen

La búsqueda de vulnerabilidades en la nube siempre ha empezado por un objetivo: un dominio concreto, un repositorio, una carpeta. Esa mentalidad de "target primero" deja una enorme superficie sin explorar. La tesis de esta investigación es invertir el orden: empezar por la vulnerabilidad, no por el objetivo, y usar fuentes de datos masivas y poco convencionales para encontrar los bugs primero y preguntarse después a quién afectan. Aplicada a dos clases de bugs conocidas —recursos cloud huérfanos alcanzables vía registros DNS colgantes (dangling DNS) y secretos hardcodeados—, la inversión de perspectiva produjo resultados sin precedente público: más de 2 millones de IPs cloud enumeradas, más de 60.000 FQDN capturados y más de 15.000 secretos validados, con organizaciones como el Tribunal del Distrito Oeste de Texas, The New York Times, el estado de California, Dior, el workspace entero de Slack de Stanford o el tenant de Bixby de Samsung entre las afectadas.

La razón de fondo por la que estas clases de bugs existen es la misma en ambos casos: el camino de mínima resistencia es inseguro. Publicar una clave de API hardcodeada en el binario es lo más cómodo que permite la librería del proveedor, y dejar apuntando un registro DNS a una IP que ya se liberó es lo que ocurre si nadie recuerda limpiarlo. Los proveedores facilitan el camino inseguro por defecto; el remedio estructural es hacer que el camino seguro sea el default.

Recursos primitivos vs. compartidos: anatomía del dangling DNS

La nube funciona prestando recursos de un pool compartido. Cuando se libera una máquina virtual, su IP vuelve al pool, pero los registros DNS que apuntaban a ella —los dangling records— suelen sobrevivir. Quien consiga que el proveedor le asigne esa IP hereda el tráfico del dominio: phishing, distribución de malware, XSS, abuso de la confianza de marca, o saltarse la verificación de hosts de confianza de un instalador de actualizaciones. Según datos de APNIC, en torno al 75% de los recursos huérfanos secuestrados se usan para black hat SEO.

La distinción técnica que ordena el problema es entre recursos primitivos y compartidos. Un recurso primitivo —una VM— recibe una IP dedicada que ningún otro cliente usa, así que cualquier tipo de registro colgante (A, CNAME, NS, etc.) es explotable. Un recurso compartido —una función serverless— sirve a múltiples clientes desde la misma IP, así que solo importan los registros de aliasing: CNAME, NS, MX.

Derribar las disuasiones modernas de AWS y GCP

El playbook clásico de enumeración existía desde 2015 (Bishop Fox con datos de DNS pasivo contra el pool de AWS; el proyecto "Flying a False Flag" en Black Hat para backends de C2), pero los proveedores añadieron disuasiones que lo mataron. La investigación aquí demuestra cómo saltárselas todas.

En AWS, las Elastic IPs se reasignan de un pool pequeño ligado a la cuenta, y desde 2024 cada IP asignada cuesta un sobrecargo que encarece enumerar por fuerza bruta. La evasión es trivial: en lugar de Elastic IPs, reiniciar instancias EC2 con IPs efímeras una y otra vez. Así se rotan IPs únicas mucho más rápido —2,4 millones de IPs únicas en seis meses.

Google Cloud apiló más defensas: 10-15 proyectos por cuenta, IPs asignadas de un pool minúsculo (8 por región), y restricciones de cuentas de facturación por tarjeta de crédito. Todas se bypassean con tres primitivas:

  • Workspace como multiplicador de cuotas: crear un Google Workspace para un dominio falso (unos 6 dólares por cuenta/mes) permite generar cuentas prácticamente ilimitadas, cada una con su propia cuota de proyectos.
  • Facturación portátil: una cuenta de facturación puede asignarse a través de varias cuentas de Google, multiplicando su uso.
  • Tarjetas virtuales (vía privacy.com; verificación KYC real incluida) para crear todas las cuentas de facturación necesarias.

El punto estructural: GCP construyó disuasiones contra la enumeración, pero no atacó la causa raíz —que las IPs huérfanas existen. Con forwarding rules sobre backend buckets con load balancer como primitiva de asignación, la enumeración volvió a ser viable. Según la investigación, es una de las primeras metodologías públicas que sortea todas las defensas de GCP.

VirusTotal como fuente de secretos: la idea clave

Para secretos no había equivalente al DNS pasivo: las herramientas existentes (trufflehog y similares, y el secret scanning propio de GitHub) rastrean ámbitos estrechos —un repo, una carpeta, y en el caso de GitHub solo código open source subido a su plataforma— mientras las aplicaciones closed source de las empresas jamás pasan por ahí.

La fuente de datos ideal debía ser diversa, masiva, con webs y ejecutables —no solo open source— y escaneable en la práctica. La respuesta estaban en las plataformas de análisis de malware: VirusTotal y similares acumulan miles de millones de archivos subidos —webs, binarios, apps móviles— y, mejor aún, ofrecen búsqueda por patrones: Retro Hunt en VirusTotal y equivalentes YARA en casi todas las demás plataformas. La misma herramienta que sirve para cazar malware sirve para cazar secretos: reglas YARA para patrones como prefijos de access key de AWS (AKIA), ejecutadas sobre el corpus entero.

Dos decisiones metodológicas marcaron la diferencia. Primera, validación: mucho trabajo previo cuenta "coincidencias de patrón" sin comprobar si la clave funciona; aquí cada secreto se validó con metadatos vía API antes de contarlo. Segunda, coste: todo el pipeline corrió en funciones serverless —una para escanear, otra para validar— pagando solo por uso, con presupuesto individual.

Resultados: qué había en los datos

Con dangling DNS: más de 2 millones de IPs cloud únicas enumeradas, más de 60.000 FQDN capturados (unos 54.000 dominios de segundo nivel únicos), más de 5.000 de ellos dentro del ranking Tranco top 1 millón. La densidad de dominios colgantes por cada 1.000 IPs era ~25 en AWS y ~36 en GCP —posiblemente porque el pool de GCP llevaba años sin poder enumerarse y la basura se acumuló.

Con secretos: más de 5 millones de archivos únicos escaneados de varias plataformas, más de 15.000 secretos validados, entre ellos más de 2.400 claves de AWS, más de 2.400 tokens de GitHub (classic y fine-grained), más de 600 service accounts de GCP y más de 460 cuentas de Stripe. Ejemplos concretos: un bot token del workspace de Bixby de Samsung con scope de lectura de casi todos los canales; el workspace completo de Slack de Stanford; y la Corte Suprema de Nebraska, que subió a una plataforma de análisis una lista de unas 300 credenciales de distintos proveedores cloud y de seguridad.

La respuesta de los proveedores: GitHub dice no, OpenAI dice sí, AWS mira a otro lado

Contactados los proveedores para reportar secretos en bloque y revocarlos automáticamente, GitHub, AWS y otros se negaron —pese a que GitHub ya opera ese mecanismo internamente (publica una clave de OpenAI en un repo público y se revoca en minutos) y pese a que cualquier atacante puede activarlo publicando un commit. OpenAI fue la excepción: dio un endpoint de reporte y las claves se revocaron automáticamente.

La solución de emergencia del investigador: como GitHub se negó a dar acceso directo, se automatizó el login en GitHub para crear un gist público con cada secreto nuevo, activando así el secret scanning de GitHub por la vía lateral y logrando la revocación. El caso AWS es el más duro: cuando detecta una clave filtrada en GitHub, no la revoca —abre un support case y restringe la clave a solo-lectura. En la práctica, la clave sigue leyendo buckets de S3 y bases de datos RDS; el caso de soporte acaba en el email genérico de facturación que nadie mira. Ejemplo: la clave de un casino que procesa presuntamente más de mil millones de dólares de apuestas al mes seguía activa. La demanda central: si un proveedor sabe que una clave está expuesta en Internet, debe revocarla inmediatamente, como hacen GCP, Slack y OpenAI.

Técnicas y herramientas mencionadas

  • Dangling DNS records: registros DNS que apuntan a IPs ya liberadas; base del secuestro de subdominios.
  • Passive DNS replication: datos agregados de tráfico DNS vendidos por proveedores de threat intel; permiten saber qué registros apuntan a una IP dada.
  • Recursos primitivos vs. compartidos: IPs dedicadas (VM) vs. endpoints compartidos (serverless); determina qué registros son explotables.
  • Bishop Fox (2015), Flying a False Flag (Black Hat): trabajos previos de enumeración de pools de AWS con DNS pasivo.
  • Retro Hunt (VirusTotal) y reglas YARA: búsqueda de patrones de secretos sobre corpus masivos de archivos.
  • Serverless para escaneo y validación: funciones cloud pagadas por uso como pipeline de bajo coste.
  • Elastic IPs vs. EC2 efímero: el reinicio de instancias rota IPs y bypasea el pool restringido de AWS.
  • Forwarding rules + backend bucket (GCP): primitiva de asignación de IPs que evita las cuotas de VMs.
  • Google Workspace + tarjetas virtuales (privacy.com): multiplicación de cuentas y cuentas de facturación para saltar las restricciones de GCP.
  • Tranco top 1M: ranking de dominios usado para medir el impacto de los FQDN capturados.
  • GitHub secret scanning (y su bypaseo vía gists automáticos): mecanismo de revocación que los proveedores no abrieron a investigadores.

Conclusiones

  • Invertir el orden de la bug hunting —empezar por la vulnerabilidad y una fuente de datos masiva, no por el objetivo— multiplica el alcance: miles de organizaciones cubiertas en una pasada donde el enfoque tradicional cubriría una.
  • Las disuasiones de los proveedores (pools de IP restringidos, sobrecargos, límites de facturación) frenan la enumeración pero no eliminan el bug: mientras existan IPs y registros DNS huérfanos, la enumeración vuelve con primitivas nuevas.
  • Las plataformas de análisis de malware son una fuente de inteligencia infrautilizada para seguridad ofensiva y defensiva: el mismo corpus de malware sirve para encontrar secretos validados a escala industrial.
  • El default inseguro es la raíz: mientras las librerías acepten claves como strings hardcodeadas y el ciclo de vida DNS/cloud no asocie propiedad a los registros, cada desarrollador bajo presión volverá a generar el mismo bug. La revocación automática de claves conocidas-expuestas debe ser estándar —y hoy, el mayor proveedor de nube no la aplica.
