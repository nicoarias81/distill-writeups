Bypass de autenticación y toma de cuentas: técnicas que siguen funcionando en 2025

  • Video: gg5zsWyZJ90 · URL: https://youtu.be/gg5zsWyZJ90 · Conferencia: 01_defcon · Título original: DEF CON 33 - Account Takeover & Authentication Bypass - Vikas Khanna

Resumen

Vikas Khanna, especialista técnico en Prevasec con foco en seguridad de aplicaciones web y API, ocho años de pentesting, red teaming y bug bounty (reconocimientos de Google, Microsoft y Apple, contribuciones a OWASP WSTG, CVEs en productos de Oracle e IBM), presenta un catálogo de técnicas de account takeover y bypass de autenticación que usa profesionalmente, dirigido a pentesters, red teamers, bug hunters y estudiantes. Cierra con su primer bug en Apple: un session puzzling que dio acceso a módulos post-login de un dominio interno.

La premisa: la autenticación protege los módulos post-login con información sensible y datos personales, y las funcionalidades alrededor —olvidé mi contraseña, OTP, gestión de sesión, cambio de email/teléfono— son el terreno donde aparecen los bugs. El vector no se limita a una lista: estas son las vulnerabilidades y técnicas que él mismo encontró una y otra vez.

El catálogo de técnicas

Session puzzling — una sesión creada en etapa pre-login (por ejemplo, al pedir el restablecimiento de contraseña y entrar email) con más permisos de los necesarios puede servir para acceder a módulos post-login sin completar OTP ni respuestas de seguridad. La sesión queda activa globalmente aunque el flujo de verificación nunca se completó.

Session fixation — pre-login y post-login comparten el mismo valor de variable de sesión; solo cambia el estado (activa/inactiva). Dos variantes: con víctima remota, si el session ID aparece en URL en pre-login, se le envía el link legítimo, la víctima inicia sesión y el atacante ya tiene la sesión activa; con máquina compartida, se copian las cookies pre-login y se reutilizan cuando la víctima inicia sesión.

Access control / IDOR — funcionalidades sensibles (cambio de contraseña, actualización de perfil) que validan solo un user ID, a veces en parámetros ocultos: modificarlo con Burp Suite da la cuenta de la víctima. En grey box, escalar de la cuenta con menos privilegios a los módulos admin (listar usuarios, desactivarlos, cambiarles contraseñas).

Force browsing — golpear módulos post-autenticación sin credenciales: si hay bug de access control, entran igual; y archivos de configuración no enlazados pero presentes en el servidor filtran información sensible.

Host header injection para secuestrar links de reset — si el valor del header Host se refleja en el Location de redirecciones 301/302, se pide reset para el email de la víctima, se cambia el Host al dominio del atacante, y el servidor legítimo envía el link de reset apuntando al dominio del atacante. La víctima hace clic, el token llega a los logs del atacante, y como aún está activo, se usa contra la aplicación real para cambiar la contraseña.

Archivos JS — los JS del frontend son oro: API keys, credenciales, endpoints sensibles que nadie mira.

PHP type juggling — la comparación con == convierte tipos: un string sin dígitos se convierte a 0. Si el hash de la contraseña del admin es un string sin enteros, enviar 0 como contraseña hace 0 == 0 verdadero. Requisito: el valor debe llegar por JSON o objeto serializado.

CSRF — sin tokens anti-CSRF, una página HTML enviada a la víctima logueada cambia su email o teléfono; después se pide el reset de contraseña y el OTP/link llega al canal que controla el atacante. También: reset directo sin pedir la contraseña anterior.

HTTP parameter pollution — repetir el parámetro de email con el correo de la víctima y el del atacante: si la aplicación envía el token a ambos y solo valida el primero (o el segundo, según la app), el atacante recibe un link activo para cambiar la contraseña. Aplica igual a OTPs.

Manipulación de respuestas — aplicaciones que validan la respuesta previa (true/false, 200/400) antes del siguiente paso: cambiar el false por true o el 400 por 200 en Burp y continuar el flujo.

Ruptura de OTP / 2FA — chequear la integridad: pedir un OTP al número propio y otro a la víctima, y probar el propio contra la cuenta de la víctima —si la app no valida la vinculación, entra—; reutilizar OTPs; leer OTPs que algunos sistemas (encontró uno en un banco popular) revelan en la respuesta; y OTPs maestros: en una app de home banking, el OTP maestro era seis ceros, suficiente para entrar a cualquier cuenta.

Brute force / password spraying — con un solo diccionario de contraseñas contra muchos usuarios alcanza para red team, donde se necesita una sola cuenta. Chequear rate limiting; rotar IP antes del umbral de bloqueo (si bloquea a los 50 intentos, rotar en el 49); mandar múltiples credenciales por request. El lab de la PortSwigger Web Security Academy es la referencia.

Credenciales por defecto — casi toda organización usa productos enterprise con contraseñas de fábrica: siguen funcionando y son oro para red teaming.

Enumeración de usuarios en WordPress — el parámetro ?author=N revela usernames, posts y comentarios por ID incremental. Y wpscan con API key (gratuita) en lugar de sin ella: los resultados cambian.

Gestión de logout insegura — especialmente en banca: reutilizar sesiones tras logout, verificar si cerrar el navegador destruye la sesión del lado servidor (reabrir en una pestaña nueva no debería funcionar), y si la sesión está vinculada a la IP —protección que frena el robo de cookies.

El bug en Apple: session puzzling con domain fronting de subdirectorios

Su primer hallazgo en Apple fue un bypass de autenticación por session puzzling. El dominio principal redirigía al SSO de Apple —que a su juicio es sólido, no lo auditó—. Pero con Google dorking encontró un subdirectorio con nombre de cadena aleatoria que contenía un módulo de login propio. Fluye así: se envían usuario y email falsos; la aplicación responde "try again" pero, al fallar, crea una sesión vinculada a ese email y la activa globalmente, incluidos los módulos de administración; con esa sesión activa se salta el login y se accede directamente al subdirectorio, descargando información confidencial (contenido blurreado en las capturas).

Tips finales

  • Pastebin para red teaming: filtra credenciales y datos sensibles.
  • DeHashed para contraseñas filtradas de las víctimas.
  • Open Bug Bounty para reutilizar vulnerabilidades que otros investigadores revelaron públicamente cuando el proveedor no respondió.

Técnicas y herramientas mencionadas

  • Session puzzling — sesión pre-login con permisos excesivos que habilita módulos post-login (el bug de Apple).
  • Session fixation — pre-login y post-login comparten valor de sesión; solo cambia el estado.
  • IDOR / access control — user ID en parámetros (u ocultos) como única validación en cambios de contraseña y perfil.
  • Force browsing — acceso directo a módulos post-auth y archivos de configuración sin enlazar.
  • Host header injection — redirecciones que reflejan el Host para secuestrar tokens de reset.
  • PHP type juggling — == convierte strings sin dígitos a 0; bypass con JSON/objetos serializados.
  • CSRF sin tokens — cambio de email/teléfono vía página maliciosa para redirigir OTPs.
  • HTTP parameter pollution — parámetro duplicado con dos emails para recibir el token de reset el atacante.
  • Response manipulation — true/false y códigos de estado editables en el proxy para saltarse pasos del flujo.
  • OTP abuse — falta de integridad entre OTP y cuenta, reutilización, OTPs en respuestas, OTPs maestros (seis ceros en un banco).
  • Password spraying + rotación de IP — un diccionario, muchos usuarios, rotar IP bajo el umbral de bloqueo.
  • Credenciales por defecto — productos enterprise con contraseñas de fábrica vigentes.
  • Enumeración en WordPress — ?author=N para usernames; wpscan con API key gratuita.
  • Gestión de logout — reutilización de sesión, destrucción al cerrar navegador, vinculación sesión-IP.
  • OSINT: Pastebin, DeHashed, Open Bug Bounty.
  • Burp Suite — proxy central para capturar, modificar y reenviar en todas las técnicas.

Conclusiones

  • Los flujos de recuperación son la superficie más rentable. Casi todas las técnicas de takeover pasan por olvidé mi contraseña, OTPs o cambio de email/teléfono: auditar esos flujos primero.
  • El estado de sesión es el activo más mal gestionado. Sesiones con permisos de más, valores que sobreviven al logout, estados que solo cambian de activo a inactivo: la gestión de sesión merece tanto análisis como las credenciales.
  • La validación del lado cliente es decorativa. Respuestas true/false editables, user IDs en parámetros ocultos, OTPs revelados en la respuesta: todo lo que decide el servidor basándose en datos que el cliente puede tocar es bypass potencial.
  • Lo viejo sigue funcionando. Credenciales por defecto, type juggling, host header injection y OTPs maestros de seis ceros siguen abriendo puertas en 2025; no hay que descartar técnicas por antiguas.
  • La reputación y la disciplina importan. Reportar responsablemente (Apple, Google, Microsoft, Oracle, IBM) y compartir metodología en la comunidad — OWASP, talks, colaboración abierta — es parte del trabajo.
