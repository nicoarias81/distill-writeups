Lecciones de hacking web: cinco casos reales de bug bounty en sistemas gubernamentales

Resumen

Los programas de bug bounty sobre sistemas gubernamentales en producción son de los escenarios más exigentes para el hacking web: superficie amplia, restricciones estrictas y tiempo limitado. Cinco años de trabajo del equipo de seguridad de CSIT (Singapur) sobre el Government Bug Bounty Program (GBBP) — lanzado en 2018 para testear aplicaciones web de las agencias del gobierno — dejaron una colección de lecciones prácticas: alrededor de 100 hallazgos aceptados (incluyendo críticos y severos) y unos 40 bugs únicos repartidos entre la mayoría de las 17 ediciones del programa, tanto en rondas públicas como en las pre-rondas internas reservadas a empleados públicos.

Cinco casos de estudio ilustran qué funcionó, qué no, y qué conviene hacer distinto tanto para atacantes como para defensores. El hilo conductor: el impacto real rara vez vive en un solo bug — nace de encadenar hallazgos aparentemente menores.

El método de trabajo: equipo y triaje contra reloj

En un bug bounty la mayoría trabaja solo; aquí se trabajó en equipo y en el mismo lugar físico. Las consecuencias son medibles: se aprende más rápido de los demás, cada bug se discute desde ángulos distintos en la sala, los reportes finales mezclan el conocimiento de varios integrantes — y, sin dinero de por medio en las rondas internas, es más divertido.

La distribución del esfuerzo sigue un patrón simple:

  1. Correr herramientas automáticas (scanners, spiders) sobre todas las aplicaciones para mapear la superficie.
  2. Priorizar las aplicaciones con más superficie y mayor complejidad.
  3. Dedicar el testing manual profundo ahí.

Caso 1: de un upload escondido a RCE vía file descriptors

Una aplicación gubernamental con el típico laberinto de formularios escondía un punto de subida de archivos Excel con vista previa. Encadenando tres debilidades se llegó a ejecución remota de código:

  • El endpoint de descarga validaba con una comprobación trivial sobre el header Referer → acceso de lectura no autorizado a documentos ajenos.
  • Esa misma lectura admitía path traversal / LFI → lectura de /etc/passwd, archivos de sistema y código fuente.
  • Con logs y código fuente a mano seguía faltando el paso final a RCE. La clave fue preguntarse qué más queda por leer: los file descriptors de los procesos en ejecución (/proc/<pid>/fd — del 3 en adelante, archivos abiertos por la aplicación). Entre ellos aparecieron secretos de configuración en memoria — claves y tokens — que permitieron autenticarse en la nube y convertir la lectura arbitraria en control total.

Lecciones para atacantes: revisar cada rincón de la aplicación (los endpoints de riesgo suelen estar bien escondidos); no conformarse con reportar el primer bug (solo con LFI no hay RCE); y pensar la cadena de explotación, no el bug aislado. Para defensores: un acceso de lectura puede significar compromiso total; no exponer logs ni código fuente por la web; y usar WAF y controles que impidan combinar piezas entre endpoints distintos.

Caso 2: command injection en el nombre de archivo

Tras días sin hallazgos en una aplicación, el equipo miró algo que rara vez se testea: el nombre del archivo en el cuerpo de la petición (no la URL, que es donde casi siempre se testa). Inyectar metacaracteres de shell en el nombre produjo una diferencia de timing medible — inyección de comandos confirmada.

El comando inyectado era ciego (sin output), así que el pivote fue exfiltrar por un canal alternativo: descargar el archivo de resultados hacia un endpoint accesible. Con eso se obtuvieron credenciales de una API interna, acceso a un servicio backend y, de nuevo, RCE — esta vez sin necesidad de encadenar un segundo bug, pero pasando por la infraestructura interna.

Lecciones: probar en los lugares poco comunes — los nombres de archivo viajan por el body y a menudo terminan concatenados en comandos shell; y la inyección ciega sigue siendo explotable si existe cualquier canal de exfiltración. Para defensores: nunca confiar en el nombre del archivo subido, y tratar toda entrada del cuerpo de la petición como entrada de usuario.

Caso 3: validación JWT inconsistente entre endpoints

El endpoint principal de login validaba los JWT correctamente — pero otro endpoint (el de refresh de token, menos visible y no documentado en la spec de la API) no verificaba la firma. Con un token autofirmado, cambiar el rol a admin bastó para tomar control de cuentas.

Lecciones: testear todos los endpoints que procesan el token, no solo el principal; el endpoint débil ni siquiera aparecía en la documentación — se encontró explorando. Para defensores: centralizar la lógica de validación de tokens en un solo componente verificado, no repetirla por endpoint.

Caso 4: OTP con el umbral de fallos controlado por el cliente

Un login por código de un solo uso (OTP de 6 dígitos enviado por email) parecía sólido: había un límite de 5 intentos fallidos. Al revisar la configuración del mecanismo, el parámetro que define ese umbral de fallos llegaba desde el cliente y era modificable. Poniéndolo en otro valor y reconfigurando el envío, el OTP quedó adivinable a voluntad → toma de cuenta sin autenticación previa.

Lecciones: los mecanismos de seguridad también tienen parámetros, y esos parámetros son superficie de ataque; el IDOR aplicado a un control de seguridad tiene impacto desproporcionado. Para defensores: los controles (límites, umbrales, rate limiting) deben validarse del lado del servidor; jamás permitir que el cliente defina cuántas veces puede fallar una autenticación.

Caso 5: de un error SQL filtrado a cloud service takeover

Una aplicación web estática, aburrida, descartada a los pocos minutos de testing manual. Con el spider de Burp corriendo de fondo apareció un endpoint con muchos parámetros y URLs largas, con valores que parecían codificados. Las pruebas clásicas de SQLi no encontraban inyección — pero provocar deliberadamente un error de SQL hizo que la aplicación devolviera en la respuesta un secreto de configuración: una API key de un servicio en la nube. Con esa clave, el servicio cloud fue tomado directamente.

Lecciones: dejar la automatización corriendo aunque el objetivo parezca trivial; los mensajes de error siguen siendo una mina (aquí no hubo inyección explotable, pero el error sí filtró el secreto). Para defensores: nunca exponer secretos en respuestas de error, y auditar qué devuelve la aplicación cuando algo falla.

Conclusiones

    A[Superficie mapeada con automatización] --> B[Priorizar apps complejas]
    B --> C[Testing manual profundo en equipo]
    C --> D[Bug individual]
    C --> E[Encadenamiento de bugs]
    D --> F[Impacto moderado]
    E --> G[Impacto crítico: RCE, takeover]
  • El impacto está en la cadena: LFI solo es molesto; LFI + file descriptors + tokens de nube es RCE. Un JWT sin verificar es un bug; combinado con un endpoint de refresh, es account takeover.
  • Lo raro es rentable: nombres de archivo en el body, parámetros de configuración de controles de seguridad, endpoints fuera de la documentación — los lugares que nadie testea guardan los hallazgos más severos.
  • Manual y automático se complementan: los scanners abren el mapa; los casos 2 y 5 se resolvieron mirando donde la automatización no llega (o dejándola trabajar más tiempo del previsto).
  • Trabajar en equipo multiplica: los mejores reportes salieron de la combinación de perspectivas de varios integrantes, no de un investigador aislado.
  • Para defensores, la lista de compras es corta y accionable: no filtrar secretos en errores ni en logs, centralizar validación de tokens, validar del servidor todo control de seguridad, y asumir que cualquier entrada —incluido el nombre de un archivo— puede llegar a un shell.

Técnicas y herramientas mencionadas

  • Burp Suite (scanner + spider) — mapeo inicial de superficie y descubrimiento de endpoints no documentados.
  • Path traversal / LFI — lectura arbitraria de archivos, incluidos file descriptors de procesos (/proc/<pid>/fd) con secretos en memoria.
  • Inyección de comandos en nombre de archivo — metacaracteres de shell en el body de la petición, detectada por diferencias de timing.
  • JWT sin verificación de firma — endpoint de refresh con validación ausente.
  • OTP con umbral controlado por el cliente — IDOR sobre el parámetro de límite de intentos.
  • Error SQL como oráculo de secretos — API key de servicio cloud filtrada en la respuesta de error, que desembocó en takeover.
