Modelado de amenazas con OWASP: Threat Dragon y la Web Security Testing Guide como métodos de aprendizaje

Resumen

El modelado de amenazas se puede destilar en cuatro preguntas: ¿qué estamos construyendo (el alcance)?, ¿qué puede salir mal (buscar agujeros)?, ¿qué vamos a hacer al respecto (mitigaciones y controles)? y ¿hicimos un buen trabajo? La promesa de esta publicación es mostrar cómo enseñar ese método de forma práctica y gratuita usando dos proyectos open source de OWASP — Threat Dragon para diagramar y enumerar amenazas, y la Web Security Testing Guide para convertir esas amenazas en casos de pentesting — sin licencias empresariales ni instalaciones forzadas de Windows.

El enfoque elegido es STRIDE, la metodología creada en Microsoft, que mapea cada amenaza con la propiedad de seguridad que compromete: manipular un almacén de datos para cambiar las alergias de un paciente compromete la integridad, y así con cada categoría. (En parte de la literatura aparece STRIDE-LM, con movimiento lateral añadido.) Pero el framework sin diagramas no sirve de nada, y ahí aparece el primer problema real de la práctica: si se le pide un diagrama del sistema a distintos equipos, cada uno manda algo distinto. El de infraestructura dibuja switches y routers sin explicar la aplicación; el de aplicación manda flujos de usuario sin decir qué componentes de infraestructura usa. El modelador acaba oficiando de unificador del equipo, destilando todo a cuatro bloques esenciales: proceso de datos, almacén de datos, flujo de datos y entidad externa, más las fronteras de confianza. Decidir hasta dónde descomponer es un arte: si el nivel es demasiado grueso, el modelo no permite nada; si es demasiado atómico, hay claridad total pero ya no se puede modelar a tiempo para el cliente.

Quién, qué, dónde y cómo: la frase de amenaza

Para describir amenazas de manera sistemática, el método de enseñanza usa una plantilla simple: identificar al actor de amenaza (un empleado, un contratista con privilegios parciales, un atacante externo — cada nivel de privilegios inherente cambia el daño posible y la verosimilitud), luego qué hace, en qué parte del sistema (conectando con el diagrama) y cómo ataca. El resultado es una frase en lenguaje natural que, escrita desde la perspectiva del adversario, se convierte casi directamente en un escenario de pentesting.

¿Y qué framework elegir? La respuesta honesta: no hay ninguno que gobierne a todos. Para entender los TTPs de atacantes contra una aplicación web se recurre a taxonomías y bibliotecas de amenazas como MITRE ATT&CK; para amenazas de sistemas ML existen ATLAS y OWASP KPECK, entre otras matrices. El nivel de abstracción decide la herramienta: un modelo de amenazas a nivel de sistema funciona bien con ATT&CK, pero modelar un driver anticheat a nivel kernel exige bajar mucho más profundo que cualquier taxonomía de sistema.

Threat Dragon: el mínimo esfuerzo posible

OWASP Threat Dragon responde a la pregunta práctica de todo formador: ¿con qué herramienta enseño sin presupuesto para licencias para todos? Es gratis, multiplataforma (existe versión web, sin VM de Windows obligatoria) y compatible con STRIDE, LINDDUN y otros frameworks. Su virtud es la austeridad: como el IDE de la facultad, al que uno le reprochaba falta de funciones, enseña los principios básicos en vez de las facilidades de las versiones empresariales. Se dibuja el DFD con sus cuatro elementos y fronteras de confianza, y se enumera con STRIDE sobre cada componente.

Trae además proyectos de ejemplo incorporados — antes solo había uno funcional; ahora hay modelos de juegos, wallets de criptomonedas y más. Trabajar con modelos simples obliga a los estudiantes a pensar en los bloques de arquitectura y en cómo la arquitectura determina los casos de uso: lo aprendido al modelar un tipo de sistema se transfiere a sistemas similares por semejanza arquitectónica. Un ejercicio típico cambia el caso de uso del mismo diagrama y demuestra que lo más importante a proteger — y por lo tanto la lectura del diagrama — cambia también. En los talleres se usa un esquema de dos vías: ejercicios comunes más problemas adicionales para quienes avanzan rápido, que terminan elevando el nivel de toda la clase.

El énfasis deliberado en el DFD por encima de la enumeración masiva de amenazas tiene una razón: hay demasiados frameworks, pero lo escaso es la claridad mental al pensar sistemas. Las preguntas que el diagrama obliga a hacerse son: ¿descompuse el sistema a un nivel útil para modelar? ¿Estoy conforme con la claridad de los componentes? Si la respuesta es no, queda trabajo; si se exagera hacia lo atómico, el tiempo del cliente se va por el desagüe.

De la enumeración al pentest: la Web Security Testing Guide

La enumeración de amenazas escrita desde la perspectiva del atacante — "usuario malicioso de la aplicación explota una vulnerabilidad de SQL injection" — es lenguaje natural para construir escenarios de prueba. Ahí entra el segundo proyecto: la OWASP Web Security Testing Guide, que aporta dos cosas que un cheat sheet no da: una vista panorámica de la seguridad de aplicaciones y una metodología estructurada para construir casos de uso de pentesting.

Ejemplo del flujo: la amenaza es SQL injection contra una base de datos; las preguntas metodológicas son qué motor es (¿MS SQL? Entonces el cheat sheet de Microsoft) y cómo se pasan los comandos. La SQL injection es una vulnerabilísima vieja que sigue apareciendo en entornos antiguos porque nunca se actualizan y las advertencias no se corrigen — hay que testearla igual. Pero el tiempo del pentester es finito y la guía ayuda a priorizar: primero pre-autenticación, luego el proceso de autenticación, después funciones que puedan llevar a RCE. El mensaje de fondo: metodología por encima de colección de trucos.

La conexión con el modelado de amenazas explica también el salto de junior a senior en pentesting. El junior recibe una aplicación y prueba las técnicas más cool para romperla. El senior lidera equipo y le preguntan "¿cómo abordo esta aplicación?"; necesita claridad de pensamiento sobre casos de uso y casos de abuso. Y el criterio final no es la vistosidad del exploit: se paga por mostrar al cliente cómo asegurar las vulnerabilidades encontradas. El modelado de amenazas responde justamente la segunda pregunta del método: qué puede salir mal.

Técnicas y herramientas mencionadas

  • Las cuatro preguntas del modelado de amenazas — qué construimos, qué puede salir mal, qué hacemos, qué tan bien lo hicimos.
  • STRIDE / STRIDE-LM — metodología de Microsoft que clasifica amenazas por la propiedad de seguridad comprometida.
  • DFD (Data Flow Diagram) — proceso de datos, almacén de datos, flujo de datos, entidad externa y fronteras de confianza como vocabulario mínimo.
  • Enumeración centrada en el atacante — plantilla actor → qué → dónde → cómo, base de los escenarios de prueba.
  • OWASP Threat Dragon — herramienta open source, gratis y multiplataforma, con proyectos de ejemplo y soporte de STRIDE y LINDDUN.
  • OWASP Web Security Testing Guide (WSTG) — metodología estructurada de pruebas de seguridad web y priorización de casos.
  • MITRE ATT&CK / ATLAS / KPECK — taxonomías de TTPs a distintos niveles de abstracción (sistema, ML, kernel).
  • LINDDUN — framework de modelado de amenazas de privacidad, con su propio juego de enseñanza.
  • Elevation of Privilege — juego de cartas para aprender modelado de amenazas.

Conclusiones

  • No existe un framework que gobierne a todos: la elección depende del nivel de abstracción del objetivo (sistema, aplicación, kernel) y de las preguntas que se necesitan responder.
  • La claridad del diagrama de flujo de datos importa más que la acumulación de frameworks; descomponer demasiado mata la velocidad, descomponer demasiado poco mata el valor.
  • Threat Dragon demuestra que el modelado de amenazas se puede enseñar con herramientas gratis y sin curva de aprendizaje: mínimo esfuerzo, máximos principios.
  • La Web Security Testing Guide convierte amenazas en escenarios de prueba ordenados por prioridad, y es el puente natural entre modelado de amenazas y pentesting.
