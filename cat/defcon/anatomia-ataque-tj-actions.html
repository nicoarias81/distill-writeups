No fue solo un leak de pipeline: la anatomía del ataque real detrás de tj-actions

Fuente: «DEF CON 33 - Not Just a Pipeline Leak: Reconstructing Real Attack Behind tj-actions - Aviad Hahami» · ver el video original

  • Video: -CSbWpj_IZM · URL: https://youtu.be/-CSbWpj_IZM · Conferencia: 01_defcon · Título original: DEF CON 33 - Not Just a Pipeline Leak: Reconstructing Real Attack Behind tj-actions - Aviad Hahami

Resumen

El 14 de marzo de 2025, hacia las 4 p.m. UTC, un atacante comprometió el popular repositorio de GitHub Actions tj-actions/changed-files e inyectó código que volcaba todos los secrets de los runners de CI a los logs. En unas cuatro horas apareció el primer issue avisando de que los consumidores estaban filtrando credenciales; en los días siguientes hubo CVEs, alertas de empresas y pánico generalizado. Alrededor de 23.000 proyectos vieron sus credenciales expuestas. La comunidad trató el episodio como un incidente de fuga masiva —y se equivocó de diagnóstico.

La investigación del equipo de seguridad de Palo Alto Networks reconstruyó el flujo completo del ataque y demostró que la fuga masiva no era el ataque sino su epílogo: la punta del iceberg. El verdadero objetivo era uno solo —Coinbase—, y el atacante llegó hasta él mediante una cadena de compromisos en cascada que arrancó tres meses y medio antes, con un pwn request contra la organización SpotBugs. Reconstruir esa cadena exige entender cuatro TTPs que explotan rasgos estructurales de GitHub: shadow commits, overrides de tags, usuarios desechables y pwn request en workflows mal configurados.

El caso es un estudio de cómo la confianza implícita en el open source —"si lo usa todo el mundo, es fiable"— se convierte en vector de ataque, y de lo ciego que es el audit log de GitHub ante técnicas que abusan de sus propias abstracciones.

El primer eslabón: un pwn request contra SpotBugs

El 6 de diciembre de 2024, más de tres meses antes de la fecha "oficial" del incidente, el atacante explotó un workflow vulnerable de GitHub Actions en el repositorio sonar-findbugs de la organización SpotBugs. La técnica: el clásico pwn request (poison pipeline execution), en su variante por misconfiguración. El atacante creó un commit malicioso en un fork del repositorio y abrió un pull request; el CI de la víctima, mal configurado, hizo checkout del código del fork y ejecutó el commit malicioso en su propio contexto.

El payload era minimalista: un cambio de una sola línea en el archivo Maven que hacía curl de un script bash desde el repositorio del atacante, lo pipeteaba a bash y redirigía stdout y stderr a /dev/null para silenciar todo. El resultado fue el robo de un personal access token (PAT) de un mantenedor de SpotBugs. Un PAT robado sigue siendo utilizable mientras su dueño no lo revoque, con todos los permisos que este le dio; el mantenedor simplemente no sabía que estaba comprometido.

Con ese token, el atacante obtuvo acceso de administrador a la organización SpotBugs.

Recon, paciencia y la ballena que emergió

Durante los meses siguientes, el atacante usó el PAT robado para explorar qué más podía alcanzar con él. El detalle revelador llegó gracias a los logs de actividad que el mantenedor de SpotBugs compartió con los investigadores: dentro del repositorio spotbugs/spotbugs había un segundo PAT —de otro mantenedor— usado como secret en los workflows de GitHub Actions. Ese token era especialmente valioso porque su dueño también era mantenedor de otra organización: ReviewDog.

Aquí el atacante demostró la virtud que define a esta operación: esperó. Durante tres meses no explotó nada ni hizo movimientos laterales, aunque técnicamente podía. El 7 de marzo de 2025, un mantenedor de Coinbase pushó un workflow de GitHub Actions que usaba tj-actions/changed-files. En ese instante, el objetivo declarado se volvió vulnerable, y el atacante se puso en marcha a toda velocidad. Los investigadores concluyen que Coinbase era, desde el principio, lo único que le interesaba: su movimiento fue tan directo y explícito hacia ese repositorio que, junto con otros IOCs, equivale a una confesión de intención.

Usuarios desechables y exfiltración cifrada para entrar en ReviewDog

El atacante no podía simplemente leer el segundo PAT: GitHub nunca muestra los secrets por UI. Para extraerlo había que ejecutar código en el contexto correcto, y la opción obvia —push de un workflow malicioso con el token de admin— habría dejado mucho ruido: commit visible, branch visible.

La solución fue el TTP de "membresías y usuarios desechables". El atacante creó una cuenta desechable, la invitó como miembro del repositorio de SpotBugs y con ella pushó una branch con un workflow malicioso que exfiltraba el PAT de ReviewDog. Cuando el CI ejecutó el workflow, el usuario desechable se borró a sí mismo y eliminó la branch. El log de actividad público muestra la branch creándose y borrándose dentro del mismo minuto: el ruido quedó asociado a una identidad que ya no existía.

El payload de exfiltración sigue el patrón estándar del mundo GitHub: serializar los secrets accesibles, cifrarlos con AES, cifrar el conjunto (secrets + clave) con la clave pública del atacante incrustada en el código, y subir el resultado como artifact de GitHub. Todo queda a la vista —y cifrado—, así que incluso alguien revisando el artifact no podría descifrarlo. Footprint mínimo, detección casi imposible.

Shadow commits: envenenar tags sin hacer commits

La técnica central del ataque —y la más elegante— abusa de una peculiaridad de la red de forks de GitHub. Un fork no es un concepto de Git sino de GitHub: por debajo es una pseudo-branch en el mismo repositorio backend. Consecuencia: los commits pushados a un fork son accesibles desde el repositorio original. Comitear a un fork equivale, en la práctica, a pushar una branch a un repositorio que no se posee — el código existe, pero nadie ve nada.

Combinado con el hecho de que los tags de Git son simples punteros a SHAs, esto permite algo potente: se puede hacer que un tag como v1 apunte a un commit que vive en un fork, sin pushar nada al repositorio principal. El TTP —bautizado "shadow commits"— tiene dos propiedades decisivas: cero ruido de commits (nada aparece en el repo) y un punto ciego total del audit log de GitHub (el evento no se registra; solo GitHub support puede entregar los ref logs).

El 11 de marzo de 2025 el atacante lo ejecutó: creó un fork de reviewdog/action-setup, pushó un commit en el fork con un payload base64 —un programa Python que recorre el filesystem procfs, extrae los maps y la memoria de los procesos y los imprime a stdout, junto con el script que lo decodifica, ejecuta y filtra la salida al log— y sobrescribió el tag v1 de action-setup para que apuntara a su commit malicioso. Ese mismo payload de memory dumping es esencialmente el que acabaría aterrizando en los 23.000 repositorios días después.

Por la cadena de dependencias —tj-actions/eslint-changed-files dependía del tag v1 de action-setup, y tj-actions/changed-files usaba el primero— el código malicioso se propagó en cascada hacia abajo. Los investigators determinaron que el tag se pushó a las 6:42 p.m. UTC y que el propio atacante lo revirtió a su valor original a las 8:31 p.m., menos de dos horas después: ya había obtenido tokens con permisos sobre tj-actions y la infección de ReviewDog le sobraba.

El objetivo: Coinbase, y el "Leroy Jenkins" final

Con control de facto sobre tj-actions/changed-files, el atacante estaba a un paso de su meta. El 13 de marzo repitió la técnica: fork del repositorio, shadow commit —con un payload de curl + script Python— y override del tag v39. El smoking gun quedó a la vista en el propio código: una condición que comprueba si la organización es coinbase (o una de las cuentas desechables del atacante) antes de ejecutar el ataque. Nadie más que Coinbase iba a recibir el impacto, aunque consumiera la versión maliciosa.

A las 3:10 p.m. UTC del 14 de marzo, una máquina de CI de Coinbase recogió la action maliciosa y filtró sus credenciales. Los logs del runner mostraban permisos de escritura sobre deployments y contents. Una hora después, a las 4:37 p.m., Coinbase fue notificada de actividad sospechosa, identificó el origen en el uso de tj-actions y eliminó el workflow. El enlace que el atacante había construido durante meses se cortó.

Veinte minutos más tarde, a las 4:57 p.m., llegó lo que la comunidad conocería como "el incidente de tj-actions": el atacante sobrescribió —otra vez vía shadow commits— prácticamente todos los tags del repositorio, apuntándolos al commit con el secret-logger que imprimía los secrets a los logs. Sin filtro por organización, sin cifrado, sin canal de exfiltración silencioso: los secrets de 23.000 repos quedaron impresos en logs. La carga masiva fue la quema del campo, no el botín.

Cómo se rastreó: ClickHouse, GitHub Archive y la comunidad

El equipo de Palo Alto Networks empezó la investigación por el final (la fuga masiva) y tuvo que escalar la cadena hacia atrás. Las herramientas: el dataset de eventos de GitHub sobre ClickHouse —SQL, gratuito, velocísimo— como fuente principal, y GitHub Archive —logs de eventos de GitHub con resolución de una hora— para mayor resolución en puntos concretos. El trabajo con los mantenedores de las organizaciones implicadas cerró los huecos: sus logs de actividad aportaron la evidencia que ninguna herramienta pública guarda. Un tuit de Adnan Khan durante la investigación fue un punto de inflexión.

Otras víctimas y el estado de las mitigaciones

La investigación confirmó actividad del atacante contra más objetivos: pruebas de payloads contra un fork de Ultralytics tres días después de que fuera breacheado (4 de diciembre de 2024), pruebas similares contra un fork de Apache Superset (67.3k estrellas) sin impacto detectado, infraestructura de shadow commits preparada contra module-federation-core sin confirmación de ejecución, y pull requests maliciosos contra BCE de Baidu con pipeline comprometido de forma confirmada.

En mitigaciones, el panorama es mixto. Contra shadow commits no hay defensa disponible: si tu repo permite forks, estás dentro. GitHub está probando immutable releases and tags —una vez creado, el tag es un puntero inmutable—, posiblemente la lección institucional del postmortem. Contra el pwn request existen múltiples herramientas de auditoría de pipelines en varios ecosistemas. Y la recomendación de higiene más urgente, repetida hasta el cansancio pero ignorada por la mayoría: dejar de referenciar actions por tag de Git y usar en su lugar el SHA de commit completo de 40 caracteres.

La pregunta abierta: ¿por qué quemar el botín?

El detalle que no cierra: el atacante demostró planificación, paciencia de meses, técnicas sofisticadas y disciplina operativa. Y luego, en el golpe final, eligió el exploit más ruidoso posible —un memory dumper que imprime a la consola y se descarga en cada máquina infectada—, renunció al cifrado doble que había usado contra ReviewDog y dejó los secretos de 23.000 repos impresos en logs. Podía llamar a casa; no lo hizo. Podía exfiltrar en silencio; imprimió.

Las hipótesis en abierta: ¿un error o pánico al verse acorralado? ¿falta de preparación para exfiltrar a esa escala, poco creíble dado el nivel del resto? ¿sabotaje deliberado —25.000 tickets de soporte pueden tumbar a GitHub support—? ¿un APT comprando reputación, aunque falte la atribución porque nadie reivindicó nada? ¿o un mercado entre dos actores, donde el profesional que encontró el token de SpotBugs lo vendió y el comprador resultó menos competente? Un post en Breach Forums sobre la técnica de pwn request, mencionando explícitamente Ultralytics y publicado el mismo mes en que SpotBugs fue explotada, insinúa la última pista. La respuesta sigue sin saberse.

Técnicas y herramientas mencionadas

  • Pwn request (poison pipeline execution): ejecución de código no autorizado en el CI de la víctima vía PR desde un fork, por misconfiguración del workflow.
  • Shadow commits: commits pushados a un fork accesibles desde el repo original, usados para inyectar código sin push visible ni registro en el audit log.
  • Tag override: reescritura de tags de Git para redirigir silenciosamente a los consumidores hacia SHAs maliciosos.
  • Usuarios desechables: cuentas creadas, invitadas como miembros y autoeliminadas para asociar el ruido a identidades que desaparecen.
  • Exfiltración vía artifacts cifrados: secrets cifrados con AES + clave pública del atacante y subidos como artifacts de GitHub.
  • Memory dumping vía procfs: payload Python que extrae maps y memoria de procesos desde /proc y los imprime a stdout.
  • GitHub events en ClickHouse y GitHub Archive: fuentes de datos para reconstruir la línea temporal del ataque.
  • Immutable releases/tags: mitigación en pruebas por GitHub para blindar los tags contra overrides.
  • SHA completo (40 caracteres) en vez de tags: práctica de referencia recomendada al consumir GitHub Actions.

Conclusiones

  • La fuga masiva de tj-actions fue la punta del iceberg: el ataque real fue una cadena planificada de compromisos —SpotBugs → ReviewDog → tj-actions→ Coinbase— iniciada tres meses y medio antes, con el atacante esperando pacientemente a que su objetivo concreto se volviera vulnerable.
  • GitHub ofrece superficies de ataque estructurales poco conocidas: los commits de forks son alcanzables desde el repo original y los overrides de tags no aparecen en el audit log; sin los ref logs de GitHub support, estas maniobras son invisibles.
  • La higiene básica del ecosistema sigue sin aplicarse: fijar actions por SHA completo en vez de por tag es la mitigación de mayor impacto disponible hoy para cualquier usuario de GitHub Actions.
  • El atacante eligió terminar con el exploit más ruidoso posible pudiendo exfiltrar en silencio; esa decisión deliberada sigue sin explicación y sugiere que el incidente podría tener capas aún desconocidas (sabotaje, venta de access, o un segundo actor menos profesional).
