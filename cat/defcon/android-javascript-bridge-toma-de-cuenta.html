JavaScript Bridge en Android: del enlace malicioso a la toma de cuenta

  • Video: lp1jOnZpDCo · URL: https://youtu.be/lp1jOnZpDCo · Conferencia: 01_defcon · Título original: DEF CON SG1 - CSIT Village - Kang Hao - Android Security Javascript Bridge Is Falling Down

Resumen

Kang Hao, investigador de seguridad de InnoH Labs enfocado en ofensiva sobre web, IoT y aplicaciones móviles, presenta un caso real —hallado antes de la era de la IA, analizado a mano, con código y capturas fuertemente censurados: la interfaz se llama xbridge y el objetivo, boundapp— de cómo un JavaScript Bridge mal programado en Android permite tomar el control de una cuenta de usuario con un solo enlace.

El escenario de apertura lo cuenta su blog con historieta: Tux, un pingüino, despierta con una notificación y hace clic en un enlace titulado "Not Scammer". La redirección lanza la aplicación "Instagreen"; el mensaje que ve es solo texto plano. Horas después, la app le avisa que su cuenta fue comprometida: contraseña incorrecta al intentar entrar, y su amiga Lucia ve publicaciones extrañas desde su perfil. Ese es el objetivo del ataque: toma de cuenta mediante un enlace malicioso, abusando de una función JSB vulnerable para ejecutar acciones no autorizadas.

Fundamentos: la superficie de ataque de Android

Para encuadrar el problema conviene dividir la superficie de ataque de una app Android en tres categorías:

  • HTTP API: el enfoque tradicional del pentest móvil. Se enruta el tráfico de la app a un proxy (Burp) y se analiza el HTTP, buscando sobre todo IDOR y problemas de lógica de negocio.
  • Componentes Android: las piezas tipo LEGO que hacen posible una app. Cuando están exportadas, otra aplicación puede acceder a ellas, lo que abre escenarios como redirección de intents o robo de archivos arbitrarios vía content providers. (Sobre esto, la misma autora tiene publicado cómo usó componentes Android para explotar el navegador de DuckDuckGo.)
  • WebView: técnicamente es un componente Android, pero por su envergadura merece categoría propia, y es el foco del análisis.

Dentro de WebView, ¿de dónde puede venir el ataque? Tres puntos de entrada:

  1. Redirección por deep link: algunos deep links aceptan parámetros de URL, y si se les pasa una página HTTP concreta, esa página se carga en el WebView de la app. Las puertas de entrada suelen ser el navegador, otra app o incluso un código QR.
  2. Pantallas H5: pantallas que usan WebView para pintar la interfaz en lugar de componentes nativos, normalmente descargadas de un servidor de confianza. El ataque aquí no es directo: el atacante inyecta un payload XSS en el servidor y envenena el contenido; cuando la app descarga la pantalla H5, carga el payload.
  3. Navegador in-app: apps como Facebook abren los enlaces en su propio navegador interno. El punto de entrada típico es el chat de mensajería: un conocido envía un enlace, se hace clic y se lanza el navegador de la app.

¿Qué es un JavaScript Bridge?

Un JavaScript Bridge (JSB) es el mecanismo que permite al código JavaScript de un WebView interactuar con el código nativo de Android. Desde JavaScript se llama a un objeto expuesto —por ejemplo AndroidBridge.showToast(...)— y Android hace la magia de mapear esa llamada al código nativo registrado con addJavascriptInterface. Toda función JSB lleva, sobre su declaración nativa, la anotación @JavascriptInterface. Con eso ya se es experto, bromea la autora, y pasa a los ejemplos reales.

El manual del investigador: estático + dinámico sin IA

Se asume que ya se encontró una redirección por deep link que carga evil.com en el WebView de la app. ¿Cómo se analiza? El flujo clásico:

  1. Extraer la APK con adb pull.
  2. Descompilar con JADX en la PC.
  3. Búsqueda estática: buscar addJavascriptInterface. Problema inmediato: aparecen muchísimas interfaces, y muchas no son alcanzables desde el deep link. Hacer tracing manual del código desde la fuente hasta el sink para saber cuál se carga es impracticable —si se usara un asistente de IA quizá no, pero este hallazgo es de la "época antigua"—.
  4. Análisis dinámico: una vía es hookear con Frida la carga de la interfaz al hacer clic en el deep link. La preferida de la autora es Chrome DevTools: con Frida se activa el modo debuggable del WebView, se conecta el móvil a la PC, se abre chrome://inspect, se inspecciona el WebView cargado y en la consola se tipea la interfaz. Ahí aparecen las funciones JSB expuestas —en xbridge, dos: showToast e invokeMethod—. Confirmado que la interfaz está viva en ese WebView, se procede.

Anatomía de invokeMethod

La función invokeMethod hace varias cosas: toma la configuración del WebView, ejecuta una verificación "secreta" que volverá a aparecer después, deserializa un string en un objeto de tipo bridge, y lo pasa a processBridgeObject. El objeto bridge tiene cuatro campos: handleName, data, callbackID y sink. Con eso ya se puede esbozar el payload.

processBridgeObject mete el objeto en un mapa y hace un lookup para resolver el módulo bridge correspondiente; módulo y datos se convierten en un bridgeRequest que pasa a onBridgeCall. Resulta que onBridgeCall es una clase abstracta: la implementación real está en las subclases. Buscando extends BridgeModule en JADX aparecen todos los handlers disponibles. Revisándolos uno por uno, uno destaca: un handler cuyo nombre es tool_base64, que recibe un objeto ImageConvertRequest con un solo campo, uri.

El problema salta a la vista: la URI se extrae como path con getPath(), y ese path —entrada del usuario— se pasa directo a new File(...). El resto del código convierte el contenido del archivo a Base64 y lo devuelve. Es decir: lectura arbitraria de archivos del almacenamiento interno de la app. Con un URI apuntando al archivo de cookies interno de la app, ahí está el camino a la toma de cuenta.

El bolas de la whitelist: el esquema javascript con doble barra

flowchart LR
    A[Víctima hace clic\nen enlace malicioso] --> B[Deep link redirige\nevil.com al WebView]
    B --> C[JS invoca\nxbridge.invokeMethod]
    C --> D[Bypass de whitelist\ncon esquema javascript://]
    D --> E[Handler tool_base64 lee\narchivo de cookies]
    E --> F[Base64 via callback\nal servidor C2]
    F --> G[Se decodifica SQLite\ny se extrae la cookie de sesión]

El payload se arma sobre una página en evil.com con una función callback que, al completarse la llamada JSB, alerta el texto Base64 devuelto. Pero no funciona: lo frena la verificación "secreta" del inicio. La lógica de esa verificación, con dominios de whitelist como boundapp.com y *.boundapp.com: toma la URL actual del WebView (evil.com), deriva el dominio con getHost(), y compara contra la whitelist —igualdad exacta contra el dominio, y endsWith contra el subdominio—. evil.com no pasa ninguna.

Primer intento: un subdominio que parezca el legítimo sin serlo, tipo t.boundapp.com.evil.com. Tampoco pasa: no es igual al dominio y no termina en el subdominio de la whitelist. Dos obstáculos, entonces: igualdad exacta del host y sufijo del subdominio.

La jugada: escribir el payload con el esquema javascript:. En Android 8 o inferior, un payload de este estilo resolvía el host de forma favorable y comprometía a cualquiera con esa versión, pero ya casi nadie está ahí. Y getHost() sobre un esquema javascript: devuelve null, así que en versiones modernas sigue bloqueado. La clave es imitar HTTP agregando una doble barra: javascript://boundapp.com/.... Ahora getHost() devuelve boundapp.com, la comparación exacta pasa y la verificación queda esquivada.

¿Y funciona el esquema javascript: de verdad? Sí: loadUrl de Android lo soporta nativamente. El matiz es que todo lo que va después de la barra se trata como comentario en JavaScript —el código de la misma línea queda afectado, el de la línea siguiente no—. Así que el payload final se estructura en dos líneas: la primera lleva el host falso que pasa la whitelist, y la segunda —la real— invoca al handler tool_base64 pidiendo el archivo de cookies. Decodificado, el exploit lee el archivo de cookies y su callback envía el Base64 al servidor C2 del atacante.

La verificación, con el payload final: getHost() devuelve boundapp.com, la comparación da verdadero, el código sigue su curso, el callback recibe el Base64 con el archivo de cookies y lo manda al C2. La demostración en video lo muestra en tiempo real: el servidor con el deep link redirige, el usuario acepta, y al instante llega al C2 el texto Base64. Al decodificarlo se ve la cabecera "SQLite format 3": con DB Browser for SQLite se abre la base, se recupera la sesión de boundapp y ahí está la cookie de sesión. Cuenta tomada.

Técnicas y herramientas mencionadas

  • JavaScript Bridge (JSB): mecanismo addJavascriptInterface + anotación @JavascriptInterface que une el JavaScript del WebView con el código nativo.
  • Deep link redirection: carga de URL controlada por el atacante dentro del WebView de la app vía parámetros del deep link.
  • adb pull + JADX: extracción y descompilación estática de la APK.
  • Frida: hook de la carga de interfaces JS y activación del modo debuggable del WebView.
  • chrome://inspect: inspección del WebView en vivo para listar las funciones JSB expuestas por la interfaz.
  • Lectura arbitraria de archivos: handler tool_base64 que pasa el path de la URI, controlado por el usuario, directo a new File(...) y devuelve el contenido en Base64.
  • Bypass de whitelist con esquema javascript://: getHost() devuelve null sobre javascript:, pero con doble barra (javascript://dominio.com/) devuelve el dominio falso que pasa la comparación; el comentario de la primera línea oculta el payload real en la segunda.
  • DB Browser for SQLite: decodificación del archivo de cookies exfiltrado y extracción de la cookie de sesión.
  • Servidor C2: receptor del Base64 exfiltrado desde el callback del payload.

Conclusiones

  • El JavaScript Bridge es una herramienta poderosa y muy usada para unir contenido web con funcionalidad nativa, pero introduce una superficie de ataque amplia que sigue pasándose por alto en las evaluaciones de seguridad de Android.
  • Una implementación insegura de un solo handler basta para escalar de un enlace malicioso a lectura arbitraria de archivos internos y, de ahí, a la toma de cuenta.
  • Las whitelists de dominio construidas con getHost() + comparación de sufijos se bypasean con esquemas no HTTP que imitan su estructura; validar el esquema y el origen real del contenido es tan importante como validar el dominio.
  • La metodología —extracción, descompilación, enumeración de handlers JSB y confirmación dinámica con Chrome DevTools— sigue siendo aplicable hoy, con o sin IA.
