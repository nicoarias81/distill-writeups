C4: canales de C2 externo portables con WebAssembly

Resumen

El external C2 —túnel de comunicación de un implante a través de servicios de terceros de confianza como GitHub, AWS o OneDrive— es una técnica veterana (atribuida en MITRE ATT&CK desde 2017) y bien documentada, con proyectos como LOL C2 que catalogan decenas de sitios compatibles. Su problema no es la idea sino la portabilidad: cada framework de C2 implementa sus perfiles externos con librerías y lenguajes propios, y portarlos de un framework a otro, o de un agente en .NET a otro en Go o JavaScript, es trabajo repetido y frágil.

C4 (Cross Compatible Command and Control) aborda exactamente ese cuello de botella compilando los canales de external C2 como módulos WebAssembly: el mismo binario .wasm se carga desde Python, Go, JavaScript, .NET o cualquier lenguaje con runtime WASM, con acceso al sistema operativo vía WASI. Los primeros plugins implementan AWS S3, Confluence y GitHub Gist, cada uno con la misma interfaz mínima de send/receive sobre JSON, lista de verificación operacional incluida (múltiples agentes simultáneos, nombres únicos por timestamp, soporte de mensajes grandes para exfiltración).

El problema de portabilidad del external C2

En una operación ofensiva típica, el implante desplegado en la red objetivo no habla directamente con el team server: usa un sitio de terceros que el tráfico empresarial normal ya visita, de modo que las comunicaciones maliciosas se camuflan entre el ruido legítimo. Cobalt Strike lo soporta con Malleable C2 profiles, Mythic con perfiles C2 propios; pero cada implementación queda acoplada al framework y al lenguaje del agente. El ecosistema de agentes de Mythic ilustra la fragmentación: Python, Go, JavaScript (incluso un agente disfrazado de extensión de Visual Studio Code), cada uno con sus librerías y sus particularidades.

El punto de partida concreto fue un perfil de C2 por GitHub desarrollado para el agente Athena (.NET, del ecosistema Mythic), con una librería .NET de GitHub. Funcionaba bien, pero portarlo a otros agentes y lenguajes exigía reescribirlo una y otra vez. La pregunta que origina C4: ¿existe un formato binario único que cualquier lenguaje de agente pueda ejecutar?

WebAssembly + WASI: el puente al sistema operativo

WebAssembly es un formato compilado —módulos .wasm que corren a velocidad cercana a la nativa— asociado al navegador (el caso canónico: Photoshop compilado y ejecutable en el browser). Para un operador ofensivo eso es insuficiente: el objetivo es el host real, no el navegador. La pieza que faltaba es WASI, la WebAssembly System Interface, que permite a los módulos interactuar directamente con el sistema operativo: leer, escribir y borrar archivos; leer el reloj del sistema; y abrir sockets para hacer peticiones de red. WASI se publicita como sistema de plugins universal, con soporte en la nube, aplicaciones server-side y sistemas embebidos.

Para materializarlo, C4 se apoya en Extism, un sistema universal de plugins sobre WebAssembly con dos kits: el plugin kit (escribir el plugin en varios lenguajes y compilarlo a .wasm) y el host kit (cargar y ejecutar ese módulo desde múltiples lenguajes). El runtime de Extism aporta tres propiedades valiosas para este caso: memoria persistente entre llamadas, control host-based (restringir a qué endpoints HTTP puede llegar el módulo) y guardrails de ejecución que mantienen el módulo contenido.

De hello world a canal operativo

La validación siguió una progresión deliberada: primero un programa Rust de seis líneas que devuelve "hello world", probado lenguaje por lenguaje a través de Extism; después un programa más complejo que hace peticiones HTTP reales, verificado con respuestas 200 de las APIs objetivo. Con ambas capacidades confirmadas (ejecución portable y red), los plugins de C2 se vuelven triviales.

Cada plugin expone dos acciones —send y receive— con parámetros en JSON:

  • AWS S3: send sube un archivo al bucket; receive lo descarga y lo elimina para no dejar rastro. Parámetros: access/secret key, nombre del bucket y región.
  • Confluence y GitHub Gist: la misma pareja de acciones sobre los servicios correspondientes.

En el host, la integración con Python es un pip install extism, un manifest que habilita las conexiones de red y WASI (imprescindible para sockets y system time), y la carga del plugin: se construye el blob JSON con las credenciales y el bucket, se invoca la acción, y se repite. Un bucle infinito de send/receive —el patrón habitual de cualquier agente open source— completa el canal.

Consideraciones operacionales

Un canal de external C2 listo para operación exige más que dos funciones que funcionen:

  • Múltiples agentes simultáneos — los mensajes se organizan en carpetas por agente emisor/receptor, garantizando que varios implantes convivan en el mismo canal (y que haya agente de respaldo si uno se quema: two is one and one is none).
  • Colisiones de nombres — cada archivo subido se nombra con el system time leído vía WASI, eliminando sobrescrituras accidentales.
  • Mensajes grandes — S3 soporta archivos enormes, condición necesaria para exfiltrar datos voluminosos del host comprometido.
  • OPSEC en el host — el manifest de Extism puede restringir los endpoints accesibles del módulo: en lugar de permitir conexiones a cualquier destino, limitarlas exactamente al bucket o servicio del canal.

Técnicas y herramientas mencionadas

  • External C2 — comunicación del implante vía servicios de terceros de confianza (ATT&CK T1102, desde 2017; catálogo LOL C2).
  • WebAssembly (.wasm) — formato binario compilado, near-native, portado entre lenguajes sin reescritura.
  • WASI — WebAssembly System Interface: filesystem, system time y sockets para los módulos fuera del navegador.
  • Extism — sistema universal de plugins WASM con plugin kit y host kit; runtime con memoria persistente, control de endpoints y guardrails.
  • Mythic C2 + agente Athena — framework y agente .NET de partida del perfil GitHub original.
  • AWS S3 / Confluence / GitHub Gist — servicios de confianza usados como canales, con acción send/receive y limpieza posterior.
  • Manifest de Extism — configuración que habilita WASI y acota los destinos de red del módulo.

Conclusiones

  • El external C2 no necesita ser difícil ni estar atado a un framework: compilar los canales a WebAssembly los vuelve portables a cualquier lenguaje de agente con el mismo binario.
  • WASI es la pieza que convierte a WASM en tecnología ofensiva viable fuera del navegador: sin acceso al filesystem y a sockets, un módulo web no sirve en un host comprometido.
  • La interfaz mínima send/receive sobre JSON, más las reglas operacionales (carpetas por agente, timestamps, limpieza de archivos), basta para un canal completo.
  • El runtime trae OPSEC gratis: los guardrails y el control host-based de endpoints permiten acotar exactamente a dónde puede hablar el módulo.
  • C4 publica sus plugins (S3, Confluence, Gist) con planes de ampliar el catálogo; WASM evoluciona rápido y merece seguimiento continuo desde el lado ofensivo y el defensivo.
