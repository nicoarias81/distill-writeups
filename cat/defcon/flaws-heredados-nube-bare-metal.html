Metal-as-a-Disservice: los fallos heredados que socavan la nube bare metal

Fuente: «DEF CON 33 - Metal-as-a-Disservice: Exploiting Legacy Flaws in Cutting Edge Clouds - Bill Demirkapi» · ver el video original

  • Video: EtGhHCr3VLE · URL: https://youtu.be/EtGhHCr3VLE · Conferencia: 01_defcon · Título original: DEF CON 33 - Metal-as-a-Disservice: Exploiting Legacy Flaws in Cutting Edge Clouds - Bill Demirkapi

Resumen

El auge del machine learning ha traído una nueva ola de proveedores cloud que ofrecen GPUs a precios competitivos —a veces a una décima parte del coste de AWS, Azure o Google Cloud— mediante servidores bare metal: hardware físico alquilado directamente, sin hipervisor ni capa de virtualización de por medio. Estos proveedores venden el acceso root directo al hardware como una ventaja de rendimiento y, en teoría, de seguridad: el servidor sería "físicamente aislado" del resto.

La realidad es otra. Un servidor bare metal expone de forma deliberada superficies de ataque que en la nube tradicional están cerradas: firmware UEFI, opciones de arranque, dispositivos PCI onboard, el Baseband Management Controller (BMC) y la red del datacenter. Mientras que los proveedores grandes llevan más de una década invirtiendo en su historia de seguridad de hardware y arranque, los proveedores nuevos de ML rara vez aplican las prácticas de reset y aislamiento que estas superficies exigen.

Este artículo recorre ese panorama de vulnerabilidades sistémicas: cómo persistir en servidores bare metal sin tocar disco, cómo backdoor de firmware UEFI, NICs y BMCs, cómo la red interna de estos datacenters esconde fallos que evocan ataques de hace dos décadas, y cómo una cadena DHCP→PXE→EFI convierte un problema de segmentación de red en RCE cross-tenant. Incluye el caso especial de RunPod, un proveedor de contenedores que hereda las vulnerabilidades de su proveedor de proveedor.

El problema de la superficie de ataque bare metal

Un servidor bare metal se distingue de una VM (donde un hipervisor media entre el inquilino y el host) y de un contenedor (donde se ejecuta el SO del host aislado salvo el acceso a la GPU): aquí se ejecuta directamente sobre el metal. Ese acceso root por diseño, el principal punto de venta, expone superficies que en cualquier otro modelo de nube están fuera del alcance del inquilino:

  • UEFI/BIOS: vulnerabilidades en el firmware de la placa, incluido el arranque por red, explotables desde la red local.
  • Dispositivos onboard (NIC, GPU): componentes privilegiados que, si se comprometen, conservan acceso al host incluso después de liberar el servidor al siguiente cliente.
  • Firmware backdooreado: si el proveedor no resetea bien la máquina entre inquilinos, un atacante puede infectar el host y mantener persistencia indefinidamente.
  • BMC: el chip que permite gestión out-of-band y que limpia el entorno entre cambios de inquilino. Comprometido, tiene control casi total sobre el host.
  • Red: sin aislamiento adecuado, el inquilino puede ver tráfico de otros servidores y ataques al flujo de provisioning pueden dar ejecución de código durante la configuración del servidor.

Es la superficie clásica de seguridad de firmware y hardware, pero con consecuencias peores: los ataques tradicionales de este tipo suelen depender de acceso físico, y aquí el acceso root remoto lo sustituye por diseño.

Provisioning con protocolos de hace dos décadas

Para gestionar cientos de servidores sin hipervisor, muchos proveedores usan Canonical Metal as a Service (MAAS), que automatiza el provisioning, el despliegue del sistema operativo y los scripts específicos del cliente. El flujo: el servidor arranca en un entorno de provisioning vía PXE boot (DHCP que responde con una imagen de arranque), pasa por estados de commissioning hasta ready —momento en que se configura el BMC— y queda disponible para desplegarse al cliente vía la API de MAAS.

El detalle crítico: MAAS depende de protocolos con casi dos décadas de antigüedad, PXE sobre DHCP y HTTP sin cifrar, para toda su API de provisioning. Esa herencia, combinada con una red interna mal segmentada, es la puerta de entrada a varios de los ataques que veremos.

Persistencia en el entorno de arranque

Los servidores bare metal suelen carecer de defensas básicas como Secure Boot —el objetivo es control total del cliente—, lo que facilita secuestrar la cadena de arranque. Un vector de persistencia sin tocar disco: crear una opción de arranque maliciosa en las variables NVRAM. Si el firmware soporta HTTP boot (casi siempre, ya que lleva más de una década en el código de referencia EDK2 y en firmwares UEFI), la opción puede apuntar a un servidor remoto del atacante en lugar del PXE local: el dispositivo obtiene IP por DHCP pero descarga una imagen EFI del atacante.

Además, UEFI permite variables autenticadas privadas: el atacante puede proteger su opción de arranque con su propia clave, de modo que limpiar la configuración sin acceso directo al firmware exige firmar con esa clave. Y si se necesitan cambiar opciones de BIOS sin consola, las estructuras de configuración ocultas de las IBVs (Independent BIOS Vendors) pueden localizarse con herramientas open source de parseo de variables UEFI, y modificarse desde el SO arrancando una imagen EFI propia en el siguiente boot que escriba los offsets deseados.

Herramientas para auditar el boot security

La enumeración básica en Linux ya da mucho contexto: dmidecode para modelo de placa y versión de BIOS, la ruta /boot/efi (partición EFI con bootloaders y configuración), y /sys/firmware para interactuar con la configuración de firmware. Encima de eso:

  • CHIPSEC: framework de análisis de seguridad de plataforma; comprueba el modo de fabricación de Intel, si la BIOS es escribible, y explica por qué un hallazgo es crítico y cómo explotarlo.
  • Intel Boot Guard: raíz de confianza de Intel al firmware del OEM. Mal configurado o no aplicado (por ejemplo, si el end of manufacturing no se alcanzó y las claves OEM no se fusionaron en el chipset), permite modificar el firmware e implantar persistencia. El firmware se extrae con las utilidades CSME de Intel, con herramientas específicas de la IBV (AFU Linux en placas AMI) o con el volcado SPI ROM integrado en CHIPSEC; UEFITool muestra las regiones protegidas y cuáles quedan expuestas para inyectar código.
  • Platbox (IOActive): equivalente para auditoría en equipos AMD, donde el análogo de Boot Guard es AMD ROM Armor — que en la práctica rara vez es seguro. Platbox además habilita lectura y escritura de la flash.

Con acceso de escritura a la flash y módulos sin protección, UEFITool 0.28 permite sustituir partes del firmware. La comunidad de game hacking ha publicado trabajo directamente reutilizable: proyectos como SMM Infect muestran cómo reemplazar una imagen SMM no utilizada por un driver EFI malicioso que mantiene persistencia tras liberar el servidor.

El downgrade como primitiva universal

Frente a Boot Guard o ROM Armor que no se pueden romper, hay una técnica de escalada de OS a entorno de arranque que funciona una y otra vez: downgradear el BIOS a una versión antigua con vulnerabilidades conocidas. El código sigue firmado —es código legítimo, solo que vulnerable—, así que pasa las verificaciones de integridad. Los contramedidas existen (los secure version numbers de Intel, con anti-rollback), pero empíricamente ningún OEM grande los usa: cuando publica un parche, no incrementa el número de versión segura.

Dispositivos PCI: el firmware que nadie resetea

Resetear la BIOS no basta: los dispositivos conectados al host —GPUs, adaptadores de red del BMC, controladores— llevan su propio firmware. Su enumeración es trivial (lspci, /sys/bus/pci), y los drivers de Linux a menudo conservan restos de funcionalidad crítica: el driver bnxt_en de los controladores Broadcom, por ejemplo, incluye la capacidad de flashear la NVRAM del adaptador, y volcados con ethtool.

La pieza clave es la option ROM: drivers EFI dentro de la flash del dispositivo que permiten la interoperabilidad con el host y se cargan en el entorno UEFI como cualquier otro driver. Sin raíz de confianza que la proteja, sustituir la option ROM es una vía de persistencia cómoda que no exige hacks de DMA ni del firmware del host. El proyecto Thundergate, pese a su década de antigüedad, sigue siendo el punto de partida para reemplazar firmware y option ROMs de adaptadores Broadcom.

Los flujos de descomisión como OpenStack Ironic pueden resetear la BIOS, pero resetear el firmware de dispositivos onboard es raro fuera de los proveedores grandes. Dell y HP ofrecen al menos una raíz de confianza básica para componentes que vienen con el servidor; los proveedores que empiezan, en general, nada.

GPU firmware es el caso especial: los microprocesadores Falcon de NVIDIA, desde Maxwell, imponen raíz de confianza y exigen firmware firmado. Sin la firma, el backdooreo de la GPU de un servidor alquilado está fuera de alcance — la oportunidad queda reducida a la cadena de suministro.

Dónde conseguir las herramientas

Las utilidades de los fabricantes imponen cada vez más verificación de firma aunque no sea técnicamente necesaria. Fuentes alternativas: los foros de BIOS modding (WinRaid, BadCaps), plataformas de análisis de malware, directorios abiertos con utilidades de Intel y —la más productiva— scrapear paquetes de drivers OEM: descargar el catálogo completo de drivers de un fabricante, extraer los ZIP, y buscar utilidades internas que se filtraron dentro de los paquetes. Así se consiguieron herramientas que permitían flashear el BMC sin tropezar con la verificación de firmware de sus equivalentes oficiales.

El BMC: el corazón comprometible del servidor

El BMC es un mini-PC dentro del servidor que permite gestión remota (consola KVM incluida) aunque el host esté apagado, independiente del SO y del CPU. Encontrar vulnerabilidades que permitan backdoor de su firmware exige inversión de tiempo, pero casi siempre hay alguna.

Enumeración desde el host con ipmi-config e ipmitool. El fruto maduro son las customizaciones propietarias sobre el firmware base: un fabricante como ASUS parte de MegaRAC y añade capas propias, mucho menos auditadas que el código base. Entre los hallazgos tipo: comandos IPMI indocumentados que resetean el BMC a fábrica, dejándolo con credenciales por defecto y permitiendo flashear su firmware con lo que se quiera, según la verificación presente.

Los canales KCS (keyboard controller style) y SOL (serial over LAN) permiten control desde el host o out-of-band, y algunas herramientas otorgan más acceso si se ejecutan desde una UEFI shell — que un script de arranque en la shell puede automatizar. Cada interfaz es una pregunta de auditoría: ¿permite acceso por defecto y con qué privilegio?

Dos lecciones sobre verificación de firmware:

  • Que la herramienta oficial rechace un firmware modificado no significa que la flash esté protegida: la verificación puede ser client-side. Una herramienta de otro fabricante para el mismo chip (un AST2500, en el caso observado) flashea sin problema.
  • Que el fabricante documente soporte de firma no significa que esté activa. En sistemas Supermicro X11/H11 la firma existe pero, por compatibilidad hacia atrás, no está habilitada por defecto. Alternativas ante un BMC firmado: downgradear a una versión anterior a 2024 con vulnerabilidades conocidas del software BMC de Supermicro, o usar herramientas de otros fabricantes del mismo chip.

La red: el camino más corto al cross-tenant

El servidor bare metal es, por diseño, acceso root a un datacenter sin necesidad de phishing ni comprometer empleados. Y en los proveedores líderes de precio del espacio ML, la seguridad de red recordaba a los ataques estilo Cain & Abel de hace dos décadas:

  • Modo promiscuo: trivialmente, Wireshark capturaba tráfico de servidores de otros clientes — ni siquiera segmentación básica.
  • ARP spoofing contra el gateway de MAAS: funciona extremadamente bien y desata un flood de tráfico.
  • VLANs aplicadas en el propio host bare metal: irrelevantes, el inquilino tiene root y las salta.
  • Firewalls en la gateway (solo puerto 22 expuesto al exterior): desde la red interna, un Nmap revela superficies mucho mayores de las que el cliente pretendía exponer — daemons SSH de hace una década vulnerables, acceso IPMI a la infraestructura del datacenter.

Un vector inesperado: alquilando un Mac Mini bare metal para inferencia, la barra de menús mostraba el icono de Wi-Fi y el datacenter tenía una red abierta para visitantes. (En AWS el dispositivo Wi-Fi aparece desconectado a nivel hardware.) macOS permite incluso monitor mode por defecto, exponiendo frames en crudo del aire: handshakes WPA2 de redes vecinas capturables para cracking. Un puente directo de un escenario de ataque remoto a la superficie física del datacenter.

De DHCP descubierto a RCE cross-tenant

La red insegura se convierte en ejecución de código a través del provisioning:

  1. En modo promiscuo, la red muestra las ofertas DHCP del gateway cuando otros servidores se provisionan.
  2. Detectado un DHCP discover, hay dos caminos: responder con una URL PXE maliciosa y un servidor propio para alimentar al servidor una imagen EFI propia en el arranque (RCE), o registrarse en MAAS suplantando la MAC del servidor.
  3. Suplantando la MAC en el registro se reciben las provisioning keys del servidor real: acceso a la configuración del cliente — contraseñas personalizadas, scripts de inicialización, credenciales de API del cliente.

Con ARP spoofing activo, en lugar de falsificar respuestas DHCP basta un MITM del servidor MAAS directamente: los protocolos van sin cifrar, así que la imagen bootx64.efi real se sustituye por una backdoor. Además, los servidores MAAS exponen por defecto un proxy HTTP squid (caché de paquetes APT) que sirve para tunelizar y escanear la red local incluso si el propio servidor está aislado. Las provisioning keys, si ya se está dentro de un entorno, se extraen en texto claro del fichero pickle en /var/lib/cloud. Y el registro por MAC tiene una race condition: competir por el registro y reclamar las claves antes que el servidor legítimo.

Caso RunPod: heredando las vulnerabilidades del proveedor del proveedor

RunPod no ofrece bare metal: alquila contenedores Docker con acceso a GPU, con un "secure cloud" de datacenters vetados. Pero un traceroute desde sus servidores mostró que revenden capacidad —probablemente por contrato mayorista— de un proveedor de bare metal por horas. Comprometiendo ese proveedor subyacente vía ARP/DHCP spoofing, apareció tráfico de clientes de RunPod: ejecuciones de entrenamiento de ML entre nodos sin cifrar, y logs sin cifrar del servicio de inferencia gestionado de RunPod con nombres de contenedores Docker incluidos.

La lección es doble: un entorno de contenedores hereda inherentemente las vulnerabilidades de los proveedores de sus proveedores; y RunPod merece mención por ser de los únicos proveedores que corrigió a tiempo para la divulgación, aislando las redes de sus clientes de las del resto.

Qué debería hacer un proveedor bare metal

  • Reflashear todos los dispositivos, no solo el BIOS: NICs, BMC, GPU. OpenStack Ironic ofrece reset de firmware en el flujo de limpieza; MAAS, según lo observado, no tiene un flujo automatizado por defecto para firmware. Las interfaces Redfish del BMC suelen ofrecer la capacidad — hay que usarla.
  • Desconectar físicamente los dispositivos PCI innecesarios, como el adaptador Wi-Fi de los Mac Mini.
  • Aislar la red: es la medida más crítica, porque los backdoors de BMC o NIC exigen inversión considerable mientras que la red fue el ataque más simple con impacto enorme.
  • No usar BMCs legacy: elegir chips con verificación de firmware integrada (plataformas con chips de resiliencia que detectan manipulación en tiempo real, como las de los proveedores grandes), sabiendo que aun así no hay protección total.

Técnicas y herramientas mencionadas

  • MAAS (Metal as a Service): herramienta de Canonical para provisioning automatizado de servidores bare metal.
  • CHIPSEC: framework de Intel para analizar seguridad de plataforma (Boot Guard, flash SPI).
  • Intel Boot Guard / AMD ROM Armor: raíces de confianza de firmware; protegen el arranque cuando están bien configuradas.
  • UEFITool: parser de firmware UEFI para localizar regiones protegidas e inyectar código.
  • Platbox (IOActive): kit de auditoría de plataformas AMD.
  • PXE boot / DHCP / HTTP boot: cadena de provisioning heredada, sin cifrar, explotable por MITM.
  • ipmitool / ipmi-config: enumeración y control del BMC desde el host.
  • lspci / ethtool: enumeración de dispositivos PCI y volcado de NVRAM de NICs.
  • Thundergate: herramienta histórica para flashear adaptadores Broadcom.
  • SMM Infect: proyecto público que muestra cómo implantar un driver EFI malicioso en firmware.
  • UEFI NVRAM variables autenticadas: mecanismo usado para persistencia en opciones de arranque firmadas por el atacante.

Conclusiones

  • La superficie de ataque bare metal es en parte imposible de cerrar del todo, y la promesa de "mayor seguridad por aislamiento físico" se desmorona cuando el proveedor no invierte una década en boot security y hardware como los grandes.
  • Para cargas de trabajo sensibles, una VM es probablemente más segura que bare metal: la implementación defectuosa generalizada de los proveedores nuevos hace que el modelo virtualizado gane en la práctica.
  • No creer en el confidential computing vendido sobre estos entornos: es, como mucho, un disuasorio.
  • Para la mayoría de organizaciones, la renta por horas de GPUs en estos proveedores sigue siendo razonable — la pregunta honesta es si la carga de trabajo es lo bastante valiosa como para ser objetivo. La alternativa radical: comprar el hardware propio.
  • Líneas de investigación abiertas: qué se puede hacer desde un contenedor con acceso PCI a la GPU, vulnerabilidades de red en entornos virtualizados, y automatizar el descubrimiento de estas vulnerabilidades sistémicas, hoy casi todo hecho a mano.
