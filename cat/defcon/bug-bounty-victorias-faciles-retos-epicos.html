De victorias fáciles a retos épicos: la edición bug bounty

Resumen

Siete años de bug bounty (~$2M en recompensas acumuladas), 15 de CTF, 18 hackeando, perfil de web application enjoyer: PHP, source code review, nada de recon —ir directo a la app principal y romperla—. El criterio de selección de hallazgos: los sorprendentes, tanto por lo fácil como por lo difícil. El recorrido cubre cuatro programas suizos y un CMS sin nombre: Swisscom (primer programa, programa propio fuera de plataformas, ~$500k ganados ahí), Swisscom Worklink, Swiss Post (e-voting, recompensas de hasta $230k para hallazgos muy críticos, vdp.post.ch) y un objetivo anónimo.

Swisscom Cockpit: tres bypasses de autenticación

El Cockpit gestiona suscripciones móviles y PII/pagos: login por número de teléfono + token SMS + captcha. Hay una instancia de staging pública en internet —objetivo privilegiado porque puede exponer código sin desplegar en producción—.

  1. Token 1111 en staging: el SMS token del entorno de staging era siempre 1111, pero el login en staging fallaba con internal server error. La hipótesis: el almacén de tokens SMS era compartido con producción. Pedir el token en staging y usar 1111 en producción = sesión iniciada en producción. $8.000, con PII de millones de clientes potencialmente expuesta.
  2. Cifrado compartido cookie captcha/token: el proceso de login setea tres cookies cifradas (captcha text, msisdn key, SMS token key). Copiando el valor de la cookie del token SMS dentro de la cookie del captcha y recargando la página, el PIN aparece en claro renderizado en el captcha —mismo sistema de cifrado, cifran con la misma clave cosas distintas—. Bypass válido pero poco automatizable (leer captcha a mano): $3.000.
  3. Cancelar = autenticado: tras pedir el SMS, cancelar el flujo dejaba la sesión autenticada. Probablemente un bug introducido al parchear los anteriores. $8.000.

Swisscom Worklink: XML injection → admin → RCE

Worklink usa un CMS desconocido llamado Weblication. El método: comprar la licencia para obtener el código y hacer source code review. El CMS no usa SQL: bases de datos XML + filesystem, con un mecanismo general anti-path-traversal. Bypass del filtro: como limpia primero los caracteres de traversal y después los pipes, dot|dot|slash sobrevive como ../. Con eso: un primitivo de borrado de archivos restringido a un directorio inexistente (invisible sin más) + un primitivo de creación de directorios arbitraria, combinables para borrar archivos en cualquier sitio.

La protección de las bases XML en weblication/wWith/5/ es solo un .htaccess. Borrarlo expone las bases. Detalle peculiar: todas las bases XML tienen extensión .php, lo que rompe el plan de leer la base de login logs (contiene los session tokens de todos los usuarios: autenticación directa) porque PHP short tags colisionan con las open tags del XML y devuelve internal server error. Todo intento de lectura directa falla por la misma razón.

La cadena ganadora:

  1. XML injection en la base de "blocked users" (usuarios bloqueados tras 3 intentos fallidos de login) vía el username.
  2. El parser llama DOMDocument::xinclude(false) —con la intención de deshabilitar XInclude—, pero PHP con false habilita xinclude: la directiva XInclude del username inyecta el contenido completo de la base de login logs dentro de la base de bloqueados. XInclude re-formatea el resultado como XML válido (no rompe el archivo).
  3. Blind XPath injection en cómo la app evalúa la base de bloqueados: un oracle por carácter ("account is blocked" vs "no user found") extrae los session tokens byte a byte.
  4. Con un token de admin → panel de administración → feature de RCE incluida.

$2.500 + $500 de bonus por la cadena, más $2.000 del propio editor Weblication (sin bug bounty, impresionado por el hallazgo).

Swiss Post: dinero infinito por esperar

Su sistema de pagos propio custom, con balance y endpoints de éxito/fallo. Manipulaciones de la sesión de pago y de precios no dieron fruto —el corte lo dio una interrupción real: un repartidor tocó el timbre y hubo que cortar un paquete—. Al volver 10-15 minutos después, había dinero en la cuenta sin origen aparente. Reproducir la manipulación fallaba; repetir todo, incluida la pausa de café, funcionaba: si la transacción excede el timeframe de pago, el chequeo de estados considera la transacción exitosa por defecto —debería defaultear a fallo—. Pagar = simplemente esperar. $3.000, probablemente lo más rentable por minuto de la sesión.

Swiss Post Peppershop: backup/restore → admin global

Otro CMS oscuro comprado con licencia para auditarlo: Peppershop, CMS suizo en PHP. El restore de backup usa un delimitador custom entre queries SQL y una feature inexplicable de tags base64_start/base64_end que se reemplazan por un string entre comillas simples del contenido decodificado. Plan: inyectar datos que, al hacer backup + restore, rompan el contexto SQL y ejecuten queries arbitrarias.

Obstáculos: sanitización global de casi todos los campos (sin newlines, hashes ni caracteres especiales) y el restore aborta al primer query inválido. Soluciones: los comandos de un pedido (campo alcanzable desde el front-end sin sanitizar) y construir un archivo de backup válido inyectando el delimitador + query nueva + comentario final. Resultado: UPDATE sobre tablas y columnas arbitrarias durante el restore. El impacto concreto: la autenticación admin es solo un .htaccess —borrarlo expone /admin sin más—, y hay un gadget en los objetos serializados almacenados en la base (PHP guardando objetos serializados en una base relacional) que borra archivos locales. El payload escribe un objeto serializado con path traversal al .htaccess en la tabla de pedidos; al restaurar el backup, el .htaccess desaparece y todo el mundo es admin.

$650. Matiz honesto: Swiss Post no usa la feature de backup/restore (crashea por memoria con su volumen de datos), así que el impacto real era nulo para ellos; pagaron igual por el hallazgo.

CMS sin nombre: bypass de parche SSTI y RCE vía sendmail

  • Bypass del parche de una CVE de SSTI explotada in the wild: el doble nivel de templating de la app se parcheó con un preg_replace que elimina las tags tras una sola evaluación. El regex no matchea newlines: el payload original con un antes de la tag de cierre lo bypasea. Segundo bypass (del colega): no cerrar las tags nunca —el template termina conteniendo las tags de cierre más adelante—. $10.000.
  • RCE vía argument injection a sendmail: contexto: Laminas PHP para todo lo relacionado con email, control del header From que pasa como quinto argumento de mail() —los argumentos del binario sendmail—. Pila de obstáculos: Laminas valida que sea email real (formato quoted-string o atom con regex enorme); PHP aplica escapeshellcmd automático a todo el comando, y el doble escape (el de Laminas + el automático) anula el escape —doble escape = sin escape = argument injection, gracias PHP—; Laminas lowercasea (mata los argumentos -C/-X en mayúsculas que necesitan las exploits clásicas); límite de 64 caracteres en el local part, insuficiente para las rutas largas de los payloads estándar.

La grieta: un comportamiento raro con angle brackets derechas revela que Laminas genera el email completo, lo parsea y re-extrae el remitente. Leyendo RFC 2047 (MIME-encoded words), el formato =?charset?encoding?...?= permite literales hexadecimales =XX, y el underscore _ se define como espacio —el espacio directo (=20) está prohibido—. Todos los caracteres del formato son válidos en un email en formato quoted-string: se pueden inyectar MIME-encoded words en el From que, al ser re-parseado, generan argument injection a sendmail. El payload cabe justo en 64 chars si el web root es corto (/app) y se sube un archivo de configuración de sendmail (con _ reemplazados por =5f para sobrevivir al upload) que redirige el dead letter file al web root y define un double-bounce recipient con el contenido del archivo escrito. Enviar a una dirección inexistente fuerza el bounce → escritura parcial de archivo en el web root → webshell PHP → RCE. $5.000. Precondiciones duras (sendmail como MTA, web root corto) que lo hacen poco explotable, pero técnicamente sublime —el payload acaba impreso en una camiseta—.

Conclusiones

  • El método consistente: comprar licencias de CMSs oscuros para auditar código fuente es una estrategia de bug bounty infrautilizada que produjo las cadenas más graves del recorrido.
  • Los bugs más rentables suelen ser los más simples (cancelar = logueado, $8.000; token 1111 compartido entre staging y producción, $8.000) y los más elegantes no siempre son los mejor pagados ($650 por admin global vía backup/restore).
  • Las interrupciones de la vida real son parte del método: el bug de dinero infinito solo apareció al volver del café —el factor tiempo es parte del payload—.
  • Los detalles del ecosistema PHP son superficie de ataque: escapeshellcmd doble que cancela el escape, short tags que rompen archivos XML, xinclude con false que lo habilita, objetos serializados como gadget de borrado.
  • Los programas suizos (Swisscom, Swiss Post) pagan bien y comunican de forma justa, con programas propios fuera de las plataformas centralizadas.
