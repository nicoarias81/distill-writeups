MicroPython frozen modules: extraer bytecode de un firmware como si nada

Fuente: «DEF CON 33 - Reverse Engineering MicroPython Frozen Modules - Wesley McGrew» · ver el video original

  • Video: QXa29AJqdRc · URL: https://youtu.be/QXa29AJqdRc · Conferencia: 01_defcon · Título original: DEF CON 33 - Reverse Engineering MicroPython Frozen Modules - Wesley McGrew

Resumen

Recorrido completo por el mecanismo de frozen modules de MicroPython —implementación desde cero de Python 3 para microcontroladores, no un port de CPython— y por el proceso de reconstrucción del bytecode que queda cocinado dentro del firmware en tiempo de compilación. El motivo práctico: muchas badges y dispositivos embebidos usan este mecanismo, y los CTFs sobre badges suelen esconder secretos, claves y código dentro de módulos congelados precisamente porque no existen herramientas públicas para desensamblarlos.

La tesis de cierre es directa: el congelado existe para eficiencia —ahorra memoria y tiempo de carga—, pero se abusa de él como ofuscación. Y no funciona como protección: con un build de referencia, paciencia y el mpy tool, el módulo se reconstruye bit a bit.

Tres formas de código, una sin herramientas

Un dispositivo MicroPython puede llevar su código de tres maneras: texto plano en un pequeño file system emulado en flash, módulos de bytecode precompilado (.mpy) en ese file system, o módulos congelados compilados dentro del firmware. Para los dos primeros hay herramientas; para el tercero, nada: el proceso de congelado convierte el .mpy en un set de estructuras de C que se enlazan estáticamente, y el compilador las distribuye por la memoria en lugares no obvios. De ahí el atractivo para esconder cosas —y los foros están llenos de gente preguntando cómo guardar contraseñas y claves lejos de los usuarios de sus dispositivos—.

Empezar fácil y quitarse lo fácil

La demo arranca en la plataforma más cómoda, Raspberry Pi Pico, donde picotool info lista los frozen modules del firmware conectado. Esa lista viaja en el campo de "binary information" del Pico y MicroPython la codifica ahí expresamente —pero es prescindible: puede eliminarse comentando la generación en la herramienta de congelado, y otros microcontroladores ni siquiera la tienen. El primer paso del ataque es, entonces, imaginarse el escenario donde el fabricante ya la quitó. Alternativa si hay acceso al REPL serial: help('modules'). Pero no siempre hay REPL, así que el método robusto no depende de ninguna de las dos cosas.

La piedra Rosetta: construir un firmware de referencia

La técnica ancla del reversing: compilar un build de MicroPython con símbolos de debug que incluya un frozen module propio (no el del objetivo) y compararlo lado a lado en Ghidra con el binario stripped del dispositivo —extraído por flash dump, actualización over-the-air o lo que toque. Los símbolos del build de referencia —mp_frozen_names (la lista de módulos), mp_frozen_mpy_content (el contenido)— sirven de mapa para localizar las estructuras equivalentes en el binario sin símbolos:

  • Ojo directo: buscar strings con .py y comparar la lista de constantes contra los módulos estándar; el excedente son los módulos del fabricante.
  • Vía robusta: la función mp_find_frozen_module referencia ambas estructuras; un cross-reference en Ghidra desde las cadenas conduce a ella, y dentro de la función aparecen las referencias al contenido congelado.

Interning de strings: los QSTR y sus pools

MicroPython evita duplicar constantes de cadena en memoria con internado: los "QSTR" (unique strings) se referencian como índices dentro de una lista enlazada de pools. Un pool guarda puntero al anterior, el largo acumulado previo (que fija por dónde empiezan los índices del pool), arrays de hashes de un byte, arrays de longitudes y los datos de todas las cadenas concatenados sin separadores —los largos son los que delimitan cada string—. Hay un pool estático, idéntico en todos los builds, generado por el script de build, y el pool congelado viene después, con los strings de los módulos congelados.

Consecuencia práctica para reconstruir el .mpy: un índice por debajo del límite del pool congelado (en el ejemplo, 962) apunta a un string ya presente en el binario base y se referencia por número; un índice por encima exige re-encodear la cadena dentro del .mpy reconstruido.

Reconstruir el .mpy: header, strings, objetos y bytecode

El header del archivo reconstruido se copia de cualquier .mpy de la misma versión —basta con que pase las validaciones—. Encima, el tipo VUINT (entero sin signo de longitud variable: 7 bits por byte, bit alto como bandera de continuación) aparece en todas las estructuras. Luego:

  • Tabla de strings: cada entrada declara si es un índice existente o un string nuevo seguido de sus datos; solo los strings que no están en el pool base se escriben.
  • Tabla de objetos: la parte más compleja a medida que el módulo usa más objetos de Python; en la práctica se copian casi byte a byte desde la memoria al binario reconstruido y, una vez cargado, se inspeccionan cómodamente desde el REPL del Unix port.
  • Bytecode: read_raw_code de mpy_tool.py revela el formato. Cada bloque lleva VUINTs para el tipo (bytecode o código nativo de máquina), el largo y si tiene hijos; el parsing es recursivo por hijos hasta agotar el árbol de funciones. Si una función está compilada a nativo, Ghidra la desensambla y decompila directamente —el camino fácil—; si es bytecode de MicroPython (no compatible con el de CPython), no hay decoder y toca reensamblar el .mpy para que mpy tool lo disassembles.

Un detalle que complica la automatización: el largo del bytecode no está referenciado en ningún lado; la ejecución simplemente se mantiene dentro de sus límites mientras no retorne. Sin parsear el bytecode no hay forma limpia de conocer el largo —punto que, anota el investigador, quizás es explotable por sí mismo—.

El resultado de la demo: el .mpy reconstruido es bit por bit idéntico al original.

Análisis una vez extraído

Con el módulo reconstruido, el Unix port de MicroPython —la versión de escritorio del intérprete— lo importa y permite inspeccionar objetos, listar funciones, ejecutarlas y trazar la ejecución (si se compila con sys.settrace, aunque el trace es burdo: indica qué función corre, no granularidad de bytecode). Si el código extraído toca hardware —GPIO, pines— hay que implementar stubs para que corra en el Unix port. Para leer bytecode a mano quedan dos referencias: la clase de opcodes de mpy tool y el intérprete de la VM en el código fuente de MicroPython, con tutoriales de bytecode de CPython como base conceptual.

Conclusiones

  • Los frozen modules son la herramienta correcta para el último tramo de despliegue —ahorran memoria y tiempo de carga— y la incorrecta para esconder secretos: solo están tan protegidos como el acceso al firmware (flash dump, REPL, actualizaciones OTA).
  • Para el reverser acostumbrado a C compilado, el bytecode de MicroPython es en la práctica una ofuscación más efectiva que un firmware en C: molesto de leer, pero factible con la metodología del build de referencia.
  • La automatización completa de la extracción es posible pero complicada por los largos no declarados de los bloques de código; a mano, con Ghidra y mpy tool, el proceso es determinístico.
  • El formato de bytecode no es compatible con CPython: ni las herramientas de disassembly de Python de escritorio ni los debuggers aplican; mpy tool es el único disassembler del ecosistema y solo consume archivos .mpy.
  • Invitación explícita de cierre: no usar esto para arruinar CTFs ajenos — y sí para aprender a navegar estructuras en Ghidra, del mismo modo que lo enseña el libro de referencia sobre la herramienta.
