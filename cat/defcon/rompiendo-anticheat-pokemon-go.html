Rompiendo el anti-cheat de Pokémon Go: cronología de un hackathon

Resumen

Tal Skverer (líder de investigación en Aztec Security) reconstruye, nueve años después, la aventura de romper las defensas de Niantic contra los scanners no oficiales de Pokémon Go: desde forjar el primer request del protocolo protobuf hasta vencer el certificate pinning y replicar la firma cifrada que la app enviaba al servidor, en un hackathon comunitario de 67 horas con la comunidad PogoDev en Discord. El trabajo sirve también como catálogo de técnicas de hacking móvil: sniffing, protobuf decode_raw, dynamic/static reverse engineering, Frida, active probing y passive analysis.

El scanner y el protocolo

Motivación personal: viviendo en un pueblo rural, el "lousy scanner" de la app —solo los nueve Pokémon más cercanos y huellas 1-2-3— no le servía. Conjetura: el servidor conoce la ubicación exacta de cada Pokémon (aparece con precisión al acercarse) y delega el cálculo de distancia al cliente porque los servidores son perezosos. Con Fiddler Classic como proxy HTTP descubrió que la app mentía sobre su content-type (declaraba form URL-encoded y mandaba binario): era protobuf serializado. Sin las definiciones originales, reconstruyó los mensajes con protoc --decode_raw y tres trucos: inferir campos por sus valores (tokens de auth reconocibles), distinguir tipos que comparten código (los "integers" con signo eran floats: coordenadas GPS), y comparar mensajes al interactuar distinto con la app. Resultado: un request container con metadata (request ID, ubicación, auth) y una lista de requests tipados; el request 106 (luego getMapObject) recibía un ID de celda S2 (nivel 15 del framework S2Cells de Google) y devolvía el MapCell con gyms, Pokestops, spawn points y la ubicación exacta de cada Pokémon. El servidor era muy relajado: bastaba con request ID, auth info y un request 106 — el resto de campos desconocidos podía omitirse. Primer scanner funcionando.

La defensa: pinning y firma cifrada (Anon6)

Un miércoles el scanner murió: la app ya no levantaba con el proxy abierto. Niantic había metido dos defensas y la comunidad (PogoDev, el Discord de la API no oficial) se lanzó a un hackathon de tres días:

  • Certificate pinning: la clase Niantic Trust Manager (extensión de X509TrustManager, el patrón para encontrar pinning) hardcodeaba la clave pública del servidor y detectaba el certificado del proxy. Salto: dynamic reverse engineering con un módulo Xposed que hookeaba checkServerTrusted (before-hook) y reemplazaba el argumento por el chain real del servidor — el proxy volvía a funcionar.
  • Anon6 obligatorio: el protocolo no había cambiado, pero el campo 6 del request container, antes opcional, pasó a validarse. Con active probing (quitar campos de un request válido hasta que el servidor responda error) lo localizaron: un mensaje con un byte array interno, siempre múltiplo de 256 más 32. El grupo se autodenominó Team Anon6.

Análisis de Anon6: con passive analysis (generar cientos de muestras desde muchos dispositivos) vieron que los primeros 32 bytes solo dependían del tiempo (fijando el reloj, eran idénticos), que 256 sugería bloques de cifrado y que Anon6 estaba atado al request (cambiar solo el cell ID invalidaba). Es decir: una firma cifrada sobre la petición que el servidor ahora verificaba — antes se enviaba pero no se validaba, por la sobrecarga del lanzamiento.

Ingeniería inversa de la firma

Todo lo protobuf vive en la parte nativa del APK (Unity + libniantic-manager.so). Con static reverse engineering (Jadx para Java; IDA para el binario nativo) localizaron el generador: la tabla de imports de time() tenía dos cross-references, y el de offset 87444 alimentaba srand, generaba 32 bytes aleatorios y usaba la constante 256 por todos lados. Verificación con Frida: un script hookeaba la entrada y salida de la función en ese offset, y el output coincidía con el Anon6 enviado por la app. Bonus: el hook reveló el input de la función — la firma, también un protobuf, con GPS (location fix), device info y sensor data (aceleración, gravedad; vacío en emuladores, lleno en devices reales — análogo a los movimientos de mouse para CAPTCHAs).

Dentro de la función (sigencrypt): semilla de 32 bytes de srand(time()) prepended al output, padding del input al próximo bloque de 256 con el remainder en el último byte, y cifrado en modo CBC con un mecanismo desconocido de expansión de la semilla como IV (cada bloque cifrado sirve de IV del siguiente). El equipo se dividió:

  • Cifrado: recorrieron toda la call chain del offset 9E9D8, decompilaron automáticamente cada función con IDA y las unieron en un único archivo C de 14.000 líneas que, con parches mínimos, compilaba y ejecutaba idéntico al original. Cifrado propio resuelto en ~5 horas.
  • Firma: la mayoría de los campos no se validaban — con active probing vía Frida (borrar campos antes de cifrar) quedaron solo 6 requeridos, dos de ellos timestamps triviales. Los hashes se identificaron por sus constantes: XXHash32 para los campos 10 y 20 (sobre la ubicación; el 10 también sobre la auth info) y XXHash64 para el campo 24 (un hash por cada request enviado, sobre sus request bytes). El último campo resistió horas por una pista falsa (parecía depender de la auth), hasta que alguien notó que la función que lo generaba no recibía ningún input: valía cualquier cosa.

A las 19:00 del tercer día —67 horas después del inicio— el primer request no oficial firmado y cifrado triunfó. El Discord superó los 10.000 miembros, con un canal de investigación al que seguían cientos de personas en voice chat solo-lectura.

Epílogo y conclusiones

  • PogoDev mantuvo la API un año y medio más y cerró; hoy sobreviven bots de pago y apps modificadas — muy lejos de lo que un API oficial de Niantic habría habilitado para accesibilidad.
  • El playbook es reutilizable en cualquier app móvil: proxy HTTP para ver el protocolo, decode_raw + passive analysis para reconstruir protobufs, active probing para aislar campos requeridos, Xposed/Frida para vencer pinning y verificar funciones, IDA + decompilación automática de call chains para replicar algoritmos nativos.
  • La defensa de Niantic (pinning + firma cifrada atada al request con datos de sensores) es un buen estudio de caso de anti-cheat por atestación de cliente: cara de forjar, pero no infalible — el eslabón débil fue el algoritmo criptográfico reversible y campos de firma que el servidor no validaba.
  • Aviso: la mayoría de las técnicas mostradas ya no funcionan contra la app actual; el trabajo documenta la historia y la metodología, con blog post en dos partes como referencia extendida.
