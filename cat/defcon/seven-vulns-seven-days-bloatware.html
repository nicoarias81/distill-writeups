Seven vulns en seven days: cazar bloatware más rápido de lo que se construye

Resumen

Vacaciones de verano en Sudáfrica, una partida al videojuego favorito y, al cerrar la sesión, un cartel que no pedía nadie: ASUS Driver Hub ofrecía instalar una actualización de drivers. Al hacer clic se abría un navegador apuntando a driverhub.asus.com, que pedía instalar más cosas y terminaba con un modal que exigía reiniciar el equipo. La velocidad del reinicio delató la trampa: no había nada en la nube. Abrir las dev tools reveló la maquinaria real: un servidor web local corriendo en la propia máquina, con el que el sitio se comunicaba. Ese momento convirtió unas vacaciones en una investigación que terminó en vulnerabilidades en cuatro productos de "bloatware" de fabricantes de hardware gamer, todas reportadas y corregidas, y seis CVEs en una semana de trabajo.

Los objetivos: ASUS Driver Hub, MSI Center, Acer Control Center y Razer Synapse 4. Todos comparten un patrón de diseño cuestionable —servicios privilegiados que exponen mecanismos de RPC (sockets TCP locales, named pipes, objetos COM) con validación insuficiente—, y todos llegan preinstalados en equipos de millones de usuarios.

ASUS Driver Hub: RCE con un clic y bypass de UAC

Con Process Explorer se identifican dos procesos, ADU.exe y AsusDriverHub.exe; el primero escucha un socket TCP. El primer obstáculo es que el instalador se niega a ejecutarse en una VM ("this is not an ASUS product"): un parche de la instrucción de salto en Binary Ninja resuelve la instalación. La segunda comprobación del mismo tipo se evita en runtime interceptando la llamada initialize del servidor web local y cambiando la respuesta de false a true.

El reversing del endpoint /reboot muestra el flujo completo: una página web hace un fetch al servidor local, que invoca la API de Win32 ExitWindows. Un harness en PowerShell replica la petición y los logs de la aplicación (un archivo con nombre aleatorio que emite muchísima información) guían cada paso: primero falta el header Origin, luego falta el body, y el JavaScript del sitio —aunque minificado— entrega la estructura exacta del POST.

El bug del "string contains"

La validación del header Origin usa una función de comparación que debería verificar si el origen es asus.com, pero es un string contains sobre nueve bytes: cualquier origen que contenga .asus.com en cualquier parte (por ejemplo, driverhub.notasus.com) pasa la comprobación. Con un origen arbitrario que incluya esa cadena, cualquier sitio web puede interactuar con el servidor local.

El salto a RCE llega con el endpoint /updateapp, que descarga un ejecutable desde una URL: la misma comprobación defectuosa se aplica al agenturl, de modo que basta una URL que contenga .asus.com para que descargue un binario del atacante. La validación de firma PE es igual de frágil: solo verifica que una de las propiedades del certificado contenga el string "ASUSTeK Computer Inc.", sin comprobar que la firma sea válida. Herramientas existentes permiten clonar la firma de un binario legítimo firmado por ASUS al payload del atacante —la firma no será válida criptográficamente, pero las propiedades que el programa busca sí estarán—.

El exploit encadenado: un usuario visita un dominio del atacante que contenga .asus.com, y un clic lanza la descarga y ejecución del payload vía el servidor local. Ningún componente corre elevado, pero los jugadores suelen ser admins: adjuntando un side-by-side assembly manifest (UAC manifest con requestedExecutionLevel) al payload con mt.exe, la ejecución se vuelve determinísticamente elevada y bypasea el prompt de UAC. Como dato de contexto de exposición, la propia BIOS de la placa madre tiene una opción para descargar e instalar ASUS Driver Hub automáticamente.

Como mitigación estructural, el Chrome Working Group tiene una propuesta de especificación para restringir el acceso de los sitios web a recursos locales —al estilo de cómo hoy se restringen cámaras y micrófonos—, lo que obligaría a un aviso explícito antes de que una página hable con la red local.

MSI Center: race condition y ejecución como SYSTEM

MSI Center exige agregar el usuario local al grupo de administradores para funcionar, y uno de sus componentes escucha en un socket TCP con contexto elevado. El protocolo es binario pero las respuestas son JSON y el cliente está escrito en .NET sin ofuscación, así que el reversing se lee casi como una revisión de código fuente: un LaunchServer que registra callbacks de conexión y de datos, y una función DataResponse que despacha cada frame a componentes. Cada frame TCP lleva cuatro bytes que identifican el componente destino y el comando a ejecutar; el envío directo de los bytes de un comando de reboot (con esos cuatro bytes, identificados vía Wireshark, copiados al PoC) reinicia el equipo desde contexto no privilegiado.

La arquitectura es interesante: un component loader escanea el directorio de instalación buscando DLLs que coincidan con API_*, las carga e inicializa, y cada componente registra su mapa de comandos. Un componente con el comando AutoUpdateSDK acepta un target y argumentos, copia el ejecutable a C:\Windows\Temp\MSICenterSDK\, verifica la firma con WinVerifyTrust (la manera correcta) y, si pasa, programa una tarea programada inmediata que lo ejecuta como SYSTEM. El defecto: el binario que se verifica y el que se ejecutan no están vinculados. La ventana es minúscula pero real: corriendo dos hilos en carrera —uno con el ejecutable legítimo de MSI (elegido solo por tener firma válida) y otro con el payload—, la tarea programada puede terminar ejecutando el binario equivocado. El PoC gana la carrera y agrega un usuario administrador al equipo.

La escalada local 2 es aún más simple y casi cómica: el componente API_Support contiene su propia reimplementación de ExecuteTask con el mismo prototipo pero cero verificación: se pasa el target, se programa la tarea y corre como SYSTEM. Alguien en el equipo decidió no usar la librería común de seguridad, o quedó código legado. El exploit completo son cuatro líneas.

Acer Control Center: named pipe con permisos rotos

Acer Control Center no usa TCP sino un named pipe, con un servicio nativo privilegiado y un cliente .NET. La función del cliente SendCommandByNamePipe envía el pipe, un target path y un argumento (113); del lado del servidor, la lógica llega a un CreateProcessAsUser con exactamente ese target. Pero el pipe está configurado con FILE_ALL_ACCESS —algo que hay que configurar explícitamente mal, no es el valor por defecto—, lo que convierte una escalada local en ejecución remota de código: desde una VM atacante sin relación de dominio, un PoC se conecta al pipe remoto y hace que la víctima ejecute notepad.

Quedaba la pregunta de por qué el proceso corría como usuario normal y no como SYSTEM. La respuesta estaba en el argumento: con el valor 113 el SID se inicializa para un proceso de integridad normal; incrementándolo a 114, coincide con la constante del SDK de Windows para un SID de proceso de mayor integridad. Cambiar 113 por 114 en el PoC convierte la ejecución remota en una escalada de privilegios completa, remota y elevada.

Razer Synapse 4: FFI de Node, DLL parcheada y el atajo COM

Razer Synapse 4 ejecuta una cantidad absurda de procesos para cambiar el RGB de un periférico, y entre ellos hay un Razer Elevation Service corriendo como SYSTEM. A diferencia de los objetivos anteriores no expone puertos ni pipes, y está escrito en C++ (reversing más duro). La pista llegó con Procmon al interactuar con el cliente Electron durante la instalación de un componente Chroma.

Como el cliente es Electron, su código fuente vive en un archivo ASAR que se extrae con la herramienta oficial del equipo de Node. Ahí se descubre que el cliente usa una foreign function interface (node-ffi, un fork privado de una librería pública) para invocar directamente una DLL nativa llamada —literalmente— SimpleService.dll. Las definiciones en JavaScript delatan las funciones nativas exportadas, verificables comparando con los exports de la DLL en Binary Ninja.

El plan de prueba fue cargar esa DLL por cuenta propia y replicar los flujos de llamada. La función SimpleLaunchUserAppProcess impone restricciones aparentemente defensivas: el primer parámetro debe ser relativo al AppData y el segundo relativo al primero —asumiendo que el payload ya viva ahí—. La ejecución falla con un log de la DLL que dice "this PE file is not trusted": otra verificación de firma. Pero aquí hay un giro clave respecto de los casos anteriores: la verificación ocurre en la DLL cliente, que el atacante controla por completo. Basta copiar SimpleService.dll, parchear la validación de certificado PE y reejecutar. El detalle final: el payload de agregar usuario necesitaba contexto elevado, así que el mismo truco del manifest UAC con mt.exe cerró el PoC.

Y el remate: un colega redujo todo ese trabajo a una sola línea de PowerShell. La interfaz real con el Razer Elevation Service es un objeto COM. Con OLE View se enumera el PROG ID, se instancia con New-Object, y Get-Member revela métodos LaunchProcess que aceptan una ruta y ejecutan el binario en contexto elevado. Sin parcheo, sin DLLs, sin FFI: LPE directa en Razer Synapse 4 sin parchear.

Lo que no funcionó y la ética de la divulgación

No todo salió: HP Support Assistant, Gigabyte Control Center (arquitectura muy interesante) y Lenovo Vantage resistieron (aunque Artful Futures/Atredis Partners publicaron poco después bugs notables en Vantage vía manipulación de registro, vale la pena revisarlos). Los seis CVEs resultantes están todos corregidos; Acer decidió fusionar dos bugs en un solo CVE.

La divulgación dejó lecciones para los fabricantes: la página de divulgación de ASUS tiene un WAF que bloqueaba los payloads del reporte (justo lo que había que enviar); hubo una colisión de investigación donde otro investigador reportó el mismo bypass de origen dos meses después y ASUS le envió el anuncio del CVE acreditado a otra persona, dejándolo "colgado"; MSI respondió impecablemente rápido y fue el primero en corregir; Razer usó su programa de bug bounty como intermediario, y la cantidad de tickets internos que llegaron al buzón del investigador cuando intentó coordinar la divulgación pública contó la historia de una comunicación innecesariamente engorrosa.

Conclusiones

  • La Pwn Triad: si encontrás un servicio privilegiado con un mecanismo de RPC —named pipe, objeto COM, socket TCP, lo que sea—, revisá si tiene problemas de autenticación o validación. Casi seguro los tiene, y ahí hay vulnerabilidad (y, seamos honestos, una receta para CVEs).
  • Los patrones que se repiten: validación de Origin por substring, verificación de firma por propiedades del certificado en vez de validez criptográfica, verificación y ejecución desacopladas (race conditions), librerías de seguridad reimplementadas sin las verificaciones, named pipes con FILE_ALL_ACCESS, y validaciones que viven en componentes que el atacante controla.
  • Software de 2025 que hace RPC local de esta manera es diseño innecesario; y si el bloatware te parece inevitable, pensálo dos veces: probablemente haya alternativas mejores.
  • Si querés cazar CVEs: mirá lo que ya tenés instalado. Antes de desinstalarlo, quizás te deje un bug gratis. Los PoCs están publicados en GitHub y queda bastante superficie de ataque por explorar en estas mismas herramientas.
