El fantasma de Internet Explorer: doce CVEs en MapUrlToZone

Fuente: «DEF CON 33 - The Ghost of Internet Explorer in Windows - George Hughey, Rohit Mothe» · ver el video original

Resumen

Internet Explorer 11 está retirado, pero su esqueleto sigue sostiendo la seguridad de Windows moderno. El concepto de security zones —esa ventana clásica donde se clasificaba Internet, intranet local, sitios de confianza y restringidos— sigue vivo en cada Windows actual, y las decisiones de seguridad de componentes como Mark of the Web, el Explorador de archivos, los antivirus y Office pasan por él. La API que lo materializa es MapUrlToZone ("MUTs"): recibe una URL o ruta y devuelve la zona a la que pertenece. Cuando esa clasificación se equivoca, se abre la puerta a lo peor: el caso Outlook de 2023 (Forrest Blizzard, zero-click, robo y relay de hash NTLM) se mitiga precisamente con una llamada a MUTs. Sobre esa superficie, dos investigadores internos del MSRC encontraron y reportaron 12 CVEs corregidos desde enero de 2025 en cuatro categorías —prefijos de ruta, clasificación errónea de hostnames, canonicalización y misceláneos—, además de un double-free, y terminaron atacando la raíz: hacer que MUTs canonicalice con el mismo código que CreateFile.

Por qué importa una API que nadie llama

El caso que demuestra el impacto máximo: en Outlook se podía crear un recordatorio cuyo sonido de aviso apuntara a un archivo en un recurso compartido de red controlado por el atacante. Cuando el recordatorio saltaba —sin un solo clic de la víctima—, Windows se autenticaba contra ese servidor con NTLM, y el hash se podía relayar contra un Exchange vulnerable para autenticarse como la víctima. Explotado in the wild en 2023 por el threat actor estatal Forrest Blizzard.

El fix de 2023: Outlook/Exchange descartan la propiedad del sonido en recordatorios nuevos, y para los recordatorios antiguos con fecha futura se añadió una llamada a MUTs —si la zona del archivo es Internet o no confiable, no conectarse—. Es decir: la mitigación de un ataque zero-click depende de que MUTs clasifique bien. El peor caso de un bug en MapUrlToZone queda definido.

La investigación externa previa (Ben Barnea, serie de cuatro posts) marcó el camino: diferencias de canonicalización entre cómo CreateFile colapsa una ruta y cómo la clasifica MUTs —por ejemplo, //localhost/../...: CreateFile elimina localhost y termina pidiendo a un dominio remoto; MUTs cree que el host es localhost y la clasifica como local—. Barnea publicó tres bypasses y un double-free; ese trabajo fue el trampolín del estudio interno.

Categoría 1: prefijos de ruta

Aplican cuando el atacante controla el esquema inicial de la ruta (CreateFile solo abre rutas file:, pero otras APIs no son tan estrictas). El hallazgo: toda ruta que empieza con shell: la clasifica MUTs como local. El truco para hacerla remota: la carpeta "Network places" seguida de tres barras y una IP. Causa raíz: MUTs consulta los defaults de protocolo del registro, y el valor por defecto del esquema shell es 0 —que mapea a máquina local—, así que corta el análisis ahí mismo. El path es remoto; MUTs dice local.

Categoría 2: clasificación errónea de hostnames

MUTs decide si el hostname es IPv6, IPv4 o DNS. Si se logra engañar a IsIPv4/IsIPv6 con una IP real, MUTs cae en la rama DNS y hace lookup; y si el hostname no contiene puntos, la resuelve como intranet local. Dos requisitos: romper el parser de IP y no usar puntos (los dotless TLD y la notación hexadecimal de IP resuelven lo segundo). Dos bypasses:

  • IPv6 con interface ID larga: //<ipv6>%<ceros...>12/<ruta> — CreateFile recorta los ceros y conecta por la interfaz 12; pero las APIs subyacentes de IsIPv6 fallan cuando el interface ID excede 8 caracteres, así que MUTs lo trata como DNS, sin puntos → intranet local.
  • Puerto con cero inicial en IPv4: //<ip-hex>:080/<ruta> — CreateFile ve el puerto 80; MUTs lo interpreta como notación octal, y como 8 no es dígito octal válido, decide que no es una IP sino un nombre DNS → sin puntos → intranet local.

En ambos casos MUTs cree que el recurso está al lado cuando está en Internet.

Categoría 3: canonicalización

Las favoritas: sin fruta fácil restante (el terreno de Barnea) y ubicuas —funcionan en cualquier contexto y hacen clasificar rutas remotas como de la máquina local, no solo de la intranet—.

  • El signo de interrogación: //./C:/?/../..//<ip>/<ruta>. MUTs asume que tras el ? vienen parámetros de query HTTP y canonicaliza la ruta a //./C: —máquina local—. Pero no es una ruta HTTP: CreateFile procesa los .. y termina abriendo el recurso remoto. Hallado, según el propio investigador, probando tecla por tecla en esa posición hasta que cayó el ?.
  • Landman redirector con barra extra: \??\UNC\//<ip>/<share>. CreateFile colapsa las dos barras y conecta por SMB al host remoto; MUTs no canonicaliza primero y busca un hostname entre las dos barras —vacío—, defaulteando a máquina local. Un solo carácter de diferencia.
  • El orden de operaciones de una barra: dos rutas que difieren en una única barra cambian el orden de canonicalización en CreateFile: con una barra, localhost sobrevive y la conexión falla; con dos, localhost desaparece y se abre el recurso remoto. MUTs siempre hace lo primero: piensa que el path empieza en //localhost → local. La lección estructural: MUTs debe manejar una nuance diminuta en todos los casos o se produce el peor escenario.
  • //./UNC/C: + IPv6: Barnea había notado en un post que ese prefijo siempre devuelve 0 (local) y lo descartó porque ningún network provider manejaba rutas con dos puntos. La observación hecha desde la cama: IPv6 está hecho de dos puntos. Una dirección IPv6 que empiece con C: burla MUTs —aunque reconocen que comprar una IPv6 que empiece con C: no es trivial.

El double-free

Durante pruebas de un fix propuesto, MUTs crasheaba: el cleanup añadido liberaba un campo de propiedad que tenía una referencia colgante en otro lugar —double free clásico. Interés especial: un bug de memory safety en MUTs es explotable directamente, sin pasar por toda la cadena NTLM/relay. Por eso valía cazarlos.

Balance y la mitigación estructural

Total: 2 bypasses por prefijo de ruta, 4 por hostname, 4 por canonicalización, 2 misceláneos —12 CVEs corregidos desde enero de 2025 en MapUrlToZone, más el double-free.

La causa raíz única de todas las categorías: diferencias de parsing entre dos APIs críticas — MUTs, que clasifica, y CreateFile, que conecta — a veces sutiles, a veces grotescas. La mitigación (activa desde enero de 2025): MUTs ahora ejecuta el mismo camino de código de canonicalización que usa CreateFile, eliminando las diferencias en los escenarios especiales. Beneficio colateral: menos complejidad y menos código, al converger dos implementaciones que llevaban décadas divergiendo con cada point-fix. Hubo regresiones por los años de decisiones legacy —cada una resuelta con lógica de caso especial—.

Conclusiones

  • "Muerto" es un estado engañoso: el motor HTML, el scripting engine y las utilidades de IE siguen en system32 del Windows más reciente, y de ellos depende la clasificación de seguridad de Office, AV, shell y Mark of the Web.
  • Una discrepancia de canonicalización entre "decidir" y "ejecutar" es una clase de bug entera: cada divergencia es un bypass potencial con impacto de tipo NTLM-leak, MITM o peor.
  • El doble estándar CreateFile-vs-MUTs era el root cause; unificar el código de canonicalización vale más que cualquier cantidad de point-fixes.
  • Para investigadores: la investigación externa (los "throwaway thoughts" de los posts de Barnea) es material de primera para el trabajo interno; y los bugs de memory safety en una API de clasificación de seguridad son el atajo directo a la explotación.
