Distilled from OffSec PEN-300 (OSEP) course material (module: Advanced Antivirus Evasion) — internal training reference, not for redistribution.

Objectives

This module revisits Antimalware Scan Interface (AMSI) bypassing with a practical twist: rather than writing a new bypass from scratch, we first build a full understanding of how AMSI works internally (memory structures, API flow, hosting applications), then attack that understanding from several directions:

  • Understand how AMSI integrates into Windows 10 and how its provider model works.
  • Learn basic dynamic analysis with WinDbg and Frida to reverse AMSI behavior.
  • Bypass AMSI in PowerShell via reflection, context corruption, and in-memory patching.
  • Weaponize the bypasses in a realistic UAC bypass case study (Fodhelper vs Windows Defender).
  • Bypass AMSI in JScript (DotNetToJscript payloads) via registry abuse and DLL-loading tricks.

The guiding idea: obfuscation alone gets flagged quickly; durable evasion comes from understanding and manipulating the mechanism itself.

11.1 Intel Architecture and Windows 10

The module works exclusively with 64-bit Windows 10, so it opens with the essentials needed to read assembly:

  • Registers: the x64 register set (RAX, RBX, RCX, RDX, RSI, RDI, RBP, RSP, R8–R15 and their 32-bit views like EAX). RSP tracks the stack, RIP the instruction pointer.
  • Microsoft x64 calling convention: the first four integer arguments are passed in RCX, RDX, R8, R9 (in that order); further arguments go on the stack. Return values land in RAX. The caller must reserve 32 bytes of "shadow space" on the stack.
  • Practical instruction vocabulary used throughout the module: mov, xor, test, cmp, je/jne/jmp, call, ret, lea, and the u (unassemble) and r (registers) commands in WinDbg.

This matters because both AMSI bypass techniques later in the module are implemented by inspecting and patching x64 assembly in memory.

11.2 WinDbg Introduction

WinDbg (Windows Debugger) is introduced as the tool for inspecting AMSI internals:

  • Attach to or start a process (File → Open Executable...), break into it.
  • lm lists loaded modules; x amsi!* searches symbols in a module; bp / bu set breakpoints; g continues; p steps over; t steps in.
  • u <address> unassemble memory, r shows registers, db/dw/du dump memory as bytes/words/unicode strings, !vprot <address> shows memory protection of a page, s searches memory.
  • Symbol resolution requires the Microsoft symbol server (srv*c:\symbols*https://msdl.microsoft.com/download/symbols).

Key practice in the module: set a breakpoint on amsi!AmsiInitialize, trigger PowerShell, and single-step through the AMSI initialization to understand the AMSI_CONTEXT structure that everything else builds on.

11.3 Antimalware Scan Interface

AMSI is a Windows 10+ interface that lets applications (PowerShell, wscript, .NET 4.8, Office VBA macros, etc.) submit "content" — script blocks, strings, buffers — to the registered antivirus provider for scanning before execution. The design:

  • A hosting application calls into amsi.dll (AmsiInitialize → AmsiOpenSession → AmsiScanBuffer/AmsiScanString → AmsiCloseSession → AmsiUninitialize).
  • amsi.dll forwards the content to the provider (Windows Defender) through COM.
  • The provider returns a scan verdict; the host decides whether to run the code.

Because every script block in PowerShell and every JScript execution flows through these functions, they are the natural target for both observation (Frida) and tampering (patching).

11.4 Understanding AMSI

The module dissects the core API prototypes (from amsi.h):

  • AmsiInitialize(LPCWSTR appName, HAMSICO *context) — allocates and initializes the amsiContext structure. This opaque buffer holds per-app state, including the provider pointer and a header.
  • AmsiOpenSession(HAMSICO context, HAMSI_SESSION *session) — creates a session inside the context.
  • AmsiScanBuffer(HAMSICO context, PVOID buffer, ULONG length, LPCWSTR contentName, HAMSI_SESSION session, AMSI_RESULT *result) — the central scanning call; AMSI_RESULT values map onto AmsiResultShouldBlock(result). A result of 1 (AMSI_RESULT_CLEAN) passes; 32768 indicates malware detection.
  • AmsiScanString(...) — convenience wrapper that ultimately calls AmsiScanBuffer.

The amsiContext buffer is the crown jewel: it is passed as the first argument to every scan call, and both major PowerShell bypasses in this module either corrupt it or make its initialization fail.

11.5 Hooking with Frida

Frida is used as the observation tool before any bypass is attempted:

  • frida-trace -p <pid> -x amsi.dll -i Amsi* auto-generates JavaScript handlers for every exported Amsi* function in amsi.dll and traces calls live.
  • Against PowerShell, this confirms the exact API flow for each script block: AmsiInitialize once at startup, then AmsiOpenSession and AmsiScanBuffer per input, AmsiCloseSession afterwards.
  • The handler scripts can be edited to dump arguments — this is how the module captures the amsiContext pointer and the raw content being scanned, and how it observes the scan result value.
  • A simple obfuscation test (splitting the string "AmsiUtils" into two concatenated halves in a script) shows that Defender's signatures catch the content passed to AmsiScanBuffer — i.e. content-level signatures — while structure-level detection watches the API flow itself.

Exercise: hook a PowerShell process and log every AMSI call together with the scanned content and the returned result.

11.6 Bypassing AMSI With Reflection in PowerShell

PowerShell itself implements AMSI in the System.Management.Automation.AmsiUtils class. Via .NET reflection we can reach its private static fields from script:

  • The classic pattern (widely signature'd today, shown here for understanding): resolve AmsiUtils with [Ref].Assembly.GetType(...), walk GetField("amsiContext", NonPublic, Static) and related fields, and set amsiInitFailed = $true. When AmsiScanBuffer sees the "init failed" state, scanning is skipped and content is treated as clean.
  • Because this one-liner is heavily signature'd, the module immediately teaches the first evasion lesson: the string "amsiInitFailed" itself triggers Defender, so field names must be built dynamically (string concatenation / Join-String style construction) rather than appearing verbatim in the payload.

The narrative then asks the more interesting question: what actually lives inside amsiContext?

11.7 What Context Mom?

Using Frida to capture the first argument of AmsiScanBuffer (the context pointer) and WinDbg to dump that memory, the module reverse-engineers the AMSI_CONTEXT structure:

  • It begins with a header whose fields include a signature-like checksum area and a provider pointer; the layout is probed byte by byte in WinDbg.
  • Listing 36 (concept): overwrite the first bytes of the amsiContext header with garbage from PowerShell. The corrupted header makes subsequent AMSI validation fail, so scans are skipped — content executes as if no AV provider agreed on a verdict.
  • Doing this in WinDbg first (editing memory with ea/ed style commands) proves the concept; doing it from PowerShell via reflection ([Runtime.InteropServices.Marshal]::WriteByte... on the captured context pointer, or SetValue on the static field with a corrupted buffer) makes it scriptable.
  • Key insight recorded in the module: attacking the data structure rather than the code defeats signature-based detection of the bypass itself, because there is no characteristic byte pattern — only a memory write to an address we hold.

Note: this technique corrupts state; it works because each AmsiScanBuffer call validates the context header before consulting the provider, and a mangled header aborts that path.

11.8 Attacking Initialization

The cleanest variant: instead of corrupting the context, make AmsiUtils believe AMSI never initialized.

  • Reflection again: fetch the private static amsiInitFailed field on System.Management.Automation.AmsiUtils and set it to true (Listing 40 concept).
  • Result: PowerShell's internal checks see amsiInitFailed, AmsiScanBuffer is never invoked for subsequent script blocks, and everything runs unscanned.
  • This is the "attacking initialization" family of bypasses — small, fast, and DLL-free, but entirely dependent on .NET reflection being available (a reason constrained-language modes and AMSI-aware hardening can shut it down).

11.9 Wrecking AMSI in PowerShell / Understanding the Assembly Flow

To go beyond reflection (which may be blocked), the module opens amsi.dll itself in WinDbg:

  • Disassemble AmsiOpenSession: it validates the context (test rcx,rcx / null checks), compares the context's magic bytes (cmp dword ptr [rcx], 49534D41h — "AMSI" little-endian) and checks the session pointer before proceeding.
  • The plan: patch the very first instruction(s) of AmsiOpenSession so the function immediately returns success (xor rax,rax; ret style stub — the canonical stub shown in the course is the two-instruction "return 0" patch) without ever validating context or calling the provider.
  • Because .text pages of a loaded DLL are PAGE_EXECUTE_READ, the patch needs VirtualProtect (or VirtualProtectEx) to temporarily flip the page to writable (PAGE_EXECUTE_READWRITE), write the stub, and restore the original protection afterwards (Listing 51 concept) — the module verifies the restore with !vprot.

11.10 Patching the Internals

The PowerShell implementation of the patch, taught step by step:

  1. Resolve Win32 APIs dynamically (the course's LookupFunc/getDelegateType helpers): LoadLibraryA/GetProcAddress resolve kernel32!VirtualProtect; Marshal.GetDelegateForFunctionPointer builds a callable delegate so no suspicious P/Invoke declarations appear in the script. (The exact helper code is intentionally not reproduced verbatim here — Defender flags those listings; the structure is: LookupFunc returns a function pointer for (dll, function), getDelegateType emits a delegate type for a given parameter/return signature list.)
  2. Find the target address of amsi!AmsiOpenSession (via the module export or a hardcoded address captured in WinDbg during the exercise).
  3. VirtualProtect the page to PAGE_EXECUTE_READWRITE (0x40), saving the old protection.
  4. Write the stub — the first bytes of the function are replaced with the return-zero sequence (in the course: the byte array beginning 0xB8, 0x57 ... i.e. mov eax, 0x80070057; ret — E_FAIL — which makes AMSI callers treat the operation as failed and skip scanning).
  5. VirtualProtect again to restore PAGE_EXECUTE_READ using the saved value (Listing 51), then verify in WinDbg that u amsi!AmsiOpenSession now shows the stub and that a known-malicious script runs unflagged.

Trade-off discussed: memory patching is version-resilient only as long as the function prologue stays the same, and it leaves the patch in memory where a scanner reading that page could notice — but it works without reflection and from script hosts where reflection is unavailable.

Exercises/Extra Mile: automate address resolution from PowerShell (walk the module list), apply the same patch idea to AmsiScanBuffer, and test under PowerShell Constrained Language Mode.

11.11 Case Study: UAC Bypass vs Microsoft Defender (Fodhelper)

With working AMSI bypasses, the module builds a full attack chain against a fully patched Windows 10 with Defender enabled. Goal: go from a medium-integrity Meterpreter session to a high-integrity one.

  • Fodhelper internals: fodhelper.exe runs as high integrity and queries the registry key HKCU:\Software\Classes\ms-settings\shell\open\command (Listing 54), which does not exist by default. If we create that path and set its (Default) value to a command, fodhelper spawns it high integrity — a pure-registry UAC bypass that writes no files to disk.
  • Why the Metasploit module fails (Listing 56): exploit/windows/local/bypassuac_fodhelper stages its PowerShell through the registry; Defender's AMSI integration scans the PowerShell content launched by fodhelper and flags the Meterpreter stager — the exploit times out and a Defender alert appears in the Security Center.
  • Manual approach works (Listing 57): create the registry path, set (Default) to powershell.exe with a -windowstyle hidden download-cradle argument that first applies the AMSI bypass and then runs the shellcode runner; launch fodhelper. The PowerShell child is high integrity and unscanned.
  • Defender still catches the stage over the network (Figure 9): the unencrypted/unencoded Meterpreter second stage is detected by Defender monitoring the interface. Fix (Listing 58/59): set EnableStageEncoding true and set StageEncoder x64/zutto_dekiru (fallback x64/xor_dynamic). With the encoded stage, the Meterpreter session opens at High Mandatory Level (whoami /groups shows S-1-16-12288) — full chain succeeds.
  • Cleanup notes: remove the registry key and consider hiding the PowerShell window (-WindowStyle Hidden) in a real engagement.

Exercise: reproduce the whole chain with a custom payload instead of Meterpreter.

11.12 Bypassing AMSI in JScript

AMSI also scans JScript, which matters for DotNetToJscript payloads (the shellcode-runner technique from earlier modules). Two differences from PowerShell:

  • Detection flow: wscript.exe hosts the script; Frida (frida-trace -p <pid> -x amsi.dll -i Amsi* — Listing 61) shows the same AmsiInitialize → OpenSession → ScanBuffer flow, and a plain DotNetToJscript shellcode runner returns scan result 32768 (malware) — Listing 62. No reflection or Win32 access exists from JScript, so the PowerShell bypasses cannot be reused.
  • Sleep trick for instrumentation: since wscript exits immediately, the test script starts with WScript.Sleep(20000); to leave time to find the PID in Process Explorer and attach Frida.

11.13 Is That Your Registry Key?

A JScript-specific bypass, credited to @Tal_Liberman:

  • JScript checks the AmsiEnable registry value under HKCU\Software\Microsoft\Windows Script\Settings\ before initializing AMSI. If it is set to 0, AMSI is disabled for that script host.
  • Confirmed dynamically: in WinDbg, break on jscript!JAmsi::JAmsiIsEnabledByRegistry, which performs a RegQueryValueExW for the key (Listing 67 concept).
  • In JScript, WshShell.RegWrite("HKCU\\Software\\Microsoft\\Windows Script\\Settings\\AmsiEnable", 0, "REG_DWORD") before running the payload; re-hooking with Frida (Listing 68) shows zero calls to any Amsi* API and the shellcode runner executes fine.
  • Caveat: the check happens only when wscript.exe starts, so the key must exist before launch. The module's robust variant (Listing 69): in a try/catch, RegRead the key; if absent, throw — the catch block sets the key and relaunches the script with cscript -e:{F414C262-6AC0-11CF-B6D1-00AA00BBBB58} <script>, where the GUID forces the JScript engine (HKLM\SOFTWARE\Classes\CLSID entry for jscript.dll) and WScript.ScriptFullName passes the original file. Second launch finds the key and runs the payload.

Exercise/Extra Mile: recreate the bypass; generate an equivalent SharpShooter payload.

11.14 I Am My Own Executable

A loading-level bypass, credited to James Forshaw:

  • Idea: AMSI needs amsi.dll. If it can't load, AMSI fails and the host proceeds unscanned. Overwriting C:\Windows\System32\amsi.dll needs admin, but COleScript::Initialize (found in WinDbg, Listing 74) loads it with LoadLibraryExW("amsi.dll", ..., 0x800).
  • The flag 0x800 = LOAD_LIBRARY_SEARCH_SYSTEM32 forces the search straight to System32, defeating classic DLL hijacking in a writable directory.
  • Forshaw's trick: copy wscript.exe to a writable folder (e.g. C:\Windows\Tasks) renamed to AMSI.dll and execute it. When the process named "amsi.dll" later calls LoadLibraryExW("amsi.dll", ...), Windows sees a module of that name already loaded in the process and aborts the load for efficiency — every subsequent AMSI API call fails, disabling AMSI.
  • Execution detail: double-clicking a .dll fails because ShellExecute treats DLLs as libraries, but CreateProcess (used by WScript.Shell.Exec) ignores the extension and runs the PE — so a process named amsi.dll really does execute.
  • Listing 75 assembles the complete JScript: try { if the copied "AMSI.dll" exists → run the DotNetToJscript payload; } catch { CopyFile wscript.exe → C:\Windows\Tasks\AMSI.dll, Exec("C:\Windows\Tasks\AMSI.dll -e:{F414C262-...} " + WScript.ScriptFullName), WScript.Quit(1); }
  • Defender reacts (Figure 12): the shell opens (AMSI bypassed) but Defender flags a process named amsi.dll and kills it shortly after. Mitigations: migrate immediately to another process, or replace the plain shellcode runner with process injection/hollowing so the flagged process is disposable. Advantage: the technique works against every AMSI-capable AV vendor, some of which won't flag the process name at all.

Exercises: recreate the rename-and-execute bypass; re-implement it with process injection/hollowing for a shell that survives the detection.

11.15 Wrapping Up

The module's through-line: bypassing AMSI is not about one magic snippet but about choosing the right attack surface for the host you are in —

Host Techniques Anchor
PowerShell reflection (amsiInitFailed), context-header corruption, memory patching of AmsiOpenSession .NET / amsi.dll internals
JScript AmsiEnable=0 registry key + self-relaunch, wscript-renamed-to-amsi.dll host startup / DLL load path
Cross-host Frida/WinDbg recon of the AMSI API flow before choosing a bypass observation first, bypass second

And the case study shows the operational reality: even a successful AMSI bypass chain can still be caught at other layers (content signatures, unencoded network stages, process names), so each stage of the chain needs its own evasion decision.

Key Takeaways for Ops

  1. Recon before bypass: frida-trace -x amsi.dll -i Amsi* on the target host process tells you exactly where content is scanned and what the verdict values are.
  2. Reflection bypasses (set amsiInitFailed) are simplest but break under CLM; memory patching (VirtualProtect + stub over AmsiOpenSession/AmsiScanBuffer) works where reflection doesn't.
  3. Avoid signature'd one-liners: build field/function names dynamically; the bypass code itself is a detection target.
  4. Chain-level evasion: a UAC bypass via fodhelper registry keys pairs a download cradle (AMSI bypass + runner) with an encoded Meterpreter stage (EnableStageEncoding + StageEncoder x64/zutto_dekiru).
  5. JScript hosts: no reflection → attack startup (AmsiEnable=0 + cscript -e:{GUID} relaunch) or the loader (copy wscript.exe as AMSI.dll; CreateProcess ignores the extension).
  6. Expect collateral detections: a process named amsi.dll gets flagged by Defender — plan immediate process migration or injection-based runners.
