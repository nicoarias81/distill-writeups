Miles de agentes de IA expuestos: cómo la reconoce el agentic recon

Fuente: «Roey Ben Chaim - Total Recon: How We Discovered 1000s of Open Agents in the Wild | [un]prompted 2026» · ver el video original

Resumen

Los agentes de IA corporativos —Copilot Studio, Agent Builder y Custom GPTs de OpenAI, middlewares de LLM, runtimes y servidores MCP— son, ante todo, aplicaciones: tienen endpoints, APIs, breadcrumbs descubribles y a veces hasta un iframe que los enlaza desde otro sitio. Ese carácter de aplicación web los vuelve rastreables con técnicas clásicas de open source intelligence. El resultado del relevamiento es contundente: decenas de miles de agentes expuestos en la web, de los cuales miles no pedían autenticación, algunos con documentos sensibles a la vista o historias de negocio de alto impacto al alcance de cualquiera.

El riesgo central es que un agente es una puerta de entrada a la empresa: suele llevar credenciales embebidas, conectarse a fuentes de datos internas y, en algunos casos, puede modificar información dentro de la organización. La exposición, además, no depende de ninguna vulnerabilidad de día cero: se apoya en configuraciones por defecto, espacios de búsqueda pequeños y brechas conocidas de las plataformas (la inyección de prompts sigue siendo un problema sin solución real).

Este artículo recorre las técnicas de descubrimiento por plataforma, el impacto real de un agente público, y una herramienta open source para auditar la postura de los agentes propios.

Copilot Studio: del tenant ID al catálogo de agentes

Al crear un recurso en Copilot Studio, Microsoft genera un sitio web con el agente embebido en un chat, y detrás una URL compuesta por varios segmentos: algunos con entropía alta, otros bastante predecibles.

  • Environment: es el contenedor de recursos de la empresa dentro del tenant. Todo tenant tiene un environment por defecto, siempre con el prefijo default seguido del tenant ID. Ese tenant ID se obtiene con una API no documentada de Microsoft: dándole el dominio, devuelve el identificador (una técnica que AADInternals popularizó; su sitio web público hubo de desactivarse porque fue abusado).
  • Solution prefix: una cadena alfanumérica de cinco a ocho caracteres que aporta unicidad. Su entropía teórica es alta, pero la mayoría usa los valores por defecto: el prefijo CR más dos o tres caracteres alfanuméricos, un subespao de búsqueda lo bastante chico para fuzzear.
  • Nombre del agente: para encontrar un solution prefix hay que emparejarlo con un agente, y los nombres por defecto abundan: copilot1, copilot2, test, ai bot, y los clásicos de cualquier entorno: dev, prod, sandbox, integration, dashboard.
flowchart LR
    A[Dominio] -->|API no documentada| B[Tenant ID]
    B --> C[Environment default]
    C -->|fuzzing CR + 2-3 chars| D[Solution prefix]
    D -->|nombres por defecto| E[Agentes del environment]
    E -->|Power Platform API| F{¿Requiere auth?}

Con este encadenamiento se llegaron a encontrar decenas de miles de agentes. La Power Platform API además permite saber si el agente requiere autenticación, y la enumeración de subdominios amplía todavía más el listado.

Agent Builder, Custom GPT y el middleware expuesto

En Agent Builder de OpenAI la lógica es similar, con un matiz que agranda la superficie: el despliegue lo hace el desarrollador. OpenAI recomienda starter kits de GitHub con nombres bien conocidos; la mayoría se despliega en Vercel o Render; y a veces la URL hasta incluye el nombre de la rama. El espacio de direcciones se reduce a algo fuzzable. Verificar la existencia de un agente es tan simple como llamar a createSession, recibir el client secret y comprobar si se verificó. Algunos agentes hallados así contenían información confidencial que no debía estar ahí.

Los Custom GPTs juegan en otra categoría: por diseño, cualquiera puede ver sus capacidades —herramientas por defecto como Python, navegador o DALL·E, y conectores custom como "listar todos tus correos de Gmail". No es recon tradicional, pero le entrega al atacante un mapa detallado de qué sabe hacer cada agente.

El OSINT sobre infraestructura rinde de forma parecida:

  • Buscando en Shodan el session ID bien definido de MCP aparecen cientos de miles de servidores MCP abiertos, con o sin autenticación.
  • Un hash de HTML llevó a una API de Copilot abierta, con su swagger y un endpoint expuesto de purge vector DB.
  • Los registros (registries) de MCP exponen la URL del backend y el listado de herramientas en su JSON.
  • Los backlinks cierran el círculo: embeber un agente de Copilot Studio en un iframe crea un backlink, y buscar copilotstudio.microsoft.com con herramientas de backlinks arrojó 2.500 agentes abiertos, varios sin autenticación. Lo mismo con agentes de Amazon.

Los obstáculos técnicos fueron los de siempre: rate limiting, fingerprinting de navegadores headless y la reducción del espacio de búsqueda para los solution prefixes.

Del descubrimiento al impacto

Un agente público invita al sondeo: preguntar por su fuente de conocimiento (a veces basta con pedirlo), medir si tiene guardrails y enumerar sus herramientas. En los ejemplos mostrados, obtener el listado de tools solo requirió pedirlas y añadir algo de "carne" al prompt para confundir las activaciones de los guardrails. Nada es infalible, y por eso un agente no debería ser público salvo que sea intencional.

Técnicas y herramientas mencionadas

  • Agentic recon: descubrimiento de agentes de IA tratándolos como aplicaciones web con endpoints y breadcrumbs.
  • AADInternals / API de tenant ID: resolución de dominio a tenant ID mediante una API no documentada de Microsoft.
  • Fuzzing de solution prefixes: ataque a la configuración por defecto (CR + 2-3 caracteres) de Copilot Studio.
  • Power Platform API: verificación de si un agente requiere autenticación.
  • createSession / client secret: sonda de existencia de agentes en OpenAI Agent Builder.
  • Shodan: búsqueda de servidores MCP abiertos por session ID.
  • Backlink search: localización de agentes embebidos en iframes vía dominios de plataforma.
  • MCP registries: catálogos que exponen backend URL y listado de herramientas.
  • Power Pawn: herramienta open source (con módulos Copilot Studio Hunter, Agent Builder Hunter, Custom GPT Hunter y LLM Hound) para evaluar la postura pública de los agentes de una organización.

Conclusiones

  • Ninguna de las técnicas requiere un zero-day: bastan configuraciones por defecto, nombres predecibles y espacios de búsqueda chicos.
  • No publicar agentes salvo necesidad, y huir de las configuraciones por defecto: la entropía alta reduce la enumeración.
  • Auditar la propia superficie con herramientas open source y cerrar los endpoints públicos que no deberían existir.
  • Sumar observabilidad a los sistemas de IA: "no sabés lo que no sabés" aplica con especial fuerza a los agentes conectados a datos corporativos.
