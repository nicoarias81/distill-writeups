Skills y AGENTS.md: la arquitectura de contexto que hace productivos a los agentes

Fuente: «The Skills System That Changed How I Work with AI (Complete Course)» · ver el video original

Resumen

Trabajar con agentes de IA sobre una codebase real choca rápido con un problema físico: la ventana de contexto. Un agente que tiene que leer todo el proyecto para responder cualquier pregunta consume tokens, tarda y, sobre todo, alucina más cuanto más tiene que procesar. La arquitectura que se describe aquí ataca ese problema en tres capas: un archivo AGENTS.md como contrato cultural del proyecto, skills como módulos de contexto que se cargan bajo demanda, y subagentes con contextos independientes que devuelven resúmenes al orquestador.

Lo interesante es que no se trata de una teoría: la arquitectura está aplicada en Prowler, un proyecto open source de ciberseguridad cloud, donde sirve para que contribuyentes humanos y agentes trabajen siguiendo las mismas convenciones. El resultado práctico es que un agente puede implementar una feature respetando los patrones del proyecto sin que nadie le pegue un documento enorme en cada sesión.

AGENTS.md: el README para máquinas

El AGENTS.md es un archivo Markdown que leen los agentes para entender el contexto de un proyecto: qué es, dónde está cada cosa, cómo se trabaja, dónde van los archivos, qué tecnologías se usan. Es la "parte cultural" del proyecto puesta por escrito. La analogía directa: el README de toda la vida es para humanos; el AGENTS.md es para el agente.

El flujo básico es simple. El usuario pide algo al agente (el LLM), el agente consulta el AGENTS.md para saber cómo trabajar con esa codebase, y con esa información va al código de forma mucho más dirigida que si tuviera que descubrir todo por sí mismo.

flowchart LR
    U[Usuario] --> A[Agente]
    A -- "consulta: cómo trabajar aquí" --> AG["AGENTS.md"]
    A -- "trabaja dirigido" --> C[Codebase]
    AG -.-> A
    A --> U

Una recomendación central de las guías publicadas (por ejemplo en agents.md) es que el archivo sea acotado. La intuición de que "más contexto = mejor agente" es falsa: demasiado contexto implica demasiado que procesar y más probabilidades de alucinar. La referencia práctica es alrededor de 250 líneas, con 500 como máximo.

Dividir el contexto: múltiples AGENTS.md y un router

Cuando la codebase no entra en 500 líneas de documentación, la solución no es un archivo gigante sino varios AGENTS.md sectorizados por feature: uno para UI, otro para API, otro para autenticación, cada uno dentro de su carpeta en el monorepo. Cada uno documenta las particularidades de esa parte de la aplicación.

Esto crea un problema de enrutamiento: si el agente corre en la raíz de un monorepo con frontend y backend, ¿cómo sabe a qué archivo ir? La respuesta es un AGENTS.md raíz que actúa como router: el usuario pregunta algo de UI, el agente consulta el archivo raíz, y este lo dirige a la carpeta correspondiente. De esta manera el agente recibe solo el contexto que necesita en cada momento.

Skills: contexto bajo demanda

Los AGENTS.md sectorizados siguen creciendo. En cuanto aparecen temas muy específicos (cómo trabajar con React, con TypeScript, con Django, cómo hacer commits, cómo abrir pull requests), el siguiente paso son las skills: unidades de contexto que se cargan solo cuando se necesitan.

Una skill agrupa flujos de trabajo, formatos y convenciones culturales, y también tareas repetitivas. Ejemplo concreto: un proyecto que publica releases en su repositorio de dotfiles y además en Homebrew tiene una skill que conoce todos los pasos (buscar el hash, generar lo necesario, publicar en ambos lados) y la ejecuta de punta a punta.

Los agentes modernos detectan skills automáticamente cuando están en una carpeta skills de su directorio de configuración, pero en la práctica los modelos suelen tratar esa detección como una sugerencia y la ignoran. Por eso la regla operativa es doble:

  1. En el AGENTS.md raíz y en cada uno sectorizado, listar explícitamente las skills disponibles y cuándo se triggerea cada una.
  2. Cada skill declara un scope (UI, API, root...) que indica dónde aplica: una skill de React pertenece a UI, las de commits o pull requests son genéricas y van al root.

Anatomía de una skill

Una skill es una carpeta dentro de skills/ con un archivo de definición. Las primeras líneas son metadata: nombre, descripción con el trigger (por ejemplo, "cuando trabajes con Next.js, routing, server actions o data fetching"), licencia, autor, versión, scope y una sección de auto-invocación. También declara qué herramientas puede usar el agente cuando la ejecuta: lectura, escritura, edición, bash, glob, grep, búsqueda en internet. Esto permite restringir: una skill de documentación interna puede limitarse a leer y escribir; una que necesita documentación técnica externa puede buscar en la web.

Para skills complejas hay una pieza adicional: recursos. Una skill de compliance, por ejemplo, incluye templates con ejemplos completos de lo que hay que producir y referencias a la documentación oficial interna. El patrón es el que mejores resultados da con IA: instrucción detallada más ejemplos concretos maximiza la probabilidad de acierto en un solo intento.

Subagentes y el orquestador

La tercera capa son los subagentes. Antes se usaban como una variante de las skills —mini-agentes con un conjunto fijo de habilidades—, pero su rol real es la delegación: el agente principal pasa a ser un orquestador que reparte trabajo entre N subagentes.

contexto propio] --> S1[Subagente 1
contexto propio]
    O --> S2[Subagente 2
contexto propio]
    O --> S3[Subagente N...]
    S1 -- "resumen" --> O
    S2 -- "resumen" --> O
    S3 -- "resumen" --> O

La clave es que cada subagente tiene su propio contexto independiente. Cuando termina, al orquestador solo le devuelve un resumen de lo que hizo: todo el proceso interno (archivos leídos, herramientas usadas, iteraciones) no entra al contexto principal. Editar 500 archivos, por ejemplo, se resuelve generando subagentes en vez de que el orquestador vaya uno por uno o escriba un script. Sumado a skills bien organizadas, el costo de contexto del orquestador apenas crece.

El caso real: Prowler

Prowler, proyecto open source de ciberseguridad en cloud, aplica todo lo anterior. Su AGENTS.md raíz incluye un project overview, guías para trabajar con Python, guidelines de commits y pull requests, la lista de skills genéricas (TypeScript, React, Node.js, Tailwind, Playwright, PyTest) y skills específicas del proyecto (UI de Prowler, API de Prowler). En un proyecto open source esto tiene un valor extra: los contribuyentes nuevos —humanos o agentes— pueden aportar de una manera culturalmente controlada, siguiendo las convenciones existentes desde el primer commit.

La compatibilidad entre agentes se resuelve con scripts: como no todos leen AGENTS.md (Claude Code, por ejemplo, espera CLAUDE.md), un setup.sh instala las skills en el formato que espera cada agente (Claude Code, Gemini CLI, Codex, GitHub Copilot) y genera los archivos equivalentes. En vez de copiar la carpeta de skills veinte veces, se usan symlinks a una única fuente.

El mantenimiento de esa multiplicidad se resuelve, como no podía ser de otra manera, con dos skills: un skill-creator con un template para crear skills nuevas, y un skill-sync que después de cada creación actualiza todos los AGENTS.md y archivos derivados. Un script de sincronización usa el campo scope de cada skill para colocarla en el archivo correcto (UI, API, SDK o root).

En el flujo diario, el agente consulta qué skills hay disponibles, y al pedirle "creá un botón en la carpeta UI para lanzar un scan" él solo carga la skill de UI de Prowler, explora la estructura, delega la exploración a un subagente, recibe un resumen con los componentes y patrones existentes, y recién ahí propone la implementación. Un detalle de diseño importante: el agente está configurado para preguntar antes de programar (¿el botón importa un finding, lo crea manual, dispara un scan?), de modo que la IA guía en vez de producir código a ciegas.

Técnicas y herramientas mencionadas

  • AGENTS.md: archivo Markdown con el contexto cultural del proyecto, leído por los agentes; recomendación de ~250-500 líneas máximo.
  • AGENTS.md raíz como router: archivo que dirige al agente hacia el AGENTS.md sectorizado correcto en monorepos.
  • Skills: carpetas con metadata (nombre, trigger, scope, auto-invocación, herramientas permitidas) que cargan contexto solo cuando se necesita.
  • Scope de skill: campo que indica en qué parte del proyecto aplica una skill (UI, API, root).
  • Recursos de skill: templates con ejemplos y referencias documentales incluidos dentro de la skill.
  • Subagentes: agentes con contexto independiente que devuelven un resumen al orquestador, ahorrando contexto principal.
  • Orquestador: agente principal que delega tareas en subagentes en vez de ejecutarlas.
  • setup.sh / symlinks: instalación multiagente de skills (Claude Code, Gemini CLI, Codex, GitHub Copilot) sin duplicar carpetas.
  • skill-creator y skill-sync: skills para crear skills nuevas y sincronizarlas automáticamente en todos los archivos de contexto.
  • Prowler: proyecto open source de ciberseguridad cloud donde está aplicada la arquitectura completa.
  • OpenCode: agente CLI usado para el flujo de demostración con delegación visible a subagentes.

Conclusiones

  • El cuello de botella del trabajo con agentes es el contexto: más contexto no es mejor, es más alucinación. La arquitectura correcta entrega el mínimo necesario en cada momento.
  • La jerarquía AGENTS.md (raíz + por feature) + skills con scope + subagentes con contextos independientes forma un sistema coherente donde cada capa reduce la carga del orquestador.
  • La detección automática de skills es en la práctica una sugerencia que los modelos ignoran; listar skills y triggers explícitamente en los AGENTS.md es lo que hace que el sistema funcione.
  • Todo lo que es repetitivo (crear skills, sincronizarlas entre agentes, hacer releases) debería ser a su vez una skill: el sistema se mantiene a sí mismo.
  • Esta estructura convierte las convenciones del proyecto en contrato ejecutable, lo cual es especialmente valioso en equipos open source con contribuyentes nuevos.
