Windows Downdate: resucitar vulnerabilidades parcheadas con actualizaciones maliciosas

Fuente: «DEF CON 32 - Windows Downdate: Downgrade Attacks Using Windows Updates - Alon Leviev» · ver el video original

Resumen

Un ataque de downgrade consiste en revertir software plenamente actualizado a una versión antigua y vulnerable, para luego explotar vulnerabilidades que se creían muertas. El precedente más famoso es BlackLotus: el bootkit UEFI no explotó un 0-day contra Secure Boot, sino que degradó el Windows Boot Manager a una versión firmada pero vulnerable, y sobre ella explotó una vulnerabilidad ya conocida y parcheada.

Ese precedente abre una pregunta incómoda: si Secure Boot era vulnerable a degradaciones, ¿qué otros componentes de Windows también lo son? La investigación detrás de Windows Downdate demuestra que prácticamente todo el stack de virtualización de Windows —desde drivers del kernel hasta el hipervisor, pasando por Credential Guard y el secure kernel— carece de mecanismos de detección o revocación de downgrades. El resultado es una herramienta capaz de degradar componentes de un sistema totalmente parcheado de forma indetectable, invisible, persistente e irreversible, resucitando miles de vulnerabilidades ya corregidas y haciendo que el término "fully patched" pierda sentido en cualquier máquina Windows.

Microsoft emitió los CVE-2024-21302 y CVE-2024-38202 en respuesta a la investigación.

Los requisitos del downgrade perfecto

Un downgrade utilizable en la práctica debe cumplir cuatro propiedades:

  1. Indetectable: los EDR no deben bloquear la operación; la vía más fiable es usar el proceso de actualización legítimo de Windows.
  2. Invisible: el sistema debe seguir apareciendo como actualizado, aunque los componentes estén degradados.
  3. Persistente: las futuras actualizaciones no deben sobrescribir el downgrade.
  4. Irreversible: las herramientas de integridad y reparación no deben detectar ni reparar la corrupción.

El objetivo no eran drivers de terceros al estilo BYOVD (bring your own vulnerable driver), sino entidades de primera parte, incluso por debajo del kernel: un "bring your own vulnerable Windows".

Secuestro del proceso de Windows Update

La arquitectura de Windows Update tiene un cliente y un servidor que se comunican vía COM. El cliente exige privilegios de administrador; el servidor opera como TrustedInstaller, y los archivos del sistema actualizados por Windows Update solo son accesibles a TrustedInstaller. El primer fallo de diseño: la elevación administrador→TrustedInstaller no es un límite de seguridad y existen PoCs públicos, de modo que esa protección es ineficaz. Pero elevarse así es detectado como malicioso por los EDR, lo que contradice el principio de indetectabilidad; la solución fue encontrar un fallo en el propio proceso de actualización:

  1. El cliente pide al servidor actualizar, proporcionando la carpeta de la actualización.
  2. El servidor valida la integridad de esa carpeta.
  3. El servidor genera los archivos finales en una carpeta bajo su control, inaccesible para el cliente.
  4. El servidor escribe la lista de acciones (pending.xml) en otra carpeta controlada por él.
  5. En el reinicio, el sistema ejecuta las acciones de la lista.

El punto débil es el estado de esa lista de acciones. La clave de registro PoqExecCmdLine —que contiene el ejecutable que procesa la lista y su ruta— no está protegida por TrustedInstaller. Controlando esa clave se controla toda la lista de acciones: un XML con operaciones de crear/borrar/mover/hardlink de archivos y crear/borrar claves de registro. Usando la acción de hardlink, el origen reemplaza al destino: archivos actuales pueden sustituirse por versiones vulnerables.

El identificador de integridad de la lista tampoco frena el ataque, porque tanto el identificador del registro como el de la lista son controlables por el atacante. Con TrustedInstaller en auto-start y la lista apuntando a las acciones de downgrade, Windows Update ejecuta el ataque por sí solo: todas las verificaciones de integridad se saltan porque la lista se asume verificada (se crea después de la verificación), sin necesidad de elevación maliciosa detectable.

Las cuatro propiedades se cumplen:

  • Invisibilidad: el sistema fue "actualizado", no desactualizado; se muestra al día.
  • Persistencia: el suscriptor de la lista de acciones no está firmado digitalmente; parcheándolo, las futuras actualizaciones se instalan vacías y el downgrade sobrevive.
  • Irreversibilidad: la utilidad de integridad y reparación (sfcreplace/dism de reparación) tampoco está firmada; parcheada, deja de detectar corrupciones.

La demostración sobre un sistema totalmente actualizado degrada el driver afd.sys a una versión vulnerable y, tras el reinicio, explota la vulnerabilidad para obtener ejecución de código en kernel (NT AUTHORITY\SYSTEM), con Windows Update reportando el equipo como completamente actualizado.

De admin a kernel: el valor de degradar el kernel

Administrador→kernel no es un límite de seguridad en Windows, pero sigue siendo una amenaza seria: muchos usuarios corren como administrador (y es el valor por defecto), lo que les expone a compromisos de kernel con toda la funcionalidad adicional que eso da. La respuesta de Microsoft fue desprivilegiar el kernel con Virtualization Based Security (VBS): un entorno virtual aislado por el hipervisor donde viven las funciones críticas —Credential Guard, HVCI, System Guard Secure Launch, VMs blindadas— y las claves, bajo el supuesto de que el kernel ya está comprometido.

Bypass del UEFI lock y neutralización de VBS

VBS se protege de su desactivación con el UEFI lock: la configuración de VBS vive en una variable UEFI de boot services, fuente de verdad por encima del registro, inaccesible en runtime. Desactivar VBS con lock requiere cargar una aplicación EFI firmada por Microsoft que pide aprobación física al usuario durante el arranque. El supuesto: solo corre código firmado (Secure Boot) y el único código firmado que toca la configuración exige acceso físico.

La sorpresa: si el cargador del sistema operativo falla al validar cualquiera de los archivos de VBS (secure kernel, hipervisor), arranca normalmente abandonando VBS, en lugar de caer al entorno de recuperación. Reemplazar cualquier archivo de VBS por uno inválido desactiva VBS saltándose el UEFI lock. Es un bypass trivial y, según la investigación, el primero publicado contra los UEFI locks de VBS.

Demostración conjunta: Credential Guard, PPL y Defender

Con todas las piezas encadenadas, sobre un sistema con la configuración más restrictiva (PPL para LSASS, UEFI locks protegiendo LSASS y los secretos de VTL1, Credential Guard activo, Defender operativo) el ataque:

  1. Revierte el parche de PPLFetch para permitir el bypass de PPL.
  2. Desactiva Credential Guard saltándose los UEFI locks.
  3. Invalida el ejecutable principal de Defender (MsMpEng) para desactivarlo.

Credential Guard y PPL para LSASS son complementarios: sin saltarse ambos, las credenciales no se pueden volcar (si solo se salta PPL, los secretos siguen cifrados). Tras el downgrade y reinicio, el secure kernel deja de correr, Credential Guard desaparece, Defender no detecta muestras maliciosas y PPLFetch culmina con un volcado de LSASS del que Mimikatz extrae credenciales que deberían estar protegidas. Windows Update sigue reportando el equipo al día.

Downgrades a través de los límites de seguridad de VBS

VBS define los límites de seguridad reales de Windows: cualquier transición VTL0→VTL1 y cualquier salto ring 3/ring 0→ring -1 (hipervisor) es una elevación de privilegio. Comprometer el hipervisor da control de todos los VTLs. La metodología: si un componente no tiene detección ni revocación de downgrades, su degradación es una vulnerabilidad en sí misma, porque facilitará la explotación de futuros parches. Resultados, todos sin detección de downgrade:

Componente CVE usado Salto de privilegio
Credential Guard (LSAISO, VTL1) CVE-2022-34709 ring 3 VTL0 → ring 3 VTL1
Secure Kernel CVE-2021-27090 ring 3 VTL0 → ring 0 VTL1 (compromete HVCI, HyperGuard)
Hipervisor (hvax/hvix) downgrade de 2 años ring 3 VTL0 → ring -1 (stack de virtualización completo)

Para el secure kernel hizo falta degradar también módulos dependientes, no solo el kernel. Para el hipervisor, las descripciones de CVE de Microsoft no precisan qué componente del stack es el vulnerable, así que se retrocedió dos años para garantizar al menos una elevación sin parchear en el binario antiguo. La conclusión: todo el stack de virtualización es vulnerable a downgrades; en la demo, el hipervisor pasa de la versión 2.2.6.1 a una de hace dos años con VBS aparentemente funcionando con normalidad.

Windows.old: el vector sin privilegios

Tras una actualización de calidad, Windows guarda el sistema anterior en C:\Windows.old para restauración. Los archivos heredan las ACL del sistema viejo (no se pueden manipular directamente), pero la carpeta Windows.old en sí es totalmente accesible para usuarios sin privilegios. La estrategia: renombrar la carpeta original y crear una Windows.old controlada por el atacante; si un administrador dispara una restauración, el sistema atacante sustituye al legítimo. Así, los mismos downgrades pueden ejecutarse desde un usuario sin privilegios.

Técnicas y herramientas mencionadas

  • BlackLotus: bootkit UEFI que bypaseó Secure Boot mediante downgrade del boot manager (origen de la investigación).
  • Windows Downdate: herramienta que automatiza los downgrades vía toma de control de Windows Update.
  • Secuestro de PoqExecCmdLine: clave de registro sin protección TrustedInstaller que controla pending.xml y todas las acciones de actualización.
  • Hardlink en pending.xml: acción de la lista de actualización usada para reemplazar archivos actuales por versiones vulnerables.
  • Bypass de UEFI lock: reemplazo de archivos de VBS por inválidos hace que el OS loader arranque sin VBS.
  • VBS/VTLs, Credential Guard, HVCI, HyperGuard, Secure Kernel, hipervisor (hvax/hvix): componentes del stack de virtualización, todos degradables.
  • PPLFetch / Mimikatz / System Informer / msinfo32: utilidades usadas en las demostraciones de volcado y verificación de estado.
  • CVE-2024-21302 y CVE-2024-38202: asignados por Microsoft a las vulnerabilidades de downgrade.

Conclusiones

  • La industria debe elevar su conciencia sobre los ataques de downgrade de SO: no se encontró mitigación alguna que impidiera degradar componentes críticos, lo que sugiere que esta superficie no fue un foco de diseño.
  • El diseño siempre es superficie de ataque: el downgrade del stack de virtualización es posible por un fallo conceptual —VTLs/anillos menos privilegiados pueden actualizar componentes más privilegiados— presente desde el anuncio de VBS en 2015, señal de que el diseño no fue examinado a fondo.
  • Estudiar ataques in-the-wild y expandirlos es valioso: BlackLotus ya empleaba downgrades contra Secure Boot; esta investigación extendió el concepto a todo el stack antes de que lo hicieran los atacantes reales, algo no siempre garantizado.
  • Quedan preguntas abiertas: ¿hay más funcionalidades de Windows vulnerables? ¿La implementación de VBS de Linux hereda estos fallos de diseño? ¿macOS y Linux son el siguiente objetivo? Conviene responderlas antes de que lo hagan los atacantes.
