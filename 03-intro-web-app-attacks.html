PEN-200 ITWAA — Introduction to Web Application Attacks

Distilled from OffSec PEN-200 (OSCP) course material (modules 18–25, Introduction to Web Application Attacks block) — internal training reference, not for redistribution.

Objective

Establish the full front-end web application attack workflow that later OSCP blocks build on: fingerprint the web server, map the application's public surface, stand up an intercepting-proxy testing rig, enumerate the application through browser dev tools / headers / sitemaps / API endpoints, and turn two concrete findings — a broken registration API and a stored XSS in a WordPress plugin — into full application compromise (admin account takeover via API privilege escalation, and admin-level actions via XSS-with-nonce-retrieval).

The block's arc, in the course's own order:

  1. Fingerprint the web server (Nmap + NSE).
  2. Brute-force the directory tree (GoBuster dir mode).
  3. Build the Burp Suite rig (Proxy → Repeater → Intruder) and prove it with a WordPress password brute force.
  4. Map the application content (Firefox Debugger/Inspector, HTTP response headers, robots.txt/sitemaps).
  5. Enumerate and abuse REST APIs (method probing, mass-assignment registration, JWT, admin password override).
  6. Stored XSS via an attacker-controlled HTTP header (the "Visitors" WordPress plugin).
  7. Privilege escalation through XSS (nonce retrieval + silent admin account creation — cookies are HttpOnly, so theft is out).

Target surface

The course lab in this block is the OffSecWP WordPress instance (megacorp1.com in the course materials, statically mapped in the local hosts file to the lab IP — no lab IP is stated in the video narration; use the IP assigned by your lab gateway). Attack box is stock Kali.

Notable attack-surface facts established across the videos:

  • Web server: Apache on Ubuntu. The narration reads the version as "2.4.4.1" — almost certainly Apache 2.4.41 (ASR artifact; verify against the actual banner in your lab).
  • GoBuster's initial dir sweep finds 10 resources, 4 of which return privilege/access errors — those "insufficient privileges" paths are exactly where later enumeration effort belongs.
  • WordPress runs the "Visitors" plugin: it logs each request's IP, source, and User-Agent into the WordPress database, then renders the stored values without sanitization in the plugin's admin dashboard (start.php builds the <td> tags; database.php handles header parsing on the write side). A classic stored-XSS sink: attacker-controlled header → DB → admin's browser.
  • WordPress session cookies (inspected in the Storage tab of dev tools): four real session cookies, all HttpOnly (plus the negligible WordPress test cookie). Consequence: cookie/session theft via document.cookie is not viable — the escalation must use the nonce-based admin-action route instead.
  • A second lab application exposes a REST API (/users, /users/<name>, /users/<name>/password, /login, /register) used for the API takeover exercise.

Techniques

The video narration describes workflows rather than command lines; commands below are normalized/reconstructed from the described actions. Items marked ⚠ are ASR ambiguities to re-verify in the lab.

1. Web server fingerprinting with Nmap

Start enumeration at the server layer, since every web app shares it. With port 80 known open, run the service scan for a banner grab:

nmap -sV -p 80 <target>
# → Apache 2.4.4.1 ⚠ (likely 2.4.41) on Ubuntu

Then layer on the service-specific NSE script http-enum for an initial content fingerprint — it discovers several interesting folders that feed the next stage (directory brute forcing).

2. Directory brute forcing with GoBuster

Map all publicly accessible files and directories before touching app logic:

gobuster dir -u http://<target>/ -w <wordlist>
# default 10 threads; lower with -t to reduce traffic on fragile targets

Result: 10 resources, 4 returning insufficient-privileges responses, 6 accessible and worth investigating. GoBuster also has fuzzing and DNS modes, but dir is the workhorse here.

3. Burp Suite rig: Proxy, Repeater, Intruder

Launch Burp Community from the Kali menu (Temporary Project → Burp Defaults). The "not tested on this Java runtime" warning is safe to ignore — Kali ships and tests Burp against the OS Java version.

  • Proxy: listener on localhost:8080. Point Firefox at it (Network Settings → Manual proxy; enable "also use this proxy for HTTPS" so all traffic is intercepted). Disable Intercept for passive work; browse megacorp1.com and review everything in Proxy → HTTP history (request left pane, response right pane). The point of the proxy: submit arbitrary input the UI would never allow — e.g. a 30-character value into a field the client caps at 20.
  • Repeater: right-click any request → Send to Repeater, edit and resend, review raw headers + unrendered body on the right.
  • Intruder (password brute force demo): add the target host to /etc/hosts first. Log in with admin / a dummy password, send the POST to Intruder. Clear all positions, then Add § around the password value only (username admin is known-correct). In Payloads, load the first 10 entries of rockyou.txt. Start attack; watch for the status-code outlier (one request replies differently from the rest) — that's the hit. Confirm by logging into the WordPress admin console with admin / [REDACTED — brute-forced from the wordlist].

4. Debugging page content (browser dev tools)

  • URL inspection: file extensions hint at the backend language (.php is obvious; framework-specific ones are cryptic). Routes make extensions increasingly rare — absence of an extension tells you routing logic decides the response.
  • Firefox Debugger (Web Developer menu): reveals JS frameworks, hidden input fields, comments, and client-side controls. OffSecWP uses jQuery, minified — click Pretty Print Source ({ } button) to read it.
  • Inspector: right-click an element → Inspect to jump to its HTML. Fastest way to find hidden form fields in the source (demonstrated on the WordPress search input).

5. HTTP response headers and sitemaps

Two equivalent inspection paths: Burp (full proxy view) or the browser's Network tool (launch it, refresh the page — it only captures post-launch traffic — then click a request and read its response headers).

  • The Server header names the web server software and, in default configs, the version; other header names/values leak stack details.
  • robots.txt (fetch with curl): Allow/Disallow directives tell polite crawlers what not to index — i.e. sensitive pages and admin consoles, exactly what we want. Entries may be stale or even invalid, but sitemaps can reveal site layout and unexplored portions of the target.

6. Enumerating and abusing APIs (admin takeover)

Closed-source apps ship APIs that expose backend logic; enumerate them like any other path. API names are usually descriptive + version number, which makes GoBuster's pattern mode (-p, pattern file using the {GOBUSTER} placeholder) ideal:

# pattern file: one line per version, e.g. /api/{GOBUSTER}/v1  (two versions tried in the course)
gobuster dir -u http://<target>/ -w <wordlist> -p <patterns-file>
# → discovers two API endpoint entries

Escalation sequence against the discovered API:

curl http://<target>/users            # → 3 user accounts, incl. an admin account
# extend path with the admin username; probe /password via GET
curl http://<target>/users/admin/password
# → 405 Method Not Allowed  ⇒ the route EXISTS, the method is wrong — try POST/PUT

Key inference from status codes: 405 ≠ 404. A 405 confirms the endpoint exists while rejecting the method; even a 404 with a JSON body saying "user not found" confirms the API itself is live. Switch methods and payload formats accordingly.

  1. Verify the login contract: POST {"username":"admin","password":"dummy"} with -H "Content-Type: application/json" → "authentication failed" = correctly formed parameters.
  2. Mass assignment at registration: POST to /register with username/password → told to include an email; comply, then smuggle in "admin": true as an extra key. No error — a new user is registered with admin privileges, which should not be permitted by design.
  3. JWT: log in as the new user → receive a JWT bearer token.
  4. Change the real admin's password: POST to the password API with Authorization: <JWT> → "incorrect method". PUT/PATCH replace rather than create — retry as PUT → no error.
  5. Prove it: log in as admin with the new password. Full admin takeover from an unauthenticated position, caused by a logical privilege-escalation bug (mass assignment) in the registration API.

Scaling the manual flow: replay any curl through Burp with curl ... --proxy http://localhost:8080, rebuild the request in Repeater to confirm identical behavior, and accumulate everything in Target → Sitemap for later re-testing (forward saved requests to Repeater/Intruder).

7. Basic stored XSS via the User-Agent header

The Visitors plugin stores the User-Agent from each request and renders it raw into a <td> tag in the admin dashboard — no sanitization on the write side (database.php) or the render side (start.php).

# With Burp as proxy, intercept disabled: browse OffSecWP, send the request to Repeater,
# replace the User-Agent value with:
User-Agent: <script>alert(1)</script>
# → 200 OK ⇒ payload stored in the WordPress DB

Log in to the admin console, open the Visitors plugin dashboard → the alert popup fires. The payload executes for any administrator who loads the plugin, persisted server-side. alert() is the standard proof-of-impact; the real payload follows next.

8. Privilege escalation via XSS (nonce-aware admin creation)

Goal: from stored JS execution to an administrative account. Cookie theft is the obvious first idea but is blocked here: dev tools → Storage → Cookies shows all four meaningful WordPress session cookies are HttpOnly (and Secure where applicable), so JavaScript cannot read them. (Secure = HTTPS-only transport; HttpOnly = no JS access. Neither flag stops the admin's browser from executing our script, which is the lever we use instead.)

WordPress blocks plain CSRF with nonces — server-generated pseudo-random tokens included per request, which an attacker can't pre-know. But the stored XSS runs inside the victim admin's authenticated session, so it can simply fetch the nonce itself:

  1. Nonce harvester: JS function requests the new-user page (/wp-admin/user-new.php) and regex-extracts the nonce from the response.
  2. User creator: second function issues the add-user request with the harvested nonce appended, silently creating a backdoored admin account the moment the real admin loads the plugin dashboard.
  3. Payload hygiene for transport: minify the JS to a one-liner (course uses JSCompress), then encode it — convert every character to its UTF-16 integer code (charCodeAt-style encoding) so no bad characters survive the header/curl/Burp round-trip. At execution time the victim's browser decodes via String.fromCharCode(...) and runs it with eval.
  4. Delivery: curl a request to OffSecWP with the encoded payload in the User-Agent header (-A), routed through Burp with Intercept on to eyeball the request before forwarding, then off. The dashboard shows an entry with an empty rendered User-Agent — expected, since the browser can't render a <script> tag as text.
  5. Verification: log in as admin, open the Visitors dashboard (payload executes), then click Users → the new admin account exists. Privileges elevated from external unauthenticated attacker to WordPress administrator. The course's stated next step is host-level compromise via a custom WordPress plugin with an embedded web shell (covered in a later block).

Detection & defense

Takeaways the course's own attack chain implies (the ITWAA block is tool-focused; these are the defensive readings of each technique):

  • Version and stack disclosure (Nmap banner, Server header, robots/sitemaps): minimize server tokens (ServerTokens Prod), and remember Disallow directives advertise sensitive paths — protect them with auth, not obscurity.
  • Directory/API brute forcing: rate-limit and alert on 404-scanning patterns; GoBuster traffic at default 10 threads is visible in access logs.
  • Client-side input limits are not validation. Anything the proxy rewrites (field lengths, parameter names, added headers, extra JSON keys) reaches the server raw — all authorization and validation must be server-side.
  • Mass assignment (the "admin": true registration bug): allow-list bindable request fields per endpoint; never bind client input directly onto user/role models. This single flaw granted full admin takeover.
  • HTTP method discipline: 405 responses confirm endpoint existence; enforce intended methods and return generic errors. Don't expose password-modification endpoints behind permissive method handling.
  • Stored XSS in header-derived fields: every attacker-controlled input — including HTTP headers — must be output-encoded at render time. The Visitors plugin failed on both write and render sides.
  • HttpOnly/Secure flags: correct and worth setting (they killed the cookie-theft route), but they are defense-in-depth only — a stored XSS in an authenticated page still performs any action the victim can, nonce included. Real fix: sanitize/encode inputs, add CSP, and require re-authentication or step-up checks for sensitive actions like user creation.
  • Nonce design caveat: nonces defeat off-site forgery, not same-origin script execution. Anything that can run JS in your origin can read your nonces.
