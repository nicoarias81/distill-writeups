Dredge: respuesta a incidentes en la nube sin SIEM, sin presupuesto y sin depender de la memoria de nadie

Fuente: «Dredge: A Open Source Framework for Cloud Incident Response - Santiago Abastante» · ver el video original

Resumen

El modelo ideal de respuesta a incidentes es el diagrama de preparación: logs centralizados, detecciones afinadas y un equipo listo para responder. La realidad, cada vez que llega el incidente de verdad, es otra: los casos de uso de detección disparan falsos positivos, y el incidente real ocurre justo donde no había monitoreo. En entornos cloud esto se agrava: organizaciones que soñaron on-premise tienen recursos en la nube y asumen que por definición es seguro, así que concentran el monitoreo en las workstations mientras un atacante lleva meses dentro sin que nadie lo visualice.

Dredge es un framework open source de incident response en la nube que nació de esa fricción: una carpeta de scripts desarrollados durante años liderando respuesta a incidentes en consultoría, que un amigo resumió con "esto lo tenés que compilar en algo, porque está re bueno pero es imposible de usar". No hay IA ni machine learning: son cuatro o cinco API calls por plataforma, automatizadas, porque en medio de un incidente, con estrés, nadie recuerda cuáles eran.

Por qué las organizaciones no están preparadas

  • Costo: archivar logs en un SIEM o en un log collector es mucho más caro que volcarlos a S3 y dejarlos ahí; la decisión parece sencilla hasta que llega el hackeo y nadie sabe cómo sacar los logs de S3. Y las alertas se cobran aparte: plataformas que facturan la ingesta de logs por un lado y la generación de alertas por otro, un combinado que se vuelve inviable para presupuestos de Latinoamérica o Europa del Este, mercados para los que la mayoría de los productos ni siquiera están pensados.
  • Falsos positivos de las herramientas grandes: los Cloud Security Posture Management irrumpieron hace unos años —en la nube no hay CVEs asociados a una configuración mala, y comunicar que una falla es un bug y no una feature es difícil, así que el negocio responde "lo necesito para trabajar" y la falla queda sin remediar—. Pero las alternativas open source llenan de ruido, y en pleno incidente nadie quiere una herramienta que devuelva toda la información habida y por haber: se necesitan solo los datos tácticos para ejecutar la respuesta y el análisis de causa raíz.
  • Gente y procesos: encontrar a alguien con mentalidad de incident responder, que además sepa de cloud security y de varios cloud providers, es casi imposible. El onboarding tomaba meses y, cuando terminaba el entrenamiento, una empresa norteamericana ofrecía el triple y se lo llevaba. Había que democratizar el conocimiento y achicar la curva de aprendizaje para que un analista saliera rápido a la cancha.

Y un indicador irónico de que algo falla: la cantidad de memes sobre lo bardo que es implementar un SIEM y lo llenos de falsos positivos que estamos. Si los memes abundan, algo estamos haciendo mal.

Los cuatro módulos

  • Log Retriever: el punto de partida. Con un mismo comando, un analista obtiene logs de AWS (Event History, GuardDuty, logs en buckets de S3), de GitHub o de GCP —con integración de Azure en camino—, todos en el mismo formato, sin conocer los pormenores de cada plataforma. No es magia: son las API calls básicas de cada proveedor, encapsuladas.
  • Threat Hunting: queries específicas sobre lo que el retriever levantó, para identificar causas raíz —por ejemplo, las API calls asociadas a evasión de defensas— e integraciones con Shodan y VirusTotal para contextualizar IPs.
  • Incident Response: las acciones de siempre, que en la nube no son triviales: aislar un servidor, deshabilitar o borrar un usuario, rotar credenciales. Además resuelve el problema de permisos: si el analista no es administrador de la cuenta del cliente y debe pedirle a un DevOps que ejecute comandos, pasarle "ejecutá dredge y mandame el output" es mucho mejor que pasarle 200 comandos sueltos.
  • Cloud Status: control de postura con información específicamente táctica, no exhaustiva.

La configuración es por archivo o por CLI: fechas de inicio y fin para acotar la búsqueda (y no ejecutar queries sobre todo el data lake), API keys de Shodan y VirusTotal, y por proveedor el flag de habilitación y los perfiles de autenticación. El repositorio trae documentación y videos de instalación y configuración.

Log Retriever en acción

Event History es el log principal del análisis forense en una cuenta de AWS: registra todas las API calls —crear un servidor, borrar un usuario—. Por consola solo se ven 50 (o 100) requests por query con paginado manual; con 200 millones de logs, eso es estar frito. Dredge automatiza la paginación por API:

python3 dredge log-retriever --provider aws --profile demo --region ... --log event-history

y el resultado es JSON, listo para greps —por un usuario de IAM como Terraform, o por una access key—.

GuardDuty es la detección automática de AWS, que se habilita con un botón: si ya está habilitado, se ve qué pasa en la cuenta; si no, lo primero de un incidente es habilitarlo, porque empieza a monitorear desde ese momento. El problema operacional: logs de 200 cuentas sin preparación previa significan recolectar cuenta por cuenta. Con todos los perfiles de autenticación en el archivo de configuración, el script baja todo a la vez.

GitHub guarda una sorpresa: los logs de consola no son los mismos que los de la API. La consola muestra logs de seguridad (accesos a la cuenta desde distintas regiones), pero un data leakage por git clone o git fetch no aparece ahí —sí en la API—. Mismo comando, cambiando el target de AWS a GitHub y pasando la organización; y, como siempre, varias organizaciones y varios repos en el archivo de configuración.

Cloud Status: la información táctica que importa

Para usuarios IAM —herramientas superpoderosas para desplegar recursos... y para que un atacante gane persistencia y se mueva lateralmente—, un control de postura tradicional da email y nombre; lo que se necesita en un incidente es:

  • si tiene acceso a consola,
  • si tiene MFA y access keys,
  • cuándo fue creado.

La fecha de creación es la clave: si el ataque fue hoy a la mañana e inmediatamente después aparece un usuario creado sin consenso, ese es el primero a revisar —persistencia probable—.

Para instancias EC2 importa el triage rápido: si tiene rol de AWS adjunto, si tiene IMDSv1 habilitado (el atacante que cae en el servidor ejecuta una request y obtiene el rol; AWS ya lo exige como IMDSv2 con token por defecto, pero los sistemas legacy abundan), el nombre de la clave SSH asociada —las claves SSH son especialmente peligrosas: se asocian dejando mucho menos rastro que un usuario IAM y no están entre lo principal monitoreado—. Con eso se gradúa el riesgo: IMDSv1 sin rol es menos grave que IMDSv1 con rol de administrador, sin necesitar el volumen de datos de un Posture Management completo.

Incident Response: aislar un servidor en AWS no es trivial

El ejemplo insignia es el aislamiento de una instancia comprometida, y muestra por qué las acciones "simples" de la nube requieren automatización:

  1. Se busca quitar el security group del servidor comprometido —no se puede: todo servidor necesita sí o sí un security group—.
  2. Se crea un security group forense nuevo y se cambia en la instancia. Pero las conexiones existentes no se cortan: no se permiten conexiones nuevas, pero la sesión establecida del atacante con persistencia sigue viva.
  3. Hay que modificar además la network ACL para bloquear el tráfico y cortar las conexiones existentes. Problema: las ACL actúan a nivel VPC y bloquean a todos los demás servidores de la red.
  4. En muy poco tiempo: crear security group, cambiarlo, crear la ACL que bloquea todo y retirarla para verificar que la instancia quedó aislada. Manualmente, prácticamente imposible.

Con Dredge: enumerar instancias (perfil, security group), enumerar el security group (permisos de internet para todos lados), y ejecutar dredge incident-response --isolate-instance <id>. El script ejecuta todos los pasos y la verificación posterior muestra el nuevo security group forense, sin tráfico permitido. Si el análisis lo requiere, ese security group puede permitir tráfico solo entre servidores forenses, para examinar la instancia desde el servidor de forense. También hay acciones para Lambda y Kubernetes, con extracción de logs de los dos.

Threat Hunting: a veces es solo saber qué buscar

La evasión de defensas parece algo súper sofisticado; en la nube, el caso típico es que el atacante deshabilite GuardDuty (o CloudTrail) para operar tranquilo. La caza se reduce entonces a:

  • bajar el log de Event History con Dredge —ese log está siempre habilitado y no puede ser deshabilitado, sin importar lo que el atacante haya hecho—,
  • grep contra las API calls asociadas a la técnica Impair Defenses (StopGuardDuty, deshabilitar CloudTrail, etc.),
  • de cada hit, asociar el usuario, la access key o quien sea que ejecutó la acción.

Y para el análisis avanzado: extraer todas las IPs de un log de GuardDuty (o de Event History, o de GitHub) y pasarlas por la API de VirusTotal con la API key configurada. El resultado es una tabla con cada IP, su geografía —servidor de Amazon, sistema de Argentina, o una IP asociada a un actor de China, Rusia o Europa, que enciende la alarma— y los hits de software malicioso.

Conclusiones

  • La preparación ideal de incident response casi nunca existe; el diseño útil parte de lo que sí está garantizado: logs del cloud provider habilitados por defecto e imposibles de deshabilitar, como Event History.
  • El costo de los SIEM, las alertas aparte y los falsos positivos dejan a muchos equipos —sobre todo fuera de los grandes mercados— sin la opción de la herramienta cara; automatizar cuatro o cinco API calls es la alternativa realista.
  • Acciones que en on-premise son triviales (aislar un servidor) tienen particularidades cloud no triviales: security groups obligatorios, conexiones existentes que no se cortan y ACLs a nivel de red completa.
  • El valor de un framework así es doble: técnica (velocidad y reproducibilidad en el momento crítico) y humano (un analista sin experiencia profunda en cada proveedor puede ejecutar la respuesta correcta con un comando).
