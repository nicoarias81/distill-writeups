1Password para Mac: cómo dos red teamers extrajeron bóvedas completas con malware de bajo privilegio

Fuente: «DEF CON 32 - Finding & exploiting local attacks on 1Password Mac desktop app - J. Hoffman, C. Morgan» · ver el video original

Resumen

Colby Morgan y Jeff Hoffman, offensive security engineers de Robinhood, dedicaron un mes de investigación a 1Password para Mac con un objetivo concreto: encontrar ataques locales para volcar el contenido de las bóvedas, porque es exactamente lo que buscan APTs y red teams al aterrizar en un endpoint. El resultado: una cadena de ataques que obtiene la "muck" (master/account unlock key, las llaves del reino que descifran la SQLite 1password.sqlite), sin SIP bypass, sin root y en su mayoría sin requerir la interacción del usuario, más un ataque a biometría que ni siquiera requiere que 1Password esté desbloqueado. 1Password fixeó lo explotable en las versiones 8.10.36 y 8.10.38 (agosto de 2024).

El modelo de seguridad local: la contraseña no se guarda ni viaja al server; se combina con la secret key local para derivar la muck. Con SSO, la muck llega en un credential bundle cifrado con una device key del keychain. El diseño es sólido, pero la superficie de ataque real estaba en la integración con el ecosistema: Electron, la extensión de browser, el native messaging host, el XPC del browser helper y el flujo de biometría.

El reconocimiento: Electron bien configurado y tres caminos de salida

Empezaron por el framework en vez de la app. Las fuses de Electron estaban todas correctamente configuradas (ASAR integrity, remote debugging port, etc.), así que la ruta clásica XSS→RCE no era viable: 1Password además casi no inyecta contenido controlado por el usuario. Quedaban tres formas de sacar contraseñas de la app desbloqueada: el SSH agent y la CLI (deshabilitados por default) y la extensión de browser (habilitada por default). Ahí apuntaron.

Ataque 1: suplantación e inyección de la extensión de browser

La extensión sincroniza todas las contraseñas con la app sin re-autenticación cuando 1Password está unlocked. En vez de RCE caro, usaron flags locales de Chrome:

  • Spoofing del extension ID: trivial y por diseño de Google (documentado en su FAQ de seguridad de extensiones): copiar el campo key del manifest.json de la extensión legítima produce el mismo ID derivado.
  • Bypass de la managed Chrome policy (que prohíbe --load-extension y allowlista extensiones): borrar el directorio de policies del Application Support de Chrome y arrancar Chrome con el flag en la misma ventana en que la policy no existe. Chrome la recrea y empieza a reforzarse, pero hace solo un chequeo superficial de ID contra la allowlist — y el ID está spoofeado, así que la extensión maliciosa queda cargada y sincroniza todo.

Veredicto de los autores: no es un bug de 1Password, es cómo funcionan los browsers. El remedio es detección: alertar sobre los flags peligrosos (--load-extension, remote debugging port y compañía).

Ataque 2: native messaging host y el bypass del getppid

La extensión habla con la app a través de un binary de native messaging host sobre stdin/stdout con JSON — sin XPC, sin audit token, sin forma segura de verificar la code signing identity del interlocutor. 1Password lo compensa con un chequeo de parent PID contra browsers confiables, un anti-patrón conocido: el clásico PID-confusion (enviar el mensaje y luego exec al proceso confiable) ya basta, pero ellos encontraron algo mejor — un árbol de tres procesos donde el padre sostiene los pipes de stdin/stdout, el hijo hace exec hacia un browser confiable y el nieto es el browser support process: el getppid check queda satisfecho, se le envía el JSON correcto (descubierto instrumentando el host con Frida) y el browser support process devuelve la muck. Sin Chrome, sin extensión.

Ataque 3: XPC del browser helper + cliente viejo sin hardened runtime

El XPC server del browser helper hace todo bien: audit token, code signing info segura, chequeo de team identifier y bundle ID. Lo que no chequea es el hardened runtime del cliente (flag que prohíbe inyección dinámica de código; nació en 2018, cuando 1Password ya existía). El plan: inyectar en un cliente viejo de 1Password con el mismo team ID y sin hardened runtime, y hablarle al server por XPC.

  • Cómo encontraron el cliente viejo: certificate transparency logs para enumerar subdominios → c.1password.com (una web cache) → Google dorks → versiones viejas de 1Password para todos los OS. La elegida: 6.5.2 para Mac, team ID correcto, sin hardened runtime.
  • Inyección: DYLD_INSERT_LIBRARIES con una dylib cuyo constructor corre el payload (el LD_PRELOAD de macOS).
  • Del echo a la muck: el server exponía echo (PoC) y sendToMain (funcional). Los mensajes de la extensión colgaban porque la conexión marcaba isBrowser=false (el bundle ID del cliente viejo no era el esperado). Espiando el tráfico XPC de la CLI op con una herramienta open source, descubrieron el blob clientInfo y el campo sessionType. Probaron sessionType: browser — un valor que la propia extensión nunca envía — y funcionó: con 1Password unlocked, el XPC server entrega la muck directamente.

Esta cadena (XPC bypass) fue reportada y fixeada por 1Password en abril de 2024; publicaron un PoC en GitHub (morganc3/1password-exploits).

Ataque 4: habilitar la CLI tocando settings.json

Con la conexión XPC emulando la CLI quedaba el escollo de que la CLI integration viene deshabilitada. settings.json guarda flags booleanos con un auth tag de integridad que resultó no estar siendo enforceado: flip a true y la integración se activa. Este fix (enforcear los auth tags) resultó ser el más importante de todos, porque desactivando la CLI integration los dos problemas todavía explotables quedan inutilizables. Fixeado en 8.10.38.

Bonus no explotado: el session ID de la CLI se deriva del PID y start time del shell padre — malware que espíe un shell corriendo op puede montarse sobre una sesión ya aprobada.

Ataque 5: biometría sin bóveda desbloqueada

El más interesante, porque no requiere que 1Password esté unlocked. Engancharon con Frida evaluatePolicy (LocalAuthentication) para que siempre devuelva true: con un fingerprint inválido —o de otra persona— la bóveda se desbloquea igual. Eso reveló que 1Password obtiene y usa la muck sin validación real del dedo, saltándose la protección a nivel keychain. Reconstruyeron la cadena completa:

  1. Un ítem del keychain llamado biometric unlock guarda ciphertext cifrado por la Secure Enclave.
  2. La clave de la enclave no se consulta; se pide que descifre: hookeando SecKeyCreateDecryptedData vieron que durante el unlock descifra ese ítem y devuelve 32 bytes.
  3. Esos 32 bytes no son la muck: son una clave AES que descifra el campo encUnlockKey de la SQLite, y ahí vive la muck.

Para ejecutar el ataque de verdad hacía falta inyectar código en 1Password y consultar el keychain en su nombre. La versión moderna tenía la fuse de ASAR integrity activada, pero: (a) encontraron una versión vieja con la fuse deshabilitada (overwrite de main.js), y (b) existía además un GitHub security advisory con un bypass de esa fuse. Con hardened runtime no se puede cargar una dylib propia, pero la app tiene el entitlement com.apple.security.cs.allow-jit: página RWX garantizada. Armaron un browser exploit sobre un CVE explotado in the wild (heap JS, primitivas de lectura/escritura, shellcode vía WASM corrupto), y resolvieron ASLR "haciendo trampa": vm_map desde afuera del proceso (no es un renderer) y las direcciones de la shared cache escritas a un archivo que el exploit lee. El flujo completo con SIP activado: compilar un C que imprime direcciones de Core Foundation, generar el shellcode ajustado, arrancar la app vieja una vez (deep signature check), matarla, relanzar con main.js modificado y explotar.

Qué fixeó 1Password (y qué no se puede fixear)

  • Fixeado: XPC validation bypass (abril), biometrics flag (8.10.36), settings auth tags enforceados (8.10.38 — la mitigación clave: desactivar la CLI integration protege de todo lo demás explotable).
  • Sin fix claro: la suplantación de extensión (así funcionan los browsers) y el getppid bypass (sin audit token en native messaging, 1Password no puede verificar a su padre; ¿la culpa es de los browsers por no usar XPC o de Apple por no dar una forma segura de mirar al padre? Línea de ownership difusa).
  • Detecciones recomendadas: alertar sobre flags peligrosos de Chromium; alertar cuando un browser es spawneado y su padre no es launchd (indica proceso malicioso o headless); y como los pipes RW pueden moverse de lugar pero todo exploit tiene que hacer exec hacia un browser confiable en algún punto, alertar sobre exec con PID reuse en procesos hijos de launchd.
  • El veredicto honesto de los autores: esperan que ataques similares funcionen contra la mayoría de los password managers — los hicieron contra 1Password porque es el que usan en operaciones de red team. Tener malware en la máquina ya es una barra alta, y la defensa práctica sigue siendo parchear a 8.10.38+.

Técnicas y herramientas mencionadas

  • Muck (master/account unlock key): clave que descifra la SQLite de la bóveda; derivada de contraseña + secret key, o recibida vía SSO + device key del keychain.
  • Fuses de Electron (ASAR integrity, remote debugging port) como primer contorno evaluado.
  • Spoofing de extension ID vía campo key del manifest.json; bypass de managed Chrome policy borrando el directorio de policies y cargando --load-extension en la ventana de carrera.
  • Native messaging host (stdin/stdout + JSON, sin audit token) y parent PID check bypass con árbol de procesos padre/hijo-exec/nieto.
  • Instrumentación con Frida: hooks de read/write del host, evaluatePolicy, SecItemCopyMatching, SecKeyCreateDecryptedData; scripts liberados en morganc3/1password-exploits.
  • XPC: audit token vs. chequeos por PID, team identifier/bundle ID sin chequear hardened runtime, DYLD_INSERT_LIBRARIES sobre cliente viejo (6.5.2), blob clientInfo y sessionType "browser".
  • Hallazgo de versiones viejas: certificate transparency logs → subdominio c.1password.com → Google dorks.
  • Biometría: Secure Enclave → clave AES de 32 bytes → encUnlockKey en SQLite → muck; inyección vía main.js (fuse vieja) + browser exploit (CVE in the wild, heap JS → WASM RWX) con ASLR resuelto vía vm_map externo.
  • Timeline: reportado enero 2024; fixes abril/8.10.36/8.10.38 (agosto 2024).
