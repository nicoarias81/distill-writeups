Del módem hackeado a millones de módems: la superficie de ataque del ISP

Fuente: «DEF CON 33 - Hacking Millions of Modems (and Investigating Who Hacked My Modem)» · ver el video original

Resumen

Una petición HTTP de prueba enviada a un servidor propio en AWS reapareció minutos después desde una IP ajena: toda la red doméstica reenviaba exactamente la misma request. Ese incidente personal —módem comprometido, atacante que mezclaba infraestructura de phishing sofisticada con operaciones "humanas" ordinarias— desemboca en la pregunta de cómo se gestiona realmente un módem: vía TR-069, un protocolo que no está expuesto a internet pero que el soporte técnico del ISP maneja a través de APIs internas. Lo que sigue es la escalada desde el portal de negocio de Cox Communications hasta la capacidad de reconfigurar el módem de cualquier cliente con solo su dirección MAC, y la constatación estructural final: un único servidor de autenticación de Comcast detrás del cual viven cientos de millones de dispositivos.

Parte 1: quién hackeó el módem

Durante un pentest, una caja en AWS logueaba requests para explotar un XXE. La request de prueba (GET /hello) apareció replicada desde una IP de DigitalOcean, y no solo desde el ordenador: teléfono, portátil y la smart TV del cuarto de invitados la reenviaban idéntica. La red estaba comprometida en algún punto intermedio; el sospechoso lógico era el módem (Cox Communications), que fue devuelto al store al ser equipo alquilado —perdiendo la evidencia para siempre.

La historia de esa IP, reconstruida históricamente, era extraña por partida doble:

  • Infraestructura de phishing: había hospedado dominios con BeEF y hook.js, campañas de phishing dirigidas contra sitios concretos —incluida una empresa sudamericana de ciberseguridad.
  • Dominios DGA: miles de dominios de algoritmo de generación de dominios, comprados y rotados, apuntando a la IP —comportamiento de malware sofisticado conviviendo con operaciones de phishing de "humano normal".

El intento de retorno: inyectar comandos en la curl que el malware reenviaba, para tomar control del C2. Sin éxito. Tampoco se recuperó nunca el binario malicioso: el módem fue entregado y la pregunta de cómo se espejaba el tráfico sigue abierta.

Parte 2: la superficie de ataque del ISP

La pista vino de una mudanza ajena: el soporte telefónico del ISP configura el módem —no solo la contraseña Wi-Fi— de forma remota. El mecanismo es TR-069, protocolo bien investigado (con varias presentaciones previas que lo pop-ean directamente), pero inaccesible desde internet. Lo interesante está en el intermediario: la API que conecta el call center con el ACS (Auto Configuration Server).

Del portal de negocio a la API interna

Sin cuenta disponible, el punto de partida fue el portal de negocio de Cox —más funcional que el residencial: gestión de VLAN, security groups, todo— y el saqueo de JavaScript en busca de endpoints. Todo el API del sitio usaba el prefijo api-cbma, que se comportaba de forma distinta al resto del tráfico: candidata a reverse proxy hacia una API interna.

El obstáculo y la solución: la Swagger UI existía pero sus recursos estáticos (.js, .css, .html) eran interceptados por el frontend. Añadiendo un %2f (slash codificado) al final del path, la request seguía llegando al reverse proxy y cargaba el backend. El swagger reveló 700 routes.

Autorización rota sin patrón

El fuzzing de los 700 endpoints (GET/POST con intruder) arrojó un patrón anómalo: ~50% errores de autorización, ~35% bad requests, ~15% éxito —sin nada discernible que separe endpoints autenticados de no autenticados. Peor: un endpoint que devolvía 200 empezaba a alternar errores de autorización al repetir la request —load balancer con autorización simplemente rota—.

El endpoint profile search aceptaba parámetro por URI; la cadena de prueba "FBI" devolvió 30 field offices del FBI con direcciones —clientes reales, PII accesible sin autenticación—. El escalado a dispositivos llegó con un endpoint documentado que aceptaba una MAC address y devolvía la IPv4 actual: desde la API de negocio, como cliente residencial, se podía golpear el propio módem. El siguiente paso, conseguir la MAC de cualquier otro cliente, era trivial: un endpoint de búsqueda de cuenta por email o nombre devolvía el user ID, y de ahí el inventario completo de equipment de la cuenta —cada iPhone, TV y dispositivo conectado— sin que el titular recibiera notificación alguna.

SAIL: el protocolo interno de dispositivos

El parámetro que bloqueaba la reconfiguración se llamaba encrypted value, y su error asociado era de "SAIL" —identificado por OSINT de LinkedIn como la capa interna de comunicaciones con dispositivos de Cox, construida sobre TR-069 con las secretas centralizadas. La criptografía estaba en el JavaScript del portal: una función runtime de encriptar/desencriptar. En vez de extraerla, un breakpoint en el punto de registro (con PIN de 4 dígitos cifrado client-side) permitía llamar a la función desde consola: cifrar 8042 y pasarlo al endpoint de device management cambió el error de SAIL de "no sé qué hacer con esto" a "desencriptado OK" —mismo esquema de cifrado en el backend, puerta abierta a los device endpoints.

Confirmación de formato con la cuenta real de un amigo MSP de Omaha: desencriptar un encrypted value genuino revela account number, device ID, device name… y la MAC address. La prueba decisiva: firmar un payload con solo la MAC como campo válido y todo lo demás como junk data —funcionó perfectamente—.

Del PII al control total

La request firmada con la propia MAC actualizó la configuración del dispositivo: la red doméstica se cayó, el módem se reconfiguró y reinició. A partir de ahí, los mismos poderes que un agente de soporte: cambiar contraseña Wi-Fi, ver dispositivos conectados, abrir puertos, usar el módem como proxy, y —la vía real a RCE— push de configuraciones o paquetes nuevos de firmware al dispositivo. La kill chain completa: encontrar account ID → obtener MAC → operación de hardware arbitraria.

El punto de falla único: el servidor de Comcast

El remate estructural: los ISP comparten software. La app de Cox no autentica contra servidores de Cox sino contra dh.something.comcast.net —un único servidor HTTP con cientos de millones de dispositivos detrás, ~10 petabytes de datos diarios de metadatos (nombres de dispositivos conectados incluidos, impensable hace una década). Con la reautorización de FISA de fondo, la conclusión es directa: pop-ear esa única API es control o observación pasiva de metadatos de cientos de millones de dispositivos. Un punto de centralización con impacto masivo.

El desenlace del incidente original

Cox, colaborativa en la coordinación (mensajes legalmente verificados, equipo correcto), confirmó dos cosas: la vulnerabilidad encontrada no era la que hackeó el módem original —fue introducida posteriormente—, y la IP de DigitalOcean no les pertenece. Alguien sí poseyó el módem, pero por otra vía. La investigación del incidente inicial queda, honestamente, sin cerrar.

Técnicas y herramientas mencionadas

  • TR-069 / ACS: protocolo de gestión remota de módems, inaccesible desde internet pero alcanzado vía APIs del call center.
  • api-cbma (reverse proxy): prefijo de la API interna de Cox; %2f para cargar Swagger UI desde el backend.
  • Authorization rota sin patrón: ~15% de endpoints expuestos sin autenticación, alternancia de errores por load balancer.
  • Account equipment + MAC lookup: enumeración pasiva de dispositivos de cualquier cliente y localización por MAC.
  • SAIL: capa interna de comunicación con dispositivos; cifrado client-side extraíble vía breakpoint en consola, firmas de payloads con MAC-only.
  • DGA + BeEF/hook.js: infraestructura del atacante original, reconstruida por historia de la IP en DigitalOcean.

Conclusiones

  • El modelo "el ISP gestiona tu módem" convierte al call center —y a la API que lo conecta al ACS— en la superficie de ataque real del CPE, mucho más rica que el módem mismo.
  • Una API interna con autorización intermitente, referenciada desde un portal público, permite escalar de PII a reconfiguración de firmware en tres pasos: account ID, MAC, push.
  • El cifrado client-side de un parámetro como encrypted value no protege nada: el mismo esquema sirve para firmar payloads arbitrarios.
  • La "internization" de los módems —menos gestión local, más gestión en la nube— crea puntos únicos de falla (un servidor de autenticación de Comcast, cientos de millones de dispositivos) cuyo compromiso es un evento de escala nacional.
  • Muchas vulnerabilidades de este ecosistema viven tras VDPs con términos de no divulgación: probablemente se han encontrado antes y no se sabe.
