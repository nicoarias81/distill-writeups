De PoC a Python malicioso: la cadena que convierte un bug del kernel en root

Fuente: «DEF CON 33 - Turning Off-the-Shelf Kernel Exploit PoCs Into Fully-Fledged Python Malware - Dennis 'dhn' Herrmann» · ver el video original

Resumen

Hay un puente que casi nadie cruza: los proof of concept de exploits de kernel que abundan en GitHub explotan la vulnerabilidad pero no hacen nada útil después, y el malware de post-explotación —ejecución de código arbitrario, robo de datos, persistencia— asume que ya hay ejecución. Este trabajo recorre el camino completo: cómo un módulo cargable del kernel es demasiado grande para caber en la memoria de un exploit, cómo superarlo con kernel ROP (stack pivoting, gadget chaining, allocated shellcode) y cómo terminar con un binario en Python capaz de montar una terminal inversa en el objetivo. Todo con permisos de usuario normales, sin que el módulo o el driver sean legítimos.

La brecha entre exploit y malware

El flujo típico de un exploit de kernel con CVE conocido es: navegar los tweets de la comunidad de kernel exploitation, probar el PoC, y ver que gana root… y ahí termina. Pero un exploit es solo el vehículo inicial: hay que ganar ejecución de código en el objetivo. Para simplificar, esta presentación parte del supuesto de que ya existe ejecución de código (por ejemplo, tras un phising o exfiltrando los datos de un navegador) y se concentra en la escalada de privilegios y la post-explotación.

En el mundo Linux, hay maneras clásicas de cargar código en el kernel: Loadable Kernel Modules (con insmod, soportado por defecto) y eBPF. El problema del módulo es que pesa mucho: un módulo que imprime "hello" ya ocupa megabytes, porque incluye depuración, KCSAN, KASAN y demás. La memoria asignada por el exploit (por ejemplo, en la estructura pipe_buffer del kernel) es apenas de unos kilobytes. La solución es usar un shellcode mínimo en el kernel y cargar la carga útil más pesada después —por ejemplo, con un driver que permita interacción—.

Kernel ROP: stack pivoting y gadget chaining

La máquina demostradora es una Debian 12 con kernel 6.1.0-25-amd64, sin vulnerabilidad real CVE (para no usar un exploit conocido): solo un binario setuid-root con una función vulnerable que ejecuta strcpy(buf, s), que permite escribir y sobrescribir el stack del propio proceso (para simplificar, con ASLR desactivado; hay técnicas conocidas para lidiar con él en la práctica).

El shellcode se divide en etapas. Stage 0 es el stack pivot clásico: mover el valor de un registro al stack pointer y hacer pop de registros —exactamente lo que ya hace un exploit normal—. Stage 1 importa el shellcode real: un commit_creds(prepare_kernel_cred(0)), más un swapgs y un iretq que regresa al modo usuario con los registros correctos. Si el exploit no gana root ahí, la escalada falló.

La idea central para evitar el problema de tamaño es combinar gadgets para rellenar memoria: en vez de inyectar el shellcode completo, usar gadget chains que escriban de a pocas palabras (cada gadget escribe unas pocas instrucciones) y eventualmente logren todo el payload. El flujo: el exploit busca en el binario del kernel los gadgets necesarios para el stack pivot, escribe los ROP chains en memoria con write(), y termina el exploit devolviendo la ejecución a un loop que ejecuta la lista de gadgets. La fase de explotación queda invisible.

De shellcode a driver: post-explotación con lenguaje C

Terminada la fase de ROP, queda la parte larga en la que el público se aburre y el expositor escribe código en C: el driver. En Linux, la interacción con el kernel se hace con el módulo framework ftrace para localizar funciones del kernel (algo estándar en rootkits y ya cubierto en muchas charlas de DEF CON). El punto aquí no es un rootkit sino la arquitectura de un hack que alguien ya haya hecho antes: el driver es el pegamento entre el espacio de usuario y el kernel, y hace de intermediario.

Un detalle importante: usar syscalls para leer y escribir archivos con los permisos actuales del usuario, en vez de manipular directamente los objetos del kernel (como struct file), que son complicados y frágiles. En el espacio de usuario, la forma más fácil de hablar con el driver es el /dev estándar de Linux. La función write del driver recibe el código de la operación desde el userland; los command IDs se pueden definir manualmente o con el struct propio, y manejar comandos arbitrarios es simple: leer la función del driver, comparar el comando y ejecutar el caso correspondiente.

El flechazo: leer archivos remotos desde el kernel

Aquí aparece la idea que cambia el alcance: ¿por qué detenerse en leer archivos locales si el kernel puede enviar tráfico por la red? Con un poco más de ingeniería, el driver puede:

  • Hacer conexiones de red desde el kernel usando struct socket, con sock_create_kern, kernel_bind, kernel_connect, kernel_sendmsg y kernel_recvmsg —casi idéntico a cómo se hace un cliente de red en el espacio de usuario—.
  • Ejecutar comandos remotos. El driver verifica si hay conexiones entrantes (poll) y, si hay un comando, lo ejecuta. La prueba de concepto: hacer que el kernel haga un comando como uname -r (en el mundo real, un solo uname -a basta). El truco de implementación es usar call_usermodehelper desde el kernel para lanzar un proceso de usuario —función que el kernel provee—, muy usada en rootkits conocidos.
  • Exfiltrar datos del kernel. Lo mismo en sentido inverso: kernel_recvmsg para recibir, y mandar los datos por el socket ya establecido.

El driver también permite ocultar procesos: en el mundo Linux, la información de los procesos vive en /proc, y con filldir64 se puede interceptar la lectura del directorio y filtrar los procesos que interese ocultar. En la demo: listar los procesos que empiezan con "x" desde el kernel con la syscall getdents64, y exfiltrarlos —muy típico en malware para ocultar lo que corre en el objetivo, incluido el propio driver—. El flujo exacto: el exploit gana root vía ROP, inicia el driver con un ping a la IP del atacante, y de ahí la máquina queda comprometida.

El asalto final: Python malicioso

Queda el problema del primer contacto: ¿cómo convencer al usuario de ejecutar un binario ELF compilado? Opción tentadora: alterar el ELF en un archivo PDF —pero el formato PDF es viejísimo y en 2025 nadie abre PDFs—. El flechazo final: escribir el malware en Python, porque Python es multiplataforma y corre en cualquier lado.

La estructura: un archivo stage0.py de apenas 30 líneas que se distribuye como que "descarga los assets del juego". Con os.chmod se le da permiso de ejecución al binario, con subprocess.Popen se lanza, y con el módulo socket se hace un loop de 50 líneas para recibir y ejecutar los comandos (stage1 en Python recibe el binario del driver por la conexión C2, lo escribe a disco y lo ejecuta). En la demo el "juego" en Python inicia y mientras tanto, en otra terminal, el atacante recibe la conexión y lista las banderas de un proceso oculto. Todas las etapas usan Python normal, sin dependencias externas. Y si el binario ELF "no es legítimo" preocupa, siempre queda la variante de generar dinámicamente un ejecutable legítimo del driver: no hay límites, solo imaginación.

Conclusiones

  • Los PoCs de kernel explotan pero no explotan bien: el módulo es demasiado grande para la memoria que el exploit controla; la solución es kernel ROP (stack pivoting + gadget chaining) con shellcode por etapas.
  • El driver posterior es el pegamento entre userland y kernel: comandos arbitrarios, conexiones de red desde el kernel con la familia kernel_*, ejecución remota vía call_usermodehelper, exfiltración y ocultación de procesos con filldir64.
  • El vector de entrega final puede ser un script Python de 30-80 líneas sin dependencias: suficiente para traer el binario, ejecutarlo y montar el C2.
  • Cada capa se puede combinar y automatizar; la cadena completa funciona con permisos de usuario normal, y el resultado es malware plenamente funcional a partir de un PoC de GitHub.
