Entrar pisando la confianza: confused deputy y roles asumibles en AWS

Fuente: «DEF CON 32 - Exploiting Cloud Provider Vulnerabilities for Initial Access - Nick Frichette» · ver el video original

Resumen

Los caminos clásicos para entrar en una cuenta de AWS —clave de acceso filtrada, bucket de S3 expuesto, instancia EC2 comprometida— son aburridos, en palabras del investigador de Datadog Nick Frichette. Este recorrido propone algo más interesante: patear la puerta explotando vulnerabilidades en los propios servicios de AWS, abusando de la confianza preexistente que los roles de IAM le otorgan a esos servicios. Dos casos de estudio —un confused deputy en AppSync que se saltaba la barrera del cross-account pass-role cambiando las mayúsculas de un parámetro, y el desastre de AWS Amplify, que durante años creó roles asumibles por cualquiera— y una malconfiguración generalizada con assume role with web identity sirven para aprender a atacar y, sobre todo, a defender entornos cloud.

Cómo se establece la confianza en AWS

Cada rol de IAM tiene una trust policy que determina quién puede asumirlo. Lo interesante ocurre cuando esa política confía en un servicio de AWS: el rol por defecto de una función Lambda, por ejemplo, permite que el servicio lambda asuma el rol, y cada vez que la función se ejecuta, Lambda lo hace en nombre del cliente. Surge entonces la pregunta ofensiva natural: ¿podría crear una función Lambda en mi cuenta apuntando a un rol de otra cuenta, y hacer que el servicio asuma ese rol en la cuenta víctima?

Lo que lo impide es el pass-role, una de las fronteras de seguridad centrales de AWS: solo se puede pasar un rol dentro de la misma cuenta; intentar cruzarla devuelve "access denied, cross-account pass role is not allowed". El objetivo del atacante es encontrar una vulnerabilidad en esa implementación para armar el servicio contra los roles que confían en él.

Vulnerabilidad 1: el confused deputy de AppSync roto con memes de Bob Esponja

AppSync es el servicio gestionado de GraphQL de AWS. Al crear una API, se genera un rol que por defecto confía en AppSync, y el servicio asume ese rol cuando la API se ejecuta. El parámetro para asignarle un rol ARN se llama serviceRoleArn, y el pass-role bloquea los cruces de cuenta.

La peculiaridad: la API de AWS es sensible a mayúsculas —pasar name en vez de Name a otro servicio devuelve un 400—, pero AppSync era una anomalía que aceptaba cualquier combinación. Y al cambiar el casing del parámetro, el filtrado que debía impedir el cross-account pass role simplemente no se aplicaba:

flowchart LR
    A[Cuenta del atacante: crear API AppSync] --> B[Pasar serviceRoleArn con casing modificado]
    B --> C[El filtrado de pass-role no se aplica]
    C --> D[AppSync asume el rol en la cuenta victima]
    D --> E[Operaciones API arbitrarias: DynamoDB scan, S3, RDS]

Cambiando una sola letra, se rompió una frontera mayor de AWS "con memes de Bob Esponja". El ataque permitía apuntar a cualquier rol de cualquier cuenta que usara AppSync legítimamente, asumirlo y ejecutar el abanico completo de llamadas API que AppSync permite invocar. La ventaja táctica frente al movimiento lateral clásico: en vez de cazar credenciales y escalar con caminos tipo Bloodhound, se aterriza directamente con la identidad de una aplicación de producción, con todos sus privilegios —subir a S3, escribir en DynamoDB, leer de RDS—. AWS publicó un boletín de seguridad y corrigió el fallo.

La malconfiguración: assume role with web identity sin condiciones

AssumeRoleWithWebIdentity descarga la autorización en un proveedor de identidades externo —privado o público como Facebook, Google o GitHub—: el usuario genera un JWT con el proveedor, lo pasa a la llamada y asume el rol. Es un patrón de diseño general que usan muchos servicios, GitHub Actions incluido: el job del pipeline firma un JWT con el proveedor de identidades de GitHub y lo canjea por el rol en la cuenta.

El detalle escalofriante es la trust policy más básica posible: permitir que el proveedor de GitHub asuma el rol, sin condiciones. Como ese proveedor es público y global, cualquiera con una cuenta de GitHub podía crear su propio action, generar un JWT firmado por el mismo proveedor y entrar. Por eso, con proveedores públicos, la condición que restringe quién puede asumir el rol —repositorio u organización concreta— es obligatoria de facto.

Cognito, el "inicio de sesión como servicio" de AWS, sí incluía por defecto una condición que restringe qué identity pool puede asumir el rol. Pero la comprobación solo verifica que se está autenticado en un identity pool, no en el identity pool correcto: como el atacante puede crear el suyo, la defensa se cae. Con el flujo básico (classic authflow) de Cognito —get ID, get open ID token, assume role with web identity—, y ya sea con la condición unauthenticated o saltándose los aros de authenticated con un user pool propio, el resultado es el mismo: asumir roles de cuentas ajenas. AWS hizo obligatoria la condición para GitHub Actions, pero el mismo patrón de malconfiguración sigue vivo en otros servicios.

Vulnerabilidad 2: Amplify regalando roles durante años

Para medir la prevalencia de la malconfiguración, se buscó en GitHub público —vía Sourcegraph— con una expresión regular que detectara ARNs de roles de IAM. Tras deduplicar y quitar placeholders, quedaron unos 8.000 roles; la automatización intentó asumir cada uno, autenticado y sin autenticar. El patrón inquietante: la enorme mayoría de los vulnerables terminaban en AuthRole o UnauthRole, con timestamps de 2018–2019 o enteros de seis dígitos —e incluso había tres roles de la propia AWS—. La pista llevó a archivos llamados team-provider-info.json, y de ahí al culpable: AWS Amplify, el framework web y móvil que abstrae la infraestructura —incluido Cognito— para que los desarrolladores no tengan que conocerla.

Como el CLI de Amplify es open source, se pudo reconstruir la cronología exacta desde el historial de commits:

  • 3 de julio de 2018: un commit introduce la variante 2 —cualquiera en el mundo puede asumir los roles AuthRole y UnauthRole que crea todo proyecto Amplify—. Amplify Studio, que usa el CLI como librería, hereda el problema.
  • 8 de agosto de 2019: un aparente arreglo accidental cambia el efecto por defecto a deny y elimina la condición. Impide que se creen roles nuevos malconfigurados, pero los ya existentes siguen vulnerables —así se los asumió en 2024—.
  • Julio de 2020: la variante 1 llega con la eliminación de autenticación de un proyecto: la plantilla CloudFormation que corre al removerla borra la condición de la trust policy, dejando el rol asumible por cualquiera.

Lo que convierte a este caso en extremo es la descubribilidad: los roles de Cognito están diseñados para estar disponibles para los usuarios —son prácticamente públicos—, y son determinísticos: conocida la UnauthRole, se deduce la AuthRole. Un adversario podía rastrear decenas de miles de apps por el dominio por defecto de Amplify buscando roles vulnerables. Y los privilegios no eran nimios: en las notificaciones a clientes aparecieron roles con acceso completo a S3 o a Kinesis. La divulgación fue en enero de 2024; AWS desplegó correcciones integrales entre febrero y abril: ya no se pueden crear estas trust policies, y modificaron STS para bloquear el assume role cross-account vía identity pools —aunque la variante misma cuenta, más laboriosa, sigue siendo posible hoy—.

Prevención: cerrar la puerta aunque la cerradura falle

Contra el escenario peor —un zero-day cross-tenant en AWS— quedan las claves de condición: aws:SourceArn, aws:SourceAccount y aws:SourceOrgID restringen qué ARN, cuenta u organización puede asumir cada rol. No vienen por defecto, hay que añadirlas manualmente a cada rol a proteger y verificar que el servicio sea compatible —EC2, Lambda y AppSync pasaron las pruebas—. Probadas contra el confused deputy de AppSync, bloquearon al adversario externo incluso con la vulnerabilidad presente. Es defensa en profundidad pura: si el pass-role se rompe otra vez —esta vez con memes o sin ellos—, queda una segunda capa que impide el acceso cross-tenant.

El resto del consejo es el de siempre, y sigue siendo lo más rentable: borrar claves viejas, limpiar usuarios de IAM antiguos, privilegio mínimo. Y auditar los roles que usan assume role with web identity: es un error fácil de cometer —AWS lo cometió dos veces—.
