login.microsoftonline.com: la plataforma de phishing que ya está en la lista blanca

Fuente: «DEF CON 33 - Turning Microsoft's Login Page into our Phishing Infrastructure - Keanu "RedByte" Nys» · ver el video original

Resumen

Cualquier operación de phishing se estrella contra el mismo muro: los dominios propios se queman, las pasarelas de correo bloquean los enlaces sospechosos, la categorización benigna de un dominio nuevo cuesta semanas y los usuarios entrenados pasan el ratón por encima del enlace buscando un dominio falso. La respuesta clásica —consent grant attacks, device code phishing, adversary-in-the-middle— tiene límites: los permisos interesantes exigen aprobación de administrador, el device code se bloquea con conditional access y el AiTM sigue dependiendo de un dominio atacante rotable.

Este artículo explora una alternativa incómoda: usar login.microsoftonline.com, el dominio legítimo de autenticación de Microsoft, como infraestructura de phishing. No como redirección ocasional, sino como plataforma completa: recolección de credenciales en claro, validación interactiva de contraseñas, extracción de códigos MFA y secuestro de notificaciones number matching — todo mientras el navegador de la víctima nunca sale del dominio de confianza de Microsoft. Al menos cuatro de las técnicas funcionan sin abandonar nunca ese dominio y varias evaden MFA por completo. La conclusión incómoda es que el dominio más confiable del ecosistema Microsoft es, de facto, el credential harvester más creíble que existe.

El punto de partida: redirecciones abiertas

Antes de las técnicas profundas, tres redirecciones abiertas aprovechan la mecánica propia de Entra ID:

  1. Federación como open redirect. Se configura un dominio del tenant atacante con una sign-in URL de federación que apunta a la página de phishing; una URL a login.microsoftonline.com con el login_hint del dominio federado redirige al instante a la página atacante (donde puede correr Evilginx o similar).
  2. App registration con prompt=none. Un app registration del tenant atacante con redirect URI hacia la página de phishing, más el parámetro prompt=none, provoca una redirección inmediata sin mostrar ni consentimiento ni login, incluso con la configuración de consentimiento más restrictiva.
  3. App registration con scope inválido. Con un scope que Microsoft no entiende, el usuario sí autentica legítimamente (contraseña, MFA), pero en lugar del prompt de consentimiento recibe una redirección silenciosa al redirect URI. El atacante recibe luego un flujo Evilginx que captura credenciales y cookies de sesión con bypass de MFA, mientras la víctima ve un "su sesión ha expirado, vuelva a iniciar sesión" verosímil.

Las tres fueron reportadas y son, presumiblemente, parcheables. Lo interesante empieza cuando el propio flujo de registro de la página de login se convierte en el colector de credenciales.

Self-service signup: el formulario que pregunta la contraseña

El self-service signup de Entra ID permite que usuarios externos registren una cuenta invitado en un tenant sin invitación previa. Durante el flujo, el tenant puede recolectar atributos personalizados —job title, display name, lo que se quiera. Nada impide crear atributos llamados password y mfa code.

El agujero lógico parece evidente: la víctima podría escribir cualquier cosa. Ahí entra el API connector, que permite validación de entrada en tiempo real sobre los atributos recolectados. El ataque completo:

  1. Se envía a la víctima una URL a login.microsoftonline.com con el client_id de la app de registro del tenant atacante, el login_hint de la víctima (correo pre-rellenado) y prompt=create para forzar el flujo de registro sin clics adicionales.
  2. La víctima inicia sesión con las credenciales de su tenant real y acepta la invitación al tenant — que no es un prompt de consentimiento, por lo que la configuración de consentimiento más dura no la detiene.
  3. Aparece la página de recolección de atributos, aún en login.microsoftonline.com, pidiendo "contraseña" y "código MFA".
  4. Entra ID reenvía los valores en claro al API connector del atacante, que los valida contra el tenant real: si la contraseña es incorrecta devuelve "contraseña incorrecta"; si el código MFA falla, otro mensaje de error específico.
  5. El ciclo se repite hasta que la víctima aporta credenciales válidas. En ese momento el atacante tiene contraseñas, códigos MFA, access tokens, refresh tokens y cookies de sesión: la cuenta completa está comprometida.

La víctima nunca interactúa con un dominio ajeno: todo transcurre en la página de Microsoft.

Custom company branding: secuestrar los botones con CSS

El branding personalizado de Entra ID permite personalizar la página de inicio de sesión de un tenant — y la documentación se queda corta: además del fondo, se puede inyectar un archivo CSS propio. No hay inyección de HTML ni JavaScript, y el CSS "peligroso" está filtrado. Pero hay un detalle revelador: el CSS llega sin filtrar al navegador y se limpia con JavaScript del lado cliente. Basta leer el código fuente para obtener la lista exacta de propiedades, reglas y funciones bloqueadas — un mapa completo de lo que sí está permitido.

Con ese mapa, la combinación es quirúrgica:

  • CSS oculta los botones legítimos de inicio de sesión.
  • La personalización del self-service password reset permite insertar un enlace arbitrario, con el texto y destino que se quiera.
  • Un poco de CSS (posicionamiento relativo al píxel, animación de fondo al pasar el ratón) convierte ese enlace en un clon exacto del botón "Next".

El resultado: la víctima escribe su correo en login.microsoftonline.com/<tenant-id-del-atacante>, pulsa el botón "Next" falso y aterriza en un dominio atacante que sirve la página de contraseña vía adversary-in-the-middle, pre-rellenando el correo e incluso cargando el branding del tenant de la víctima. La transición de dominio es perfectamente invisible.

Pass-through Authentication para acceso inicial

Pass-through Authentication (PTA) es un mecanismo de sign-in híbrido: Entra ID reenvía la contraseña en claro a los agentes PTA on-premise, que la validan contra el domain controller — y el agente decide si acepta o rechaza la autenticación. Es la base del ataque de persistencia conocido: backdoor en el agente PTA que vuelca credenciales en claro tras comprometer el dominio.

El giro aquí es usarlo para acceso inicial, no persistencia: montar PTA en el tenant del atacante, backdoorar el agente con PTASpy (herramienta de AADInternals que hookea la API LogonUser de Windows) y conseguir que usuarios de otros tenants inicien sesión en el tenant del atacante. Las restricciones son duras: PTA solo aplica a usuarios híbridos sincronizados del propio tenant, y los usuarios cloud-only quedan fuera.

La pieza que lo resuelve es doble. Primero, la característica poco conocida email as alternate login ID permite iniciar sesión con cualquier dirección del atributo proxyAddresses — y para usuarios cloud-only el campo email se propaga automáticamente a proxyAddresses, incluso con dominios no verificados. Para usuarios sincronizados esa propagación no funciona (comportamiento documentado por Microsoft), y ahí entra el truco final: un glifo de fuente personalizada. Via @font-face — permitido por el filtro CSS — se define una fuente que solo aplica al carácter guion (0x2D) y lo renderiza como una "s" curvada que al ojo humano es indistinguible.

El dominio comprado es micro-of.com; el navegador ve "micro-of.com", la víctima lee admin@microsoft.com. Con esa dirección se crean usuarios en el tenant atacante (con conditional access para que no accedan a nada real), y la URL de phishing es simplemente login.microsoftonline.com con ese login_hint — que además puede ofuscarse con URL encoding. Como el dominio es el legítimo, el password manager de la víctima autocompleta las credenciales con gustosidad, y PTASpy las recibe en claro.

Bypass de MFA con imágenes intercambiables

PTASpy original acepta siempre la autenticación sin validar la contraseña, y un password en claro no sirve si el MFA está forzado. La solución reutiliza el CSS: se oculta el título entre el correo y el campo de contraseña y se sustituye por una imagen servida desde el servidor del atacante.

  • Primera carga de la imagen: "Enter password". La víctima escribe la contraseña, Entra ID la reenvía al agente PTA, y PTASpy — modificado con una función de validación real — comprueba contra el tenant: si falla, devuelve error; si acierta, éxito.
  • Tras validar, el servidor de imágenes pasa a estado "autenticado" durante unos minutos, se redirige a la víctima al login por segunda vez y la imagen que recibe es "Enter code". El código OTP que la víctima teclea viaja por el mismo canal y el backdoor del agente PTA lo valida en tiempo real.

La limitación residual es doble: el OTP se captura en un campo de contraseña (visiblemente distinto del flujo normal) y las notificaciones number matching del Authenticator — las más usadas en entornos corporativos — no pasan por un campo de texto. Para esas:

  1. Tenant 1: mismo CSS del glifo; la víctima autentica con contraseña y el agente PTA captura credenciales. Entra ID emite un código de dos dígitos para el number matching, que el atacante reenvía a su servidor web.
  2. Tenant 2: CSS distinto que reemplaza el cuadro de sign-in completo por una imagen: el teclado de dos dígitos del Authenticator. Como el código no se sabe de antemano, el atacante genera las 100 imágenes posibles y sirve la correspondiente al código real que Entra ID acaba de emitir.
  3. La víctima ve en su pantalla (legítima) el número, recibe la notificación en el móvil, toca el dígito en el Authenticator. El servidor del atacante hace polling constante hasta que la autenticación MFA sucede, y el compromiso está completo: access token, refresh token y cookies de sesión.

Con un solo tenant se puede replicar vía la personalización de branding por idioma: el CSS se sirve según el parámetro de idioma de la URL (por ejemplo, francés para mostrar el prompt MFA). El único rastro es que el título de la página cambia de idioma — un detalle que casi nadie mira justo cuando acaba de sonar una notificación en el teléfono.

Técnicas y herramientas mencionadas

  • Consent grant attack: phishing de consentimiento OAuth en lugar de credenciales; bloqueado por admin approval en tenants endurecidos.
  • Device code phishing: sigue siendo efectivo, pero bloqueable con conditional access.
  • Adversary-in-the-middle (Evilginx): proxy inverso que captura credenciales y cookies de sesión con bypass de MFA; dependiente de dominio propio.
  • Self-service signup + atributos personalizados + API connector: colector de credenciales con validación en tiempo real dentro de Entra ID.
  • Custom company branding / CSS en la página de login: filtrado client-side legible; permite ocultar botones y clonarlos con enlaces del self-service password reset.
  • Pass-through Authentication (PTA) + PTASpy: agente PTA backdoorado (AADInternals) que vuelca credenciales en claro y valida contraseñas y OTP en tiempo real.
  • Email as alternate login ID: sign-in con direcciones del atributo proxyAddresses, incluidas las de dominios no verificados (usuarios cloud-only).
  • @font-face glyph swap: fuente personalizada que renderiza el guion de "micro-of.com" como una "s" legible.
  • Branding por idioma + parámetro de idioma en URL: variante de un solo tenant para alternar entre página de contraseña y prompt MFA.
  • Number matching (Authenticator): evadido generando las 100 imágenes posibles del teclado de dos dígitos y sirviendo la correcta en tiempo real.

Conclusiones

  • login.microsoftonline.com actúa como redireccionador gratuito de páginas de phishing, servidor de imágenes arbitrarias y colector de credenciales validadas — todo desde el dominio con más reputación posible, el que los password managers autocompletan sin dudar.
  • Las defensas centradas en "mirar el dominio" quedan neutralizadas: el dominio es siempre el legítimo. La inspección de parámetros (login_hint con dominios casi idénticos), el monitoreo de registros de signup con atributos anómalos como "password" y la alerta sobre accesos a tenants desconocidos son los indicadores realistas.
  • El MFA no es un seguro contra flujos que controlan el renderizado de la propia página de login: si el atacante valida credenciales y códigos en tiempo real, el segundo factor se cosecha igual que el primero.
  • Varias de las técnicas se apoyan en comportamientos documentados y por diseño (branding, PTA, alternate login ID), lo que sugiere que no hay un "patch" único sino una revisión de confianza: la superficie de personalización de una página de login es también superficie de ataque.
