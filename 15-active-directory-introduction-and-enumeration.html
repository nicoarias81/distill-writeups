PEN-200 Module — Active Directory Introduction and Enumeration (ADIE block)

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-200 (OSCP) course material (module: Active Directory: Introduction and Enumeration) — internal training reference, not for redistribution.

Objective

Enumerate an Active Directory domain from a Windows foothold in an assumed breach scenario: starting with only a set of domain credentials (Stephanie, a regular user in the corp.com lab), walk the escalation ladder of enumeration tooling — legacy net.exe → PowerShell with .NET/ADSI/LDAP → PowerView → SharpHound/BloodHound — and build a map of the domain good enough to reveal an attack path to Domain Administrator. The module's stated arc: enumerate users and groups first (every AD install has them), then computers/OSes, then relationships (local admin access, logged-on sessions, SPNs, object permissions/ACLs, domain shares), then automate the whole picture with graph analysis.

Structure follows the course order: ADIE_02_01–02_04 (manual enumeration), ADIE_03_01–03_05 (PowerView deep dive: computers, sessions, SPNs, ACLs, shares), ADIE_04_01–04_02 (SharpHound collection + BloodHound analysis).

Target surface

  • Domain: corp.com (lab domain), PDC dc1.corp.com.
  • Hosts (from AD computer-object enumeration, 6 total, 3 servers incl. one DC): CLIENT74 (oldest OS — Windows 10, build 1709), CLIENT75 (Windows 11, our RDP jump host), FILES04 (file server), WEB04 (web server / IIS), plus DC1.
  • Key identities: stephanie (initial low-priv user), jeffadmin (Domain Admins member), jeff (session on FILES04), jen (sole member of Management Department), iis_service (IIS service account with an SPN), pete, krbtgt, built-in administrator.
  • Transcript note: the ASR output contains no 192.168.x lab IP addresses — hostnames are used verbatim and any IP (web04.corp.com's internal address) is only described as "an internal IP address". All passwords recovered in the videos are quoted below as [REDACTED].

Techniques

1. AD enumeration with legacy Windows tools — ADIE_02_01

Assumed breach start: authenticate to the domain from a Windows 11 machine (CLIENT75) over RDP:

xfreerdp /u:stephanie /d:corp.com /v:<client75-ip>   # then enter the password

net.exe is installed by default on every Windows box and queries AD without any extra tooling:

net user /domain                          :: list domain users
net user jeffadmin /domain                :: details for one user
net group /domain                         :: list domain groups (default + custom)
net group "Sales Department" /domain      :: members of one group

Methodology: usernames with admin-ish prefixes/suffixes (jeffadmin) deserve a targeted check — that one confirms membership of Domain Admins, i.e. a straight route to domain compromise if the account can be taken. Enumerate every group and catalog it; the group membership web is what later sections mine. net.exe limitations that motivate the next sections: it lists user objects in groups but not nested group objects, and it cannot display arbitrary attributes.

2. PowerShell and .NET classes: building the LDAP path — ADIE_02_02

Scripts live on the client; run them with powershell -ep bypass (bypass the execution policy designed to stop accidental script execution).

# PDC role owner via the System.DirectoryServices.ActiveDirectory namespace
$domain = [System.DirectoryServices.ActiveDirectory.Domain]::GetCurrentDomain()
$domain                                  # verify
$pdc = $domain.PdcRoleOwner.Value        # -> dc1.corp.com

# Domain DN via ADSI (correct LDAP naming: DC=corp,DC=com — two single quotes = search from top of hierarchy)
$dn = ([ADSI]'').distinguishedName       # -> DC=corp,DC=com

# assemble the full LDAP path, dynamic so the script is reusable in any engagement
$ldap = "LDAP://$pdc/$dn"

Why dynamic instead of hardcoding dc1.corp.com / DC=corp,DC=com: the script then ports to future engagements. ([ADSI]'') is preferred over splitting the corp.com string, since ADSI returns the DN already in the format LDAP requires.

3. Search functionality: DirectoryEntry + DirectorySearcher, nested groups — ADIE_02_03

Wrap the LDAP path in System.DirectoryServices classes and search:

$dirEntry = New-Object System.DirectoryServices.DirectoryEntry($ldap)
$dirSearcher = New-Object System.DirectoryServices.DirectorySearcher($dirEntry)
$dirSearcher.FindAll()                   # unfiltered: returns every object in the domain

Filter on the sAMAccountType attribute (present on all user/computer/group objects). The value 805306368 (hex 0x30000000 — the ASR reads it as "hex 30 million") enumerates all domain users:

$dirSearcher.filter = "(&(objectCategory=person)(sAMAccountType=805306368))"

Iterate the results with nested foreach loops — outer loop over result objects, inner loop printing each property (a Write-Host between objects just aids readability). Filter on any property of any object: filtering name = jeffadmin and adding memberOf to the printed properties confirms his Domain Admins membership.

Refactor into a reusable function LDAPSearch taking the query as a parameter, dot-source it into memory, and call it with arbitrary LDAP filters — e.g. objectClass=group lists all groups, not just the global groups net.exe showed (Domain Local groups such as Print Operators, IIS_IUSRS also appear). From the command line, pipe results into a variable and foreach over them printing selected attributes (CN, member) per group.

The payoff example: net group "Sales Department" /domain showed only users Pete and Stephanie, but the LDAP query shows Development Department is also a member — a nested group. Chasing the chain: Development Department contains Management Department, whose sole member is jen. Nested groups are common and scale to the largest AD implementations; net.exe misses them entirely, which is the case for custom enumeration tooling.

4. AD enumeration with PowerView — ADIE_02_04

PowerView (already staged in C:\Tools on CLIENT75) replaces hand-written .NET scripts — internally it does the same thing (obtain the LDAP path via .NET classes, query over LDAP):

Import-Module .\PowerView.ps1
Get-Domain                                    # basic domain info (cf. GetCurrentDomain)
Get-NetUser | select cn                       # all users; pipe to Select to tame the attribute flood
Get-NetUser | select cn,pwdlastset,lastlogon  # dormancy indicators
Get-NetGroup | select cn                      # all groups
Get-NetGroup "Sales Department" | select member

Enumeration heuristics the video calls out: - Dormant accounts (old pwdLastSet, stale lastLogon) — taking one over causes less interference and draws less attention during an engagement. - Users who haven't changed their password since a policy change may hold a weaker-than-current-policy password — prime password-attack candidates.

5. Enumerating operating systems via AD — ADIE_03_01

Get-NetComputer | select dnshostname,operatingsystem,operatingsystemversion

Six computer objects, three of them servers including the DC. Grab this early: OS data gives the relative age of systems (oldest here: a Windows 10 client, build 1709) and locates the weak targets — the lab surfaces a web server and a file server for later attention.

6. Local admin access and logged-on sessions — ADIE_03_02

Find-LocalAdminAccess sweeps the domain checking whether the current user (stephanie) has administrative privileges on any computer. Mechanism: it calls OpenSCManagerW (ASR renders it "OpenServiceW") against each machine's Service Control Manager requesting SC_MANAGER_ALL_ACCESS; a successful connection requires admin rights, so success == local admin. Result: stephanie is admin on CLIENT74 — a high-value finding, but the course deliberately stays the course ("zoom out and generalize") instead of pivoting immediately.

Session enumeration to map which user is logged in where:

Get-NetSession -ComputerName <target> -Verbose

Under the hood: NetWkstaUserEnum (needs admin) and NetSessionEnum (historically did not). In this lab NetSessionEnum returns Access is denied even where expected — a modern Windows hardening issue:

  • NetSessionEnum supports query levels 0/1/2/10/502; PowerView defaults to level 10, which should return computer + user names without admin.
  • The ACL governing this lives on the SRVSVC_SESSION_INFO registry key (HKLM\SYSTEM\CurrentControlSet\Services\LanmanServer\DefaultSecurity); inspect with Get-Acl -Path <key>. Reading is open to several built-in principals, but a capability SID (an unforgeable token granting a Windows component/UWP app access to resources — the long trailing SDDL string) prevents remote enumeration. The change lands around Windows 10 build 1709 (version 16299, the oldest OS in the lab) and applies to Windows Server since 2019 (build 1809+).
  • Keep NetSessionEnum in the toolkit — older systems abound in real environments.

psloggedon (SysInternals, C:\Tools\PSTools) is the fallback: it reads the SIDs of logged-in users from the registry (HKEY_USERS) and converts them to usernames, plus uses NetSessionEnum to see who is connected via resource shares. Caveat: it depends on the Remote Registry service — disabled by default on workstations since Windows 8 (admins enable it for management/deployment tooling), enabled by default on Server 2012 R2/2016/2019/2022, and it self-stops after 10 minutes idle but auto-starts on a connect.

\\C:\Tools\PSTools\psloggedon.exe files04       # jeff found logged in with his domain user
\\C:\Tools\PSTools\psloggedon.exe web04         # no users (possibly a false negative if the service is off)
\\C:\Tools\PSTools\psloggedon.exe client74      # jeffadmin has a session there

Chain forming: stephanie is admin on CLIENT74, and jeffadmin (Domain Admin) has a session on CLIENT74 — admin access there likely means stealing jeffadmin's credentials. Document, don't chase yet: the goal is thorough analysis, not a quick win.

7. Enumeration through Service Principal Names — ADIE_03_03

Service accounts run services and carry SPNs; they typically hold more privileges than regular users, and their SPNs make them Kerberoasting targets in later modules.

setspn -L iis_service                       # built-in Windows tool, list SPNs of one account

or, all accounts at once with PowerView:

Get-NetUser | select samaccountname,serviceprincipalname

(krbtgt shows up in this output too — parked for later modules.) The iis_service SPN points at a web server: nslookup web04.corp.com resolves to an internal IP; browsing there shows a site requiring login. Document the SPN linkage — it is the entry ticket for the upcoming Kerberos attack modules.

8. Enumerating object permissions (ACLs) — ADIE_03_04

The permissions that matter most from an attacker's view (per the course's table): GenericAll (full control), GenericWrite/WriteProperty (set attributes), AllExtendedRights (e.g. add members, reset passwords), ForceChangePassword, plus others listed in Microsoft's docs.

Get-ObjectAcl -Identity stephanie           # every ACE granting/denying permission to stephanie

# the three interesting properties per ACE:
#   ActiveDirectoryRights  - what permission is applied
#   ObjectSID              - the object being acted on (SIDs are unreadable as-is)
#   SecurityIdentifier     - WHO holds the permission

Convert-SidToName <sid>                     # PowerView: SIDs -> readable object names

First example: RAS and IAS Servers holds ReadProperty on stephanie — a common default configuration, no attack vector, but it demonstrates the read pattern.

The hunt: enumerate a specific object (Management Department) and filter for the highest-value right:

Get-ObjectAcl -Identity "Management Department" |
  ? {$_.ActiveDirectoryRights -eq "GenericAll"} |
  select SecurityIdentifier,ActiveDirectoryRights

Five principals hold GenericAll here: Domain Admins (unsurprising) — and stephanie, which for a regular domain user is almost certainly a misconfiguration. Demonstrate the power (and the cleanup):

net group "Management Department" stephanie /add /domain   :: abuse GenericAll
net group "Management Department" stephanie /del /domain   :: clean up after
Get-NetGroup "Management Department" | select member       :: verify both ways

Method note: in a real engagement you'd run the GenericAll/ACE sweep across all domain objects, not one — the exercise shows the discover→abuse cycle on a single target.

9. Enumerating domain shares — ADIE_03_05

Find-DomainShare                                 # all shares in the domain (slow; be patient)
Find-DomainShare -CheckShareAccess               # only the ones the current user can read

Three servers expose shares. Priorities:

  • SYSVOL (on the DC): maps to C:\Windows\SYSVOL\SYSVOL\corp.com and every domain user can read it; it hosts domain policies and scripts. Inside Policies, an OldPolicy folder contains oldpolicybackup.xml — a classic forgotten artifact describing an older policy plus an encrypted password for the local built-in Administrator. This is the Group Policy Preferences (GPP) pattern: GPP-stored passwords are AES-256 "encrypted" with a private key Microsoft published on MSDN, so any GPP cpassword decrypts trivially. On Kali:

bash gpp-decrypt '<cpassword string>' # Ruby script on Kali; plaintext recovered -> [REDACTED]

  • DOCshare on files04.corp.com (non-default share): a folder literally named Do Not Share holds startemail.txt — an email where jeff stored a cleartext password: [REDACTED]. (It may have been changed; document it regardless.)

Meta-lesson: each recovered password sketches the organization's password policy profile (word-choice patterns, length, suffix digits), which feeds targeted wordlists for password guessing/brute force instead of using generic ones.

10. Collecting data with SharpHound — ADIE_04_01

Import-Module .\SharpHound.ps1
Invoke-BloodHound -CollectionMethod All -OutputDirectory "$env:USERPROFILE\Desktop" -OutputPrefix "corp_audit"

Counterintuitive but correct: the SharpHound PowerShell cmdlet is invoked as Invoke-BloodHound (discover any cmdlet with Get-Help). CollectionMethod All runs every collection except local group policies; output is JSON, auto-zipped (corp_audit_*.zip) for transfer to Kali; a .bin cache file is created to speed up repeat collections and can be safely deleted. The lab run scanned 106 objects — a snapshot of everything visible from stephanie's context, ready for analysis.

11. Analyzing data with BloodHound — ADIE_04_02

On Kali (also installable on Windows with its dependencies):

sudo neo4j start          # graph DB; web UI at localhost:7474; default creds neo4j/neo4j -> forced password change
bloodhound                # GUI; auto-detects the running Neo4j instance

Neo4j is a graph database (nodes, edges, properties — not rows/columns), which is what makes attack-path visualization natural. Transfer the SharpHound zip, upload via the Upload Data button (or drag-and-drop). Database Info tab summarizes what was ingested — here: 5 sessions (gathered via the same NetSessionEnum/psloggedOn techniques from earlier), 10 users, 58 groups, and the full ACL set.

Prebuilt Analysis queries used:

  • Find All Domain Admins — graph nodes (draggable; hover or Ctrl-toggle for info, or set Node Label Display → Always Display in Settings): members are jeffadmin and administrator; edges are group memberships.
  • Find Shortest Paths to Domain Admins — BloodHound's killer feature: minimal paths to the goal (own a computer, a user, or a group). Hovering an edge shows its type — the CLIENT74 edge reads Admin 2 (stephanie admin on CLIENT74, matching Find-LocalAdminAccess); right-click an edge → Help for an explanation of the abuse options. It also exposes what manual enumeration missed: jeffadmin has a session on CLIENT74 — his credentials may be cached there, so code execution on CLIENT74 (impersonation/credential theft) yields a Domain Admin.
  • Shortest Paths from Owned Principals — first requires marking what you own. Search an object, right-click → Mark User as Owned / Mark Computer as Owned (owned nodes get a skull icon). Mark stephanie and CLIENT75 (partial control only — no admin on it, so privesc may be needed later; marking it anyway fits the what-if mindset). Then the query renders the full attack chain:

CLIENT75 --[HasSession]--> stephanie --[AdminTo]--> CLIENT74 --[HasSession]--> jeffadmin --[MemberOf]--> DOMAIN ADMINS

Mark every controlled object as owned — short paths may hinge on a particular ownership. The module closes by deferring the rest of BloodHound's prebuilt queries to the challenge labs.

Detection & defense

  • Domain enumeration via SAMR/net.exe/LDAP (techniques 1–4): the queries are ordinary directory operations from an authenticated domain user — no exploit signatures. Defense is visibility and hygiene: alert on bursts of net user /domain-style SAMR queries and unusual LDAP filter volume from a single host, and treat any curious low-priv account enumerating the entire directory (filtering on sAMAccountType, objectClass=group, reading memberOf everywhere) as recon.
  • PowerShell tradecraft: powershell -ep bypass and Import-Module of tools like PowerView/SharpHound are loud in PowerShell script-block logging (4104) and module logging — enable both; AppLocker/WDAC on admin-workstation tiers also blocks ad-hoc tool imports.
  • Find-LocalAdminAccess sprays the Service Control Manager across the network — the SCM connection attempts (event 4699/7045-adjacent, and 4624 logon bursts) are the tell. Least privilege fixes the finding: if stephanie is not local admin on anything, the attack chain dies here.
  • NetSessionEnum: modern Windows already restricts it (the SRVSVC_SESSION_INFO key hardening described above) — keep clients current. Remote Registry being enabled on servers is what makes psloggedon work; audit where it is enabled and why, since it also enables remote registry reads.
  • SPN exposure: every domain user can read all SPNs — unavoidable by design, which is exactly why service accounts are Kerberoastable. Mitigations live in the later attack modules, but the groundwork is set here: long random (25+ char) service-account passwords, no service accounts running as Domain Admin, and monitoring TGS-request spikes (4769 floods).
  • ACL misconfigurations (GenericAll held by a regular user on a group): enumerate your own domain for high-value ACEs held by non-admins (BloodHound does this wholesale) and remediate the delegation model — the lab itself flags stephanie's GenericAll as a misconfiguration that converts a low-priv user into someone who can edit group membership at will. Group membership changes (4728/4732 add-to-group events) should alert outside change windows.
  • SYSVOL/GPP: MS14-025 removed GPP cpassword support — any oldpolicy XML still in SYSVOL with a cpassword is a live credential leak readable by every authenticated domain user. Scan SYSVOL for cpassword, purge stale policy folders, and rotate the affected local Administrator passwords (or adopt LAPS-style randomization).
  • Shares: a Do Not Share folder inside a published share and cleartext passwords in text files are data-loss-prevention bread and butter — inventory non-default shares, DLP-scan their contents, and retrain around credential storage. Recovered passwords also build the attacker's password-policy model: enforce passphrases/policy that don't collapse to guessable patterns.
  • SharpHound: collection touches LDAP at volume and queries sessions — watch for the LDAP read burst and SharpHound's recognizable process/name patterns; mark owned-object mapping impossible to prevent entirely, so shrink the graph: the fewer admin sessions on workstations (and the fewer privileged users browsing/working there), the fewer edges BloodHound can connect. Tiered admin and credential-guard on CLIENT74-class machines would have broken the exact chain this module ends on.
