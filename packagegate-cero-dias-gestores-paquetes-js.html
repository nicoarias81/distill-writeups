PackageGate: cero días en todos los gestores de paquetes de JavaScript

Fuente: «DCSG1 - PackageGate: Finding 0 days in every JS Package Manager - Oren Yomtov, Idan Dardikman» · ver el video original

Resumen

El ecosistema de JavaScript atraviesa una ola de ataques de supply chain: el primer gusano de dependencias, paquetes enormemente populares como Axios comprometidos infectando a millones de usuarios, campañas que empeoran de forma sostenida. Casi todos esos ataques comparten un origen: el mecanismo de lifecycle hooks —los scripts preinstall/postinstall—, que permite a un paquete ejecutar código arbitrario en la máquina de la víctima durante la instalación.

La industria respondió con dos defensas: bloquear la ejecución de scripts (--ignore-scripts) y fijar el árbol de dependencias con lockfiles que incluyen un hash de integridad por paquete. La investigación de PackageGate planteó una pregunta incómoda: ¿el tooling realmente hace cumplir esas promesas? La respuesta: de cinco gestores de paquetes auditados —npm, Yarn, pnpm, Bun y VLT— se encontraron bypasses de integridad en cuatro y bypasses de ejecución de scripts en cinco, con un marcador final de nueve de diez hallazgos. npm y Yarn, precisamente los de mayor base de usuarios, decidieron no corregir varios de los problemas.

Las defensas prometidas y su punto ciego: las dependencias URL

Un lockfile fija la versión exacta y un hash de integridad calculado en la primera descarga: si el registry cambia el contenido, el gestor se niega a instalarlo. Pero existe una característica poco conocida: las dependencias URL, que apuntan a un tarball alojado en cualquier servidor, no solo en el registry. En pnpm, Bun y VLT, la ruta de código de las dependencias URL nunca añade el hash de integridad al lockfile. Basta con que exista una única dependencia URL en cualquier punto del árbol —y con Webpack, Babel y React ya hay miles de dependencias que nadie revisa— para que el árbol deje de estar fijado: el servidor puede servir contenido benigno el día uno y malware un año después, en cada instalación.

npm sí verifica la integridad de dependencias URL, y Yarn resistió todos los intentos de bypass de integridad. Pero npm cayó por otra vía oscura: npm-shrinkwrap.json, un lockfile que un paquete puede embarcar consigo. Al instalar un paquete que trae su shrinkwrap, npm lo fusiona con el lockfile del proyecto consumidor. Publicar un paquete con un shrinkwrap conteniendo una entrada sin hash envenena el lockfile raíz de quien lo instale, desactivando la verificación de integridad de forma persistente.

El bypass de scripts: de allowlists ingenuas a .npmrc dentro del repo

El segundo frente es más grave, porque ejecutar código arbitrario en la instalación compromete la máquina directamente. Bun, seguro por defecto, bloquea los scripts de paquetes salvo una allowlist comparada por nombre de paquete. Comparar por nombre es el error: una dependencia URL que no existe en el registry puede declarar el nombre que sea —axios, esbuild— y pasar el filtro con su script ejecutándose igualmente.

VLT obligó a pensar más abstractamente: si no hay forma de abusar del mecanismo de scripts, cualquier escritura arbitraria de archivos durante la instalación sirve. VLT implementó su propio extractor de tarballs con un regex para bloquear path traversal que no detecta .. en medio o al final de la ruta. Un tarball malicioso con entradas de ruta manipuladas escribe donde quiera —por ejemplo, sobre el binario de git— y la siguiente instalación de una dependencia git ejecuta el payload.

pnpm y Yarn compartieron el mismo descuido en dependencias git: durante la fase de fetch ejecutan los scripts prepare y preparepackage sin comprobar la preferencia del usuario contra los scripts, aunque sí la respetan en las fases de build. Un paquete git con script prepare se ejecuta sin importar la configuración. Y npm, que hace casi todo bien —incluido respetar --ignore-scripts en dependencias git—, cayó ante su propio ecosistema de configuración: al instalar una dependencia git, npm clona el repo a una carpeta temporal y lanza un npm install como subproceso dentro de ella. El repo es del atacante, y con él su .npmrc, que puede fijar la ruta del ejecutable git hacia otro payload del mismo repo; una dependencia git anidada dentro de la dependencia git garantiza la ejecución determinista. Resultado: ejecución de código, con potencial de propagación tipo gusano y robo de tokens.

Divulgación: los pequeños responden, los grandes no

VLT parcheó ambas vulnerabilidades en ocho días —ni que decir que su equipo es el original de npm antes de la adquisición por Microsoft—. pnpm corrigió los dos problemas y emitió CVEs para avisar a sus usuarios. Bun también parcheó, con releases a las tres semanas y a los tres meses.

Yarn, aunque sin bugs de integridad, declinó arreglar el bypass de scripts, alegando que es decisión arquitectónica. npm rechazó el bypass de scripts como "fuera de alcance" —también tras intentos de apelación— y, en el caso de la integridad, a más de 150 días del reporte no había cerrado el reporte ni dado fecha de arreglo, muy por encima de los 90 días estándar de divulgación responsable. Por eso se publica: si unos investigadores independientes encontraron estas cadenas, actores con respaldo de estados-nación también pueden, y los usuarios necesitan saber cómo defenderse.

Qué puede hacer un equipo

  • Migrar de npm o Yarn a pnpm o Bun, que maduran rápido, toman la seguridad en serio y bloquean scripts por defecto; actualizarlos a las últimas versiones cubre los bugs aquí descritos.
  • Commitear los lockfiles y no dejarlos en .gitignore: sin lockfile, cada ejecución de CI descarga las versiones más recientes de todo el árbol, y alguna de esas ejecuciones puede coincidir con el próximo ataque de supply chain.
  • Desconfiar de dependencias URL y git en el árbol: son las vías recurrentes por donde se escapan las garantías de integridad y de scripts.

Técnicas y herramientas mencionadas

  • Lifecycle hooks / postinstall — mecanismo que casi todo el malware de supply chain en JS usa para ejecutarse en la instalación.
  • --ignore-scripts — flag que bloquea la ejecución de scripts; su cumplimiento varía por gestor y por tipo de dependencia.
  • Lockfile + hash de integridad — fijación exacta de versión y verificación de contenido del tarball.
  • Dependencias URL — tarballs alojados fuera del registry; ruta de código sin verificación de integridad en pnpm, Bun y VLT.
  • npm-shrinkwrap.json — lockfile embarcado en un paquete que npm fusiona con el del consumidor; vía de envenenamiento del lockfile raíz.
  • Allowlist por nombre (Bun) — filtro de scripts saltado mediante spoofing del nombre vía dependencia URL.
  • Path traversal en extractor de tarballs (VLT) — regex defectuoso que no detecta .. intermedio/final; escritura arbitraria y sobrescritura del binario git.
  • Scripts prepare en dependencias git — fase de fetch que ejecuta scripts ignorando la configuración del usuario en pnpm y Yarn.
  • .npmrc con git.path en repos temporales de npm — configuración embarcada en un repo git que redirige el ejecutable git a un payload del atacante.

Conclusiones

  • Nueve de diez bypasses documentados: ninguna garantía de seguridad de los gestores de paquetes JS es completa; los lockfiles y los bloqueos de scripts tienen excepciones poco conocidas.
  • El patrón recurrente es que las rutas de código poco usadas —dependencias URL, dependencias git, shrinkwraps— carecen de los controles del camino principal.
  • npm y Yarn no han corregido varios de los problemas; pnpm, Bun y VLT sí lo hicieron, en varios casos con CVEs.
  • La defensa práctica hoy: pnpm o Bun actualizados, lockfiles commiteados y auditoría de dependencias URL/git en el árbol.
