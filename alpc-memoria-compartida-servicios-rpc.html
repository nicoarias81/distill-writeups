Memoria compartida ALPC: del parche de Windows a SYSTEM

Fuente: «DEF CON 32 - Using ALPC security features to compromise RPC services - WanJunJie Zhang, Yisheng He» · ver el video original

Resumen

ALPC (Advanced Local Procedure Call) es el mecanismo ligero de comunicación entre procesos de Windows, base de la mayoría de los servicios RPC del sistema y superficie de ataque enorme. Para pasar mensajes de forma eficiente, ALPC y RPC comparten memoria: el cliente escribe en una sección compartida y el servidor la lee directamente. En 2017 se demostró que esa memoria era un vector de double-fetch — el cliente podía cambiar el contenido mientras el servidor lo procesaba — y Microsoft respondió con un mecanismo de "vistas seguras" en el kernel.

Este artículo disecciona ese mecanismo y el defecto que lo rodea: el tamaño de asignación de las regiones de la sección no se valida, lo que permite provocar un wrap del offset y crear dos vistas que apuntan a la misma página física. El kernel solo protege la primera; la segunda queda escribible y el double-fetch vuelve. A partir de esa primitiva se recorren las vías de explotación — corrupción de memoria en servicios RPC, bypass de UAC y una cadena completa contra el servicio DCOMLaunch que termina en shell SYSTEM desde un usuario estándar, saltándose DEP, CFG y XFG.

Arquitectura: ALPC, RPC y la sección compartida

La mayoría de servicios RPC de Windows se apoyan en ALPC o en named pipes y comparten el mismo modelo de seguridad; un fallo en ALPC se propaga a los servicios RPC que lo usan. Para evitar la sobrecarga de copiar datos, el kernel usa secciones (section objects) como mecanismo eficiente de paso de mensajes. Dentro de una sección, cada región representa un rango de memoria compartida abierto en el contexto de un puerto dado: el servidor tiene acceso de lectura y el cliente solo de escritura.

El catálogo histórico de fallos

Tres familias de vulnerabilidades marcan la historia de esta superficie:

  • Bugs lógicos de suplantación: cuando un servicio opera sobre archivos en nombre del llamante, no manejar bien symlinks y enlaces permite escribir, borrar o crear archivos sin los permisos correspondientes (CVE-2020-0911, con el device map del usuario y el directorio del instalador como ejemplo). Las técnicas de explotación — NTFS junctions, hardlinks, object symlinks, oplocks — están ampliamente documentadas.
  • Corrupción de memoria en el kernel ALPC: race windows entre creación de vista y de puerto que permiten destruir el objeto de puerto y provocar dereferences de punteros colgantes. Explotarlas exige ganar la carrera, lo que las hace poco prácticas.
  • El double-fetch de 2017: el kernel no protegía la protección de la sección compartida al pasar mensajes. Con VirtualProtect el cliente cambiaba la memoria de solo-lectura a escritura y modificaba parámetros mientras el servidor los usaba — visible con un servidor que imprime un string dos veces con un sleep entre medias.

Cómo funciona el parche de Microsoft

Tras el parche, el kernel crea vistas "seguras" que impiden cambiar atributos de memoria desde user space, y tanto el kernel como rpcrt4.dll activan un modo seguro: antes de deserializar, el servidor comprueba la región usada para el mensaje. Las reglas: la región no puede estar vinculada a más de dos view objects, y el kernel fuerza los atributos de la memoria a solo-lectura. Si algo falla, la región se marca como insegura y rpcrt4.dll copia la memoria compartida a un buffer de heap antes de procesarla — el double-fetch desaparece.

El detalle de implementación en el kernel: los VAD (virtual address descriptors) marcan qué rangos son "secure views"; al llamar VirtualProtectEx, funciones de protección de WSLE y manipulación del PTE (los bits de escritura se limpian, y los bits reservados 60-62 de Intel se usan con un propósito propio de Microsoft) dejan la página en no-acceso/lectura para el cliente. MiCheckSecureVAD y la comparación con la máscara de protección deseada rechazan el cambio.

La vulnerabilidad: regiones superpuestas

El offset de inicio de cada región se calcula automáticamente a partir de la región anterior; el tamaño de asignación, en cambio, no se valida. Si se solicita un tamaño extremadamente grande, el offset final hace wrap — por granularidad de vista — hasta cero, y la nueva región se superpone con la primera: dos vistas mapean la misma página física.

El kernel solo asegura la primera vista (la que se usa para enviar el mensaje ALPC). La segunda queda fuera de toda protección y es escribible. Escribiendo por la segunda vista se modifica el contenido que el servidor está leyendo por la primera: el double-fetch vuelve, y MiSecureView no protege contra esto. Verificado en Windows 11 contra un servicio RPC custom: la misma dirección física aparece en ambas vistas, la primera marcada de solo lectura y la segunda escribible.

Vías de explotación

Corrupción de memoria en servicios RPC

Con el double-fetch hay tres patrones de buffer overflow, condicionados a que el servicio use la memoria compartida sin copiarla a otra dirección:

  1. Filling del argument gap: un servicio con múltiples output streams llena la memoria compartida; tras terminar la función de servidor y volver a rpcrt4.dll, el tamaño del stream en memoria ya no coincide con el máximo permitido y se provoca el crash.
  2. Tamaño de string vía puntero: cambiar el tamaño cuando el servidor deserializa provoca out-of-bounds read al copiar a heap — solo negación de servicio.
  3. Spoolss: al abrir una impresora, el nombre se accede dos veces (wcslen); cambiando el offset del stream entre ambas lecturas se obtiene un out-of-bounds write de bytes nulos — explotable pero exige ganar la carrera y construir objetivos fiables.

Bypass de UAC

El servicio de información de aplicaciones (AppInfo) lee la línea de comandos directamente de la memoria compartida sin copiarla — candidato ideal. Las defensas del servicio: una whitelist de programas y argumentos que no disparan la ventana de confirmación, y una verificación de la sección de imagen del proceso lanzado contra el fichero (evita ejecutar un binario distinto al validado). Pero los argumentos no se revalidan: combinando un fichero .msc malicioso que autoejecuta un script con services.msc (en la whitelist) se obtiene una consola de alta integridad sin confirmación. No es una violación del modelo de Microsoft — UAC no es un boundary de seguridad — pero es una escalada práctica de medium a high integrity.

De double-fetch a SYSTEM: la cadena contra DCOMLaunch

La pieza central es un servicio de DCOMLaunch alcanzable por un usuario normal, con una función de configuración de "games" cuyos tres parámetros son estructuras simples (sin punteros) — usa memoria compartida directamente. El GUID de juego se lee del registro, y la clave correspondiente es controlable por el usuario actual: cada usuario tiene su propia configuración en su hive.

La función de servidor comete dos errores fatales:

  • Fuga de memoria: escribe el puntero de la memoria compartida del servidor de vuelta en la memoria compartida. La dirección no cambia entre peticiones, así que con una llamada al servidor y un hilo leyendo en bucle se recupera la dirección — base para construir objetos y vtables falsas dentro de la memoria compartida.
  • Stack array overflow: usa un índice leído de la memoria compartida para escribir un puntero fuera de los límites de un array en el stack — fuga de información y overflow con primitiva de escritura en una sola función.

La estrategia de explotación, paso a paso:

  1. Llamar a la función del servidor y leer en bucle la memoria compartida hasta recuperar el puntero de la vista del servidor.
  2. Construir en la memoria compartida un objeto falso y su vtable con la información filtrada.
  3. Cambiar el índice para sobrescribir el RPC message pointer en el stack del servidor (el objeto vive en el stack del thread, fácil de alcanzar con el overflow).
  4. Al volver al motor RPC, el objeto falso dirige el flujo: se construye un binding handle falso en memoria compartida y se llega a la llamada virtual.
  5. Saltar XFG: la primera entrada de la vtable choca con la ruta del DLL que se quiere cargar (ambas ocupan el mismo espacio), pero hay una función invocable en el offset 0x70 de la vtable — nunca llamada, sin verificación en la práctica — que permite el register pivoting: intercambia RCX para que apunte a la ruta del DLL malicioso.
  6. La callback de combase.dll (pasable por XFG) invoca LoadLibraryExW con la ruta en el segundo parámetro.

El resultado demostrado: un usuario del grupo Users, integridad media, sin privilegios de administrador, termina con whoami respondiendo SYSTEM con todos los privilegios.

Lecciones de bug hunting

  • No confiar ciegamente en los parches: el fix de 2017 dejó un defecto adyacente — el tamaño de asignación sin validar — que reactiva la vulnerabilidad original. El análisis de parches sigue siendo una de las vías más productivas para encontrar bugs.
  • No pasar por alto los side effects: el wrap de offsets es un efecto secundario del cálculo automático de regiones, no un camino obvio de auditoría.
  • La explotación sigue teniendo barreras altas: aunque el double-fetch se reproduce en cualquier servicio RPC, encontrar un servicio explotable — que use memoria compartida sin copiarla, con parámetros adecuados y operaciones sensibles — exige auditoría paciente; en servicios del sistema de Microsoft casi no existen candidatos, y los de terceros son terreno abierto.
  • Queda investigación pendiente: automatizar la extracción de información de interfaces RPC para encontrar servicios y argumentos explotables, y examinar las funcionalidades especiales restantes de ALPC/RPC.

Técnicas y herramientas mencionadas

  • ALPC/RPC sobre secciones compartidas: paso de mensajes eficiente en Windows; el cliente escribe, el servidor lee.
  • Secure views / MiSecureView: mecanismo post-parche del kernel que marca VADs como seguros, fuerza PTEs a solo-lectura y bloquea VirtualProtectEx.
  • Regiones con offset wrap: tamaño de asignación sin validar que produce dos vistas sobre la misma página física.
  • Double-fetch: modificación del contenido compartido entre lectura y uso por el servidor.
  • NTFS junctions / hardlinks / object symlinks / oplocks: técnicas clásicas contra bugs de suplantación en servicios con operaciones de ficheros.
  • UAC bypass vía AppInfo: whitelist de programas/argumentos + .msc malicioso (services.msc).
  • Register pivoting: intercambio de RCX vía callback de combase.dll para redirigir a LoadLibraryExW.
  • XFG bypass: entrada de vtable no invocada en offset 0x70 sin verificación efectiva.
  • WinDbg: depuración en kernel y user mode para verificar PTEs, WSLEs y el estado del servidor durante la explotación.

Conclusiones

  • El mecanismo de seguridad de memoria compartida de ALPC, diseñado para eliminar el double-fetch, se evade con un defecto de validación de tamaños: dos vistas sobre la misma página física bastan para dejarlo sin efecto.
  • La cadena completa — fuga del puntero de vista, objeto falso en memoria compartida, overflow de stack, pivoting de registro y salto de XFG — demuestra que una primitiva de double-fetch "lenta" escala hasta SYSTEM en servicios del sistema.
  • La seguridad de ALPC condiciona la de los servicios RPC: Microsoft ha trabajado de forma sostenida en endurecerla, pero los requisitos para explotar los fallos restantes son estrictamente limitados, no inexistentes.
  • Para el bug hunter: analizar parches críticamente, desconfiar de que un fix cierre todo, y perseguir los side effects que nadie audita.
