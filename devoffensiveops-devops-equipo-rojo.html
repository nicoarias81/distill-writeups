DevOffensiveOps: DevOps aplicado a las operaciones del equipo rojo

Fuente: «DevOffensiveOps: Usando DevOps para Operaciones de Equipo Rojo - Jorge Moya - Ekoparty 2024» · ver el video original

Resumen

Las culturas y herramientas que el mundo del software construyó para desplegar aplicaciones —infraestructura como código, integración y entrega continua, gestión de configuraciones— sirven igual para desplegar y operar la infraestructura de una emulación de adversario. La propuesta, presentada por el fundador de una consultora ecuatoriana de seguridad ofensiva, se llama DevOffensiveOps: aplicar DevOps al equipo rojo para que subir toda la estructura de comando y control, redirectores y CDN tome minutos y dos comandos, y bajarla sea igual de rápido cuando el equipo azul empieza a seguir los indicadores de compromiso.

El recorrido va de los conceptos básicos (DevOps, CI/CD, IaC) al esquema completo de un C2 operado como un despliegue de software: instancias en AWS, Cloudflare como capa de enmascaramiento, Caddy como redirector con listas de control de acceso por user agent, y un pipeline de CI/CD que compila, ofusca, firma y publica el implante —todo demostrado en vivo, con el beacon conectándose al comando y control en pantalla.

La infraestructura de un equipo rojo como despliegue de software

Para actuar como un APT hay que pensar como un APT: un comando y control centralizado, redirectores por los que pasen las comunicaciones de las máquinas víctimas, y la capacidad de levantar y destruir todo rápido. El esquema de referencia:

flowchart LR
    V[ Máquina víctima con el implante] -->|HTTP/HTTPS| CF[Cloudflare: IPs enmascaradas]
    CF --> R1[Redirector 1 - Caddy]
    CF --> R2[Redirector 2 - Caddy]
    R1 -->|túnel seguro| TS[Team Server / C2]
    R2 -->|túnel seguro| TS
    OP[Operador] -->|VPN| TS
  • El problema a resolver: levantar a mano (o con scripts sueltos) cuatro redirectores más tres team servers toma alrededor de un día por cada ejercicio. Y cuando el equipo azul empieza a rastrear los IOC —IPs, software específico, hasta los favicons—, la única respuesta viable es destruir toda la infraestructura y volver a operar desde otro lado sin dejar huella. Eso exige que la destrucción sea tan rápida como el despliegue.
  • Las herramientas de DevOps, reusadas: Terraform para infraestructura como código (controlar AWS, Cloudflare, DigitalOcean, Azure, VMware por script: encender instancias, publicar balanceadores, VPCs, DNS, CDN); TeamCity para el pipeline de CI/CD del implante; Ansible, Puppet y Chef como la categoría de gestión de configuraciones que replica ajustes en cientos de servidores con un comando.
  • El equipo rojo como cliente de cloud: la misma flexibilidad que tiene un equipo de desarrollo para subir un entorno, la quiere el operador ofensivo —y con la misma disciplina de código versionado y despliegue reproducible.

La demo: dos comandos hasta el C2 completo

Primer comando: terraform apply. La configuración de Terraform describe tres bloques:

  • Team Server: crea la instancia en AWS e instala todo lo necesario para el comando y control (en el caso expuesto, Sliver). Su script genera además la configuración HTTP del C2 con el tráfico "moldeado" para que las peticiones parezcan legítimas, y levanta los listeners en HTTP y HTTPS.
  • Redirectores: la misma configuración copiable N veces; cada instancia corre Caddy como servidor web. El script de userdata descarga una lista remota de user agents autorizados y extensiones de archivo (HTML, CSS, JS, JSON, XML —las que peticiona el implante), y con eso genera condiciones en el caddyfile: si la petición no viene de un implante con el user agent correcto, el visitante ve una página web legítima; si viene del implante, Caddy la reenvía como proxy reverso al team server por el puerto correspondiente. Es, en la práctica, una lista de control de acceso que garantiza que al C2 solo se llegue con un implante propio.
  • CDN (Cloudflare): toma la IP de cada redirector y crea registros A proxidados (www → IP del redirector). Un nslookup del dominio devuelve IPs de Cloudflare, nunca las reales; el equipo azul que encuentre el dominio en el implante y lo visite desde un navegador verá la página legítima.

En la demo, con un terraform apply quedaron creados redirector 1, redirector 2 y team server, con sus DNS proxidados. ¿Más redirectores? Copiar el bloque, renombrar a redirector 3 y 4 (en instancias y en el CDN) y volver a aplicar: segundos. ¿Migrar de zona o de proveedor? Cambiar el código y aplicar. Si el operador intuye que el equipo azul lo está siguiendo, destruye todo y reopera desde otro lado.

Segundo comando: el botón de compilar. El pipeline de CI/CD del stager encadena, con un clic:

  1. Descarga el código fuente actualizado desde GitHub.
  2. Reemplaza cadenas que son IOC: la librería de tipos por un número aleatorio y el nombre del proyecto; el ejemplo clásico es Rubeus, que detectado y borrado al instante por Defender si se compila tal cual —el pipeline recorre todo el código reemplazando la palabra por una cadena aleatoria.
  3. Compila (build).
  4. Ofusca: siendo C#, un lenguaje intermedio, con dnSpy es fácil recuperar el código fuente; ofuscado, ya no tanto.
  5. Firma el binario con sigthief, herramienta que roba firmas de binarios legítimos (en la demo, la de Chrome). La firma queda inválida porque la integridad no concuerda —pero tener un binario firmado baja la calificación de maliciosidad.
  6. Genera un shellcode, lo publica por SSH en un repositorio y limpia los directorios generados (el rename aleatorio crea un directorio nuevo por compilación).

Cada compilación produce un binario con hash distinto —compilar el mismo código hoy y mañana da archivos diferentes—, lo que rompe las detecciones por hash. El stager descargado en la demo aparecía firmado por "Google LLC", y al ejecutarse se registró como beacon conectado al comando y control por HTTP.

Higiene operacional: qué queda expuesto y qué no

Las respuestas a las preguntas de la sala precisaron el modelo de exposición:

  • El team server no se publica: se accede solo por VPN (o canal seguro). En la demo quedó el SSH abierto al mundo por comodidad; en un escenario real, no.
  • Los redirectores solo abren 80 y 443, y con una regla que solo acepte peticiones originadas en las IPs de Cloudflare. Nada de la infraestructura está publicada al mundo: la única puerta de entrada es el CDN, y del CDN hacia adentro, solo el implante.
  • Flexibilidad de proveedores como anti-atribuición: el team server puede vivir en OVH y los redirectores en DigitalOcean o Amazon; hoy Cloudflare, mañana Azure. Si todo sale con IPs de un mismo proveedor, ese patrón se vuelve un IOC en sí mismo. Variar el patrón baja la probabilidad de trazabilidad hacia el operador.
  • Balanceador en vez de instancias? Factible (CloudFront en lugar de Cloudflare, o un balanceador de Amazon en lugar de los redirectores), pero la flexibilidad multi-proveedor es la que manda.
  • ¿Contenedores en vez de instancias? Válidos también; la preferencia por instancias viene de 15 años de infraestructura tradicional.
  • Parte del código (stagers, scripts Python de tráfico maleable, herramientas para Sliver) está publicado en el repositorio del expositor; la configuración de Terraform, no.

Conclusiones

  • DevOffensiveOps es la aplicación directa de la cultura DevOps al equipo rojo: infraestructura como código para el C2, CI/CD para los implantes, y el mismo principio de despliegue rápido, reproducible y destruible.
  • Dos comandos bastan para pasar de cero a C2 con redirectores enmascarados por CDN y una página señuelo legítima: terraform apply y el botón de compilar. La misma velocidad aplica a la retirada: si el equipo azul acerca el cerco, se destruye todo y se reopera desde otra zona o proveedor.
  • La evasión empieza en el pipeline, no en la víctima: renombrar IOCs, ofuscar, firmar con certificados ajenos y recompilar cada vez —hash siempre distinto— desactiva toda una familia de detecciones antes de que el implante toque un solo endpoint.
  • La flexibilidad de infraestructura es una táctica de seguridad operacional: no seguir un patrón único de proveedores o IPs reduce la trazabilidad hacia el operador y la eficacia de las defensas que lo buscan.
