FRFuzz: fuzzing asistido por IA para descubrir vulnerabilidades zero-day

Fuente: «FRFuzz: an Open Source Fuzzing Framework - Antonio Morales - Ekoparty 2025» · ver el video original

Resumen

El fuzzing es hoy la técnica más eficiente para encontrar vulnerabilidades de día cero: se estima que entre el 80% y el 90% de los fallos de seguridad graves en Google Chrome, los navegadores, Linux y Android se descubren con un fuzzer — un programa que ejecuta miles de entradas mutadas sobre un software buscando que se rompa, para después analizar el crash. FRFuzz es un framework open source (C++, licencia AGPL v3) que resuelve las tareas repetitivas de ese proceso y añade capacidades basadas en modelos de lenguaje. Su autor lo usó durante el último año para encontrar más de 50 vulnerabilidades zero-day, incluyendo un exploit de ejecución remota de un clic en Evince y decenas de fallos en GStreamer y LibArchive.

La historia del proyecto arranca en 2022 con una idea sencilla: GitHub es una base de datos enorme de código, así que en vez de escribir a mano el harness —el código pegamento que conecta un fuzzer con una librería—, se podría generar tomando como ejemplo código open source existente. El lanzamiento de ChatGPT en noviembre de 2022 convirtió esa idea en algo automático: en enero de 2023 nació un prototipo de generación de harnesses con GPT. Ocho meses después, el equipo Open Source Security de Google publicaba algo muy similar —la confirmación involuntaria de que el enfoque era bueno—, y el proyecto creció hasta convertirse en un framework completo.

Plunger: desatascar la cobertura de código con LLMs

El primer módulo, Plunger ("el desatascador"), nace de una observación: un fuzzer es no determinista, y una LLM también. Unir dos procesos no deterministas parecía mala idea, y resultó ser la clave. Cuando el fuzzer lleva, por ejemplo, 28 minutos sin producir ni una sola entrada nueva tras 19 horas de ejecución, Plunger entra en acción:

flowchart TD
    A[Fuzzer atascado: sin nuevos inputs] --> B[Extraer cobertura de código LCOV]
    B --> C{¿Líneas o funciones sin ejecutar?}
    C -->|Sí| D[Seleccionar función objetivo
y encolar candidatos]
    D --> E[Construir prompt con el código
de la función y el proyecto]
    E --> F[LLM genera un fichero de entrada]
    F --> G[Validar con reglas YARA
contra alucinaciones]
    G -->|Válido y aporta cobertura| H[Añadir al corpus del fuzzer]
    G -->|Inválido| I[Descartar]
    H --> A
    C -->|Cobertura completa| J[Fin del desatasco]

El flujo toma la traza de cobertura de LCOV, identifica líneas rojas (no ejecutadas) o funciones enteras nunca alcanzadas, elige la función más "óptima" para cubrir y le pide a la LLM que genere ficheros de entrada que la alcancen. El prompt es deliberadamente restrictivo: "eres un generador de archivos de fuzzing, tu único trabajo es darme un fichero, sin explicaciones, sin texto adicional" — porque los modelos tienden a añadir "acá tenés tu archivo" y a veces entregan mil ceros seguidos o directamente código C cuando se les pide JSON.

La validación contra alucinaciones se hace con YARA: reglas mínimas de pattern matching que solo comprueban que la salida se parece a un archivo del formato esperado (magic bytes, estructura básica, sin basura). El objetivo no es validar que el archivo sea un PDF o un JSON conforme al estándar, sino únicamente no contaminar el corpus del fuzzer. Por eso el consejo es reglas lo más simples posibles.

Detalles prácticos que marcan la diferencia:

  • Para archivos binarios se pide contenido en base 64, se detecta, se decodifica y se pasa al fuzzer.
  • El punto fuerte son los formatos recursivos: para PDF la LLM corrige sola los offsets internos del archivo — algo que hasta ahora era muy difícil con técnicas clásicas — y con contenedores MKV funciona muy bien también.
  • GPT-5 invocado por API con el effort al máximo (unos dos minutos por respuesta) dio, con diferencia, los mejores resultados entre Cloud, Gemini y OpenAI.

Telescope: value coverage más allá de la cobertura de líneas

Cobertura de código del 90% no significa ausencia de fallos. Un servidor web de ejemplo lo demuestra: una división por el resultado de un cálculo de padding HTTP puede ser cero con una petición trivial, causando una denegación de servicio en un solo proceso. La cobertura marcaba esa línea como ejecutada 1.900 veces — y el bug estaba ahí, en una catedral, sin que la métrica lo viera.

La respuesta es el value coverage: una vez cubierto el código, cubrir los rangos de valores de variables críticas. La primera implementación era una función inline que dividía un entero de 32 bits por la mitad sucesivamente (splitting binario), convirtiendo cada valor en un execution path distinto que AFL podía distinguir y perseguir. La versión final es un LLVM pass que trabaja sobre el código intermedio del compilador desde la versión 14, y se invoca puntualmente sobre la función "de mala espina" en lugar de sobre todo el programa.

Las alternativas existentes no cubren este caso: el cmplog de AFL++ y el trace-division beta de Clang/LibFuzzer (con use-value-profile) intentan maximizar valores de divisiones, pero sin poder elegir variables concretas — y maximizar todas las variables de 64 bits de un archivo es computacionalmente inviable.

Triage: de 80.000 crashes a 7 fallos únicos

Con cobertura y valores cubiertos llega la montaña de crashes: en herramientas de Linux es habitual alcanzar millones. Revisarlos a mano en GDB llevaría años. El módulo de triage reduce la montaña a los fallos únicos mediante tres estrategias:

  1. Address Sanitizer: ejecutar con red zones de detección de corrupción de memoria, parsear el reporte del sanitizer y la backtrace, y agrupar. De 509 crashes puede quedar un informe HTML con 7 únicos: sanitizer usado, tipo de fallo (segmentation fault, use-after-free de tipo write), frames diferenciadores de la call stack — porque una misma vulnerabilidad puede ser alcanzada por varios paths —, cantidad de crashes que corresponden a cada uno y enlaces a los ficheros.
  2. GDB en memoria real: los sanitizers modifican la memoria del proceso y no siempre reproducen el fallo tal como lo sufriría un usuario. Ejecutar bajo GDB permite ver registros, variables, metadatos del heap y threads sin instrumentación añadida.
  3. Patterns sin crash: no todo fallo revienta el programa. En Java o Python no hay segmentation faults, y un bypass de autenticación puede no romper nada. Se buscan entonces salidas de jemalloc o el asignador del sistema ("invalid pointer", "double free or corruption"), warnings, mensajes de logging sospechosos y errores lógicos.

Democratisar el fuzzing: campañas, AutoBuild y profiles

El framework existe porque el fuzzing, conceptualmente simple, es en la práctica muy complejo de arrancar: compilar con muchos flags, escribir harnesses, conocer el toolchain. Tres piezas lo bajan a tierra:

  • Campañas preconfiguradas: frconsole list muestra proyectos listos para fuzzear (los primeros, unos 100) e install descarga el código, lo compila en paralelo y deja todo preparado en unos 20 segundos, con varios escenarios de compilación para distintos engines. Cada proyecto tiene su build.sh y su link de descarga; la base de datos es colaborativa.
  • AutoBuild: para proyectos fuera de la lista, un sistema experto —"500 if-else", nada de IA— que intenta compilar e instrumentar automáticamente cualquier proyecto C/C++ que use configure/make, meson o cmake.
  • Profiles: escalar a las CPUs actuales de 96-128 cores con LibFuzzer colapsa a partir de 8-16 procesos, y AFL++ exige dominar un mar de opciones (master/slave, mutaciones binarias o ASCII, trimming, sanitizers, power schedules, MOPT). Los profiles codifican esas decisiones como bits — al estilo de los permisos de archivos en Linux — en códigos como 333, y el framework analiza la máquina, lanza todos los procesos posibles y configura el multiprocessing solo. Un comando basta: frconsole fuzz <campaign> -p 333 <cores>.

Resultados y camino por delante

Un año de uso intensivo sobre el ecosistema Ubuntu/GNOME produjo resultados concretos:

Proyecto Resultados
Evince Más de 10 vulnerabilidades, incluyendo CVE-2025-53367: ejecución remota de un clic abriendo un PDF, con exploit funcional con todas las mitigaciones activas (stack canaries, RELRO y demás)
GStreamer ~30 vulnerabilidades, algunas críticas; el framework multimedia de Ubuntu (Totem, previsualizaciones de iconos) queda a un function pointer overwrite del RCE en varios casos
LibArchive Un fallo grave en archivos RAR, detalles pendientes de divulgación

El efecto de la IA sobre el flujo de trabajo es brutal: ya no hacen falta diccionarios ni gramáticas — "¿para qué necesito una gramática si tengo el GPT haciéndome un input case de muerte?" —, y tareas que consumían una semana (escribir un harness o una gramática) se resuelven solas. Es hacer lo mismo, pero mucho más rápido.

En el radar del proyecto: módulo de Docker para ejecutar en contenedores locales o en la nube, interfaz REST además de la consola, explorar el kernel de Linux (drivers, Bluetooth, software de red) donde hoy reina syzkaller, y un engine propio — ULI Engine (Universal Language Interface) — para dejar de depender de los cambios de diseño de AFL++ o LibFuzzer, con soporte para Java, JavaScript y Python además de C/C++.

Sobre los caminos no tomados: la ejecución simbólica sigue siendo impracticable en software real — con call stacks de 35 llamadas la explosión de estados es intratable —, y el siguiente salto natural es agentic: dar al módulo de triage acceso a GDB mediante un agente que ejecute comandos y analice resultados por sí mismo, un experimento ya en marcha que promete.

Técnicas y herramientas mencionadas

  • FRFuzz: framework open source (C++, AGPL v3) de fuzzing asistido por IA; consola frconsole con campañas, triage y multiprocessing automático.
  • Plunger: módulo de FRFuzz que detecta atascos del fuzzer y genera corpus con LLMs para cubrir líneas y funciones no ejecutadas (traza LCOV).
  • Telescope: módulo de value coverage de FRFuzz, implementado como LLVM pass, que cubre rangos de valores de variables críticas.
  • LLVM: infraestructura de compiladores; el pass de value coverage requiere versión 14 o superior.
  • AFL++ / LibFuzzer: fuzzing engines soportados; AFL++ con cmplog, power schedules, MOPT y multiprocessing master/slave.
  • Address Sanitizer (ASAN): detector de corrupción de memoria con red zones; base de la agrupación de crashes en el triage.
  • GDB: depurador usado en la segunda fase del triage para reproducir fallos en memoria sin instrumentación.
  • YARA: pattern matching mínimo para validar que la salida de la LLM se parece al formato esperado y descartar alucinaciones.
  • AutoBuild: sistema experto de FRFuzz (configure/make, meson, cmake) que compila e instrumenta proyectos automáticamente.
  • ULI Engine: engine propio en desarrollo de FRFuzz, con soporte previsto para Java, JavaScript y Python.
  • Evince / GStreamer / LibArchive: proyectos donde el framework encontró más de 50 zero-days en un año.

Conclusiones

  • El fuzzing encuentra la gran mayoría de los zero-days de software crítico, y su barrera real no es conceptual sino operativa: compilar, instrumentar, triagear. FRFuzz ataca exactamente ahí.
  • Las LLMs encajan de forma natural en el ciclo del fuzzer: generan corpus que desatascan la cobertura (Plunger), corrigen offsets de formatos complejos como PDF, y eliminan la necesidad de diccionarios y gramáticas — siempre que se valide su salida con reglas YARA mínimas contra alucinaciones.
  • Cobertura de código 100% no es seguridad: el value coverage dirigido (Telescope) y el triage automatizado de millones de crashes son complementos obligatorios para encontrar los fallos que la métrica no ve.
  • El resultado práctico — 50+ zero-days en un año, incluyendo RCE de un clic en el visor de PDF por defecto de Ubuntu — confirma que automatizar el proceso, no solo el motor, es donde está la ganancia.
