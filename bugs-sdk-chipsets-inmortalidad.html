Bugs de SDK que no mueren: la inmortalidad de las vulnerabilidades heredadas de chipsets

Fuente: «DEF CON 33 - What is Dead May Never Die: The Immortality of SDK Bugs - Richard Lawshae» · ver el video original

Resumen

Los chipsets de red —Wi-Fi, módems, set-top boxes— llegan al mercado acompañados de un SDK: el paquete de aplicaciones, drivers, scripts, toolchains y código de ejemplo que permite a un fabricante integrar el chip en sus productos. Ese SDK transporta servicios HTTP, UPnP, SSH y protocolos propietarios que terminan corriendo en dispositivos de decenas de marcas, muchas veces sin que el fabricante final lo sepa. El resultado es una superficie de ataque que sobrevive a cambios de dueño, a descontinuaciones y a una década de parches: un bug en el SDK de un chipset es potencialmente un bug en todo el install base de ese chip.

La evidencia más contundente: una vulnerabilidad en la implementación UPnP de Realtek descubierta en 2014 entró recién al catálogo CISA KEV unos diez años después, porque seguía siendo explotada activamente. Qué está muerto no muere nunca.

Qué es un SDK de chipset y por qué concentra riesgo

Un SDK de chipset es realmente un system development kit: todo lo necesario para integrar el chip en un ecosistema de terceros. Incluye componentes estándar (servicios SSH, HTTP) y no estándar (protocolos propietarios, RPC). Los chipsets modernos son sistemas completos en un chip, y los fabricantes de chips necesitan minimizar el tiempo de integración de sus clientes para vender más silicio.

Ese modelo genera tres patrones de falla recurrentes:

  1. Servicios desconocidos en producción. El dispositivo integra el chip y el SDK trae consigo servicios que nadie auditó ni documentó. En una auditoría del Oculus se descubrió un servicio UDP que el equipo no sabía que existía; una secuencia específica de paquetes bastaba para tirar el dispositivo offline. La divulgación tuvo que hacerse ante el fabricante del chipset móvil, porque ni siquiera era código del dueño del producto.
  2. Código de ejemplo en producción. El código de demostración del SDK nunca está pensado para producción, pero es el camino fácil de integración: sin auditoría, sin hardening, directo al firmware.
  3. Dependencias desactualizadas. Los SDK arrastran librerías que requieren seguimiento individual de CVEs; algunos proyectos open source se bifurcan, se modifican y jamás absorben las actualizaciones del original.

Cambios de dueño y copia-pega: por qué el bug es inmortal

Las líneas de chipset cambian de manos constantemente. Broadcom es en origen Avago, que compró Infineon en 2008, compró Broadcom en 2015 y adoptó su nombre; en 2016 Cypress adquirió el portafolio IoT de Broadcom (incluido el SDK WICED); en 2017 Broadcom compró Brocade. Cada adquisición deja a la nueva dueña sosteniendo un producto que no desarrolló, apoyándose en los mismos SDK heredados.

Dentro de esos SDK hay patrones que multiplican el impacto de cada bug:

  • Servicios propietarios copiados entre versiones. No todos los chips usan el mismo SDK, pero los servicios escritos por el fabricante se copian y pegan en cada versión. Un fallo allí replica idéntico en toda la línea de producto.
  • Command injection multi-arquitectura. Un SDK que sirve a varias arquitecturas, dispositivos y layouts de memoria convierte una sola inyección de comandos en explotación de todo el install base. Es la clase de bug favorita de los autores de botnets por exactamente esa razón.
  • Install base disperso e irrecuperable. Cuando el bug sale a la luz, el SDK ya está "esparcido al viento" entre decenas de vendors: no hay forma de volver a meter el genio en el tubo de pasta de dientes.

Superficies de ataque frecuentes en chipsets de red

En los SDK de Broadcom y familia, la superficie HTTP típica es un cruce de mini_httpd, mini_http y GoAhead (este último aparece en muchísimos SDKs del mercado), y la implementación UPnP propia es históricamente muy defectuosa —con evidencia de derivación del código de Realtek. El SDK WICED, hoy bajo Cypress, comparte ese ADN. MediaTek y Microchip presentan patrones similares, y el código fuente de varios SDKs es localizable en repositorios públicos, material de partida directo para investigación ofensiva.

El caso fundacional del análisis es Realtek: la implementación UPnP defectuosa hallada en 2014 siguió explotándose durante años hasta ganar un lugar en la lista CISA KEV una década después. El bug "viejo" nunca murió porque el install base heredado nunca se actualizó.

Otro ejemplo ilustrativo es QCA (Qualcomm Atheros, antes Quantenna), usada por AT&T en sus set-top boxes y módems. Su servicio QCS API expone cientos de comandos de configuración Wi-Fi y, sobre él, un servicio RPC que permite ejecutar esos comandos remotamente —una combinación de superficie de administración completa y accesible por red.

Técnicas y herramientas mencionadas

  • SDK de chipset (system development kit): bundle de aplicaciones, drivers, scripts, toolchains y código de ejemplo que define la superficie de ataque heredada del chip.
  • mini_httpd / mini_http / GoAhead: servidores HTTP embebidos recurrentes en SDKs de Wi-Fi y routers.
  • UPnP propietario (Broadcom/Cypress, Realtek): implementaciones defectuosas, con derivación documentada entre fabricantes; el caso Realtek 2014 llegó a CISA KEV ~10 años después.
  • QCS API + RPC (Qualcomm Atheros/Quantenna): cientos de comandos de configuración Wi-Fi ejecutables remotamente vía RPC en set-top boxes y módems de AT&T.
  • Command injection: vector de explotación masiva cuando un SDK abarca múltiples arquitecturas; objetivo predilecto de botnets.
  • CISA KEV: catálogo de vulnerabilidades explotadas activamente, referencia de longevidad de bugs heredados.

Conclusiones

  • El bug de un SDK de chipset no es un bug de un producto: es un bug de toda la flota de dispositivos que integraron ese chip, a menudo sin que los fabricantes conozcan los servicios involucrados.
  • Las adquisiciones y los copia-pega entre versiones de SDK garantizan que el código vulnerable sobreviva a cambios de dueño, nombres de marca y generaciones de producto.
  • Código de ejemplo sin auditar, dependencias bifurcadas sin actualizar y servicios propietarios desconocidos son los tres proveedores habituales de superficie de ataque en chipsets de red.
  • Una vulnerabilidad puede seguir explotándose activamente una década después de su descubrimiento; para investigación ofensiva y defensa, el mapa de SDKs vigentes importa más que la frescura del CVE.
