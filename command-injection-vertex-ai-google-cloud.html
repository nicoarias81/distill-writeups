Command injection en Vertex AI: cazar una clase de fallo en Google Cloud

Fuente: «Hunting in Google Cloud: Command injection in Vertex AI - Valentino Massaro» · ver el video original

Resumen

Valentino Massaro se especializa en encontrar fallos en la inteligencia artificial de Google, y de tanto en tanto baja a Google Cloud. Su método, tal como lo contó, arranca definiendo una misión concreta — "quiero encontrar una inyección de comandos en Google Cloud" —, con un plazo y un objetivo de impacto; ahí se pone a leer reportes antiguos de esa clase exacta de vulnerabilidad hasta entender los patrones, y recién entonces empieza a cazar.

El resultado de esta misión fue una inyección de comandos en Vertex AI Studio, reportada, validada y pagada como S2 (por requerir interacción de usuario). El recorrido del análisis: el programa de recompensas de Google Cloud, reportes históricos de command injection, el fallo paso a paso, y consejos para quien quiera intentarlo.

El programa: Google Cloud VRP

El Vulnerability Reward Program de Google Cloud es complejo y sus reglas son largas, pero la tabla de pagos resume bien qué es lo que más importa:

  • Fallos críticos (RCE en producción, cross-tenant): hasta 100.000 USD, con bonus en eventos.
  • Lectura y modificación de datos en proyectos: hasta 20.000 USD.
  • Secure by Default (menor impacto o más condiciones/interacción): pagan menos.
  • Ejecución de código en el cliente (XSS): hasta 20.000 USD.
  • Otros fallos: hasta 15.000 USD.

¿Hay fallos en Google Cloud? La respuesta corta: sí. Puede ser difícil y puede tomar tiempo, pero todo sistema tiene fallos; lo que pasa es que se publican menos reportes, y eso da la impresión de que no hay nada.

Reportes antiguos: el patrón de Cloud Shell

Como la misión era inyección de comandos, Valentino buscó todos los reportes históricos de esa clase y notó que en Cloud Shell eran muy comunes:

  • 2016: el parámetro project aceptaba un punto y coma seguido de un comando; al cargar el enlace, la consola de Cloud Shell ejecutaba código en la instancia de la víctima. Simple y con bastante impacto.
  • 2021: la feature para clonar repositorios incluía un valor de forma insegura; payload distinto, mismo concepto.
  • 2022: el mismo parámetro project, pero esta vez inyectando código Python — internamente se parseaba de forma insegura y eso terminaba en ejecución de código.

Después de leer esos tres, la conclusión fue directa: seguramente hay mitigaciones, pero tienen que existir más variantes. Y Vertex AI era un producto nuevo — y los productos nuevos suelen tener problemas de seguridad.

El fallo: de texto controlado por el usuario a código generado

En Vertex AI Studio había un chat para probar Gemini con prompts. Una feature clave, construir con código, tomaba ese prompt y lo convertía en código replicante — Python, Node, cURL — para usar las APIs de Google. Ecuación inmediata: texto controlado por el usuario + generación de código = inyección de comandos.

La búsqueda del hueco:

  1. El texto del prompt se incluía de forma segura (triple comilla doble en Python). Sin hueco ahí.
  2. Pero el prompt admite contenido que no es texto: imágenes con enlaces.
  3. Al insertar una comilla doble en la URL de la imagen, el código generado se rompía y permitía inyectar código arbitrario — en Python, en Node, en cURL y en otros lenguajes. La imagen se embebe vía fromUri en vez de fromText, y ahí entra la comilla.
  4. Incluso se podían insertar saltos de línea, lo que hacía la explotación mucho más versátil: control total del código generado.
  5. Siguiente paso lógico: un polyglot con instrucciones de command injection en varios lenguajes a la vez, para un ataque genérico que funcione sea cual sea el lenguaje de salida.

El salto de impacto: Prompt Management

Con la inyección sola, el escenario era flojo: la víctima tiene que ver el contenido malicioso en el chat, copiarlo y pegarlo. Demasiada fricción. La solución llegó con Prompt Management, una feature para importar y exportar archivos de prompts en JSON, con parámetros y variables. Ahora el vector se distribuye: se arma un prompt.json con la inyección, se comparte masivamente, y las víctimas lo importan sin revisar.

El escenario de ataque quedó definido así: el archivo con la inyección se distribuye por Internet, las víctimas lo importan vía Prompt Management en Vertex AI, y la feature de generación de código inyecta el comando en cualquiera de los lenguajes de salida. Bonus que llegó solo: justo al reportar, se agregaron features nuevas — deploy as app (Cloud Run) y notebook de Google Colab — que habrían multiplicado el impacto, al correr el código inyectado con bastantes privilegios.

Reporte, triage y pago

El reporte se armó con escenario claro: requisitos, lo que consigue el atacante, diagrama del flujo. La respuesta inicial fue el clásico "nice catch"; después de que el equipo lo revisó con detenimiento, llegó el bounty, clasificado como S2 por la interacción de usuario requerida. Proceso cerrado.

Consejos para cazar en Google

  • Definir una misión: una clase de fallo, un producto, un plazo. "Quiero una command injection en Google Cloud" rinde más que vagar por la superficie.
  • Especializarse en un producto y pegarle por meses o años: saber tanto del producto que si el viernes sale una feature, el sábado ya está testeada. Leer todo el JavaScript.
  • Leer reportes antiguos: para Google VRP existe un repositorio público en GitHub con los reportes; es la mina de patrones.
  • Entender el threat model: saber qué buscar antes de buscar. ¿Dónde está la data sensible? ¿Qué productos son más sensibles que otros?
  • Demostrar impacto y escribir buen reporte: acelera el triage y aumenta el éxito. La página oficial de Google VRP explica exactamente el formato que esperan.

En las preguntas quedó una nota práctica: para saber si el código corre en un sandbox o en una instancia real, se puede consultar la metadata de Google Cloud y revisar con qué service account corre la instancia — la forma directa de entender el contexto de ejecución antes de reportar.

Conclusiones

  • Google Cloud tiene fallos, y las clases clásicas — como la inyección de comandos — reaparecen en cada producto nuevo; los reportes históricos son el mejor mapa para encontrar las variantes.
  • Vertex AI Studio concatenaba texto controlado por el usuario en código generado (Python, Node, cURL): la inyección entró por la URL de una imagen (fromUri), no por el texto del prompt, que estaba bien escapado.
  • El salto de impacto vino de cambiar el vector de entrega: de copiar-pegar en el chat a un archivo JSON de prompt importable y distribuible masivamente.
  • Un buen reporte de Google VRP necesita escenario de ataque explícito: requisitos, impacto y diagrama; la clasificación S2 reflejó la interacción de usuario.
  • El método gana por especialización: un producto, una clase de fallo, años de profundidad, y testear features nuevas apenas salen.
