Regex rotas: cuando el patrón de validación abre la puerta

Fuente: «DEF CON 33 - Regex For Hackers - Adam 'BuildHackSecure' Langley, Ben 'nahamsec' Sadeghipour» · ver el video original

Resumen

Las expresiones regulares están por todas partes: validan correos, dominios, orígenes de postMessage, encabezados CORS y URLs antes de un redirect. El problema es que la mayoría de esos patrones están mal escritos, y un patrón mal escrito no es solo un bug estético: es una puerta de entrada. Un punto sin escapar convierte trusted.com en xtrusted.com; un ancla $ ausente permite colgar el dominio legítimo de un subdominio atacante; un ^ faltante deja pasar URLs enteras donde el patrón solo debería coincidir con el inicio. Regex es, según Adam Langley y Ben Sadeghipour —cuya experiencia suma más de 1,8 millones de dólares en recompensas de bug bounty—, causa raíz de muchas vulnerabilidades client-side y también de varias server-side.

Este artículo recorre los fundamentos que deciden si un patrón es seguro o no, los cuatro errores clásicos que se repiten en código real (con sus bypasses concretos en postMessage, open redirects, CORS y SSRF), y el uso ofensivo de regex sobre GitHub: encontrar subdominios ocultos tras certificados wildcard, recuperar rutas de API filtradas, extraer credenciales de heap dumps y construir wordlists propias. Todo el material proviene del taller de DEF CON 33 impartido por ambos, cofundadores de la plataforma de formación Hacking Hub.

Los fundamentos que deciden todo

Regex es un lenguaje de patrones de búsqueda: localiza, confirma y extrae porciones concretas de texto. Funciona como una máquina de estados —cada regla avanza al siguiente paso y, si falla, el intento retrocede y prueba en otra posición—. Antes de hablar de vulnerabilidades conviene fijar las piezas que luego se explotan:

  • Literales y word boundaries. Buscar computer también encuentra supercomputer. Envolviendo la palabra con \b se exige que no haya letras pegadas a los lados, eliminando falsos positivos.
  • Anclas. ^ obliga a que el string empiece exactamente ahí (^https://); $ obliga a que termine ahí y nada más. Un dominio de validación sin $ al final coincide con www.trusted.com.attacker.com.
  • El punto es un wildcard. En regex, . significa cualquier carácter (salvo salto de línea). Es el detalle que más desarrolladores tumba: para un punto literal hay que escribir \..
  • Conjuntos y rangos de caracteres. [abc] acepta una de esas letras; [^abc] invierte la regla; [a-zA-Z0-9] combina rangos mayúsculas, minúsculas y dígitos.
  • Cuantificadores. + (uno o más), ? (cero o uno, como la s de https?), {16} (exactamente dieciséis), {16,19} (rango, ideal para números de tarjeta de 16 a 19 dígitos), * (cero o más, útil para espacios opcionales o tabs de relleno).
  • Atajos. \d (dígito), \s (cualquier espacio o tabulación), \w (letras, dígitos y guion bajo); sus versiones en mayúscula (\D, \S, \W) niegan la clase.
  • Grupos y alternancia. Los paréntesis agrupan para repetir un bloque ((\d{4}\s*){3} en vez de repetirlo a mano) o para extraer la porción que interesa del resultado; la barra vertical (|) alterna opciones como espacio o guion dentro del patrón de una tarjeta.

Con estas piezas se construyen patrones reales: un código postal tipo letra + dos dígitos + espacio + dígito + dos letras con $ al final, o un detector de tarjetas que tolera separadores variables.

Los cuatro errores clásicos en un patrón

Casi todos los bypasses que se ven en código real se reducen a cuatro descuidos, frecuentemente combinados:

  1. Punto sin escapar. El patrón www.trusted.com acepta www.xtrusted.com: basta registrar ese dominio para pasar cualquier validación de origen o de redirect.
  2. Falta el ancla final $. Sin ella, www.trusted.com valida también www.trusted.com.attacker.com, o un dominio legítimo usado como query string de otro.
  3. Falta el ancla inicial ^. El patrón coincide en medio del string, así que una URL completa —o un redirect encadenado— pasa el filtro aunque no empiece por lo esperado.
  4. Subdominios demasiado laxos. Aceptar cualquier subdominio (.*\.trusted\.com) incluye entornos de prueba tipo qaprod.1 con código viejo y vulnerable; conviene restringir a [a-zA-Z0-9_]+ o, mejor, listar explícitamente los subdominios permitidos con un grupo alternado ((admin|www|download)).

De patrón débil a toma de cuenta

flowchart LR
    A["Patrón débil: punto sin escapar y sin ancla final"] --> B["Dominio atacante: www.xtrusted.com o trusted.com.attacker.com"]
    B --> C["La validación de origen/URL da el visto bueno"]
    C --> D["El navegador entrega datos o ejecuta el redirect"]
    D --> E["XSS, robo de cookies, token OAuth o cuenta secuestrada"]

Las consecuencias concretas se ven en cuatro escenarios recurrentes:

  • postMessage sin origen verificado. Dos ventanas del navegador se comunican con este mecanismo (por ejemplo, un popup de login que devuelve datos a la página madre). Si el listener valida el origen con un regex, el punto sin escapar y la ausencia de $ permiten que www.trusted.com.attacker.com pase el control; el payload devuelto (por ejemplo, un <img> con onerror en el error del evento) se pinta en la página y se convierte en XSS con robo de cookies y toma de cuentas. La corrección combina $ al final y \. en cada punto.
  • Open redirect con cuenta secuestrada. En un caso real reportado por Sadeghipour, la URL aceptaba sitio, aplicación y path, pero el path no exigía empezar por /; bastó añadir .evil.com al path para redirigir a un dominio propio. El redirect capturaba un token OAuth tras el login, así que no fue un redirect simple sino una toma de cuenta completa: 14.000 dólares de recompensa.
  • CORS mal filtrado. El pre-flight de CORS envía el Origin al servidor, que decide con un regex si devuelve Access-Control-Allow-Origin (y credenciales, hoy permitidas casi solo por Chrome). Con las mismas fallas, un dominio atacante con una x intercalada o un subdominio tomado puede leer respuestas autenticadas de la API víctima.
  • SSRF vía validación de dominio. Un servicio que genera el PDF de un perfil de LinkedIn acepta un dominio; el punto sin escapar permite xlinkedin.com con un registro DNS apuntando a localhost, y la falta de ^ permite pasar una URL completa cuyo redirect legítimo de LinkedIn termina consultando 127.0.0.1 o los metadatos de la nube. El patrón corregido queda como ^https://linkedin\.com/in/\w+, con el path restringido a \w.

GitHub como fuente de ataque con regex

Para bug bounty, Sadeghipour dejó atrás los descubridores de assets tradicionales (Subfinder, Amass, crt.sh, C99) porque todos los demás los usan y porque con regex sobre GitHub se llega a sitios que ninguna base de assets conoce. Algunos usos que rinden dinero:

  • Subdominios tras un wildcard. Cuando un certificado wildcard (*.corp.site.com) oculta lo que hay detrás, buscar en GitHub con patrones que combinan la cadena del dominio con contexto de código revela subdominios que habría que fuerza bruta a ciegas.
  • Filtrado por palabras clave con contexto. Añadir api, dev o el nombre de la app al patrón no solo encuentra endpoints: muestra cómo se usan, qué rutas exponen y qué datos filtran los desarrolladores.
  • Código fuente interno filtrado. En un programa público, un compañero tenía un SSRF interno imposible de probar fuera de AWS o GCP. Buscando el dominio con regex en GitHub apareció una instancia de JFrog Artifactory con el código fuente completo expuesto: recompensa de 5.000 a 6.000 dólares que ninguna herramienta de asset discovery tenía indexada.
  • Rutas de API imposibles de fuerza bruta. En un programa holandés que exigía identidad local para registrarse, el regex encontrado en GitHub entregó tanto las rutas de la API como el esquema de usernames (inicial del nombre + apellido + año de nacimiento), reconstruible con apellidos neerlandeses comunes: 5.000 dólares. En otro programa, unas rutas obscuras de cinco segmentos (región-app-entorno-país) filtradas en GitHub llevaron a instancias de Spring Boot Actuator con heap dump abiertos: cuatro hallazgos a 3.000 dólares cada uno en un par de horas.
  • Instancias de GraphQL. Un patrón que cruza cualquier dominio objetivo (por ejemplo netflix.com, ford.com) con graphql localiza endpoints de GraphQL dispersos por todo el ecosistema de una empresa.

El consejo central: cuando un endpoint aleatorio no entrega rutas y la fuerza bruta no avanza, casi seguro alguien filtró esas rutas en GitHub —solo hace falta un regex bueno para encontrarlas—.

Secretos y revisión de código a golpe de patrón

Los heap dumps de Actuator son binarios ilegibles; pasarlos por strings y grep busca la palabra password, pero devuelve ruido y, según el propio Sadeghipour tras revisar sus dumps antiguos al armar el curso, deja pasar muchísima información. Con regex se puede extraer todo lo que termina en un signo igual (parámetros), o cadenas base64 que acaban en == (posibles contraseñas), o tokens con formato conocido: los JWT empiezan con eyJ seguido de caracteres base64url y un punto; las claves de AWS tienen su propia forma reconocible. Buscando eyJ junto a dominios concretos en GitHub aparecen tokens publicados por descuido —incluso uno colgado en un subdominio de investigación de Netflix—.

En revisión de código, los patrones son igual de rentables. En PHP, un echo que imprime directamente variables de GET o POST sin validación delata XSS inminente; un system() que recibe entrada del usuario apunta a RCE. También hay regex para buscar regexes: detectar los patrones de los paquetes de expresiones regulares de PHP, JavaScript y Python para auditarlos a mano, encontrar strings de basic auth (base64 terminado en =), o localizar web shells subidas a GitHub —como una que apareció buscando system( combinado con $_GET o $_POST—. Con el operador AND en mayúsculas (obligatorio en la búsqueda de GitHub) se puede acotar a ecosistemas concretos, por ejemplo plugins de WordPress en programas tipo WordFence. Y las grandes empresas open-sourcean sus frameworks internos y herramientas empresariales desplegables en una EC2 propia: el código está en línea, listo para revisarse en busca de vulnerabilidades.

Del patrón a la herramienta

Regex también es la materia prima de herramientas propias. Creatures of Habit, una de las utilidades creadas por Langley, recorre GitHub incrementando por cada paquete, descarga extensiones web y extrae las rutas definidas por frameworks concretos —Flask, Laravel, ASP.NET, Ruby on Rails, Go— para fabricar wordlists de rutas reales que luego sirven contra otros dominios. La misma idea se aplica a parámetros: iterando código PHP se extraen los strings centrales de GET y POST, de cabeceras HTTP y de métodos, generando wordlists de parámetros que los desarrolladores reutilizan una y otra vez en query strings, bodies y paths.

Técnicas y herramientas mencionadas

  • Regex (expresiones regulares) — lenguaje de patrones de búsqueda; causa raíz frecuente de vulnerabilidades client-side y server-side.
  • postMessage — canal de comunicación entre ventanas del navegador; su validación de origin por regex es objetivo clásico de bypass.
  • Open redirect / toma de cuenta vía token OAuth — redirect controlado que captura tokens de sesión; caso real de 14.000 dólares.
  • CORS y pre-flight — el Origin validado por regex decide si el servidor expone respuestas autenticadas a terceros.
  • SSRF con DNS controlado — dominios propios apuntando a localhost o a metadatos de nube para saltarse validaciones de dominio.
  • Búsqueda con regex en GitHub — sustituto ofensivo de Subfinder, Amass, crt.sh y C99 para asset discovery y discovery de rutas.
  • Spring Boot Actuator / heap dump — endpoint de diagnóstico Java cuyo dump de memoria contiene variables de entorno, credenciales y requests HTTP completos.
  • strings + grep con regex — extracción de secretos (parámetros, base64, JWT eyJ, claves AWS) de dumps binarios.
  • Revisión de código con patrones — detección de echo de entrada sin validar (XSS), system() con input de usuario (RCE) y basic auth en PHP.
  • Creatures of Habit — herramienta que genera wordlists de rutas y parámetros recorriendo GitHub (Flask, Laravel, ASP.NET, Rails, Go).
  • Hacking Hub — plataforma de formación y CTFs cofundada por los autores del taller.

Conclusiones

  • La diferencia entre un regex seguro y uno vulnerable casi siempre se reduce a cuatro detalles: escapar los puntos (\.), anclar el inicio (^), anclar el final ($) y restringir los subdominios aceptados en lugar de usar wildcards.
  • Un patrón débil no es un fallo teórico: convierte validaciones de postMessage, CORS, open redirects y SSRF en XSS, lectura de datos autenticados, robo de tokens y acceso a localhost.
  • GitHub es hoy una fuente de reconocimiento superior a las herramientas tradicionales de asset discovery: subdominios tras wildcards, rutas de API, código fuente interno y credenciales filtradas se recuperan con buenos patrones, incluidos JWT (eyJ) y claves de AWS.
  • Wordlists propias construidas con regex sobre código real —rutas por framework, parámetros, cabeceras— superan a las genéricas, porque reflejan lo que los desarrolladores efectivamente escriben y reutilizan.
