Rootkits que viven debajo del sistema operativo: detección en tablas ACPI

Fuente: «ACPI Rootkit Detection Tool - Manuel Gil Cernich - Ekoparty 2025» · ver el video original

Resumen

Cuando una máquina está comprometida, la mayoría de las herramientas de detección mira el sistema operativo: procesos, servicios, drivers, memoria. Pero existe una capa por debajo, donde el malware puede persistir incluso después de formatear el disco y reinstalar todo: las tablas ACPI, el mecanismo que el firmware le entrega al sistema operativo al arrancar y que contiene código ejecutable. Un rootkit que se esconde ahí sobrevive a la reinstalación del sistema, arranca antes que cualquier antivirus y opera con un nivel de privilegio que pocas soluciones de endpoint alcanzan a inspeccionar.

La propuesta es una herramienta de detección de rootkits en ACPI, construida en Rust, que permite volcar las tablas del firmware, analizar su contenido y descubrir modificaciones maliciosas — desde hooks hasta código AML inyectado. El proyecto es open source y funciona tanto en Windows como en Linux, con acceso directo al firmware sin depender de herramientas del proveedor.

Este artículo explica qué es ACPI, por qué es un vector de persistencia tan potente, cómo funciona la herramienta de detección y qué se puede hacer para auditar los propios equipos.

Qué es ACPI y por qué importa para la seguridad

ACPI (Advanced Configuration and Power Interface) es el estándar que define cómo el sistema operativo descubre y configura el hardware, y cómo gestiona la energía. No es un driver ni un módulo del kernel: son tablas de datos que el firmware (BIOS/UEFI) expone al arrancar, y que el sistema operativo consume casi sin cuestionarlas.

El punto crítico es que dentro de esas tablas no solo hay datos: hay código. La especificación define AML (ACPI Machine Language), un bytecode que el kernel interpreta y ejecuta en contexto de kernel, con privilegios elevados. Ahí viven los métodos que controlan eventos de hardware, transiciones de estado de energía (S0, S3, S5), botones, térmica, batería. El sistema operativo confía ciegamente en este bytecode: nadie valida que lo que dice la tabla del fabricante sea lo mismo que la tabla que llega tras una actualización de BIOS, y menos aún que no tenga lógica maliciosa.

Eso convierte a ACPI en un lugar perfecto para un rootkit: persistencia a nivel firmware, ejecución con privilegios de kernel antes de que el sistema operativo haga su primer análisis, y sobrevivencia a reinstalaciones. El antecedente más conocido es LoJax, el rootkit UEFI descubierto por ESET en 2018, que usaba un módulo malicioso en tablas ACPI para inyectar un agente en Windows en cada arranque.

Cómo funciona la herramienta de detección

La herramienta, escrita en Rust, recorre el flujo completo de análisis de ACPI. Primero localiza el RSDP (Root System Description Pointer) — en BIOS legacy buscando la firma en el área de memoria de la EBDA y en UEFI leyéndolo desde la configuración de EFI — y desde ahí navega la estructura de tablas: RSDT/XSDT, y las tablas que colgan de ellas (FADT, MADT, HPET, entre otras). El foco principal está en las DSDT y SSDT, que son las que contienen el AML ejecutable.

Sobre esas tablas aplica varias estrategias de detección:

  • Validación de firmas y checksums: cada tabla ACPI lleva un checksum; un atacante que modifica una tabla y no recalcula bien el checksum deja una anomalía detectable.
  • Detección de métodos sospechosos: análisis del AML buscando patrones típicos de malware — operaciones con puertos de E/S, accesos a memoria física, operaciones sobre la región de la BIOS (WPR0 y similares), llamadas a métodos como _PIC o \_SB usados fuera de contexto, y firmas conocidas de rootkits públicos.
  • Comparación con referencias: contraste de las tablas volcadas contra versiones conocidas del fabricante del equipo, para detectar diferencias que no correspondan a una actualización legítima.

La salida es un reporte de las tablas encontradas con su contenido y las anomalías detectadas, lo que permite al analista decidir si lo que hay en la máquina es legítimo o fue tocado.

El vector de ataque: cómo se instala un rootkit ACPI

Para que un rootkit ACPI exista, alguien primero tiene que escribir en el firmware. Las vías típicas: explotación de vulnerabilidades en la actualización de BIOS (muchos vendors firman mal sus actualizadores o permiten flashear regiones protegidas), malware con privilegios de kernel que abusa de interfaces como \_-WAK o de primitivas de escritura en NVRAM, y en el peor caso, acceso físico al equipo. Una vez en el firmware, el atacante modifica la DSDT o inyecta una SSDT adicional con su código AML, recalcula los checksums y listo: el rootkit se ejecuta en cada arranque.

De ahí la asimetría defensiva: para el atacante basta escribir una vez; para el defensor, la única forma confiable de verificar es volcar y analizar las tablas desde el propio sistema en ejecución — que es exactamente lo que hace la herramienta.

Técnicas y herramientas mencionadas

  • ACPI: estándar de configuración y energía; define las tablas que el firmware entrega al sistema operativo al arrancar.
  • AML (ACPI Machine Language): bytecode dentro de las tablas DSDT/SSDT que el kernel interpreta con privilegios elevados.
  • RSDP / XSDT / RSDT / FADT / MADT: estructura de tablas ACPI que la herramienta navega para llegar al código ejecutable.
  • LoJax: rootkit UEFI (ESET, 2018) que usó ACPI como vector de inyección en cada arranque de Windows.
  • Rust: lenguaje en el que está implementada la herramienta, disponible como proyecto open source.
  • UEFI / BIOS legacy: los dos modos de arranque en los que la herramienta localiza el RSDP.

Conclusiones

  • Las tablas ACPI son una superficie de persistencia que vive debajo del sistema operativo: un rootkit ahí sobrevive al formateo y arranca antes que cualquier defensa de endpoint.
  • El punto débil estructural es la confianza: el kernel ejecuta el AML del firmware sin validarlo, así que la detección depende de herramientas que auditen las tablas activas.
  • La herramienta de detección (open source, en Rust) permite volcar la estructura completa de tablas, validar checksums y buscar patrones AML de rootkits conocidos en Windows y Linux.
  • Auditar el propio firmware debería ser parte del análisis forense de un equipo comprometido: si el disco está limpio pero el rootkit está en la DSDT, el incidente nunca terminó.
